### self-check input rail:声明式入口闸机(Self-Check Input Rail)
**是什么**:NeMo 内置的输入护栏——用户消息进门前,先被填进 `prompts.yml` 的"安检清单"模板(`User message: "{{ user_input }}"`),发给同一个 LLM 回答 Yes/No;`output_parser: is_content_safe` 把自然语言解析成拦/放。Yes → 直接回固定拒答(定义在内置 `flows.v1.co`,可改),意图识别和生成**根本不启动**;No → 放行走原流程。
**解决什么问题**:给入口装上不依赖模型自觉的第一道闸——被拦时用户看到的是闸机的拒答,不是模型的拒答,主流程开销全省。
**我们的办法**:纯 YAML 零 Python——`config/config.yml:10-13` 的 `rails.input.flows` 点名 `self check input`(写几道串几道,按序执行),`prompts.yml` 配判定提示词;`task: self_check_input` 是暗号,写错加载时直接报错。实测:阶段 1 的两条 payload(套 key、卡通 SYSTEM OVERRIDE)全拦,对照组"写一首秋天的诗"正常放行无误伤;安检输出里还能看到安检员的 `<think>` 逐条核对过程。

### 自检的上限 = 主模型自身的安全水平(Self-Check = Same LLM Wearing a Hat)
**是什么**:self-check rail 没有独立检测模型——判定者就是主 LLM 换顶"安检员"帽子再问自己一遍。这与两条已知路线本质不同:llm-guard 是专职分类器(deberta,本地毫秒级),独立 LLM 法官是另起调用、不看对话历史。
**解决什么问题**:定性了这类护栏的天花板——它拦的是"模型自己能看出来的坏";模型看不出来的(如格式伪装注入)它也漏。这是收官对照 llm-guard 三层护栏时的核心论据。
**我们的办法**:安检清单(policy 那十条)是明文提示词、照抄官方 `examples/bots/abc/prompts.yml` 可自行增删——灵活,但责任转移给了你:清单没写到的,闸机就当没看见。
