### compile() 当免费语法门卫(Syntax Gate via compile)

**是什么**:Python 内置函数 `compile(source, filename, mode)`——把源码字符串编译成代码对象但**不执行**;语法有错抛 `SyntaxError`(自带出错行号 `e.lineno`),没错就安静通过。不需要 AI、不需要网络、零成本。
**解决什么问题**:写代码的主要是 AI,而 AI 常生成语法就通不过的代码;没有这道闸,坏代码先落盘污染 workspace,运行时才暴露。把检查提前到"落笔之前",坏代码进不了门,报错带行号、AI 拿到能直接改。
**我们的办法**:`llm_helper.py:17` `verify_code_syntax()`:`compile(code, "<string>", "exec")`,except 时返回 `(False, "第 N 行: ...")`;只对 `.py` 后缀启用,普通文本直接放行。门卫有顺序——先查"在哪写"(workspace 边界),再查"写什么"(语法),反了等于替越界路径白做检查。实测 `def broken(:` 被拦,workspace 自始至终没有 broken.py。

### 能查证的就不用 AI(Deterministic Checks over LLM Judgment)

**是什么**:防御资源分配原则——"有标准答案"的事(语法对不对)交给编译器这类确定性权威,又快又免费;AI 判断只留给"没有标准答案"的事(比如"这段代码意图危险吗")。
**解决什么问题**:防止防御设计上的错配:用 AI 查语法是拿概率性判断干确定性的活(慢、贵、还可能漏),用确定性检查去判断意图则根本办不到。两者各归其位,防线才既可靠又经济。
**我们的办法**:阶段 3 语法门卫用 `compile()`;意图判断("危险吗")明确留到阶段 6 的 LLM 事前审批。与攻防矩阵-0011「确定性的定义」同源:校验基准要选在攻击者能力边界之外、不依赖模型状态。

### verification 三态回执(passed / failed / skipped Verification Field)

**是什么**:write 结果 JSON 里多一个 `verification` 字段,三值:`passed`(查了且过)、`failed`(查了且拦)、`skipped`(非 .py,没查)。
**解决什么问题**:让调用方(将来的 AI)知道这份文件**到底过没过检**,而不是一个含糊的 success——"没查"和"查了通过"在安全语义上完全不同,不区分就会给 AI 错误的信心。
**我们的办法**:对照组实测:合法代码 → `passed`;`def broken(:` → `failed` 且不落盘;`.txt` 普通文本 → `skipped` 不挡路。三态与结构化拒绝(见执行工具-0002)配合,工具结果的全部读者都是 AI。
