### self-check output rail:出口闸机(Self-Check Output Rail)
**是什么**:挂在 `rails.output.flows` 的出口质检——bot 回复生成后、交给用户前,填进 `self_check_output` 清单模板(占位符 `{{ bot_response }}`,入口闸是 `{{ user_input }}` 别抄串),再调同一个 LLM 判 Yes/No;Yes → 用户看到固定拒答、刚才那次生成白干。与入口闸是同一台机器,区别只在检查对象:入口检"用户带来的坏",出口检"bot 自己造出来的坏"(幻觉、违规、编出密钥)。
**解决什么问题**:入口闸管不着已出厂的货——输入完全合法、输出却带密钥的场景(实测 T1"帮我编个 .env 示例")只有出口闸能管,这正是 starter-agent 第三层 llm-guard Sensitive 的位置。
**我们的办法**:挂闸在 `config/config.yml:14-16`,清单在 `config/prompts.yml` 的 `self_check_output` 段。实测:默认十条清单**没有"不得泄露密钥"** → T1 编造的逼真密钥直接出厂;补一条"任何密钥/令牌/密码,编的也不行"→ 立刻拦下。结论:闸机本身是好的,漏的是清单——清单写多全,防护就有多全,责任全在写清单的人。

### 清单路线 vs 模式路线(Semantic Checklist vs Pattern Matching)
**是什么**:输出安检的两种机制路线——self-check 是"读懂语义再对照明文清单"(清单没覆盖的语义就漏);llm-guard Sensitive/Secrets 是按格式/熵识别密钥(`ik-live-` 这种串不管清单写没写都命中)。
**解决什么问题**:定性了 self-check 路线的系统性盲区:防护上限 = 清单覆盖度,默认清单连"密钥"都没有;模式路线则不看语义只认形态,低熵假 key 反而漏(见 0014 战利品配套卡)。两条路线的盲区形状互补。
**我们的办法**:收官对照的核心论据——对照 NeMo 与 llm-guard 三层护栏时,比的是机制(语义清单 vs 模式/熵),不是闸的位置;两者在同一位置(出口)却各有漏法。

### explain() 调用链回放(LLMRails.explain())
**是什么**:NeMo 自带的监控回放——每次 `generate()` 后调 `LLMRails.explain()`,返回对象的 `llm_calls` 列出本次请求实际跑了哪几个 LLM 调用,`llm_calls[i].task` 是任务名(`self_check_input` / `general` / `self_check_output`)。
**为什么重要**:"到底哪道闸拦的"不再是猜的——T2(输入直接带密钥)调用链只有 `['self_check_input']`,证明入口拦的、出口没见到;T1 三段全走,证明出口闸真的检过、真的没拦。没有它,机制验证只能看表面现象。
**我们怎么用**:无参数,目前在一次性验证命令里用;阶段 5 算延迟/token 账单全靠它数调用次数,届时正式进代码。

### 推理模型把自检回答"憋死"(Reasoning Model Truncation → Fail-Closed)
**是什么**:实测坑——MiniMax-M2 的思考链偶尔吃光默认 max_tokens,自检调用返回空,闸机按 fail-closed 当拦截处理。
**解决什么问题**(暴露的问题):安全上"拦错不放过"是对的,但正常请求会被误伤——fail-closed 在"质检员说不出话"时退化成随机拦人;用推理模型当自检法官必须给 prompt 调大 max_tokens(官方建议)。
**我们的办法**:记录在案,阶段 5 算延迟/token 账时一并处理(调大自检 max_tokens);也是"推理模型当 judge"路线特有的成本项,对照 llm-guard 专职小模型时是个论据。
