## 1. 授权矩阵(人 × Agent × 工具 × 资源)

| 人 | Agent | 工具范围 | 授权途径 |
|---|---|---|---|
| divh(运维位) | starter-agent(Python) | 全部 6 个 | `agent#admin` → 经 `deployed_on` 级联继承全部部署工具 |
| bob(只读位) | ts-second-agent(TS) | filesystem-read-file、filesystem-list-dir | 直接 `can_execute` 元组;两工具亦部署于 ts agent |
| 任何其他/匿名 | 任意 | 无 | 无元组即拒绝(fail closed 是 OpenFGA 的免费赠品) |

资源维度:`resource:workspace-notes ← accessible_via — tool:filesystem-read-file`,`can_access` 沿 can_execute 级联——**资源不单独发授权,永远从工具级联**,避免同一权限两处维护。

## 2. 模型(model.fga DSL,与 API JSON 对应见 authz-model.md)

```
model
  schema 1.1

type user

type agent
  relations
    define admin: [user]

type tool
  relations
    define deployed_on: [agent]
    define can_execute: [user] or admin from deployed_on

type resource
  relations
    define accessible_via: [tool]
    define can_access: can_execute from accessible_via
```

四元组靠**三元组级联**表达:agent 维 = 工具上的 `deployed_on` 关系;资源维 = 两级展开。设计红利(实测):运维位加新工具只写一条 `deployed_on`,人侧授权自动继承。

## 3. 为什么鉴权是 PEP,而不是 Prompt

**Prompt 是建议,PEP 是闸门。** 模型(尤其被注入后)会把"你没有权限"当成可以绕过的提示,而不是物理边界;代码闸门则不可协商。本项目的三个 PEP 分工,一句话:**网关管身份,Agent 管会话,server 管出口**:

| 层 | PEP | 问的问题 | 被注入绕得过吗 |
|---|---|---|---|
| 网关 | fga_check 插件(OpenFGA)+ deny_command(出口) | 这个**身份**能用这个工具吗/命令能出网吗 | 不能——调用必经网关,裁决在 Agent 之外 |
| Agent | 任务票 → D4 → LLM 法官(串联闸) | **这一轮任务**授权了什么/这次调用危不危险 | 进程被完全攻破才失守(纵深防御的诚实边界) |
| 数据/出口 | fetch 白名单+凭证策略;microVM PUBLIC | 出得去网吗/碰得了私网吗 | VM 级兜底 |

Prompt 里的"你没有权限"一条都不算——它既不拦截也不留证;PEP 的每次拒绝都带 code、身份归属并落审计。

## 4. 两层授权的粒度分工(票 10 拍板,实证确认)

- **ContextForge 原生 RBAC 管"能看什么"**:团队可见性 + 类别级权限 + virtual server 工具子集;文档明言 "There is no per-tool grant"。本次实证:工具 private 时 bob 目录为 0(可见性先行于一切)。
- **OpenFGA 管"能执行什么"**:四元组细粒度(can_execute/can_access),经自写 `tool_pre_invoke` CPEX 插件在每次调用前 check,False 即 403(FGA_DENIED,带身份归属)。
- 集成顺序课:bob 依次撞户口(email_users 建号)→ 可见性(工具 public)→ RBAC 执行权 → 才轮到 FGA——**认证身份 ≠ 授权身份,可见性先于裁决**。

## 5. 任务级动态收窄(阶段 42)

静态矩阵之外还有时间轴:每轮用户消息签一张 120 秒任务票(scope=本轮工具子集,关键词规则推断),串联闸第零道验票。静态授权答"运维位能用 shell",任务票答"**这一轮**用不用得上 shell"——时间维度的最小权限。

## 6. 已知深化方向(不落地,记录判断)

1. **授权下沉数据层**(对照实验 5-12,lesson 0040):业务数据若升级为多租户/状态机型,应把最后一道闸放进数据 store(权限跟数据声明,生成代码带不走)——当前 workspace 是笔记级数据,未做。
2. **确认门 vs 自动裁决**(对照实验 9-7,复刻 6/13 暂停于 `harness复刻/`):不可逆操作的高危场景可引入"人工确认 token(单次性、绑定参数)"——自动闸(本项目)与确认门是两条路线,分界=误判代价的对称性。
3. **出口白名单的完整形态**:deny_command 黑名单是教学最小闭环;生产应白名单域名+代理强制,与 fetch_server 策略表合并为统一出口策略点。
4. **哈希链外锚**:证据链链头应定期锚定到外部(如签名后交第三方/时间戳服务),否则"截断重造"仍需靠链外手段发现(阶段 44 验证器已报警该形态)。
