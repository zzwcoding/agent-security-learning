# 0015:容器加固 —— 假设里面已沦陷,把爆炸半径锁死

## 一、三问(阶段动机)

- **这一阶段是干嘛的**:不改 Agent 一行逻辑,给它的运行环境上枷锁:非 root 用户、只读根文件系统、tmpfs `/tmp`、内存/CPU 限额、capabilities 全降、禁止提权。
- **为什么需要这么设计**:三层护栏是**数据边界**(拦毒文本、拦密钥),容器是**进程边界**——它的失效假设是"护栏全崩、注入得手、攻击者已经能让 Agent 执行任意命令",此时目标从"防住攻击"变成"限制爆炸半径"。两类边界回答不同的问题,缺一不可。
- **解决了什么问题**:阶段 9 的战利品 B(`run_command` 创建标记文件)在加固容器里直接失效:根 fs 只读,`touch /app/PWNED` 报 `Read-only file system`。同时诚实记账:网络 egress 未限,密钥仍可通过 http_post 外泄——这是留给路线 2 的缺口。

## 二、全链路一览

```
攻击者注入得手,劫持 run_command
  → 拿到的是 uid=1000 无权用户(非 root)
  → 写文件?根 fs 只读,只有 /tmp(tmpfs, 64MB, noexec)可写
  → 提权?capabilities 全零 + no-new-privileges,su/sudo 无路
  → 搞破坏?内存 3g / CPU 2 核封顶,拖不垮宿主
  → 持久化?--rm 容器退出即焚,只有挂卷(workspace/memory.json)留得下
  → 外泄?网络通——egress 未限,这是唯一敞开的门(已知缺口 → 路线 2)
```

## 三、跟着数据走 3 步(战利品 B 的两世)

1. **阶段 9(宿主裸奔)**:`run_command("touch PWNED-direct-injection")` → 退出码 0 → 宿主文件出现。攻击者写权限 = Agent 进程权限 = 用户本人权限。
2. **本阶段(加固容器)**:同样的命令 → `touch: cannot touch '/app/PWNED': Read-only file system`。命令照样被执行了(护栏没拦、容器也没拦"执行"),但**效果**被环境吞掉——加固管的是效果,不是意图。
3. **缺口实录**:同容器里 `urllib` 访问 `api.minimaxi.com` 拿到真实 HTTP 404——网络是通的。换言之:写不了文件,但能把读到的东西 POST 出去。egress 不过滤,容器就漏风。

## 四、新技术点四要素:Docker 加固参数 & codex sandbox_mode 精读

- **名字**:容器加固(Container Hardening);对照精读对象 = OpenAI codex CLI 的 `sandbox_mode` 三档。
- **作用**:用操作系统/容器机制压缩"被攻陷后的可用权限"。与护栏的关系:护栏减少"沦陷概率",加固减少"沦陷损失",乘积才是风险。
- **参数**(本项目选用的六项,挂载点 `scripts/docker-run.sh` + `Dockerfile`):
  - `USER agent`(Dockerfile):非 root 运行,攻击者拿到无权用户;
  - `--read-only`:根 fs 只读,写操作全部 syscall 级失败;
  - `--tmpfs /tmp:rw,noexec,nosuid,size=64m`:唯一可写口,内存盘、不可执行、限额;
  - `--cap-drop ALL` + `--security-opt no-new-privileges`:capabilities 全零,禁提权;
  - `--memory 3g --cpus 2`:资源封顶,防拖垮宿主;
  - 网络:**保留**(LLM API 与 fetch 硬依赖)——egress 缺口就此留下。
- **用法对照(codex 三档,信源 [codex 沙盒模式解析](https://backgrind.com/blog/codex-cli-sandbox-modes/) + [仓库协议定义](https://github.com/openai/codex))**:
  | codex 档 | 写权限 | 网络 | 对比本项目的抉择 |
  |---|---|---|---|
  | `read-only`(默认) | 全无 | **默认关** | 比我们严:codex 默认连网都不给 |
  | `workspace-write` | 仅 cwd+/tmp | **默认关**,可显式开 | 对应我们的挂卷 workspace + tmpfs,但网络我们选了开 |
  | `danger-full-access` | 全部 | 开 | 等于我们阶段 9 前的裸奔态 |
  另两个可借鉴的设计:codex 把 `sandbox_mode` 与 `approval_policy`(人审)分成**两个独立维度**;它的沙盒用 OS 原生机制(macOS Seatbelt / Linux Landlock+seccomp)直接锁 Agent 进程,不依赖容器——路线 2 的 microsandbox 也是这个思路。

## 五、关键顿悟

- **加固管效果,不管意图**:恶意命令在容器里照样"执行",只是效果被只读 fs 吞掉。评估一层防御要先问:它拦的是意图、动作,还是后果?
- **最小权限先砍写**:六个参数里收益最大的是只读 fs 和非 root——攻击者最常用的落地动作(写文件、改配置、植持久化)全部归零。
- **防御有账单**:镜像 4.96GB(torch/transformers/双 deberta/spacy 模型),启动多 5 秒模型加载;安全与成本的交易要记明账。另一个工程细节:挂卷文件必须 `chmod 666`,否则非 root 容器用户写不动记忆——权限模型在边界上要手工对齐。

大下载不是本阶段独有的,是三次累计;本阶段是把它们搬进了镜像:

| 时机 | 下载内容 | 体积量级 | 落在哪 |

| 阶段 14(首次跑 Sensitive) | Isotonic deberta NER(敏感实体识别)+ spacy 中英模型 | ~1GB + 58MB | 宿主 HF 缓存 + `.venv` |
