# 0029 阶段 29:OTel GenAI 审计字段落 Langfuse

**学了什么**:langfuse 4.x 的 OTel 化改造面——CallbackHandler 只收 (public_key, trace_context)、events-only 模式砍掉老读端点、SDK 读 API 不水合 input/metadata;审计观测(as_type=tool)挂中间件的最小侵入落法;OTLP 出网捕获验证法。

**过程**:
1. agent.py:新增 `TOOL_DATA_CLASS` 数据分级表(六工具全覆盖)与 `CURRENT_ROUND`;`make_tool_audit()` 审计中间件(wrap_tool_call 最外层,工具执行后旁路记 `audit:<工具名>` 观测,metadata 五要素:who=thread_id/when=UTC ISO/why=本轮用户消息原文/params=工具参数/data_class=分级),失败打印告警不静默
2. ask() 设 CURRENT_ROUND 并在 config.metadata 带上 audit.when/why(trace 级);main() 调整初始化顺序(langfuse_client 先于 build_agent 传入),退出时 flush() 防短命进程丢上报
3. 注释轮换:docstring/BANNER → 阶段 29

**卡在哪**(本阶段主要工作量是排坑):
- v4 events-only 模式:`api.trace.list`/`legacy.*` 全 404,`observations.get_many` 读得回 name/type/traceId 但 **input/metadata 恒为 None**——对照实验(刚写入的探针观测也读不回)证明是读路径降级,不是写丢失
- run-agent.sh 会覆写 LANGFUSE_BASE_URL,验证时需绕过脚本直设环境
- **最终验证法:OTLP 出网捕获**——本地收包器 + 把 LANGFUSE_BASE_URL 指过去跑一轮真实工具调用,检查 SDK 发出的字节:`audit.who=cli-session`、`audit.when/why`(trace 级 + 观测级共 9 处)、`audit.params`、`audit.data_class=workspace 目录清单` 全部在案(23030 字节载荷)
- 交叉证据:真实 Langfuse 库(3000)的 ClickHouse `events_full` 表中存在 `audit:list_dir` 事件行(读不到字段是 blob 水合在读 API 之外,UI 可见)
- **审计观测归队(用户 UI 实测发现 + 已修)**:初版审计观测落成独立根观测(UI 里是单独一条 trace,和 agent trace 割裂)。根因:v4 无人立环境上下文时 CallbackHandler 自建根,中间件也自建根。修复:ask() 每轮先用 `start_as_current_observation(name="cli-round", as_type="chain")` 立起上下文壳——CallbackHandler 会尊重环境上下文,模型 generation、工具 span、审计观测全部归到同一 trace_id 下,cli-round 为根。ClickHouse 实测:同 trace_id 六观测全为子观测 ✓

**结论**:审计五字段落库完成且已归队(单 trace 单轮完整复盘),阶段 31"审计复盘"攻击的地基就绪。
