# 0024 Presidio 记忆落库脱敏(阶段 28)

## 三问(阶段动机)

**终极目标**:Agent 就算被注入完全劫持,也拿不到真密钥、留不下敏感数据。

路线图:

```
✅ 阶段26-27:凭证代理(LLM 路 + fetch 路,密钥不进 Agent/模型)
👈 阶段28:Presidio 记忆落库脱敏(PII 不落盘)
⬜ 阶段29:OTel 审计字段    ⬜ 阶段31:四次攻击验收
```

**这一阶段是干嘛的?** 对话历史写进 `memory.json` 之前,先过一遍 Microsoft Presidio:Analyzer 找出 PII(邮箱/手机号/身份证/卡号/IP…),Anonymizer 把它们替换成 `<EMAIL_ADDRESS>` 这样的占位符,然后才落盘。

**什么需求逼的?** `memory.json` 是全系统唯一真实持久化的数据资产,而路线 1 实证过它两头都是洞:毒记忆能自触发(洞在输入侧,路线 3 修),用户随口说的 PII 会原样躺在磁盘上、跨会话回灌(洞在存储侧,本阶段修)。密钥已经撤走了(26/27),但用户在对话里说的手机号邮箱,Agent 照样会记下来。

**解决了什么麻烦?** 数据的"保存形态"和"使用形态"分离:当轮对话模型该看到的照旧(上下文完整,少一层误伤),落盘的是消毒后的副本。脏数据落不了盘,就永远不会跨会话存活。

## 全链路一览(落库消毒管道,JD 第 3 条"数据脱敏"的落点)

```
用户输入 ──→ L4 输入护栏 ──→ ReAct 图(模型/工具) ──→ checkpointer(内存,当轮上下文)
                                                              │ 进程退出
                                                              ▼
                                              save_memory:messages_to_dict()
                                                              │
                                              memory_guard.sanitize_messages()
                                              ┌───────────────┴───────────────┐
                                              │ Presidio Analyzer(找)          │
                                              │  NER(en_core_web_sm)           │
                                              │  + 内建正则(邮箱/IP/卡号…)      │
                                              │  + 自定义正则(手机号/身份证)    │
                                              │ Presidio Anonymizer(换)        │
                                              │  命中 → <实体类型> 占位符        │
                                              └───────────────┬───────────────┘
                                                              ▼
                                                   memory.json(干净落盘)
                                                              │ 下次启动
                                                              ▼
                                                   load_memory 回灌(干净的历史)
```

关键选择:**消毒点只卡落库出口,不碰对话过程**。拦在入口会误伤正常对话(下面实测果真如此),拦在出口则每条数据在"被持久化"这个不可逆时刻前必过一道闸。

## 跟着数据走:一条回复的消毒全程

CLI 实测:问"13800138000 加 1 等于几",模型答 `13800138000 + 1 = 13800138001`,退出时:

```
save_memory 取到 2 条消息 → sanitize_messages → 替换 6 处
memory.json:6 个 "<CN_PHONE>",11 位数字原文 0 处残留
```

直接单测更直白,一段混合中英文文本进去:

```
输入:联系 zhangsan@example.com 或 13812345678,卡号 4111111111111111,IP 是 10.0.0.23
输出:联系 <EMAIL_ADDRESS> 或 <CN_PHONE>,卡号 <CREDIT_CARD>,IP 是 <IP_ADDRESS>
身份证 110101199003074258 → <CN_ID>
```

注意 `<CN_PHONE>` 和 `<CN_ID>` 是**自定义识别器**的战果——Presidio 内建识别器偏英文,中文场景的高频 PII 要自己加正则(PatternRecognizer 十行一个),这是中文落地最重要的一课。

## 附:encrypt 可逆模式数据流图(只画不实现,路线 4 熟悉档)

上面 Anonymizer 的 replace 是**不可逆**的(换掉就没了);生产中还有一类需求是数据要"脱敏上云处理、响应再还原",靠的是可逆的格式保留加密(FPE/tokenization):

```
                     ┌────────────── 本地信任域 ──────────────┐
用户数据:手机号 13812345678                                │
      │ 1. tokenize:真值 → 随机令牌(如 TOK-7f3a),映射存本地金库
      ▼                                                          │
上云:把 "TOK-7f3a" 交给云端 LLM/服务处理(云只见过令牌)           │
      │                                                          │
      ▼ 2. 响应回来若引用 "TOK-7f3a"                              │
本地 detokenize:令牌 → 13812345678(只有本地能还原)             │
                     └────────────────────────────────────────┘
要点:①还原映射(金库)永不出本地,泄露的只是令牌;
     ②格式保留让下游系统无感(令牌长得像手机号也行,FPE);
     ③代价:云端推理全程在假数据上进行,依赖"任务可令牌化"。
```

## 关键顿悟

- **消毒点选出口而不是入口**:入口已有 L4 护栏(今天实测连"请记住我的联系方式"都误杀);PII 本身不是攻击,不该拦对话,该拦的是"敏感数据落盘"这个不可逆动作。
- **中文场景必须自己补识别器**:Presidio 的 NER 和内建正则默认英文向,手机号/身份证这类中国高频 PII 全靠自定义 PatternRecognizer——引入框架不等于覆盖需求,识别器清单就是治理清单。
- **两层防线会打架,而且都"没错"**:L4 护栏把想交出 PII 的用户拦在门外(误报),本阶段的出口消毒兜住漏进来的(漏报)——护栏互相补位是纵深防御的常态,不是设计失误。
