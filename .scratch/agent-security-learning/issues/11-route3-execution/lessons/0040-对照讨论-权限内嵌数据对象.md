# 0040 - 对照讨论:权限内嵌的数据对象(实验 5-12)——最后一道闸下沉到数据层

> 阶段 45 对照讨论(不落地,票 10 既定);参照实验:`ai-agent-book/chapter5/permission-embedded-data-objects/`。

## 它做了什么

场景:业务代码可能被 Agent 生成/重写——生成的代码不可信。该实验把应用层刻意做小:生成代码只能调用**稳定对象层**,而权限、校验器、状态机、连带后果全部**跟着数据类型声明**,由 store 在**每次操作**时强制检查。三条演示:合法招聘流转通过;跳过候选人状态迁移/写越界薪资被数据层校验器拒;跨租户读取被权限边界拒。

## 与路线 3 的四个对照

1. **不可信调用方同构**:我们不信任的调用方是"被注入的模型",他们的是"被生成的代码"——解法相同:不让调用方持有特权,只给它受限上下文(我们:任务票 scope;他们:scoped `AccessContext`,**不发生特权数据库连接**)。"最小权限"从 API 设计语言变成数据访问语言。
2. **PEP 落点比我们更深**:我们的强制点在网关(FGA/EGRESS)与中间件(票/D4/法官)——都在**调用路径**上;他们把最后一道闸**下沉到数据层**:即使上游全漏,写库/越租户在 store 处仍被拒。对照我们:memory.json 有装载校验(40),但 workspace 文件没有数据层强制——"数据层是最后防线"是授权矩阵文档值得补的一节。
3. **权限跟数据走,不跟代码走**:权限规则声明在数据类型上(`PermissionRule`),不散落在业务代码里——生成/重写代码**带不走、绕不开**权限。对照网关 RBAC:粒度止步"可见性";对照 OpenFGA:四元组在调用面。该实验展示第三种挂法:**在数据的家**。
4. **三层管道同构**:他们 store 的"同步权限/校验 → 持久化+引用完整性 → 异步反应(有界深度)"与我们"网关闸 → 中间件闸 → 出口闸(白名单/VM)"是同一个节奏:先静态快检,再落地,后异步扩散。

## 取舍(为什么对照不落地)

落地成本:PostgreSQL 中间件+多租户 schema+状态机,1-2 天量级;对本项目增益:workspace 是"笔记"级数据,非多租户业务对象——收益不匹配。**记入交付物 01(授权模型设计)的"已知深化方向"**:若业务数据升级为多租户/状态机型,授权应下沉数据层。

## 一句话带走

**网关闸得住调用,数据层闸得住后果**——授权做得再深,问一句"最后一道闸在哪层",答案决定了"业务代码被 AI 重写"这种场景的下限。
