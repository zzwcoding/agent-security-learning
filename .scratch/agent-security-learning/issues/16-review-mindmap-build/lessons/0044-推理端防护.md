# 0044 - 推理端防护:TEE、数据最小化与同态加密前沿(熟悉档)

> 复习期增补 lesson(2026-09-03)。定位:**熟悉档**——能讲清概念、定位与成熟度,不动手实践。触发问题:消息旅程图第 5 站(推理端,LLM 服务商的机器)"什么都不放"之外,还有没有能放的?

## 1. 三问

**这一阶段是干嘛的?** 补齐第 5 站的知识:prompt 到了别人的机器上,除"不发"之外,工业界和学术界各有什么牌。

**为什么值得学?** JD 第 3 条(端云混合、数据脱敏与隐私保护)的理论地基;"推理端怎么防"是面试高频题,答得出 FHE/TEE/ZKML 的分工是区分度。

**它解决什么麻烦?** 第 5 站"什么都不放"是判断不是偷懒——这个判断的底气来自知道"能放什么、为什么现阶段不放"。

## 2. 难题本质

明文 prompt 必须出现在服务商的内存里才能被模型算——常规加密下 CPU/GPU 算不了密文。第 5 站的所有防护都在回答一个问题:**能不能让"对方能算、但看不懂"**。

## 3. 三档方案(按离生产的距离)

### 第一档:生产可用

**① TEE 机密计算(可信执行环境)**
- 原理:硬件(Intel TDX / AMD SEV / NVIDIA H100 机密计算模式)给内存划加密隔离区,云厂商自己也读不到;远程证明(attestation)让你验证"对面跑的真是那段代码"
- 真实案例:Apple Private Cloud Compute(私有云计算、无留存、可验证镜像);Azure/GCP 有机密计算产品线
- 局限:信任从"服务商"转移到"芯片厂商+证明链";成本高一截

**② 不发(数据最小化 + 隐私路由)**——本项目的选择
- 脱敏后上云(Presidio,阶段 28);敏感任务路由本地小模型(Ollama/llama.cpp)
- 第 5 站最强防护 = 敏感数据根本不到这一站;这是路线 4 熟悉档"端云混合"的核心思想

### 第二档:前沿研究(知道名字与定位即可)

**③ FHE 全同态加密**:直接在密文上计算,服务商全程只见密文——理想解;现状是做 LLM 推理不可行(密文计算慢几个数量级,Zama 等有小模型 demo)

**④ 零知识证明 / ZKML**:服务商产出结果附密码学证明"我确实用声称的模型正确计算"——解决**完整性**(结果可验证),**不是隐私**(数据对方看得见);ezkl 等项目,大模型证明开销巨大

**⑤ MPC 安全多方计算**:推理拆给多方分片算,单方看不到全量——同样慢,研究阶段

## 4. 关键顿悟

- **"什么都不放"是判断不是放弃**:第 5 站的信任边界划在凭证代理,底气来自知道 TEE 贵、FHE/ZKML 远,"不发"是现阶段唯一零信任解
- **FHE 管隐私、ZKML 管完整性**——两者回答的问题不同,面试常被混着问,拆开答就赢了一半
- **隐私保护的最优解往往是路由而非加密**:敏感的不上云,比上云再加密便宜且可靠

## 5. 面试一句话

"推理端防护分三档:生产能用的是 TEE 机密计算和数据最小化;FHE 全同态管隐私但太慢、ZKML 管完整性不管隐私,都在前沿;我们的选择是信任边界划在凭证代理 + 敏感数据路由本地。"
