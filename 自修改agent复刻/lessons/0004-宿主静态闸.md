**这一步是干嘛的?** 候选补丁写出来了,发布前得过安检。安检有十个关卡(`CHECK_NAMES`,evolution.py:43-54),本阶段点亮前两个:`static_compile`(能编译吗)和 `security_scan`(有没有可疑语法),其余八格保持熄灭——**过静态闸远不等于能发布**。

**什么需求逼的?** 候选代码迟早要被执行(阶段 5 沙箱里跑),执行前先用便宜的手段粗筛一遍:语法都通不过的、一上来就 `import os` 的,根本不值得花沙箱的钱和时间。就像机场安检:先看登机牌(X光快筛),才轮到全身扫描(沙箱)。

**解决了什么麻烦?** 快速、便宜地拦掉最蠢的攻击,把昂贵的沙箱资源留给"看起来无害"的候选。同时它给整套验证定了形:`validate_candidate()` 返回一张十格灯表,后面阶段做的事情就是逐格点亮,发布决定(阶段 8)就是看"是否全绿"。

## 3. 跟着数据走:好候选和坏候选各过一次闸

**好候选**(阶段 3 生成的正常补丁):

- `compile(candidate_source, "candidate/retry_policy.py", "exec")` 把源码编译成字节码但不运行——语法错误在这一步就炸,`static_compile` 不亮,函数直接返回灯表。
- `_safe_ast` 用 `ast.parse` 把源码变成**语法树**——可以把语法树想成"把代码拆成一棵零件清单树",然后 `ast.walk` 逐个零件检查两条禁令:
  1. **任何 `import` 都不要**(`ast.Import` / `ast.ImportFrom`,所以 `import os`、`import socket`、`from subprocess import run` 全被一刀切——这个补丁本来就不需要任何外部模块);
  2. **不许调用** `eval` / `exec` / `compile` / `open` / `__import__`(这五个是"代码能自己动手脚"的口子)。
- 好候选两关全过:灯表前两格 ✓,后八格 ·。

**捣乱候选**:正常补丁尾部被追加 `import os` + `os.system('echo pwned')`。注意灯表结果——`static_compile` 居然是 **✓**!这段代码语法完全合法,编译得过;拦住它的是第二关 `security_scan`(import 被拒)。这正说明两关各有分工:**编译关拦"写错的",AST 关拦"写得太能干的"**。

**重要预期管理**(也是 README 原话):AST 拒绝列表**不是**安全边界。它只能查"语法树长什么样",查不住运行时的千奇百怪(比如 `getattr(builtins, 'ev'+'al')` 这种绕法一抓一把)。真正的安全边界是阶段 5 的加固容器——AST 关只是让便宜的门先挡一道,别把昂贵的门当第一道用。

## 4. 新技术点:ast 模块三件套(parse / walk / 节点类型)

- **名字**:`ast`(Abstract Syntax Tree,抽象语法树),标准库。配套用的是 `ast.parse`、`ast.walk`、节点类 `ast.Import` / `ast.ImportFrom` / `ast.Call`。
- **作用**:`ast.parse(源码)` 把文本代码变成树对象(只解析不执行);`ast.walk(tree)` 深度优先遍历返回**每一个**节点;节点类用来判断"这个零件是什么"——`ast.Call` 是函数调用节点,它的 `.func` 是被调对象,`.func.id` 在直接调用函数名时是函数名字符串。
- **参数**:`ast.parse(source)` 默认按"模块"解析;`compile(source, 文件名, "exec")` 第二个参数只是出错时的显示名,不要求是真实路径。
- **用法**(evolution.py:146-153 的 `_safe_ast`):

```python
tree = ast.parse(source)
forbidden_calls = {"eval", "exec", "compile", "open", "__import__"}
return not any(
    isinstance(node, (ast.Import, ast.ImportFrom))
    or (isinstance(node, ast.Call) and isinstance(node.func, ast.Name) and node.func.id in forbidden_calls)
    for node in ast.walk(tree)
)
```

`isinstance(node.func, ast.Name)` 这个判断别漏:调用节点的 `.func` 也可能是属性访问(如 `os.system`),那种情况 `.func` 是 `ast.Attribute`、没有 `.id` 字段,不判断会直接 AttributeError。

## 5. 关键顿悟

- **安检是灯表,不是单选题**:`validate_candidate` 返回十格布尔表,全 False 起步、过一关亮一灯。发布决定(阶段 8)退化为"数绿灯",不需要临场判断——判断越少,操纵空间越小。
- **编译关和 AST 关拦的不一样**:能编译的恶意代码(捣乱测试里 `static_compile` 仍是 ✓)要靠 AST 拦;两关是互补的筛子,不是一个开关。
- **AST 拒绝列表是纵深防御,不是安全边界**:语法层检查挡得住直球,挡不住绕行;真正关住候选代码的是阶段 5 起的沙箱。便宜的门先挡一道,贵的门做最后防线——两层都要有。
