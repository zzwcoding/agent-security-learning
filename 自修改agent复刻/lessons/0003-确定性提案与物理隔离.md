# 0003 - 阶段 3:确定性提案与物理隔离

## 1. 三问(这一阶段是干嘛的)

**位置感**:

```
✅ 1 看病:失败轨迹读进来,病可见
✅ 2 确诊:多条轨迹聚合成"修改请求"
✅ 3 开药:确定性提案,最小 diff 候选代码   ← 你在这里
⬜ 4 安检:宿主静态闸(编译+AST 拒绝列表)
⬜ 5 隔离病房:加固 Docker 容器跑候选
⬜ 6/7 体检:容器内 7 项语义检查
⬜ 8 放行决定 + manifest
⬜ 9 可信根自证(SHA-256)
⬜ 10 真实 LLM 提案(MiniMax)
⬜ 11 验收入口:负对照必拒 + 三方同门槛
⬜ 12 对照收官:加固 Docker vs microVM
```

**这一步是干嘛的?** 立案之后"开药":从稳定源码生成一份**修改过的副本**(候选代码),打上 diff(改动说明书),写进 `output/candidate/`。注意"开药"这一步在参考项目里也是**零模型参与**的——纯字符串替换;模型登场要等到阶段 10。

**什么需求逼的?** 要修生产代码,最危险的写法是"直接在 `stable/retry_policy.py` 上动手"。万一改坏了,生产立马挂;而且改完就没有"改动前"的底稿可以比对了。所以规矩是:**候选与稳定物理隔离**——候选写进另一个目录,`stable/` 一个字节都不动;改没改对,后面有整支验证队伍(阶段 4-7)盯着,验过了才谈发布(阶段 8)。

**解决了什么麻烦?** "自我修改"从"改自己"降级成"给自己写草稿"。草稿随便写,错了扔掉就行;正本的安全靠"草稿必须过全部检查才能转正"来保证。这是整个实验的题眼。

## 2. 全链路一览

```
修改请求(阶段 2 的 diagnosis)
      │
      ▼
generate_candidate()(evolution.py)
  ├─ 从 stable/retry_policy.py 源码出发(不改文件,只拿文本)
  ├─ 三段整块替换:_replace_once × 3 + 版本号升 1.1.0-candidate
  └─ 打包:源码 + unified diff + SHA-256
      │
      ▼

      │
      ▼
demo.py 打印 diff,并把 stable 读回来逐字节比对("未被改动: True")
```

## 3. 跟着数据走:一剂"三味"的药

**为什么是三段替换,不是一段?** 看修复内容(evolution.py:23-41 的 OLD_*/NEW_* 常量):

1. `NON_RETRYABLE_CODES` 表里加 `PAYMENT_DECLINED`;
2. `should_retry` 函数体开头加 `if not retryable or error_code in NON_RETRYABLE_CODES: return False`;
3. `should_open_circuit` 加"永久错误立即熔断(`consecutive_failures >= 1`)"。

三味药是**协调**的:第 2、3 味都去查 `NON_RETRYABLE_CODES` 这张表,所以第 1 味必须先把 `PAYMENT_DECLINED` 加进表里,否则查表永远查不到。少改任何一段,行为都不闭环——比如只改 `should_retry` 不改熔断,不重试的问题好了,但"连错 5 次才熔断"还在陪葬永久错误。

**替换怎么保证不误伤?** `_replace_once`(evolution.py:105-108)要求旧代码块在源码里**恰好出现一次**:出现 0 次(稳定版升级过了、对不上号)或 2 次以上(源码被塞了奇怪的东西)都直接抛错拒绝动手。**捣乱输入走一遍**:假设有人把 `stable/retry_policy.py` 里的 `should_retry` 改了名,`_replace_once(stable, OLD_RETRY, ...)` 数出 0 次匹配,`ValueError`——补丁宁可失败也不乱改,这叫 fail loud(大声失败)。

**候选长什么样、写到哪?** 生成的候选源码 = 稳定版 + 4 处小改(版本号升 `1.1.0-candidate` + 上面三段),由 `candidate_from_source` 打包成 `{source, diff, changed, source_sha256}`,再由 `write_candidate` 写进 `output/candidate/retry_policy.py`。demo 最后把 `stable/retry_policy.py` **重新读一遍**和改动前的文本逐字节比对,打印 `stable 未被改动:True`——物理隔离不是口号,是当场可验的事实。

## 4. 新技术点:difflib.unified_diff

- **名字**:`difflib.unified_diff`,标准库 `difflib` 模块;输出格式就是 `git diff` 同款的 unified 格式(`---`/`+++`/`@@`/`-`/`+`)。
- **作用**:对比两段文本,生成"改动说明书"。它只做**描述**不做**修改**——正好契合本项目的分工:diff 给人审查,替换 `_replace_once` 才动手。
- **参数**:两个行序列(注意是**行**的列表,不是整块字符串,所以先用 `splitlines(keepends=True)` 切行且保留换行符,否则 diff 对不上),外加 `fromfile`/`tofile` 两个标签(diff 头部的 `---`/`+++` 文件名,本项目标成 stable 与 candidate 的路径,让 diff 自带"从哪改到哪")。
- **用法**(evolution.py:118-123):

```python
diff = "".join(difflib.unified_diff(
    stable_source.splitlines(keepends=True),
    candidate_source.splitlines(keepends=True),
    fromfile="stable/retry_policy.py",
    tofile="candidate/retry_policy.py",
))
```

它返回的是**行迭代器**,所以要 `"".join(...)` 拼成一个字符串再存进候选包。本项目用在 `candidate_from_source` 里,阶段 8 这份 diff 原文还要进 release_manifest 存档。

## 5. 关键顿悟

- **物理隔离是安全的地基**:`stable/` 和 `output/candidate/` 是两个目录,候选写一百遍也碰不到正本;再加一道"读回比对"的现场证据,隔离从设计承诺变成可验事实。
- **最小 diff,但三段协调**:补丁越小越好审,但"小"不等于"一处"——修复要在行为上闭环(改函数必须连着改它查的表),阶段 7 的旧任务回归检查盯的就是这类"改了一半"。
- **整块替换 + 恰好一次匹配 = 补丁只对"认识的"稳定版生效**:稳定版一旦漂移,补丁大声失败而不是瞎猜着改。这跟阶段 9 的 SHA-256 自证是同一个思想的两个侧面:动手前先确认世界还是你以为的样子。
