# 0006 - 阶段 6:容器内语义检查(上)——验证行为,不是验代码长相

## 1. 三问(这一阶段是干嘛的)

**位置感**:

```
✅ 1 看病  ✅ 2 确诊  ✅ 3 开药  ✅ 4 安检  ✅ 5 隔离病房
✅ 6 体检(上):签名兼容 / 失败重放 / 永久错误熔断   ← 你在这里
⬜ 7 体检(下):临时恢复 / 旧任务回归 / canary / 回滚
⬜ 8 放行决定 + manifest
⬜ 9 可信根自证(SHA-256)
⬜ 10 真实 LLM 提案(MiniMax)
⬜ 11 验收入口:负对照必拒 + 三方同门槛
⬜ 12 对照收官:加固 Docker vs microVM
```

**这一步是干嘛的?** 容器里的入口程序(`sandbox_runner.py`)把候选源码**真正执行**起来(`exec`),然后检查它的**行为**:函数签名还对不对?把当年的失败案例重放一遍,它还敢不敢乱重试?永久错误来 1 次,熔断跳不跳?

**什么需求逼的?** 阶段 4 的静态检查只能看"代码长什么样",而 diff 完全可以"长得人畜无害、行为暗中使坏"。真正能回答"这个补丁修没修好病"的只有**行为证据**——把生产事故原样重放,看新代码的反应。

**解决了什么麻烦?** 把"验证"从"审查代码文本"升级成"审查行为表现"。这是 LLM 提案能被信任的根基:不管补丁是确定性生成的还是模型写的,都得在行为考试里拿同样的分。

## 2. 全链路一览

```
宿主 validate_candidate
  └─ run_in_sandbox("validate", 源码, 轨迹, stable)
        │ stdin: JSON 请求                    一次性加固容器
        ▼                                 ┌─────────────────────────┐
        │                                 │ _namespace(): exec 候选  │
        │                                 │   ↓ (第一次真正执行!)    │
        │                                 │ 检查1 签名兼容(inspect) │
        │                                 │ 检查2 失败重放(逐次问)  │
        │                                 │ 检查3 永久错误熔断        │
        │ stdout: {"checks": {7 个布尔}}  │ (后 4 项阶段 7)          │
        ▼                                 └─────────────────────────┘
宿主把布尔表填进十格灯表,demo 打印 ✓/·
```

## 3. 跟着数据走:三项行为考试

**考试 1:`public_api_compatible`(签名兼容)**。用 `inspect.signature` 把候选两个函数的签名**逐字符**比对:`should_retry` 必须还是 `(error_code, retryable, attempt)`,`should_open_circuit` 必须还是 `(consecutive_failures, *, error_code='', retryable=True)`。为什么这么苛刻?因为生产里有一堆调用方按这个签名在调它——补丁哪怕写得再聪明,把参数改个名,调用方当场全炸。**签名是候选与外界的契约,契约不容补丁重谈。**

**考试 2:`failure_replay`(失败重放)**。先从轨迹里筛出 `outcome == "failure"` 的(两条支付轨迹),然后对每条轨迹的**每个尝试序号**(0 到 attempts-1,共 4+3=7 个提问)都问一遍候选的 `should_retry(错误码, retryable, 序号)`,要求**全部回答"别试了"**。这里有个容易看漏的细节:超时轨迹(`TEMPORARY_TIMEOUT`)**不在考卷里**——它的 `outcome` 是 `success`(重试一次成功了),它是阶段 7"临时恢复"考试的正样本。失败重放的考卷只收"失败"的案例。

**考试 3:`nonretryable_circuit`(永久错误熔断)**。只问一个问题:`should_open_circuit(1, error_code="PAYMENT_DECLINED", retryable=False)`——才失败 1 次,跳不跳闸?新候选答"跳"(永久错误 1 次就熔断)✓;老稳定版答 `1 >= 5 → False`,必挂。

**顺手做个思想实验**:如果把**老稳定版**喂进这套检查,`failure_replay`(它 7 个提问里有 6 个答"再试一次")和 `nonretryable_circuit` 都会挂——这正是我们想要的可分辨性:检查必须能区分"带病的"和"修好的",否则就是摆设。

## 4. 新技术点:exec + inspect 的"加载并体检"组合

- **名字**:`exec(compile(...))` + `inspect.signature`,标准库。
- **作用**:`_namespace`(sandbox_runner.py:47-50)把候选源码编译并执行进一个**独立命名空间字典**——相当于把补丁装进一个一次性沙盒房间跑起来,房间里冒出来的函数对象都能通过名字拿到(`namespace["should_retry"]`)。`inspect.signature(函数)` 返回签名字符串形式,用于逐字符比对契约。
- **参数**:`exec(code, namespace_dict)` 第二个参数是全局命名空间,给独立字典(而不是让它用调用者的 `globals()`)是底线——候选定义的任何名字都不会泄漏进 runner 自己的作用域。
- **用法**:注意 `exec` 在宿主进程里是阶段 4 AST 黑名单的头号禁词,而在容器里它就是干活的工具——**同一个操作,权限取决于它在隔离边界的哪一侧**。另外 `main()` 里 `redirect_stdout(_NullWriter())`(sandbox_runner.py:112)把候选执行期间的打印全部吸进黑洞:候选就算 `print("劫持协议")` 一万遍,stdout 上只有 runner 最后写的那一行 JSON。

## 5. 关键顿悟

- **验证的是行为,不是代码长相**:静态闸看"像不像好代码",沙箱语义检查看"办事对不对"。LLM 生成一个风格完全不同但行为正确的补丁,照样能过;长得一模一样但少修一味药的,当场挂。
- **候选与调用方的契约 = 函数签名**:签名兼容检查保护的不是候选自己,是它的所有现有调用方。自我修改最容易踩的坑就是"改了内部,毁了接口"。
- **不可信代码终究要被执行,问题是"在哪执行、执行完能干什么"**:`exec` 在宿主是禁词、在容器是工具;候选的打印进不了协议通道;容器跑完即焚。执行不可回避,边界必须事先焊死。
- **内容寻址的日常红利**:本阶段改了 runner,镜像名自动变、`docker build` 自动重建——你什么都不用做,镜像永远和代码对齐。
