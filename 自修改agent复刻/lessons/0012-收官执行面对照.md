## 3. 跟着数据走:一次 microVM 验证与两个踩坑

**数据流**:Docker 版把 runner 烧进内容寻址镜像,镜像名 = Dockerfile+runner 哈希;microVM 版没有镜像,改为每次把 runner 经 stdin 写进 VM 的 `/tmp`——信任源同样是宿主上这份 runner 文件,锚定方式从"镜像哈希"变成"每次直写"。请求/响应协议逐字节一致,所以 `_parse_response` 的验收逻辑照抄 Docker 版:退出码 0 + 合规 JSON + `ok:true`。

**踩坑一(自己踩的,fail closed 兜住了)**:写 runner 的 `exec("sh", ["-c", "cat > /tmp/..."])` 忘了喂 `stdin`,`cat` 永远等待,SDK 抛 `ExecTimeoutError` → 被 catch → `SandboxError` → 拒绝。**新后端第一跑就验证了 fail closed 开箱生效**——因为异常契约是自建协议层规定的,与执行面无关。

**踩坑二(Docker 侧,harness 的坑)**:给探针跑 `docker run ... sh -s`,输出为空——`_docker_command` 的镜像带 `ENTRYPOINT [python, -I, runner]`,命令行参数会追加给 ENTRYPOINT 而不是替换它,`sh -s` 被当成了 runner 的参数。修复:`--entrypoint sh` 显式覆盖。**教训:对照实验的 harness 自身也要验证"探针真的在目标环境跑了"。**

**探针数据的关键对照**(详见复盘第二节):Docker 容器内 nobody+零 cap+只读 fs+彻底断网,但与全体容器**共享 linuxkit 内核**;microVM 内 root 满血+可写 /etc,但内核独享、宿主 macOS 零可见、用完即焚。两种哲学:"捆死里面的人" vs "反正出不了这间房"。

## 4. 新技术点:给执行面写"可替换适配层"的三个要点

本阶段没有新 API(microsandbox 的 `Sandbox.create(ephemeral=True)` + `exec/shell` 主线阶段 21-22 已教),有价值的是适配层设计:

- **契约先行**:新后端照抄旧后端的异常类型(`SandboxError`)和返回结构,调用方(`validate_candidate`)零改动。判断"适配完成"的标准是**旧测试全绿**,不是"新代码能跑"。
- **差异最小化**:列出新旧执行的机构性差异(镜像→stdin 直写;Popen→SDK exec;强删容器→ephemeral 自动焚),每个差异问一句"旧版的对应保障这里还有吗"(镜像哈希锚定 → 直写同源;超时强杀 → SDK timeout)。
- **同步封装异步**:`run_in_microvm()` 用 `asyncio.run()` 包住 SDK 的 async API,让同步调用方无感——适配层把"世界是异步的"挡在自己身后。

## 5. 关键顿悟(收官总结)

- **协议化让执行面成为零件**:runner 与宿主只经 stdin/stdout JSON 对话,于是"容器还是 VM"对验证逻辑不可见。想让关键组件可替换,先把它的输入输出钉死成协议。
- **四种执行隔离哲学真实存在**:共享内核+捆权限(Docker)、独享内核+内里放权(microVM)、共享内核+ syscall 过滤(gVisor 一类,票 09 阶段 32 会对照)。选型要看场景里"最怕什么":怕内核逃逸选 microVM,怕资源滥用加限幅,怕数据外泄补出网白名单。
- **对照实验的结论要敢下**:复盘给出了不和稀泥的答案——候选验证场景选 microVM,网络短板用主线白名单补齐,Docker 降为备选。含糊的"各有优劣"对读者毫无价值。
- **复刻的终点是对照,不是抄完**:能逐文件说清"原样复刻/有意改进/真实差距"(复盘第五节),这份复刻才完成了它作为学习方法的使命。
