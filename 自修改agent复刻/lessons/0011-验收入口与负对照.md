# 0011 - 阶段 11:验收入口——三方同台,负对照必拒

## 1. 三问(这一阶段是干嘛的)

**位置感**:

```
✅ 1-10 看病→…→真实 LLM 提案
✅ 11 验收入口:负对照必拒 + 三方同门槛 + evidence   ← 你在这里(16/16 gate 全过)
⬜ 12 对照收官:加固 Docker vs microVM
```

**这一步是干嘛的?** `run_experiment_9_6.py` 是"验收考官":一次运行串起全流程——可信根拍快照 → **先跑负对照**(一剂故意的坏药)→ 确定性提案 + 真实 LLM 提案 → 三方各过同一组门槛 → 行为指标量化对比 → **16 条验收 gate** 全过才 `accepted: True` → 原始证据落盘(`evidence.json` + SHA-256 + 产物哈希 + latest 指针)。实测:三方决定 `release / release / reject`,基线故障调用均值 3.5 → 候选 1.0,16/16 过。

**什么需求逼的?** 前面每阶段都是"各自跑各自看",没有回答一个问题:**怎么证明整套体系真的在拦坏东西?** 只演示好补丁能过,不能说明闸有效——**必须放一个已知坏的补丁进去,证明它必死**。这就是负对照(negative control),实验科学的基本功:测不出阴性的试剂等于没测。

**解决了什么麻烦?** 给"这套验证体系本身"一个验收标准。从此体系的质量不靠感觉,靠 16 条可机检的 gate:`real_coding_model_called`(必须真调了 API)、`known_bad_candidate_rejected_and_retained`(坏补丁必拒且留档)、`same_release_gate_for_both_generators`(两代生成器用同一张灯表)、`failure_replay_reduces_calls`(故障调用均值真的从 3.5 降到 1.0)……全过才算实验成功。

## 2. 全链路一览

```
可信根快照(before)
   │
   ├─ 负对照 generate_rejected_control → validate → reject(拿到"死法")
   │        └─ 死法打包成 rejected_history ──────────┐
   ├─ 确定性提案 generate_candidate                  │
   ├─ 真实 LLM 提案 ←── prompt 里带着这段"别学我"历史 ─┘
   │
   ├─ 三方各自:validate_candidate(同一张灯表)+ behavior_metrics(沙箱内量化)
   ├─ release_manifest × 3 → decisions: release / release / reject
   │
   ▼
16 条 gate 全布尔化 → accepted = all(gates)
   ▼
validation/<run>/:evidence.json + evidence.sha256 + artifact_hashes.json + 三方 manifest/候选
validation/latest.json + latest.sha256(指向最近一次完整证据)
```

## 3. 跟着数据走:负对照的"死法"变成教材

**第 1 步,坏药上场**。`generate_rejected_control`(evolution.py)造的负对照是:`should_retry` 一律 `return False`——把所有重试全禁了。它"看起来治好了"本次事故(永久错误确实不再重试),但行为检查当场三灯连灭:`temporary_recovery`(临时错误也不能重试了)、`old_task_regression`(旧行为被破坏)、`canary_ready`。**好补丁和坏补丁的差别不是"改没改",是"改的行为是不是恰好该改的那些"——配重检查就是干这个的。**

**第 2 步,死法变成 LLM 的教材**。负对照的检查结果打包成 `rejected_history` 塞进真实 LLM 的 prompt:"Previously rejected candidates (do not repeat their failure)"。注意方向:我们不是隐瞒坏案例,而是**主动把失败模式喂给模型**——这让 LLM 更容易成功,但它的输出照样全须全尾过一遍闸,成功率和安全性各管各的。

**第 3 步,行为指标量化**。`behavior_metrics` 让沙箱里的 `metrics` 动作"驾驶"候选策略重演失败轨迹,数出真实调用次数:带病基线 3.5 次(PAYMENT_DECLINED 被 `should_retry` 放行到 4 次)/两个好候选 1.0(一次到位)/负对照虽然也是 1.0——**单看这个指标负对照像好药**,所以指标必须配合灯表:temporary_recovery_rate 基线 1.0、负对照 0.0。单一指标都会被骗,组合起来才撒不了谎。

**第 4 步,gates 全布尔化**。16 条 gate 每条都是可机检的布尔表达式,`accepted = all(gates.values())`——和阶段 8 的发布公式同构:**验收也是查表,不是评议**。证据链落盘后,任何人可以 `shasum -c latest.sha256` 验证据没被改过。

## 4. 新技术点:证据文件链(sha 文件 + 最新指针)

- **名字**:校验文件(checksum file,`sha256sum -c` 格式:`<哈希>  <文件名>`)+ canonical 指针(`latest.json` / `latest.sha256`)。
- **作用**:证据可以被篡改,所以证据自带指纹(`evidence.sha256`);最近一次实验的路径会变,所以用固定位置的 `latest.json` 指过去。审计流程变成:验 `latest.sha256` → 看 `latest.json` → 顺 `input_artifacts` 里的哈希回溯到当时的输入。
- **用法**:验证一行命令:`cd validation && shasum -a 256 -c latest.sha256`(macOS 自带 shasum;Linux 用 sha256sum)。⚠ 坑:清单里写的是**相对文件名**,必须在文件所在目录执行,在上级目录跑会报 "FAILED open or read"(本次实测踩到,是路径问题不是内容问题)。
- **本项目落点**:`run_experiment_9_6.py:178-198` 写 evidence;`artifact_hashes.json` 对目录里所有 `.py` 候选留指纹。

## 5. 关键顿悟

- **没有负对照的验证体系不可信**:只见过"好的能过",等于不知道闸是否通电。负对照必须"设计成会死于我们最在乎的那几盏灯"——这里死于配重检查(过度修复)。
- **失败是资产**:负对照的死法喂给 LLM 当上下文,历史拒绝记录留在 manifest 里。安全系统不掩盖失败案例,而是把失败变成防御的一部分。
- **单一指标都会被骗,组合指标才接近真相**:故障调用均值 1.0 的可能是好药也可能是毒药(把重试全禁了),配上 temporary_recovery_rate 才分得开。验收 gate 的本质是**多维布尔组合**。
- **验收也要 fail closed**:任何一条 gate 不过,`accepted: False`,退出码非零——CI 里直接红。没有"大体上算过"这种结论。
