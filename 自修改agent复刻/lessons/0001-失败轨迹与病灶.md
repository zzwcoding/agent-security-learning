# 0001 - 阶段 1:失败轨迹与"病"长什么样

## 1. 三问(这一阶段是干嘛的)

**位置感**:我们在复刻一个"能给自己改 bug 的 agent,但改不改、能不能上线,全由模型外的确定性代码说了算"的系统(实验 9-6)。全程 12 步:

```
✅ 1 看病:失败轨迹读进来,病可见        ← 你在这里
⬜ 2 确诊:多条轨迹聚合成"修改请求"
⬜ 3 开药:确定性提案,最小 diff 候选代码
⬜ 4 安检:宿主静态闸(编译+AST 拒绝列表)
⬜ 5 隔离病房:加固 Docker 容器跑候选
⬜ 6/7 体检:容器内 7 项语义检查
⬜ 8 放行决定 + manifest
⬜ 9 可信根自证(SHA-256)
⬜ 10 真实 LLM 提案(MiniMax)
⬜ 11 验收入口:负对照必拒 + 三方同门槛
⬜ 12 对照收官:加固 Docker vs microVM
```

**这一步是干嘛的?** 把生产环境里 agent 犯的事故记录(`failure_trajectories.json`,下称"失败轨迹")读进来,打印出来,让"病"能被看见。

**什么需求逼的?** 生产出了这样的事故:一笔被拒的扣款(`PAYMENT_DECLINED`,系统明确标了 `retryable=false`,意思是"这种错别重试"),agent 却连着提交了 4 次。拿到这种事故,你手里有两个候选药方:

- 药方 A:往 agent 的 prompt 里加一句"遇到不可重试的错误别重试";
- 药方 B:修改 agent 的重试控制代码 `stable/retry_policy.py`。

这个实验的立场是选 B,原因有两个:

1. **prompt 是"劝",代码是"闸"**。prompt 里的嘱咐会被长上下文稀释、被别的指令覆盖,相当于在门上贴张"请勿入内"的纸条;而 `should_retry()` 是个函数,返回 `False` 就是 `False`,闸落下了就是落下了。
2. **只有代码改动才有"验证"可言**。prompt 加了一句话,你没法系统地检验它管不管用;代码改了,后面可以编译它、重放失败案例、跑回归测试(阶段 4-7 干的全是这个)。

**解决了什么麻烦?** 病要治,先得确诊;确诊要靠证据。这一阶段把"证据"摆上桌面——后面每一个阶段(聚合、诊断、改代码、验证)都围着这份轨迹数据转。

## 2. 全链路一览

本阶段的数据流只有一条,但是完整的:文件(生产者)→ 读进内存 → 打印+圈病灶(消费者)。

```
failure_trajectories.json          demo.py
┌──────────────────────┐    ┌────────────────────────────┐
│ 3 条事故记录(生产环境)│───▶│ load_trajectories():       │
│ 每条:哪次任务、哪个工具│    │   read_text 读成字符串      │
│ 什么错、能否重试、试了几│    │   json.loads 变成 Python 列表│
│ 次、结局、一句话证据    │    │ main():逐条打印,圈出病灶    │
└──────────────────────┘    │   "retryable=false 却重试了 3 次"│
                            └────────────────────────────┘
```

后面 11 个阶段就是往这张图的下游不断接环节:聚合 → 提案 → 静态闸 → 沙箱 → 发布决定。每一环节消费上一环节的产物。

## 3. 跟着数据走:run-payment-001 的旅程

**第 1 步,它躺在文件里**(`failure_trajectories.json` 第 2-10 行),长这样:

```json
{
  "id": "run-payment-001",
  "tool": "charge_card",
  "error_code": "PAYMENT_DECLINED",
  "retryable": false,
  "attempts": 4,
  "outcome": "failure",
  "evidence": "The same declined payment was submitted four times."
}
```

翻译成大白话:任务 run-payment-001 调用扣款工具 `charge_card`,银行回了"卡被拒",这种错系统标了 `retryable=false`(别试了,再试也是拒),结果 agent 前前后后试了 4 次,全失败。

**第 2 步,被读进内存**。`demo.py:20` 的 `json.loads(...read_text(encoding="utf-8"))` 把文件先整体读成一个字符串,再解析成 Python 的列表——3 条轨迹变成 3 个字典。

**第 3 步,被打印、被圈病灶**(`demo.py:28-31`)。重试次数 = `attempts - 1`(第一次是正常调用,之后才算"重试"),所以 run-payment-001 重试了 3 次。圈病灶的条件就一行:`retryable` 为假 **且** 重试次数 > 0——两条支付轨迹双双命中,一条超时轨迹(`retryable=true`)安安静静,说明"该重试的能重试、不该重试的也在重试",病是单向的。

**第 4 步,病灶指到代码**。看 `stable/retry_policy.py:11`:

```python
def should_retry(error_code, retryable, attempt):
    return attempt < MAX_RETRIES
```

签名里收了 `retryable` 这个参数,函数体却压根没用它——只看次数没到 3 次就允许再试。这就是病根:参数收了不认账。同文件 `:16` 还有第二个 bug:熔断 `should_open_circuit` 不看错误类型,只有连续失败满 5 次才熔断,永久性错误也得陪跑满 5 次。**注意这两个 bug 是实验故意埋的(文件第一行注释写明 "intentionally contains the reproduced bug"),复刻时必须原样保留**——修好了,后面 11 个阶段就没病可治了。

## 4. 新技术点:标准库读 JSON 的固定搭配

本阶段零依赖、零框架,唯一要带走的是 Python 标准库读 JSON 文件的惯用两连:

- **名字**:`pathlib.Path.read_text()` + `json.loads()`,都在标准库(`pathlib` / `json` 模块)。
- **作用**:`read_text()` 一步把整个文件读成字符串(相当于"打开-读-关闭"三件事并一件);`json.loads()` 把 JSON 字符串解析成 Python 对象(`loads` 的 s = string; counterpart `json.load()` 直接收文件对象,两者别混)。用 `Path(__file__).parent` 拼路径而不是写死绝对路径,脚本换台机器也能跑。
- **参数**:本项目的关键参数就一个——`encoding="utf-8"`。不写的话 macOS 上通常没事,但换到某些 Windows 机器默认编码是 GBK,中文一多就 `UnicodeDecodeError`,这是跨平台脚本最常见的翻车点之一。
- **用法**:`demo.py:20` 就是最小形态:

```python
ROOT = Path(__file__).parent
trajectories = json.loads((ROOT / "failure_trajectories.json").read_text(encoding="utf-8"))
```

跑法:项目零依赖,系统 Python 直接跑即可,`cd 自修改agent复刻 && python3 demo.py`。(到阶段 10 引入 LLM 客户端时才需要建 venv 装包,到时候教。)

## 5. 关键顿悟

- **修代码,不是修 prompt**。prompt 是贴在门上的纸条(可能被无视),代码是闸(落下就落下);而且只有代码才谈得上"验证"——后面 7 项语义检查验的全是行为,prompt 没法验。
- **要不要自我修改,由数据说了算,不由拍脑袋**。修改的"起诉状"就是生产轨迹:两条"不该重试却在重试"的实锤,才够立案(阶段 2 会把"≥2 条"定成硬门槛)。
- **stable 里带 bug 是故意的**。病根 `stable/retry_policy.py:11` 收了 `retryable` 参数却不用——复刻时"顺手修好"反而是错的,整个实验演的就是"怎么安全地把这个 bug 改掉"。
