# 0009 - 阶段 9:可信根自证——裁判和病历不许被碰

## 1. 三问(这一阶段是干嘛的)

**位置感**:

```
✅ 1-8 看病→…→发布决定 + manifest
✅ 9 可信根自证(SHA-256 前后对比)     ← 你在这里
⬜ 10 真实 LLM 提案(MiniMax)
⬜ 11 验收入口:负对照必拒 + 三方同门槛
⬜ 12 对照收官:加固 Docker vs microVM
```

**这一步是干嘛的?** 流水线开工前给六个"可信根"文件各拍一张 SHA-256 快照,收工后再拍一次,逐个对比:六个哈希必须纹丝不动。实测输出 `trusted_surfaces_unchanged = True`。

**什么需求逼的?** 前八个阶段建了一整套验证体系,但有个前提没人验过:**裁判本身可信吗?** 想一个最毒的攻击:不去绕沙箱、不碰灯表,直接改 `sandbox_runner.py`——把七项检查全改成"无条件返回 True"。之后任何垃圾补丁都能全绿通过。验证体系自己被腐化,比没有验证体系更危险,因为它给危险行为盖"已验证"的章。同理,`stable/`(病人)、`failure_trajectories.json`(病历)、`candidate_sandbox.py`/`Dockerfile.sandbox`(病房图纸)任何一个被悄悄改掉,整条流水线就成了表演。

**解决了什么麻烦?** 给可信根加"封条":口说无凭,"我没改"不值钱,**密码学证据才值钱**。SHA-256 前后快照就是封条——文件改一个字节,哈希天翻地覆,当场暴露。

## 2. 全链路一览

```
开工前:snapshot_trusted_roots() → 六个哈希(before)
   │
   ├─ 聚合 → 提案 → 静态闸 → 沙箱 → 发布决定(阶段 1-8 全流程)
   │    └─ 顺带:证据轨迹各自算 trajectory_sha256,进 manifest 存档
   │
收工后:snapshot_trusted_roots() → 六个哈希(after)
   │
   ▼
before == after ? → trusted_surfaces_unchanged: True/False(demo 逐文件打印 ✓/✗)
```

## 3. 跟着数据走:六个名字为什么是这六个

| 可信根 | 角色 | 被改了会怎样 |
|---|---|---|
| `stable/retry_policy.py` | 病人(生产正本) | 改了它,"回滚"回的就是被改过的版本 |
| `failure_trajectories.json` | 病历(立案证据) | 改病历,想立什么案就立什么案 |
| `evolution.py` | 主裁判(聚合/提案/决定) | 改决定公式,`reject` 变 `release` |
| `candidate_sandbox.py` | 狱吏(沙箱驱动) | 改 docker 参数,禁网变通网 |
| `sandbox_runner.py` | 阅卷人(七项行为检查) | 改成无条件全 True,考试作废 |
| `Dockerfile.sandbox` | 病房图纸 | 换基础镜像,加固全部作废 |

注意它们的共同点:**全部是"验证与依据"侧的文件,没有一个是"被验证对象"**。候选代码、输出产物都不在名单里——它们本来就该被流程随便折腾。这就是"可信根不进自我修改权限"的落点:**自我修改的权限边界,不是靠自觉,而是靠这份名单加哈希封条划出来的**。

**证据侧还有一个细节**:`diagnose()` 现在给每条立案轨迹算 `trajectory_sha256`(`repr(sorted(item.items()))` 的哈希——把字典转成规范字符串再哈希,同一份证据永远算出同一个指纹),随 manifest 存档。起诉状不但要交,还要按手印:事后有人想替换病历里的证据,指纹对不上。

## 4. 新技术点:用 repr+sorted 给 dict 做稳定指纹

- **名字**:无新 API,是 `hashlib.sha256` 之上的一种**规范化(canonicalization)技巧**。
- **作用**:JSON dict 的键序在不同语言/序列化器下可能不同,直接对原始文本哈希,"同一份数据"可能算出不同指纹;反过来,格式化的空格差异也会造成假阳性。先 `sorted(item.items())` 把键值对排序,再 `repr()` 转成确定性的字符串表示,最后哈希——**内容相同 → 表示相同 → 指纹相同**,与键序和空格无关。
- **参数/用法**(`evolution.py` 的 `diagnose()`):

```python
"trajectory_sha256": sha256_text(repr(sorted(item.items())))
```

这个套路在行业里有个更正式的版本叫 canonical JSON(JCS,键排序+固定分隔符),思路一致:哈希前先规范化。以后你要对任何"结构化数据"做指纹/签名,第一步都是先想清楚"什么算同一个"。

## 5. 关键顿悟

- **验证体系自己也需要被验证**:链上每个环节都可以造假,唯一的断点是"链条两端的密码学封条"。安全设计要永远追问一句:"这个组件腐化了,谁来看着它?"
- **可信根是名单,不是感觉**:六个文件白纸黑字列出来,权限边界才可审计。"重要的东西要保护好"是愿望,"这六个文件前后哈希必须一致"才是机制。
- **同一思想的第三次出现**:阶段 3 的"恰好匹配一次"(补丁只对认识的稳定版动手)、阶段 5 的内容寻址镜像(镜像和源码绑定)、本阶段的封条对比(流程没碰裁判)——全都是"**先确认世界还是你以为的样子,再行动**"。
- **为阶段 10 铺路**:下一步真实 LLM 进场,同样的快照对比会证明它"只交了提案,没碰考场"——LLM 的权限边界也靠这张封条显形。
