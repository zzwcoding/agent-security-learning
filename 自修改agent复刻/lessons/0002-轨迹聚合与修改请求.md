# 0002 - 阶段 2:轨迹聚合与"修改请求"立案

## 1. 三问(这一阶段是干嘛的)

**位置感**:终极目标不变——复刻"LLM 只产提案、模型外代码把所有关"的自我修改系统。路线图:

```
✅ 1 看病:失败轨迹读进来,病可见
✅ 2 确诊:多条轨迹聚合成"修改请求"     ← 你在这里
⬜ 3 开药:确定性提案,最小 diff 候选代码
⬜ 4 安检:宿主静态闸(编译+AST 拒绝列表)
⬜ 5 隔离病房:加固 Docker 容器跑候选
⬜ 6/7 体检:容器内 7 项语义检查
⬜ 8 放行决定 + manifest
⬜ 9 可信根自证(SHA-256)
⬜ 10 真实 LLM 提案(MiniMax)
⬜ 11 验收入口:负对照必拒 + 三方同门槛
⬜ 12 对照收官:加固 Docker vs microVM
```

**这一步是干嘛的?** 阶段 1 只是把 3 条轨迹摆上桌;这一步把散轨迹**聚合成一个正式的"修改请求"**——就像病历汇总成一份"手术申请单",上面写清:要不要动手术(.change_required)、动哪里(target)、依据哪些证据(source_case_ids)。

**什么需求逼的?** 如果**一条**轨迹就能触发"改自己的代码",那这个开关太容易被扳动了:一次偶发故障、甚至一次被精心构造的提示注入,都能骗系统去改自己的重试逻辑。所以要把门槛定成**同一失败模式至少 2 条独立轨迹支持**才立案——两条独立证据都指向同一模式,才像真病,不像噪声或操纵。

**解决了什么麻烦?** 给"自我修改"这个高危动作装了**点火条件**:不是想改就改,得先立案。而且立案结论(根因是 `stable/retry_policy.py` 的控制逻辑,不是 prompt)由这段确定性代码直接给出——模型后面只负责"照方抓药",不负责"确诊"。

## 2. 全链路一览

阶段 2 在"读轨迹"和"改代码"之间插入了**确诊**环节:

```
failure_trajectories.json(3 条轨迹)
        │  阶段1:读
        ▼
   diagnose()(evolution.py)          ← 本阶段
   ├─ 过滤:只留「失败的 + 不许重试的 + 却重试了」的轨迹
   ├─ 分组:按 (tool, error_code) 归堆
   ├─ 门槛:每堆 ≥2 条才立为 pattern
   └─ 定位:根因指到 stable/retry_policy.py
        │
        ▼
   demo.py 打印"修改请求"(本阶段的消费者,数据流在此闭合)
        │
        ▼  (后面阶段)
   生成候选补丁 → 静态闸 → 沙箱 → 发布决定
```

## 3. 跟着数据走:3 条轨迹的立案过程

**第 1 步,过滤**(evolution.py:20-22)。逐条检查三个条件,全中才进分组:

| 轨迹 | outcome=failure? | retryable=false? | attempts>1? | 结果 |
|---|---|---|---|---|
| run-payment-001 | ✓ | ✓ | ✓(4 次) | 进入分组 |
| run-payment-002 | ✓ | ✓ | ✓(3 次) | 进入分组 |
| run-timeout-001 | ✓ | ✗(retryable=true) | — | **被排除** |

run-timeout-001 是"超时后重试一次就成功"——这是**健康行为**,健康的证据不立案。demo.py:25 会把排除名单打印出来,门槛不只拦人,还要让人看见"拦了谁、为什么"。

**第 2 步,分组**。剩下的 2 条按 `(tool, error_code)` 归堆:都是 `charge_card` + `PAYMENT_DECLINED`,进同一堆,堆里 2 条。

**第 3 步,过门槛**(`evolution.py:26` 的 `if len(items) >= 2`)。这堆 2 条,✅ 立案,算出两个量化指标:cross_trajectory_support=2(几条轨迹支持)、total_redundant_calls=5(3+2=共 5 次多余重试)。

**捣乱输入走一遍**:假设生产里只有 run-payment-001 一条轨迹——分组后这堆只有 1 条,过不了门槛,`diagnose()` 返回 `change_required=False`,demo 打印"没有足够支持的失败模式,不改代码",流程到此为止。**这就是闸**:单条证据,哪怕看起来再铁,也扳不动"改自己代码"的开关。

**第 4 步,立案输出**。最终修改请求长这样(demo.py:33-36 打印):根因=`stable/retry_policy.py`,证据轨迹=run-payment-001、run-payment-002,理由="重试/熔断控制无视 retryable=false,根因在控制代码,不在 prompt"。注意"根因在哪个文件"是**写死在确定性代码里的结论**(evolution.py:36),不是从数据里推断出来的玄学——因为这类系统里,谁负责改什么,本来就该是运维者预先划定的管辖范围。

## 4. 新技术点:collections.defaultdict

- **名字**:`defaultdict`,标准库 `collections` 模块。
- **作用**:带"默认出厂值"的字典。普通字典访问不存在的键会报 `KeyError`,分组场景得先判断"这堆存不存在再决定建不建";`defaultdict(list)` 把这个判断藏起来了——访问不存在的键时自动配一个空列表,直接 append 就行。比喻:普通字典是不管事的仓库管理员,取货前得先问"有没有这个货架";defaultdict 是看到新货名就自动先装一个空货架。
- **参数**:构造时传一个"零值工厂",如 `list`(空列表)、`int`(0)、`set`(空集)。本项目用 `defaultdict(list)`(evolution.py:19)。
- **用法**:

```python
repeated: Dict[tuple[str, str], list[Dict[str, Any]]] = defaultdict(list)
for item in trajectories:
    repeated[(item["tool"], item["error_code"])].append(item)   # 键不存在也不报错
```

本项目用在 evolution.py:19-22:第一次见到的 `(tool, error_code)` 组合自动开新堆。和阶段 10 会用到的普通 dict 的区别:这里键集合事先不可知(生产会冒出什么错误组合谁知道呢),所以才需要"自动开货架"。

## 5. 关键顿悟

- **自我修改需要"点火条件"**:≥2 条独立轨迹支持同一模式才立案。这不是数字迷信,是把"偶发噪声"和"单点操纵(比如注入的假轨迹)"挡在门外的硬门槛。
- **立案(确诊)和开药(生成补丁)是分离的**:根因定位由确定性代码写死,模型后面只负责生成补丁文本。确诊权不在模型手里,是整个安全骨架的第一根柱子。
- **门槛要可见**:demo 打印了"被排除:run-timeout-001(正常重试,不该立案)"。闸不仅拦,还要让旁观者能复核拦得对不对——这和阶段 8 的 release_manifest 是同一个思想:结论可审计。
- **诚实标注**:参考版 `diagnose()` 还给每条证据轨迹算了 SHA-256(为阶段 9 的可信根自证服务),本阶段按"不超前"纪律暂未复刻,到阶段 9 补上。
