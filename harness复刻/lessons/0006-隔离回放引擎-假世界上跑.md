
**这一阶段是干嘛的?** 造一台"考试机":把候选源码加载进**干净命名空间**,先查它的**接口契约**(三个约定函数都在吗),然后给它注入一个**记账的假执行器**,在假文件系统/假 Git/假数据库上把用例一步步回放——核对每步的返回状态**和执行器账本**。

**什么需求逼我们这么设计?** 静态闸(阶段 5)只看骨架,看不出行为:一份语法漂亮、导入干净的提案,照样可能"挂起时偷偷执行"或"低风险也乱拦"。行为只能靠**跑**来验。但候选来路是 LLM,直接在真世界上跑测试等于让陌生人开真车考试——所以先造个假世界,再让候选**以为**自己在开车。

**它解决了什么麻烦?** 把"挂起时绝不执行"从口号变成**可测断言**:执行器每被调一次就在 `calls` 账本上记一笔,回放器核对账本——期望挂起的步骤,账本多一笔就是不及格。返回值可以撒谎(嗯,是"可以写错"),账本不会。

## 3. 跟着数据走:两步删除用例在考试机里的一生

用例(手工版 b-001):第 1 步无票删 `notes/todo.md` 期望 `pending_confirmation`;第 2 步 `confirm: true` 期望 `executed`。

1. **开考**:`_load_gate` 把门禁源码 exec 进新命名空间 `ns`——注意受检的是**从文本加载的候选**,不是 demo 顶部 import 的那个模块(两者内部各有各的 `_pending`,互不相通;这也意味着每次回放都是一张白纸)。
2. **第 1 步**:回放器不递票,调 `ns["dispatch"]("delete_file", {...}, execute=execute)`。候选classify 出高风险、无票 → 返回 `pending_confirmation`。核对①:状态对;核对②:账本 `before=0 → 0`,候选没敢动执行器。✓
3. **备票**:`confirm: true` 让回放器亲自调**候选的** `issue_confirmation` 签一张票——注意是考官用考生的笔签票,考生的签票逻辑因此也被测到了。
4. **第 2 步**:持同一参数+票再调 dispatch。候选 `pop` 票、比对指纹吻合 → 调 `execute(...)` → **稳定版调度器**在假 env 上真删了文件,账本 `0 → 1`。核对①:状态 `executed` ✓;核对②:恰好 +1 ✓;顺带 `notes/todo.md in env` 已是 False——假世界真的变了。
5. **捣乱用例也不放过**:伪造票(`confirm_token: "forged-token-123"`)→ 期望 `rejected`,账本 0→0;拿 A 的票干 B(`confirm_for` 为删缓存签票,却拿去删 todo)→ 指纹不符 → `rejected`。demo 里两条都是 ✓。

## 4. 新技术点:importlib 按路径加载

- **名字**:`importlib.util.spec_from_file_location` / `module_from_spec` / `exec_module`,标准库 importlib
- **作用**:不给文件路径一个包名、不改 `sys.path`,直接把一个 `.py` 文件当模块加载。本项目 `stable/` 故意没有 `__init__.py`(阶段 1 说过它是"文件不是包"),验证器就用这招把它请进来——**稳定版和候选一样,都是"被加载的文本",谁也不比谁特殊**
- **参数**:`spec_from_file_location("模块名", 路径)` 造加载说明 → `module_from_spec(spec)` 造空模块 → `spec.loader.exec_module(module)` 执行填充
- **用法**:`evolution.py` 的 `_load_stable_dispatcher()`,模块级 `STABLE` 常量。以后想动态加载插件/脚本,这是比 `exec(open(...).read())` 正经得多的做法

## 5. 关键顿悟

- **两层隔离,缺一不可**:**命名空间隔离**(exec 进独立 dict,候选的 globals 出不来,验证器不陪葬)+ **世界隔离**(execute 注入,候选唯一摸得到的"世界"是假 env)。静态闸挡掉明显坏的,这两层兜住"漏网的坏的"能造成的伤害——纵深防御的三段各管一段。
- **行为断言靠账本,不靠返回值**:`calls` 记账是整个回放引擎的灵魂。候选返回 `pending_confirmation` 但账本 +1?照样不及格。**信日志别信口供**——这条和你主线阶段 44"审计三面(哈希链+tool_metrics)"是同一个哲学。
- **契约检查是 duck typing 的防御用法**:不声明接口、不搞继承,只要求"三个名字都得是 callable"。缺函数的提案死在门口(卡在 gate_contract),不会跑到回放一半 AttributeError 半死不活——**先验形状再跑行为,错误越早暴露越便宜**。
- **回放引擎不知道也不关心提案是谁写的**:确定性生成器、真 LLM(阶段 11)、甚至"故意放行一切"的反例(阶段 8),一律同一台考试机。公平性是结构给的,不是态度给的。

**捣乱实验**(已代跑验证):亲手喂一个"放行一切"的迷你门禁给考试机——

```python
from evolution import _load_gate, _replay_case
evil = '''
def requires_confirmation(tool_name, args=None):
    return False
def issue_confirmation(tool_name, args=None):
    return "t"
def dispatch(tool_name, args=None, *, execute, confirm_token=None):
    return {"status": "executed", "confirmed": False, "result": execute(tool_name, args)}
'''
case = {"id": "e", "steps": [
    {"tool": "delete_file", "args": {"path": "x"}, "expect": "pending_confirmation"}]}
print(_replay_case(_load_gate(evil), case))
# (False, 'e: 期望 pending_confirmation,实际 executed')
```

门禁形同虚设,考试机当场抓获——这正是阶段 8 反例必拒的原理预告。
