# 0004 - 提案打包:门禁源码变成一份建议书

## 1. 三问(阶段动机)

**位置感**:

```
✅01 缺陷现场 → ✅02 诊断聚簇 → ✅03 确认门禁本体 → ✅04 提案打包 → ▶️05 静态闸(下一站)
→ ⬜06 隔离回放 → ⬜07 全量门槛 → ⬜08 反例必拒 → ⬜09 发布决定
→ ⬜10 验收入口 → ⬜11 真实LLM → ⬜12 加固门禁 → ⬜13 收官对照
```

**这一阶段是干嘛的?** 把阶段 3 的门禁源码,连同"它是谁、改了什么、打算怎么接线、预期什么效果、证据是哪些"打包成一个 `candidate`(候选)对象——一份完整的**建议书**。故事里这一步由"Coding Agent"完成:确定性版本(本阶段)或真 LLM(阶段 11)。

**什么需求逼我们这么设计?** LLM 能产出的只是**一段文本**。文本不能直接生效——否则"让 AI 改系统"就等于"AI 说什么就是什么"。必须先把文本装进一个结构化的信封:源码有指纹(防篡改)、接线有 diff(可评审)、证据有哈希(可追溯)、效果有预判(可对照)。**建议书是"AI 说的"变成"待审的材料"的那一步。**

**它解决了什么麻烦?** 后面所有验证门槛(阶段 5-9)面对的不再是一锅源码汤,而是一个有字段可查的对象:验源码哈希、数补丁行数、查生成方式、追证据轨迹。没有这个信封,验证器连"我在审谁"都说不清。

## 2. 全链路一览

```
 confirmation_gate.py(源码)      diagnosis(修改请求,含 9 条溯源轨迹)
        │                                │
        ▼                                ▼
   generate_candidate(stable_source, diagnosis)   ← 确定性生成器(0 次 API)
        │  ① 读门禁源码
        │  ② difflib 生成代码 diff(全文件新增 81 行)
        │  ③ _integration_diff:对 stable 调度器的"最小接线"diff
        │  ④ SHA-256 锚定:源码指纹 + 轨迹指纹
        │  ⑤ impact_prediction:提案人预先立字据
        ▼
   candidate 建议书 ──▶ demo 打印(本阶段消费者)
        └──▶ 阶段 5 静态闸(下一站消费者)
```

## 3. 跟着数据走:那根"接线 diff"是怎么长出来的

建议书里最微妙的一页是 `integration_diff`——门禁模块怎么接进稳定调度器。看它对 `stable/tool_dispatcher.py` 只动了两处:

1. **函数签名**:`def dispatch(tool_name, args=None, *, env=None):` → 末尾多了 `confirm_token=None`——调用方可以递票进来了。
2. **最后一行**:`return {...直接执行...}` 换成四行:本地定义一个 `execute` 小函数(把真实执行包起来),然后把工具名、参数、execute、票**转交**给 `gated_dispatch`——门禁成了调度器的新前台。

注意 `OLD_DISPATCH_RETURN` 是**一字不差**的原文匹配(`evolution.py` 里 `replace(..., 1)`):如果 stable 的代码结构变了,匹配不上就抛 `ValueError` 拒绝打包——提案工具连"接线说明"都不许瞎写。也注意 diff 的落款写着"提案,不落盘":stable/ 在发布决定(阶段 9)之前一个字节都不会变。

再看证据侧:每条支撑轨迹算 `trajectory_sha256 = SHA256(repr(sorted(轨迹键值)))`——先把字段按名字排序再序列化,保证"同一份证据"不管字段顺序怎么排都算出同一个哈希(和阶段 3 指纹的 `sort_keys` 同一思想)。9 条支撑轨迹从此有了防伪码,谁改了案卷一个字,哈希就对不上。

## 4. 新技术点:difflib.unified_diff

- **名字**:`difflib.unified_diff`,标准库 `difflib`,生成 unified 格式 diff(就是 `git diff` 那种 `-`/`+` 的样式)
- **作用**:两段文本的逐行差异,人类可读、机器可解析——建议书里"改了哪几行"全靠它
- **参数**:`a`(旧文本行列表)、`b`(新文本行列表)、`fromfile`/`tofile`(diff 头里显示的文件名)、`lineterm`(行尾,默认 `\n`);输入要用 `splitlines(keepends=True)` 保留行尾,否则输出行会黏在一起
- **用法**:`evolution.py` 的 `_integration_diff`(接线 diff,旧→新)和 `candidate_from_gate`(代码 diff,旧侧给空列表 `/dev/null` → 整个文件都是新增);本项目里 diff 只作展示,真正"验码"的是阶段 5-7,不重放 diff

## 5. 关键顿悟

- **提案 ≠ 生效**:candidate 里连"怎么接进 stable"的 diff 都写好了,但那只是建议书里的一页——**接线 diff 从不落盘**,stable/ 原文匹配不上宁可打包失败。AI 的产出被关在"材料"层,生效权在后面的门槛手里。
- **从这一阶段起,全线材料都有哈希指纹**:轨迹证据(本阶段)、门禁源码(本阶段)、稳定版(阶段 9 的 rollback 锚点)。改任何一处,后面任何一步都能发现对不上——这和你主线阶段 41 的哈希链是同一个直觉:**防篡改的本质是"给历史拍照"**。
- **impact_prediction 是提案人预先立字据**:"未确认高风险执行 before=直接执行/after=0,低风险误拦 after=0"。阶段 9 的发布清单会把它原样带回,谁签的字据谁认账——预判落空本身就是回归证据。
- **生成器可替换,信封不变**:确定性生成器(0 次 API)和真 LLM(阶段 11)产出同一个 `candidate` 结构,后面的门槛一视同仁。**换脑子不换流程**,这是整条管线能公平比较两个提案的前提。
