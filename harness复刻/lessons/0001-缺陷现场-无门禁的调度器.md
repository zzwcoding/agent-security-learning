# 0001 - 缺陷现场:无门禁的调度器与 11 条失败轨迹

## 1. 三问(阶段动机)

**位置感**——终极目标:复刻"实验 9-7:由用户反馈触发的高风险操作确认门禁"——Agent 犯了不可逆的错误后,系统**自己**给工具调度器装一道"先确认再执行"的门禁。13 阶段路线图,你在这里:

```
✅01 缺陷现场 → ⬜02 诊断聚簇 → ⬜03 确认门禁本体 → ⬜04 提案打包
→ ⬜05 静态闸 → ⬜06 隔离回放 → ⬜07 全量门槛 → ⬜08 反例必拒
→ ⬜09 发布决定 → ⬜10 验收入口 → ⬜11 真实LLM(可选) → ⬜12 加固门禁 → ⬜13 收官对照
```

**这一阶段是干嘛的?** 搭"案发现场":一个没有门禁的工具调度器(`stable/tool_dispatcher.py`),加一份"案卷"(11 条失败轨迹),再让 demo 把案子当场重演一遍。

**什么需求逼我们这么设计?** 用户的愤怒来自三个互不相识的地方:有人打字纠正("谁让你直接删的!")、有人点踩(连文字都懒得打)、还有事后审计规则报警(当时没人在场)。三类信号指向同一个缺陷:`delete_file`、`git_push(force=True)`、`DROP TABLE` 这类**不可逆**操作,和"读个文件"一样直接执行了。要修它,得先把它原样摆出来。

**它解决了什么麻烦?** 后面所有阶段(诊断、提案、验证、发布)都要回答同一个问题:"修的到底是哪个缺陷?"这一阶段把缺陷固化成可运行、可重演的代码和数据——案卷(JSON)是证据,调度器是罪犯,demo 是现场还原。

## 2. 全链路一览

```
 failure_trajectories.json          stable/tool_dispatcher.py
 (案卷:11 条失败轨迹)               (现场:6 个工具,无风险分级)
        │                                   │
        └────────> demo.py <────────────────┘
                    │  ① 读案卷,按三类信号分组计数
                    │  ② 抽第一条用户纠正轨迹,展示用户原话
                    │  ③ 现场重演:dispatch('delete_file') 再犯一次
                    ▼
             屏幕输出(可观察变化):
             "{'ok': True, 'deleted': ...} / 文件还在吗:False"
             —— 没有任何环节问过用户,这就叫缺陷
```

## 3. 跟着数据走:删掉季度报告的那 10 秒

以案卷第一条 `traj-2026-0702-del-report` 为例:

1. **案卷原文**(`failure_trajectories.json` 第 2 条):`signal: user_correction`,`user_feedback: "谁让你直接删的?我还没备份!"`,涉案调用 `{"tool": "delete_file", "args": {"path": "reports/2026-Q1-draft.docx"}, "user_confirmed": false}`。最后那个字段是关键——**没有确认记录**。
2. **demo 读入**:`demo.py:15` 把 JSON 变成 Python 列表,按 `signal` 分组 → 屏上打出 `user_correction: 4 条 / post_hoc_audit: 4 条 / user_thumbs_down: 3 条`。
3. **现场重演**(`demo.py:31`):`dispatch("delete_file", {"path": ...}, env=env)` 一路畅通——调度器查表(`tool_dispatcher.py:105` 的 `TOOLS` 字典)找到 `_delete_file`,直接删,返回 `{'ok': True, 'deleted': ...}`。**中间没有任何一步停下来问人。**
4. **后果**:`target in env['files']` 变成 `False`。内存环境里删的是字典键,真实世界里删的就是用户的季度报告。

注意案卷里还有一条**对照轨迹** `traj-2026-0725-confirmed-delete`:同一个 `delete_file`,用户说了"可以,删吧"之后执行,结果正常。所以缺陷不在工具本身,在"**没确认就执行**"这个流程缺失——这就是第六章说的"换更强的模型也照样犯"的 Harness 问题。

## 4. 新技术点:命名空间包导入

- **名字**:namespace package(命名空间包),Python 3.3+ 的导入机制
- **作用**:`stable/` 目录里只有一个 `tool_dispatcher.py`,**没有** `__init__.py`——按老规矩这不算包,但 Python 3 会把没有 `__init__.py` 的目录当成"命名空间包"放行,所以 `from stable.tool_dispatcher import dispatch` 照样能跑
- **参数/用法**:无需任何配置;本项目 `demo.py:10` 就这么导的。为什么故意不放 `__init__.py`?参考项目想让 `stable/` 保持"一个独立可按路径加载的稳定根"(后面 evolution.py 会用 `importlib` 按文件路径加载它,连包结构都不依赖——那是阶段 6 的伏笔)
- **对比**:普通包(有 `__init__.py`)是"正规门店";命名空间包是"路边摊",能买卖但没有招牌

## 5. 关键顿悟

- **缺陷在 Harness 不在模型**:对照轨迹 0725 证明同一工具确认后没问题;审计轨迹 0711 更狠——删的只是缓存文件,照样违规。**流程违规与删的东西值不值钱无关**,缺的是"先问一声"这个动作。
- **`stable/` 是案发现场,也是今后的可信根**:v1.0.0 从此冻结,后面任何提案都**不许改它**(阶段 10 会用 SHA-256 快照自证这一点)。它甚至没有 `__init__.py`——保持独立,方便被当成"文件"来对待。
- **内存模拟环境是一切离线验证的地基**:`default_env()` 用字典假装文件系统/Git/数据库,所以"删报告""覆盖远端""DROP TABLE"都能在本机安全地重演一万次——没有它,后面的回放验证(阶段 6-7)根本没法做。
