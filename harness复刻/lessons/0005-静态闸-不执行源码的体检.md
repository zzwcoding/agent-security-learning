# 0005 - 静态闸:不执行源码的体检

## 1. 三问(阶段动机)

**位置感**:

```
✅01 缺陷现场 → ✅02 诊断聚簇 → ✅03 确认门禁本体 → ✅04 提案打包 → ✅05 静态闸 → ▶️06 隔离回放(下一站)
→ ⬜07 全量门槛 → ⬜08 反例必拒 → ⬜09 发布决定 → ⬜10 验收入口
→ ⬜11 真实LLM → ⬜12 加固门禁 → ⬜13 收官对照
```

**这一阶段是干嘛的?** 给候选源码装第一道模型外门槛:**不运行它,先体检文本**——大小不超 64KB、语法能编译、导入只准用白名单里的 6 个纯计算标准库、不准出现 `eval`/`exec`/`open`/`__import__` 这些危险内建调用。

**什么需求逼我们这么设计?** 候选的来路是"LLM 生成的文本"(阶段 11 起是真模型)。对来路不明的代码,最危险的动作就是直接运行——`exec` 一行恶意源码,验证器自己就沦陷了。所以执行前必须有一个**完全不需要执行**的检查层:它只看文本长什么样,看不出来安全问题就一票否决,连被 `exec` 的资格都没有。

**它解决了什么麻烦?** 把"这份代码能不能被安全地加载"从玄学变成机械规则。三道关卡全是确定性的:字节超没超、`compile()` 抛不抛异常、语法树上有没有白名单外的节点。同一份提案谁来验结果都一样——这正是"模型外"的含义:**验证不靠另一个 AI 的判断,靠数学。**

## 2. 全链路一览

```
candidate.source(一段源码文本)
      │
      ▼
[关卡0] 字节数 > 64_000? ──是──▶ 六项检查全 False,就地拒绝
      │否
      ▼
[关卡1] compile() 编译 ──SyntaxError──▶ 全 False(static_compile 都过不了)
      │通过 → static_compile ✓
      ▼
[关卡2] _safe_ast:ast.parse 建语法树 → ast.walk 逐节点巡逻
        · ast.Import / ast.ImportFrom:模块名(取第一段)在 ALLOWED_IMPORTS?
        · ast.Call + ast.Name:被调用的名字在 FORBIDDEN_CALLS?
      │违规 ──▶ 就地拒绝(security_scan 不得过)
      │干净 → security_scan ✓
      ▼
checks 字典(六项)──▶ 本阶段 demo 打印;阶段 6-7 接管后四项
```

六项检查的名字在 `CHECK_NAMES` 里一次定齐(与参考一致),后四项 `gate_contract`/`boundary_replay`/`retention_replay`/`confirmation_single_use` 由接下来两个阶段逐个接管。

## 3. 跟着数据走:一行 `import os` 的死亡之旅

往我们的门禁源码末尾偷加一行 `import os`,送进 `validate_candidate`:

1. **关卡 0**:64KB?一行而已,过。
2. **关卡 1**:`compile()` 编译——`import os` 语法完全合法,编译通过,`static_compile ✓`。
3. **关卡 2**:`ast.parse` 把全文变成语法树,`ast.walk` 逐节点巡逻。走到那行 `import os`,遇到一个 `ast.Import` 节点,它的 `alias.name` 是 `"os"`,取第一段 `"os"` 去查 `ALLOWED_IMPORTS`(hashlib/hmac/json/re/secrets/string)——**查无此人**,`_safe_ast` 返回 False。
4. **后果**:`validate_candidate` 就地 `return`,`security_scan` 保持 False,后四项自然也全 False。这段源码永远走不到阶段 6 的 `exec`——它连被加载的资格都没混上。

再看 `eval` 那个坏提案:`preview = eval('1+1')` 语法合法、没有 import,但 `ast.walk` 遇到一个 `ast.Call` 节点,它的 `func` 是 `ast.Name` 且 `id == "eval"`,命中 `FORBIDDEN_CALLS`,同样死在关卡 2。**注意两行的死法不同**:import 死在"白名单查无此人",eval 死在"黑名单当场抓获"——一白一黑,双保险。

## 4. 新技术点:ast 模块

- **名字**:`ast`,标准库,Python 抽象语法树(Abstract Syntax Tree)工具
- **作用**:`ast.parse(源码)` 把文本变成树(程序的结构骨架);`ast.walk(树)` 遍历每个节点。**源码是人读的文本,语法树是机器验的骨架**——检查"代码里有没有 import 了个不该 import 的"这种结构性问题,在树上查节点比在文本上正则靠谱得多(正则会被字符串常量里的假代码骗,比如 `x = "import os"` 在树上只是个字符串,不会误伤)
- **参数**:`ast.parse(source)` 返回 `Module` 节点;`ast.walk(node)` 产器逐个吐出所有后代节点;常见节点:`ast.Import`(import x)、`ast.ImportFrom`(from x import y,模块名在 `node.module`)、`ast.Call`(函数调用,`node.func`)、`ast.Name`(名字,`node.id`)
- **用法**:`evolution.py` 的 `_safe_ast`。这个套路可以直接搬去审任何"不放心但要加载"的配置代码——先 parse 再巡逻,比跑起来再看出事强

## 5. 关键顿悟

- **白名单 > 黑名单**:导入侧只许 6 个纯计算标准库,而不是"禁 100 个危险模块"——黑名单永远列不全(`os` 禁了还有 `posix`、`subprocess`、`socket`……),白名单漏不掉。调用侧的 `FORBIDDEN_CALLS` 才是黑名单,但它只做兜底,主防线是白名单。
- **fail closed 是默认值,不是异常处理**:`checks` 初始化成六项全 False,任何一步走不下去就地 return——"没验过"和"验出问题"的下场一样是拒绝。检查结果字典的初始值本身就是安全姿态(和你主线网关的 fail-closed 同一门风)。
- **静态闸是预筛,不是沙箱——诚实边界**:`getattr(builtins, "eval")("...")` 这种绕法语法树上看不出恶意;AST 只抓"直白的坏"。所以它的定位是**把明显不合格的挡在 exec 门外**,真正的安全保证在阶段 6:就算过闸的候选真是坏的,它拿到的也只有验证器注入的假执行器,碰不到真实环境。**两层各管一段,谁也不吹自己是万能的。**

**捣乱实验**:`python3` 进交互,复现一次巡逻——

```python
from evolution import _safe_ast, ALLOWED_IMPORTS
print(_safe_ast("import json\n"))          # True:白名单内
print(_safe_ast("import random\n"))        # False:白名单外
print(_safe_ast("open('/etc/passwd').read()\n"))  # False:危险内建
```

再体会一下字符串陷阱:`_safe_ast('x = "import os"\n')` 返回 **True**——文本里看着像坏代码,树上只是个字符串常量。这正是"用 AST 不用正则"的理由。
