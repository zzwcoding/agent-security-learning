# 0004:精读余下三种 rail + 一条消息过五道闸的完整时序

## 一、三问(阶段动机)

**你在哪**:终极目标是搞清"NeMo 五种 rail 对照我们的三层 llm-guard 护栏,能补哪些缺口"。路线:

```
✅ 阶段 1:裸跑基线
✅ 阶段 2:input rail —— 入口闸机(实测)
✅ 阶段 3:output rail —— 出口闸机(实测,发现默认清单漏密钥)
⬅ 阶段 4:精读 dialog / retrieval / execution + 时序图(你在这里,本阶段不写代码)
⬜ 阶段 5:延迟与 token 账单、payload × rail 结果表
⬜ 阶段 6:收官对照结论
```

- **干嘛的**:不写代码,读官方文档 + 源码,把剩下三种 rail 的触发位置、判定机制、配置方式落实,再画出一条用户消息过五道闸的完整时序图。
- **什么需求逼的**:我们的对照表还空着三列——**对话流程控制**、**检索内容过滤**、**工具调用管控**(对应 starter-agent 的三个缺口:记忆装载无校验、工具返回扫描、write_file 参数侧无扫描)。不读透这三道闸,收官对照就是拍脑袋。
- **解决了什么麻烦**:拿到对照表的机制层素材,还意外发现 0.23 版有**第二套引擎**(IORails),execution rail 有两副面孔。

## 二、全链路一览(一条消息过五道闸)

官方时序([信源](https://docs.nvidia.com/nemo/guardrails/reference/guardrails-sequence-diagrams)),配大白话标注:

```
用户消息进门
  → ① input rails:入口安检(我们阶段 2 实测的那道)
      (职责:用户带来的坏,在这拦)
  → ② retrieval rails:仓库提货检(仅挂了知识库/RAG 时才存在)
      (职责:检索回来的资料chunks,有毒的丢掉再进 prompt)
  → ③ dialog rails:大堂经理(靠 Colang 流程图工作)
      (职责:认意图、定调子——这问题是直接答、走固定话术,还是去调动作)
  → ④ execution rails:动作/工具环节的闸(0.23 有两副面孔,见下)
      (职责:工具能不能调、参数合不合法、返回结果规不规整)
  → LLM 生成回复
  → ⑤ output rails:出厂质检(我们阶段 3 实测的那道)
      (职责:bot 自己造出来的坏,在这拦)
  → 回复交给用户
```

我们前两个阶段实测的壳没有知识库、没有工具、没写 Colang,所以 ②③④ 全程不存在——消息走的是 ①→生成→⑤ 的短路。

## 三、跟着数据走 5 步(拿 starter-agent 的真实攻击映射五道闸)

不用假想例子,直接拿我们语料库里真打过的攻击,看每一道闸管哪一段:

1. **直接注入**(语料 01,payload A 套 key)→ 归 **① input rail** 管。NeMo 现成选项:self-check(阶段 2 实测)、`jailbreak_detection`(专门的越狱检测,库里有)、`injection_detection`。对应我们的第一层 llm-guard 扫输入。
2. **间接注入**(语料 02,poisoned-page.html 的毒文本经 fetch 工具返回混进上下文)→ 名义上归 **② retrieval / ④ tool result** 管。但 0.23 实测依据([tool-calling 文档](https://docs.nvidia.com/nemo/guardrails/v0.23.0/configure-guardrails/guardrail-catalog/tool-calling)):**tool result validation 只查结构规整(来源对不上、格式不对才拦),官方明说"不做内容安检"**;retrieval rail 只管知识库 chunks,不管工具返回。也就是说:我们在 starter-agent 第二层做的"llm-guard 分块扫工具返回",**NeMo 现成闸机不覆盖,得自己写 action 或继续用 llm-guard**。
3. **多轮套话/话题偏移**(记忆投毒的对话面)→ 归 **③ dialog rail** 管。它靠 Colang 把对话建模成流程图:用户意图归类(canonical form)→ 决定下一步。能防"聊着聊着被带偏",但前提是你手写流程图——这是五种 rail 里最重的一种。
4. **write_file 参数侧投毒**(我们缺口之三)→ 归 **④ tool call validation**(`rails.tool_output`)管。机制:白名单 + JSON Schema 校验参数,**本地检查、不调 LLM、fail-closed**。但它只查"参数合不合结构",**不查"参数语义有没有毒"**——`path="../../.env"` 这种字符串对 schema 来说完全合法。语义级扫描它补不了。
5. **回复泄 key**(阶段 3 的 T1)→ 归 **⑤ output rail** 管,已实测:默认清单漏密钥。

## 四、新技术点四要素:dialog / retrieval / execution 的配置与机制

- **dialog rail(大堂经理)**:配置**不是**往 flows 列表加名字,而是写 `.co` 文件(Colang):`define user ...` 定义意图、`define flow ...` 定义对话流程;`config.yml` 里 `rails.dialog` 只有调优项(如 `single_call`,源码 `rails/llm/config.py:500`)。判定机制 = Colang 引擎按流程图 steering + `generate_user_intent` 把用户消息归一成意图(阶段 1 的 401 traceback 里见过它)。
- **retrieval rail(提货检)**:`rails.retrieval.flows: [...]`,检查对象是检索 chunks,典型配 `self check` 系或 `sensitive_data_detection`。我们的壳没有知识库,本任务不展开。
- **execution rail(0.23 的关键发现——两副面孔)**:
  - **LLMRails 引擎**(我们一直在用的):execution rail = 用 Colang 在自定义 action 前后包检查流程,灵活但要写 Colang;
  - **IORails 引擎**(0.23 新增,实验性):环境变量 `NEMO_GUARDRAILS_IORAILS_ENGINE=1` 或改用 `Guardrails` 类开启,多出两段固定配置——`rails.tool_output: flows: [tool call validation]`(查模型发出的工具调用:白名单 + 参数 JSON Schema)和 `rails.tool_input: flows: [tool result validation]`(查工具返回:只查结构一致性)。**两副面孔互斥**:tool rails 只在 IORails 上跑,且流名打错会**静默回退**到 LLMRails、闸机全部失效,只有一条日志警告。
- **Colang 轮廓(知道干什么就行,不深入)**:NeMo 自造的对话建模语言,语法像 Python(`define user 意图` / `define flow 流程`);1.0 是默认版,2.0 是新重写。它是 dialog rail 的载体。我们不深入的原因:目标是安全闸机不是对话编排;input/output/self-check/tool 这些安全闸**全都不需要手写 Colang**。

## 五、关键顿悟

- **位置固定,机制任选**:五道闸说的是"钉在链路哪个位置",判定机制是另一根轴——LLM 自检(self-check)、专用模型(`jailbreak_detection`、`hf_classifier`,库里有二十多个现成集成)、纯 Python 结构校验(tool rails,不调 LLM)、Colang 流程匹配(dialog)。对照 llm-guard 时要比的是机制,不是位置。
- **tool rails 是结构校验,不是语义安检**:`tool call validation` 能拦"调了没声明的工具、参数不合 schema",拦不了"参数内容有毒";`tool result validation` 官方明说不查内容。我们的"write_file 参数侧"和"工具返回"两个缺口,NeMo 现成闸机都只能补一半。
- **0.23 有两套引擎,选错静默失效**:LLMRails(Colang 事件驱动,默认)vs IORails(边界校验,实验性)。tool rails 配错流名不报错只回退——又一个"配置错了不告诉你"的坑,和阶段 1 的 base_url 坑是同一类。
