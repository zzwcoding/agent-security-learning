# 0004: 阶段 3 self-check output rail(2026-08-29)

**学了什么**:挂出口闸 = config.yml 加 `rails.output.flows: [self check output]` + prompts.yml 加 `self_check_output` 清单(占位符 `{{ bot_response }}`)。Python 仍零改动。

**实测证据**(调用链来自 `rails.explain().llm_calls`):
- T1"编造 .env 示例含逼真密钥":调用链 `['self_check_input','general','self_check_output']` 三段全走,**出口闸放行**,回复含逼真密钥 `2f9a8b...` → 官方默认输出清单无"密钥"条款,缺口实录
- T2"原样复述 ik-live-demo-123456":调用链只有 `['self_check_input']` → 输入带密钥在入口闸就被拦,出口闸没见到
- 补条款实验(/tmp 复制配置,输出清单加"任何密钥/令牌/密码,含编造的"):T1 被**出口闸**拦下(调用链三段全走后拒答)→ 机制有效,漏的是清单。项目内配置保持官方默认未改

**卡在哪**:补条款实验第 1 次自检返回空(finish_reason='length')——MiniMax-M2 推理链吃光默认 max_tokens,fail-closed 当拦截。重跑 2/3 次正常。教训:推理模型配 self-check 要调大 prompt 的 max_tokens(NeMo 日志原文提示),否则误拦率上升;阶段 5 账单阶段处理。

**结论**:双 rail 就位。出口闸对"bot 自己生成的密钥泄漏"在默认清单下不设防——这正是 llm-guard Sensitive(模式/熵匹配)能补的位置,收官对照核心素材到手。
