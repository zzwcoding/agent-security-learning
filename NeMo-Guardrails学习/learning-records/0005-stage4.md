# 0005: 阶段 4 三种 rail 精读 + 时序图(2026-08-29)

**学了什么**(信源都挂在 lesson 0004 里,此处只记结论):
- 官方时序:input → retrieval → dialog → execution → 生成 → output(docs: guardrails-sequence-diagrams)
- dialog rail = Colang .co 流程,config 里 `rails.dialog` 只有调优项(源码 rails/llm/config.py:500)
- retrieval rail = `rails.retrieval.flows`,只管知识库 chunks
- **execution rail 两副面孔**:LLMRails 的 Colang action 包装 vs IORails(实验性,`NEMO_GUARDRAILS_IORAILS_ENGINE=1` 或 `Guardrails` 类)的 tool rails:
  - `rails.tool_output` = tool call validation:白名单 + JSON Schema 校验参数,本地不调 LLM,fail-closed
  - `rails.tool_input` = tool result validation:只查结构/来源一致性,官方明说不做内容安检
  - 流名打错 → 静默回退 LLMRails,闸机全失效,只有日志警告
- 内置库 `library/` 有二十多个现成集成:jailbreak_detection、injection_detection、sensitive_data_detection、hf_classifier、llama_guard、activefence 等

**对本任务对照表的直接影响**(阶段 6 素材):
- 缺口"write_file 参数侧无扫描":tool call validation 只补结构(schema/白名单),语义扫描补不了
- 缺口"工具返回扫描(间接注入面)":NeMo 现成方案不覆盖(retrieval 管 KB、tool result 不管内容)→ 仍靠 llm-guard 或自写 action
- 缺口"记忆装载无校验":五种 rail 均不直接对应,closest 是 dialog/retrieval,待阶段 6 定论
