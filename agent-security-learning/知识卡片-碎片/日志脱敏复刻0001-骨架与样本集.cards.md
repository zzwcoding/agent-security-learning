# 日志脱敏复刻0001-骨架与样本集 —— 知识卡片

### 考卷先行与负例并存(test corpus first, negatives included)

是什么:这是给安全防御系统造测试集的两条顺序纪律：标注好的样本集(在本项目里叫"考卷"[自造]——它就是后面所有脱敏规则的考试题)必须在防御逻辑动手之前定稿；"负例"(长得像敏感信息、其实不该被脱的正常内容)必须和真敏感的正例同一天进考卷——负例与正例，必须在第一条规则写出之前入册。"考卷先行"有现成的行话对应：留出测试集纪律(hold-out test set，动手前封存、验收才启用的考卷)，更早的同构是临床试验预注册(pre-registration，医学期刊编辑国际委员会 ICMJE 的规矩：先注册方案、后招募受试者)。"负例"也有正式定义可挂——软件测试行规 ISTQB(国际软件测试资格认证委员会)给负面测试(negative testing)的官方定义是：按组件或系统"本来不打算被使用的方式"去测它。

为什么重要:顺序反了会得两种病。其一，引擎写完再造考卷：规则会照着自己能做的样子出题，先有答案后出题就成了自我循环，考出来的成绩是虚的。机器学习评测给这类病起过正式名字：测试集污染(test set contamination，又称 benchmark data contamination——被评估的模型考前接触过考题，评测结果失真)；"规则作者顺手出题"是同族病，病根都是出题人与被考者不独立。其二，考卷里若全是敏感正例，规则作者会默认"宁可错杀"，把日志里所有长得像的都脱掉；而日志是给排障人看的，脱过头就废了。负例的存在，逼着每条规则从第一天起就回答"你会不会误伤它"。

我们怎么用:样本集一次配齐三类：密钥类与 PII(Personally Identifiable Information，个人身份信息)类两类正例，外加负例；并把脱敏的目标函数写成"该脱的都脱了 + 不该动的原样留下"——负例就是后一半的验收员。比如长得像手机号的纳秒耗时数字，就是一条负例。

### 同串异义[自造](same literal, opposite semantics)

是什么:同串异义是格式类脱敏的死穴：同一串字符在不同日志语境里语义完全不同，只看格式的规则引擎无从区分，识别只能赌。

一串数字的两次命运:教学样本的客服对话里，用户说"身份证号是 11010119900307721X，手机号 13800138000"，这条里的 `13800138000` 真是手机号。它 11 位、`138` 开头，手机号正则 `1[3-9]\d{9}` 命中得没毛病；性能日志 `latency_ns=13800138000` 里的同一串数字却是一段纳秒级耗时，形状与手机号一模一样，正则见了照样两眼放光。真把它替换成 `[REDACTED_PHONE]`，运维只会一头雾水:我的延迟数据呢?

解决什么问题:这个现象同时撑起误报与漏报两头:形状像就脱，把耗时当手机号，日志被毁；反过来，自然语言口令(如"我网银密码是 Blue moon over river 77")没有格式可查，格式规则永远看不见。补缝的办法分三层。第一层是校验位：银行卡的 Luhn 校验(官方出处是 ISO/IEC 7812-1 标准)定位是错误检测——按模 10 加权求和，专为抓手工输入笔误、OCR(光学字符识别)误读、相邻数字换位这类偶然错误而设计。所以校验位能排除抄写错误与部分伪造，但不能证明卡号真实存在；身份证末位校验同理，验的是"没抄错"，不是"真被签发"。第二层是上下文提分：Presidio(微软开源的 PII 识别与匿名化引擎)的上下文增强是官方实现。一条只是形状像手机号的弱命中，初始分低到 0.01，上下文里出现"手机"这类词就加权到 0.46(数字取自 Presidio 官方教程示例：弱命中 0.01，加上下文相似分 0.45 后为 0.46)。它还支持请求级上下文：把字段名、列名当上下文传入，正文里没出现那个词也能提分——结构化日志的 schema(字段结构约定)自带字段名，等于免费的语境分。第三层才是 LLM(大语言模型)：纯自然语言里的语境与语义裁决，只有 LLM 类引擎能商量。

我们的办法:把一正一负两条同串样本一起钉进考卷，作为规则引擎已知会误报、语义引擎该救回来的经典考题；两种引擎孰能兜住，留给基准数据验证。

### 假值样本构造纪律[自造](fake-sample hygiene)

是什么:这是一条"样本文件自己不能变成泄露源"的工程纪律。测试集里的敏感信息全部用假货，但假货要造得讲究:要么让密钥扫描器认不出，要么用全世界都知道是假的著名假值。

两个手法:手法一，拆字符串拼接。把假密钥写成 `"sk" + "-proj-ABCD..."` 两半：密钥扫描器(GitHub 的 push protection、TruffleHog 这类在代码里搜真实密钥的工具)按 `sk-proj-` 前缀做字面量/模式匹配，拆开后源码里不存在完整字面量，扫描器不报警；而程序运行时拼接出的完整假密钥，照样能拿来考正则引擎。GitHub 的机制分两层：推送时按模式拦截(push protection)是预防层，代码入库后的 secret scanning 告警是事后层。TruffleHog(开源密钥扫描器)更进一步：命中后会拿这把钥匙去真调一次服务，给出 verified/unverified/unknown 三态结论，假钥匙过不了验证、落的是 unverified，不是命中即报警。手法二，著名假值。`4111 1111 1111 1111` 是支付行业通行的公开测试卡号——支付服务 Braintree(PayPal 旗下)的沙箱文档官方将其列为 Visa 测试卡，支付公司 Stripe 的官方测试卡则是 `4242 4242 4242 4242`；各家测试卡的共同点：测试卡号按行业惯例不会被签发为真卡，但 Luhn 校验能通过。`AKIAIOSFODNN7EXAMPLE` 是 AWS(亚马逊云服务)文档里的官方示例密钥——格式完全合规，却人人皆知是假的。

解决什么问题:不讲纪律的测试样本是颗自埋的雷：样本文件被扫描器报警、被当成真密钥走泄露处置，甚至随仓库外流都说不清。连 AWS 官方文档都告诫开发者"不要把访问密钥或凭据信息写进应用文件"——官方都怕人把真的写进去，测试样本更不能长得像真的。纪律让样本做到"格式真实到能考引擎，来源清白到不怕扫描"。这背后还有个通用事实：源码里的字面量与运行时拼出来的值，是扫描器看到的两个世界。

我们的办法:样本集全部照此办理——密钥类一律拆字符串拼接，卡号与云密钥用文档公测的著名假值，全套样本零真密钥。
