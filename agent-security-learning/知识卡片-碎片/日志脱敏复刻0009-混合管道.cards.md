# 日志脱敏复刻0009-混合管道 —— 知识卡片

### 补位不替补[自造](自造英文:always-run backfill scheduling)

是什么:补位不替补[自造](便宜引擎先扫全量、贵引擎总跑一遍只补漏的排班原则)是双引擎脱敏管道的调度设计,在组合文献里属于 parallel ensemble(并行组合:两引擎都全量跑,结果合并去重)。反面写法是条件触发——便宜引擎零命中才请贵引擎出场。动机是单引擎都有死穴:正则微秒级出结果,却抓不住"上海市浦东新区桂花路333弄12号502"这种没有固定格式的住址;LLM 抓得住住址,但单次要两秒以上、报出的值还不干净。要解的从来不是"选哪个引擎",而是"怎么排班"。

解决什么问题:防的是排班错误导致的漏脱,尤其是条件触发。文献里的 cascade(级联)正是靠条件触发省钱:FrugalGPT(提出级联调用思路的知名论文)的思路是先用最便宜的模型回答请求、必要时才升级到更贵的模型(原文:LLM cascade answers a query with cheap LLMs first, escalating to more expensive ones only when needed)。级联敢触发,是因为配了专门的打分器来判"结果可不可接受"——脱敏管道里没有这种判定器,"正则零命中"不是一个合格的触发条件,它隐含"没有格式型敏感就没有语义型敏感"的假设。一条混合样本当场证伪:

```
客服记录:请把补办证件寄到 上海市浦东新区桂花路333弄12号502,收件人电话 13812345678。
```

正则命中手机号(它的地盘),触发条件不成立,LLM 没跑——住址(LLM 的地盘)原样留在脱敏结果里。两种敏感住在同一条日志,条件触发就注定漏掉第二种;结论是脱敏系统保完备优先于省钱,漏一条住址是事故,每条多花两秒不是——这与成本敏感的级联取向正相反,是召回优先的并行组合取舍。补扫对象选"脱敏后的文本"还有个工程红利:回填按文本顺序逐层替换即可,不必把模型报的字符区间换算回原文坐标。

我们的办法:正则先扫全量,LLM 在脱敏后的文本上总跑一遍、专找正则够不着的语义类别,两段命中合并去重——标准的并行组合写法。回归里固定加入两类敏感同现一条日志的组合样本——排班策略要拿最刁的组合考,不能只拿各引擎擅长的单类样本考。

### 枚举约束(JSON Schema enum)

是什么:enum 是 JSON Schema(描述"JSON 该有哪些字段、什么类型、取值范围"的标准规范)的关键字,把某个字段的取值从"随便写"收窄成"只能从名单里选"。官方语义是"把取值限制到一个固定集合"(restrict a value to a fixed set of values):实例值与名单元素逐一相等比较,相等即通过。它配合结构化输出(structured outputs,在解码层强制输出合法 JSON 的机制,已有专卡)生效。这套组合在文献里有专名:constrained decoding(约束解码)——schema 被编译成有限状态机,解码器每走一步都对词表的 logits(候选 token 的打分)做屏蔽,不在名单里的 token 概率直接归零。这不是劝它别乱写——它根本写不出来。

解决什么问题:小模型给所有检出项填同一个含糊类别,比如全部写"敏感值",占位符就全变成 `[REDACTED_敏感值]`。脱敏后文本里看不出哪处原来是卡号、哪处原来是住址,类别区分度全丢。给 type 字段配上中文类别名单(身份证号、住址、口令、金融 PIN 等)后,占位符变成 `[REDACTED_住址]` 这样逐项准确的样子。

一个反向设计决策:名单故意不含手机号、邮箱、银行卡号这些格式型类别——那是正则引擎的地盘,写进名单反而诱导 LLM 越界抢活,又慢又容易跟正则的精确结果打架。

我们的办法:检测 schema 的 type 字段配 enum 名单,实测占位符类别从此逐项准确。名单同时活在 schema、提示词的类别清单与代码常量三处,改一处必改三处——这个重复可以用代码生成消除。

### 占位符污染[自造](placeholder pollution)

是什么:占位符污染[自造]是补扫型管道的一种自伤形态——LLM 在"已脱敏文本"上补扫时,把上一道工序留下的占位符(如 `[REDACTED_PHONE]`,替换敏感值后留下的标记)本身当成了敏感值。它阴险在能通过逐字验收:占位符确实逐字出现在文本里,子串检查挑不出任何毛病。

解决什么问题:不防的话,模型会报出 `{"type": "phone", "value": "[REDACTED_PHONE]"}` 这类检出项并通过验收,回填后占位符被再套一层标记,文本被反复污染,命中统计也被假命中灌水。占位符能过逐字验收,不是验收谓词写错了——谓词本身正确。错在占位符是上一道工序**人为引入的新文本**,它长得就像一个待脱敏的值,识别器没有任何理由不把它当敏感值。社区里常见的两条实践可作旁证,Presidio(开源的个人敏感信息识别与匿名化框架)生态就有:占位符形状要选得让后续识别器不命中;标准做法是基于匿名化返回的替换区间追踪,而不是对脱敏文本重跑识别。补扫选"脱敏后文本"拿了逐层回填的工程红利,就要付"占位符进管道"的代价——过滤规则就是这份账单。

我们的办法:补扫收数前加一条硬规则——以 `[REDACTED` 开头的检出值一律不收;这个判断是纯字符串前缀匹配,不依赖模型自觉。

### 引擎互不裁判[自造](no cross-engine adjudication)

是什么:引擎互不裁判[自造]是双引擎脱敏的裁决原则:两引擎的输出可互当参考,但不互当验收的金标,验收只对统一的人工标注答案进行。它针对的事实是:两个脱敏引擎都会误报,但错的维度不同。正则错在形状巧合——把长得像手机号的纳秒计时值 `latency_ns=13800138000` 当成真命中。LLM 错在语义猜疑——干净日志时而多检出,而且非确定性地时有无。

为什么重要:两个引擎的典型错误发生在不同维度,机器学习文献把这叫 error diversity(错误多样性),并给出组合有价值的条件:成员既要各自够准(accurate),又要互相不同(diverse)。正因犯错维度不同,组合才可能比任何单引擎准——所以引擎之间做共识、投票本是标准手段,业界的银标语料(silver standard,由多引擎共识自动生成的标注)就是这么来的。但组合的裁判必须独立于成员:若用"另一个引擎没检出"去否决某个命中,能执行的只剩"两引擎都命中才保留"——LLM 检出而正则看不见的住址会被整批错杀,误报没少多少,真报先死了。验收评测只能对金标(gold standard,由专家人工标注的答案)进行,让引擎同场对分。

我们怎么用:引擎行为用统一的人工标注基准量化,对上真值的命中才算对;引擎之间可以互看输出当参考,但不拿彼此当验收的裁判。
