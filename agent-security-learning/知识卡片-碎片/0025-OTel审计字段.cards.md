# 0025 OTel 审计字段 —— 知识卡片

### 审计五要素[自造](GenAI audit five fields)

是什么:审计五要素(audit five fields,自造的设计概念,官方无对应标准)是给 Agent 工具调用立的五个必答问题:谁(who)发起、何时(when)发生、以何理由(why)、调了什么工具带什么参数(params)、碰了什么数据(data_class)。五项里只有两项对得上 OTel(OpenTelemetry,CNCF 的开源可观测性标准)为 GenAI(Generative AI,生成式 AI)应用制定的语义约定(semantic conventions,状态 Development、规定 gen_ai.* 字段名的规范)——官方属性:`gen_ai.tool.name`(工具名)与 `gen_ai.tool.call.arguments`(官方定义:"传给工具调用的参数")。官方明确警告后者 may contain sensitive information(可能含敏感信息),这正是 params 记录要过脱敏的动机。who/when/why/data_class 官方没有标准属性,属自定义扩展——放进自造的 `audit.*` 命名空间(namespace,字段前缀约定的归属空间)以便与 `gen_ai.*` 官方前缀区分开,再存进 Langfuse(LLM 应用的观测追踪平台)的 metadata。

解决什么问题:自动摄像头式的旁路观测记的是"模型看见了什么",回答不了追责问题:某次 `write_file` 是谁发起的?为什么这一轮会调它?碰的是用户文件还是沙箱内部?其中"以何理由"必须引用本轮用户消息原文,不能写"用户发起了请求"这类转述——倒查时人对的是原话。data_class 靠一张数据分级表当词典:每个工具登记碰的是什么数据,如 `read_file=用户工作区文件(读)`、`run_command=一次性 microVM(独立内核的微型虚拟机)内部`、`http_post=出网请求(白名单域名)`;新工具进来必须先登记。

我们的办法:五字段写进每条工具调用观测的 metadata——标准两项用 `gen_ai.*` 原名,自定义三项用 `audit.*` 前缀,读的人一眼能分清哪些是标准、哪些是项目扩展。实测一次"看看 workspace 目录里有什么文件"的调用,逐项核对五字段全在案,如 `audit.why=看看 workspace 目录里有什么文件`(用户原话)与 `audit.params={"path": ...}`。

### 审计中间件旁路观测(audit middleware)

是什么:审计中间件指挂在工具调用包装层最外圈(wrap_tool_call 这类统一入口)的记录器:工具真实执行完,由它在旁路补记一条独立观测(形如 `audit:<工具名>`,类型标为 tool),业务工具代码零改动。"挂最外圈包一圈"在 AOP(Aspect-Oriented Programming,面向切面编程)里叫 around advice(环绕通知,把目标调用包在中间的拦截方式),decorator(装饰器)也是同一语义;独立观测的类型对应官方标准字段 `gen_ai.operation.name=execute_tool`(官方对"执行工具"操作的标准命名)。"旁路"是说工具本身不感知自己在被记录——记录不进工具的输入输出,只走观测通道。

解决什么问题:逐个改工具函数加审计代码,既侵入又必然漏——新工具一多总有人忘。这正是横切关注点(cross-cutting concern,Kiczales 等人经典论文中的定义:影响多个模块、却无法被封装进单一模块的程序侧面)的两大后果:scattering(散布:同一逻辑散落各处)与 tangling(缠绕:业务代码里混进无关逻辑)。挂在最外层则所有工具自动全覆盖;审计、限流、认证这类横切关注点全都长在这一层,安全里的拦截型检查(如输入护栏)与它挂在同一层。

我们的办法:工具执行后由中间件写一条带五要素的观测。实测模型调 `list_dir`,平台上出现 `audit:list_dir`(type=TOOL)这条独立观测,业务代码一行未动。

### trace 壳归队[自造](root shell / rejoin into one trace)

是什么:trace 壳归队指每轮对话开始先立一个占位根观测(壳),让后续模型生成、工具执行、审计观测都挂进同一条 trace 的做法。Langfuse(LLM 应用的观测追踪平台)会把收到的每条 OTel(OpenTelemetry,CNCF 的开源可观测性标准)span(一次有起止时间的操作区间)转成一条 observation(观测记录,官方口径 converts into rich Langfuse observations)。OTel 的规则链决定了谁是根:当前 Context(上下文)里没有 Span 时,新建 Span 就是根 span(root span),且每个根 span 必须(MUST)生成新的 TraceId——新根就是一条新 trace,因此先立的壳就是本条 trace 的根。进程内的上下文传递由官方 instrumentation(埋点层)透明处理,跨进程才需按 W3C traceparent(跨服务传递 trace 上下文的标准 HTTP 头)显式注入/提取——壳一立,后续的模型生成、工具执行、审计观测自动归队。

解决什么问题:实测踩坑:没立壳时,审计观测落成了独立根观测——按上面的规则链,当前 Context 里没有壳,新建 Span 就当根、生成新 TraceId。UI 里它自然是单独一条 trace,与 agent 主 trace 割裂,复盘时同一次调用的两半对不上号。

我们的办法:每轮开始先建壳——用 `start_as_current_observation(name="cli-round", as_type="chain", metadata={when, why})`——再进 ReAct(模型边推理边调工具的循环)循环。实测壳一立,三类观测在同一 trace 里完整回放。

### 读 API 不水合(events-only 与读路径降级)

是什么:水合[自造](hydrate,自造词,官方没有对应说法)指观测平台把底层存储的原始数据装配成接口或界面可读详情的动作——写入明明成功、读接口却不回详情,就是"没水合"。官方机制是"写模式决定端点可用性":events-only 是 Langfuse 4.x 的默认写模式(环境变量 `LANGFUSE_MIGRATION_V4_WRITE_MODE`),只写新事件表、不再写旧表;官方说明旧读端点在此模式下不可用——从"旧端点读的正是旧表"可推知 404 的原因,读要改走 Observations API v2(新版读接口)装配详情。官方原话点明:"The legacy and dual modes are migration utilities, not permanent operating modes"(旧模式只是迁移工具,不是长期运行模式)。结论:读路径降级是预期设计,不是写丢了。

解决什么问题:这是个容易误判成"审计没写进去"的陷阱:拿平台 API 验证写入,读不到就当丢了;实际存储里有,UI 是从底层装配后才可见的。旧读端点(traces/observations 这类 GET 接口)全部 404 属预期行为,连刚写入的探针观测都读不回来。

我们的办法:验证改走写端字节(见下一张卡的取证方法),或改用 Observations API v2 做读验证——不只字节取证一条路;并把"观测系统升级会动读路径"记成通用教训:平台读不到不等于没写上。

### OTLP 字节级取证(byte-level verification via OTLP capture)

是什么:指把观测平台的接收地址指到本地收包器(一个本地自起的 HTTP 接收服务),直接检查客户端 SDK(Software Development Kit,软件开发工具包)发出的原始字节。OTLP(OpenTelemetry Protocol)是 OTel(OpenTelemetry,开源可观测性标准)定义的遥测上报协议:OTLP/HTTP 默认端口 4318,载荷是 Protobuf(二进制或 JSON 两种编码),且官方明确"OTLP/HTTP 与 OTLP/gRPC 的 Protobuf schema 相同"——字节是源头事实的标准化载体。"载荷里写了什么,发出去的就是什么"是项目经验推论,不是官方表述,但它是绕过平台读接口取证的前提。

为什么重要:它让"审计字段写没写上"从平台 API 的口说变得可证:读 API 会因写模式降级、不回传详情,但字节是 SDK 发出的源头数据;字节里五字段全在,等于证明客户端确实发出了这些字段。注意:Langfuse 只收 OTLP over HTTP(接收路径 `/api/public/otel` 下的 `/v1/traces`),不支持 gRPC——收包器必须用 HTTP transport,否则根本收不到。

我们怎么用:本地起一个 OTLP 收包器,把 `LANGFUSE_BASE_URL` 环境变量指过去跑一轮对话。在收到的载荷里逐字段核对审计五字段(`audit.*`,即"审计五要素"一卡定义的 who/when/why/params/data_class),全部在案。教训:审计的验证不能只依赖平台 API,能从发出的字节层面取证最稳。
