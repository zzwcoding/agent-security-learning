# 0012 全流程安全总账与迁移指南 —— 知识卡片

### 数据出口泄露五路径[自造](five leak paths of data egress: L1–L3/H/N)

是什么:数据出口泄露五路径[自造]是把"agent 的敏感数据从哪里漏出去"整理成五个固定类别的威胁模型(把可能的威胁分门别类想清楚的清单)。Agent 的日志、trace(跨组件的完整调用记录)、记忆、落盘文件好比几条下水道,泄露沿五条路流。前三条是数据本身出逃。L1 是格式类密钥:API key、JWT(JSON Web Token,带签名的令牌格式)、Bearer 令牌(放在 HTTP 头里、持有即可用的凭据)、连接串口令(如 postgres://user:pass@host/db)随工具输出和调试日志落盘。L2 是结构化 PII(Personally Identifiable Information,个人身份信息):卡号、身份证、手机号进日志,甚至伪装成正常数字,比如把手机号 13800138000 填在"延迟值"字段里。L3 是语义类敏感信息:住址、"我网银密码是 Blue moon..."这类自然语言口令、病历诊断——没有固定格式、正则写不出来。后两条是防御系统自己的内伤。H 是引擎脏输出:LLM 幻觉出的"检出值"被当真回填,或 NER(Named Entity Recognition,命名实体识别,从文本里认出人名电话等实体的技术)把护照号错标成人名。N 是脱敏过度反噬:正常数据被咬掉、调试价值被毁,安全功能自己变成事故——这就是隐私领域常说的 privacy-utility tradeoff(隐私遮蔽越多,数据可用性越低)在脱敏上的体现。

解决什么问题:没有这张清单,防泄露就是东一榀西一榀的补丁;列全五条路,每条路才能配对应的闸,也才知道哪条最挤。这套五分法有两个现成的行业锚点。一是 CWE-532(通用弱点列表里"把敏感信息写入日志文件"的弱点条目)。CWE-532 的原文说:把敏感信息写进日志,"往往会给攻击者提供一条额外的、防护更弱的获取途径"(an additional, less-protected path)。拿到日志就不用再攻破主系统——这是本卡的引申,不是 CWE 原文。二是 OWASP GenAI LLM02:2025(Sensitive Information Disclosure,敏感信息泄露):风险范围圈定 PII、财务、健康记录、业务数据、凭据与法律文书,缓解清单里就有"用模式匹配做遮蔽与标记化"。它把凭据和 PII 并列,与经验事实一致——Agent 日志里最高频的泄露物是 L1 密钥,不是身份证。工具调用参数里带着凭据,日志如实照抄。

我们的办法:五条路各配各的防线——L1 靠自写密钥正则守在线路径,L2 靠格式规则加校验位验证,L3 靠端侧模型(跑在本地的小型模型)离线补扫,H 靠"检出值必须逐字出现在原文"的确定性验收,N 靠负例(长得像敏感信息、其实不该脱的正常文本)和效用分(衡量脱敏后文本还剩多少调试/统计价值的分数)盯住。实测中同一串 13800138000 在样本里是手机号、在负例里是延迟纳秒数,各引擎处理各不相同,正好当检验这套分类的试金石。

### 密钥类规则必须自配(self-supplied secret rules)

是什么:密钥类规则必须自配[自造]是一条脱敏选型原则:API key、JWT、连接串这类凭据的检测,不在通用 PII 工具或可观测平台(Langfuse、OTel(OpenTelemetry,开源可观测性标准)这类 LLM 追踪/观测平台)的能力范围内;要么引入 secret scanning(密钥扫描,专门识别代码与配置里泄露凭据的成熟工具品类)引擎,要么自己写规则,并放进热路径(数据流出时同步处理的在线路径)。

解决什么问题:它防的是"接了框架就等于防了密钥"的错觉。主流 PII 框架的实体清单按个人身份信息组织——人名、电话、银行卡、住址——压根没有"密钥"这个类别,可观测平台的脱敏清单同理;而密钥恰恰是 Agent 日志最高频的泄露物。语义引擎也帮不上忙:密钥是格式问题不是语义问题,`sk-proj-ABCD1234` 该抓哪一截,只有正则认得准——连专做密钥扫描的 TruffleHog 也只认结构化凭据、不认独立口令,同一个道理。这不是某家的缺陷,而是工具定位使然。不过密钥检测并非业界空白:GitHub secret scanning 内置 500 多种密钥模式,覆盖约 200 家供应商;TruffleHog 能识别 800 多种密钥类型(其中 700 多种支持到对应平台主动验证);自写正则的理由是脱敏管线要在日志热路径内嵌运行,而不是业界没有——自写十余条规则,相当于自建一个微型 secret scanner。

我们的办法:密钥类交给自写的正则规则集(十余条,覆盖 Bearer 令牌、Slack token、连接串等形状),部署在在线热路径上。接入任何第三方平台前,先查它的实体/脱敏清单里有没有密钥类,没有就默认不防、自己补——GitHub 官方的 custom patterns(自定义模式)正是"清单没有就自己加"的正规机制。

### 泄露窗口[自造](leakage window)

是什么:泄露窗口[自造]是在线脱敏与离线补扫之间的时间差里,语义类敏感信息"已经落盘、但还没被脱掉"的那段暴露期。它不是可以修掉的缺陷,而是分层设计的固有代价——在线热路径只容得下极轻量的处理:本项目把在线延迟预算定在微秒级,能跑的只有正则(单条微秒级)。能读懂"请把证件寄到上海市浦东新区桂花路333弄12号502"这类住址的语义引擎,单次要秒级(本项目实测冷启动约 1.7 秒),只能安排在离线补扫,两次扫描的间隔就是窗口。这种"实时一道闸加批处理一道闸"的双通道并非自创:ServiceNow 的数据隐私功能就把匿名化分成 real-time(实时)与定时作业(批处理)两类。

解决什么问题:不把窗口摆上台面,会有两种自欺。一种是假装零暴露,以为"分了层"就等于"立刻全脱干净",实际上住址在补扫落地前一直躺在磁盘上。而且窗口内的数据往往已被复制、归档,实际暴露期比名义窗口更长。另一种反过来因噎废食,为了把窗口压到零,把秒级模型硬塞进在线路径,延迟预算当场爆掉。量化后的窗口是可接受、可写进设计文档的工程指标,泄露量上限 = 窗口时长内的敏感信息写入量;业界有同款思路,IBM 年度数据泄露成本报告就用 MTTI(平均识别时间)加 MTTC(平均遏制时间)给泄露生命周期定量,2025 年两项合计 241 天——承认它、盯着它,好过否认它。

我们的办法:采用正则在线全量加语义离线补扫的两段式,把"窗口上限 = 补扫间隔"写进设计文档并与业务方确认,同时注明窗口内的副本和归档让实际暴露大于名义值。对窗口内暴露零容忍的出口(如记忆库落盘),改用能在在线跑的 NER(命名实体识别)系引擎把单一检查点守在写入前。
