# 0033 FGA 授权闸 —— 知识卡片

### tool_pre_invoke 插件钩子（tool_pre_invoke plugin hook）

是什么：tool_pre_invoke 是 MCP 网关（挡在 AI Agent 和工具提供方之间、统一转发并管认证的中间层）在工具调用真正送达上游之前触发的插件钩子（hook：框架预留的挂载点，外部代码可在此插入自己的逻辑），官方给它的定位正是参数校验与安全检查的执行位。钩子有三种出口：放行、改写请求参数后放行、抛出 PluginViolation（插件违规对象，携带拒绝码和原因）拦截。

解决什么问题：check 接口只负责回答，不会自己被问到——授权查询若散落在业务代码里靠人记得调用，总有路径漏问。钩子把"先问裁判"[自造：指 OpenFGA 裁决接口]钉死在执行路径上：不经过它，调用出不了网关。fail closed（出错或拿不准时一律拒绝、绝不默认放行）也在这层延续，正合 OWASP Fail Securely 原则（安全机制失效时要走与"拒绝操作"相同的执行路径）：裁判联系不上（返回 FGA_UNREACHABLE）或身份映射读不到，一律拒绝。

我们的办法：本项目在这个挂载点上装了一个自写的授权插件 fga_check：它从请求的 JWT（JSON Web Token，带签名的登录令牌）里取出用户邮箱，换算成授权引擎里的用户，再向 OpenFGA（Google Zanzibar 论文的开源关系型授权引擎）发一次 check（OpenFGA 回答"谁对什么有什么关系"的裁决接口）。裁决为 false 就走第三种出口，调用被拦成 403（HTTP 的"禁止"响应）。这类拦截插件必须注册成 sequential 模式（顺序执行模式：插件逐个跑、可中途拦停请求）并给高优先级——transform 模式只改写或记录、无权拦停，disabled 则完全不加载。实测两头都有行为——低权身份调 shell 工具收到 `FGA_DENIED - bob(user:bob) 无权执行 shell-run-command`，高权身份同样的调用则真实执行并返回命令输出。把 OpenFGA 服务停掉再调任何工具，全部以 FGA_UNREACHABLE 拒绝，恢复服务即复原。

### 网关粗筛与 FGA 细裁（coarse gateway gate + fine-grained FGA decision）

是什么：这是网关（代理并管理工具调用的中间层）与 OpenFGA（Google Zanzibar 论文的开源关系型授权引擎）之间的分工：网关先用粗粒度检查点筛人，全部通过后才轮到细粒度裁决。用零信任架构的标准词对照：三道粗筛相当于 PEP（Policy Enforcement Point，策略执行点：响应请求、落实访问决策的部件）的预筛职责，OpenFGA 相当于 PDP（Policy Decision Point，策略决策点：评估策略后算出允许或拒绝的部件）。粗筛共三道：第一道是户口[自造：喻账号库里有无登记此人]：用户在网关账号库里存在，缺了报 "User not found"。第二道是可见性（visibility：工具对当前用户是否可见），私有工具不进对方目录。第三道是 RBAC（Role-Based Access Control，按角色分配权限）执行权：普通角色没有 execute 权限。分工口诀一句话：网关管能看什么，OpenFGA 管能执行什么。

解决什么问题：粗细分离让两类判断各归其位。账号存在、目录可见这类粗判断不必画进授权模型（authorization model：OpenFGA 里定义关系如何推导的规则文件）；"这个具体的人能不能执行这个具体的工具"这种细判断，交给关系数据。这套分工在验证时有个易错点：前三道的拒绝是 PEP 在本地做出的（PEP 本地决策），只有过了这三道、问到 PDP 才算拿到远程裁决——把 PEP 本地决策误当成 PDP 的细粒度裁决结果，验证结论就全错。

我们的办法：调试集成时按层认领拒绝，识别依据是各层报错文案不同。再把工具可见性放宽为 public（公开：对所有用户可见）、RBAC 放行执行权，让 FGA 成为唯一决定"能不能执行"的最后一层。

### 认证身份与授权身份分离（authentication identity vs. authorization subject）

是什么：认证身份是令牌（本项目用 JWT，JSON Web Token，带签名的登录令牌）证明的"你是谁"。授权身份是权限引擎里实际参与判定的那个主体，两者可以不是同一个人格。对应标准术语：票面[自造：借彩票"票面"喻令牌里声明的身份]身份就是 authentication identity（认证身份）。映射后的 user:bob 这类字符串才是 PDP（Policy Decision Point，策略决策点）判定所需的 subject（主体：权限判定所针对的对象标识）。在本项目的接法里，票面上的邮箱和 is_admin（令牌里的管理员标志字段）只够通过网关的认证和 RBAC（Role-Based Access Control，按角色分配权限的粗粒度控制）。工具能不能用，由 OpenFGA（Google Zanzibar 论文的开源关系型授权引擎）按一份映射表决定：邮箱映成 FGA 用户，例如 admin@example.com 映成 user:divh、bob@example.com 映成 user:bob。check（OpenFGA 回答"谁对什么有什么关系"的裁决接口）问的是映射后的用户有没有 can_execute（可执行）关系。

解决什么问题：不做这层分离，授权就退化成"持票即有权"——票里写什么身份就信什么。OWASP 授权清单把底线写成 "deny by default"（默认拒绝：凡未被明确允许的一律不给）：令牌只负责验明正身，权限由授权引擎里的关系数据说了算。它还有一条配套要求：失效的访问控制检查要集中到一处统一处理——身份映射读不到就属于这类失效，所以同样落进唯一的拒绝出口，而不是被当成"查无此人即放行"。票面标志再高，过了前置层还要看映射后的主体在关系图上有没有可达路径。

我们的办法：插件内置邮箱到 FGA 用户的映射表；实测两个权限不同的身份都能过完前置层，但只有管理员票在 check 处被放行并真实执行了 shell 命令——两张票都合法，结局由映射后的授权关系定。通用纪律：生产环境这层映射应交给 IDP（Identity Provider，统一发放身份的身份提供方）按 OIDC（OpenID Connect，基于令牌的标准认证协议）惯例用组或 scope（令牌里声明的权限范围字段）决定，而不是手写表。
