# 自修改复刻0008 发布决定与manifest —— 知识卡片

### 发布决定公式[自造](release decision formula)

是什么:发布决定公式[自造]是全部检查跑完之后"由谁、按什么规则说可以上"的最终裁决式,写成一行就是:`accepted = candidate.get("changed", False) and bool(checks) and all(checks.values())`。它对应发布领域的门禁实践:质量门禁(quality gate,衡量代码达标与否的一组条件)与部署门禁(deployment gate,满足既定条件才放行部署),经典问法是"今天能不能把项目发布上线"。业界门禁常留人工审批一环,本公式更严:决定是一段确定性代码,不是一个角色,同一个候选[自造](改出来、还没验证转正的草稿代码)谁来跑都是同一个决定。

为什么重要:如果"能不能发布"由生成补丁的一方自己顺口说了算,验证体系就是摆设——考生自己给自己打分;将来换成真实大模型生成补丁时,这一点只会更要紧。公式还有两个易漏的细节。其一,`bool(checks)` 守卫:灯表[自造](候选放行前的固定格数布尔检查表)为空也算不合格——Python 官方文档写明 `all()` 传入的序列为空时返回 True,"没跑检查"会被误判成"全过",这里显式堵上。其二,"连改都没改"的候选(`changed=False`)哪怕检查全绿也拒,理由是"没有改动稳定版[自造](自我修改系统里作为修改对象的正式代码区)源码"——自我修改连改都没改,不算完成修复。

我们怎么用:决定只有两个出口——有实际改动且灯全绿才放行进灰度(灰度发布:canary release,新版本先放给一小部分真实用户、稳定版继续承接主要流量),否则拒绝;决定与理由一起产出,机器读决定、人读理由。

### 发布清单(release manifest)

是什么:发布清单[自造](release manifest,把发布决定连同全部依据固化成的一份可审计文件)是发布时把决定与依据固化落盘的机制。"release manifest"并非业界标准词,对标的是软件供应链的证明件(attestation)思想:SBOM(软件物料清单,类似一份配料表)与供应链分级标准 SLSA 的出处证明(provenance,关于产物"在哪、何时、如何制成"的可验证信息);in-toto 是这一族里较早且知名的标准。哈希锚定产物、diff(diff:逐行写明删了什么、加了什么的改动说明书)锚定改动、检查结果锚定验证、出处锚定来历、理由锚定拒绝——一句话:结论可以不信,证据必须齐全。

解决什么问题:发布环节光吐一句"行/不行",事后没法复核;有了 manifest,任何人(审计者、未来的你)拿着它就能复核这个决定,不需要重跑整个流程。三方指纹里回滚哈希等于稳定版哈希——回滚目标就是现在生产上跑的这个版本,不是"某个老版本";"最小 diff"也从口号变成 patch_size 里可核查的数字。一份好候选的 manifest 长这样:

```json
{"stable_sha256": "3fa8...", "candidate_sha256": "9c2d...", "rollback_sha256": "3fa8...",
 "patch_size": {"added": 8, "deleted": 4, "changed": 12},
 "provenance": {"generator": "deterministic", "model": null, "api_calls": 0}}
```

provenance(出处记录)写明补丁在何地、何时、经何步骤生成(where / when / how),调没调模型,留底待查;换成大模型生成后这一栏会是另一副面孔。

我们的办法:manifest 由发布决定代码在裁决时同步生成并落盘,实测好候选与被拒候选各存一份、字段对齐。

### 放行只到灰度[自造](release only up to the canary stage)

是什么:放行只到灰度[自造]指发布决定通过后的落点不是生产,而是灰度这一档缓冲区:经典灰度发布(canary release)按业界定义是逐步把新版本放给一小部分真实用户。本系统里,候选[自造](改出来、还没验证转正的草稿代码)只在容器内的验证流量里试跑、真实用户碰不到。它更接近镜像流量(shadow/mirrored traffic,把请求复制给新版本、真实用户不受影响)与暗启动(dark launch,真实负载下运行但功能隐藏)一族。清单(发布清单:把发布决定连同全部依据固化成的一份可审计文件)里 `scope` 字段写死"shadow traffic only; stable remains unchanged",把上线半径钉死——决定只到这一档,越过去要有新的证据。

解决什么问题:灰度是发布系统和生产系统之间的缓冲带;若放行即上生产,一个漏网的坏补丁就直接打给全部用户。业界把放量本身当决策:canary 本质是分阶段放量(staged rollout),每加大一档流量都算一次新的发布决定,要有新证据才继续。配套的关键设计是回滚触发条件(rollback trigger)预先写死在清单里,例如"任何一次不可重试错误重复,或临时恢复回归,立刻回滚";这也早有先例——业界称之为"集群免疫系统"(cluster immune system),回归指标一超统计显著性阈值就自动回滚。触发条件在发布前定好,不是出事后临场争论。

我们的办法:清单的灰度栏写死镜像/影子验证流量的范围与预声明的回滚触发条件,稳定版[自造](自我修改系统里作为修改对象的正式代码区)一个字节不动;退路健康另有专门的回滚检查背书。

### 拒绝留档与全因枚举[自造](rejection archival & full-cause enumeration)

是什么:拒绝留档与全因枚举[自造]指被拒候选[自造](改出来、还没验证转正的草稿代码)也要落一份与放行清单平级的存档。拒绝理由还要把灯表[自造](候选放行前的固定格数布尔检查表)里没过的灯全部列出来、而不是只报第一盏。NIST(美国国家标准与技术研究院)把审计日志(audit log)定义为"系统活动按时序排列的记录,含给定时段内的访问与操作"——审计对象是全部系统活动,不放行的同样在册。被拒候选的理由栏形如 `"failed gates: security_scan, sandbox_execution, ..."`——审计者能看清它死得多彻底。

解决什么问题:只报第一个失败项,审计者会误以为后面的检查没跑或没问题;全列出来,才看得出整条验证链每一格都被正确触发过。"全因枚举"没有单一对应的标准文档,但有两层近亲:工程界"一次性报告全部错误"的老惯例(编译器、表单校验都这么做),与审计记录完整性要求(日志须足以重现事件序列)。"拦了什么也要留下记录"本是安全审计的通用纪律,这里把它落成结构化档案:拒绝理由机器可读、人也读得懂,哪些提案被拒过、为什么,本身就是审计的一部分。

我们的办法:好候选与捣乱候选(比如偷运 `import os` 的)各落一份清单;实测捣乱候选在静态检查就被拦下、后续检查全灭,理由栏把每一盏没亮的灯都点了名。
