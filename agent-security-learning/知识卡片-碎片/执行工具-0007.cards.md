### subprocess 列表形式:代码不经 shell 解释(subprocess List Form, No Shell Parsing)

**是什么**:`subprocess.run([sys.executable, "-c", code])`——把程序和参数**逐项**交给操作系统,不经过 shell 解释;对照阶段 4 的 `shell=True`,那种形式下命令文本被 shell 完整解析(`;`、`&&`、重定向全生效)。`sys.executable` 保证跑代码的和跑工具的是同一个 Python(同一个 .venv)。
**解决什么问题**:列表形式下,代码字符串只是"python 的 -c 参数",里面就算写了 shell 语法也不会被解释——从机制上削掉一层注入面,而不是靠检查堵住。
**我们的办法**:`execution_tools.py:36`:`subprocess.run([sys.executable, "-c", code], capture_output=True, text=True, timeout=30, cwd=WORKSPACE_DIR)`。与执行工具-0004「shell=True」卡对照读:同一个 subprocess,传参形式决定 shell 解释器在不在链路里。

### 安检流水线是可复用的,不是 shell 专用(Reusable Gate Pipeline)

**是什么**:语法(免费、有标准答案)→ 筛子(免费、死板)→ 法官(花钱、会理解)三道闸,从 shell 命令原样复用到 Python 代码执行——换种输入照样一层层过。过闸顺序就是成本顺序:便宜的先挡,贵的只处理灰色地带。
**解决什么问题**:证明防御设计可以"换壳不换芯"——新工具进门不用重新发明安全机制,复用同一条流水线即可。
**我们的办法**:`code_interpreter` 实跑四案:干净代码全过、`def broken(:` 闸 1 带行号拒、`os.system('echo pwned-by-code')` 法官连动机都点破后拒绝、`open('hello.txt').read()` 误伤被法官救回——阶段 5-6 在 shell 上演过的戏码在代码上原样重演。

### 危险模式表按"语种"分组(Per-Language Denylist Patterns)

**是什么**:黑名单的条目因执行语种而异——shell 防 `rm -rf`,Python 防 `os.system / eval / exec / open(`,因为两种输入"开门作恶"的方式不同。参考项目的模式表就是按语言分组的。
**解决什么问题**:一份通用名单防不住所有语种;每种执行通道有自己的"通向危险的钥匙",筛子得认得本语种的钥匙。
**我们的办法**:`open(` 上黑名单是**故意的粗糙**——子串匹配分不清读和写,但筛子的职责只是"喊法官来看看",精细判断归法官。这再次实锤执行工具-0005 的分工:别指望黑名单精细。
