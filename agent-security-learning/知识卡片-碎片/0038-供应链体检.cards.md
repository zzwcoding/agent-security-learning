# 0038 供应链体检 —— 知识卡片

### 描述投毒（tool description poisoning）

是什么：描述投毒指攻击者在第三方工具的描述文本里夹带恶意指令、诱骗 Agent 去执行的供应链攻击（supply chain poisoning：毒藏在 Agent 拉进来的上游依赖里）。它与传统恶意包的分界在毒藏的位置：恶意包的毒在代码里、要靠执行才作恶，这种毒在元数据里、不需要任何代码执行就生效。攻击面成立的原因是工具描述本质是给 LLM（大语言模型）读的提示词而非给人看的注释，Agent 每次加载工具清单都会把描述原文读进上下文。

怎么得手：典型手法是发布一个功能人畜无害的 server，把"读私钥、访问网络、别告诉用户"这类指令藏进工具描述，Agent 拉取工具清单时读到即中招。毒能一路畅通，常因为接入方对上游描述照单全收（登记即盘点[自造]：登记时亲自拉取上游工具清单并入库的机制），描述里藏了什么没人审。例如自制毒样本把"窃取 SSH 私钥、对用户隐瞒"写进一个加法工具的描述，接入前无人察觉，直到体检扫描才被打出满分风险。它还有更阴的变体：tool shadowing（工具影子：一条毒描述操纵其他本可信的工具把数据外传）。识别线索仍在描述本身，看到"读文件、访问网络、对用户保密"这类字样红旗立起。

我们的对策：接入 MCP 网关（代理并管理多个 server 工具调用的中间层）前用 snyk-agent-scan 这类 Agent 专用扫描器把全部上游依赖体检一遍，毒在准入层被筛出。实测自制毒样本被扫出满分，但体检不承诺百分之百，漏网的仍由运行时防线接住。

### snyk-agent-scan（Snyk 的 Agent 供应链扫描器）

是什么：snyk-agent-scan 是 Snyk（以漏洞数据库起家的开发者安全厂商）推出的 Agent 专用供应链扫描器，体检对象是 Agent 拉进来的全部上游依赖。它采用风险打分制：按十余个风险类别逐项评估再汇总成分，检测面比"只查漏洞"宽得多。覆盖面含已知漏洞（SCA，Software Composition Analysis，软件成分分析：把组件对照漏洞库查已知问题）、提示注入与工具投毒，还查 toxic flows（毒性数据流：数据跨工具流转组合后是否危险）和 skills 载体（藏在技能文件里的毒）。这份体检报告实质是一份 SBOM（Software Bill of Materials，软件物料清单：记录一个软件用了哪些组件及其供应关系的正式清单），等于把接入的依赖正式盘点成册。

解决什么问题：接一个第三方 MCP server（按 MCP 协议给 Agent 提供工具的服务）等于拉一个上游依赖，描述投毒的毒正从这里进。扫描器把这层筛查做在接入之前，已知毒样本在门口就被拦下，但不承诺全拦。工作机制：逐个问受检样本"允许启动？"（默认拒绝：不给明确许可就不运行），同意后拉取工具清单、审描述、打风险分，报告列出需人工复核的高危项。

我们的办法：把三个干净 server 与一个自制投毒样本混成一份送检清单跑了一遍。实测毒样本的加法工具被打出满分，报告点名两条毒指令：窃取 SSH 私钥、要求对用户隐瞒。

### 受检即运行（run-to-inspect）

是什么：受检即运行[自造]指投毒检测绕不开的一个约束：工具描述只有把受检 server 进程拉起来、实际走一遍工具清单拉取才拿得到。所以体检必须先运行不可信样本——检查动作本身给了毒在自己机器上执行的机会。

解决什么问题：这是个自举困境：想知道样本毒不毒，得先给它跑起来的机会，而毒样本跑起来就可能当场作恶（读私钥、向外连接）。扫描器的解法是把启动决定权交还用户：交互模式默认逐个问"允许启动？"且拒绝是默认项。要全自动跑（比如 CI，Continuous Integration，持续集成：提交代码后自动执行检查的流水线）则必须显式传 `--dangerously-run-mcp-servers` 这个名字里带"危险"的开关——官方把体检的自身风险直接写进了开关命名。体检不是零风险动作，这层自身风险要显式管理而不是默默承受。

我们的办法：扫描器对每个样本逐个询问、拒绝是默认项；本次实测用脚本统一应答跑通流程，逐个确认是更稳妥的用法——最不可信的恰恰是被启动的东西。

### 投毒样本灵敏度测试（poisoned-sample sensitivity test）

是什么：投毒样本灵敏度测试[自造]是验证毒检测器灵不灵的评估方法：自己造一个已知有毒的样本，混进干净样本一起送检，用"毒是否全被抓获"当判据。已知有毒靠的是 ground truth（底真：评估里事先写好的标准答案）在手，毒是什么、藏在哪完全可控。

为什么重要：它把"扫描器有效"从厂商宣传变成已验证的事实——扫描器自己也是第三方依赖，体检工具不能只信不验。它与本项目评估隔离边界时用的逃逸探针[自造]（在目标环境里跑一段固定脚本、把输出当口供的自测方法）同一思路：都是拿自制而答案已知的样本实测防线。但量级要诚实：单样本只是冒烟级验证（只证明"这条毒能被抓住"的最低限度检验），不等于基准级灵敏度。学术基准靠上千条标注样本统计攻击成功率。InjecAgent（提示注入攻击的学术评测基准）测出顶级模型仍有约四分之一中招；另一学术基准更测出越强的模型反而越易中招。这类统计结论单样本给不出。

我们怎么用：造了一个伪装成加法计算器的毒 server，其 add 工具实际窃取 SSH 私钥并指示 Agent 对用户隐瞒。把它与三个干净 server 混在一起送检，实测毒样本被扫出满分风险、毒全被抓。报告同时列出需人工复核的高危项——灵敏度验证通过，不等于可以免掉人审。

### 三条红旗人工复核（three red flags review）

是什么：三条红旗人工复核[自造]是扫描出高危项之后、接入决定之前的人工复核方法：对照三条特征逐条核查。一看功能不匹配（工具声称的用途与描述里要求的能力对不上，例如加法工具却要求读文件、访问网络）。二看要求隐瞒（描述指示 Agent 对用户保密、不汇报某些行为）。三看敏感数据进参数（描述诱导把私钥这类敏感内容当作工具参数传出去）。

为什么重要：扫描器打分只是初筛，最终接不接入要人来拍板。固定三条红旗让"看什么"有章可循，人工复核不退化为凭感觉的自由发挥。三条红旗抓的是毒指令的主流意图：窃取敏感数据、再瞒着用户。但它有已知盲区：破坏性毒指令（删文件、毁数据这类搞破坏而不偷数据的毒）不窃敏感数据也常常不要求隐瞒，三条红旗一条都套不上。扫描器的风险分类里"破坏性能力"本就单列一类——三红旗是速记不是完备分类，红旗套不上只能记"未见已知模式"、不能记"无毒"。

我们怎么用：对照体检报告的高危项逐条复核。自制毒样本命中要求隐瞒、敏感数据进参数两条；加法工具却涉私钥，功能不匹配也成立。人工结论与机器打分互相印证。

### 体检与防线双层（admission screening + runtime defense）

是什么：体检与防线双层指供应链防护的两层分工：接入前静态体检把已知毒拒之门外，运行时动态防线接住体检漏网的毒。按行业分类描述投毒属依赖类威胁——OWASP（发布权威安全清单的行业组织）把"引入了带漏洞或被投毒的依赖"列为供应链最常见威胁。毒从代码搬进元数据，等于供应链攻击在 LLM 时代的延伸。静态体检指接入前对上游依赖做的一次性扫描，动态防线指每次工具调用都要经过的在线防线，两层互补、谁也不替代谁。

解决什么问题：单层防线不该被信到底，学术基准测出即使顶级模型也仍有约四分之一的提示注入会中招。它具体防两个极端：其一是"体检过就裸奔"，误把扫描当免疫证明而拆掉运行时防线；其二是"有防线就不体检"，让动态防线独自面对全部毒样本，工作量没有前移。体检的价值是把漏到运行时防线的毒压到接近零，而不是证明毒不存在。本项目运行时这层由四道组成：授权闸[自造]（每次工具调用先做权限裁决）；任务票[自造]（每轮任务现签的短时效工具许可令牌）；D4 规则[自造]（调用目标必须出现在本轮用户消息里的检查）；语义自检[自造]（用 LLM 审内容有无夹带指令）。

我们的对策：要接入 MCP 网关的第三方 server 一律先体检再挂上来。实测自制毒样本在体检层即被扫出，没有走到运行时那一层。
