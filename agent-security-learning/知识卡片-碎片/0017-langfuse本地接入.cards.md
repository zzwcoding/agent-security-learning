# 0017 langfuse本地接入 —— 知识卡片

### Langfuse 自托管观测平台(self-hosted LLM observability)

是什么:Langfuse 是给大模型应用做 tracing(链路追踪:把一次请求经过的每一步录成可回放档案)与可观测的开源平台。它不是装完即用的库,而是要自己跑起来的一整套数据系统——官方对自托管的描述是:跑的正是 Langfuse Cloud 背后的同一套基础设施。本机实测形态是 6 个容器(2 个应用 + 4 个存储)——应用容器是 web 管界面与回放,以及把上报事件分拣入库的 worker。存储的分工比"元数据 vs 明细"更专业——postgres 是事务型主库(OLTP,逐行增删改、要强一致的数据),管账号与项目。clickhouse 是列式分析库(OLAP,海量明细按列存、聚合查询快),放录像明细。redis 当上报队列,agent(自主调用模型与工具完成任务的应用程序)发完即走、不阻塞对话。minio(兼容 S3 的对象存储)存超长文本等大字段。摄取路径值得记住:web 分批收到上报后,先把原始事件落进对象存储,redis 里只存排队引用。worker 再从对象存储取出、写入 clickhouse——先落盘、处理成功才入库,中途故障不丢数据、可重放,这才是"发完即走"的真正底气。

解决什么问题:终端日志是一次性流水,滚过就没;复盘攻防需要能倒带、能逐帧看、能搜索筛选的结构化档案。选型上还有一层:观测数据本身是敏感资产,trace(一次完整问答录下的完整档案)里躺着用户输入、工具返回甚至密钥。发去 SaaS(厂商托管的云端版)等于把攻防演练录像存到别人服务器,真实安全项目里常是合规红线。自托管的代价是自己维护 6 个容器,收益是数据不出本机、能随便折腾(掩码、删库重来)。同时要知道边界:官方把 docker compose(Docker 官方的多容器编排工具)部署定位为本地试用——单机、无高可用、无备份,不是生产形态。

我们的办法:用 docker compose 在本机拉起全套容器,注册建项目后拿到成对密钥——public key(标明录像归属哪个项目的门牌号,可出现在客户端代码里)与 secret key(配对才有写入权限的钥匙,绝不进代码)。实测拉起 6 个容器(2 应用 + 4 存储),一句"workspace 里有哪些文件"全程录成完整 trace,可逐步回放当证据。

### 回调旁路观测(LangChain CallbackHandler)

是什么:回调旁路观测,是不站在业务调用路径上、只从旁边接收事件记录的观测方式,负责给 Agent(自主调用模型与工具完成任务的应用程序)全程录像。机制上,LangChain(大模型应用编排框架)与 LangGraph(其上的 Agent 运行时框架)在执行链上预埋了一圈广播点,即 callback(回调)机制——官方称它是挂钩进组件执行过程的标准机制。Langfuse 的 CallbackHandler 就是接广播的听众,提供了现成实现,自动捕获 LLM 调用、工具调用、检索步骤(retriever,框架里"去知识库取资料"这类环节)和编排链的 trace。关键性质是"只听不动手":与中间件(站在调用路径上、手里有拦停权的检查层)对比,回调只接收事件、没有返回干预的通道,拦不了也改不了,接上它业务行为零变化。

解决什么问题:要给已在运行的 Agent 补全程录像,又不能动编排结构与防御逻辑。回调是框架原生扩展点,改一行配置就能接入。上报本身——攒批、发送、进程退出时 flush(清空缓冲强制发完)——全由 SDK(软件开发工具包)在后台完成,业务代码一行不用写。

我们的办法:只在每次 Agent 调用的 config(调用的配置字典)里加 `"callbacks": [handler]` 一项,平台地址与密钥全从环境变量读。实测一句"workspace 里有哪些文件"被录成 7 条观测(1 个根链 + 2 次模型生成 + 1 次工具调用 + 2 个内层编排链),与执行步骤一一对应。

### trace/span/observation 数据三件套(trace, span, observation)

是什么:Langfuse 把观测数据组织成三件套:trace(一次完整问答的案卷)、span(案卷里按时间贴的一张张纸条,一次模型调用或一次工具调用各占一张)、observation(官方对每张纸条的统称)。这套分层不是 Langfuse 自创,底层直接建在 OpenTelemetry(OTel,CNCF 维护的开源可观测性标准)上。但对应关系要分两层说。类型分类是 Langfuse 自有的——官方把 observation 分成 event(瞬时点)、span(区间)、generation(模型生成)、tool(工具调用)、chain(编排链)、retriever(检索)、guardrail(护栏动作)等十来种。类型名 span 与通用区间概念同名,一个是记录类型、一个是概念。与 OTel 对齐的是属性层——OTel 的 GenAI 语义约定(semantic conventions,规定一次 LLM 调用该记哪些 `gen_ai.*` 属性的行业规范)管的是模型名、token(模型计费计量的文本单元)用量这类字段记什么,Langfuse 沿用的是这套字段口径。还有一条官方事实:所有 observation 在库里概念上是同一张平面表,树状层级只是父子指针搭出来的视图——绕过界面直查库表核数,正是走的这层。

解决什么问题:终端日志是平铺流水,看不出谁套谁;trace 是树而不是流水账——根链套模型链,模型链套生成或工具调用。父子关系两侧各有记法:框架侧靠 run_id(每次操作的唯一编号)与 parent_run_id 串联,Langfuse 侧靠父 observation 的 id 挂接,界面上的缩进树由此而来。每张 span 还记下完整输入输出、耗时与 token 数,事后能搜、能筛、能对比。

我们的办法:例如用 API 核对一次"workspace 里有哪些文件"的问答,查得 7 条 observation(1 根链 + 2 次模型生成 + 1 次工具 + 2 个编排链),类型与嵌套和执行步骤一一对应;复盘时再靠 level(每条观测的严重级别,界面按它着色)把异常从正常流水里筛出来。

### 图外观测盲区与手动补录(out-of-graph blind spot & manual span)

是什么:图外观测盲区[自造](自动录像只覆盖框架生命周期内的事件,框架之外的安全动作不留任何痕迹的现象)是旁路观测的覆盖缺口。旁路观测,指从旁边接收事件记录、不碰业务行为的观测法。输入护栏[自造](拦在用户消息进入模型之前的注入检查点)拦在消息进入 Agent 运行图之前,此时图(LangGraph 把一轮对话编排成的节点执行流)还没启动。框架没发过任何事件,这次攻击在观测平台上就彻底不存在。现象是监控大屏岁月静好,攻击者却已经敲过一次门。

解决什么问题:拦截成功本身是必须留档的安全事件,自动摄像头却天生录不到它。补法是 SDK(软件开发工具包)的手动开单接口 `start_as_current_observation`(手动开一张 span——案卷里的一张纸条——并自动计时的方法)。在被拦分支里开一张观测:as_type 填 "guardrail"(官方定义是防止恶意内容或越狱攻击的组件,界面上渲染成护栏图标),写入输入原文、判决与注入分数。level 填 WARNING(警告级,界面标黄,与正常 trace 一眼区分)。最后调 flush()(清空缓冲、强制立即上报)——SDK 默认在后台排队攒批,官方说法是借此优化 API 调用与网络等待,但攻击现场等不起批次间隔。官方还提醒,短命进程退出前要显式 flush,否则可能丢事件。好在 flush 失败只重试、不抛异常,笔录不会拖垮业务。这套实践可称拦截笔录[自造](把被拦攻击记成可查记录的做法)。

我们的办法:图外一事走手动开单,图内每步走自动录像,两条路汇进同一个 trace 仓库。实测一条卡通 jailbreak(假扮合法身份、要求忽略之前所有指令的攻击)注入分数 1.0 被拦后,列表里多出一条 GUARDRAIL 类型的 WARNING 记录,与放行的正常问答同列可对照。

### 客户端掩码(client-side mask function)

是什么:mask(掩码)函数是数据离开本进程之前过的最后一道闸——官方定义正是"在 trace 数据离开你的应用之前抹掉敏感信息"。观测 SDK(软件开发工具包)每次上报字段(输入、输出、元数据)都先交给它,它返回什么服务器就存什么,明文永远不落到观测库里。挂法有两代:本机用的是客户端构造参数 `Langfuse(mask=fn)` 这个旧式钩子;官方现推荐 `mask_otel_spans`——旧钩子看不到第三方 instrumentation(第三方自动埋点库)生成的最终原始 OTel(OpenTelemetry,CNCF 开源可观测性标准)span 属性,新接口直接对最终 span 生效。

解决什么问题:观测面(监控系统里存放的数据面)也是攻击面(可能被攻击者触碰的暴露面)——trace 里躺着用户输入、工具返回甚至密钥。mask 与输出护栏[自造](拦在模型输出送回用户之前的检查点)的分工是:护栏管"模型不该说的话",mask 管"监控系统不该存的话",各管一段互不替代。它和"事后去数据库删数据"有本质区别:mask 在客户端执行,明文根本没离开本机,而事后删除时明文已经落过盘,窗口期就是事故期。行业旁证是 OTel 的 GenAI 遥测默认连 prompt 内容和工具参数都不采集——默认这些字段就含敏感数据。实测还发现一层互保:含密钥的工具返回会被工具返回护栏[自造](拦在工具结果回喂模型之前的检查点)先拦下、根本到不了模型,防御栈顺带保护了观测面。

我们的办法:写递归掩码函数——字符串按正则打码(密钥词 key/secret/token/password 后跟等号或冒号的片段换成 `***`),字典与列表逐层下钻;挂载时先建带 mask 的客户端、再建 CallbackHandler(回调处理器,自身没有 mask 参数),后者才继承设置(官方新姿势 mask_otel_spans 则对 handler 生成的 span 自动生效,无需讲究这层顺序)。实测嵌假密钥的攻击 payload(攻击者投递的恶意文本本体)被拦后,直查底层明细库,存的是 `INTERNAL_API_KEY=***`,明文未出库。

### Docker Compose 声明式编排(declarative multi-container orchestration)

是什么:Docker Compose 是 Docker 官方的多容器编排工具——官方定义:定义和运行多容器应用的工具,全部服务写进单个 YAML 配置文件(YAML,缩进式的结构化配置格式)。用一个 yml 文件声明"要哪几个容器、各自什么镜像、谁等谁先起、端口怎么映射、数据存哪",一条命令全部拉起,生命周期一起起、一起停。相比手写逐条 docker run,增益在声明式管理——只描述"要什么状态"而不写操作步骤。"谁等谁先起"有精确机制:依赖顺序靠 depends_on 声明,但短语法只等对方"启动了"、不等"健康了";要等 healthcheck(健康检查)通过,必须写 `condition: service_healthy`。

解决什么问题:观测平台是典型的多容器系统(本机 6 个容器),手写逐个启动繁琐又容易漏掉依赖顺序;compose 把整套拓扑收敛成一个可版本管理的文件。另有一条安全纪律:官方部署指南第一步就是"更新 compose 配置文件里的密钥再启动"。文件里的 CHANGEME 占位密钥是全网公开值——哪怕实例只跑在本机,也等于全网共用一把锁,起服务前要先换成随机值。

我们的办法:官方 compose 文件原样使用,只改四处环境配置——关掉向官方回传的使用遥测(安全项目的观测数据不外发),三个加密密钥换成随机值。后台拉起 6 个容器后浏览器界面即用,日常排查看 `docker compose ps`(各容器健康状态)与 `docker compose logs -f 服务名`(盯单个服务日志)。
