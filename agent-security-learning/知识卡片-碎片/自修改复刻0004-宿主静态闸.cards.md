# 自修改复刻0004 宿主静态闸 —— 知识卡片

### 检查灯表[自造](gate light table)

是什么:检查灯表[自造]指把候选放行前的全部检查组织成一张固定格数的布尔表:表从全灭起步,过一关亮一格,发布决定退化为"数绿灯"。业界管这类机制叫 quality gate(质量门禁)——SonarSource(SonarQube 背后的公司)的文档说它"通过回答唯一的问题:我的项目可以发布了吗——来执行质量策略",条件本身是事先固定好的一组。好比体检报告的指标栏[自创比喻]——一格一项、亮没亮一眼可查,不存在"考官觉得差不多就行"的自由裁量。

为什么重要:它让"能不能发布"不依赖任何临场判断,判断越少、操纵空间越小;它也让验证体系可以逐格点亮、逐步建设,每新增一种检查就是多亮一格,而不是往一个函数里堆 if。学界有同款思路:论文 AutoSafeCoder 让静态分析与模糊测试(fuzzing,喂随机输入找崩溃)作为先后两道关卡接力把关。灯表还诚实表达进度:只亮两格就明说"离能发布还早",不会被误读成基本合格。

我们怎么用:一张十格灯表,前两格是静态检查(能编译、无可疑语法),其余八格留给后面的沙箱(隔离运行不可信代码的环境)行为检查与发布审查;实测正常候选只亮前两格——过静态检查远不等于能发布,捣乱候选第二格熄灭、当场拒绝。

### 静态编译关[自造](compile-only gate)

是什么:静态编译关[自造]指用 Python 内置函数 compile() 对候选源码做"只编译、不运行"的语法检查。官方定义是"把源码编译成代码对象或 AST(抽象语法树)对象";mode 取 "exec" 表示按语句序列编译,语法不合法就地抛 SyntaxError(语法错误异常)。它对代码的善恶完全失明——再恶毒的意图,只要语法合法就能通过这一关。

解决什么问题:候选代码迟早要被执行,执行前先用最便宜的手段粗筛一遍——语法都通不过的候选,不值得花沙箱(sandbox,隔离运行不可信代码的环境)的钱和时间。好比机场先看登机牌快筛、才轮到全身扫描[自创比喻]。连"只编译"也不是零风险:官方文档明说,足够大或足够复杂的字符串可能让 Python 解释器本身崩溃(官方限定在编译成 AST 对象的场景)——所以这一关只能当最便宜的粗筛,不能当保险箱。反面印证也来自官方:内置 exec() 的文档警告"此函数会执行任意代码,喂入不可信的用户输入会导致安全漏洞",可见编译关和内建限制都不是安全边界。调用形如 `compile(源码, 文件名, "exec")`。第二个参数惯用 `'<string>'`,只用于报错显示、表示源码来自字符串而非真实文件。它和 AST 关分工互补:编译关拦"写错的",AST 关拦"写得太能干的"。

我们的办法:它占灯表第一格;实测一段语法完全合法的恶意候选,这一格照样亮——证明它只认语法不认善恶,拦恶意得靠下一关。

### AST 拒绝列表(AST denylist)

是什么:AST 拒绝列表是把源码解析成 AST(Abstract Syntax Tree,抽象语法树——把代码拆成一棵"零件清单树"的语法结构)之后,逐个节点对照"禁止出现的东西"清单的静态检查。清单只有两条:一是不许出现任何 import(`import os`、`from subprocess import run` 一刀切,因为这套系统的候选补丁本来就不需要外部模块);二是不许调用 eval、exec、compile、open、__import__ 这五个"代码能自己动手脚"的口子。两条禁令也是行业惯例:安全扫描工具 Bandit(扫 Python 代码安全隐患)就内置"危险调用"与"危险 import"两族黑名单检查。

解决什么问题:专门拦"写得太能干的"候选。把 exec 这类口子拉黑的依据,官方文档写得直白——exec()"此函数会执行任意代码,喂入不可信的用户输入会导致安全漏洞"。实测一个坏候选:正常补丁尾部被偷运 `import os` 加 `os.system('echo pwned')`,它语法完全合法、编译能过,拦住它的正是这一关。遍历用 `ast.walk(tree)`,官方说明是"递归产出所有后代节点"且不保证遍历顺序,判断只看"有没有"、不依赖先后。实现时 `isinstance(n.func, ast.Name)` 的判断别漏:`os.system` 这类属性调用的 `.func` 是 ast.Attribute、没有 `.id` 字段,漏判会直接抛 AttributeError。核心判断形如:
```python
not any(isinstance(n, (ast.Import, ast.ImportFrom)) or
        (isinstance(n, ast.Call) and isinstance(n.func, ast.Name)
         and n.func.id in forbidden_calls) for n in ast.walk(tree))
```
还要看清边界。官方文档明说,`ast.parse`(把源码解析成语法树)成功"不保证源码是合法的 Python 代码、也不做作用域检查"——所以编译关要放在第一格,两关互不替代。语法层检查也挡不住 `getattr(builtins, 'ev'+'al')` 这类运行时拼名字的绕行,这是业界共识;官方文档另提醒,覆盖 __builtins__ 并不构成安全机制。它只是纵深防御(defense in depth,层层设防)里便宜的第一道门——按 NIST CSRC 词汇表的定义,纵深防御就是"跨多层、跨人/技术/运营建立可变屏障"的信息安全策略,真正关住候选代码的是后面的沙箱(隔离运行不可信代码的环境)。

我们的办法:在宿主机(跑验证程序的本机)上纯解析地跑这道检查、绝不执行候选,实测偷运 import 的坏候选当场被拒。
