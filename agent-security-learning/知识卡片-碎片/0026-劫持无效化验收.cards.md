# 0026 劫持无效化验收 —— 知识卡片

### 假设已失守验收(assume-breach acceptance)

是什么:「假设已失守」的验收思路指先承认最坏情况——模型已被提示注入(prompt injection,往模型读到的内容里塞恶意指令、诱骗它替攻击者执行)完全控制——再量化"劫持者到底能拿走什么"。它对应零信任(Zero Trust,Forrester 提出、NIST SP 800-207 形式化的架构)的出发点:假定攻击者已在环境里,口诀是 never trust, always verify(永不信任、始终验证)。真正的安全指标是失手之后的爆炸半径(blast radius,一次得手的攻击能波及的范围;行业惯用语,非正式标准术语)有多大。

为什么重要:它把"防住没有"这种非黑即白的问句,拆成四条可举证的收益通道——逃出去看宿主机 / 把数据送出网 / 拿到真密钥 / 干完不留痕。每条通道都要拿出实测证据,而不是"应该防住了"的口头担保。顺带一票:礼貌款(措辞礼貌的注入请求的简称)外泄还会被模型自己拒绝——模型本身也是一层(不可靠的)防线,验收时值得记上,但不能只靠它。

我们怎么用:对加固定型 Agent 连打四类主动攻击、逐项取证,总账是"劫持有效 / 收益为零 / 现场完整"。实测:白名单拒名单外请求只要 2–4 毫秒,正常请求(同批正常工具调用)约 2.4 秒,差三个数量级——拒绝先于虚拟机拉起。fail closed(故障即关门)是惯用词;NIST 沿用 Saltzer–Schroeder 的 fail-safe defaults(故障安全默认值):默认即无权限,故障时倾向拒绝而非放行——关门先于资源投入。

### VM 内 root 不是入侵信号(root inside VM is not an intrusion signal)

是什么:这条监控判据说的是:在"一次性 microVM(带独立内核的微型虚拟机,用完即焚)+ 假设里面跑的一切都恶意"的架构下,虚拟机内部的 root(Linux 最高权限账号)行为不构成入侵信号。root 在里面本来就该满血;真正该触发告警的信号是出网行为,尤其是连向出网白名单之外目标的尝试。边界必须说清:这条判据只在"一次性 + 全按恶意对待 + 焚毁兜底"的架构下成立——在长生命周期容器上,容器里冒出终端 shell 往往就是入侵,同类检测反而是高价值信号。

解决什么问题:边界换了,告警规则也得跟着换。传统判表把"获得 root""改写系统目录"当入侵迹象;老规则在这种架构下只会满屏误报,把真信号淹没——运行时威胁检测引擎 Falco 的官方文档也提醒:默认规则只是起点,可用例外与定制规则适配自己的环境。

我们的对策:借鉴 Falco 默认规则的句式——告警条件描述行为而非描述身份,例如 "Terminal shell in container" 检测的就是"容器里出现终端 shell"这个动作而不是某个账号。这里把监控重心放到出网侧:权限异常只留痕不告警、名单外出网即告警,实测(该数据来自对照方案,非本架构的验收数据):root 操作畅通无阻而私网连接在网关处被直接拒绝。

### 可见面枚举法(visible-surface enumeration)

是什么:「可见面枚举」[自造](自创方法名)指验证"密钥不可见"这类断言的方法:把劫持者能看到的一切位置列成清单,逐一面拿出证据。这些位置包括进程环境、文件系统、工具的执行环境、持有真值的对照进程、密钥源头。它不信任单点检查——环境变量这一面尤其宽:OWASP(网页应用安全领域的开放知识库项目)密钥管理速查表提醒,环境变量对所有进程可见,还可能进日志或系统转储;其他渠道如子进程继承、崩溃转储、/proc(Linux 下暴露各进程信息的伪文件系统)也真实存在——所以只查配置文件远远不够,必须逐面枚举。

为什么重要:它把"密钥藏好了"从一句担保变成一条可回答的时间线——真密钥在什么时刻、进过谁的进程;这也与 OWASP 最小权限的立场一致("工程师不应能接触所有 secret")。逐面枚举还会逼你发现"根本不该出现的出现点"——任何一面漏答,整个结论就不成立。

我们怎么用:逐面取证——进程环境用 `ps -Eww` 查,零密钥;文件面全仓子串搜索,0 命中;工具执行环境(虚拟机内 `env`)只有 10 个良性变量;对照面(转发代理)真密钥在,且"只在"代理;源头:macOS 钥匙串 Keychain,126 字符随机串、唯一存放点。结论:真值只在分发瞬间进代理、拼进待发的 `curl` 命令行,从未进模型上下文 / Agent 进程 / 宿主文件 / 记忆文件(Agent 的长期记忆存储文件)。

### 被拦攻击也要留痕(logging blocked attacks)

是什么:这条审计纪律指:输入护栏(行业惯用语:挂在用户输入进入模型之前的自动拦截器,按意图给输入打分、拦下高分注入)拦下的攻击也要上报。上报形态是一条审计观测(即一条带级别、分数等字段的结构化审计记录)——级别 WARNING、附拦截打分。静默丢弃等于销毁证据:OWASP 日志速查表(Logging Cheat Sheet)的理由很直接——对有限合法值清单的校验失败"只可能是攻击活动",被拦注入正是这类事件。

为什么重要:不记被拦事件,安全系统对"有人来过但被拦了"完全失忆。复盘时只见岁月静好,看不出有人正在试探。更看不出攻击者正在换姿势重试。OWASP 还要求事件分类有统一且成文的口径(type / confidence / severity 三字段),拦截打分正对应其中的 confidence(置信度)字段。连防御链自己崩掉的那一轮也要以 ERROR 级留痕:监控系统不说谎,才配当审计。

我们的对策:被拦的每次注入上报一条 WARNING 观测并附分数,打分为 1.0/1.0/1.0/0.9/0.9——其中"用命令工具执行 `env | sort`"这条不带"忽略指令"字眼的话术也得了 0.9,说明分类器学的是意图形态而不是关键词。取舍:按意图打分也会误伤正常话术,OWASP 对告警泛滥(alarm fog,告警雾)的警告就是反面提醒——知道分类器的脾气比相信它全对重要。

### 压缩体透传缺头(compressed body passthrough without Content-Encoding)

是什么:这是一类代理转发缺陷:代理把上游返回的 gzip 压缩响应体按原始字节转给下游,却没有一并转发 Content-Encoding(HTTP 头,声明"body 用什么算法压缩")。按 HTTP 语义标准 RFC 9110 第 8.4 节,Content-Encoding 属于表示元数据(representation metadata,记录"这个表示被怎样编码过")——头和体共同构成一个完整表示,只转发体不转发头等于把表示拆散。下游拿到压缩字节却不知道要解压,读出来就是乱码。

解决什么问题:转发类代理容易只想"体"不想"头":实测踩坑正是用原始字节流(`aiter_raw`)转发了压缩体、却漏掉声明解压方式的头。httpx(Python 的 HTTP 客户端库)官方文档对两种 API 的区分正命中此坑:`aiter_raw` 返回原始字节、不做 gzip/brotli 等内容解码,`aiter_bytes` 才返回已解码内容。另注:这是正确性缺陷而非攻击手法,在攻击手法知识库 MITRE ATT&CK 里没有对应条目。

我们的办法:把代理的转发从"原始字节"改成"已解压字节"(`aiter_bytes`),Content-Encoding 在代理侧消化掉,下游永远拿到可读明文体——取舍是放弃字节级原样,换来"下游不需要懂压缩"的单一语义。实测修正后响应恢复正常解析。
