# 0028 隔离级别光谱精读 —— 知识卡片

### 逃逸面[自造](escape surface)

是什么:逃逸面[自造](指不可信代码逃出隔离环境前必须打穿的代码与接口,是给隔离强度记账的尺子)借自业界的攻击面(attack surface)概念。容器把整个宿主内核的 syscall(应用请求内核办事的接口)边界全暴露给 guest(来宾负载),这条边界上有千级 CVE(公开漏洞编号)历史。gVisor(谷歌开源的用户态沙箱)官方 intro(概述)页最强一句是「攻击者必须同时打穿 gVisor 的 Sentry(gVisor 用 Go 写的用户态内核进程,替应用接住系统调用)内核和宿主 Linux 内核,两者不共享任何代码」。microVM(带独立内核的微型虚拟机)只暴露极小的设备模拟面,逃逸面收敛到 VMM(虚拟机监督程序,即 hypervisor 的实现程序)那点代码。

解决什么问题:NIST CSRC 术语表对攻击面的官方定义是:系统边界上攻击者可尝试进入、施加影响或提取数据的点的集合——是「边界上可触达的点」,而非代码总量;代码量只是度量它的代理尺度(proxy),不是官方等式。回答「为什么共享内核不够」——光有隔离的名词不够,要数得清攻击者可触达的点、要打穿的代码。两家的工程努力其实是同一个方向:砍暴露面,只是砍的位置不同。gVisor 在 syscall 边界重写一层厚的;Firecracker(亚马逊开源的 microVM 运行时)只留一层薄的设备模拟,把内核交给硬件虚拟化(芯片级虚拟化指令)隔开。

我们的办法:不自建隔离层,只做两件事——把不可信工具放到隔离光谱(从进程到容器再到用户态内核和虚拟机的强度排布)最右端的 microVM,再在外面配出网白名单。实测两种环境的内核不同:容器里 `uname -r` 显示与宿主同版本,microVM 里是独立版本,逃逸面差异看得见。

### Firecracker 极简设备模型(minimal device model)

是什么:Firecracker(亚马逊开源的 microVM 运行时)的设备模型指它模拟给 guest(来宾虚拟机)的硬件清单,官方口径是设备清单极短:清单上只有 virtio(虚拟化场景的标准设备接口)Net/Block/Vsock 三件加一个串口;保留 i8042(老式键盘控制器芯片)但用途限死为「只当重启信号」;另外还有 KVM(内核虚拟机模块)支持的老式中断设备——PIC(可编程中断控制器)、IOAPIC(I/O 高级可编程中断控制器)和 PIT(可编程间隔定时器);取舍逻辑是:不在清单上的设备根本不存在,不存在就不用防。

解决什么问题:设备模拟代码是 VMM(Virtual Machine Monitor,虚拟机监督程序)暴露给 guest 的主要攻击面——guest 每多见一种设备,就多一类可打的解析代码。配套的形态约束同样极简,官方原句 "Each Firecracker process encapsulates one and only one microVM"(一个进程只包一台 microVM,内含 API/VMM/vCPU 三类线程);官方密度数字是最小配置(单核加 128 MiB 内存)下每宿主核每秒稳定创建 5 台,36 核机即每秒 180 台——安全与密度两头成立。

我们的办法:本项目把 Agent 工具的不可信命令放进这类极简形态的 microVM 执行;对照组容器暴露的是整个宿主内核,可打的门不在一个量级。

### 来宾即恶意[自造](assume-malicious guest)

是什么:「来宾即恶意」[自造](给隔离技术的威胁模型起手式起的名字)是 Firecracker 设计文档的立场。原文是 "all vCPU threads are considered to be running malicious code as soon as they have been started"(vCPU(虚拟 CPU)线程一启动,就一律当作恶意代码),且这些恶意线程 "need to be contained"(必须被容纳住)——判定恶意的同时承诺兜底,而不是拒收不跑。

解决什么问题:它把设计题从「赌 guest 不会被攻破」改成「guest 被攻破后能碰到什么」。答案被压到最小:guest 直达的只有极简设备清单;官方的信任区分层是嵌套式的——从最不受信任的 guest vCPU 线程一路递增到最受信任的宿主,层层之间由屏障(barrier)隔开;网络过滤这类责任全部放到 guest 之外。

我们的对策:同构的落法是先承认提示注入(把恶意指令塞进模型读到的内容里、诱骗模型替攻击者执行)会完全得手,再量化「得手后能碰到什么」。实测虚拟机内 root(Linux 最高权限账号)满血不构成失守,失守与否看出网与宿主可见性。

### jailer:Firecracker 的降权启动器(jailer)

是什么:jailer 是 Firecracker 自带的降权启动包装程序,官方生产部署文档要求经它启动("should be started using the jailer"),替代条款是部署方自施「等于或严于 jailer 的进程约束」。工作顺序:先用 root(Linux 最高权限)完成全部需要特权的设置——配 cgroup(内核的资源限额机制)、经 unshare()(把进程挪进新内核隔离空间的系统调用)开一个新挂载命名空间、pivot_root()(切换进程的挂载根)换根并 chroot(".") 进替身根目录。然后才降权切换 uid/gid。最后 exec(以新程序替换当前进程)拉起 Firecracker,可选再加 `--new-pid-ns` 隔离进程号空间。官方给 jailer 的定位句是 "isolate the Firecracker process in order to enhance Firecracker's security posture"(把 Firecracker 进程隔离开,以增强其安全姿态)。seccomp(内核的系统调用过滤机制)过滤器按线程逐个加载,对 vCPU 的时机官方写明是 "right before executing guest code"(赶在执行任何 guest 代码之前)。

解决什么问题:VMM 本身也是个进程,若以特权身份长跑,被打穿一次就等于交出宿主机。jailer 把「需要特权的时刻」压缩到启动前段,特权用完即交——攻击者即使打穿 VMM,拿到的也是一个降权、被 chroot 圈住、被 seccomp 滤过的进程,而不是宿主 root。

我们的办法:本项目没有重造这一层,选型时拿它当对照标准——所用运行时拉起沙箱的过程是否「先收紧再交棒,guest 代码未跑先装过滤」。

### 隔离与策略分工(VMM does no traffic filtering)

是什么:这是 Firecracker 设计文档写明的一句分工:"Firecracker does not perform any network traffic filtering"(Firecracker 不做任何网络流量过滤)——guest 的全部出站流量都被视为不可信,但流量过滤是宿主层的责任,VMM(虚拟机监督程序)只管隔离、不管策略。

解决什么问题:不分工有两种坏结果:把过滤塞进 VMM 会膨胀它的代码量,暴露面跟着变大;以为 VMM 会兜底的人会漏配外层策略。gVisor Security Model(安全模型)页的另一句原话补齐了另一半:"A sandbox is not a substitute for a secure architecture"(沙箱不是安全架构的替代品)——出网策略、密钥隔离、审计都在沙箱外各就各位,才成体系。

我们的对策:本项目在 microVM 外配了两层——工具层域名白名单加网络层「只许公网」预设,实测名单外请求连虚拟机都不启动、私网连接在网关处被拒,恰好落在「宿主层过滤」一侧;官方给的宿主层落地手段就是防火墙规则(nft 或 iptables-nft 这类工具)。

### 双墙原则[自造](two-wall security model)

是什么:双墙原则[自造](对 gVisor 安全模型的提炼,官方锚点是「两个独立的内核,内侧那个独占于被沙箱的工作负载」)是两道串联的墙。第一墙:应用对宿主 System API 的直接交互全部被 Sentry(gVisor 用 Go 写的用户态内核进程)拦截,没有任何系统调用直通宿主,每一条都由 Sentry 的独立实现代答。第二墙:Sentry 自己能用的宿主 API 被压到「更安全的受限集合」,官方描述是只剩 FD(文件描述符)复制与关闭、同步、定时器、信号管理这类窄动作;官方同时写明两个例外:建新 socket(网络套接字)仅当 host networking(gVisor 的可选网络模式,让沙箱直接使用宿主网络栈)模式启用,打开文件仅当 directfs(gVisor 里让 Sentry 直连容器根文件系统的机制,2023 年中起默认启用)启用。

解决什么问题:第二墙防的是「攻破 Sentry 之后连锁提权」:攻击者就算拿下这层内核,也发现它自己默认连文件都开不了,第二跳没有落点。配套纪律是工程性的,官方句句在案:"No CGo is allowed. The Sentry must be a pure Go binary."(禁与 C 语言混合编译,Sentry 必须是纯 Go 二进制)、所有 unsafe 代码集中收进以 unsafe.go 结尾的文件、持续 fuzzing(自动化随机输入测试)。

我们的办法:本项目未采用 gVisor——要跑任意 Linux 命令,选了兼容性接近完整的 microVM(独立内核的微型虚拟机);但这道第二墙的思路可复用:给隔离层自身断权,比给隔离层多写检查更压得住连锁失败。

### Gofer(gVisor 的独立文件代理进程)

是什么:Gofer 是 gVisor 里独立于 Sentry(用户态内核进程)的文件代理进程,官方原句:"The Gofer process manages the container's filesystem and provides file descriptors to the sandbox upon request"(Gofer 进程管理容器的文件系统,并按请求向沙箱提供文件描述符);官方给它的定位是「稍更受信任的伴生进程,跑在稍更特权的上下文里」——权限略高于 Sentry。Sentry 这边,官方写明沙箱自身运行在一个空的 mount namespace(挂载命名空间,进程专属的文件系统视图)里,另有隔离的用户命名空间和最小化的 capabilities(Linux 的权限位集合);directfs 关闭时,需要文件才经 socket(进程间通信端点)向 Gofer 要 FD(文件描述符,指向已打开文件的句柄),再据此读写。

解决什么问题:文件系统是内核攻击面里最肥的一段——符号链接(指向别处路径的特殊文件)与恶意挂载是经典的逃逸跳板。官方文档写明 directfs 自 2023 年中起在 runsc(gVisor 的运行时命令)中默认启用:启用后 Sentry 直连容器根文件系统、自己解析路径,访问被限定在容器 rootfs(容器根文件系统)视图内;directfs 关闭时,全部文件操作才由 Sentry 经 socket 向 Gofer 要 FD 代答。两种形态都在收窄暴露面——前者把 Sentry 的访问圈进容器视图,后者把解析交给权限稍高的 Gofer;攻破 Sentry 的攻击者面对的也只是窄接口或容器内视图,而不是内核整段文件系统代码。

我们的办法:同一目标在本项目由 microVM 方案达成——虚拟机自带独立文件系统,实测虚拟机内看不到任何宿主目录,文件攻击面根本不与宿主共享。

### 平台三代:ptrace、systrap、KVM(gVisor platform backends)

是什么:gVisor 拦截应用系统调用的实现载体先后有三种。ptrace 平台用 `PTRACE_SYSEMU`(调试器接口里「让代码照跑、但拦下系统调用」的模式),代价是上下文切换开销大——官方已写明它 "is no longer supported"(不再支持)且预计最终彻底移除,所以是「先后」而非长期并存的三代。systrap 平台自 2023 年中取代 ptrace 成为默认,借 seccomp(内核的系统调用过滤机制)的 `SECCOMP_RET_TRAP`(让违规调用触发 SIGSYS——seccomp 违规时内核发给进程的信号——把控制权交回 gVisor),轻得多。KVM 平台让 Sentry 同时扮演 guest OS 和 VMM(虚拟机监督程序),没有虚拟硬件层,沙箱仍保持进程模型。

解决什么问题:拦截机制决定性能与部署场景,官方的选择建议是:裸金属(不跑在虚拟机里)用 KVM 平台性能最好;虚拟机内用 systrap 更合适——同一套安全模型配不同的接地方式。

我们的办法:本项目未用 gVisor,这张卡记的是选型要看的另一半:评估沙箱不只看隔离强度,还要看它靠什么机制接到硬件上。同一功能可以有不同实现,性能与适用场景各不同,且实现本身有生命周期(ptrace 被废弃即一例)。

### 硬件虚拟化不自动等于更安全(virtualization ≠ security)

是什么:硬件虚拟化不自动等于更安全:不应因为用了虚拟化硬件就断定系统更安全或更不安全。这句提醒出自 gVisor Security Model(安全模型)页的 FAQ 小节。原话比喻「正如单是使用承载式车身(unibody alone)并不能让汽车安全」,关键限定词是 alone——仅凭一项技术就宣称安全,是把必要条件当成了充分条件。为什么单靠硬件虚拟化还不够,官方 FAQ 小节写明:"device emulation code in the host kernel (e.g. APIC) or optimizations (e.g. vhost) can be more complex than a simple system call"(宿主内核里的设备模拟代码——如 APIC,高级可编程中断控制器——或优化路径——如 vhost——可能比一次简单系统调用更复杂)。VM(虚拟机)方案里,guest 的硬件中断由宿主内核里的设备模拟代码(如 KVM 的 APIC 模拟)代劳,这段代码越复杂,暴露面越大。

解决什么问题:它纠正「VM 一定比用户态内核安全」的直觉,把比较拉回逃逸面记账:硬件虚拟化的芯片级硬边界是真优势,但边界内暴露的代码量同样要数。两家的答案从两端逼近同一目标——gVisor 不做设备模拟、直接用沙箱化的宿主 API;Firecracker 保留 VM 硬边界、把设备清单削到极简。

我们的办法:本项目取 Firecracker 一侧的组合——硬件虚拟化硬边界加极简设备(microsandbox 这类轻量运行时,以 libkrun(把 Linux 的 KVM(内核虚拟机模块)包成轻量库)这类底座实现),而不是全功能模拟的传统虚拟机。
