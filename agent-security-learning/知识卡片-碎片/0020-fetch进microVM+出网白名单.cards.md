# 0020 fetch进microVM+出网白名单 —— 知识卡片

### 劫持网页抓取工具的 SSRF 与密钥外泄(SSRF via hijacked fetch tool)

是什么:SSRF(Server-Side Request Forgery,服务端请求伪造)指诱骗服务器替攻击者发请求、进而读取或篡改其内部资源的攻击。OWASP(开放全球应用安全项目,Web 安全领域的权威组织)的定义强调后果是"读+改内部资源",不只是"发个请求"。放到 Agent 身上,毒从网页抓取工具进:被提示注入(prompt injection,把恶意指令塞进模型读到的内容里、诱骗模型替他执行)劫持后,抓取工具可以被诱导去访问任何宿主机能到达的地址。

怎么得手:抓取工具原来直接在宿主机上发 HTTP 请求,宿主机能到哪它就能到哪。三条现成路径:打内网设备(如 `http_get('http://192.168.1.1/')` 摸路由器管理页)、访问云元数据端点(169.254.169.254,上面放着云平台临时凭证)、把偷到的密钥直接 POST 到攻击者自己的服务器。这条链真实世界发生过:2019 年 Capital One 泄露事件就是攻击者用 SSRF 读云元数据端点拿到凭证,MITRE ATT&CK(攻击手法知识库)把"窃取云实例元数据服务里的凭证"收录为独立条目并引用此案。

我们的对策:两层各挡一类——工具层的域名白名单让名单外请求连执行环境都不启动,实测拒绝是瞬间的;网络层默认拒私网,攻击者在沙箱里绕过工具层裸跑 `curl http://192.168.1.1/`,只得到 exit 7(连接被拒)。

### 工具层出网白名单(tool-layer egress allowlist)

是什么:出网白名单是只放行显式许可目的地的出网控制;这道检查以代码形式住在抓取工具的函数体里,请求真正发出前先验 URL 的协议与域名——scheme 只许 http/https,host 必须在名单内,不过就拒绝。它的威胁模型默认工具已被劫持:OWASP(开放全球应用安全项目)的 SSRF 防护清单里,网络层防火墙的定位是"给易受 SSRF 攻击的应用兜底"(原句 limit the impact of an application vulnerable to SSRF),不是假定应用永远干净。取向是 fail closed(默认拒绝):当检查无法给出确定结论时,默认拒绝而非默认放行——宁可让合法请求失败,也不让恶意请求出门。

解决什么问题:检查放在拉起沙箱之前还是之后,差的是资源与绕路——放在前面,名单外的请求连一台一次性虚拟机都不用开。实测四种请求的命运:`https://httpbin.org/get` 在名单内放行;`https://example.com` 被秒拒(虚拟机根本没启动);`http://192.168.1.1/` 同样被拒;`file:///etc/passwd` 栽在协议检查上——返回 `只允许 http/https,收到 scheme=file`。最后这条拦截有官方背书:OWASP 明确把 `file://` 这类 URI 列为 SSRF 可达目标(可用来读服务器本地文件),拦它不是过虑。

我们的办法:在抓取工具的 server 里做协议加域名两道检查,并与沙箱网络层的兜底配套——这种双层纵深是 OWASP 认可的组合(两层都设防,单层被绕过还有下一层)。字符串层的白名单理论可绕,内网与云元数据那更致命的一半交给网络层去挡——整套加固对模型暴露的工具签名一字未改,防御升级不需要模型配合。

### microsandbox 网络策略(Network / NetworkProfile)

是什么:microsandbox(把不可信代码关进一次性 microVM 的开源运行时;microVM 指带独立内核的微型虚拟机)SDK 里的 Network 对象,是给沙箱出网装防火墙的声明式配置,用 `Sandbox.create(network=...)` 挂上去。三种现成形态:`Network.allow_all()`(全开,含私网与宿主机)、`Network.none()`(全关,但命令执行与文件传输仍走宿主—沙箱通道)、`Network.from_profiles(NetworkProfile.PUBLIC)`(只许公网)。from_profiles 的组装思路是官方说的 deny-by-default(默认拒绝):先把所有出口设为拒,再用 profile 一组一组往白名单里加。

解决什么问题:精细档位靠 `NetworkPolicy(default_egress=Action.DENY, rules=(...))` 自己拼规则。官方文档警告规则要"具体的排前面,宽的排后面",原话是 a broad rule placed before a narrow one swallows it(宽规则排前会吞掉窄规则,"吞掉"二字的出处)。`deny_domains=("某域名",)` 还能在三层拦特定域名:DNS 解析(直接回 NXDOMAIN,即"域名不存在")、TLS 首包(SNI,握手时声明的目标域名)、TCP 出网(查缓存兜底)。

我们的办法:抓取工具拉起沙箱时一行 `Network.from_profiles(NetworkProfile.PUBLIC)`,与工具层白名单合成两道防线。规则级域名白名单在这个版本拼不出来、黑名单形态的 deny_domains 是唯一可用的域名限制(根因见下一张卡的 fake-IP 机制)——此结论来自实测,官方文档未否认。

### fake-IP DNS 代理与规则级白名单失效(fake-IP DNS proxy)

是什么:fake-IP DNS 代理指沙箱网关代答域名解析的机制——沙箱内解析域名拿到的不是真实 IP,而是 198.18.0.0/15 保留段(sing-box 的默认 fake-IP 网段 inet4_range)里的假 IP,真实连接由网关按"假 IP 到真目标"代理出去。这段地址是 RFC 2544 划给网络基准测试的保留段,并不是 RFC 1918 私网段。它的启动条件很苛刻:实测环境里只在放行 PUBLIC profile(上一张卡说的"只许公网"预设)的策略下才生效——这是我们环境特有的实测结论,不是 fake-IP 的通用属性。

解决什么问题:它解释了规则级域名白名单为什么拼不出来——不放行 PUBLIC 组时 DNS 全死,连白名单里的域名都解析不了;一放行,公网又全开,"先放行某域名、其余全拒"两头不可兼得。这不算孤例:198.18.0.0/15 不在常见"私网段"判断清单里,任何按"目标 IP 是否私网"写 SSRF 拦截的工具,遇到 fake-IP 网段都会判断失真(方向未必相同,但都说明"拿 IP 段猜安全"靠不住)。唯一能用的域名限制是黑名单形态的 `deny_domains`,配上 PUBLIC profile 实测既存活又真拦。

我们的对策:把策略形状挨个实测(从给 DNS 端口放行到混排规则都试过),最终定型为"工具层白名单加网络层 PUBLIC"的组合。beta 版(0.6.16)的文档语义不可信——每个"应该可以"都要配一个 exit code,以实测版本为准。
