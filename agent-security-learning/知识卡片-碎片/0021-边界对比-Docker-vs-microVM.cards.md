# 0021 边界对比-Docker-vs-microVM —— 知识卡片

### 逃逸探针(escape probe / canary)

是什么:逃逸探针[自造](escape probe,自造词、网上无权威对应)指在目标隔离环境里跑一段固定脚本、把输出当"口供"做横向对比的评估方法。它最接近的成熟概念是安全行业的 canary(金丝雀,厂商 Thinkst 的大意是放在没人该碰的地方、一被触碰就报警),但那是求被触的诱饵,这里的探针是求自测的口供——两者别混。它刻意保持零武器化[自造](自设约束词,非行业标准),动作上限是"看"与"轻触":读身份与挂载表、对目标发 TCP connect 试连通、用一次性写入探权限边界——写进几秒后焚毁的环境,不留痕。它不利用漏洞、不外传数据,所以能放心进教学仓库。

为什么重要:它把"隔离好不好"从概念感觉变成一组可比对的观测——身份 / 文件可见性 / 网络可达性 / 写权限;同一份脚本在每个环境里各跑一遍,差距直接落在带 exit code 的对比表上,环境升级后重跑同一份脚本即可防回归。

我们怎么用:脚本只用 POSIX sh 加 python3 socket(不用 curl/ping,精简镜像里没有这两个工具);送进 microVM 时先把脚本 base64 编码再执行,躲开引号转义地狱;动作覆盖四类——看身份 / 读宿主路径 / 扫内网 / 试提权(能不能写 /etc、能不能用 sudo)。

### 挂载卷直通(volume mount passthrough)

是什么:挂载卷直通[自造](bind mount passthrough)指容器把宿主机目录原样映射进容器内部、容器里读写直达宿主文件系统的机制。Docker 官方把这种"宿主目录直通"叫 bind mount(绑定挂载),以区别于由 Docker 托管的 volume(数据卷),这张卡说的是前者。官方对它的警告很直白:默认对宿主文件有写权限,可能影响宿主上与容器无关的进程,并且明确提示"有安全影响"。它本是共享代码与数据的开发便利,却等于在隔离边界上开了一扇按需定制的门。

怎么得手:攻击者只要读到挂载进来的目录,就等于读到了宿主文件。比如在容器里对挂载目录下的文件来一句 `cat`,拿到的就是宿主上的原文。实测最扎眼的一条:六项容器加固(只读根文件系统、剥光 capabilities、降权为非 root 用户等)一条都拦不住它——挂载进来的工作区目录里的真实文件直接可读。官方给的缓解 readonly/ro(只读挂载)挡得住写、挡不住读,恰好救不了这半;而且容器用完即焚(--rm)也救不回来——写进挂载目录的内容落在宿主真实路径上,不随容器销毁消失。

我们的对策:换一次性 microVM 当执行环境就根本不开这扇门——虚拟机内看不到任何宿主目录,宿主文件零可见,攻击成果无处持久化。

### 云元数据端点窃取(cloud metadata credential theft)

是什么:云元数据端点是云厂商固定挂在 169.254.169.254 这个链路本地(link-local,169.254.0.0/16 保留网段)地址上的实例信息接口,实例内的进程访问它就能领到云平台的 IAM 临时凭证(临时身份令牌)。AWS 官方文档说明这类地址只在实例内可达(IMDSv2 令牌明确 rejected if you attempt to use it outside of the instance)——边界信任模型是官方明说的:它默认信任实例内的一切访问者,"够得着它"约等于"偷到这台机器的云身份"。

怎么得手:只要负载的出网不受限,一条 TCP 连接就进门。实测在加固 Docker 容器里对它发起连接是成功的——容器加固管文件权限、管 capabilities,唯独不管出网;同一批探针里,局域网网关 `192.168.0.1:80`(路由器真在听 80 端口)也可达,内网横移通道同样敞开。AWS 还提示:容器场景常要把 hop limit(跳数限制)从默认 1 调大才能继续访问 IMDS——容器离元数据端点只隔一跳,这层兼容性设计与我们实测"容器里连接成功"互相印证。

我们的对策:一次性 microVM 的网关默认拒私网与链路本地地址——同一路由器 80 端口,容器连得上、microVM 连不上(curl 得到 exit 7,连接被拒),连专门的网络 profile 都不用配。官方缓解是 IMDSv2(先发 PUT 请求换会话令牌再领凭证,纯 GET 的 SSRF 拿不到东西),而网络层默认拒链路本地正是 MITRE 给这条手法的缓解措施(M1035),挡得更彻底。

### 收紧内部与丢弃内部(hardening vs disposability)

是什么:这是"给不可信代码找执行环境"的两种相反取向——加固派(行业依据是 NIST SP 800-190 的容器分层加固)的答案是捆紧内部:只读文件系统、剥权限、降权;丢弃派(行业出处是 12-factor——一套应用部署方法论——的"进程用完即弃",以及 LinuxKit 这个打造极简不可变 Linux 的开源项目的"不可变基础设施")的答案是内部不做加固,整个环境用完即焚。类比[自造]:一个给牢房上锁,一个给牢房装自毁按钮。

解决什么问题:决定防御预算花在内部还是花在边界。实测对比把两派的真实短板摆上台面:加固容器里写 `/etc` 确实被只读文件系统挡住,但挂载卷与出网两扇门关不上。这不算巧合。NIST 800-190 把"无界网络访问"列为容器风险,并单列对策"控制容器出网流量"(4.4.2)。但它把这道防线放在网络层,而不是捆容器内部——只读文件系统、剥权限、降权这类容器加固,天生一条都管不到出网。一次性 microVM 里 root 反而能随便写 `/etc`,但这不算失守——写的是一台几秒后焚毁的虚拟机的 `/etc`。12-factor 说的"用完即弃"本指应用进程层,扩到整个虚拟机是合理引申,方向一致。

我们的对策:选丢弃派,把预算押在边界——宿主零可见 / 私网默认拒 / 用完即焚,这三道硬墙比内部六道捆绑更值钱。丢弃派也有现成落地——Docker Desktop 的基础 LinuxKit 走的正是"不可变"路线(下一张卡接着说)——两种边界的真实差距靠探针实测得出,不停留在概念对比。

### 容器共享谁的内核(Docker Desktop linuxkit)

是什么:macOS 上 Docker 容器共享的并不是 Mac 内核,而是 Docker Desktop 自带的一台 Linux 虚拟机的内核——这台 VM 的内核构建自 linuxkit 项目(一个打造极简不可变 Linux 的开源项目),官方文档并不把 VM 本身叫作 linuxkit。新版 Docker Desktop 已改用 Apple Virtualization framework(旧版是 HyperKit)来跑这台 VM,linuxkit 这个名字如今主要活在项目本身与内核镜像里。"容器共享内核"的准确说法因此是:容器世界共享那台 Linux VM 的内核与它的挂载直通;而 microVM(代表实现如 AWS Firecracker,官方自述"把硬件虚拟化的安全与隔离、和容器的速度与灵活合在一起")每次一份全新内核。

解决什么问题:判断内核逃逸的影响面。linuxkit 主打"不可变"——内核镜像整台同机共用,同一个内核漏洞被打穿后,容器一侧波及"大家共用的那台":同机所有容器,加上那台 VM 挂出去的宿主路径;microVM 一侧只波及"你自己那份,用完就烧"。

我们的办法:同一份探针脚本在两种环境各跑一遍,内核版本直接进对比表——容器里 `uname -r` 显示 `6.12.76-linuxkit`,microVM 里是另一个独立内核版本号,隔离级别差异肉眼可见。
