# 0029 网关上岗 —— 知识卡片

### MCP 网关（ContextForge Gateway）

是什么：MCP 网关是挡在 AI Agent（自主调用工具的 AI 程序）和 MCP server（工具提供方，MCP 即 Model Context Protocol——Agent 调用外部工具的开放协议）之间的独立转发组件。所有工具调用都改从它走，由它统一认人、查权限、留记录。ContextForge（IBM 的开源实现，PyPI 包 `mcp-contextforge-gateway`）官方定位是三合一：gateway（转发）加 registry（工具注册表，登记有哪些工具可调）加 proxy（统一对外端点），而且不只收 MCP、还收 REST/gRPC 这类普通 API。好比给大楼设了前台：人人走大门，前台认得出你是谁、能不能进、来了都登记。实测它有两套互不通用的登录凭证体系（凭证面[自造]）：看板（浏览器里的 Web 管理界面）登录走邮箱账号，API 调用走 HTTP Basic 密码（随请求明文带用户名密码的老式认证）。

解决什么问题：没有网关时，Agent 直连各个 MCP server，server 自己不知道连接者是谁、有没有权限、干了什么，出了事无从追责。网关把"谁在调用工具"收拢到一个位置，认证（核验身份）、授权（判定权限）、审计（留存记录）就都能在同一个点上做。另有一个使用注意：Basic 这条老通道官方默认是关的（`API_ALLOW_BASIC_AUTH=false`），API 侧推荐改用 JWT（带签名的登录令牌）。

我们的办法：把网关当"部署对象"而非自己写的代码——给它独立的虚拟环境（依赖互相隔离的目录）和独立配置目录，只听本机回环地址（127.0.0.1，只有本机能连），实测浏览器一打开就是登录墙（未登录时访问被重定向到的登录页），`curl /health` 返回 `{"status":"healthy"}`。工作目录是它的"户口"——官方数据库默认用相对路径的 sqlite 文件（`sqlite:///./mcp.db`，sqlite 即单文件嵌入式数据库），同一命令在哪个目录跑就读哪份配置、用哪个库，独立目录让两边互不污染。

### 默认封锁管理面（secure by default）

是什么：secure by default 指安全产品出厂就把管理面（产品自带的管理后台和管理接口）关死、要管理员显式打开的设计取向。它和 secure by design（在架构设计阶段就内置安全）是相邻的两回事——一个管"出厂配置"，一个管"图纸怎么画"。ContextForge 正是这种默认：不动配置时 Web 看板（浏览器里的管理界面）和管理 API 都不启用，启动日志明写 `Admin API routes not mounted` 和 `Static files not mounted - UI disabled`；还有更典型的 fail-closed（出错或无配置时默认拒绝、而非默认放行）实例——允许列表（allowlist，放行名单）空着时，默认封锁全部跨网关路由。

解决什么问题：管理面本身就是攻击面——登录口一旦暴露，攻击者就多一个爆破口令、调用管理接口的入口。美国政府联合指南把这套理念的价值说成两条：缩小攻击面，并把安全配置的负担从运营者身上卸掉——"忘了关"这类人为失误从根上被删掉。

我们的办法：本地要看板才在配置里显式打开 `MCPGATEWAY_UI_ENABLED=true` 和 `MCPGATEWAY_ADMIN_API_ENABLED=true` 再重启，实测把开关改回 false 后登录墙（未登录时被重定向到的登录页）立刻消失。注意一个坑：官方开发示例 .env（存环境变量的配置文件）里这两个开关默认写 true（官方明说是为了让本地开箱即用），真正"出厂关死"的是代码默认值。

### init_secrets（网关密钥生成器）

是什么：init_secrets 是 ContextForge 自带的密钥生成脚本，用密码学安全的随机源（人猜不出的高质量随机数）一次生成三把密钥，官方要求首次启动前就得跑。网关缺了密钥会 fail fast（启动即报错退出），官方原话说连本地开发环境也不许缺。三把分别是 `JWT_SECRET_KEY`（签发登录令牌的私章）、`AUTH_ENCRYPTION_SECRET`（加密存储用的钥匙）、`BASIC_AUTH_PASSWORD`（API 的 HTTP Basic 密码）。

解决什么问题：网关没有私章就签不出登录令牌，整个认证直接瘫。让密钥由脚本随机生成而非人手定，弱密码和密钥被抄进代码库这两类事故就从流程上被排除。

我们的办法：用 `--patch-env .env`（存环境变量的配置文件）把生成值直接补写进网关配置（官方设计是替换 `__REPLACE_ME__` 占位符）。密钥文件靠仓库的 .gitignore 挡在版本库外；实测三把全是随机值，全程没人工设过密码。另记两条通用纪律（出自 OWASP）：密钥要定期轮换（BASIC_AUTH_PASSWORD 改配置重启即可换新）；.env 这类环境变量可能进日志或系统转储、属次优做法——生产环境应上 vault（专用密钥保险库）。

### CSRF 双票机制（CSRF double-submit cookie）

是什么：CSRF 即跨站请求伪造（Cross-Site Request Forgery）——一种借已登录浏览器的凭证冒充用户发请求的攻击。防御侧的经典做法是 double-submit cookie（卡片里的"双票"[自造比喻]：服务端把一张票种进 cookie，又在表单里塞一张票，提交时两张对上才放行）。机制成立的根因是浏览器只让同源 JS 读 cookie（同源即协议、域名、端口都相同）——外部小站的攻击脚本摸不到第一张票，自然也抄不出第二张，所以改状态的动作（比如登录）必须证明请求来自网关自己的登录页。ContextForge 登录页用的就是这套：种一张 20 分钟有效的 CSRF 通行 cookie，它刻意不带 HttpOnly（禁止 JS 读取的标志）——JS 要读它回填请求，双票才玩得转。

解决什么问题：它解决的是外部站点借你已登录的浏览器伪造改状态请求（比如提交登录表单）这类攻击。但这套双票牵出一个浏览器行为坑：cookie 带 Secure 标志（承诺只在 HTTPS 里递）时，浏览器在 `http://` 上会直接丢掉它——Chrome 对 localhost 放行，Safari 不放行。实测 Safari 提交登录直接报 `CSRF token cookie missing`，本地 http 环境走不完登录。

我们的办法：本地教学环境在配置里关掉 `SECURE_COOKIES` 再登录，生产保持默认开启并上 HTTPS，实测关掉后 Safari 也能走完登录。通用纪律：OWASP 已把朴素双票标为 discouraged（不推荐），更稳的是签名版 signed double-submit——票据用 HMAC（带密钥的哈希签名）绑到用户会话上。

### uv venv --python（钉 Python 版本建环境）

是什么：这是 uv（Astral 出品、Rust 写的 Python 虚拟环境与包管理器）钉死解释器（运行 Python 代码的程序本身）版本建虚拟环境的命令，写成 `uv venv --python 3.12`。它针对的坑是版本约束冲突：很多包在元数据里声明 requires-python（包自己声明的 Python 兼容范围），解释器不满足时包管理器会强制拒绝安装。uv 选解释器还有条官方规则——挑第一个兼容版本而不是最新版本，所以钉 3.12 就复用本机的 3.12，不会自作主张换 3.13；本机没有对应版本时它会自己下载。

解决什么问题：实测撞过一次真实的约束——ContextForge 声明要求 Python ≥3.12 且 <3.14，而系统 python3 是 3.14.7，直接装会被包管理器拒绝。加 `--python 3.12` 后，uv 找到本机已有的 CPython 3.12（Python 官方参考实现）直接复用，冲突就地化解。

我们的办法：给网关单开一个钉在 3.12 的虚拟环境当依赖隔离的家，装包也指定这个环境的解释器，实测秒级建好、与 Agent 自己的环境互不污染。另一种等价钉法是在项目里放 `.python-version` 文件（一行写个版本号）。
