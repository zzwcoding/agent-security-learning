# NeMo 0004 三种 rail 精读与五闸时序图 —— 知识卡片
来源:`NeMo-Guardrails学习/lessons/0004-三种rail精读与五闸时序图.md`

### 五道闸:位置固定,机制任选(NeMo Five Rails: Position vs Mechanism)
**是什么**:一条用户消息完整过五道闸——① input rails(入口安检:用户带来的坏)→ ② retrieval rails(提货检:检索 chunks 有毒丢掉再进 prompt,仅挂知识库/RAG 时存在)→ ③ dialog rails(大堂经理:认意图定调子)→ ④ execution rails(动作/工具环节的闸)→ LLM 生成 → ⑤ output rails(出厂质检:bot 自己造的坏)。
**解决什么问题**:"五道闸"说的是**钉在链路哪个位置**,判定机制是另一根轴——LLM 自检(self-check)、专用模型(`jailbreak_detection`、`hf_classifier` 等二十多个现成集成)、纯 Python 结构校验(tool rails,不调 LLM)、Colang 流程匹配(dialog)。对照 llm-guard 时要比机制,不是比位置。
**我们的办法**:实测壳没有知识库、没有工具、没写 Colang,所以 ②③④ 全程不存在——消息走 ①→生成→⑤ 短路;拿真实攻击映射:直接注入→①、间接注入(工具返回带毒)→名义 ②④ 实际没人管、多轮套话→③、write_file 参数投毒→④ 只补一半、回复泄 key→⑤。

### dialog rail:Colang 流程图 steering(Dialog Rails / Colang)
**是什么**:五种 rail 里最重的一种——配置**不是**往 flows 列表加名字,而是写 `.co` 文件(NeMo 自造的对话建模语言,语法像 Python:`define user 意图` / `define flow 流程`;1.0 默认、2.0 重写)。判定机制 = Colang 引擎按流程图 steering + `generate_user_intent` 把用户消息归一成 canonical form 再决定下一步(直接答/固定话术/调动作)。`config.yml` 里 `rails.dialog` 只有调优项(如 `single_call`)。
**解决什么问题**:防"聊着聊着被带偏"——多轮套话、话题偏移(记忆投毒的对话面)归它管;但前提是**手写流程图**,覆盖面 = 你画出来的分支。
**我们的办法**:只记轮廓不深入——目标是安全闸机不是对话编排;input/output/self-check/tool 这些安全闸全都不需要手写 Colang。`generate_user_intent` 在阶段 1 的 401 traceback 里见过,印证它默认就跑。

### tool rails:结构校验,不是语义安检(Tool Call / Result Validation)
**是什么**:IORails 引擎下的两段固定配置——`rails.tool_output: flows: [tool call validation]` 查模型发出的工具调用(白名单 + 参数 JSON Schema,**本地检查、不调 LLM、fail-closed**);`rails.tool_input: flows: [tool result validation]` 查工具返回(**官方明说只查结构一致性,不做内容安检**)。
**解决什么问题**:给工具环节提供确定性闸机——能拦"调了没声明的工具、参数不合 schema、返回来源对不上";但 `path="../../.env"` 对 schema 完全合法,**参数语义有没有毒、返回内容有没有毒,都拦不了**。
**我们的办法**:对照结论——我们的两个缺口(write_file 参数侧投毒、间接注入经工具返回)NeMo 现成闸机各只能补一半;"llm-guard 分块扫工具返回"NeMo 不覆盖,得自己写 action 或继续用 llm-guard。

### 两套引擎与静默回退(LLMRails vs IORails Engine)
**是什么**:NeMo 0.23 有两套互斥引擎——LLMRails(Colang 事件驱动,默认,我们一直在用;execution rail = 用 Colang 在自定义 action 前后包检查流程,灵活但要写 Colang)vs IORails(0.23 新增实验性,环境变量 `NEMO_GUARDRAILS_IORAILS_ENGINE=1` 或改用 `Guardrails` 类开启,边界校验,tool rails 只在它上面跑)。
**解决什么问题**(暴露的坑):execution rail 有"两副面孔",选错引擎 = 闸机不存在;更毒的是 **tool rails 流名打错不报错,静默回退到 LLMRails、闸机全部失效,只有一条日志警告**——和阶段 1 的 base_url 坑同类:"配置错了不告诉你"。
**我们的办法**:用 tool rails 前必须确认引擎已切到 IORails;验收时以"攻击是否真被拦"为准,不能只看配置写了没——explain() 回放调用链(见 NeMo-0003 卡)是验活的手段。
