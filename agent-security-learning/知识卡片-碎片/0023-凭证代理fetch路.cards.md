# 0023 凭证代理 fetch 路 —— 知识卡片

### 占位符最后一刻注入(placeholder injection / last responsible moment)

是什么:最后一刻注入指请求里只写占位符、真密钥拖到请求即将发出的那一刻才由中间层替换进去,对应业界的 secret injection / just-in-time injection。典型如 Vault Agent 在消费点把动态密钥注入应用,以及动态密钥(dynamic secrets,按需签发、消费者消亡即失效)。「最后一刻」借自精益开发的 last responsible moment,其原始定义是「决策延迟的成本开始超过收益的那一刻」,用在密钥上即把凭证复用面压到最小(OWASP:动态密钥应尽量使用,以缩小凭证被复用的面)。真密钥只在即将出网的那一条请求里存在,替换完随请求走,不进环境变量、不进文件、也不进模型上下文。

解决什么问题:LLM 的密钥撤出 Agent 进程后,「密钥随请求出网」这条路还开着:模型只要在工具参数里写出真值(比如从上下文里骗到的 token),请求就会原样把它发出去;反过来,模型其实永远不需要见到真值。实测链路:模型生成 `http_post("https://httpbin.org/post", "token={{SECRET:DEMO_API_KEY}}")`,抓取工具把占位符换成真值后发出,远端回显 `{"form": {"token": "demo-sk-1234..."}}`。真值确实到了远端,而 Agent 进程的环境、内存、对话上下文里自始至终只有占位符。

我们的办法:替换点选在抓取工具的 server 进程而不是本地代理:抓取请求在一次性 microVM(短生命周期的微型虚拟机,请求即弃)里用 curl 发出,出网流量到不了宿主机上的代理,而策略表与出网白名单恰好同住这一层。真值用一条子进程命令从 macOS 的系统密钥库 Keychain 现取(如 `security find-generic-password -s DEMO_API_KEY -w`),用完即弃,实测合法请求四秒内完成且回显真值。

### 密钥名值分离(secret name vs secret value)

是什么:密钥名值分离(指「用密钥的一方只持有名字、永不持有值」的权限拆分)把一件事拆给三个组件:模型负责「要用哪个密钥」——在参数里写名字如 `{{SECRET:DEMO_API_KEY}}`;策略表负责「给不给」——按域名查授权;Keychain 负责「值是什么」。这个拆分对应能力导向安全里的指称(designation)思想:对象能力(object capability)是一种不可伪造的引用,权威只能被「递到手里」。被骗的持有者最多交出它手里有的东西——模型被骗了也最多写出一个名字,而名字过不了策略表。IAM 语境里则是策略决策点(策略表)与策略执行点(抓取工具)的拆分。严格说这是能力与 ACL(访问控制表,按名字授权)的混合:策略表按域名授权,并非纯对象能力。

解决什么问题:它针对「藏密钥」思路的天花板:真值一旦塞进环境变量,Agent 的所有子进程都看得见,藏得再好也只是换了个暴露面;拆权限则让攻击者即使完全劫持模型,拿到的也只是一张待审批的申请单。它与『占位符最后一刻注入』(见前卡)是同一思想的两次落地——对象能力文献的主张是:把一次性特权推迟到将要使用它的时候才授予。实测合法占位符一路走到远端并回显真值,模型全程没接触过真值。

我们的办法:凭证策略表与出网白名单放在同一个文件、同一段检查序列里——域名能不能去(白名单)与去了能带什么(凭证表)连着查,形态如 `httpbin.org` 只许用 `DEMO_API_KEY`。实测合法占位符正常放行,未授权名直接被拒,不带占位符的普通请求不受影响。

### 授权先于取值(authorize before lookup)

是什么:取值前的授权检查是凭证分发里的顺序纪律:策略检查必须排在密钥库查询之前,未授权的名字连密钥库都不碰,直接拒绝。这类拒绝是 fail closed(默认拒绝——检查给不出确定结论就拒绝,宁可让合法请求失败也不放行可疑请求)。

解决什么问题:顺序换了就漏信息:若先查密钥库再判授权,调用方就能从报错差异反推出密钥库里到底存了哪些名字。这类泄露对应业界编号 CWE-204(Observable Response Discrepancy,可观察响应差异——不同的响应会暴露内部状态信息),官方缓解建议是避免不一致的提示意外向攻击者泄露内部状态;除此之外,拒绝消息对「不存在的名字」与「存在但未授权的名字」还必须同构,否则仍留半个预言机(oracle——靠观察响应差异推断内部信息的探测渠道)。实测未授权名 `{{SECRET:OTHER_KEY}}` 的返回是「密钥 OTHER_KEY 未授权给域名 httpbin.org(请求未发出)」——报出的名字与域名只是回显调用方的输入,不算响应差异;差异只可能出现在「名字不存在」与「存在但未授权」两种响应之间,本实现两者同构,且请求未发出、密钥库未被查询,风险可控。

我们的办法:把策略检查代码放在密钥库查询之前,一次拒绝同时守住「不出网」与「不泄露密钥库存」两件事;实测未授权名在请求发出前即被拒,合法请求不受影响。

### 子进程继承环境变量(child process environment inheritance)

是什么:子进程会默认整份继承父进程的环境变量。POSIX.1-2024 对 exec 族的规定是:execl/execv/execle/execvp 这些不带 envp 参数的形式,新进程的环境取自调用方的外部变量 environ——这就是子进程「默认整份继承」父环境的标准来源;而 execve 的环境完全由调用方传入的 envp 数组决定。也就是说,操作系统创建子进程时,把父进程的 env(进程可见的一组键值配置,形如 `KEY=value`)原样复制给它。这意味着环境变量天然是跨进程的泄密通道——塞进 Agent 环境的任何「密钥」,它的每个子进程(包括抓取工具的 server)随手 `env` 一下就能看到。

解决什么问题:它解释了为什么「把密钥放回环境变量」不是凭证分发的合法落点。OWASP 明确提醒:环境变量一般对所有进程可读,还可能被带进日志或系统转储,因此不推荐用它存放密钥;12factor 推荐配置进环境变量与此并不矛盾——那是部署时注入配置的语境,不是长驻进程的密钥托管。抓取工具的 server 正是 Agent 的子进程,环境里的密钥等于重新放回攻击面,把 LLM 密钥撤出进程的努力就白做了;同理,任何能转储/导出环境的代码(dump 环境,注入得手后最便宜的一招)都能一次读走全部环境密钥。

我们的办法:密钥值的通道因此选系统密钥库现取:抓取工具的 server 在需要的那一刻用一条子进程命令向 Keychain 查询真值,值只活在即将发出的那条请求里,环境变量从头到尾只有占位符。即便确有必要给子进程传环境,也应按 POSIX 的 execve 接口用 envp 参数显式构造一份干净环境,而不是默认整份继承。
