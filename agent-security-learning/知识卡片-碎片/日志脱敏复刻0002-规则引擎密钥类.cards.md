# 日志脱敏复刻0002-规则引擎密钥类 —— 知识卡片

### 重叠裁决[自造]:具体优先、通用兜底(match overlap adjudication)

是什么:重叠裁决[自造](本项目对重叠命中取舍步骤的叫法)是多条规则同时命中同一段文本时的取舍机制——命中按"规则优先级、出现位置"排序,排前的先登记字符区间,后来的发现区间被占就让位。排序背后是一条设计原则:格式具体的专属规则排前,行为宽泛的兜底规则排后。

解决什么问题:规则之间会互相看中同一处敏感值,谁赢决定占位符标签准不准。比如请求头里的 `Bearer sk-proj-ABCD...`:宽泛的 bearer_token 规则认"Bearer 后面跟令牌"这个形状,专属的 api_key 规则认 `sk-` 开头的密钥格式,两条都想脱这一段。专属规则赢了,结果就是更精确的 `Bearer [REDACTED_API_KEY]`;兜底规则若赢,标签就变糊。同理 `token: xoxb-...`:兜底的"token: 赋值"规则想抓整串,专属的 Slack 令牌规则排在前头只把 `xoxb-` 值收走,键名 `token:` 原样保留。Presidio(微软开源的 PII 识别与匿名化引擎)按分数裁决,把上下文线索与校验结果折算成分数,高分命中吃掉低分(互不包含时);一段若整体包住另一段,它取更长的那条,哪怕分数更低。detect-secrets(开源密钥检测工具)按(类型, 位置, 哈希)去重合并;gitleaks(开源密钥扫描器)让各规则独立上报、互不压制。需要说明:这三家都不拿"数组顺序"当字符区间级的占坑裁决;我们选的顺序裁决是另一支,Presidio 选的是 score 裁决(按可信度分数定胜负)。顺序裁决是简化设计,代价是高优先级区间一旦占坑,本该命中另一子段的规则直接出局,两条无法共存。

我们的办法:规则表的排列顺序就是优先级,刻意把格式具体的放前、宽泛兜底的放后——顺序排错,兜底规则会抢走专属规则的地盘,占位符标签跟着全糊。实测这处双命中落成 `Bearer [REDACTED_API_KEY]` 而不是 `[REDACTED_BEARER_TOKEN]`。

### 捕获组与 span(capturing group)

是什么:捕获组是正则表达式里用圆括号圈出的"命中中的一小节"——整条正则匹配的范围可以很大,括号里的组单独圈出真正要脱的那截;span 是这截文字在原文里的起止坐标,Python 的 `m.span(g)` 返回第 g 组的 `(start, end)`。打个比方:安检翻包,整箱行李是匹配范围,只没收刀(捕获组),箱子和其他物品原样还你。

解决什么问题:脱敏的精细度全靠它,口诀是"键名是结构,值才是秘密"。连接串 `postgres://admin:S3cr3t_P4ssw0rd@db.internal:5432/prod` 里只有口令是秘密,用户名与主机名得留着——排障要靠它们定位是哪台库;正则 `://[^\s:/@]*:([^\s@]+)@` 整段命中,组 1 只圈口令,替换就只动组 1 的区间。三个使用细节:`\b`(词边界)防 `xsk-xxx` 这类粘连误匹配;`(?i)` 表示忽略大小写;组存在但没为匹配贡献文字时(Python 官方措辞 "exists but did not contribute to the match"),span 返回 `(-1, -1)`、`group()` 返回 None——两种判法等价,先过滤掉再用。一条规则有几种可选写法时组号可以是元组:兜底规则的 `(1, 2, 3)` 对应双引号值、单引号值与裸值三种写法,哪组参与了就用哪组。工业对照:gitleaks(开源密钥扫描器)规则里也有同一个概念 `secretGroup`,官方释义是 "Int used to extract secret from regex match"(一个整数,用来从正则命中里抽出秘密),指明抽哪一组当秘密;它的扫描报告里,一条记录(叫 Finding)同时带两个字段:`Match` 存整段命中,`Secret` 只存按 secretGroup 抽出的那一截文字。

我们的办法:每条密钥规则在规则表里声明自己的捕获组号,引擎只对组区间做替换、区间外的字符原样拼回;实测连接串脱成 `postgres://bob:[REDACTED_URL_CRED]@db:5432/x`,除口令外一字未动。

### 类别标签占位符(category-labeled placeholder)

是什么:类别标签占位符是替换敏感值时写明类别的占位符,如 `[REDACTED_JWT]`、`[REDACTED_SLACK_TOKEN]`、`[REDACTED_CREDIT_CARD]`,与无差别的 `[REDACTED]` 相对。它是给排障人留的门牌:看到标签,就知道这个位置曾是什么。

解决什么问题:日志脱敏不该摧毁可排障性。全换成无差别占位符,日志只剩"这里有个秘密"的废话——分不清曾是个 JWT、一张卡号还是一段连接串口令,排障线索断在占位符上。带类别的占位符把"曾是什么"留在现场,配合键名保留(如 `token: [REDACTED_SLACK_TOKEN]`),上下文依然可读。行业里这一做法有三个出处。Presidio(微软开源的 PII 识别与匿名化引擎)默认就拿实体类型当占位符,输出 `<EMAIL_ADDRESS>` 这类——与本项目同一约定,都是占位符携带类别名;但外观格式不同,它用尖括号、无 REDACTED 字样,而 `[REDACTED_*]` 这个前缀也没有官方成文标准,属本项目自定的外观格式。Google DLP(谷歌云的数据防泄漏服务)有个 `ReplaceWithInfoTypeConfig` 选项,官方描述就是"用 infoType 的名称替换每个命中"。OWASP(开放式 Web 应用安全项目)把敏感数据的处理归纳为五种:removed(删除)、masked(打码)、sanitized(净化)、hashed(哈希)、encrypted(加密)——带类别占位符更接近 masked/removed 之间的一种可读化变体。OWASP 对会话 ID 还专门提示:若需追踪会话级事件,可考虑换成哈希值——"保留可追踪性"有官方背书。

我们的办法:每条规则配一个专属占位符,命中即按类别替换;实测 4 条密钥样本共命中 7 处,各处都带着自己的类别标签,键名全部原样。
