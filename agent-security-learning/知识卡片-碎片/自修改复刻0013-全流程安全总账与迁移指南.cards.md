# 0013 全流程安全总账与迁移指南 —— 知识卡片

### 自我修改五路径威胁模型[自造](five-path threat model)

是什么:自我修改五路径威胁模型[自造](给「会自我修改的 Agent」画的威胁总图)指的是:这类系统好比一座能给自己砌墙的房子,攻击者共有五条入侵路线。五条路是:注入驱动的自我修改、模型端投毒、改裁判、伪造证据、验证体系表演。枚举攻击路径、逐条设防是安全工程现成的威胁建模(threat modeling,把攻防两侧都画进图里做风险评估)的惯例,五条路的具体划分是这份清单自造的部分。它的独特主张在后三条——根本不碰模型,专打验证体系与证据本身——其中最毒的是改裁判,验证体系被腐化后比没有验证更危险。

怎么得手:五条路各有入口:
- 注入驱动的自我修改:恶意 issue、网页、工具返回值里藏指令,骗 Agent「优化一下重试逻辑」,实际植入外传数据的代码。毒来自提示注入(prompt injection,把恶意指令塞进模型读到的内容里),自我修改能力让它落地生根;
- 模型端投毒:模型供应商被污染或模型被越狱,生成的补丁「看起来合理」,但该熔断(circuit breaker,失败时切断重试的成熟模式)时永不熔断;
- 改裁判:不绕沙箱(sandbox,隔离运行不可信代码的环境),直接把验证器改成无条件全 True,此后任何垃圾补丁都能盖上「已验证」的章。现实里有系统外的翻版:2024 年 XZ Utils 后门没有强攻任何服务器,而是腐化上游版本库与构建链,让带毒版本正常通过发布验证,直到有用户发现登录时 CPU 占用异常才败露;
- 伪造证据:篡改作为修改依据的事故记录,凭空捏造「该改代码」的理由,操纵流程改不该改的东西;
- 验证体系表演:没有坏样本对照,一套检查「看起来在工作」,实际什么也拦不住——业界把这种样子货叫 security theater(安全表演)。

我们的对策:五条路各有一道模型外的确定性闸接着。注入与假证据靠「多条独立事故记录指向同一失败模式才许触发修改」的点火门槛加草稿隔离收窄。被投毒的补丁靠只考行为、不看长相的行为考试拦住。改裁判与伪造证据靠可信根(root of trust,天生被信任、因此必须从设计上保证安全的起点,NIST 即如此定义)——此处取其软件级用法,指本系统圈定「哪些文件不许被改」的那份清单——哈希封条自证。做法是给这些文件在开工前和收工后各拍一次哈希(SHA-256,内容指纹)快照,纹丝不动才算数。快照对象是正本代码、验证器与事故记录存档。体系有没有空转,靠负对照(一个设计好必须死的坏补丁)必死来证明——它死得对,说明闸还真的在拦。注入本身不归这套骨架防:这套骨架是「假设注入终会成功」思路的下游,目标是让得手的注入拿不到有价值的后果。

### 注入的持久化通道[自造](injection persistence via code writes)

是什么:注入的持久化通道[自造]指提示注入把「一次性的欺骗」升级成「长期后门」的那条路径:在本系统的威胁模型里,持久化的主通道是让系统把恶意逻辑写进代码或配置。模型权重、训练语料这类非代码载体同样藏得住后门,但那归「模型端投毒」(模型本身或其训练材料被污染)路径的对应防线负责。普通注入骗的只是一次回答;对会自我修改、会写配置的系统,只要骗成一次「写文件」,恶意逻辑就成了永久住客,每次启动、每次调用都反复生效。

怎么得手:攻击话术不需要新花样——恶意工单里一句「帮我优化一下重试逻辑」,诱导 Agent 生成一段夹带数据外传的补丁;若这段补丁能直接落到正式代码区,后门就此长驻。业界把这招的管线版叫流水线投毒执行(poisoned pipeline execution,向构建管线配置注入恶意代码或命令、得手后以流水线身份行动)。它收录在 OWASP(发布业界最广引用安全风险清单的非营利组织)的十大风险清单里,与这条路几乎同构。写进代码的恶意逻辑还能藏得很深。微软研究院的代码补全投毒研究 TrojanPuzzle 更狠:可疑载荷片段干脆不进训练数据,只在注释等死角埋触发点,等模型生成代码时才把完整载荷吐出来——按特征扫数据集的静态检查什么都扫不到。所以这类攻击的门槛不在「骗到模型」,而在「写入正本」:骗得再成功,写不进正本就只能算草稿。

我们的对策:防在写入路径上——草稿与正本物理隔离(两个互不相通的目录),草稿写一百遍也碰不到正式代码。转正还要连闯三关。点火门槛要求同一失败模式有两条以上独立事故记录;行为考试把补丁真正执行起来,按「事办对没有」打分;最后只放行到影子灰度(shadow traffic,只喂镜像验证流量)。隔离草稿等于拆掉了注入的持久化通道——这套骨架不承诺拦住注入,但让得手的注入拿不到「长期驻留」这个最大头。

### 三权分离[自造](separation of duties in the pipeline)

是什么:三权分离[自造]指一种架构原则:把一次高危自动化里的三种权力——生成权(写提案)、验证权(打分)、决定权(放行)——强制分给三个互不隶属的主体。要害在后半句:任何一方被腐化,都不能单独造成危害。它是安全工程经典原则职责分离(separation of duties,关键操作拆给多个主体、单人无法独立完成破坏)在「AI 改代码」场景的实例;口语版就是:考生永远不能给自己打分——行业安全清单里的表述几乎同义,不让任何单一主体(无论人还是程序)能独自把敏感代码一路送到上线。

解决什么问题:如果生成补丁的一方也能验证、能发布,验证体系就是摆设——考生自己给自己打分。现实里模型的提示词可以被注入,补丁可以被投毒,沙箱(sandbox,隔离运行不可信代码的环境)也可能被漏洞打穿。三权分离保证的是:串起这些失守点的每一条「下一步权限」都握在模型外的确定性代码手里——没有单点被腐化能单独造成危害。它的保证范围还有一条清晰边界:职责分离的经典表述是「在不串谋的前提下降低恶意活动风险」——单人失守不成灾,多方合谋不在保证之内。

我们的办法:生成权归模型,它只能交一份提案文本进隔离目录。验证权归检查灯表[自造](候选放行前的固定格数布尔检查表,过一关亮一格),检查在沙箱里跑。决定权归一行模型外公式 `accepted = 有实际改动 and 灯表非空 and 全绿`,规则短到无法作弊,全绿也只放行到灰度(canary release,新版本先放给一小部分流量的分阶段上线)。

### 热更新按自我修改待遇[自造](hot-updates treated as self-modification)

是什么:热更新按自我修改待遇[自造]是一条迁移规则:凡能改变 Agent 行为的热更新通道,都按「改自己代码」同等待遇处理,而不是改完直接生效。这些通道包括配置文件、系统 prompt(写给模型的指令文本)与工具清单;待遇的具体形状是走候选、验证、灰度、回滚的流水线。这套待遇是业界 GitOps(声明式、版本化不可变、自动拉取、持续调和的运维方法,把系统期望状态存进版本库、由自动化把真实环境拉回声明状态)在 Agent 配置上的特例。

解决什么问题:配置和 prompt 常被当成「改改没关系」的轻量操作,攻击与事故恰好从这里进来。比如藏在热更新配置里的一条「把用户消息原文转发到外部地址」,一旦直接生效就全量命中,每一轮对话都在替攻击者外传数据。这不是多虑:「改动绕过审批直达生产」本身就是行业持续交付十大风险的第一条——拿到权限的人能独自把代码或制品一路推到生产,中途没有强制审批;配置热更新正是它的 Agent 版入口。配置错误与密钥暴露则是基础设施即代码(infrastructure as code,用文本配置声明并管理运行环境)安全清单的常客。还有两笔日常账:改坏时没有回滚点,事后没人说得出谁在何时改了什么。

我们的办法:迁移处方是把「候选物」从源码换成配置文本,其余骨架原样复用——同一套流水线已在代码自我修改上验证过,配置只是换了个乘客。配置改动先落候选区,过静态与行为检查(把改后的配置真正跑一遍看行为),再以灰度(canary release,新版本先放给一小部分流量的分阶段上线)方式生效;回滚触发条件发布前写死,决定与理由落盘留档——配置每个版本都在库里留有完整历史,回滚有据可查,与 GitOps 的思路互为印证。

### 考题外休眠逻辑[自造](dormant logic beyond exam coverage)

是什么:考题外休眠逻辑[自造]指恶意补丁在全部行为考题上表现完全正常、却埋了一段「只在考题没覆盖的输入上才触发」的恶意分支的攻击形态;近亲是逻辑炸弹(logic bomb,被故意埋进软件系统、满足指定条件才触发恶意功能的代码)。它利用的不是防线太弱,而是考试本身有限:行为检查只能考已知行为。

怎么得手:比如全部行为检查考的都是已知错误码上的重试与熔断表现,恶意补丁在这些考题上全绿,同时埋一句 `if error_code == "SPECIAL": do_evil()`,上线后等生产里出现这个错误码才引爆。更深一层:验收判据全过只证明「体系按设计运行」,不证明「设计覆盖了所有该考的行为」——这层覆盖率没有任何自动化能自动保证。现实注脚:2024 年 XZ Utils 后门在常规构建与测试里表现一切正常,只在特定链接条件成立时才激活,于是带着全套绿灯发布了出去。

我们的对策:现有缓解是把爆炸半径预先框死——全绿也只进影子灰度(shadow traffic,只喂镜像验证流量、真实用户不受影响),回滚触发条件发布前写死。开放解法是四件套,也是整套体系最值得继续投入的缺口:
- 更随机的属性测试(property-based testing,用随机输入检验代码该普遍成立的性质);
- 与稳定版[自造](作为修改对象的正式代码区)对拍的差分测试(differential testing,同一输入喂两个实现、只比输出,分歧本身就是缺陷信号)——恶意分支必然制造分歧,对拍因此抓得住休眠分支;用之前先划掉「预期 diff」的输入域:故意要改的行为本来就该有差异,只对不该变的输入比;
- 对条件分支提出覆盖要求;
- 安全评审人工把关,任何自动化都替代不了。
