# 0009 可信根自证 —— 知识卡片

### 可信根封条对比[自造](before/after hash seal)

是什么:可信根封条对比[自造]是在验证流水线开工前与收工后,对一批"被假定不会被腐化"的文件各算一次 SHA-256 哈希、再逐个比对的完整性自证方法;SHA-256 是安全散列算法,给任意内容算出固定长度的单向指纹,内容改一个字节,指纹就面目全非。被点名的这批文件借安全工程的正式概念**可信根(root of trust)**之名——美国标准机构 NIST 把它定义为天生被信任、必须从设计上保证安全的起点,其余信任都由它派生。这套自我修改系统点名的六个,覆盖生产正本、事故记录存档、聚合与发布决定的代码、沙箱(隔离运行不可信代码的环境)驱动、逐项行为检查程序、沙箱的容器镜像定义文件。六个全是"验证与依据"侧的角色,没有一个是"被验证对象"——候选代码与运行产物本就不在名单上,本来就该被流程随便折腾。

为什么重要:验证体系自己也需要被验证。六个名字各有其守:
· 生产正本——稳定版[自造](作为修改对象的正式代码区)里的重试控制代码——被改,回滚回去的就是被改过的版本;
· 失败轨迹[自造](生产事故的结构化记录)存档被改,想让系统"修"什么就能伪造出什么依据;
· 主裁判(聚合与发布决定的代码)的比较逻辑被改,"拒绝"当场变"放行";
· 狱吏(沙箱驱动程序)的容器参数被改一个,"禁网"变"通网";
· 阅卷人(逐项行为检查程序)被改成无条件返回通过,考试作废;
· 图纸(沙箱的容器镜像定义文件)被换掉基础镜像,全部加固作废。
最毒的攻击根本不绕沙箱、不碰检查项,而是直接改写验证器本体,让验证体系反过来给危险行为盖"已验证"的章——腐化的验证体系比没有验证体系更危险。这与"考题住在可信根一侧"(行为检查的考题必须放在补丁改不到的那一侧)是同一威胁的两面:那张卡讲考题该放在哪,这张卡讲拿什么证明它真没被碰。还有一条容易被当成口号的道理:口说无凭,"我没改"不值钱,密码学证据才值钱;"重要的东西要保护好"是愿望,"这六个文件前后哈希必须一致"才是机制——可信根是一份白纸黑字的名单,不是一种感觉,权限边界因此可审计。工业界对应物是可信平台模块(TPM,硬件形态的可信根)的度量启动(measured boot):启动时逐个组件计算度量值、累积进防篡改日志,再交远端服务器核验;这与本卡"开工前、收工后各拍一次快照"是同一思想的不同工程形态,类比而非同一机制。层级上也须点明:严格按 NIST 的定义,可信根是信任的来源(如硬件密钥、启动固件),这六个文件是信任链末端被重点看护的可信表面(trusted surface);本卡借名取义,把整份名单当作自证体系要守护的根。这套做法也是"先确认世界还是你以为的样子,再行动"的又一次落地:替换旧代码前先确认目标恰好出现一次、镜像名由构建材料的哈希派生,都是同族手段。

我们怎么用:流水线入口先给六个可信根逐一拍哈希快照,出口再拍一次,逐个对比后输出单一布尔结论,形如 `trusted_surfaces_unchanged = True`;对比过程逐文件打印 ✓/✗ 供人复核。实测整条流水线跑完,六份指纹纹丝不动。

### 规范化指纹(canonicalization / canonical JSON)

是什么:规范化指纹[自造]指哈希之前先把结构化数据转成一种与键序、空格无关的规范表示,使"内容相同 → 表示相同 → 指纹相同"成立的预处理步骤;这里的指纹指用 SHA-256 这类摘要函数给数据算出的比对值。Python 里最短的三步写法是"先排序、再文本化、后哈希":`repr(sorted(item.items()))` 先把键值对按键排序,再用 repr() 转成确定性的字符串表示,最后喂给哈希函数。注意 repr() 输出的是 Python 字面量(布尔与空值写作 True/False/None,字符串用单引号),并非标准 JSON(JSON,一种键值对文本格式)——这套简写只在同一语言内部自洽,跨语言、跨系统互算要用行业正式标准。

解决什么问题:直接对结构化数据的原始文本算哈希,"同一份数据"可能算出不同指纹。JSON(一种键值对文本格式)的键序在不同语言、不同序列化器下可能不同;`{"a":1,"b":2}` 与 `{"b":2,"a":1}` 是同一份数据、字节却不一样,指纹就对不上。反过来,格式化产生的空格差异又会造成"没改却被判改了"的假阳性;数字还有更隐蔽的一种——**`1` 与 `1.0`、`100` 与 `1e2`** 写法不同、数值相同,直接哈希也是各算各的。所以凡是要给结构化数据做指纹或签名,第一步都是先想清楚"什么算同一个"。这个套路的行业正式版本是 JCS(JSON Canonicalization Scheme,RFC 8785,规范化 JSON 的正式标准):键递归排序、去掉多余空白、固定转义规则、数字按统一规则序列化、统一用 UTF-8——思路完全一致,哈希前先规范化。

我们的办法:给每条作为修改依据的事故记录算一条内容指纹,形如 `"trajectory_sha256": sha256(repr(sorted(item.items())))`,指纹随发布清单[自造](把发布决定连同全部依据固化落盘的可审计文件)存档。这就好比起诉状不但要交,还要按手印:事后有人想偷换存档里的证据,指纹对不上,替换当场暴露。
