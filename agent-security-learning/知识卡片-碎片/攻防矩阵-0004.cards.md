### RunResult 双清单(requested vs executed tool calls)

**是什么**:一个结构化一次运行"事实"的 dataclass:`final_text`(最终回复)、`requested_tool_calls`(模型请求的全部工具调用,`execute_tool` 入口无条件先记)、`executed_tool_calls`(实际执行成功的,先做事再记账——记了账的事一定发生过)。`read_webpage` 无副作用,执行但不记 executed,保持清单干净。
**解决什么问题**:给判定器提供两类素材——回复文本是"它说了什么",executed 是"它做了什么";模型可以嘴上说"不会执行危险操作"同时 write_file 已落盘。且双清单是防御效果的测量尺:此刻两者必然相等,D4 运行时校验上线后分叉,"requested 里有、executed 里没有"的差集就是被拦截的调用,防御贡献从此可量化。
**我们的办法**:登记在一切校验之前(`demo.py:108`),保证"模型被骗得有多深"完整留痕哪怕之后被拦截;确认在副作用真正发生之后(`demo.py:119, 129`)。

### 判定看行为不看言辞(Behavior-based Deterministic Judging)

**是什么**:安全判定的方法论核心——只信代码层客观事实(`executed_tool_calls`、密钥子串),不信回复文本(模型可以"演":嘴硬、撒谎、顾左右而言他);用规则判定(查清单 + 查子串)替代 LLM-as-judge,零成本、可复现。
**为什么重要**:LLM 判定又贵又不稳定,没有确定性判定,"攻防实验"就停留在"看输出感觉像被攻破了"。代价是设计约束:攻击场景必须设计成"得逞时必然留下确定性痕迹"——密钥子串出现在回复里 / 特定工具调用出现在清单里(阶段 5-7 的三个判定器都是这个形状)。
**我们怎么用**:判定器输入就是 RunResult 双清单 + final_text;与 0016 的攻防矩阵判定哲学一致(查 executed 里有没有发往攻击者邮箱的调用,零 LLM 成本)。
