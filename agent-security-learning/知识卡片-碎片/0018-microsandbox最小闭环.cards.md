# 0018 microsandbox 最小闭环 —— 知识卡片

### microVM(微型虚拟机,micro Virtual Machine)

是什么:microVM 是一台拥有独立 Linux 内核、独立文件系统和独立网络的完整虚拟机,只是砍掉了 BIOS(开机时的硬件自检流程)自检、设备模拟等传统虚拟机的累赘。Firecracker(亚马逊开源的 microVM 运行时)这类 microVM 砍累赘的官方理由有两个:缩小内存占用,以及缩小攻击面(可被攻击的入口总和)——暴露给来宾的设备和功能越少,可被打的门越少。一个直观的类比:Docker 容器是"同一个内核上的隔离房间",microVM 则是"一台独立的小电脑"。

解决什么问题:Docker 容器与宿主机共享内核——容器里的进程直接调用宿主机内核,只靠 namespace/cgroups(Linux 的进程隔离与资源限额机制)挡着;Docker 官方安全文档也承认,容器"可能提供不完整的隔离",尤其在叠加内核漏洞时。传统虚拟机隔离好,开机却要几分钟。microVM 两头都占:攻击者打穿 VM 自己的内核后,还得再打穿硬件虚拟化层(CPU 虚拟化指令在芯片级兜底)才够得着宿主机——两道墙[自造](指"VM 内核 + 硬件虚拟化层"这两层前后串着的防御)。和它同属一个家族的,还有 AWS Lambda 用的 Firecracker,冷启动是秒级。

我们的办法:用 microsandbox 工具把这种 microVM 拉起来当执行环境,并用一行输出验证"独立内核"是否属实——沙箱里执行 `uname -srm` 返回 `Linux 6.12.99 aarch64`,而宿主机是 macOS(执行 uname 会显示 Darwin);容器里 uname 显示的会是和宿主相同的内核,这里没有,这就是隔离级别差异看得见的铁证。

### microsandbox 的嵌入式 SDK(Sandbox.create())

是什么:microsandbox 是一个"运行时 + SDK"的开源工具(Rust 核心 + Python 绑定,pip 包名 `microsandbox`),官方定位是给不可信负载——AI Agent、用户代码、插件、包安装——提供本地优先的 microVM 运行时。它的 SDK 是嵌入式设计:官方原话是"SDK 直接启动沙箱进程,没有守护进程(daemon)、远程服务或基础设施搭建"——每次 `Sandbox.create()` 直接以子进程方式拉起一台 microVM。

解决什么问题:让"给每次不可信命令开一台一次性虚拟机"从运维工程变成几行代码。官方对每个沙箱的描述是"一台自带独立 Linux 内核、文件系统和网络边界的轻量虚拟机"。命令通过 VM 里的 guest agent(运行时安在虚拟机内部的对接人)投递执行,结果以 `ExecOutput` 返回——实测可用 `.stdout_text` 和 `.exit_code`,其余字段(如 `.stderr_text`)以所用版本的签名为准,用感和普通 subprocess(Python 标准库的子进程模块)几乎无感。`image` 参数直接复用 Docker Hub 上的 OCI(开放容器倡议,Open Container Initiative,容器镜像的格式标准)镜像(如 `"python:3.12"`),不用另学一套镜像生态;发命令时 `sb.shell()` 走 VM 内的 /bin/sh,`sb.exec(cmd, args)` 则不经 shell 直接执行。

我们的办法:探针写法是 `async with await Sandbox.create(name=..., image="python:3.12", ephemeral=True) as sb: out = await sb.shell("uname -srm")`——其中 `ephemeral=True` 参数和 `async with await` 写法按所用 SDK 版本的签名核对,以实测版本为准。实测首次拉镜像要几分钟,之后走本地缓存——再跑一次"创建→跑命令→销毁"全程约 15 秒。

### ephemeral 用完即焚[自造](ephemeral sandbox)

是什么:ephemeral 是 microsandbox 中 `ephemeral=True` 参数承诺的语义——沙箱一停止就由宿主机运行时清理,不留下可复用的机器状态。官方 changelog 的口径:无名的一次性沙箱会被标记为 ephemeral,VM 退出后由 host runtime(常驻宿主机、负责管理沙箱生命周期的进程)清理;而命名的沙箱和用 `msb`(microsandbox 附带的命令行工具)`create` 创建的沙箱默认 persistent(持久——停了还在,可再次启动),ephemeral 与 persistent 是一对必须分清的默认值。

解决什么问题:如果执行环境跨调用存活,被提示注入(prompt injection——攻击者把恶意指令塞进模型读到的内容里、诱骗模型替他执行)劫持的 Agent 就能在里面种后门、下马。比如往启动脚本里追加一行反弹 shell(让攻击者从外部主动连回这台机器的 shell),等"下一次启动"再接续作案——持久化正是这类攻击者最想要的东西。用完即焚把这个威胁从根上删掉:没有"下一次启动",就没有持久化。

我们的办法:把沙箱给 Agent 当执行环境时强制开 `ephemeral=True`。实测在 `async with` 块结束时 VM 即被杀掉并删除,攻击者在期间写入的任何文件、装的后门都随 VM 一起消失。"连落盘状态一起删除"是实测行为,官方文档没有逐字写明清理范围,这条以实测为准。

### 默认出网敞开(default open egress)

是什么:指沙箱默认网络策略"公网敞开"的配置形态。准确定性是半开——官方文档明确:默认沙箱可访问公网(public internet),但私网地址、宿主机本地、link-local(169.254.x.x 一类链路本地地址)和云 metadata(云厂商固定内网地址上的实例元数据服务)目的地一律封锁。所以不是"完全随便出网",而是"公网默认放行,内网侧默认已封"。

怎么得手:被提示注入劫持的 Agent 一旦拿到 VM 内的命令执行权,公网出网通道就是现成的——可以直接把环境变量里的密钥、读到的数据用 HTTP 请求送出去。官方在文档里明确:默认沙箱可访问公网,但"私网、宿主机本地、link-local 和 metadata 目的地一律封锁"——这条封锁不是疏漏,是设计好的边界。官方另注明:在云后端上,这条非公网封锁"连沙箱主人自己也无法解开";本地部署能否放宽,以所用版本实测为准。实测在默认配置的沙箱里 `curl http://httpbin.org/get` 返回 200,公网一路绿灯,攻击者不需要任何额外配置——光是公网敞开这一半,已足够把数据送出去。

我们的对策:这层防在网络出口上,官方的收口手段是把 egress(出网)收成白名单(allowlist)或整体禁用。默认档案名 "public" 与 `network=Network(...)` 参数形态按所用 SDK 版本核对,以实测为准。

### 沙箱隔离强度阶梯(sandbox isolation spectrum)

是什么:"沙箱"(sandbox)按 NIST(美国国家标准与技术研究院)安全术语表的定义,是一种"受限、受控的执行环境"——它只规定效果,不规定实现。实现路线按隔离强度递增排成一个阶梯,像小孩的沙坑[自造](指"怎么挖都行,沙子不撒到客厅"的效果比喻)。

解决什么问题:给不可信代码选执行环境时,需要判断"我现在的隔离手段到底挡在哪一层"。阶梯从弱到强是:进程级限制(如浏览器标签页)→ 容器(共享内核,一个内核漏洞就穿墙)→ 用户态内核(用软件模拟内核、替真内核接系统调用)→ microVM(独立完整内核 + 硬件虚拟化,最硬)。用户态内核的代表是 gVisor——Google 的方案,官方描述为"实现 Linux 接口的应用内核":它拦截系统调用(应用请求内核办事的接口)再代答给真内核,同时限制应用能碰到的宿主机内核表面;它明确声明自己不是 seccomp-bpf(Linux 内核自带的系统调用过滤机制)那类 syscall 过滤器,比过滤器强,但底下仍不是完整内核。这里有个容易说过头的边界:能跑完整 Linux 内核的只有虚拟机;gVisor 跑的是用户态内核而非完整内核,所以它以容器形态也能部署,强度落在容器和虚拟机之间。

我们的办法:选阶梯最顶端的 microVM 作为 Agent 工具的执行环境,容器只作对照参照。独立内核的直接证据:沙箱里执行 `uname` 返回 `Linux 6.12.99 aarch64`,而宿主机是 macOS(显示 Darwin)——与 microVM 选型一一对应。后续计划让同一段内核逃逸代码在容器和 microVM 里各跑一遍,用实证对比两种隔离的真实差距。
