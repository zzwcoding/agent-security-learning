### RailsConfig / LLMRails / generate:声明式护栏的挂载点(NeMo Guardrails Minimal API)
**是什么**:`nemoguardrails` 包顶层三个件——`RailsConfig`(配置)、`LLMRails`(运行时,相当于"LLM 的物业前台")、`generate()`(发起对话)。`RailsConfig.from_path("config")` 传的是配置**目录**,`config.yml` 里 `models:` 必填一个 `type: main`,`engine: openai` 走兼容协议;`generate(messages=[...])` 入参出参照抄 OpenAI Chat Completions。
**解决什么问题**:护栏与业务代码解耦——以后加闸机只改 `config/` 里的 YAML,`chat.py` 一行不动;相比裸调 openai client,多出的就是一个可编程中转站。
**我们的办法**:配置在 `config/config.yml`,加载/调用在 `chat.py:11-12,23`。实测踩坑:NeMo 0.23 起用自家 HTTP client,**不认 `OPENAI_BASE_URL` 环境变量**,自定义端点必须写进 YAML 的 `parameters.base_url`(第一次跑 401 打到 api.openai.com 才发现,查源码 `llm/frameworks/default.py:119` 确认);api key 默认读 `OPENAI_API_KEY` 环境变量。

### 零 rail ≠ 纯透传:NeMo 默认流程(NeMo Default Generation Flow)
**是什么**:什么都不配,NeMo 每条消息也跑两步——①意图识别(先调一次 LLM 猜"用户想干嘛")②生成回复(再调一次 LLM,还自带一张出厂 system prompt)。它不是传话筒,是默认就开工的前台。
**解决什么问题**:解释了"裸跑基线"的真实含义——零防御不等于零环节;每次对话有隐藏的额外 LLM 调用和注入的指令,算延迟/token 账单时不能漏。
**我们的办法**:裸跑时攻击语料在这两步里原样穿过、框架没看内容一眼,两条 payload 全是最后一站被 MiniMax-M2 的对齐拒掉(框架零功劳)。记住这笔隐藏开销,阶段 5 算账要用;对齐靠不住已有专卡(模型对齐依赖),此处只记机制。
