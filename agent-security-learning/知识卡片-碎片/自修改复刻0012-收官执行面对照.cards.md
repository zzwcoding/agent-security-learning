# 自修改复刻0012-收官执行面对照 —— 知识卡片

### 执行面适配层[自造](execution-surface adapter)

是什么:执行面适配层[自造]是把沙箱(隔离运行不可信代码的环境)后端整体换掉、而上方验证逻辑一行不改的改造方法(执行面[自造]=不可信代码在哪一版隔离环境里运行)。协议界早有现成背书:MCP(Model Context Protocol,AI 应用连工具与数据的开放协议)原话是「协议语义在每种传输方式上完全相同,传输只是一层绑定」——换传输不换语义,正是「换后端零改调用方」的依据。适配器模式(Adapter,让接口不兼容的对象得以协作的经典设计模式)说的也是同一件事。适配完成的判据不是「新代码能跑」,而是旧测试全绿——这条判据是自创的验收标准。

解决什么问题:换后端有两个经典事故——调用方被迫跟着改写,旧版保障悄悄丢失。对策三条:
- 契约先行:新后端照抄旧后端的异常类型与返回结构。同一个 `SandboxError`(这套自建协议里统一的沙箱异常类型),同一套「退出码 0、输出为合规 JSON(JSON,一种键值对文本格式)、ok 为真」的验收逻辑,调用方零改动。MCP 的 stdio 传输(在客户端拉起的子进程标准流上按行传消息)换个载体,消息语义一字不改——绑定在变,契约不动。容器行业同款先例:OCI Runtime Spec(开放容器计划的运行时规范,给容器运行时定统一行为标准)的目的就是「在多个运行时之间提供一致环境」,runc/crun/kata 这些实现才得以互换。
- 差异最小化:把机构性差异列成清单,逐条追问「旧保障还在吗」。候选送达从烧进镜像改为经 stdin(标准输入,进程的标准输入流)直写虚拟机的临时目录,信任源不变,锚定物从镜像哈希换成每次直写宿主上那一份运行器文件。起进程从 `Popen`(直接派生子进程的系统接口)改为走 SDK(Software Development Kit,软件开发工具包,此处指沙箱工具提供的编程库)的 exec,删容器从强杀改为 ephemeral(用完即被运行时焚毁)自动消失。
- 同步封装异步:用 `asyncio.run()` 把 SDK 的异步接口包成同步函数,「世界是异步的」被挡在适配层身后。官方文档同时画了边界:同一线程里已有事件循环在跑时它不能再被调用,且应作为主入口、尽量只调一次。验证管线将来若整体搬进异步环境,这层同步封装就到头了——这是适配层真实的边界。

我们的办法:按这三条把微型虚拟机(microVM:带独立内核的一次性小虚拟机)后端接进验证管线,同一批候选在两种执行面各过同一组检查。实测新后端刚接进管线时,曾因忘喂标准输入而等到超时,异常顺着契约落进统一拒绝出口——fail closed(拿不到可信的通过证据就一律不放行)跨执行面开箱生效。

### 探针假跑[自造](silent probe no-op)

是什么:探针假跑[自造]指对照实验里的测量脚本根本没在目标环境执行、却留下「看似正常的空结果」的失效形态(探针=为观测隔离环境真实行为而送进去跑的固定脚本)。实测成因出在 Docker 的一条入口语义上:镜像的 ENTRYPOINT(容器一启动就先执行的入口命令)写成 exec 形式(`ENTRYPOINT ["prog","arg"]` 这样的数组写法)时,`docker run` 镜像名后面的命令不替换入口、而是追加成它的参数;入口写成 shell 形式(用 shell 包一层的写法)时,这些参数则被整个忽略。两种写法殊途同归:想喂一段探针脚本而敲下 `sh -s`,它根本没被执行,容器照常启动、输出为空。

为什么重要:空输出在对照实验里特别危险——很容易被误读成「沙箱里什么也干不了」,于是得出错误的隔离结论,其实目标环境压根没被测到。补全官方组合规则才不会再踩:入口 exec 形式对 run 参数是追加,shell 形式是整个忽略,而 CMD(镜像自带的默认命令)正相反,`docker run` 给了参数就整体覆盖它;想换入口,官方指定的手段是 `--entrypoint`。通用教训也有现成名字:变异测试(mutation testing,往代码里注入小改动看测试能否抓住的方法)的行话说,测试全过、坏变异却存活(survived),恰恰说明测试缺了这一环;混沌工程(chaos engineering,主动注入扰动检验韧性的方法)的对照组同理——空结果不构成证据,测量工具自身先要被证明真的在目标环境里跑过。

我们怎么用:探针容器一律显式 `--entrypoint sh` 覆盖镜像入口,再经标准输入喂脚本;实测覆盖后探针输出正常返回,两种执行面的对比数据从此可信。
