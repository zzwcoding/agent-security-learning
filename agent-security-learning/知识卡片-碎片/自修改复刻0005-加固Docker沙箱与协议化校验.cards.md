# 自修改复刻0005 加固Docker沙箱与协议化校验 —— 知识卡片

### 验证窄协议(protocolized verification exchange)

是什么:验证窄协议[自造](宿主程序与一次性容器之间唯一的数据交换约定)是一条固定格式的 JSON(JSON,一种键值对文本格式)消息通道。宿主把候选代码[自造](改出来、还没验证转正的草稿代码)与验证数据打包成一份 JSON,经标准输入(stdin,进程的标准输入流)塞进一次性容器,容器干完活只回一份 JSON 到标准输出(stdout)。这个形状不是自创的:模型上下文协议 MCP(Model Context Protocol,大模型接入外部工具的开放协议)的 stdio 传输,规格正是"一次性子进程、stdin 进 JSON、stdout 出 JSON"——本协议与它同构。宿主不 import(导入并加载)容器里的代码、不解析候选的任何行为,只认 stdout 回来的那份格式合规的 JSON——"不信任"在这里落实成"只通过窄口子交换结构化数据"。

解决什么问题:如果宿主和容器之间可以自由读写文件、共享内存、随意开接口,被验证的恶意代码就有无数个口子去伪造验证结果、摸宿主环境。窄协议把交换面压到最小,而且每一份消息都能做格式校验——不合规即拒绝;"stdout 只许写协议消息"这条纪律,与 MCP 规范对服务器的硬约束"不得向 stdout 写任何非协议消息"同款。官方文档还点名了"一次性收完容器输出"这类读法的坑:Python 标准库的 communicate()(等输出收完再一次性取回的读法)会把数据全部缓在内存,官方原话是"数据量大或无上限时不要用";宿主不读、操作系统的管道缓冲区被写满时,子进程还会死锁。

我们的办法:请求形如 `{"action": "ping", "source": <候选全文>}`,宿主实测收到的回执形如 `{"action": "ping", "source_bytes": 778, "trajectories_seen": 3}`——只有这几个协议字段,没有多余信息。取舍:输出读取是"收完再检"的简化实现,上一段的官方警告正是它的短板——恶意容器理论上可先用海量输出挤占宿主内存,该短板已记入复核清单(留待收官时统一复核的项目内待办)。

### 内容寻址镜像(content-addressed image)

是什么:内容寻址镜像[自造](组合叫法;'content-addressed,按内容算地址'是存储系统的行业通用思想)指镜像(Docker 的可复用打包环境)的名字由"构建材料"的哈希派生,而不是随手起的名字。具体做法:把镜像定义文件与容器入口程序两份文本一起算 SHA-256(安全散列算法,给任意内容算出唯一指纹),取前 12 位拼进名字,形如 `sandbox:4f8a2c1b9d3e`。定义文件或入口程序改一个字节,名字就整个变掉。这套思想有行业标准背书:OCI(Open Container Initiative,容器镜像格式的开放标准)规范把这种哈希叫 digest(内容标识符),官方说它"充作内容标识符,实现按内容寻址"。

解决什么问题:它把"跑的镜像"和"定义文件描述的镜像"焊死在一起。捣乱思路走一遍:假如有人偷偷改了本机现成镜像里的入口程序,让它无条件回"验证通过"——下次运行时系统按新内容算哈希,现成镜像里查不到这个名字。于是系统按锁定的定义文件现场重新构建一份干净的。想用被动手脚的镜像,得先让哈希对上,做不到。这正是 OCI 规范写明的保证:只要摘要本身经可信渠道送达,就能对来自不可信来源的内容独立重算摘要、确认它没有被改过。Git 官方文档开篇自称"内容寻址文件系统"——以内容哈希为 key(键)的键值存储,"凭哈希查本地镜像、查不到就重建"正是这个存储模型的日常用法。这和另一种核对是同一个思想:替换旧代码前,先确认目标位置恰好只有一处旧代码——先确认世界还是你以为的样子。

我们的办法:运行时先按内容算哈希查本地镜像,查不到就现场构建(取前 12 位是工程简化,OCI 规范用的是全量 `sha256:` 加 64 位十六进制字符)。日常红利:改了入口程序,镜像名自动变、自动重建,镜像永远和代码对齐,不需要任何人记得"重新构建"。

### Docker run 最小安全配方(minimal hardening flag set)

是什么:Docker run 的最小安全配方[自造](对一组安全 flag 固定搭配的叫法)指一条 `docker run` 命令上叠加的安全与资源 flag(命令行开关),把"跑不可信代码"的爆炸半径收到最小。关键认知:Docker 的默认运行其实很松——自带网络,以 root(Linux 最高权限账号)运行,权限位 capabilities(Linux 的细粒度权限集合)全开;安全不是 Docker 的出厂默认,是这些 flag 的叠加。

按"拦什么"分组的实配清单。网络与通信组:`--network none`(官方语义:只建回环网卡(loopback),数据送不出去),再加 `--ipc none`(不共享进程间通信资源)。文件系统组:`--read-only`(根文件系统只读),再加 `--tmpfs /tmp:noexec,nosuid`(要写也只能写进一块临时区:noexec 禁止执行、nosuid 忽略提权位,官方把两者列为并列项)。身份组:`--user 65534:65534`(降为非 root 的 nobody 账号),再加 `--cap-drop ALL`(权限位全丢),再加 `--security-opt no-new-privileges`(官方语义:禁止容器内进程获得新权限,装了它容器里的 su/sudo 直接失效)。资源组:`--pids-limit 16`(限进程数,防 fork 炸弹——进程疯狂自我复制耗尽系统),配 `--memory 64m` 与 `--memory-swap`(内存和 swap 一起限,单限内存会被 swap 绕过),再加 `--cpus 0.5`。痕迹组:`--rm`(跑完即删,官方原文连容器附带的匿名卷一起删),再加 `--log-driver none`(不落日志)。对照:官方文档里 `--pids-limit -1` 才表示不限进程数。

我们的办法:把整组 flag 写成一个固定函数拼进每条 `docker run`;容器入口进程再加 `python -I` 启动开关(Python 的隔离模式:不加载用户 site-packages 和 PYTHON* 环境变量),容器内环境一并收干净。

### fail closed(关死失败)

是什么:fail closed 指安全检查凡是"没拿到可信的通过证据",结局一律是不通过——宁可全灭,也不放行;反义词是 fail open(失败时默认放行)。它的学名叫 fail-safe defaults,出自 Saltzer 与 Schroeder 的经典安全设计原则清单,核心句是(中译)"基于许可而非排除来做访问判定——默认情形就是没有权限";更锋利的论据是 fail-safe 的错误会被立刻发现(拒绝是显式的),fail-open 的错误却静默通过(原话中译:"在正常使用中可能无人察觉")。

解决什么问题:沙箱验证的"异常"五花八门,每一种都长得像"临时故障";只要任何一种被当成"这次没验完,下次再看",恶意候选就能借故障蒙混过关:
- 墙钟超时(超时先强制删容器再报错);
- 内存超限(OOM,内存耗尽被系统终止);
- 退出码非零或输出不是 JSON(格式违规);
- 容器运行时缺失(执行环境不在)。
fail closed 把"没验成 ≠ 验过了"写成铁律:所有异常殊途同归,结论都是拒绝。

我们的办法:宿主侧设一个统一的失败出口——上面任何一项异常都汇入同一个"检查失败"出口,检查灯表[自造](候选放行前的固定格数布尔检查表,过一关亮一格)一格不亮。实测一个夹带恶意 import 的候选连沙箱门都没摸到:在更前面的静态检查就被拦下,沙箱的钱没花。
