# 自修改复刻0003 确定性提案与物理隔离 —— 知识卡片

### 候选与稳定版的物理隔离(candidate–stable physical isolation)

是什么:候选与稳定版的物理隔离[自造],指模型产出的修改草稿与正式生产代码被写进两个互不相通的目录、在文件系统层面互不可及的安排。这里的稳定版[自造]指自我修改系统里作为修改对象的正式代码区,候选代码[自造]指改出来、还没验证转正的草稿副本。这不是新发明:NIST 的 SSDF(安全软件开发框架,SP 800-218)实践 PS.1 要求"保护一切形态的代码不被未授权访问与篡改",思路同源:不该碰正式代码的东西,就在机制上让它碰不到。ThoughtWorks 技术趋势也把"给编码代理上沙箱执行"(隔离环境加受限文件系统)列为值得关注/采用的实践。物理隔离把"自我修改"降级成"给自己写草稿"[自造比喻]——好比改动先落功能分支(feature branch,与主线并行的开发分支)或预演环境(staging,上生产前模拟真实运行的副本环境)验证、再合入主干(trunk/main,正式代码所在的主线分支)。草稿错了扔掉就行,正本要转正必须过全部检查。

解决什么问题:它同时防两类风险:事故风险(草稿里的坏改动波及生产)和追溯风险(改完没有原稿可比对)。隔离还要配一道现场证据才可信:每轮生成后把稳定版重新读一遍、与改动前的文本逐字节比对。这正是"用哈希/校验和(checksum,给数据算出的比对指纹)验证完整性"的思路(提炼自 SSDF 的完整性校验要求)。比对打印形如「稳定版未被改动: True」的一行结论,隔离就从设计承诺变成当场可验的事实。

我们的办法:候选一律写进独立目录,稳定版一个字节不动;生成流程末尾固定做读回逐字节比对,实测每轮结果都是 True。

### 恰好一次匹配与大声失败[自造](自造组合叫法;exact-once/fail loud 是两个行业通用词)

是什么:恰好一次匹配是整块替换式打补丁的一道自我保护规则:每段要被替换的旧代码块,必须先在源码里恰好出现一次;出现 0 次(稳定版升级漂移、对不上号)或 2 次以上(源码被塞进了奇怪的东西)都直接抛错、拒绝动手。fail loud(大声失败)是它的配套立场:宁可让补丁失败并报错,也绝不含糊地猜着改。工程里有同款信条:维基百科把 fail-fast(快速失败)定义为"宁可停止正常运行,也不带着疑似缺陷的状态继续跑",《程序员修炼之道》(The Pragmatic Programmer)把它叫"尽早崩溃""死程序不说谎"。

解决什么问题:补丁最怕打偏,而行业默认语义恰恰是"尽力而为地猜"。经典打补丁工具 GNU patch 允许模糊系数(fuzz factor,匹配时容忍上下文有几行对不上的容差);手册明说"容差越大,补丁打错的几率越高"。patch 默认最大容差 2 行,实在贴不上的碎片写进 .rej(被拒绝的碎片)文件了事。比如稳定版里的重试函数被人改了名,替换器数出 0 次匹配,立刻抛 ValueError(内置的值错误异常)中止。严格匹配的价值正在于此:不像默认容差那样带着出入硬贴,静默生成一份根本没打上的"补丁",让病灶假装被治好。它和"动手前先算一份 SHA-256(安全散列算法,给文件算出唯一指纹)摘要做比对"是同一个思想:动手前先确认世界还是你以为的样子。

我们的办法:替换函数内置出现次数判断,计数不为 1 就抛错,等效于把模糊系数设为 0、拒绝产生 .rej 文件;给稳定版函数改名的捣乱输入走一遍即抛错,稳定版一个字节都没被改动。

### 补丁行为闭环[自造](behaviorally closed patch)

是什么:补丁行为闭环[自造]指一份补丁的各处改动互相配套、合在一起才构成完整的新行为;"最小 diff"(diff 即改动说明书,逐行写明删了什么、加了什么)里的"小"指改动行数少,不等于只改一处。Google 的工程实践指南(Small CLs)有同款标准:一个改动最合适的尺寸,是"恰好一个自包含的改动"(self-contained change)——只解决一件事的最小改动,并且小改动会被审得更细。修复常常是一剂多味的药[自创比喻]:改了函数,就得连着改这个函数查的表。

解决什么问题:"改了一半"的补丁最隐蔽——每一处局部看都对,合起来行为却不闭环。比如修"不可重试的错误被反复重试"要三处协调:先把新错误码加进禁重试清单;再让重试函数开头查这张表、命中就拒绝重试;再让熔断函数对永久错误立即熔断(连错 1 次就断,而不是熬满 5 次)。后两处都查第一处那张表,少改任何一段都不闭环:只改重试不改熔断,不重试的病好了,"永久错误陪跑满 5 次"的病还留着。

我们的办法:修复内容预先写成成对的旧块/新块常量,几段作为一个整体一次替换、一次打包;审补丁以"行为是否闭环"为准而非"处数最少",回归检查(regression,改完再跑一遍旧功能确认没弄坏)也重点盯这类改了一半的病。

### difflib.unified_diff(Python 标准库的 diff 生成器)

是什么:difflib.unified_diff 是 Python 标准库 difflib 模块里的文本对比函数,对比两段文本、输出 unified 格式(`---`/`+++`/`@@`/`-`/`+`)的"改动说明书"。unified 是由 GNU diff 推广、POSIX 手册收录的统一差异格式,git 默认也采用它。这份说明书只描述、不做修改:它只负责把改动说清楚给人看,真正动手改的另有其人——本项目正是看中这个分工才选它。

解决什么问题:审查补丁的人需要一眼看到"改了哪几行、从什么改成什么"。输出里 `@@ -l,s +l,s @@` 这样的行头给出改动块在两个文件里各自的起始行与行数(l 是起始行、s 是行数)。`-` 行来自旧文件,`+` 行来自新文件。用法上有三个易错点:输入必须是"行"的列表,要先用 `splitlines(keepends=True)` 切行并保留换行符,直接喂整块字符串 diff 会错位;`fromfile`/`tofile` 两个标签会写进 diff 头部,标成"修改前/修改后",说明书就自带从哪改到哪;返回值是行迭代器,要用 `"".join(...)` 拼成字符串再存。还有两个官方要点:参数 n 控制上下文行数、默认 3 行——传统补丁工具靠上下文行定位改动位置,上下文越多越贴得稳;difflib 默认给 3 行,与上一卡"不猜着改"是同一处较真;输入行若不带结尾换行符,官方推荐的另一条路是传 `lineterm=''`。

我们的办法:生成候选补丁时同步产出 diff 原文、随候选打包,发布存档时一并归档,人审与机器验证看同一份说明书。最小调用形如 `difflib.unified_diff(old_lines, new_lines, fromfile="修改前", tofile="修改后")`。
