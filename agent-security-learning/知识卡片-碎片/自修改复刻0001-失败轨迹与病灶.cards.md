# 0001 失败轨迹与病灶 —— 知识卡片

### 失败轨迹[自造](failure trajectory)

是什么:失败轨迹是一条结构化的生产事故记录,完整写明 Agent 一次失败任务的全过程。它是"Agent 自我修改"系统的输入原料——系统要改自己的代码,不能靠拍脑袋,得先靠这类记录看见自己病在哪。好的事故记录还要能算出影响面,比如这次事故多打了 3 次本不该发生的请求,还压住一笔该到账的支付。运维方法论 SRE(站点可靠性工程)的事故复盘就要求写明事故、影响、处置三件事。

解决什么问题:生产里 Agent 会犯"同一个错反复重试"这类事故,比如银行已明确回绝的扣款它连着提交了 4 次。把事故固化成统一格式的记录,后面聚合、立案(把聚合结果定为一份正式的修改请求)、改代码、验证每个环节才有东西可消费,修改的"起诉状"[自造](比喻自创)才算立得住。这种字段组合也有行业参照——HTTP 重试库 urllib3 裁决"该不该重试"时,就按错误类别、请求方法、状态码清单逐类判定。它默认只重试幂等方法,即同一请求重复发结果不变的那种。

我们的办法:每条事故落成一行 JSON 记录,关键取值形如 `"error_code": "PAYMENT_DECLINED"` 配 `"retryable": false` 再配 `"attempts": 4`,再附一句人话 evidence(证据原文)。`retryable=false` 意思是"这种错别重试",与"试了 4 次"并排一放,"不该重试却在重试"的实锤就摆在纸面上了。

### 改代码,不改 prompt[自造](本卡片体系自立的立场口号,非现成术语)

是什么:这是给自我修改系统选"改哪里"的一条立场:修 bug 要把改动落在代码的控制逻辑上,而不是往 prompt(写给模型的指令文本)里加一句嘱咐。要说清楚:靠文字反馈改进并不算错——研究项目 Reflexion 就让 Agent 用语言反思任务反馈来改进(不更新模型参数),是公认有效的路线。区别在于文本改进无法机器验证,代码改动却可以编译、重放失败案例、跑回归测试。自创比喻(文献里没有对应说法):prompt 是"劝"——像门上贴张"请勿入内"的纸条,可能被无视,而代码是"闸"——重试控制函数返回 `False` 就是 `False`,落下了就是落下了。

解决什么问题:prompt 里的嘱咐会被长上下文稀释、被别的指令覆盖,而且加了一句话没法系统地检验它管不管用。代码则相反——研究项目 Voyager 让 Agent 把学到的技能沉淀成可执行代码库,靠环境反馈、执行报错和自我验证来迭代改进,吃到的正是"程序可被机器验证"的红利。所以只有代码改动才谈得上"验证",后续所有语义检查(对候选改动逐条跑的自动化行为测试)验的全是行为,prompt 无从验起。

我们的办法:面对"不可重试的错误被反复重试"这个病,立场选改重试控制代码而非加 prompt;立案结论也明写"根因在控制代码,不在 prompt",模型只许照方抓药。

### 故意预埋的 bug(intentionally seeded bug)

是什么:指在稳定版[自造](自我修改系统里作为修改对象的正式代码区)里故意保留、不许提前修掉的已知缺陷。它是整个自我修改流程要对付的固定目标:提案、安检(发布前对候选改动的静态安全检查)、验证、发布(把改动正式对外推出)每个环节演的都是"怎么安全地把这个 bug 改掉"。行业里有近亲:混沌工程把"凡能打破稳定状态的事件"都当作可注入的实验变量。软件测试里也有"植入缺陷"(seeded fault / mutation testing)的成熟做法,故意往代码里种 bug 看测试抓不抓得住——这里就是它的静态版,检验对象换成整条自我修改流水线。

解决什么问题:复刻或测试自我修改系统需要一个确定、可复现的病。要是有人手痒把它修好,后面所有环节就无病可治,整条验证链当场断掉。SRE 书(发布工程一章)要求发布流程的任何改动"应是有意的,而非意外的",预埋缺陷把"有意"写到极致。

我们的办法:把"此缺陷系有意保留"写进代码首行注释,复刻纪律是原样保留,顺手修好反而算做错。这次的病根有两处:重试函数收了 `retryable` 参数却不用、只看次数没到上限就放行,熔断同样不看错误类型而让永久性错误陪跑满 5 次。

### 标准库读 JSON 的惯用两连(Path.read_text() + json.loads())

是什么:这是 Python 标准库(pathlib 与 json 模块)读 JSON(JSON,一种键值对文本格式)文件的两步固定搭配:先用 `Path.read_text()` 把整个文件一次读成字符串,相当于把"打开-读-关闭"并成一步;再用 `json.loads()` 把字符串解析成 Python 对象。

解决什么问题:零依赖地读配置和事故记录,不必引入任何第三方库。最大的翻车点是编码参数:官方文档写明,不指定 `encoding` 时文本模式用的编码取决于平台(platform-dependent,会调用 locale.getencoding() 取系统区域设置)。中文 Windows 上常落到 GBK 这类本地编码,文件里中文一多就会抛 UnicodeDecodeError(内置的标准解码异常),所以跨平台读中文务必显式写 `encoding="utf-8"`。另外别和收文件对象的 `json.load()` 混用,loads 的 s 是 string(字符串);顺带一提,3.6 起两者都能直接吃二进制——loads 接受 bytes/bytearray(按 UTF-8/16/32 解码),load 的文件参数也能用二进制模式打开。

我们的办法:用 `Path(__file__).parent` 拼相对路径而不是写死绝对路径,脚本换台机器也能跑,读文件固定带上 `encoding="utf-8"`。最小形态形如 `json.loads((ROOT / "data.json").read_text(encoding="utf-8"))`。
