# 日志脱敏复刻0005-离线回归pytest —— 知识卡片

### 认证挑战头(HTTP authentication challenge)

是什么:认证挑战头是服务器返回的"请出示凭据"响应头——RFC 7235(现由 RFC 9110 §11 承接)定义:它 "indicates the authentication scheme(s) and parameters applicable to the target resource"(指明适用于目标资源的认证方案与参数)。服务器返回 401(Unauthorized,此处意译为未认证)响应时必须携带它,典型样子是 `WWW-Authenticate: Basic realm="api"`。它与请求方发出的凭据头(形如 `Authorization: Basic ...`、真正携带密钥,RFC 说 Authorization "allows a user agent to authenticate itself"——让客户端证明自己)同样带 Basic 字样、长得几乎一样,语义却完全相反。凭据头是"这是我的密码本,拿去";挑战头是"请出示密码本",里面根本没有秘密。

解决什么问题:形状类脱敏规则容易把两个头一锅端,可脱挑战头是纯误伤——它只声明服务器接受哪种认证方案,一个密钥都不含。而且这类头在日志里躲不掉:规范明文禁止代理改写 WWW-Authenticate 与 Authorization 这两个字段("MUST NOT modify"),它们是合法、必然大量出现在日志里的内容——脱挑战头不是在除害,是在误伤。realm 是其中的参数,官方措辞是 "a scope of protection"(保护范围);RFC 7617 补充说它只是 "free-form string that can only be compared for equality"(自由格式的字符串,只能比较是否相等)。我们的规则天然挡得住,靠的是只认字面键名:Basic 认证规则要求文本出现字面单词 `Authorization`,挑战头里只有 `WWW-Authenticate`,对不上;`realm` 也不命中引擎里那条"形如 键名=值 就当密钥脱"的兜底规则的键名表,于是零命中、原样放行。

我们的对策:把这条边界写成回归断言 `assert sanitize('WWW-Authenticate: Basic realm="api"') == (原文, [])`——文本不变与零命中两个条件都要;将来谁把正则放宽成 `(?i)\bAuth\w*:\s*Basic` 这类模糊匹配,这条断言立刻亮红。

### 断言式回归测试(pytest)

是什么:断言式回归测试[自造](把回归写成一行行断言的做法)是把"引擎行为对不对"写成一行行 assert(断言:机器可判定的等式,不成立就报错)、每次改动后自动重跑的验证方法。回归测试按 ISTQB(国际软件测试资格委员会)v4.0 的说法属于变更相关测试(change-related testing)——验证改动之后,没被改到的部分依旧正常。pytest 是被广泛使用的 Python 测试框架——官方文档的自我介绍很朴素:"helps you write better programs"(帮你写出更好的程序)。它会自动发现文件名 test_ 开头或 _test 结尾的测试文件与 test_ 开头的函数,逐个执行、失败即亮红。和手跑脚本看输出的区别:脚本输出的对错靠人眼判断,人眼会累会漏,assert 不会。失败时框架还自动打印断言两侧的实际值,不用自己写 print 调试——这招官方叫断言重写(assertion rewriting):assert 语句在运行前被改写,把内省信息直接放进失败消息里。

为什么重要:规则既是资产也是负债:每条正则都在特定形状上生效,改任何一条(嫌正则太长、把下限调短)都可能让别的规则误伤别的文本,没有回归时这种伤是无声的。测试把"我以为还是对的"与"它真的是对的"之间的差距,变成机器可判定的一行红字。纯规则引擎的测试不碰网络、不碰模型,全套 0.01 秒跑完,快到可以每次改动都跑——真正贵的是没有它之后的排查。

我们怎么用:给规则引擎配了 7 个边界测试,每个锁一个曾差点写错的地方——
· 截断的 PEM 私钥块(文本格式的密钥块);
· 带空格的自然语言口令;
· 认证挑战头(服务器索要凭据的响应头)。
命名即文档:函数名直接写行为结论(如 `test_basic_auth_redacted_prose_and_challenge_not`),要脱什么不脱什么全在名字里;注释讲为什么这是边界——规则会换写法,边界不会换。

### 两档负例[自造](two-tier negatives)

是什么:两档负例[自造](行业里没有现成的对应术语)是把负例(长得像敏感信息、其实不该被脱的正常文本)按"回归里怎么处置"分成两档的设计。"必须干净"档指引擎理应完全放行的文本,如口令规范说明、干净的业务日志——它们进回归,命中即红。"已知误报"档指形状必然骗过格式规则的文本,如长得像手机号的纳秒耗时 `latency_ns=13800138000`——如实承认它会中招,故意不锁进"必须干净"。方向要钉死:这里的负例指"预期零命中、应当放行"的文本(度量里的真负例),与 ISTQB 的 negative testing(故意用系统没被预期的方式去喂,看它能不能正确接住)方向相反,不是一回事。

为什么重要:回归套件是一份长期承诺:锁进什么,就得一直做到什么。把已知误报锁成"必须干净",测试要么永远红着、逼人写出错误的规则,要么逼人删掉承诺——两种结局都让回归说谎。留在套件外,它才能在后续基准评测里当真值负例(即不敏感、理应放行的样本),算出真实的查准率(precision,报出的命中里真敏感项的占比)。这个指标的经典公式(scikit-learn 文档)是 tp/(tp+fp),其中 tp=真阳性(真敏感被报出)、fp=假阳性(不敏感被误报),最好值为 1。这套分档挂靠的度量概念是误报(false-positive result,ISTQB 的定义:缺陷并不存在、测试却报了缺陷的结果)——"已知误报"档就是承认这类结果存在,但不让它们绑架回归。做法上最接近 WAF 和杀毒软件的误报调优与例外管理,行业里没有现成的标准词条,定位是项目设计约定,并与查准率的度量惯例接轨。这条与"先定考卷再动工"分工:考卷[自造](项目对动工前标注好的测试样本集的叫法)管动工前样本怎么定,这条管动工后哪些负例进自动化回归。

我们怎么用:"必须干净"档与正例行为一起构成引擎的 7 个回归测试,全绿才算完工;"已知误报"档留在样本集里、不进断言,预留给后续基准评测量化成查准率损失。以后每添一条新边界,先问一句:它是"必须干净",还是"已知误报"?
