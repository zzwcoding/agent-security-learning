# 自修改复刻0007 容器内语义检查下 —— 知识卡片

### 成对检查[自造](paired must-change / must-not-change checks)

是什么:成对检查[自造]指每一项"新行为必须变对"的检查旁边,都站着一项"旧行为不许变"的检查,两者互为配重的验证设计。只考新行为的验证体系会培养出投机取巧的补丁:最省事的过关修法是把出问题的功能整个禁掉。比如把重试一刀切关掉,失败重放[自造](拿生产真实失败案例当考卷的验证方式)照样满分——可临时故障也没人重试了,超时恢复率从 100% 掉下来。治一个病不能治出另一个病,反向考题必须成对出现。

为什么重要:它把"验证体系自己会被应试"这件事纳入设计。旧行为那半边,近亲是业界的不变式(invariant,任何改动后都必须仍然成立的性质);把它逐条落成检查,就是后文回归测试的思路。新行为那半边,对应性质测试(property-based testing,验证"代码普遍该成立的性质")要守的 property。蜕变测试(metamorphic testing,用"输入变了但输入之间该满足的关系仍成立"来出题)里源考题与配重考题(source / follow-up test case)的分工,与失败重放和临时恢复的配对结构相似。补丁(尤其是将来的大模型补丁)会在考卷结构里找最省事的过关路径,单边考题等于邀请它用阉割功能换绿灯;成对出题之后,想全绿就必须真的把病治好、且不伤别处。

我们怎么用:实测一个把重试整个禁掉的偷懒补丁,在"新行为必须对"的几格检查里全绿,到"临时恢复"这一格当场熄灯。成对检查专逮卷面全对却功能被阉的候选[自造](改出来但还没验证转正的草稿代码)。

### 临时恢复检验[自造](temporary recovery check)

是什么:临时恢复检验[自造]是一道专考"该重试的还得能重试"的行为检查。它问候选[自造](改出来但还没验证转正的草稿代码)"可重试的临时超时错误、第 0 次和第 1 次尝试,该再试吗",必须答"再试"。它考的对象,对应业界重试模式(Retry pattern)里的瞬时故障(transient fault,偶发、通常会自愈的错误,稍候重试多半就成功)。它也是失败重放[自造](拿生产真实失败案例当考卷的验证方式)的配重——失败重放说"失败过的别再试",这条说"该重试的还得能重试",两句话合起来才是完整的重试纪律。

为什么重要:业界重试模式本就把"放弃(cancel)"与"重试(retry)"并成一对,还自带次数上限——重试到预定的次数仍不成功,就按失败上报。瞬时故障时好时坏,围绕它写的测试若不控制随机性,就成了 flaky test(不稳定测试:同一份代码既跑出过通过、也跑出过失败);同理,修复"不该重试的在重试"时,不能顺手把"该重试的能恢复"也修没了。

我们怎么用:提问形如 `should_retry("TEMPORARY_TIMEOUT", True, 0)`,期望答案是"再试";实测修复后的候选两句全答对,一刀切禁掉重试的候选在这格熄灯。

### 旧任务回归[自造](old-task regression check)

是什么:旧任务回归[自造]是把补丁动手之前世界本来的老规矩逐条重演、要求新补丁对这些老场景的回答一分不许漂移的行为检查,守的正是"旧行为不许变"的不变式(invariant)。考题就是旧行为的行为快照,比如:第 0 次、第 2 次尝试可以重试,第 3 次不行(3 次封顶);连续临时失败 4 次不熔断(circuit breaker,失败攒到阈值就暂时切断对下游调用的模式),攒到 5 次才熔断(阈值还是 5)。

为什么重要:这是回归测试(regression testing,软件测试标准 ISTQB 对它的界定:改动后重测软件的未变区域、确认没有在这些未变区域引入新缺陷)在行为层的用法:补丁的世界里,旧行为是防波堤。它有个在 ISTQB 里分开定义的搭档——确认测试(confirmation testing,重跑上次失败的用例、验证修复确实生效),失败重放[自造](拿生产真实失败案例当考卷的验证方式)与临时恢复检验正对应这一侧。对将来真实大模型交来的补丁,"看起来合理但破坏旧行为"是最典型的失败模式,这道检查就是专门拦它的。

我们怎么用:老规矩全部写成"具体输入→期望输出"的硬编码断言;实测修复后的候选[自造](改出来但还没验证转正的草稿代码)逐问答对,动了病灶之外行为的补丁会当场暴露。

### 金丝雀过拟合考题[自造](canary anti-overfitting probe)

是什么:金丝雀过拟合考题[自造]是一道专拿失败轨迹[自造](生产事故的结构化记录)里从未出现过的错误码出题的行为检查,考补丁学会的是"规则"还是只背下了"答案"。这里的 canary 取"金丝雀式预警"之意,与发布领域的金丝雀发布(canary release,新版本小流量逐步放给真实用户)同名不同物:那边是放量上线,这边是预警用的小考题。考法带一处陷阱:挑一个躺在永久错误清单里、但数据里从没出现过的码(例如 `AUTH_DENIED`),故意把它标成 `retryable=True`,看候选[自造](改出来但还没验证转正的草稿代码)听规则还是听标记。

为什么重要:防的是过拟合(overfitting,模型把见过的材料背得太熟、换新数据就答不对的机器学习通病,即"背答案"压过了"泛化")。题目取自从未参与修复的留出集(held-out set,从头到尾不给修复看、专门用来考试的题目),这类从没露过面的输入(unseen input)最能照出背答案;只拿修过的那个错误码出题,等于鼓励补丁写死"只认识这一个码"。一对互相矛盾的信号一给,背答案的补丁当场露馅,学会查表规则的补丁才过得去。

我们怎么用:期望答案是"不重试、1 次就熔断,同时临时错误的恢复不受影响";实测学会查表规则的候选三项全对。

### 回滚就绪验证[自造](rollback readiness check)

是什么:回滚就绪验证[自造]是把"退路"也当考生的一道检查:它验证的不是候选,是回滚目标。做法是发布候选之前,先把稳定版[自造](自我修改系统里作为修改对象的正式代码区)源码也执行、考试一遍。确认版本号还是老的(比如 `VERSION` 仍是 `1.0.0`),老行为(比如第 0 次能试、第 3 次拒)依然健康。

为什么重要:发布领域里回滚本就是"切回去":蓝绿部署(blue-green deployment,新旧两套环境并存、随时整体切换的发布方式)的回滚,是把流量切回一直没接客的那套;金丝雀放量的大部分时段,老版本仍承接主要流量,是天然退路。但蓝绿部署的文档只写切回,不要求先验证切回目标可用——"退回前先证明退路现在就能跑"是本文的自造加严,与运维界"备份必须试恢复"的恢复演练(restore testing)是同一条纪律。这也是"敢灰度"的底气来源(灰度发布:canary release,新版本先放给一小部分真实用户、稳定版继续承接主要流量的分阶段放行方式)——退出通道被证明是通的,发布决策才大胆得起来。

我们怎么用:实测稳定版通过版本号与老行为考试,证明退路是通的;发布环节因此可以放心把候选放进灰度。

### 考题住在可信根一侧[自造](exams live on the trusted-root side)

是什么:考题住在可信根一侧[自造]指行为检查的考题代码必须放在补丁改不到的那一侧。它们与验证程序一起归入可信根[自造](安全工程正式概念 root of trust:NIST 定义为"高度可靠的硬件、固件或软件组件,因被天然信任,必须从设计上保证安全"(节引),其余信任都从它派生;NIST 即美国国家标准与技术研究院)。此处取其软件级用法,属自造延伸。

解决什么问题:考题就是验证体系的裁判规则;如果考题本身写在后续流程(将来包括大模型补丁生成)够得着的地方,删掉答不对的几行断言,全绿就唾手可得。NIST 还给"专管校验更新"的信任根单列了子类(update verification),与这里"验证器不许被补丁改动"的约束几乎一一对应。考题不可改写,绿灯才有含金量;这与"稳定版代码、审计日志(按时间顺序记录系统活动的日志)、验证器不进自我修改权限"是同一条安全骨架。

我们的办法:全部行为检查连同验证程序一起,住在容器内的验证运行器里、归验证器一侧,不放在宿主(跑验证流程的本机)任由后续流程修改;每道考题都是"几组具体输入→期望输出"的硬编码断言,没有模糊地带——比如"第 3 次尝试还该重试吗→必须答不"就是这样一条写死的断言。
