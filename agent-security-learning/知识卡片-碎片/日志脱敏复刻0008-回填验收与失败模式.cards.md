# 日志脱敏复刻0008-回填验收与失败模式 —— 知识卡片

### 原文出现检查(verbatim occurrence check)

是什么:原文出现检查是一个确定性谓词(输入定了、结果就定的判断式,由机器判定,不掺模型的主观),判断"模型给出的替换值是否是原文的子串"。它是回填验收闸[自造](LLM 脱敏结果回填——回填即把验收通过的值替换进原文本——之前的确定性验收:模型报出的每个值必须在源文本里逐字找到,否则整条作废,已有专卡)的核心判定,参考实现里叫它"值出现在文本中"检查。判定式是 `value.lower() in text.lower()`:两边都转小写再比对,容忍模型改写大小写——模型报 `ALICE@CORP.COM` 而原文是小写 `alice@corp.com`,照样过闸。这个判定有官方背书:Python 文档原话是"空串总被视为任何字符串的子串"(Empty strings are always considered to be a substring of any other string),并给出等价写法 `y.find(x) != -1`(find 找不到才返回 -1)。

解决什么问题:它把"模型的话"翻译回"文本里的坐标"——模型的输出是不可信的值,但"这串值在不在原文里"机器说一不二,不可信的建议接上确定性的检查,才变成可信的操作。两个坑要挡在门外:一是空串,`'' in 'abc'` 为 True,不先排除,模型交白卷也能过闸;二是正则元字符,但要不要转义取决于替换机制——若用 str.replace(按字面做文本替换的方法),值只是普通文本,完全不需要转义;只有把值直接当正则模式用(比如 re.sub 的第一个参数传值)才需要先 re.escape(把字符串里的正则特殊字符转义的标准操作),Python 3.7 起它只转义真正可能在正则里有特殊含义的字符(最小转义)。官方还特别提醒:re.escape 的输出不能拿去当 re.sub 的替换参数——替换参数里只有反斜杠需要转义,转义用错了地方,替换结果照样错。还有一个易误判处:"是子串"不等于"是干净的值"——模型报 `card: 4111 1111 1111 1111` 能过闸,但键名 `card:` 被连着一起替换掉了,过闸只是必要条件,不是充分条件。

我们的办法:每个模型报出的值先过这个谓词、再回填;替换按值的长度降序进行,先长后短,防止短值先动刀破坏长值的匹配位置——与规则引擎的重叠裁决[自造](多个命中按优先级裁定谁保留,已有专卡)是同一思想。

### 检出≠脱成(detection ≠ redaction)

是什么:"检出≠脱成"指敏感信息被检测出来,不等于它被安全替换掉了——从"看见"到"换掉"之间还隔着一步,这一步自己会失败。它是残余泄露(脱敏完成后仍留在文本里的敏感信息)的一种来源,且与漏检不同:漏检是引擎没看见,这一种是看见了、也判对了,却没能替换。业界的成熟框架也是这么分家的:Microsoft 的 Presidio(开源的个人敏感信息识别与匿名化框架)把 detection(识别)与 anonymization(匿名化)拆成两个模块。后者只作用于前者的输出,而且默认只替换检出的片段、未识别内容原样不动。

怎么发生的:端侧小模型检出了社保号,判得对,但报出的值不干净:`holder_ssn: 123-45-6789 /think`。尾巴 `/think` 是模型思考标签的碎片,不是原文的子串——过不了验收闸(验收闸=模型报值回填前的逐字子串检查,已有专卡),被拒收,原值不动。回填后的文本里,社保号原样躺着:

```
[PAYMENT] order 20260831-0042 charged
[REDACTED_敏感值]
holder_ssn: 123-45-6789        ← SSN 原样留在文本里
```

解决什么问题:它点破验收闸的能力边界——闸保护的是"不做错误的替换",不保证"该替换的都替换了",拒收不等于安全;"闸不管漏检"也是行业常态,Presidio 对未识别内容默认不动就是佐证。描述性短语同理:模型交回"用户的网银登录口令"这类转述,判得再对也无处落刀。要量化这类泄露,得靠专门的残余泄露指标,光数检出项没用。

我们的办法:引擎分工从源头减少——格式型值(社保号和各类卡号、手机号)的字符区间正则永远给得准,交给正则先行兜住;LLM 只管它真正的主场,即住址、自然语言口令这类语义类别,值不干净的情形随之变少。

### 端侧推理非确定性(LLM inference nondeterminism)

是什么:端侧推理的非确定性是指同配置重复推理仍可能得到不同输出的现象。同一条提示词、同一个随机种子,在同一台机器上跑两次,端侧模型(跑在本地设备上的模型)的答案也可能不一样。官方归因很具体:浮点加法不满足结合律,(a+b)+c 不总等于 a+(b+c),大量浮点求和时先加谁后加谁(归约顺序)不同,结果就差一点点。误差逐层放大,足以翻转模型的最终判断——而归约顺序由 kernel(计算核函数)、批次组成与线程调度决定,不是纯硬件层的锅。PyTorch 官方把 randomness(随机性)与 nondeterministic algorithms(非确定算法)列为两个独立来源,种子只管前者;推理服务文献给后者的标准术语是 batch invariance(批次不变性,要求每个元素的归约顺序不随批次大小改变)——它点明这不是随机,是顺序依赖。

实测的样子:同一条日志样本、同一配置跑两次,一次报 0 个敏感项、一次报 2 个——两次都是"真"的,这不是代码 bug,是物理现实。

解决什么问题:它修正对"可复现"的期待。固定随机种子(seed,控制模型采样随机性的参数)只锁得住软件层,锁不住归约顺序;vLLM(流行的开源大模型推理服务)的 FAQ 说得很直白:同样的请求可能被打包进不同的批次,逐步产生略微不同的 logits(模型对每个候选 token 的打分),分歧一旦开始,后续只会越岔越远。推理服务文档给的缓解有关键计算用 float32(更高精度的浮点格式)、temperature>0(采样温度,控制采样随机性的参数)时给请求固定种子;PyTorch 另有强制确定性算法的开关——都带性能代价。评测基准跑一次只是一次抽样,单次跑分里的个别出入可能只是这种噪声,不说明引擎退步或进步。

我们的办法:把"同配置复跑会有出入"当作默认认知,关键结论不建立在单次运行上。
