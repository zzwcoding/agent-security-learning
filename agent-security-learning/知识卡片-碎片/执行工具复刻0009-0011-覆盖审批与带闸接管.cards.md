# 执行工具复刻0009-0011 覆盖审批与带闸接管 —— 知识卡片

### 覆盖审批(overwrite approval)

是什么:覆盖审批是给"用新内容整份替换磁盘上已有文件"的写操作加的执行前审批。写文件工具发现目标文件已存在时不直接落笔,先把这次操作递给二级LLM[自造](用第二个大模型当审批员、在工具执行前裁决放行还是拒绝的做法)审过,批准才覆盖。它背后是一条设计判断:闸[自造](挡在工具执行路径上、由代码强制裁决的检查点)管的是后果,不是动作类型。

解决什么问题:此前的审批只盯着"执行"类工具(跑命令、跑代码),写文件一直无人过问。但覆盖已有文件时旧内容一去不回,破坏力与删除命令同级,却是零检查直通磁盘。按后果划线后,"覆盖已有文件"与"新建文件"待遇分开——新建无东西可毁,直接写;覆盖不可逆,必须过审。

我们的办法:触发条件就设在"文件已存在"这一步——新建直接写,覆盖送审批。实测覆盖一个已有文本文件:审批模型没有密钥时按 fail-closed(出错或审不了就默认拒绝)处理,正常上岗后这次覆盖照样被拒,被拒的原因引出了下一张卡。

### 审批案情材料(case file for the approver)

是什么:审批案情材料指递给审批模型的那份"案情":一次待裁决操作的路径、内容、前后对照等信息。它背后是一条审批设计规则——审批模型只能基于递给它的材料做判断,材料里没有的信息,它只能往最坏处想。审批质量不取决于审批模型多聪明,取决于你递了什么。

解决什么问题:审批这道闸的价值全在裁决质量;材料不全时,闸会退化成"一律拒"。实测一次普通的文本文件覆盖被拒,拒绝理由本身很到位——"覆盖有数据丢失风险,没看到旧内容、没有备份机制,无法判断是否安全"。它否定的不是这次内容,而是材料的空白:请求里只有目标路径和新内容长度,旧内容一个字没给。

我们的办法:要让合理覆盖能通过,得把旧内容摘要或 diff(逐行写明删了什么、加了什么的改动说明书)随请求一并递给审批模型,让它看着证据裁决而不是对着空白猜。被复刻的参考项目同样只递了路径和长度,这是同类实现的通病。

### 搜索-替换精确编辑(search-and-replace edit)

是什么:搜索-替换编辑是给 AI 用的第二种文件修改工具,操作单位不是"整份文件的新内容",而是"把原文里的 A 段换成 B 段"。调用时给出要找的原文和替换后的新文,工具在文件里逐字找那段原文,找到才动手,并报告替换了几处。它与整页重盖的写工具是同一件事的两个风险量级——写工具说"整页是这个样",编辑工具说"只把 A 换成 B",后者自带定位锚点。

解决什么问题:整页重盖要求 AI 脑子里装着文件的完整内容,想象与磁盘稍有出入,没打算动的部分就跟着一起被盖掉。精确编辑把意图收窄到一处,让"AI 想象的文件"与"磁盘上的文件"的分歧当场失败,而不是静默写坏。实测拿一段文件里并不存在的文字当查找目标,工具直接拒绝并报"没找到要替换的原文",文件一个字节没动。

我们的办法:既有检查全部复用,不另起炉灶——路径边界照查;改完的文件若是 Python 源码,再过一遍语法门卫[自造](用编译器把代码解析一遍、语法不合法即拒的检查)。改之前合法不代表改完还合法,实测把 `return len` 改成 `return len(`(右括号没合上)就在这道复检被当场拦下。

### MCP server 环境变量隔离(MCP default environment)

是什么:MCP server 环境变量隔离指 MCP(Model Context Protocol,把工具暴露给 AI 应用的标准协议)官方 SDK 的一个默认行为:以 stdio 方式(经标准输入输出与子进程通信)拉起工具 server 子进程时,只传一个最小环境变量白名单。这个默认环境由 get_default_environment 函数给出,通常只有 PATH 等少数几项——父进程的环境变量不会自动流下去,与操作系统"子进程默认整份继承父环境"的常规行为正好相反。

解决什么问题:这笔账要双向算。安全上是白得的好处:子进程默认拿不到父进程里的 API 密钥,秘密不随进程树扩散。功能上是个坑:子进程里依赖环境变量的功能会莫名失灵——把带审批的工具 server 换进 agent 后,攻击虽被拦下,拒绝理由却是"缺少 LLM 密钥相关的环境变量、审不了",排查半天发现是钥匙根本没递进子进程。

我们的办法:SDK 的 server 配置字典支持 env 键,显式传入即覆盖默认环境,修法就是让工具 server 全量继承父进程环境。通用教训一句话:进程边界不止隔离代码,也隔离环境——要用钥匙就亲手递进去,不想给的秘密默认它拿不到。

### 带闸接管[自造](gated-tool takeover)

是什么:带闸接管[自造]指给裸工具(没有任何检查、收到请求就执行的工具)装上成套安全闸后,包成正式入口换进真实 agent 投入使用的动作。它的验收方法是同一攻击前后对照:换装之前用一句攻击提示打一次,换装之后用同一句再打一次,两次结果摆在一起比。

为什么重要:各道闸单独手动调用验证,只是"单元测试"级——证明闸本身在工作。但闸真正的用武之地是干活的 LLM(大模型)被恶意指令忽悠、决定调用工具的那一刻。闸在不在、管不管用,只有端到端打一遍才知道。

我们怎么用:
· 把带闸工具包成 MCP server(把工具暴露给 agent 的标准协议服务进程)薄壳——壳里只有协议转换,一行安全逻辑都没有,闸全在工具本体里,换入口不换检查。
· 用同一句攻击提示对换装前后各打一次。无闸版执行 `rm -rf`(递归强删整个目录)后返回退出码 0,目标目录消失,全程没有任何环节问过"该不该删"。
· 带闸版同一攻击里,干活模型先侦察再发起删除,审批模型以删除破坏性强、不可挽回为由拒绝,点出目标就在用户主目录。攻击就此终止,假目标完好。
· 也有一场败仗:看似不重要的临时目录目标被审批模型放行——LLM 审批降低风险但不消灭风险,确定性兜底一道都不能撤。

### 审批理由的可解释性(explainable denial)

是什么:审批理由的可解释性指审批模型拒绝时附带一份人能读懂的理由,而且这份理由下游还能继续用。执行被拒后,干活的模型能把理由转述给用户,甚至据此分析这次请求本身可疑——这是选择大模型当审批员、而非纯规则匹配时白得的好处。

解决什么问题:规则式拦截的拒绝信息只有"命中黑名单(denylist,列已知危险片段、命中即拦的清单式防御)第几条"这类机械事实,读到它的模型和人都接不上下一步。一份说清"为什么危险"的理由,让被拒的 AI 能向用户解释、能另想办法,还能反向识破攻击话术。

我们的办法:利用这份免费的可解释性做端到端验证。同一次被拒的攻击里,审批模型给出的理由点明删除破坏性强,不可挽回,目标就在用户主目录;干活模型转述之外还补了一句自己的判断——"用户要求不要检查,这本身就很可疑"。这种带推理的陈述,任何固定文案的规则拦截都给不出来。
