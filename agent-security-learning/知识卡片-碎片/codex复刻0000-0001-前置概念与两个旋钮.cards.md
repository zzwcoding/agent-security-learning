# codex复刻0000-0001 前置概念与两个旋钮 —— 知识卡片

### 沙箱与强制者层级(sandbox and its enforcer)

是什么:沙箱(sandbox)是一种由操作系统内核强制执行的能力限制机制。它让进程在"被削权的笼子"里运行:笼子外的文件、网络、其他进程,在系统调用(应用请求内核办事的接口)层直接失败,返回 EPERM(内核表示"操作不被许可"的错误码)。关键是问一句"谁执行限制":提示词里写"请不要删除文件",执行者是模型自觉,幻觉、注入、误解都能破防。应用层用正则拦"危险命令"靠字符串匹配,写法无穷多、匹配不完,而只有内核执行的沙箱绕不过——被限制的进程根本不知道笼子存在,越界对它只是"失败了"。

解决什么问题:终端 agent(在终端里自主调用工具、执行命令的 AI 程序)的价值来自"真动手",这决定了约束不能只停留在提示词层。沙箱并非新发明:Chrome 的每个渲染进程、iOS 的每个 App 都跑在沙箱里,用途永远是同一件事——跑不完全可信的代码。它给安全评估立了第一问:这个产品的限制是谁执行的?答案若是"模型自己",基本等于没有限制。

例子:同一条 `rm -rf ./build`,提示词防线可能被一句"忽略之前的指示"绕过;内核沙箱下,这条命令对可写范围之外的路径只会收到 EPERM,模型说什么都改变不了结果。

### 两个独立旋钮(sandbox mode × approval policy)

是什么:codex(OpenAI 出的终端编码 agent,用自然语言让它改代码、跑命令)的权限是两个独立旋钮[自造](把两项权限配置比作两个互不联动的调节钮的说法),不是一个开关。沙箱模式(sandbox mode)回答"命令跑起来后,内核层能做什么"——可写哪里、能否联网。审批策略(approval policy)回答"命令被沙箱挡住后,流程上怎么办"——弹窗问用户,还是直接拒绝。审批策略的取值有 untrusted、on-request(默认)、never 三档,它不产生任何安全边界,只决定人机交互的密度。

解决什么问题:把两件事混成一个开关,会犯最常见的错——把 approval 弹窗当成安全边界。审批提示作用于提示词层,模型可以绕:换种说法再请求、把大动作拆成多步。沙箱绕不过:内核策略默认全拒(deny default),违规写返回 EPERM,与模型意图无关。所以"会不会弹窗"和"安不安全"是两回事:嫌弹窗烦,该调的是审批档位,不是把沙箱放开。

例子:两者可独立组合设定,形态如 `codex --sandbox read-only -a never`(只读沙箱,配永不弹窗),也可以写进配置文件的 `sandbox_mode` 与 `approval_policy` 两项。

### 越权命令的执行链路与拒绝回喂(rejection feedback loop)

是什么:一条命令从模型提出到落地,走一条固定链路。模型产出的工具调用(模型发出的"请执行这条命令"的请求)此时只是文本;codex 拿当前生效的"沙箱模式 + 审批策略"组合来裁决:沙箱先判"能不能",被挡后审批再判"怎么办"。执行结果或拒绝原因,都会作为工具返回文本回灌进上下文(context,模型当次读到的全部内容),模型据此调整下一步。

解决什么问题:它回答"无人值守时怎么办"——自动化流水线里没有人可以点弹窗。

例:模型提议 `echo hacked > ~/.zshrc`(往用户家目录的 shell 配置文件写入),read-only 沙箱下这条写路径在系统调用层就失败。审批策略若是 on-request,就弹窗问你,点同意则这条命令在沙箱外执行、写入成功。若是 never,则不弹窗,直接把硬拒绝文案喂回模型——文案形如 "writing is blocked by read-only sandbox; rejected by user approval settings",模型读到便自己绕道,比如改为只给建议不动手。失败同时表现为非零退出码,自动化流水线因此能感知并继续,而不是对着一个永远等不到按键的弹窗干等。

### 失败闭合的默认值(fail-closed defaults)

是什么:失败闭合(fail-closed)是一种默认值设计纪律:安全系统的默认状态,必须让"出错、未配置、机制缺失"倒向安全一侧,而不是放行一侧。codex 的落地有三处:网络默认关闭;Windows 上没有等价沙箱机制时,把 workspace-write 档静默降级为 read-only——宁可降级也不假装安全;CI(持续集成,无人值守自动跑脚本的流水线)无头模式默认审批策略 never,绝不弹窗干等。

解决什么问题:它对冲的是"默认值会骗人"。同一个仓库克隆到两个目录,可能一个生效 workspace-write、另一个生效 read-only——取决于你几周前在哪个目录回答过一次信任提示;脚本里不显式传 `--sandbox`,行为就是抽奖。旗标还会随版本变动:`--full-auto` 已被删除,旧教程仍在推荐。配错的代价也不对称:配松是安全事故,配紧只是 agent 干不了活。

例子:评估任何 agent 产品时,把默认值与降级行为单独过一遍——试它的无头模式、试它没配沙箱机制的平台,看它倒向的是"拒绝"还是"放行"。

### 可写挂钩目录即代码执行(writable git hooks)

是什么:这是一条"可写文件升级成任意代码执行"的攻击路径。`.git/hooks`(git 版本库的挂钩目录,存放提交等事件发生时自动执行的脚本)里的脚本,会在对应 git 事件触发时被运行。谁控制了这个目录的写权限,谁就埋下了"下次事件自动执行"的代码。

怎么得手:agent 一旦被 prompt injection(往模型读到的内容里塞恶意指令、诱骗它替攻击者执行的攻击)劫持到能写工作区文件,向 .git/hooks 写入一个提交前钩子即可。攻击至此收手,用户下次正常提交代码时脚本自动执行,无需再次发动。codex 的对策是把 .git 连同 .agents、.codex 列为沙箱内不可写的保护路径。

例子:做安全评估时的追问不是"这个目录可写能删什么",而是"它能升级成什么"——一条可写路径的终点,可能就是任意代码执行。
