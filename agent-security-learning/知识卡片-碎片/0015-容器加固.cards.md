# 0015 容器加固 —— 知识卡片

### 进程边界与数据边界(process boundary vs data boundary)

是什么:数据边界与进程边界[自造](按拦的对象把 Agent 防御分成"拦毒文本"与"限进程权限"两组的自创划分)是两类互补边界。数据边界指挂在文本进模型路径上的自动检查,如输入扫描、工具返回过滤、输出过滤,拦的对象是毒文本。进程边界指用操作系统机制限制 Agent 进程自身权限的手段,代表是容器加固(hardening,收紧容器的运行参数)。两者的分工是:护栏[自造](挂在 Agent 链路上的防御检查点)压低沦陷概率,加固压低沦陷后的损失,相乘才接近真实风险。例:若护栏把沦陷概率压到十分之一、加固把沦陷损失压到百分之一,两者叠加后风险约是原来的千分之一;只装其一就少压一个数量级。

解决什么问题:数据边界是概率性的。OWASP(开放全球应用安全项目,发布十大安全风险等权威指南的行业组织)对提示注入的权威判断是:现有措施只能缓解影响,无法根除。提示注入(prompt injection,往模型读到的内容里塞恶意指令、诱骗它替攻击者执行)靠分类器打分,而分类器会漏判、能被话术绕过。所以失效假设必须包含"护栏全崩、攻击者已能让 Agent 执行任意命令"。进程边界为这个最坏情形兜底:目标从"防住攻击"换成"压缩爆炸半径(blast radius,一次得手的攻击能波及的范围)"。这个词有出处:NIST SP 800-190(美国国家标准与技术研究院的容器安全指南)原文就带引号使用 "blast radius",说的是限制被投毒镜像能波及的范围。Docker 官方文档同义:入侵者即便在容器内提权到 root(Linux 的超级用户,拥有系统全部权限),也更难造成实质破坏、更难逃逸到宿主(宿主:运行容器的那台机器)。只装一类,另一类失效时就没有退路。

我们的办法:给已装三层护栏(输入扫描、工具返回过滤、输出过滤)的 Agent 叠加一组容器加固参数(非 root 身份 / 只读根文件系统(read-only filesystem,容器内整棵目录树设为不可写)/ 内存与 CPU 限额 / 剥光特权位)。实测注入照样劫持到命令执行。写标记文件被只读根文件系统以 `Read-only file system` 拒绝。出网未限,如实记为已知缺口。

### 拦的是意图、动作还是后果(what a defense actually blocks)

是什么:拦什么三分法[自造](评估一层防御前先问它到底拦住了哪一环:攻击者的意图、命令的执行动作、还是执行在环境里造成的后果)是给防御定性的第一步。容器加固属于最后一类:恶意命令在加固容器里照样被执行,只是效果被环境吞掉。

为什么重要:不定性就会错位记账——把"命令还是跑了"记成整层防御失败,或把"跑了但没成"夸成全链安全。这个定性有官方背书。NIST SP 800-190(美国国家标准与技术研究院的容器安全指南)指出,只读根文件系统让容器对入侵更有韧性(resilient,被攻破后仍能限制破坏),篡改会被隔离在环境里。Docker 官方同样把"拿到权限"与"造成损害"分成两环来谈。定性之后还能排出加固的优先级。攻击者拿到执行权后最常见的落地动作是写文件、改配置、植持久化(在机器上安插重启后仍存活的后门)三类。只读文件系统与非 root(root 即 Linux 最高权限账号)两项参数,就把这三类全部挡下。

我们怎么用:让同一条攻击在无防御与加固两种环境各跑一遍、只比最终效果。无防御宿主上,`run_command("touch PWNED-direct-injection")`(用能执行操作系统命令行的工具在当前目录创建标记文件)退出码 0、文件真实出现。加固容器里同一条命令照样执行,却得到 `Read-only file system` 报错、文件不存在。结论:这层防御拦的是后果,不是执行本身。

### 构建期烘焙(build-time baking)

是什么:构建期烘焙[自造](把运行时才需要的重型依赖——模型文件、深度学习框架、分词工具——提前到构建镜像时联网下载一次、固化进镜像层的做法)是只读加固的直接推论。英文工程圈惯用 bake 一词。注意撞词:Docker 官方还有一条 `docker buildx bake` 命令,指多目标构建编排,与"把依赖烤进镜像"毫无关系。容器以只读根文件系统加非 root 身份运行,运行时没有可写位置、也下不了东西,依赖只能在构建期取好。

解决什么问题:不烘焙,加固容器一启动就缺模型缺包,根本跑不起来。烘焙附带可移植性:镜像自带全部依赖,不依赖宿主机缓存。代价要记账:依赖全部算进镜像,实测镜像约 4.96GB、启动多约 5 秒的模型加载。烘焙之外还有两笔工程细账。一笔是 /tmp 挂的 tmpfs(内存盘:放在内存里的临时文件系统,内容不落盘、断电即失):官方说明 tmpfs 内容只保存在宿主内存里,且计入容器的内存 cgroup 限额(cgroup:内核按组记账和限制资源用量的机制);也就是说,64MB 的 /tmp 挤占的是内存额度而非磁盘。另一笔是挂载属主:挂载进容器的工作区文件默认归宿主用户所有,非 root 的容器用户写不动。本项目在挂载侧用 `chmod 666`(把文件权限放开为所有用户可读写)手工放开,否则 Agent 的记忆文件写不进;更干净的另解是构建时按宿主 UID(用户在 Linux 里的数字编号)建同名用户,从根上对齐属主。

我们的办法:在 Dockerfile(声明如何一步步构建容器镜像的配置文件)的构建过程里先跑一次扫描器(注入分类护栏的加载入口)初始化。让模型联网下载并落进镜像层,一次性把依赖"烤"进镜像。

### codex 的三档沙箱模式(codex sandbox_mode)

是什么:沙箱模式(sandbox_mode)是 OpenAI 的命令行编码 Agent codex 用来规定 Agent 进程能写哪里、能不能联网的参数,共三档。`read-only` 档什么都不能写、网络默认只许 localhost(本机回环地址,出不了外网);`workspace-write` 档只有当前工作目录和 `/tmp`(临时目录)可写、网络默认关但可显式打开;`danger-full-access` 档读写全部、网络开放,等于裸奔[自造](无任何防御的基线形态)。

解决什么问题:三档把"给 Agent 多大权限"变成可枚举的选择,而不是全有或全无。两个设计点值得借鉴。其一,机器限制与人审分离:官方原话是沙箱负责划定边界、审批策略决定何时先来问你,两者互相独立——sandbox_mode 与 approval_policy(人工审批策略,决定哪些动作要人点头)各调各的。其二,它的沙盒官方明说"既不是虚拟机也不是容器",直接用操作系统原生机制锁 Agent 进程——macOS 用 Seatbelt(系统自带的强制访问控制框架),Linux 用 bubblewrap(把命令包进受限环境运行的沙箱工具;早期实现用 Landlock 与 seccomp,即内核的文件访问限制与系统调用过滤机制)。

我们的办法:拿三档对照自家抉择——自建方案相当于 `workspace-write` 档(仅工作区加临时目录可写)。网络因要调 LLM API(大模型接口)而选择保留,比 codex 默认松;这道敞开的门如实记为缺口,靠出网白名单(只放行访问少数已知域名的出站连接)补齐。对比一笔:三档里只有 `danger-full-access` 一档放开网络与全部写权限;自建方案比 codex 默认(`read-only`、网络仅 localhost)松了两处——可写目录与出网。
