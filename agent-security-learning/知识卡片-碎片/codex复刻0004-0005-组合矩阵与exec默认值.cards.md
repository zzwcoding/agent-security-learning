# codex复刻0004-0005 组合矩阵与exec默认值 —— 知识卡片

### granular 审批(granular approval)

是什么:granular approval 是 codex(OpenAI 出的终端编码 agent,用自然语言让它改代码、跑命令)里按类别细分的审批配置形态。它不是命令行上的一个取值,而是配置文件(config.toml,Codex 的 TOML 格式配置文件)专属的结构体。这个结构体把"要不要问人"拆成三个分类开关:sandbox_approval(被沙箱挡住时是否征询)、rules(命中自定义规则时是否征询)、skill_approval(动用某项技能时是否征询)。
解决什么问题:命令行的审批策略(approval policy,决定"命令被沙箱挡住后怎么办"的设置)只有 untrusted、on-request、never 三档,粒度是一刀切;想要"某一类动作自动拒、另一类照常问"的细分控制,只能落到配置文件里。开关设为 false 的含义是自动拒而非弹窗——延续了"无人在场时不等待"的思路。
精读结论:评估 agent 产品的审批配置时,先分清哪些取值暴露在命令行、哪些只活在配置文件里;后者往往是更细但更少人知的控制面。
例子:概念形态如 `sandbox_approval = false`(被沙箱挡住时不弹窗,直接自动拒),而命令行上敲 `--ask-for-approval granular` 是不存在的——这个值只在配置文件里合法。

### untrusted 更吵不更安全(untrusted: louder, not safer)

是什么:untrusted 档(审批策略里最严的一档,只有"已知安全"的只读命令自动放行、其余全部征询)有一个反直觉结论:它没有让系统更安全,只是让它更吵。它改变的是"问你多少次",沙箱(sandbox,由操作系统内核强制执行的能力边界)范围一点没动。
解决什么问题:破除"审批越严越安全"的错觉。判断一个"沙箱模式 × 审批策略"组合安不安全,只看沙箱那一列;审批列决定的是弹窗密度和失败长什么样。所以 untrusted 的正确用途不是"加保险",而是"不信任当前任务本身"的场景。
精读结论:给 agent 选审批档位时,想要"安静的安全",答案是更紧的沙箱配上 never(永不弹窗),而不是换一个更响的审批档位。
例子:workspace-write(允许写工作区)沙箱配 untrusted 时,连沙箱本来会静默放行的普通命令(比如跑一次构建)也要先弹窗点一次同意——安全边界与配 on-request 时完全相同,弹窗次数却多出数倍。

### 全放开档的唯一辩护(the only defensible full-access)

是什么:danger-full-access(全放开档,沙箱不设任何限制)配 never(永不弹窗审批)是一个"没有任何东西拦任何东西"的组合。它唯一可辩护的使用场景,是外层已有另一套沙箱兜底——例如一次性容器(跑完即销毁的隔离环境),或没有挂任何凭据(密钥、登录态)的 CI runner(持续集成流水线里执行任务的主机)。这是 codex 官方帮助文本给出的原话立场。
解决什么问题:给"什么时候可以全开"立一条可检验的判据,而不是凭胆量:这一层之下的机器丢了也无所谓吗?若答案是否,全开就不成立。
精读结论:评估或使用带 bypass(绕过)字样的旗标时,先看它要求的外层前提有没有被满足,再决定放行。
例子:`codex --dangerously-bypass-approvals-and-sandbox`(别名 --yolo)只应出现在"外层已是一次性容器、环境里没有任何云密钥"的机器上;在日常开发机上敲它,一次 prompt injection(往模型读到的内容里塞恶意指令、诱骗它替攻击者执行的攻击)就能直接落盘执行。

### 静默别名是配置债(silent alias)

是什么:静默别名是一种"旧值仍能加载、含义却已悄悄改变"的兼容处理。codex(OpenAI 出的终端编码 agent)已删除 on-failure(旧审批档,失败后才征询)这个取值。但老配置文件里写 `approval_policy = "on-failure"` 依然能正常加载:内部按一套别名规则把它映射成 on-request(现行默认档,沙箱内自由跑、想越界才问),全程不报错。
解决什么问题:它暴露一类评估陷阱:"能加载"不等于"语义没变"。用这种方式做兼容,过期配置不会提醒任何人,行为却已经不同。
精读结论:评估 agent 产品对已废弃配置取值的处理时,区分三种待遇——报错、警告、静默换义;只有报错才把"过期"传达给了人,静默换义最危险。
例子:同一行 `approval_policy = "on-failure"` 零报错跑起来,实际生效的却是 on-request;用户以为"失败后才打扰",实际"想越界就弹窗",而日志与界面上找不到任何差异提示。

### 无头模式砍掉审批旗标(headless drops -a)

是什么:codex exec 是 codex(OpenAI 出的终端编码 agent,用自然语言让它改代码、跑命令)的无头模式,即非交互执行入口。任务描述从参数或标准输入传入,进度走标准错误,最终答案走标准输出,专供脚本和流水线调用。它根本不提供审批旗标 `-a`/`--ask-for-approval`:该选项只长在交互式界面(TUI,人在终端里与 agent 对话的界面)的命令上,exec 内部把审批策略写死为 never(永不弹窗)。
解决什么问题:管道另一端没有人。假如 exec 允许配弹窗档位,agent 跑到一半打印 "Approve? [y/N]" 就永远等不到按键,CI(持续集成,无人值守自动跑脚本的流水线)会一直挂到超时。codex 的解法不是在文档里提醒"无头别配弹窗",而是让这个组合在命令行层面无法写出。消灭一类故障的正确方式是让组合无法表达,而不是文档提醒。
精读结论:自己设计 agent 的命令行接口时照抄这条:不可能的组合应该不可能表达。exec 的权限旋钮只剩 --sandbox 一个,配 never 后失败就是非零退出码,自动化天然能感知。
例子:`codex exec -a on-request "review 这个 PR"` 得到的不是弹窗,而是 `error: unexpected argument '-a' found`——错误在启动瞬间发生,而不是三小时后的超时。

### 弃用旗标的硬删与软删(hard vs soft deprecation)

是什么:废弃一个命令行旗标有两种做法:硬删是让它从合法参数表里消失,一敲就报错;软删是保留它但只打印弃用警告,并按替代品继续执行。codex(OpenAI 出的终端编码 agent)对旧的一键便利旗标 --full-auto 同时用了两种:交互式命令上是硬删,`codex --full-auto ...` 直接报错;无头入口 codex exec 上是软删,能跑,只打印弃用警告并映射到 --sandbox workspace-write 继续执行。
解决什么问题:两种待遇的选择取决于那条路径上跑着多少存量自动化:交互命令是人手敲的,报错成本只是重敲一次;exec 跑在大量既有 CI 脚本里,硬删会一夜打爆别人的流水线。软删给迁移期,硬删给终局。
精读结论:看到任何教程还在用 --full-auto,直接判定为过期资料;自己下线旗标时,按"这条路径上有多少无人维护的调用方"来选软硬。
例子:同一旗标两种输出——`codex --full-auto "..."` 返回 `error: unexpected argument '--full-auto' found`;`codex exec --full-auto "..."` 返回 `warning: '--full-auto' is deprecated; use '--sandbox workspace-write' instead.`,然后照常跑完。
