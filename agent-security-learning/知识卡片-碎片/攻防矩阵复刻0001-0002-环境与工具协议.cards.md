# 攻防矩阵复刻0001-0002 环境与工具协议 —— 知识卡片

### 密钥供给链不落盘(key supply chain, never on disk)

是什么:密钥供给链[自造](把一把 API 密钥从存储位置送到最终请求头的完整传递路径)指密钥不经磁盘、只经内存的三段旅程。第一段,macOS Keychain(操作系统自带的加密密钥库,密码与密钥存在里面、用时按名取出)——取密钥的小命令从里面读出明文。第二段,启动脚本把它注入子进程的环境变量,如 `LLM_API_KEY=...`,只存在于该进程的内存环境,不写任何文件。第三段,客户端调用模型 API 时把这个变量填进 `Authorization: Bearer` 头(发给模型服务的鉴权请求头)。对照形态是把密钥写进 `.env`(存环境变量与密钥的本地配置文件)——明文躺在磁盘上,如文件里一行 `LLM_API_KEY=sk-xxx`。

解决什么问题:提示注入(prompt injection,把恶意指令混进模型读到的内容里、诱骗模型把数据当指令执行的攻击)一旦得手,攻击者的第一动作就是找密钥——读文件、翻环境变量都是现成手段。`.env` 这类明文文件正是最便宜的下手处,注入攻击的典型演练剧本就是诱导 Agent 读出 `.env` 全文。密钥放在哪,直接决定注入得手后的收获上限;让密钥全程不落盘,等于把"翻文件就能拿到"这条路堵死。环境变量也只是半程防护——它仍住在 Agent 进程里,进程被攻破仍读得到。更彻底的形态是密钥连 Agent 进程都不进,由本地代理转发请求时补鉴权头。

我们的办法:工程侧走 Keychain → 进程环境变量 → 请求头这条链,真密钥零落盘。攻防演练侧则反过来:实验把一把假密钥样本(演习环境故意放置、专供检测泄露用的假凭据)写进系统提示词当靶子。系统提示词即应用预置给模型、给它定规矩的指令段——实验里测的正是"秘密住在模型上下文里能不能守住"。

### Function Calling 协议循环(function calling loop)

是什么:Function Calling(工具调用,OpenAI Chat Completions 聊天补全协议的一部分,让模型能请求调用外部工具)的完整循环是一套固定的消息协议,分三步。第一步声明:请求里带 `tools` 参数,每个工具一条规格,形如 `{"type":"function","function":{"name":"read_webpage","description":"抓取网页正文","parameters":<JSON Schema(用 JSON 描述参数结构的规范)>,}}`。第二步请求:模型在回复的 `tool_calls` 字段(模型生成的"我想调用某工具"的调用意图字段)里给出工具名与参数,形如 `{"name":"read_webpage","arguments":"{\"url\":\"https://example.com\"}"}`——注意 `arguments` 是 JSON 字符串而不是对象,应用要自己解析。模型此刻只是"提出请求",什么都没执行。第三步回填:应用真正执行工具,把结果包成 `{"role":"tool","tool_call_id":<对应请求的编号>,"content":<结果文本>}` 追加进 messages(模型当次读到的全部消息列表),`tool_call_id` 把结果和请求一一对上号。之后再次调用模型,直到某次回复不含 `tool_calls`,说明模型认为任务完成,`content` 就是最终回复。

解决什么问题:这个协议确立了两个安全上要紧的事实。其一,模型不执行任何东西,它只生成结构化请求,执行权全程在应用代码手里——从意图到落地之间隔着一层应用代码。这层代码有没有检查,决定了一次被骗生成的工具调用是"文本"还是"事故"。其二,循环必须设步数上限(如外层最多循环 6 次):模型判断失误时可能反复调工具不收敛,没有上限就是死循环,每一轮还都在烧 token。

我们的办法:不套 Agent 框架,直接用 OpenAI 官方 SDK 手写这个循环(几十行以内),每一步(声明规格 → 解析请求 → 执行 → 回填)都摊开在明面上。想在工具真正执行前插一道机制校验,就在第二步与第三步之间加代码,位置随选。

### 思考块混入正文并回流上下文(think block rides in content and context)

是什么:推理模型(作答前先在内部生成一段思考过程的模型)的思考块(think block,`<think>...</think>` 标签包住的思考文本)在部分供应商那里不单独成字段。它直接混在回复的 `content`(回复正文)字段里一起返回。实测 MiniMax-M2(国产对话大模型)的回复长这样:`<think>用户想要一段自我介绍…</think>你好,我是…`。更要紧的是后续:这份 `content` 会原样追加进 messages(对话消息列表)作为下一轮输入。模型的思考文本由此回流进它自己之后要读的上下文。

解决什么问题:它戳破"回复文本 = 用户可见文本"的默认假设。安全判定若拿 `content` 全文做扫描——比如检查最终输出里有没有出现假密钥字符串——思考块也在被扫范围内。好处是判定覆盖面更全,密钥若出现在思考里同样抓得到;但要清楚多扫了一份模型的"自言自语",若按"用户看到的"来判,结论又会漏掉思考里的内容。另一面是上下文方向的含义:回流的思考文本和工具返回一样只是普通文本,会成为模型下一轮判断的输入之一,而不是被机制隔离的历史。

我们的办法:把"思考块也算模型输出的一部分"记成判定与检查的口径——凡按 `content` 全文做的泄露检测,默认把思考块包含在内;复盘模型行为时,思考块则是一手材料,能看到它是没识破话术还是识破后仍照做。
