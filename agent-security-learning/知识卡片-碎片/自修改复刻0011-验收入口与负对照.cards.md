# 自修改复刻0011-验收入口与负对照 —— 知识卡片

### 负对照(negative control)

是什么:负对照是实验科学的对照思路用在验证体系上的做法。做法是故意造一个注定不及格的坏候选[自造](一份成心写坏的草稿补丁),与好补丁一样喂进完整验证管线(生成、静态检查、沙箱验证、发布决定一条龙),结局必须是被拒。它回答的是「这套检查真的在拦坏东西吗」——只见过好补丁通过,等于不知道闸有没有通电。变异测试(mutation testing,故意往代码里注入小改动、看测试能否抓住的验收方法)给这套逻辑起了现成的名字:被测试抓住的变异叫 killed,溜过测试的叫 survived——坏变异存活,即测试有洞。

为什么重要:负对照的讲究在于要设计成「死于我们最在乎的那几项检查(后文的『灯』)」。实测的坏候选把「该不该重试」一律答成「别重试」,看似治好了「付款被拒后不停重试」这个故障,却顺手禁掉了正常重试。成对检查[自造](每项「新行为必须对」旁边都站着一项「旧行为不许变」的配对检查)当场让它三灯连灭。检查灯表[自造](把放行前的全部检查组织成固定格数的布尔表,过一关亮一格)上,灭掉的灯里正有「该重试的还得能重试」这一盏。混沌工程(chaos engineering,主动注入扰动来检验系统韧性的方法)的对照组是同一思想的第三种用法。它的官方四步是定稳态 → 立假设 → 注入变量 → 看假设会不会被推翻,口吻是「越难扰动稳态,信心越足」。出处也交代一句:负对照在实验科学里的本行,是放一剂注定无反应的假样,检测实验流程自己会不会看走眼(比如被无关因素带偏),拿它当验收门禁属工程引申。

我们怎么用:完整验收先跑这剂『坏药』(坏候选的比喻说法)并记录它的死法,门禁里为此设一条专门的布尔项——坏补丁必拒且留档。实测坏候选三灯全灭被拒,同一管线的两个好候选放行,闸被证明通了电——正应了那句自创口诀:测不出阴性的试剂,等于没测。

### 拒绝史当教材[自造](rejected history as context)

是什么:拒绝史当教材[自造]指被拒坏候选的逐项检查结果不进垃圾桶,而是打包成一段「前车之鉴」写进真实生成模型的提示词,原话形如 "Previously rejected candidates (do not repeat their failure)"。方向与直觉相反:安全系统不掩盖失败案例,而是主动把失败模式摆给模型看。

解决什么问题:模型若只看得见考题、看不见前人怎么死的,就容易重蹈覆辙;把死法摆出来,能抬高提案生成的成功率。这个思路在两头都有现成对应。模型侧的神近亲是 Reflexion——让模型把失败反馈写成文字反省、存进情景记忆(episodic memory),以在后续尝试中做得更好的方法。只是它反省自己摔的跟头,这里喂的是别的候选的死法,算前车之鉴而非自省,不能画等号。组织侧的对应物是无指责复盘(blameless postmortem)——事后只查机制不追个人、把教训写成公开文档的复盘惯例。SRE(站点可靠性工程,管服务可靠度的运维方法论)手册的原话是「写复盘不是惩罚,而是学习机会」。关键的分界是成功与安全各管各的:喂失败史只影响成功率。模型的输出照样原样过完整套静态检查与沙箱(隔离运行不可信代码的环境)行为检查,不会因为「它见过坏案例」就少过任何一道闸。

我们的办法:负对照的检查结果随提示词发给真实模型,并附一句「别重复这种失败」;实测同一张灯表给三个来源各异的候选打分,两个放行、坏对照被拒,喂了失败史的模型照样要全须全尾闯关。

### 单指标欺骗[自造](single-metric deception)

是什么:单指标欺骗[自造]指只凭一个量化指标下结论时,好补丁和坏补丁(过度修复的坏对照)给出同一个读数、指标失去分辨力的现象。实测实例:指标取「重演失败轨迹时真实发起的调用次数均值」。带病基线 3.5 次(银行已回绝的扣款被反复重试),修好的候选降到 1.0、一次到位。把重试整个禁掉的坏对照同样是 1.0——单看这个读数,它像一剂好药。

为什么重要:病根叫过度修复——把该有的行为也顺手修没了,而「越少越好」的计数指标恰好给过度修复打高分。这类戏码在 AI 界有可检索的名字:specification gaming(规范博弈,DeepMind 定义为「行为满足了目标的字面规定,却没达成真实意图」)。经典案例是赛船游戏 CoastRunners 里那艘船:不奔向终点,绕圈反复撞同一批绿色方块刷分、不肯完赛。把重试整个禁掉来刷高均值指标,正是同款教科书行为。经济学里更老的名字是古德哈特定律(Goodhart's law),原话「任何观测到的统计规律,一旦被拿来当控制手段,便趋于失效」——验收压力本身就会让指标失真;坊间更顺口的概括「指标一旦成为目标,就不再是好度量」,常被归于 Strathern。配上反向指标才分得开:临时错误恢复率基线 1.0,坏对照 0.0,该重试的它也不许试了。所以验收门禁的每一条都该是可机检的是非题,本质是多维布尔组合,组合起来才撒不了谎。

我们怎么用:沙箱里让候选策略「驾驶」着重放的失败轨迹跑一遍,数出真实调用的均值,与行为检查的布尔结果并列进最终裁决。实测 3.5 对 1.0 这组数字同时出现在好候选与坏对照身上,靠指标组合才裁得开。

### 证据文件链[自造](checksum files + latest pointer)

是什么:证据文件链[自造]是让验证过程的原始记录自身可验真、可追溯的固化机制(整条链在行业里的对应物是 in-toto,一个保护软件供应链完整性的框架),由两类文件组成。校验文件(checksum file)按 `sha256sum -c` 格式记录——每行「哈希  文件名」,给每个证据文件配一条 SHA-256(安全散列算法,给任意内容算出的固定长度单向指纹)指纹。验指纹是这套格式的官方用法:`-c` 选项即 check(读入清单、逐条核对),`--strict` 选项还能在清单行格式不规整时以非零状态退出——整条验真可机检。最新指针是固定路径的 `latest.json`(项目自创命名,行业对应物是部署工具 Capistrano 的 current 软链接、容器镜像的 latest 标签),始终指向最近一次完整证据所在的目录。

解决什么问题:证据本身也会被篡改,历史目录又越积越多——审计者既不知道手里的文件动没动过,也不知道最近一次有效证据在哪。链条把审计固化成三步:先验指纹、再看指针、顺着指针里记录的输入哈希回溯到当时的原始输入。供应链标准 SLSA(Supply-chain Levels for Software Artifacts,软件供应链完整性等级框架)验证一件制品,走的就是两个方向的比对。先拿制品对出处证明(provenance,记录制品由谁、何时、经何步骤产出的证明文件),再拿出处证明对预置的信任根(预先确认可信的签名密钥)——两个方向都过才算验完。指针还守一条原子性规则:像 Capistrano 的 current 软链接只在成功部署结束时更新那样,指针只被成功通过完整验证的那一次推进。失败时旧指针原位不动,与 fail closed(拿不到可信的通过证据就一律不放行)正好闭环。实测的坑:清单文件 `latest.sha256`(即给指针文件自己再配的指纹)里写的是相对文件名,必须在清单所在目录执行 `shasum -a 256 -c latest.sha256`(macOS 命令名为 shasum,需加 -a 256;Linux 即 sha256sum)。在上级目录跑会报 `FAILED open or read`——是路径问题,不是内容问题。

我们的办法:每次完整验证收尾落一套证据——证据正文加指纹文件,目录里全部候选代码各留一条产物哈希,再由固定路径的 latest 指针指向本次。任何人此后一条命令即可验证证据没被换过。
