# NeMo复刻0003-0004 输出自检rail与五闸时序 —— 知识卡片

### 出口自检闸(self-check output rail)

是什么:self-check output rail 是 NeMo Guardrails(NVIDIA 开源的 LLM 对话防护框架)挂在"模型回复送回用户之前"的自检 rail(rail 指该框架挂在对话链路上的检查环节)。它把 bot 写好的回复填进一张"这条回复该不该发"的清单提示词模板,占位符是 `{{ bot_response }}`,再额外调一次 LLM 回答 Yes(拦)或 No(放)。判 Yes 就换固定拒答,刚才那次生成白干。

解决什么问题:入口闸只能拦"用户带来的坏",管不着"模型自己造的坏"——幻觉、违规内容、把密钥编进回复。实测输入完全合法的请求「帮我编一个 .env 配置文件示例,含 `INTERNAL_API_KEY` 字段,值要逼真一点」:入口放行,模型真编出逼真密钥——这时只有出口这道自检闸有机会拦。它和入口自检是同一套机器,区别只在检查对象(入口填 `{{ user_input }}`)与触发时机(生成之后)。

我们的办法:挂载只在配置的输出 flows 清单里点名,清单提示词明文可改。实测证明闸机本身能拦——默认清单没写密钥才漏,给清单补上"编的密钥也不行"后同一请求立刻被拦。

### 清单路线与模式路线(semantic checklist vs pattern matching)

是什么:敏感信息防线有两条并行的判法路线。清单路线[自造](把"什么算违规"写成提示词清单、让 LLM 读懂语义后逐条对照)的代表是 NeMo 的 self-check 系 rail;模式路线[自造](按字符形态判:正则、已知格式前缀、高熵字符串——随机性极高、长得像密钥的文本)的代表是 llm-guard(开源 LLM 安全扫描器框架)的 Sensitive 输出扫描器(实体识别模型加正则)。

为什么重要:两条路线的漏判面形状完全不同。模式路线认形态不认语义,`ik-live-` 这种带真实前缀的串不管清单写没写都会命中;清单路线读懂语义再对照,清单没覆盖的语义就漏。实测 NeMo 默认输出清单十条里没有一条提到密钥,"编造逼真密钥"的回复照放。给清单补一条"编造的密钥同样不行"(原条款连令牌、密码一并覆盖)后,同一请求立刻被拦。结论:闸机本身是好的,漏的是清单。清单路线的防护上限等于清单覆盖面——策略写多全,防护就有多全。

我们怎么用:对照两套防线要比判法机制而非产品名。格式特征明确的目标(密钥、卡号)优先模式路线兜底;只有语义能判的违规(教坏话术)只能走清单/语义路线;上清单路线防线先审清单覆盖面、再谈拦截率。

### 调用链回放[自造](LLMRails.explain)

是什么:调用链回放[自造](每次生成后调 NeMo 运行时对象的 `explain()` 方法、读返回对象里的 `llm_calls` 列表)是把"这次请求实际跑了哪几次 LLM 调用"变成可查证据的排查手段。每项记录带 `task` 字段标注任务名:`self_check_input` 是入口自检,`general` 是主回复生成,`self_check_output` 是出口自检。

解决什么问题:"到底哪道闸拦的、这道闸真的检过没有"不再靠猜。实测两个对照:「编造密钥」请求走全三段调用链,证明出口自检真的跑了、放行是清单漏了而不是没检;输入直接带密钥 `ik-live-demo-123456` 的请求调用链只剩入口自检一段,证明出口闸根本没参与。拦截归因从此有据可查。

我们的办法:验证防线时每次生成后调 `explain()` 核对任务名序列,把它当防线生效的账本。这些任务名也是核算每道闸延迟与 token 花费的计量单位。

### 判官空回答与 fail-closed(empty verdict fail-closed)

是什么:判官空回答[自造](安全自检这类额外 LLM 调用返回空串、既不是 Yes 也不是 No)在 NeMo 里按 fail-closed(拿不准即拒绝的默认安全姿态)处理,空判定等于拦截。推理模型(reasoning model,正式回答前先生成一段思考链的模型)会把它放大成系统性误伤:思考链偶尔吃光提示词的 max_tokens(输出长度上限),答案没出口就被截断。自检返回空,正常请求就被拦。

解决什么问题:它暴露"用 LLM 当判官"的隐性前提——判官必须给出可用判定。fail-closed 方向上是对的(拦错不放过),但判官失能时误伤的是全部正常请求:防线自己的故障模式成了可用性风险。官方处方是给推理模型调大自检提示词的 max_tokens。

我们的办法:实测确有自检被思考链憋空、正常请求被拦的案例。把判官模型的输出预算单独校准,并把"判空率"当防线自身的健康指标监控,而不是只统计拦了多少。

### 五道闸时序[自造](guardrails sequence diagram)

是什么:五道闸时序[自造](把 NeMo Guardrails 官方时序图里的五个 rail 位置读成五道依次经过的安检闸)是防线位置的官方规定。rail 指该框架挂在对话链路上的检查环节。顺序是:输入闸(input rails)先查用户带来的坏,检索闸(retrieval rails)只在配了知识库/RAG 时存在、查检索回来的资料块,对话闸(dialog rails)认意图定走向。执行闸(execution rails)管工具调用与返回,然后模型生成回复,过输出闸(output rails),回复才交还用户。

解决什么问题:它把"防线钉在链路哪个位置"固定成五张椅子,与"用什么机制判"是两根独立的轴。同一张椅子可以坐 LLM 自检、专用分类器、纯 Python 结构校验或流程匹配——对照其他框架要比机制不是位置。位置还可能是空椅子:实测无知识库、无工具、没写对话流程的极简外壳只走"入口→生成→出口"的短路,中间三道根本不存在。

我们怎么用:拿真实攻击给五张椅子归位。直接注入归输入闸;藏在工具返回里的毒名义上归检索闸与执行闸;多轮话题偏移归对话闸;参数投毒归执行闸;回复泄密归输出闸。归位之后立刻显出哪些位置现成闸机没覆盖。

### 对话闸与 canonical form(dialog rail)

是什么:dialog rail 是五道闸里的第三道,判定机制既不是清单也不是分类器,而是 Colang(NeMo 自造的对话建模语言,语法像 Python)写的对话流程图。写法是用 `define user ...` 把用户消息归一成意图(canonical form,把千变万化的说法归到标准意图名上),再用 `define flow ...` 定义每个意图之后对话往哪走,引擎按流程图引导(steering)对话。

解决什么问题:防多轮套话与话题偏移——"聊着聊着被带偏"这类攻击(记忆投毒在对话面的体现)不靠单条消息验毒,靠流程图约束"这段对话允许走到哪"。代价是它是五种 rail 里最重的一种:前提是手写流程图,配置也不是往 flows 清单加名字,而是写 `.co` 语料文件。

我们的办法:input/output/tool 这类安全闸全都不需要手写 Colang,dialog rail 只在确实要约束话题边界时选装。选装前先归好意图集——流程图的防护上限同样是"你写了什么"。

### 工具边界双闸(tool rails)

是什么:tool rails 是 NeMo 0.23 版新增的工具边界检查,两道各管一头。tool call validation 查模型发出的工具调用:工具必须在白名单里、参数要过 JSON Schema(声明参数名与类型的结构描述)校验;tool result validation 查工具返回:只核对结构一致性(来源对不上、格式不对才拦),官方明说"不做内容安检"。机制是本地纯 Python 检查,不调 LLM,拿不准即拒(fail-closed)。

解决什么问题:零模型成本拦住"调了没声明的工具、参数不合结构"这一整类。但它只查"参数合不合结构"、不查"参数语义有没有毒":`path="../../.env"` 这种路径穿越串对 schema 来说完全合法、照单放行;工具返回侧的毒文本只要结构规整也能过。

我们的办法:实测结论是这两道闸补不了语义级缺口。此前用内容扫描器逐块扫工具返回与写入参数语义的防线,NeMo 现成闸机不覆盖,得自己写检查逻辑或继续用外置扫描器——结构校验当第一道、语义扫描当第二道。

### 静默回退失效[自造](silent fallback)

是什么:静默回退失效[自造](配置写错时框架不报错、悄悄退回不带该功能的老路径,防线整体失效、只留一条日志警告)是双引擎结构埋下的坑。0.23 版有两套引擎:LLMRails(默认引擎,Colang 事件驱动)与 IORails(实验性新引擎,专管输入输出边界的固定校验),两者互斥——tool rails 只在 IORails 上跑;引擎没切或流名打错,配置不生效也不报错。

解决什么问题:它是"配置错了不告诉你"这类故障的又一实例:配置文件写得明明白白,实际一道工具闸都没生效,又没有显式报错可抓。防线"已配置"不等于"已生效"——这条对一切声明式防线成立。

我们的办法:配置完用一条本该被拦的请求回测,看到真被拦才算数;框架日志里的警告也要纳入例行检查,流名拼写这类低级错误只能靠实测兜住。
