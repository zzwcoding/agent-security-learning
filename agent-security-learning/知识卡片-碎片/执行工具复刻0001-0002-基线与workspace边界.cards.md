# 执行工具复刻0001-0002 基线与workspace边界 —— 知识卡片

### git archive 子树提取(git archive subtree extraction)

是什么:这是一种从历史提交里抠出子目录干净副本的 Git 手法。`git archive` 是 Git 内建命令,把某个历史 commit(提交快照)里指定范围的文件打包成 tar 流输出到标准输出,本身不改工作区、不碰暂存区(index,Git 里登记"下次提交要带哪些文件"的地方);配合 `tar -x --strip-components=N`(解包时剥掉 N 层目录前缀),就能从历史里抠出一个子目录的干净文件副本。

为什么重要:对照更常见的 `git checkout <commit> -- <path>`:后者会把历史文件塞进当前暂存区,和手头未提交的改动搅在一起;`git archive` 拿到的是与当前 Git 状态完全无关的纯副本,连提交历史都不带。要复刻一个外部项目的"最终形态代码"时,需要的正是这种纯副本——顺带的安全收益是,提交历史里后来才删掉的敏感文件不会跟着进来。

我们怎么用:一条管道在提取时就做完三件事:`git archive <commit> <子目录> | tar -x --strip-components=3 --exclude='*.env' -C 目标目录`。`--strip-components=3` 剥掉三层目录前缀,让文件直接落进目标目录;`--exclude='*.env'` 在提取那一刻就排除环境变量文件(通常存放 API 密钥),密钥从头就不进新目录——拷贝代码和拷贝密钥在源头上分开。

### 先归一化再判归属(resolve then relative_to)

是什么:先归一化再判归属[自造](经验总结写法,非标准术语)是用 Python 标准库 pathlib 的 `Path.relative_to` 方法做路径边界检查的固定两步。第一步 `resolve()` 把用户给的路径换算成真实地址,顺带解析掉 `..` 这类绕路写法和符号链接。第二步 `relative_to(参照目录)` 回答"这个路径在参照目录里面吗":在,正常返回;不在,抛 ValueError。一行代码即 `(工作区目录 / path).resolve().relative_to(工作区目录.resolve())`。

解决什么问题:路径检查最容易栽在"比文字"而不是"比路径"上。老写法用 `startswith`(Python 字符串方法,判断是否以某段文字开头)做前缀比较:`/workspace-evil/x.txt` 的开头确实是 `/workspace`,前缀比较直接放行。好比门卫只核对"地址是不是以幸福小区开头","幸福小区北街8号"也能混进去,可那根本不是这个小区;`relative_to` 比的是路径一级一级的组成,假前缀骗不了它。另一个坑是拿原始字符串直接判断:`../escape.txt` 里的 `..` 表示"往上一级",不换算就看不出真实落点,符号链接同样能把落点藏起来。先 `resolve()` 归一化,绕路写法才现形。

我们的办法:写文件工具在真正落笔前执行上面那两步,越界立即拒。实测一次故意捣乱的写请求 `../escape.txt`:resolve 一换算就露馅——落点在工作区之外,检查直接拒掉,磁盘从头到尾没被碰一下,任何位置都没有多出这个文件。

### 信任边界=进程边界,闸写在执行侧(trust boundary = process boundary)

是什么:信任边界(trust boundary,安全设计里"可信一侧"与"不可信一侧"的分界线)在这套 Agent 架构里落在进程边界上。每个工具 server(真正执行命令、写文件的服务进程)都是独立子进程,不 import 客户端任何代码。于是模型与客户端一侧即使被攻破,另一侧进程的代码也原封不动。

为什么重要:它决定安全闸[自造](挡在工具执行路径上、由代码强制执行的检查点)应该写在哪一侧。闸若写在模型那一侧(提示词里叮嘱"别执行危险命令"、客户端代码里做检查),模型一旦被提示注入(prompt injection,诱骗模型把读到的恶意内容当指令执行的攻击)攻破,叮嘱会被说服绕开。闸写在 server 进程内部就不同了:裁决根本不经过模型,攻击者从模型那边最多拿到"发起一次调用"的机会,执行与否由它够不到的另一侧进程说了算。

我们怎么用:
- 起点是零检查的旧工具:命令收到就用 shell 直接跑、写文件只有弱路径校验;把闸逐个写进 server 内部。
- 用同一批攻击提示做对照验收:无闸版本上得手、装闸后失败,对比才成立。
- 例子:模型被诱导生成的"删除整个目录"调用只是一段 JSON(一种键值对文本数据格式)意图,server 内部的检查会在派发那一刻拒掉它——模型说服不了闸,闸不在它能说话的地方。

### 软拒绝纸条[自造](structured denial return)

是什么:软拒绝纸条[自造](指工具拒绝执行时不抛异常、不让程序崩溃,而是返回结构化"纸条"的做法——因形如递给调用方的一张纸条而得名)是面向 AI 调用者的拒绝返回约定。纸条是一段 JSON(一种键值对形式的文本数据格式),形如 `{"success": false, "error": "路径越界: ../escape.txt(只允许写 workspace/ 内)"}`。success 标成败,error 写原因。

解决什么问题:工具拒绝的读者往往不是人,而是 AI——它拿到结果后还要继续推理。两种坏写法:抛异常让整轮程序崩掉,AI 失去继续工作的能力,用户只看到一串报错堆栈;只返回笼统的 "failed",AI 不知道哪里错了、无从修正。一张写清原因的纸条让它读得懂"为什么不行",才能向用户解释,或者自己换个方案(比如把文件改写到允许的目录里重试)。

我们的办法:拒绝信息写两件事——违规事实加允许范围,让"下一步该怎么办"能直接从错误信息里推出来;实测越界写请求被拒时,error 同时说明"路径越界"与"只允许写 workspace/ 内",磁盘从头到尾没被碰。预料之中的拒绝应主动写成这种可读结果,而不是依赖框架异常兜底。

### 换壳不换芯[自造](tool core, swappable entry)

是什么:换壳不换芯[自造](指工具代码与它的调用入口刻意解耦的设计纪律,借"换外壳、不换机芯"的说法得名)要求工具本体不依赖任何特定入口。工具本体指执行逻辑连同内嵌的安全检查,可被不同入口原样复用。最小形态是三件套:命令行入口只负责读懂用户敲的参数、递给工具本体、把结果打印成 JSON(一种键值对形式的文本数据格式),工具本体自带全部检查。新入口——比如把同一份工具包成 MCP server(把工具暴露给 Agent 的标准协议服务进程)——直接复用同一份工具代码。

为什么重要:安全检查的落位跟着这个设计走。检查若写在入口层——比如只在命令行程序里校验路径——之后换一个入口(如 Agent 经 MCP 调用同一个工具),检查就留在旧入口里没跟过来,新链路等于不经任何检查直通工具;检查内嵌在工具本体里,任何新入口接上即自带防线,接入方式变多也不会稀释防护。

我们怎么用:先拿命令行当第一个用户验证工具本体,之后接 Agent 入口时零改动复用同一份工具;自检办法是只从新入口打一次越界请求(如 `../escape.txt`),确认同样被拒——入口换了、检查还在,才算复用成功。
