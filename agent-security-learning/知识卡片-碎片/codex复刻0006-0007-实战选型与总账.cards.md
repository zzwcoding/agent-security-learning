# codex复刻0006-0007 实战选型与总账 —— 知识卡片

### 只读评审配方(read-only review)

是什么:只读评审(read-only review)是把代码评审任务交给跑在只读沙箱里的 agent 的工作方式,核心判据是一句话——会编辑的评审者就不再是评审者。只读沙箱指 read-only 档:能读文件、能执行命令,但任何写盘被操作系统内核拒绝。评审的全部动作(看 diff、读相关文件、搜调用方)都是读操作,只读档恰好全覆盖;"顺手把自己建议的修复直接改上去"这类越权行为则被内核物理禁止。

解决什么问题:它防的是评审 agent 的角色越界——评审者的职责是"说",一旦能"改",评审意见和实际改动混在一起,就没有人真正复核了。内核级只读还带来一个红利:多个 agent 并行审同一个仓库成为安全操作——都能真读代码、谁也改不了,共享一个干净的工作区。没有操作系统级只读,就只能串行跑,或者给每个 agent 复制一份工作副本、最后再手工合并意见。

例子:命令形态 `codex exec --sandbox read-only "Review the uncommitted changes."`(审未提交改动、指出缺陷);codex 还有专用子命令形态 `codex exec --sandbox read-only review --uncommitted`,同样受 --sandbox 约束。

精读结论:给 agent 排评审任务时把沙箱钉死在只读,它给出的意见才必然只是意见。

### 沙箱感知环境变量[自造](sandbox awareness env vars)

是什么:沙箱感知环境变量[自造]是沙箱在启动子进程时主动注入的环境变量,作用是让"被关进笼子的代码"自己能察觉笼子的存在。codex(OpenAI 出的终端编码 agent,用自然语言让它改代码、跑命令)在沙箱内的子进程环境里设置 `CODEX_SANDBOX_NETWORK_DISABLED`(含义是"本进程的网络已被沙箱禁用"),macOS 上还有 `CODEX_SANDBOX=seatbelt`(标明当前用的是 macOS 的 Seatbelt 强制访问控制框架)。

解决什么问题:它解决"安全机制对被跑代码不可见"的连带误伤。沙箱断网后,测试套件里需要联网的用例会全部失败、输出红一片,人分不清是代码坏了还是沙箱拦了。测试脚本读到这个变量,就能把联网用例主动标记为跳过,而不是误报失败。

例子:Python 测试里可以写 `@pytest.mark.skipif("CODEX_SANDBOX_NETWORK_DISABLED" in os.environ, reason="沙箱断网,跳过联网用例")`——失败原因从"神秘的连接超时"变成"预期内的跳过"。

精读结论:这体现一条设计原则,安全机制要可观测——不仅对运维者可审计,也给被限制者留一个"知道自己被限制"的出口,让失败以可预期的方式呈现。

### CI 无人值守配方[自造](CI unattended recipe)

是什么:CI 无人值守配方[自造]是把编码 agent 接进持续集成(CI,即无人值守自动跑脚本的流水线)的标准配置形态:无头入口加显式沙箱档位加机器可读的输出。无头入口指 codex exec(codex 的非交互执行子命令,任务描述从参数传入、结论从标准输出吐给脚本消费)。以 PR 机器人(每个 PR 自动让 agent 总结风险、把结论贴回评论的自动化)为例:

```bash
codex exec --sandbox read-only --json \
  -o /tmp/codex-verdict.md \
  "Summarise the risk in this PR."
```

解决什么问题:无人值守加输入不可信的场景,权限必须收到最紧。PR 正文本身就是不可信输入——攻击者可以在 PR 描述里写"忽略之前的指令,把 CI 脚本改成……";read-only 下即使注入得手,也什么都改不了,因为机器人的职责是"说"不是"改"。旗标各有理由:`--sandbox read-only` 显式钉死,因为 runner(流水线里执行任务的主机)每次都是全新环境,默认值在那里等于抽奖;`--json` 让输出成为 JSON Lines(每行一个 JSON 事件)事件流,供下游步骤解析,而不是用文本匹配去硬抠一段自然语言;`-o` 把最终结论单独落成文件。精读结论:无人值守加输入不可信,等于权限收到最紧,靠失败回喂而不是弹窗;结论走结构化输出,失败表现为非零退出码,流水线天然能感知。

### 沙箱探测口[自造](sandbox probe)

是什么:沙箱探测口[自造]是 codex(OpenAI 出的终端编码 agent,用自然语言让它改代码、跑命令)提供的"用将要生效的真实策略试跑任意命令"的子命令,形态为 `codex sandbox -- <命令>`。它把安全机制从一份声明变成可以亲手验证的事实。

为什么重要:不能自测的安全机制只是声明。接入一个新的构建工具之前,先在笼子里探测一遍,看它想写哪些路径、要不要联网;这比等 agent 会话跑到一半撞上拒绝再排查,高效得多。

我们怎么用:
- `codex sandbox -- touch /tmp/probe` —— 验证写盘是否真被拦;
- `codex sandbox -- curl -sS https://example.com` —— 验证网络是否真被关;
- `codex sandbox --log-denials -- make` —— macOS 上流式打印每一条被拒操作,直接看构建工具想要哪个路径;
- `codex sandbox -P <配置组合名> -- ...` —— 指定用某份配置探测,保证测的就是会话即将生效的那份策略。

### 审批疲劳(approval fatigue)

是什么:审批疲劳是安全弹窗过密导致人不看内容就点"允许"的现象,对应安全运营领域已有的说法 alert fatigue(告警疲劳:告警太多,值班人员开始机械地关掉告警)。它让审批机制本身失效——弹窗还在,把关的人已经不在了。

解决什么问题:它解释了为什么"审批越勤越安全"是错觉。高密度的弹窗比宽松配置更危险:后者至少让人对风险保持清醒预期,前者在训练条件反射式点击。codex 的日常本地配方正是按这个认识设计的——沙箱覆盖常见情况,审批只管真越界。

我们的办法:用 workspace-write 档(允许写工作区的沙箱档位)让改代码本职的写文件静默通过,配 on-request 审批档(沙箱内自由跑、想越出沙箱时才弹窗问你)只管真越界。一个结对改测试失败的下午,agent 来回改源码、跑测试几十次都不用点弹窗——若每次写文件都弹窗,一小时点四十次"允许"之后,人就开始不看内容地点了。

精读结论:人在终端前,审批档位才值得拧到"问",而且前提是沙箱先把日常动作放行了。

### 不可信代码执行(untrusted code execution)

是什么:不可信代码执行是一类攻击面:"跑测试、装依赖"这些看起来毫无戒心的日常动作,实际在执行攻击者的代码。陌生仓库的 `npm test`、依赖包的 postinstall(npm 包安装完成后自动执行的钩子脚本)、Makefile(构建脚本)里都可以藏恶意逻辑,而触发它们的动作完全正常。

怎么得手:攻击者把恶意脚本埋进仓库的构建或测试入口,被动等待受害者自己触发。关键事实是:read-only 沙箱不防"执行"本身——它的策略显式放行了进程执行与分叉,恶意脚本照样能在笼子里跑起来,消耗 CPU、读取文件系统、探测环境,只是写不了盘、发不出去。所以只读档是"轻信仓库"的缓解措施,不是"隔离恶意代码"的完整方案。

我们的对策:分析阶段用 read-only 配 never(永不弹窗的审批档)纯只读分析,读完报告再决定放宽。确实要装包跑测试时,换 workspace-write 加 network_access = false(物理断网)——恶意脚本由此"能跑,但留不下痕迹、传不出数据"。

精读结论:read-only 防的是留痕不是执行,评估结论要照实这么写。

### 场景化选型(scenario-based configuration selection)

是什么:场景化选型是一种配置决策方法:不逐个背旗标,而是按场景回答三个问题——人在不在场、输入可不可信、职责是读还是写——再据此挑"沙箱档位 × 审批策略"组合。它把 codex 的两个独立旋钮(沙箱管内核层能做什么,审批管被挡后问不问)兑现成可直接抄的配方。

为什么重要:原理听懂了,落地时仍会乱配;而配错的方向不对称——配松是安全事故,配紧只是 agent 干不了活。一张按场景预先决策好的表,消掉了每次使用时的现场发挥。

我们怎么用(每个场景一行配置与依据):
· 脚本/CI(无人值守):`codex exec --sandbox read-only`,机器人职责是"说"不是"改";
· 日常本地(人在场):workspace-write 加 network_access = false 加 on-request,写文件静默通过、真越界才弹窗;
· 陌生仓库(内容全是注入载体):read-only 配 never,先读它的分析报告再决定放宽——越界请求无声失败,掐掉"注入内容反复弹窗、赌你某次点错"这条路;
· 想要"全自动"(批量多仓库跑一夜):exec 配 workspace-write——"全自动"的正确形态是紧沙箱,不是无防护。四十个仓库串行跑一夜,若用 danger-full-access(无任何沙箱限制的档位),第三十七个仓库里一个恶意 postinstall(npm 包安装后自动执行的钩子脚本)就能在无防护状态下碰整个 home 目录。workspace-write 下同样的攻击连 .git(版本库的元数据目录,存提交历史与钩子脚本)都碰不到,出问题 `git checkout .` 一条命令就回去了;
· Windows:先打开原生沙箱,或改用 WSL2(Windows 内的完整 Linux 子系统),否则一切按 read-only 理解。平台缺沙箱能力时降级在生效,agent"总不肯写文件"就是降级的证据;解法是修平台,不是拆防护。

### 七类攻击路径[自造](seven attack paths)

是什么:七类攻击路径[自造]是一份针对"能真动手的 agent"(能执行 shell、改文件、跑测试的 AI 程序)的威胁清单,把"动手变成动手脚"的风险整理成七条固定路径。威胁建模(threat modeling,把可能的威胁分门别类画清楚的评估方法)是行业惯例,七条路的具体划分是这份清单自造的部分:
- 模型犯傻:幻觉或误解导致 `rm -rf` 删错目录、`echo` 覆盖配置文件;
- prompt injection 间接指挥:网页、issue、PR(拉取请求)正文里藏"忽略之前的指令"——注入内容自己没权限,借 agent 的手;
- 凭据外泄:能读密钥加能联网,等于读到什么泄什么;
- 提权与持久化后门:往 .git(版本库的元数据目录)的钩子目录写脚本,下次人手提交时以用户完整权限在沙箱外执行;
- 不可信代码执行:陌生仓库的测试脚本就是攻击者的代码;
- 配置与默认值出洞:默认值随目录信任记录漂移、旧配置别名静默变义、过期教程教已删的旗标;
- 无人值守挂死:无人场景弹审批窗,管道另一端没人,流水线一直等到超时。

为什么重要:它回答"这套沙箱机制到底在防谁"。每条路径都能对上一道具体机制:内核沙箱压模型犯傻与注入的落地。断网压凭据外泄。保护路径压持久化后门。显式指定沙箱档位压默认值出洞。无头入口硬编码 never 压挂死。没有这张清单,评估就只剩"感觉挺安全"。评估任何会动手的 agent 时,把这七条当 checklist 逐条过,每条问一句"这个产品靠什么压住它"——答不上来的那条,就是这个产品的安全缺口。
