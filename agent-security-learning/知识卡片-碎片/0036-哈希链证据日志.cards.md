# 0036 哈希链证据日志 —— 知识卡片

### 哈希链（hash chain）

是什么：哈希链是一条前后咬合的日志记录序列：每条记录的哈希由「前一条的哈希拼上本条内容」共同算出。哈希（hash）指内容摘要——内容改一个字，摘要就完全不同。证书透明日志标准（RFC 6962）把这类日志定义为 append-only（只许追加）的 Merkle Tree（把记录两两配对求哈希、逐层收拢成一个根哈希的树状结构），并强调「只增不减」——追加是定义的一部分。本项目用 sha256（一种常用的密码学摘要算法）计算，公式形如 `entry_hash = sha256(prev_hash + canonical_json)`，其中 canonical_json 指规范化 JSON（序列化前把字段按固定次序排好，同一内容永远得到同一段输入字节）。

解决什么问题：逐条独立打指纹的日志有个缺口——改一条记录，只需把那一条的指纹同步改对。哈希链把全部记录锁成一体：改、删、重排任何一条，它后面所有的哈希全都对不上，「有人动过记录吗」从此是机器可判定的检查。它回答的是法庭式问题：「这件事发生过，且记录没被改过。」边界要诚实：链不拦住动手的人，只保证动手必被发现。验证手段也有轻重：重算全链是朴素的一致性检查，工业级的 consistency proof（一致性证明：只出示少量中间哈希即可向第三方证明「日志只增未改」）不必重算整条。防抵赖的下一级是签名回执，由生成方用只有自己持有的私钥给每条记录签名（如 Ed25519 这类现代签名算法），把「谁写的」也钉死。

例：攻击者改第 1 条的参数，验证器（重算链条核对哈希的检查方）重算发现第 1 条哈希不符；把第 1 条整条删掉，第 2 条记着的前哈希对不上，一样现形；更狠的一步是连算法都照抄、把第 1 条的哈希重算成正确值——第 1 条过了，第 2 条的前哈希却又对不上。链还是断，因为每一条记录都被后一条盯着；「只增不减」意味着删整条不是更新，是破坏。

我们的办法：工具执行完由审计中间件（挂在工具调用外圈补记一笔的拦截层）往本地链文件追加一条记录，另配独立验证脚本重算整条链，报出从第几条开始验不过。实测改行、连哈希重算两类当场被抓——删首条同理是推演：第 2 条的前哈希对不上，一样现形。

### 观测与证据分离（dual-write audit）

是什么：观测与证据分离 [自造]（本项目自创的提法）是审计记录的两条出口分工：观测面（可查可看的追踪平台）答「系统做了什么」，本项目用的是 Langfuse（LLM 应用的观测追踪平台）。证据面（独立保存、防篡改的本地日志）答「记录可信吗」。实现靠审计中间件（挂在工具调用外圈、工具执行完在旁边补记一笔的拦截层）一次遍历双写（同一笔事件同时写两处）：一份发往观测平台，一份追加进本地的证据文件。两份记录都按审计五要素 [自造]（本项目定的五字段，非行业标准）组稿：who 发起、when 发生、why 理由、params 参数、data_class 碰了什么数据。

解决什么问题：观测平台自己就是可变系统——实测重建一次观测部署，全部历史随之丢失。「这件事发生过、且记录没被改过」是法庭式问题，答案必须锚在观测系统之外；证据若只存在观测平台里，平台一重建、一被改，证据跟着一起蒸发。这不止是本项目教训：NIST SP 800-53 的 AU-9 控制项（审计信息保护，protection of audit information）要求审计记录与审计工具自身都防未授权的访问、修改、删除。审计数据独立于被观测系统，由此成为合规点名的前提。反向同样成立：观测平台被人改了，两份记录对不上，证据链也应能把它检出来。

我们的办法：一次遍历双写，观测与证据互不依赖，证据侧是追加写的哈希链文件（每条哈希揉进前一条哈希的本地日志）。取舍是证据面朴素得多——没有查询界面，只保留「能用脚本整链重验」这一种读法。

### append-only 追加写（append-only）

是什么：append-only（追加写）是一种存储纪律：文件只许在尾部追加新记录，不许改写、不许删除已有内容。本项目证据日志的载体是 jsonl（JSON Lines，每行一条 JSON 记录的纯文本格式），「只追加」靠打开文件时的 O_APPEND 标志（操作系统的一个打开选项，保证每次写入自动落到文件末尾）落实。

解决什么问题：证据日志要当历史档案，文件若能随意覆写，改一条记录可以不留任何痕迹。但边界必须诚实：append-only 只约束写文件的程序，拦不住有权限的人覆写或截断文件。NIST（美国国家标准与技术研究院）词汇表正好有这对词条：tamper-evident（改动易检测——动手未必拦得住，但一定留下可发现的痕迹）与 tamper-resistant（改动难实施——用权限和介质把动手本身变难、变贵）。append-only 加哈希链属于前者，防改那一半靠文件权限与 WORM（Write Once Read Many，一次写入多次读取的介质级不可覆写存储）这类后者的手段。工业实例是 S3 Object Lock（AWS 对象存储的合规锁定特性）：保留期内对象不可覆写不可删，Compliance 模式下管理员账号也解不开。口语说的「纪律不是魔法」，对应的正是这对术语。

我们的办法：证据文件按追加方式打开、一条记录一行，「动过必被发现」由哈希链负责。取舍是按这对词条分工记账：tamper-evident 归哈希链，tamper-resistant 这一半本项目靠文件权限顶住，WORM 属生产加强、暂未上，不用惯例冒充保证。

### 参数级数据分级（parameter-level data classification）

是什么：参数级数据分级是审计打危险度标签的粒度升级：不只看调了什么工具，还看这一次的参数里装了什么。判定做法是把参数序列化成文本后匹配敏感模式（pattern，正则表达式一类的特征规则）：命中凭证词判「凭证相关（高危）」，命中 http 词判「出网行为」。全部未命中就落回工具级默认（登记表给每个工具配的基准级别）。

解决什么问题：工具级分级答的是「这个工具碰什么」，分不出同一工具的两次调用差多远。例如同一个文件写入工具，写 `notes.txt` 是记笔记，写 `.env`（集中存放密钥凭证的文件）是动凭证，危险度天差地别。分级的依据是潜在影响（potential impact）而非工具身份：FIPS 199（美国联邦分级标准——按信息失去保密/完整/可用后的最坏影响定级）定的正是这个逻辑——影响决定级别，级别决定管控强度。参数级回答「这一次碰的是什么」，审计从「目录」进化到「个案」。

我们的办法：同一个分级函数供观测记录与证据链共用，两处落下同一个 `data_class` 标签。按这套规则推演，写 `.env` 会命中凭证词判高危，实测走查的一笔是写 `notes.txt`、落回默认——「同一工具不同参数，危险度不同」在记录里看得见。

### 链长覆盖测试（chain-length coverage test）

是什么：链长覆盖测试 [自造]（本项目给这类测试起的名字）是给哈希链这类「前后咬合」校验定的测试纪律：验证用例必须包含长度大于 1 的链，不能只拿单条记录试。机制根源在链首这个边界情形（boundary case，数据恰好落在规则特判处的用例）——首条没有前一条，前哈希记为空串，于是首条的正确哈希恰好等于「不带前缀、直接对正文做 sha256」的结果。写入器（生成并追加记录的一方）若漏拼前缀，算出的错值会在单条链上碰巧对上。这套测试还隐含一个前提：验证得由独立角色来做——RFC 6962 把它命名为 auditor（审计者：与写入方分开、专查日志是否守规矩的一方），写入器与验证器分离，检查才可信。

为什么重要：巧合通过比失败更危险——坏写入器带着绿灯上线，真实数据一进来链条就断。「验证通过」之前要先审「算法写对了没」，而覆盖真实形态（链上至少两条记录）正是最便宜的审法。

我们怎么用：实测抓到过一次真实的漏拼——写入器少拼了前缀，单条记录验证通过，放到两条的链上立刻验不过，据此定位修复。此后把「至少两条记录的链」定为这类校验器的最低测试形态，写入器与验证脚本也始终保持分属两处。
