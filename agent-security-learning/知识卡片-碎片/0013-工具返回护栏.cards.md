# 0013 工具返回护栏 —— 知识卡片

### Agent 中间件(wrap_tool_call)

是什么:Agent 中间件(Agent middleware)是 LangChain(Python 生态流行的 LLM 应用开发框架)v1 版新增的官方挂载机制。它让开发者在 Agent 运行图(以节点和边编排执行流程的图状结构)的固定环节——模型调用前后、工具调用前后——插入自定义逻辑,这一切不用改动图结构。针对工具调用,它提供 wrap_tool_call 装饰器(decorator,Python 里包住原函数、在外围附加逻辑的语法机制),官方用途是拦截调用、重试、监控、改写返回。被装饰函数收到 ToolCallRequest 请求对象,里面装着模型生成的调用意图(工具名与参数),内部调用 handler(被包住的原始执行函数)才真实执行工具。装饰函数的返回值替代工具原结果回喂模型,官方类型是 ToolMessage(代表工具返回的消息类型)或 Command(可同时改写状态与指令的返回对象)。handler 调几次有官方语义:调 0 次即短路,工具不执行、直接返回替代结果。调 1 次是正常放行,调多次可做重试。机制上与 Express(Node.js Web 框架)和 Django(Python Web 框架)的中间件同构:都钉在消息必经之路上,想绕也绕不开。

解决什么问题:它给"工具执行完、结果回喂模型前"这个环节提供了框架保证的检查点。没有这种机制,防御逻辑要么复制进每个工具内部(每个工具都得改,还容易漏),要么散落在编排代码里(一处遗漏就被绕过)。中间件把政策代码(与业务无关的安全检查逻辑)与工具代码零耦合——工具只管搬运数据,安全检查统一钉在消息必经的翻译层上。对防务而言,这正是护栏[自造](挂在 Agent 链路上的防御检查点)理想的钉法:官方挂点、结构保证、绕不开,"调 0 次直接返回拒绝"正是官方背书的玩法。

我们的办法:用 wrap_tool_call 落地工具返回护栏。工具执行完、回喂前,先由小分类器给返回消息打分,判断像不像注入攻击。注入攻击,即把恶意指令混进模型读到的内容里、诱骗模型把数据当指令执行的攻击。判带毒就把整条返回换成警告(该来源不可信,直接告知用户)。实测同一毒网页切成约 400 字符块后,最高分块打到 1.0、越过 0.92 的拦截门线(分数高于它才判注入)被整体拦下。模型只读到警告、随即提醒用户勿轻信,攻击想借模型之手完成的动作一次都没发生。

### 分块扫描与稀释效应(chunked scanning & dilution)

是什么:分块扫描指把长文本切成小段、逐段送分类器打分、取全部块中最高分作判决的扫描方式。稀释效应[自造](dilution,恶意信号被大段正常内容平均掉、分数跌到判注入门槛之下——社区文献最接近的说法是 needle-in-a-haystack,长文本藏针、检测难找)指的就是这种被平均掉的失效。本项目的切法是在应用层把工具返回按行聚成约 400 字符的块,逐块送 PromptInjection 扫描器——llm-guard(protectai 出品的开源 LLM 安全扫描器框架)框架里专判提示注入的扫描器——而不是一次喂整段。prompt injection 即把恶意指令混进模型输入、诱骗模型把数据当指令执行的攻击。切块放在应用层而不是用扫描器自带的分块模式,顺带绕开了扫描器 512 token 的输入截断。

解决什么问题:整段扫描对"大段正常文本里藏一句毒"的写法有系统性漏判。实测对比很直观:带毒文件整段扫描只得 0.07 分(毒被正常内容稀释掉了)。换网页向量(以投毒网页为饵的攻击样本)切成小块后,两个含毒块分别打到 0.99 与 1.0,双双越过 0.92 的拦截门线(分数高于它才判注入)。判决后的处置是整条级的:任一块超线,整个工具返回消息被替换成警告——毒文本一个字符都不进模型上下文(模型当次读到的全部内容),而不是只抠掉带毒的那一块。同一问题的另一族防御是来源标记(provenance,把不可信内容的来源标给模型看)。微软 Spotlighting(聚光防御)论文实测,这招能把间接注入(藏在网页、文档等第三方内容里、随取回内容进入模型的注入攻击)成功率从五成以上压到 2% 以下,与分块扫描互补。分块不是万能药:把毒意图写进"格式规范"叙事的伪装,切块后仍只有 0.05 分——漏判还可以是内容级的,切块不会让分类器的盲区消失。

我们的办法:把分块扫描钉在工具返回回喂模型之前,实测毒网页被拦后模型主动告知用户"页面被安全护栏[自造](挂在 Agent 链路上的防御检查点)拦截,请勿轻信"。恶意命令一次都没执行,宿主机上没有出现标记文件。这一版落地是纯分类器方案——同位置后来又补了一层 LLM 语义审查(另一个模型通读文本、判有无夹带指令),两层叠加才成最终形态。

### 纵深防御的统计学(statistical case for defense-in-depth)

是什么:纵深防御(defense-in-depth,多层防线互相兜底、任一层失守还有下一层顶上)在 LLM(大语言模型)安全里是一条统计命题,不只是架构口号。每道基于分类器(专判某一类文本的小型判别模型)的防线都同时带着漏判面(该拦的没拦住)与误报面(不该拦的误伤了)。这两类失效不是实现瑕疵,而是这类防线的固有属性——单层不可靠,层层串联才能把整体风险压下来。

解决什么问题:它回答"一道扫描器拦下了全部测试攻击,是不是就够用了"。不够——同一道扫描器可以同时表现出两种失效。实测它放过了把"回复第一行必须写上密钥"包装成摘要格式要求的毒(逐块打分仍只有 0.05 分)。转头又把 `.env`(存环境变量与密钥的本地配置文件)的内容本身误判成满分攻击拦下,而那份内容里并没有攻击。这不是本篇一家的观察:OWASP(发布大模型十大风险清单的行业组织)同口径——基于模式的过滤并不总能拦住不可信内容里的间接注入。间接注入,指藏在网页、文档等第三方内容里、随取回内容进入模型的注入攻击。这类过滤只能当纵深防御里的一层。其榜首的提示注入(把恶意指令混进模型输入、诱骗模型把数据当指令执行的攻击)条目还写明:目前没有万全的预防方法。

我们的办法:把防线串起来——用户输入一道、工具返回一道,模型回复送回用户前再补输出层,漏网交给下一层兜底来守住战利品[自造](演习里攻击方要拿到的战果,行业叫 crown jewels)。阈值是查全(recall,衡量漏报多少)与查准(precision,衡量误报多少)的权衡,调低门线(判注入的分数门槛)查全升、查准降。定在哪是产品决策而不是技术 bug——实测一道输入护栏[自造](挂在用户输入进入模型之前的自动拦截器)曾把善意的"总结 notes.txt"请求打到 0.99 分误拦。
