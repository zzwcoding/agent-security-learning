# 复刻 0002 诊断聚簇 —— 知识卡片

### 失败簇[自造](failure cluster)

是什么:失败簇[自造](参照实验自创的聚簇叫法)是诊断器把多条失败轨迹[自造](把一次失败任务全过程写成结构化记录)按同一风险类别归成的堆。喂进堆里的证据来自三类互不相识的反馈渠道:用户打字纠正、用户点踩(连文字都懒得打的低摩擦负反馈)、事后机器审计(当时无人在场,事后按规则回查才现形)。

为什么重要:三类渠道彼此不知情,同簇出现就互为旁证。比如删除文件簇的信号清单里同时有用户纠正与事后审计,说明人的抱怨和机器的回查指向同一病灶。单看任何一方都可能被当成用户挑剔或误报;合在一起,立案(把一簇失败定为一份正式修改请求)就硬得多。

我们怎么用:参照实验的 11 条轨迹聚成 3 个失败簇,对应未确认的删文件、删表与强推,支持度(凑数立案的不同轨迹条数)为 3/3/2;复刻实测数字一致。支持度只数不同轨迹,一条轨迹反复犯同类错仍算一次;立案门槛沿用多轨迹支持门槛(同一模式至少 2 条不同轨迹支持才立案的已有专卡)。

### 负反馈分诊[自造](feedback triage)

是什么:负反馈分诊[自造]是立案(把一簇失败定为一份正式修改请求)前的一道过滤纪律:每条负反馈先问一句"这归我管吗",不归管的直接排除、不入簇。参照实验让风险分级函数代答:`classify_risk` 给出事操作打风险类别标签,打得出标签才算归管,打不出标签的(低风险操作)连轨迹一起出局。

为什么重要:负反馈表象都一样,病因却不同:嫌周报措辞生硬而点踩是内容质量问题,未确认先删文件才是流程缺陷。不先分诊,系统会被引去修不属于门禁的东西;对会自己改自己的系统,误立案比漏立案更危险,因为它会推动系统改掉本来正确的行为。

我们怎么用:参照实验共设三道过滤,各挡一种噪声:
· 结局不是失败的跳过——挡住结果正常的对照轨迹;
· 已确认的调用跳过——双保险,防未来数据混入;
· 打不出风险标签的跳过——挡不归管的抱怨。
复刻实测三条"该排除"的轨迹各被对应过滤拦下;一条真违规的递归强删命令(rm -rf)因支持度不足只记录、不立案。
