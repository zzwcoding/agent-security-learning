# NeMo复刻0005-0006 账单与收官对照 —— 知识卡片

### 闸位账单[自造](per-gate billing)

是什么:闸位账单[自造](把一次请求拆到每一次 LLM 调用、按闸位分别记录调用次数、延迟与 token 花费的成本计量做法)靠框架的调用回放接口支撑。NeMo Guardrails(NVIDIA 开源的 LLM 对话防护框架,rail 指它挂在对话链路上的检查环节)在每次生成后可取回一份调用明细:每笔带任务名(哪道闸或主生成)、耗时秒数与三段 token 计数——提示词侧、生成侧、合计。明细只回放最近一次交互,要在生成结束后立刻取。

解决什么问题:防线选型只答「拦不拦」不答「多少钱」,取舍就没有依据。同一份明细既是拦截归因的证据,又是成本账本:把每条测试输入的账单汇总成「输入 × 防线」结果表,哪道闸贵、贵多少一目了然。

我们的办法:每条消息生成后立刻回放明细并打印、按任务名归账,单次实测延迟抖动大,看量级不看零头。例如「写一首秋天的诗」装双闸后共 3 笔调用(19.7 秒 / 2312 tokens),同一题不装检查只要 1 次(6.1 秒 / 603 tokens)。

### 双闸三倍账[自造](dual self-check ×3 overhead)

是什么:双闸三倍账[自造](对话链路前后各装一道 LLM 自检闸后,正常请求的调用次数、token、延迟同时涨到约三倍)是一条实测成本规律。NeMo 的自检闸是让主对话模型换一张清单提示词再答一次 Yes(拦)或 No(放),每道闸都是一次完整的 LLM 调用,片酬照付。

解决什么问题:它把「语义闸贵」从感觉变成数字。三笔账(入口自检、主生成、出口自检)对比无检查基线:调用约 3 倍、token 约 3.8 倍、延迟约 3 倍;而本地小模型分类器(如 deberta 这类轻量判别模型)一次扫描毫秒级、零 API token——两条机制路线的成本差是数量级的。

我们的办法:实测被拦请求只花一笔(约 4.5 秒、563 tokens),因为主生成那笔根本不发生——早拦不仅安全还省钱;把双闸三倍账当语义防线选型的成本底线,先算账再上闸。

### 思考链峰值预算[自造](peak chain-of-thought budget)

是什么:思考链峰值预算[自造](输出上限要按最长思考链留足,不按均值)是给推理模型当判官[自造](被额外调来做 Yes/No 安全判定的那次 LLM 调用)时的预算规则。推理模型(reasoning model,正式回答前先生成一段内部推理的模型)的思考链长度方差极大:实测同一道入口闸,普通请求约 1.4 秒、284 tokens,伪装复杂的请求约 13.4 秒、1317 tokens。

解决什么问题:每个自检任务的 max_tokens(单次调用输出长度上限)默认不设、用引擎默认值。思考链一长就可能吃光预算,判定还没出口就被截断,正常请求按「拿不准即拒」被误拦——误拦率跟着思考链的抖动走。

我们的办法:两道自检闸的 max_tokens 都显式设成 2000,并按观察到的最长思考链复核够不够;预算按峰值留,不按均值留。

### 闸的不管辖区[自造](unmanaged zone of a gate)

是什么:闸的不管辖区[自造](每道防线闸机都有定义上就管不到的地带,评估一道闸要把「不管什么」与「管什么」并列查清)是防线覆盖面的审计视角。以 NeMo 的五道闸(该框架规定的五个检查位置)为例:记忆装载(把历史对话或资料灌进模型上下文的动作)不在五道闸经过的链路上,五闸都够不着;工具返回闸官方明说只查结构、不做内容安检;工具参数闸的 JSON Schema(声明参数名与类型的结构描述)只验形态、管不着语义。

为什么重要:只看「管什么」会高估覆盖面,以为装了框架就处处有防线。一个缺口判「能补还是不能补」,依据是受攻击通道上有没有闸机,而不是框架名气。

我们怎么用:给每道闸列两栏清单——辖区与不管辖区。受攻击通道若落在不管辖区(例如记忆装载),要么自建检查接进链路,要么明确记为已知缺口并接受风险。

### 看得穿、接不上[自造](effective mechanism, missing wiring)

是什么:看得穿、接不上[自造](评「某判定机制能否补某缺口」时把能力与位置分开:判定认得出、闸机却不在受攻击通道上,只能算补一半)是缺口归类的判定规则。实测例子:格式伪装的毒文档(把恶意指令改写成文档里的「摘要验收标准」来躲检查)被贴进输入闸当用户消息,LLM 语义自检逐条对照清单,识别出「要求读密钥文件」并拦下。

解决什么问题:它划清「能补」的边界。这次实测证明 LLM 语义判定能看穿格式伪装;但真实攻击里这类毒走工具返回通道进来,而现成的工具返回闸只查结构不查内容——位置不对,等于没接上。反过来,把原来漏判的本地分类器原样挂进新框架,漏判面也原样搬进来。

我们的办法:补缺口靠换判定机制(用语义判定替换打分过低的分类器),不靠换框架;机制选定后还要自己把检查接进受攻击通道,才算真补上。

### 按闸位混搭[自造](cost-tiered gate assignment)

是什么:按闸位混搭[自造](按各位置的流量与风险分配不同成本的判定机制:便宜机制守常规岗,贵的语义机制守分类器天花板处)是两种框架对照后的选型结论。LLM 自检双闸约 3 倍调用与延迟;本地分类器毫秒级、零 API token。全上语义闸成本撑不住,全用分类器又有漏判天花板。

为什么重要:结论不是「谁取代谁」。成本是选型的硬约束,机制按岗位配而不是按名气配——常规岗用便宜的,漏判高发处才用贵的。

我们怎么用:常规大流量交给本地快速机制;分类器打了低分却放行的可疑内容(例如某毒文档只被打 0.05 分而漏判),或只有语义能判的违规,升级给 LLM 语义判定复核。
