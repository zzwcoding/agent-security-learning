# 0039 五条验收 —— 知识卡片

### 验收判表（acceptance matrix）

是什么：验收判表[自造]是一张把整套 Agent 防线的安全断言拆成固定几条判据的验收清单，每条判据都配一个可观察的通过标准。它把行业里先写验收标准（acceptance criteria，动手验收前先写明"做成什么样算过"）的做法搬到了安全改造上。判据写法可对齐 ASVS（OWASP 发布的应用安全验证标准）的条目样式：每条判据带稳定编号，用"验证（Verify that）……"的句式陈述。每条判据都要走完"发起攻击→防线拦下→证据落盘"的闭环，判不过的事实不允许用感觉代替。

为什么重要：它把安全成果从"感觉安全"变成"逐条可证"，验收结论不依赖任何人的口头担保。验收在这里不是自述，是可复跑的记录——谁重跑同一攻击，都应看到同一拦截与同一份证据。这也是 Scrum（迭代开发框架）对"完成的定义"（DoD，Definition of Done，写明做到什么程度才算完成的底线）立的硬规矩：不达标的活不算交付，没有商量余地。

我们怎么用：把判据按防线职责定为五条（"五条验收"是本项目对这套判据的叫法），逐条采集真实运行的落盘证据：
- 收敛：Agent 代码里查不到对模型或工具的直连，一次真实任务的全部工具调用都带网关路由前缀。
- 授权：同一个高危工具做成对照表，越权身份拿到拒绝码，授权身份放行。
- 缺口核销[自造]（拿实测证据把评估期间登记在案的每个已知安全缺口销账）：每个缺口都要有一项"已堵上"的实测记录，不许拿"应该修好了"销账。
- 审计：观测平台有活数据，证据日志过完整性校验，人为改一条记录，完整性校验立即报错。
- 体检：固定一批毒样本（预先构造、答案已知的恶意样本）全部被进闸扫描抓住，命中的再过一道人工复核。

### 集成级安全验收（integration-level acceptance）

是什么：集成级安全验收[自造]指各道防线单独测试全部通过之后，把整套防线当整体再打一遍的验收层。单层测试相当于单元测试（逐个模块各自验），整体打一遍才是集成测试（把模块连起来跑真实场景）；层间语义冲突（每层单独看都正常、合在一起才暴露的矛盾）只有联动时才现形。

为什么重要：多层串联的纵深防御（defense in depth）有一笔概率账：单层被穿概率 p 的四道闸，整体被穿约 p⁴——前提是层间独立（不同原理、因不同原因失守）且每层 fail closed（拿不准就拒）。但这笔账有个反向警示：安全冗余研究的经典文献（Littlewood 与 Strigini）指出，独立性在安全里恰恰最难成立。原因是打穿一层的手法常能复用到另一层，几道闸可能栽在同一个坑上（common-mode，共因失效：一个原因同时放倒多层）。所以独立性不是免费假设，而是验收要用实测去逼近的目标；这笔账也只有在整体联动运行里才核实得了。

我们怎么用：验收实测用一次真实攻击穿全套防线。例如管理员身份对命令工具发一条出网请求：第一道出口闸[自造]（网关里最先跑的命令检查插件）直接回拒绝码，被拦过程落盘成证据；按各层已验的拒绝语义推演，即使这道闸漏过，后面还有调用授权、命令必须出自用户消息的规则与沙箱出网兜底三道各管一段的防线。

### 诚实记录（honest acceptance record）

是什么：诚实记录[自造]是验收的一条成文纪律：交付文档按 as-built（实际建成的样子）写，而不是按 as-advertised（宣称建成的样子）写；发现两者不符，差异本身也要写进验收结论。它直接决定交付物的可信度，因为下一个读者会照着文档去依赖这套系统。

为什么重要：按宣传写文档等于替组件夸口，读者照文档做的依赖迟早踩坑。描述一旦失真，基于它的检查再认真也失去了意义。写局限更不是自曝其短——NIST（美国国家标准与技术研究院）的渗透测试指南本来就要求报告写明每种技术手段的能力与局限。与宣传不符也未必是缺陷，常见真相只是实际分工和宣传说的不一样，但这种差异必须写明而不是含糊过去。

我们怎么用：例如验收时发现证据组件里的一张审计表是空的——查实它按设计只管管理员操作，工具调用的审计走的是另一条指标通道。文档于是如实记"该表为空及原因"，验收结论照样通过，但写的是真实行为而不是"审计全覆盖"。

### 截断重造报警（truncation-rebuild alarm）

是什么：截断重造报警[自造]是哈希链（每条记录的指纹都掺着前一条指纹、改动任何一条后段全对不上的防篡改日志）验证器的一条边界检查。它盯的是首条记录的前向指纹：正常链的首条前面没有记录，这个字段的合法取值是空串（本项目验证器即按此判定）。空值在这里是被定义的合法边界值而不是"缺失"，所以判据是纯机械的：非空即截断——若它非空，唯一合理的解释是有人截走了链头一段、让幸存记录顶到了文件开头。

解决什么问题：截断链头是比篡改中间更省力的破坏——删掉开头几条，幸存的每条记录跟自己记的前指纹仍然咬合，逐条校验查不出缺了开头。这条检查把"文件是不是从第一条原始记录开始"也变成机器可判定的问题，破坏从静默丢失变成显式报警。业界有同款先例：证书透明（Certificate Transparency，把证书日志公开挂出来供任何人审计的业界机制）的规范（RFC 6962）就把违反"只增不删"列为可及时公开检测的违规，这条报警正属此类。

我们的办法：验证器保留这条检查，并把它的定性从"报格式错误"改成"疑似截断重造"的报警项。报警的输出形态例如一行"疑似截断重造：首条前指纹非空"。这是验收暴露出的边界情况反过来完善验证工具本身的一个实例。
