# 自修改复刻0006 容器内语义检查上 —— 知识卡片

### 行为级验证(behavior-based verification)

是什么:行为级验证[自造](对本项目"验证行为而非代码长相"这一验证方式的叫法)指把候选代码真正执行起来、按"它办事对不对"来裁决。静态检查只能看"代码像不像好代码",而改动说明书(diff,逐行写明删了什么、加了什么的文本)完全可以长得人畜无害、行为暗中使坏。

为什么重要:它让"能不能信任一个补丁"变得可证,而且不看出身:不管补丁是确定性模板生成的还是大模型写的,都得在行为考试里拿同样的分。配套还有一道负对照(negative control,借自实验科学的标准名词:与试验组同样处理、预期无效应的对照)——把修好前的老版本喂进同一套检查,它必须挂;对照一旦出了效应,按定义就提示污染或偏倚,检查区分不了"带病的"和"修好的",就是摆设。

我们怎么用:容器内的验证程序把候选源码执行起来逐项考试,回一份 `{"checks": {...}}` 形态的布尔表,宿主据此点亮检查灯表[自造](候选放行前的固定格数布尔检查表)的对应格。实测老稳定版[自造](自我修改系统里作为修改对象的正式代码区)在"失败重放"(重放当年失败案例,考它敢不敢乱重试)与"永久错误熔断"(考不可重试的错误是否一次就停)两项必挂,修复后的候选全部通过。

### 独立命名空间加载(isolated-namespace exec)

是什么:独立命名空间加载[自造](对"装进独立字典再执行"这种加载方式的叫法)指用 `exec(compile(源码, ...))`(内置的"先编译再执行"组合)把候选代码装进一个独立字典当命名空间跑起来。命名空间指变量名与函数名到对象的映射;它好比一个一次性房间[自造](比喻:命名空间是一次性的独立字典,房间里的名字互不外漏),房间里冒出来的函数对象都能按名字取出,如 `namespace["should_retry"]` 拿到的就是候选定义的那个函数。

解决什么问题:验证行为的前提是先把候选"加载并体检",而加载方式本身有讲究。Python 官方文档对 `exec` 的说明是:可选的字典参数省略时,"代码就在当前作用域执行"——名字会漏进验证程序自己的作用域;给了独立字典,候选的任何名字都出不了房间。还有一条官方提醒必须记住:官方明说覆盖 `__builtins__`(Python 内置函数所在的字典)"不是安全机制——被执行的代码仍然能访问全部内置函数"。命名空间隔离只隔名字,安全要靠外层的容器边界。这里还有一层自创观点[自造](不是行业术语,是一句自创的心得):同一个操作,权限取决于它在隔离边界的哪一侧。同一个 `exec`,在宿主机上是静态检查的头号禁词(执行任意代码的口子),在一次性容器里就是干活的工具。

我们的办法:容器内固定用 `exec(compile(源码, "<候选>", "exec"), 独立字典)` 加载候选;宿主上的静态检查依旧把 `exec` 列为禁止词,两层规则并行不悖。

### 签名兼容检查(signature compatibility check)

是什么:签名兼容检查[自造](对"把签名当契约来查"这道检查的叫法)是用 `inspect.signature`(Python 标准库的内省函数,返回函数的参数签名)把候选函数的签名与约定逐字符比对的检查。签名指一个函数收哪些参数、参数叫什么——它是候选补丁与所有现有调用方之间的契约,契约不容补丁重谈。

解决什么问题:自我修改最容易踩的坑是"改了内部,毁了接口":补丁哪怕写得再聪明,把参数改个名,生产里按老签名调用它的代码当场全炸。这个检查保护的正是调用方而不是候选自己。比如约定重试函数必须还是 `(error_code, retryable, attempt)` 三个参数;补丁把它缩成 `(error_code, attempt)` 两个,就算行为再对也直接拒。比对本身还有个官方细节:`inspect.signature` 默认 `follow_wrapped=True`,会沿 `__wrapped__` 链解开装饰器——被 functools.wraps(保留原函数元信息的标准装饰器)包过的函数会直接报出原函数的签名,比对前关不关这个默认值是个真实决策点。解析失败时官方约定抛 ValueError(给不出签名)或 TypeError(类型不支持),一律按检查不通过处理。

我们的办法:容器内对每个公开函数做整串比对,形如 `str(inspect.signature(候选函数)) == "(error_code, retryable, attempt)"`——`str()` 出的是官方的规范渲染。取舍:整串文字比对比 Python `Signature` 对象自带的 `==` 相等比较更严,连注解写法的差异都敏感,实测签名无漂移的修复候选过此格、漂移的当场出局。

### 失败重放(failure replay)

是什么:失败重放[自造](对"拿真实失败案例当考卷"这种验证方式的叫法)是把当初生产里失败的事故记录原样重放给候选补丁、逐次核对它反应的验证方法。考卷只从失败轨迹[自造](生产事故的结构化记录)里收 `outcome`(结局字段)为"失败"的案例;对每条轨迹的每个尝试序号(第 0 次、第 1 次……直到它实际试过的最后一次)都问一遍候选"这次还该不该重试",要求全部回答"别试了"。

为什么重要:它把"修好了"从改动说明书上的一行 diff,变成对原始事故的逐次可核对答复;考卷是当初真实发生的事故,不是凭空编的测试用例,补丁糊弄不过去。用标准行话说:它一半是回归测试(regression testing)——ISTQB(国际软件测试认证委员会)的定义是"程序修改后再次测试,确认改动没有在未变的区域引入或暴露缺陷";另一半是对改动本身的复测,行话叫确认测试(confirmation testing,ISTQB 定义:修复缺陷后再次运行,确认该缺陷引起的失败不再复现),运行时领域同款的还有 Azure 熔断模式的"失败请求重放"(记录失败请求,等服务恢复再重放)。

我们怎么用:实测两条支付失败轨迹共 7 个提问,修复后的候选 7 问全部答"别试了"。一个易看漏的边界:超时后重试成功的那条轨迹不在考卷里——它的结局字段是成功,属于"临时恢复"(考超时后重试能不能成功)考题的正样本(术语:测试里预期应当通过的用例);重放考卷只收失败的案例。

### 永久错误熔断验证(nonretryable circuit-breaker check)

是什么:永久错误熔断验证[自造](对这道单题行为检查的叫法)专考"不该重试的错误是否立即止损":才失败 1 次,问候选的熔断函数(候选代码里做熔断判断的函数)跳不跳闸。熔断(circuit breaker)是分布式系统的成熟模式,Azure 的官方定义是"失败攒到阈值后,暂时切断对一个远程服务的访问,而不是反复重试注定失败的操作";经典实现分三态:Closed(放行)、Open(切断)、Half-Open(半开试探)。

解决什么问题:病根之一是熔断函数只看次数不看错误类型,让"银行明确回绝"这种永久性错误陪跑满 5 次才断。判据要按错误类型分类,不是本卡片独有的讲究:Azure 把"按异常的性质调整策略"列为设计要点。Resilience4j(Java 生态主流的熔断库)的配置项就分成 recordExceptions(计入失败统计)与 ignoreExceptions(忽略不计)——按错误类型分类计数是行业惯例。检查只问一句"连错 1 次,跳不跳":修复后的候选答"跳",老稳定版按 `1 >= 5` 算出"不跳"必挂——一个提问就把病灶与疗效分开。"一次就断"也有行业背书:Azure 叫它加速熔断(accelerated circuit breaking),响应里信息足够判定时允许立即跳闸。

我们的办法:提问形如"连续失败 1 次且错误类型为不可重试,该开闸吗",实测修复候选答"开"、老稳定版答"不开"。熔断判据必须同时看次数与错误类型,只数次数的版本在这道题前无处遁形。

### 输出通道独占(stdout blackhole for untrusted code)

是什么:输出通道独占[自造](对"候选打印进黑洞、协议通道归验证程序"这一安排的叫法)指候选代码执行期间,把它进程的标准输出整体重定向进一个黑洞写入器[自造](吞掉一切写入内容、什么都不往外送的对象)。实现用标准库的 contextlib.redirect_stdout(官方定义:临时把 sys.stdout 重定向到另一个文件或文件类对象的上下文管理器),官方示例用的就是标准库的 io.StringIO(内存里的字符串流):`with redirect_stdout(io.StringIO())`。自实现的丢弃版不占内存,StringIO 版多一个留存下来做审计的选项。

解决什么问题:候选是不可信代码,而协议走标准输出——候选哪怕只是无心地 print 几句,也会往协议通道里塞脏字节;存心的话,更可以伪造一份 `{"ok": true}` 冒充验证结论。把候选的打印全部吸进黑洞,标准输出上就只剩验证程序最后写的那一行 JSON,污染与伪造都无从下手。但官方文档自己给了两条警告:一是它改的是全局的 sys.stdout;二是对子进程的输出完全无效。从"改的是全局的 sys.stdout"这条警告也能推出来:它只换 Python 层的引用,候选用 `sys.__stdout__` 或 `os.write`(底层系统调用写文件)直写 1 号文件描述符(操作系统的标准输出通道,即 fd 1)照样漏出去;起子进程则是另一个漏出口。在"候选可以伪造 `{"ok": true}`"的威胁模型下这是实质漏洞——所以候选始终跑在容器里,漏出去的字节也只漏进一次性容器;协议通道"只许验证程序写"的纪律,与 MCP(模型上下文协议,大模型接入外部工具的开放协议)规范"不得向 stdout 写任何非协议消息"的硬约束同款。

我们的办法:用 `with redirect_stdout(黑洞写入器):` 包住整段候选执行,实测就算候选连打一万遍,宿主收到的也只有协议 JSON 一行;起子进程那类逃生通道,则由容器边界兜底。
