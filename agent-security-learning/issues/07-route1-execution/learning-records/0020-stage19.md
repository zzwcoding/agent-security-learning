**卡在哪/结论**(按踩坑顺序):
1. **v4 弃用旧读接口**:服务端 4.x 默认 events_only 数据模型,`GET /api/public/traces` 返回 410;查数据用 `/api/public/v2/observations`(但该接口只给元数据,查内容要直查 clickhouse `events_full`,或看 UI)。教训:SDK 与服务端大版本要对着[兼容矩阵](https://langfuse.com/docs/compatibility)看。
2. **`get_client()` 不是单例是"领取"**:内部查 LangfuseResourceManager 实例表——表空则建默认(无 mask),有一个则按 `_create_client_from_instance` 复刻配置(mask 在拷贝字段里)。所以挂 mask 必须先 `Langfuse(mask=fn)` 登记,再 `CallbackHandler()`(它内部调 get_client 继承)。顺序反了掩码不生效。
3. **护栏与观测意外联动**:deberta 对任何 `KEY=高熵串` 一律判注入 1.0 → 带密钥的工具返回根本走不到 trace,工具返回护栏顺带保护了观测系统。mask 仍是必要的确定性兜底(护栏是概率模型)。
4. **分类器误报成本实录**:"读一下 notes.txt / 看看 demo.txt 写了什么"全判注入 1.0,只有"把 notes.txt 的内容读出来"句式放行——验证掩码时连撞 4 次。上线前阈值标定+人工通道是必须算的账。
5. **两行 payload 产生 2 条 trace**:input() 按行读,两行=两次独立输入=两次拦截=两张案卷;护栏是逐行设防的,拆行投毒是已知弱点形态(用户提问时发现的)。

**运维备忘**:Langfuse 容器由 Docker 托管(`restart: always`),与本会话无关;管理命令 `cd langfuse && docker compose ps/up -d/stop/down`(加 `-v` 才删数据)。遥测已关(TELEMETRY_ENABLED=false),.env 里三个 CHANGEME 密钥已换随机值。
