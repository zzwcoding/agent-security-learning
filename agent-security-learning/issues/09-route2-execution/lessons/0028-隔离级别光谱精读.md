# 0028 — 隔离级别光谱:Firecracker 与 gVisor 精读对照

> 精读对象:Firecracker design doc(`docs/design.md`)+ gVisor 架构指南(intro/platforms/security 三页)。
> 要回答的两个问题:①为什么共享内核不够(容器);②用户态内核拦了什么(gVisor)。落点是给阶段 21-31 的实测结论补理论地基。

## 1. 光谱总览:隔离强度 = 你逼攻击者穿过的代码量

```
进程            同一内核,同一 UID,无边界          (lesson 0019:MCP 子进程≠沙箱)
  ↓
容器            namespace/cgroup 划权限,仍共享宿主内核 —— 逃逸面 = 整个内核 syscall 攻击面
  ↓
gVisor          用户态内核(Sentry)接管全部 syscall,应用永不直达宿主内核
                宿主面只剩"极小 syscall 集" —— 逃逸面 = Sentry+Gofer 的代码
  ↓
microVM         独立内核 + 硬件虚拟化 —— 逃逸面 = VMM 本身
                (Firecracker:Rust 极简 VMM;microsandbox/libkrun 同档的轻量形态)
```

**核心原理:攻击面 = 你暴露给不可信代码的代码量。**容器把整个宿主内核暴露给 guest;gVisor 换成自己写的内核 + 一个文件代理;microVM 只暴露一个极小的设备模拟器。三者的全部工程努力,都是在砍"暴露面"。

## 2. Firecracker:把"假设恶意"做成架构

- **形态**:基于 Linux KVM 的 VMM,**一个进程 = 一个且仅一个 microVM**(API/VMM/vCPU 三类线程)。密度数字:最小配置(单核 + 128 MiB)下**每宿主核每秒稳定创建 5 个 microVM**(36 核机 = 每秒 180 个)。
- **极简设备模型**:只给 virtio Net/Block/Vsock + 串口 + i8042(用途被限死为重启信号)。没有的设备根本不存在——不存在就不用防。
- **威胁模型原文**:*"all vCPU threads are considered to be running malicious code as soon as they have been started"*——guest 一启动即视为恶意代码,防线全在 guest 之外(嵌套信任区,区区之间设屏障)。
- **jailer**:生产环境必须经 jailer 启动——先做需要特权的设置(cgroup、chroot),**降权后 exec** Firecracker,此后只能碰显式授予的资源;seccomp 过滤器按线程、在任何 guest 代码执行前加载。
- **最值得记住的一句**:*"Firecracker does not perform any network traffic filtering"*——guest 全部出站流量视为不可信,**过滤是宿主层的责任**。

**这就是我们架构的影子**:阶段 31 的残余记录"VM 内公网出口仍开,须外层过滤"——Firecracker 的设计文档明说了这不是缺陷而是分工:VMM 只管隔离,策略在外层(我们的 fetch 工具白名单 + PUBLIC profile 兜底正是那个"宿主层过滤")。阶段 23 的两层出网设计,和业界 microVM 的标准分工完全对齐。

## 3. gVisor:不模拟硬件,重写内核

- **形态**:Go 写的**用户态应用内核**。Sentry 实现 Linux syscall 的一个子集,**没有任何系统调用直通宿主**——每一条都被 Sentry 的独立实现接管。可作为 OCI 运行时(runsc)插进 Docker/K8s,保有容器级轻量。
- **双墙原则**(安全模型页原文提炼):第一墙,应用↔宿主 System API 的直接交互全部被 Sentry 拦截;第二墙,Sentry 自己能用的宿主 API 被压缩到"a safer, restricted set"——防的是"攻破 Sentry 之后连锁提权":Sentry 不许 open 文件、不许建新 socket,宿主面只剩 FD 复制/关闭、同步、定时器、信号管理。
- **Gofer**:独立文件代理进程。Sentry 跑在**空的 mount namespace** 里,文件操作经 socket 向 Gofer 要 FD——文件系统攻击面(符号链接、恶意挂载)整个被挪出 Sentry。
- **平台演进**(架构指南 platforms 页):ptrace(`PTRACE_SYSEMU`,让用户代码跑但发不出宿主 syscall;上下文切换开销大)→ **systrap**(2023 年中起默认:seccomp `SECCOMP_RET_TRAP` 陷 SIGSYS 交给 gVisor)→ KVM 平台(Sentry **同时扮演 guest OS 和 VMM**,没有虚拟硬件层,沙箱仍保持进程模型)。选择:裸金属用 KVM 平台,VM 内/无虚拟化用 systrap。
- **工程纪律**:Sentry 必须是纯 Go 二进制(禁 CGo)、unsafe 代码全部收编进 `unsafe.go` 结尾的文件、持续 fuzzing。
- **最值得记住的一句**(FAQ 的比喻):*"不应因为用了虚拟化硬件就断定更安全或更不安全,正如单是使用承载式车身并不能让汽车安全"*——VM 的 guest 内核要做设备模拟(如 APIC),**内核里的设备模拟代码可能比一条 syscall 处理路径更复杂**。gVisor 不做设备模拟,直接用沙箱化的宿主 API。

## 4. 对照表

| 维度 | 容器 | gVisor | Firecracker/microVM |
|---|---|---|---|
| 信任根 | 宿主内核(全部) | 宿主内核(极小 syscall 面)+ Sentry/Gofer 代码 | 独立内核;信任 VMM |
| guest 看到的 | 真内核 | Sentry 实现的"假"内核(兼容子集) | 真 Linux 内核(自己的) |
| 逃逸面 | 内核 syscall 攻击面(千级 CVE 历史) | Sentry+Gofer 的实现量 | VMM 的实现量(Rust,极简设备) |
| 兼容性 | 完整 | 大部分常用;冷门 syscall/JIT 场景可能不兼容 | 接近完整 |
| 性能 | 原生 | syscall 密集型负载明显变慢 | 接近原生,内存/启动开销小 |
| 代码暴露哲学 | 全暴露 | 重写一层换小暴露面 | 换一层薄的(设备模拟)换硬边界 |

两家的哲学其实是同一条——**砍暴露面**——只是砍的位置不同:gVisor 在 syscall 边界重写了一层厚的;Firecracker 只保留一层薄的设备模拟,把内核交给硬件虚拟化隔开。

## 5. 回到我们的项目

- microsandbox(Rust + libkrun)= Firecracker 一档的轻量形态:独立内核、极简、嵌入式拉起。阶段 24/31 实测的"容器共享 6.12.76 内核 vs VM 独享 6.12.99 用完即焚"就是这张光谱表的实物版。
- 我们没有自建任何隔离层——**我们做的是"把不可信执行面放到光谱最右端 + 在外层配策略"**(fetch 白名单、PUBLIC profile、一次性)。这恰好是两篇文档共同主张的正确姿势:沙箱不是安全架构的替代品(gVisor 原话:*"A sandbox is not a substitute for a secure architecture"*),出网策略、密钥隔离、审计在沙箱外面各就各位,才是体系。
