# 0025 OTel GenAI 审计字段落 Langfuse(阶段 29)

## 三问(阶段动机)

**终极目标**:Agent 就算被注入完全劫持,事后也查得清——谁、何时、以何理由、动了什么。

路线图:

```
✅ 阶段26-27:凭证代理(LLM 路 + fetch 路)
✅ 阶段28:Presidio 记忆落库脱敏
👈 阶段29:OTel GenAI 审计字段落 Langfuse
⬜ 阶段31:四次攻击验收(审计复盘是其中一刀,本阶段是它的地基)
```

**这一阶段是干嘛的?** 按 OTel GenAI 语义约定,把审计五字段钉进现有 Langfuse 链路:**谁 / 何时 / 以何理由(引用本轮用户消息原文)/ 调了什么工具带什么参数 / 碰了什么数据(分级)**。

**什么需求逼的?** 阶段 19 的自动摄像头是"模型看见了什么"的旁路记录,它回答不了审计的问题:某次 `write_file` 是**谁**发起的?**为什么**这一轮会去调它?碰的是用户文件还是 microVM 内部?出了事倒查,这五样缺一不可。

**解决了什么麻烦?** 阶段 31 的"审计复盘"攻击(注入得手后的一串动作,要能在 Langfuse 里完整回放)有了地基:每次工具调用都有一条带五要素的显式审计观测。

## 全链路一览

```
用户输入 ──→ ask():CURRENT_ROUND["why"]=本轮消息(以何理由)
                │
                ▼ 先立 trace 壳(v4 上下文不自动传播,谁先立谁当根)
        with start_as_current_observation(name="cli-round", as_type="chain",
                                          metadata={audit.when, audit.why})
                │
                ▼ ReAct 循环(CallbackHandler 尊重环境上下文,自动归队)
        模型发起工具调用 ──→ 审计中间件(wrap_tool_call,最外层)
                │                 工具真实执行后,旁路记一条观测:
                │                 name=audit:<工具名> as_type=tool
                │                 metadata = {audit.who, audit.when,
                │                             audit.why, audit.params,
                │                             audit.data_class}
                ▼
        结果 → 护栏(L2)→ 回喂模型        flush() 进程退出前全量上报
```

一个真实踩坑:初版没立 `cli-round` 壳,审计观测落成了**独立根观测**——UI 里它是单独一条 trace,和 agent trace 割裂(实测发现于用户 UI 验证)。修复就是上面那层壳:v4 的 CallbackHandler 其实尊重环境上下文,壳一立,模型 generation、工具 span、审计观测全部归进同一条 trace。

数据分级表(`TOOL_DATA_CLASS`)是审计的"词典":read_file=workspace 用户文件(读)、run_command=一次性 microVM 内部(宿主不可见)、http_post=出网请求(白名单域名,可含凭证占位符)……新工具进来必须先在这登记碰的是什么数据。

## 跟着数据走:一次 list_dir 的审计全程

CLI 实测"看看 workspace 目录里有什么文件"→ 模型调 `list_dir` → 退出时 flush:

- Langfuse 库里出现观测 `audit:list_dir`(type=TOOL)
- 写端字节级验证(见下面的坑):OTLP 载荷里 `audit.who=cli-session`、`audit.when=ISO 时间戳`、`audit.why=看看 workspace 目录里有什么文件`、`audit.params={"path": ...}`、`audit.data_class=workspace 目录清单` 全部在案

## 新技术点:Langfuse v4 的 OTel 上下文(和它的坑)

- **名字**:langfuse 4.x 基于 OpenTelemetry span;`start_as_current_observation(name, as_type, input, metadata)` 建观测,`as_type` 原生支持 `"tool"`
- **坑(实测)**:①4.15 的 `CallbackHandler` 只收 `(public_key, trace_context)`,老教程的 `user_id/session_id` 参数没了;②自托管实例是 **events-only 模式**,老读端点(`api.trace.list`、`legacy.*`)全部 404;③SDK 读 API `observations.get_many` **不回传 input/metadata**(连刚写入的探针都读不回)——读路径降级,不是写丢了
- **验证怎么做的**:OTLP 出网捕获——本地起收包器,把 `LANGFUSE_BASE_URL` 指过去跑一轮,直接检查 SDK 发出的字节。写端五字段全在,等于证明存储里有(UI 从 blob 水合后可见)
- **教训**:观测系统升级会动读路径;审计的验证不能只依赖平台 API,能从"发出的字节"层面取证最稳

## 关键顿悟

- **审计和观测是两种记录**:观测记"发生了什么"(摄像头自动就有),审计记"事后追责要什么"(五要素,得自己钉)。前者帮调试,后者帮复盘,别混为一谈。
- **"以何理由"要引用原话**:审计里写"用户发起了请求"没用,要把本轮用户消息原文带上——倒查时人对的是原话,不是你的转述。
- **中间件是最小侵入的审计位**:wrap_tool_call 挂在最外层,工具执行完补一条记录,业务代码零改动——和护栏同一个挂法,安全横切面全都长在这里。
