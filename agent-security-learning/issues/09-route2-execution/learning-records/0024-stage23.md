# 0024 阶段 23:fetch 进 microVM + 出网白名单

**学了什么**:microsandbox 网络策略 API(`Network`/`NetworkPolicy`/`NetworkProfile`/`Destination`)的真实行为边界;SSRF 防御的两层落法——工具层域名白名单 fail closed(VM 都不拉起)+ 网络层 `from_profiles(PUBLIC)` 私网默认拒;以及"文档语义 ≠ beta 实况,探针矩阵才是真相"。

**过程**:
1. 重写 `mcp_servers/fetch_server.py`(27 行 → 72 行):`http_get`/`http_post` 改 async,`_gate()` 白名单闸(scheme 限 http/https、host 精确在 `ALLOWED_DOMAINS`,不过连 VM 都不拉),`Sandbox.create(network=Network.from_profiles(PUBLIC))` + VM 内 curl(`-w` 追加状态码标记,URL/body 经 shlex 转义);**去掉了 -L**——重定向是白名单后门
2. 顺手修掉阶段 3 遗留:`agent.py` 的 `/tools` `/call` 原来只连 filesystem_server(硬编码),改为 `ALL_SERVERS` 名单 + `call_tool_any`(问遍名单谁认识谁执行);实测 `/call run_command` → `Linux 6.12.99`
3. 注释轮换:fetch_server 头部"阶段 5 故意裸奔"换成阶段 23 两层防御注释;agent.py BANNER/docstring 同步
4. 验证:MCP stdio 五用例(httpbin GET/POST 200、example.com/192.168.1.1/file 协议全拒)3.5 秒;网络层兜底单独实证——PUBLIC profile 下 VM 内裸跑 curl,192.168.1.1/10.0.0.1/169.254.169.254/127.0.0.1 全部 exit 7

**卡在哪**(本阶段重头戏,六轮探针矩阵,详见 lesson 0020 表格):
- 规则级域名白名单(`Rule.allow(destination=Destination.domain(...))`)在 SDK 0.6.16 实测不可用:custom 策略下 VM 内 DNS 全死(default_egress=ALLOW 也死),唯一让 DNS 活的是策略含 **public 组放行**——fake-IP DNS 代理(返回 198.18.x.x)只随 PUBLIC profile 装配,而它一启动公网全开,domain 规则成摆设
- `deny_domains` 是例外,真的在 DNS 层 NXDOMAIN(P3 实测),但那是黑名单语义
- 本机宿主 DNS 是 fake-IP 代理(Clash 系),"宿主解析真 IP + curl --resolve 钉管道"方案也作废(解析出来就是 198.18.x.x)
- 不硬撑,按纪律定型为两层防御;SDK 修复 domain 规则后可把工具层闸下沉到网络层

**结论**:执行面第二个工具迁移完成,缺口 1(SSRF/egress)核销:白名单外域名工具层拒、内网/元数据网络层拒。接口变化仅一处:不再跟随重定向(原 httpx follow_redirects=True)。fetch 白名单初值只有 httpbin.org,加域名改 `ALLOWED_DOMAINS` 元组即可。
