# 0027 阶段 27:凭证代理 fetch 路

**学了什么**:占位符凭证分发模式——模型写 `{{SECRET:NAME}}`,策略表(域名→密钥名)决定给不给,Keychain 决定值;策略检查先于取值,子进程继承环境所以密钥值不能走环境变量;"最后一刻注入"把密钥存在时间压到单条请求。

**过程**:
1. `fetch_server.py` 增加凭证层:`CREDENTIAL_POLICY = {"httpbin.org": ("DEMO_API_KEY",)}`(与阶段 23 白名单同处);`_resolve_secrets()` 正则替换 `{{SECRET:NAME}}`,未授权/取不到 → 拒绝文案,请求不发、VM 不拉;Keychain 读取用 `security find-generic-password -s NAME -w` 子进程现取
2. Keychain 种演示密钥 `DEMO_API_KEY`(值 `demo-sk-1234567890abcdef`,假 token)
3. 注释轮换:fetch_server 头部(23→27 两层描述)、agent.py docstring/BANNER
4. 验证:MCP stdio 四用例 + CLI 真实 `/call` 链路

**卡在哪**:无硬卡点。一个设计修正:交接原案"由代理(proxy.py)替换占位符",但 fetch 的 curl 在 microVM 里发,VM 出网过不了宿主代理(阶段 23 实测 custom 策略弄死 DNS)——注入点移到 fetch_server(模型外分发进程,白名单同处),LLM 路不动。另外注意:不存在的密钥名也报"未授权"(策略检查先于存在性查询),这是有意的——不向调用方泄露 Keychain 里有哪些名字。

**microsandbox per-domain secret 对照笔记(三行,交接指定动作)**:
1. SDK 内建:`Sandbox.create(secrets=[Secret.env(env_var="X", value=..., allow_hosts=("api.example.com",))], on_secret_violation=BLOCK_AND_LOG)`——值由宿主拉 VM 时塞入,VM 内进程按环境变量名用,网关按目标域名放行,违规阻断并记日志(types.py SecretEntry/Secret,`_microsandbox.pyi` create 的 secrets 参数)。
2. 我们的手写版:思想一致(按域名授权+最后一刻注入+违规 fail closed),差异在注入点位置——SDK 版在 VM 边界,手写版在宿主分发进程;且 SDK 版仍要求调用方交明文 value,"值从哪来"还是得自己接 Keychain,等于只省了正则替换几行,不够抵迁移成本。
3. 路线 3 预演:LLM 路(proxy.py)和 fetch 路(fetch_server)现在是两个策略点;生产形态应收进同一个网关组件——这正是路线 3 MCP 网关的动机之一。

**结论**:两次凭证分发实测通过(httpbin 回显真值;CLI /call 同样通过),fail closed 两例通过。至此"密钥不可见"攻击(阶段 31)的三条可见面全部封死:LLM key 在代理进程、fetch 密钥在 Keychain 按需取、Agent/模型上下文只有占位符。演示密钥留在 Keychain(service=DEMO_API_KEY,值为假 token),可 `security delete-generic-password -s DEMO_API_KEY` 清除。
