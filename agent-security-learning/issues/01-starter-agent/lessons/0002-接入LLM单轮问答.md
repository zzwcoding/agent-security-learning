# 阶段 2:接入 LLM 单轮问答

## 一、三问(阶段动机)

**这一阶段是干嘛的**:把阶段 1 回声循环里"处理"那一环,从 f-string 换成一次真实的 LLM 调用。

**因为什么需求需要这么设计**:Agent 的一切能力都源于"能问模型"。但一上来就连工具一起接,链路里会同时出现 LLM、MCP、LangGraph 三个新东西,出问题无法定位。所以先只接 LLM:输入 → 模型 → 回答,一次只引入一个变量。供应商用 MiniMax-M2——实测 Keychain 里 `kimi` 条目是 OAuth token(只能给 Kimi Code 用),`api.moonshot.cn` 直接拒;`minimax` 是标准 API key,一次调通。

**解决了什么问题**:确立了"OpenAI 兼容协议 + 环境变量注入"的接入形态——换供应商只改三个环境变量,代码一行不动;同时确立密钥纪律:真 key 只存在于 Keychain 和进程环境变量里,磁盘上不落明文。

## 二、全链路一览

```
终端输入
   │
   ▼
agent.py 主循环
   │  组装 [SystemMessage, HumanMessage]   ← 每轮新构造,不带历史
   ▼
ChatOpenAI.invoke()
   │  HTTP POST {base_url}/chat/completions
   │  Header: Authorization: Bearer $LLM_API_KEY ←── agent-key 从 Keychain 取出,
   ▼                                                   run-with-keychain.sh 注入环境变量
MiniMax API → 模型生成
   │
   ▼
reply.content → print 到终端
```

## 三、跟着数据走 3 步

1. **组装消息**:你输入"用一句话解释什么是 MCP",代码把它包成 `HumanMessage`,前面垫一条 `SystemMessage("你是一个简洁的中文助手。")`,组成一个**两条消息的列表**。OpenAI 协议里对话就是一个 JSON 数组:`[{"role":"system",...},{"role":"user",...}]`,LangChain 的 Message 对象只是它的 Python 包装。
2. **发 HTTP 请求**:`llm.invoke(...)` 本质是一次 `POST {LLM_BASE_URL}/chat/completions`,body 里带 `model` 和 `messages`,Header 里带 `Authorization: Bearer <key>`。LangChain 帮你做了序列化、重试、响应解析。
3. **取回答**:响应 JSON 里 `choices[0].message.content` 就是回答,LangChain 解析成 `AIMessage`,我们打印它的 `.content`。MiniMax-M2 是推理模型,思考过程以 `<think>...</think>` 包在 content 里——这是供应商的格式怪癖,后面 Agent 循环里不用管它,但眼睛要认得。

**验证单轮无记忆**:连问"它叫什么名字",模型不知道"它"指谁——因为每轮消息列表都是新构造的。这不是 bug,是阶段 6 要解决的问题,现在先亲手感受到"历史不是免费的"。

## 四、新技术点四要素

### OpenAI 兼容协议(OpenAI-compatible API)

- **名字**:OpenAI 兼容接口,生态归属:事实行业标准,MiniMax / Moonshot / DeepSeek / 通义等都提供
- **作用**:解决"换供应商就要重写代码"的问题。一套 API 形状(`/chat/completions` 端点 + messages 数组 + Bearer 鉴权),所有兼容供应商通用;和供应商私有 SDK 的区别:不锁定生态
- **参数**:三要素——`base_url`(请求发给谁)、`api_key`(身份凭证)、`model`(用哪个模型)。选型时:国内直连选国内端点,要工具调用能力需确认模型支持 `tool_calls`(MiniMax-M2、Kimi-K2 都支持)
- **用法**:本项目挂载点 `config.py` 的三个 `LLM_*` 环境变量 + `scripts/run-with-keychain.sh` 的 case 分支(加新供应商=加一个分支)

### ChatOpenAI(LangChain 的聊天模型封装)

- **名字**:`ChatOpenAI`,出自 `langchain-openai` 包(v1.6.0)
- **作用**:把上述 HTTP 调用封装成一个对象;统一接口意味着以后接 LangGraph、流式输出、工具调用都不用换类。和裸 `requests.post` 的区别:少写序列化/解析,且消息类型带 role 校验
- **参数**:`ChatOpenAI(base_url=, api_key=, model=)`;常用还有 `temperature`(0=确定性,默认随供应商)、`max_tokens`(不设=用到完)。本阶段保持默认,需要时再调
- **用法**:

  ```python
  llm = ChatOpenAI(base_url=..., api_key=..., model=...)
  reply = llm.invoke([SystemMessage("..."), HumanMessage("...")])
  reply.content  # str
  ```

  挂载点 `agent.py:24`(`llm = ChatOpenAI(...)`)

## 五、关键顿悟

- **对话即数组**:发给模型的永远是一个完整的消息数组,模型本身没有"会话"概念——你觉得它"记得",是因为客户端把历史重新发了一遍。想通这点,阶段 6 的对话历史就是顺水推舟。
- **key 的旅程比 key 本身重要**:Keychain → `agent-key` 读出 → 环境变量 → 进程内存 → HTTP Header,全程不落磁盘。后面的假密钥战利品(阶段 6)正是反向利用这个常识:写在 `.env` 里的 key 等于送给人看。
- **先实测再选型**:`kimi` key 认证失败是 30 秒 curl 试出来的,不是猜的。供应商接入类决策,永远先跑通最小请求再写代码。
