## 3. 跟着数据走:`Bearer sk-proj-...` 的双规则争夺

样本 1 的请求头(`samples.py:29`):

```
headers: {"Authorization": "Bearer sk-proj-ABCD1234...mnop3456", ...}
```

**两条规则同时看中了同一个值:**

- `bearer_token` 规则(regex_sanitizer.py:47):`(?i)\bBearer\s+(...)` ——捕获组抓到 `sk-proj-...`,想打上 `[REDACTED_BEARER_TOKEN]`
- `api_key` 规则(regex_sanitizer.py:44):`\bsk-[A-Za-z0-9_-]{20,}\b` ——整段命中,想打上 `[REDACTED_API_KEY]`

裁决过程(sanitize 里):api_key 在规则表**第 8 位**,bearer_token 在第 9 位——按 (优先级, 位置) 排序后 api_key 先到,占住了这段 span;bearer_token 轮到时发现区间已被占,弃权。最终:

```
Authorization": "Bearer [REDACTED_API_KEY]"
```

为什么这个结果是**对的**?设计哲学是"**具体优先,通用兜底**":`sk-` 开头是 OpenAI 风格密钥的专属格式,识别得又准又具体;`Bearer X` 只是"这后面有个令牌"的宽泛描述。专属规则排前面赢了,占位符标签也更精确。同理,样本 3 的 `token: xoxb-...`——兜底规则 secret_assignment(`token:` 赋值)想抓整串,但专属的 slack_token 排在它前面,`xoxb-` 值被 Slack 规则收走,**键名 `token:` 原样保留**。

## 4. 新技术点:Python re 的捕获组与 span

- **名字**:捕获组(capturing group),`re` 标准库;本项目里是规则表的第 4 列 `group`。
- **作用**:把"命中的一段"和"要脱的一小节"分开。比喻:安检翻包,整箱行李是匹配范围,只没收刀(捕获组),箱子和其他物品(键名、前缀)原样还你。
- **参数**:`m.span(g)` 返回第 g 组的 `(start, end)`;组没参与匹配时返回 `(-1, -1)`(所以 sanitize 里有 `if m.span(g)[0] >= 0` 的过滤,regex_sanitizer.py:65)。组号 0 = 整个匹配;`(?i)` 是忽略大小写;`\b` 是词边界,防 `xsk-xxx` 这种粘连误匹配。
- **用法**:最典型的是连接串规则(regex_sanitizer.py:34):

  ```python
  re.compile(r"://[^\s:/@]*:([^\s@]+)@")   # 组 1 = 口令本身
  # postgres://admin:S3cr3t_P4ssw0rd@db.internal:5432/prod
  #              ^^^^^^^^^^^^^^ 只脱这里,admin 和主机名保留
  ```

  兜底规则 secret_assignment 有三个可选写法(双引号值/单引号值/裸值),所以 group 是元组 `(1, 2, 3)`——哪组参与了用哪组(regex_sanitizer.py:55-57)。这就是"**键名是结构,值才是秘密**"的落地。

## 5. 关键顿悟

- **占位符带类别标签,是给排障的人留的门牌。** `session_jwt: [REDACTED_JWT]` 一眼知道"这里曾是个 JWT";全换成无差别 `[REDACTED]`,日志就只剩"这里有个秘密"的废话。**脱敏不该摧毁可排障性**。
- **规则表顺序就是优先级,而且要刻意安排:格式具体的规则在前,行为宽泛的兜底在后。** 顺序错了,兜底规则会把专属规则的地盘抢走,占位符标签全变糊。
- **0 命中不等于引擎坏了。** 本次运行 PII 类 3 条 + 负例 3 条全部原样通过——PII 规则还没写(阶段 4),负例则证明密钥类规则没碰它们。**看到引擎的能力边界,才好安排下一阶段**。
