# 0009 — 阶段 9:混合管道(regex 先行,LLM 脱敏后补扫)

> 本阶段代码:`pipeline.py`(新)、`llm_engine.py`(schema 加 type enum)、`main.py`(换成管道路径表)。
> 本阶段发生了一次**路线中途修正**,是整个复刻到目前为止最重要的一次"实测推翻设计"。

## 1. 三问:这一阶段是干嘛的?

**位置感**:

```
✅ 1-8 规则引擎 / LLM 引擎 / 验收闸  ✅ 9 管道   ← 你在这里
⬜ 10 campaign 三引擎跑分 → 11 对照收官
```

- **干嘛的?** 把两台发动机接成一条流水线:regex 先扫,LLM 补扫,验收闸把关,输出一份合并的脱敏文本。
- **什么需求逼的?** 单引擎都有死穴:regex 快但抓不住住址;LLM 抓得住住址但慢、会漏、value 不干净。"选一个引擎"是伪命题,问题是**怎么排班**。
- **解决什么麻烦?** 排班方案本身也要被实测检验。本阶段第一版排班("regex 零命中才叫 LLM",为了省 LLM 的钱)被一条捣乱样本当场推翻——见 §3。

## 2. 全链路一览

```
日志文本 ──► ① regex_sanitizer.sanitize(微秒级,格式型全脱,span 精确)
              │ 脱敏后的文本(占位符已就位)
              ▼
            ② llm_engine.detect_pii(秒级,在脱敏后文本上找语义盲区:住址/口令/病历…)
              │ 占位符污染防御:模型把 [REDACTED_*] 检出来的,一律不收
              ▼
            ③ accept_and_redact(阶段 8 的验收闸,过闸项顺序回填)
              ▼
            合并脱敏文本 + 两段引擎的命中/耗时统计
```

为什么 LLM 跑在**脱敏后**的文本上?两个好处:① 它不会把 regex 已经精确脱掉的值再检一遍(检出的只剩 regex 抓不住的);② 我们的回填是**按文本顺序逐层替换**,不需要像参考项目那样把 LLM 的 span 映射回原文坐标——实现更简,语义等价。

## 3. 跟着数据走:一条捣乱样本推翻了第一版设计

第一版管道按开工包写的策略:"**regex 零命中才进 LLM**"(省 LLM 成本)。拿这条样本一测:

```
客服记录:请把补办证件寄到 上海市浦东新区桂花路333弄12号502,收件人电话 13812345678。
```

结果:regex 命中 1 处(手机号)→ **LLM 没跑 → 住址原样留在文本里**。

手机号(regex 的地盘)和住址(LLM 的地盘)住在**同一条日志**里,第一版排班就漏了第二种敏感。"省钱的条件触发"在安全场景是不成立的——**脱敏系统保完备优先于省钱**,漏一条住址是事故,多花两秒不是。于是改成参考项目的形态:**LLM 在 regex 脱敏后的文本上总跑一遍**,专找 regex 抓不住的。回归测试:

```
客服记录:请把补办证件寄到 [REDACTED_住址],收件人电话 [REDACTED_PHONE]。
```

两个类别都脱掉,而且 enum 生效后占位符类型准确(不再是阶段 8 那个无区分度的 `[REDACTED_敏感值]`)。

**教训**:阶段路线里写的策略也要过考卷。设计时觉得"显然省钱"的条件触发,实测一条混合样本就现原形——**排班策略要拿最刁的组合样本考,不是拿各自的单类样本考**。

## 4. 新技术点:schema 的 enum 枚举约束

- **名字**:`enum`(JSON Schema 关键字),在 Ollama 结构化输出里生效于解码层。
- **作用**:把"type 字段随便写"变成"type 只能从名单里选"。阶段 8 的挂账(0.6B 全输出"敏感值",占位符没有区分度)由此修掉——模型生成 type 时,不合名单的 token 直接被屏蔽,只能落在 `llm_engine.py:33` 的 12 个中文类别里。
- **参数**:`{"type": "string", "enum": PII_TYPES}`;名单即 `llm_engine.py:31` 的 `PII_TYPES`(身份证号/社保号/银行卡号/护照号/驾照号/病历号/诊断/治疗/住址/口令/金融PIN/生物特征)。注意**故意不含**手机号/邮箱/卡号这些格式型类别——那是 regex 的地盘,写了反而诱导 LLM 越界抢活。
- **用法**:`PII_SCHEMA` 的 items 定义里(`llm_engine.py:47`)。名单、SYSTEM_PROMPT 里的类别清单、PII_TYPES 三处保持一致——改一处必改三处(这个重复可以用代码生成消除,留给读者当练习)。

## 5. 关键顿悟

- **"便宜确定的先走"没错,错的是"贵的只在便宜的一无所获时才上"。** 正确的排班是**补位不替补**:regex 打完,LLM 永远补扫一遍它擅长的类别——成本每条多两秒,换来混合样本不漏。
- **两个引擎都会误报,但错的类别不同**:regex 错在形状巧合(latency 那串数字),LLM 错在语义猜疑(干净日志时而多检出、非确定性地时有时无)。谁也当不了对方的裁判——阶段 10 用 gold 基准量化,不靠互相兜底。
- **占位符也是文本,也要防污染。** LLM 补扫的是"已脱敏文本",它可能把 `[REDACTED_PHONE]` 本身检出来当敏感值——过子串闸还真能过(它确实在文本里)。管道里加了一行防御(`pipeline.py:26`):以 `[REDACTED` 开头的一律不收。
