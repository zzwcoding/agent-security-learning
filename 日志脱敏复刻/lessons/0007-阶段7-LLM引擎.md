## 3. 跟着数据走:一条日志的两种引擎口径

同一条样本 7(支付日志),两个引擎的答案并排看:

- **规则引擎**:2 项,干净的值——`4111 1111 1111 1111`(Luhn 过)、`123-45-6789`。键名 `card:`/`holder_ssn:` 保留。
- **LLM 引擎**:2 项,**但 value 不干净**——`'card: 4111 1111 1111 1111'`(键名混进了值)和 `'holder_ssn: 123-45-6789 /think'`(键名 + 还混进了思考标签碎片 `/think`,这已经不是原文的子串了!)。

再看样本 6(CRM 回显):规则 2 项,LLM **0 项**——它思考了 384 个字,最后说没有。0.6B 的召回就是这么不稳定。

**这不是失败,这是画像**:0.6B 能圈出"这附近有高敏",但①召回不稳(会漏)②value 边界不净(带前缀、带垃圾)。所以阶段 8 的结论已经被预告:**模型输出永远不能直接信任,每一个回填都要过确定性验收**。

然后是 LLM 的主场实测(`llm_engine.py` 的 SYSTEM_PROMPT 里的类别,规则引擎一个都覆盖不了):

```
输入:客服记录:请把补办证件寄到 上海市浦东新区桂花路333弄12号502,收件人电话 13812345678。
输出:敏感值 = '上海市浦东新区桂花路333弄12号502'   ← 住址,正则写不出,LLM 抓到了
      敏感值 = '13812345678'
```

**规则引擎在住址这个类别上永远 0 分;LLM 能拿分。** 这就是第二台发动机存在的全部理由。

## 4. 新技术点:format schema 与 TTFT

- **名字**:Ollama 的结构化输出(structured outputs)——请求里 `"format": <JSON Schema>`;TTFT(Time To First Token,首 token 延迟)。
- **作用**:`format` 在**解码层**约束生成——模型每吐一个 token,Ollama 只放行能让 JSON 保持 schema 合法的那些,非法的直接被屏蔽。这和"提示词里求它输出 JSON"是两个位面的约束:提示词是**劝**,format 是**闸**。阶段 6 的 markdown 围栏问题,在这里被物理消灭(`llm_engine.py:68`)。
- **参数**:`options.temperature`(0.1,检测任务要稳)、`options.seed`(42,固定随机种子让结果可复现——阶段 10 基准的前提)、`stream:true`(逐 token)。
- **用法**:TTFT 的测法(`llm_engine.py:75-90`)——请求发出记 `started`,流里第一个含 thinking/content 的 chunk 到达再记一次,差值就是 TTFT。本次实测:**冷启动 1717ms**(含把模型从硬盘加载进 GPU)→ 热了以后 58~131ms。端侧延迟的大头是冷加载,不是推理。

## 5. 关键顿悟

- **"逐字摘抄"必须写进 prompt,而且光写进去还不够。** prompt 里已经三令五申 value 逐字复制,0.6B 照样给你 `card: 4111...`。真正的防线在下游验收(阶段 8)——**对模型的正确期待是"大致可靠",工程要按"必然出错"设计**。
- **冷加载支配端侧延迟。** 1717ms vs 58ms:第一次贵在把 500MB 模型搬进显存。这也解释了常驻服务的价值(Ollama 默认 5 分钟不请求就卸载)和阶段 10 基准要先"暖机"的原因。
- **两台发动机的地盘真的不同。** 同一文本:规则引擎抓格式(准、稳、微秒),LLM 抓语义(住址能抓、格式反而不稳)。谁也不取代谁——阶段 9 的管道分工和阶段 10 的数据,今天都见到了影子。
