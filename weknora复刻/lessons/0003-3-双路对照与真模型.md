## 1. 三问（阶段动机）

**这一步干嘛？** 两件事：①试验台升级成双路对照（BM25 和向量并排，同一次查询两种结果一眼对比）；②接上**真模型**，让 kitty→cat 的语义魔法在你的浏览器里发生。

**为什么这一步出了个真事故？** 真 GLM 首跑时 embedding-3 返回 429"余额不足"。这反而是最好的教学现场：chat 和 embedding 是**两条独立的付费路**，而且换供应商只动了 gateway 一个模块——"唯一出网口"第一次实战分红（全程记录 ADR 0003）。

## 2. 全链路一览（现在的供应商格局）

```
chat  ──► GLM glm-4-flash（免费档，已实测通）
embed ──► MiniMax embo-01（1536 维，已实测：cos(kitty,cat)=0.74 ≫ cos(kitty,stock)=0.25）
fake  ──► CI/测试专用
```

三路在 `llm_gateway` 里同接口，配置全走环境变量：`run-with-keychain.sh` 启动时从 Keychain 注入两把 key。

## 3. 跟着数据走（页面上的一次双路查询）

1. 你用 `bash scripts/run-with-keychain.sh` 起服务（key 从 Keychain 注入，不落盘）。
2. 上传一份英文 txt（比如写几句 "The cat sits on the mat." 之类）。
3. 点"🔄 建/重建向量索引"→ `index_chunks` 把卡片们发给 MiniMax，拿回 1536 维向量存进 SQLite。
4. 查询框输入 **kitty** → 左栏 BM25：命中 0（库里没有这个词，倒排说实话）；右栏向量：**cat 那张卡片排在第一**，得分约 0.7+。
5. 同屏对照就是书 3.2 两节的核心论点：**关键词路精确但死板，语义路灵活但模糊**——所以阶段 4 要把它们融合。

## 4. 新技术点四要素

### Duck typing 响应解析（设计手法，不是库）

- **名字**：鸭子类型——"叫起来像鸭子就是鸭子"。
- **作用**：MiniMax 响应是 `{"vectors": [...]}`，OpenAI 兼容是 `{"data": [{"embedding": ...}]}`。不判供应商名，直接看响应里有哪个键（`if "vectors" in data`）——换第三家供应商也不用改代码。
- **本项目用在哪**：`llm_gateway.embed`（`llm_gateway/__init__.py`）。

### MiniMax embo-01 的脾气（供应商差异实录）

- 端点 `https://api.minimaxi.com/v1/embeddings`，模型名是 **embo-01（字母 o）** 不是 emb0-01（数字 0）——打错直接不认（社区踩坑实录）。
- 载荷要 `type: "db"`（存文档）或 `"query"`（查询）——**非对称嵌入**：同一段文字，存的时候和查的时候算的向量不一样（检索模型的小优化）。我们统一用 db（有意简化，对账报告交代）。
- 1536 维；key 直接 Bearer，不用老版 GroupId（实测确认）。

## 5. 关键顿悟

- **付费墙是真实世界的第一课**：设计时的"智谱全包"撞上"embedding 要充值"，15 分钟换到 MiniMax——靠的不是运气，是 gateway 收口 + 配置面外置。架构的回报总在意外时刻到账。
- **fake / 真 API 的验证分工**：fake 证明"形状与排序逻辑对"（CI 里跑一万次），真 API 证明"语义对"（你亲手跑一次）。两层都不可少。
- **向量检索没有"零命中"**（2026-09-10 用户实测发现）：库里只有一张 cat 卡片时，查任何词向量路都返回它——余弦永远算得出分、永远有第一名，哪怕第一名也不怎么近。BM25 能说"没这个词"（倒排查无此人），向量只会说"它是最近的"。**想看两路的性格差异，库至少要有 2-3 份不同内容的文档**——一张卡片时两路都发挥不出来。这也是阶段 4 融合时"该信谁"的深层动机。
- **换 embedding 供应商 = 必须重建索引**：不同模型的向量空间不可比（WeKnora 甚至按 embedding 模型身份分组拒绝混检）。所以页面上的按钮叫"建/**重建**"。
