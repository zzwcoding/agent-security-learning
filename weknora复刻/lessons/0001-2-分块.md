## 1. 三问（阶段动机）

**这一步干嘛？** 给 ingest 模块生命：读 txt → 切成知识卡片 → 存进步 1.1 建好的账本。从此"文档进来变成卡片"这条流水线真的转起来了。

**为什么不能整篇文档直接用？** 书 3.2 原文（chapter3.md:272）：

> "分块必不可少，原因有二。其一，嵌入模型对输入长度有限制，且一整篇文档只压缩成一个向量时，多个主题混在一起，向量无法精确表达任何一个……其二，检索的目标是只把相关的那部分注入上下文，片段太大会连带引入大量无关内容，浪费窗口、稀释注意力。"

大白话：embedding 模型是照相机，一次只能拍清一张小照片；整本书塞进一张照片全糊了。而且检索时你只需要相关那一页，把整本书糊在 LLM 脸上既贵又干扰它。

**为什么用"固定大小硬切"这种最笨的策略？** 书 3.2 给了三类策略，原文说固定切分"实现简单、结果可预测，但完全无视文档结构"（chapter3.md:276）。第一口先吃最简单的——跑通流水线；书里说块大小"实践中常见的起点是每块 256-1024 token、相邻块重叠 10%-20%"（chapter3.md:282），我们取 512，重叠留到阶段 5。这正是 WeKnora 的切法思路（`knowledge_process.go:283 processChunks` 里也是固定窗口+重叠）。

## 2. 全链路一览

```
fixture_2000tokens.txt ──► parse_file ──► chunk_text(512) ──► replace_chunks ──► SQLite chunk 表
（2000 字符的原料）        （读文件+看门）   （剪成 4 张卡片）     （先删后插入账）     （唯一事实源）
                              │                                        ▲
                              └─ 不是 txt？抛 ParseError ──► 文档置 failed 态（坏鱼不搅汤）
```

## 3. 跟着数据走（真实 fixture 走一遍）

1. **原料**：`tests/fixtures/fixture_2000tokens.txt`，恰好 2000 字符（内容是同一句"知识库把文档切成小块……"循环填满）。
2. **看门**：`parse_file` 先看扩展名——`.txt` 放行，其他（比如 `.bin`）当场抛 `ParseError`；再 `read_text(utf-8)` 读全文。
3. **剪卡片**：`chunk_text(text, 512)` 一行切片表达式，每 512 字符剪一刀：2000 = 512×3 + 464，得 **4 张卡片**，序位 0/1/2/3。（小插曲：这步的测试我第一版把末块算成 368，跑测试被抓出来——2000-1536=464。测试先行抓的就是这种想当然。）
4. **入账**：每张卡片包成 `Chunk(doc_id, seq, text)`，`replace_chunks` 先删后插写进账本。
5. **捣乱输入**：`fixture_corrupted.bin`（二进制垃圾）进来 → `parse_file` 抛 `ParseError` → `ingest_file` 把文档置 `failed` 态再抛 → **后面好文档照常入库**（`test_parse_failure_marks_document_failed` 验证）。一条坏鱼不许搅一锅汤（PRD §7-⑨）。
6. **重建**：`reingest_document(doc_id)` 按登记的路径重读原文重切——账本里永远是4 张卡，不会变 8 张（`test_reingest_via_ingest_keeps_count`）。

## 4. 新技术点四要素

### 切片（slice）与列表推导——Python 内置

- **名字**：序列切片 `seq[start:end]` + 列表推导式。
- **作用**：`text[i:i+512]` 表示"从第 i 个字符取到第 i+512 个"。比喻：**裁纸刀**——`range(0, len(text), 512)` 是每隔 512 字符画一条裁切线，列表推导把每条线裁下来的纸收集成一摞。
- **参数**：切片越界不报错（`text[1536:2048]` 在 2000 字符的文本上自动裁到末尾得 464 字符）——这个"宽容"特性正好让末块不用特判。
- **用法**：`ingest/__init__.py` `chunk_text` 一行：`[text[i:i+size] for i in range(0, len(text), size)]`。

### pytest 的 `pytest.raises`——异常断言

- **名字**：`pytest.raises`，pytest 的上下文管理器。
- **作用**：断言"这段代码必须抛这个异常"——不抛反而算测试失败。比喻：**消防演习查岗**：警铃（坏文件）响了，必须看到喷淋（ParseError）启动，没启动就是事故。
- **用法**：`with pytest.raises(ParseError): ingest.ingest_file(...)`（`tests/test_ingest_chunking.py` `test_parse_failure_marks_document_failed`）。

## 5. 关键顿悟

- **分块是"索引期做加法"的第一刀**：书里反复强调（3.5 上下文感知检索也是同一个哲学），离线索引期多做的功课，都会变成查询期的命中率。切块策略选笨的先跑通，是对的做法——但记住书 3.2 的伏笔（chapter3.md:284）："分块都会切断片段与其原始上下文的联系"，这个债阶段 5（上下文增强）来还。
- **失败要留痕，不要消失**：解析失败的文档不是"没入库"，而是"入库了、状态 failed"。这样页面能告诉你哪份文件坏了（步 1.3 就能在列表里看到），而不是静默丢失——可观察性从第一天就设计上。
- **token 我们用字符近似**：这是本项目的有意简化（真 WeKnora 用分词器算 token）。中文场景 1 字符≈1 token 误差不大；英文场景 1 token≈4 字符。差距已记，收官对账报告会交代。
