## 1. 三问（阶段动机）

**这一步干嘛？** 给系统装上"橱窗"：Streamlit 入库页——上传 txt、看文档列表、点开看 chunk 卡片。前两步建的东西（账本、分块）之前只能在测试里看见，现在在浏览器里看见。

**为什么非要有个页面？** 学习纪律：每个阶段都要有**可观察变化**。看不到的系统等于不存在的系统——页面上"卡片列表真的多了一行"，比一百行日志都有说服力。

**为什么 webui 只读 store、写走 ingest？** 这是模块卡上的分工：页面是"表现层"，业务逻辑一行都不许住在这里。比喻：页面是**餐厅的点餐屏**——你点什么它传给后厨（ingest），屏上显示的库存（列表）直接读仓库账本（store），但屏幕自己不炒菜。

## 2. 全链路一览（阶段 1 完整闭环，至此闭合）

```
浏览器上传 txt ──► 落盘 data/uploads/ ──► ingest.ingest_file ──► chunk 表 ──► 页面列表展示
   （你点按钮）      （webui 做的唯一杂活）   （解析→分块→入账）    （账本）     （你再点开看卡片）
```

## 3. 跟着数据走（你在页面上的每次点击）

1. **起服务**：`streamlit run main.py` → 执行 `webui.main()` → `store.init_db("data/app.db")` 建/连账本。
2. **选知识库**：页面调 `store.list_kbs()`（只读）；没有就提示先跑种子脚本——`scripts/seed_kb.py` 是 KB 创建的唯一入口（页面不许写 store，这是卡上的约定）。
3. **上传**：选一份 txt 点"入库" → 文件先落盘 `data/uploads/`（webui 唯一的杂活）→ `ingest.ingest_file(kb_id, path)` → 成功显示 doc_id；若传了坏文件，页面红字报 ParseError，文档列表里它挂着 ❌ failed。
4. **看列表**：`store.list_documents(kb_id)` → 每行 ✅/❌ + 文件名 + 状态。
5. **看卡片**：选一份文档 → `store.list_chunks(doc_id)` → 每张卡片一个可展开折叠块，标着序位和字符数。

## 4. 新技术点四要素

### Streamlit（技术栈点名框架，本阶段真引入）

- **名字**：Streamlit（开源 Python Web 应用框架）。
- **作用**：用纯 Python 写网页，不碰 HTML/JS。比喻：**会自己刷新的告示板**——你写"贴这张纸"（`st.write`），它负责把纸贴到浏览器上。
- **参数/用法**（本阶段用到的）：
  - `st.title/header/subheader/write`：贴标题和文字。
  - `st.file_uploader("...", type=["txt"])`：文件上传框；返回 UploadedFile（`getvalue()` 取字节），没传时是 `None`——所以代码里 `if uploaded and st.button(...)` 两个条件都要。
  - `st.selectbox(...)`、`st.button(...)`：下拉与按钮，返回被选的值/是否按下。
  - `st.expander(...)`：折叠块（卡片列表用它，不然页面太长）。
- **运行模型（最重要的一个认知）**：每次交互**整个脚本从头重跑一遍**。所以状态必须存在数据库里（我们的做法），不能存在 Python 变量里——变量每次重跑就清零了。
- **本项目用在哪**：`webui/__init__.py` 全部；入口 `main.py`（`streamlit run main.py`）。

## 5. 关键顿悟

- **页面是观察窗，不是藏逻辑的地方**：webui 里最难找的就是业务逻辑——因为一行都不许有。以后排查问题：显示错→看页面；数据错→看管线。分工清楚，bug 减半。
- **"每次交互整脚本重跑"决定状态放哪**：这是 Streamlit 最反直觉的一点。理解了它，你就明白为什么我们坚持 store 落 SQLite 而不是全局变量。
- **阶段 1 闭环的真正含义**：从这一刻起，"文档 → 卡片 → 账本 → 页面"这条流水线是真的了。后面 BM25/向量/RRF 全是给这条链加"查找"能力，地基不会再动。
