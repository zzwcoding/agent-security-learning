# soc-demo 压力测试方案（2026-09-12）

> 定位：项目做完了，回答三个问题——**这套架构的承压上限在哪？瓶颈先出现在哪个组件？防线（fail-closed）在过载下松不松？**
> 前两个是工程问题，第三个是本项目的教学卖点：INV-1 说"任何异常一律拒绝执行"，压力本身就是一种异常。
> 量级口径：这是单机演示/教学项目，目标是**找到本机拐点并讲清为什么**，不是做生产 SLO 认证。

## 一、GitHub 工具调研结论（2026-09-12）

| 工具 | 仓库 | 是什么 | 对本项目的 fit |
|---|---|---|---|
| **autocannon**（主选） | [mcollina/autocannon](https://github.com/mcollina/autocannon)（~8.5k★） | Node 写的 HTTP/1.1 压测器，wrk/wrk2 思路，CLI+编程 API 两用；作者就是 Fastify 作者 Matteo Collina | **零新运行时**：npm devDependency，脚本能直接 import，将来可包进 vitest 出趋势报告；CLI 一行流起压 |
| k6 | [grafana/k6](https://github.com/grafana/k6) | Go 引擎 + JS 脚本，thresholds/scenarios 人体工学最好 | 备选：要装 Go 二进制（brew），脚本语言 JS 但运行时独立；如果将来要复杂场景编排再上 |
| Artillery | [artilleryio/artillery](https://github.com/artilleryio/artillery) | YAML/JS 场景化压测平台，支持分布式 | 备选：YAML 场景对"多步链路"表达好，但多一层抽象；单机演示用不上分布式 |
| @fastify/under-pressure | [fastify/under-pressure](https://github.com/fastify/under-pressure) | Fastify 官方过载保护插件：监控 eventLoopDelay/heap/RSS，超阈自动 503 | **被测侧增强**：给三个 Fastify 服务装上，压测时就能观察" shedding 行为"而不是裸奔到 OOM |
| 0x / clinic.js | autocannon-ci 与 [nearform 调优指南](https://nearform.com/insights/tuning-node-js-app-performance-with-autocannon-and-0x/) | 压测 + 火焰图定位热点 | 分析阶段用：autocannon 压住的同时对 agent 进程采火焰图 |

**选型拍板：autocannon 为主 + under-pressure 上被测侧 + 0x 看火焰。** 理由一句话：Node 项目的压测器用 Node 生态原生的，依赖进 devDependencies、脚本进 `scripts/bench/`，跟现有 vitest/CI 一套纪律；k6/artillery 的场景编排能力对本项目是杀鸡用牛刀（真要用，autocannon 的 `requests`/`context` API 也够写多步链路）。

## 二、被测对象的四个"理论天花板"（压测就是去实测它们）

| # | 瓶颈点 | 理论值/机制 | 出处 |
|---|---|---|---|
| 1 | **分发循环吞吐上限** | run-dispatcher 100ms tick，若每 tick 领 1 单 → 上限 ~10 run/s；队列深了只会长延迟不会丢（`run_jobs` 落表） | `app.ts` DISPATCH_INTERVAL_MS=100 |
| 2 | **autorun 事件消费上限** | 2s tick 轮询 outbox，ingest 突发速率 > 消费速率时 cursor 滞后拉大；失败不动游标=至多延迟不丢 | `autorun.ts:234 ?? 2000` |
| 3 | **SQLite 单写者水位线** | WAL + 5s 忙等已在（`db.ts:136-137`）；写并发上来后 busy 等待会转成请求延迟，5s 兜底超时 | store/db 两处同口径 |
| 4 | **SSE 扇出预算** | 每个订阅者一个 100ms setInterval 读增量——N 个订阅者 = N 个定时器抢 agent 事件循环；eventLoopDelay 是第一个崩的指标 | `app.ts SSE_PUSH_INTERVAL_MS=100` |

外加一个 Python 侧变量：**guards 扫描是同步 await 在闸的路径上**（llm-guard+Presidio CPU 密集），它慢一拍，所有工具调用慢一拍——压测要单独给它标定 p99。

## 三、分层方案（B0→B5，每层有独立产出，可停在任何一层）

### B0 · 准备（半小时）
- 环境：compose 默认九服务 + fake LLM（零出网，结果可复现）；`data/` 清空起压；记录机器规格（chip/内存/docker version）——所有数字没机器规格就是废纸。
- 约定：每轮压测前 `docker compose restart` + 预热（低强度 30s）；同一轮内不并行跑别的压测；数字只同机比。
- 观察面**零新增**：现有 `/healthz`、`run_jobs`/`runs`/`run_events`/`audit_entries`/`event_cursors` 五张表 + SSE 流就是仪表盘，压测脚本读表出报告即可。

### B1 · 单端点微基准（autocannon 一行流，半天）
对四个热点各出一张卡（p50/p99/req/s/错误率）：
- `POST :3001/api/v1/webhooks/alerts`（真 fixture body）——ingest 验型+映射+转发
- `POST :3002/api/v1/alerts`——M2 upsert 去重路径（同 sourceRef 二连发测 201/200 两分支）
- `POST :8002/internal/mint`——HMAC 铸票（签名成本标定）
- `GET :3002/api/v1/alerts` 类读口——SQLite 读路径（WAL 下读写不互斥的实测）

命令样例：`npx autocannon -c 20 -d 30 -m POST -H content-type:application/json -b @fixtures/alerts/one.json http://127.0.0.1:3001/api/v1/webhooks/alerts`

### B2 · 链路场景（脚本 `scripts/bench/*.mjs`，一天）
- **突发**：一次性灌 100/500 条告警 → 从 runs 表/audit 量"告警到 run 拉起"的端到端延迟分布（P50/P95/P99），验证 B0 表 #2 的 cursor 滞后曲线。
- **持续流**：X alerts/s 持续 5 分钟爬坡（X=10/30/50/100）→ 找 ingest 拐点：错误率起跳的 X 是多少、outbox 积压是否收敛。
- autocannon 的 `context`/`requests` API 写多步链路（推告警→查 run→读 SSE 首帧）。

### B3 · 常驻循环水位（一天，教学价值最高的一层）
- 并发 run 爬坡（1/5/10/20/50 并发起流水线）→ `run_jobs` 队列深度时间序列 + 实测分发吞吐，对照 B0 表 #1 的 ~10 run/s 理论值。
- 队列深压时顺带测审批链：awaiting_approval 的 run 在深队列下 TTL 扫描是否还准时（派活的循环顺带扫过期卡——队列满时过期裁决会不会被饿死？）。

### B4 · SSE 扇出（半天）
- 1 个高事件率 run × N 订阅者（50/100/200）→ 量 agent 的 eventLoopDelay（装 under-pressure 后有现成指标）与订阅者滞后（Last-Event-ID 补发长度）。
- 对照实验：同样 N，换成 1s 轮询客户端——给"取餐铃 vs 轮询"一个真实数字。

### B5 · 防线在压下（半天，收官）
压力中做捣乱实验，验证过载时 fail-closed 不松动：
- guards 进程 kill/挂起 → 闸应拒绝（fail-closed）而非放行；恢复后行为。
- gateway 停 → 铸票失败路径在高压下的表现（不留"已批准无票"悬置态）。
- SQLite 压力锤：并发写 case-backend 到 busy 超时边界 → 观察 5s 忙等的延迟曲线与 503/错误面。
- 装 under-pressure 前后对照：裸奔（延迟飙升/内存涨）vs 有 shedding（503+服务存活）——这本身就是一节课。

## 四、产出物与验收

- `scripts/bench/`：B1 的命令清单 + B2-B4 的 autocannon 脚本（每个脚本自带"应看到什么"注释）。
- `docs/research/2026-09-XX-压力测试报告.md`：每层一张结果表（数字+机器规格+复现命令），拐点结论写进"瓶颈先出现在哪"。
- `lessons/` 一篇教学文：四个天花板的理论值 vs 实测值对照表 + B5 的 fail-closed 压下实验（这是"会搭更会防"的续篇）。
- 可选 CI 接入（第二期再说）：autocannon 10s×3 端点的 smoke-bench 只记趋势**不设门禁**——本机 runner 数字抖，当门禁会 flaky。

## 五、明确不做（量级裁剪）

- ❌ 分布式压测/多机发压（单机演示项目，本机拐点够用）
- ❌ 生产级 SLO 定义（99.99% 之类）——用"本机拐点+延迟分布"口径
- ❌ LLM 真出网压测（fake/stub 压确定性链路；真 key 压测烧钱且不可复现）
- ❌ 给 chroma/openfga/contextforge 三个官方件做深度调优（它们是背景板，压测只观察不改造）

## 六、执行顺序建议

B0 → B1（半天出第一批数字）→ B3（先打最可疑的天花板：分发循环）→ B2 → B4 → B5。B3 提前是因为它最可能第一个爆——100ms 单领单 tick 若实测 ~10 run/s，后面的"持续流"场景设计都要以它为分母。
