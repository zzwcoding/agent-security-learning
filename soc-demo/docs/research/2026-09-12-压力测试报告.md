## 方法（B1 轮）

- **布景**：`docker compose up -d` 默认九服务（ingest :3001 / case-backend :3002 / agent :3003 / guards :8001 / gateway :8002 / chroma / contextforge / openfga / web）；起压前四口 + guards `/healthz` 全绿。
- **清库约定**（照 0-0/教学线）：每轮前 `docker compose down → 清空 data/ → up`，SQLite 观察一律走 REST 读口，绝不从宿主开容器在写的库文件。
- **fake LLM 零出网**：`AGENT_LLM=fake`，verdict 确定性，数字可复现。
- **EVENT_DRIVEN=off 起 agent（本轮口径，偏离默认 on 的原因）**：B1 是单端点微基准，关掉 autorun 消费以隔离下游流水线——不然 ingest 卡每条告警都会拉起 run，测的就不是端点了。链路影响归 B2/B3 层再开。EVENT_DRIVEN 无公开读口可查，靠布景纪律保证。
- **限速档**：全部 autocannon `overallRate` 限速开环（250-500/s）+ connections=20（红线 ≤20）+ amount/duration 档位见脚本头注。找"错误率起跳"的爬坡拐点归 B2。
- **逐请求唯一体**：ingest/mint/upsert-new 卡走 `requests[].setupRequest` 每请求造唯一 sourceRef/jti（防 INV-6 去重把流量吃成 occurrences+1）；`idReplacement` 不可用于 body——autocannon 按 27 字节/id 算 Content-Length，本版 hyperid 实产 24 字节，服务端等死（autocannon 8.0.0 实测坑）。
- **p95 口径**：autocannon 默认百分位集无 95；起压前向 `hdr-histogram-percentiles-obj` 导出的 percentiles 数组补插 95，读出的是真 HDR 分位，非插值估算。

## B2 · 链路突发与持续流（票 66，burst 两档 + sustained 四档）

### 方法（B2 轮）

- **布景**：默认九服务 + fake LLM，**EVENT_DRIVEN=on（默认口径——B2 测的是含 autorun 消费的完整链路）** + `setup-openfga.sh`；起压前三口 /healthz 全绿；`docker compose down → rm -rf data → up` 清库起跑，burst 与 sustained 同一轮会话（档间不重启，每档开压前确认上一档积压已排干）；脚本内置 probe（2 条推→拉→completed）先验链路再上量；每档告警 host 逐条唯一（同 B3 口径，防同主机活跃案 merge 分支）。
- **施压面（框架红线）**：autocannon 编程 API 直打 `POST :3001/api/v1/webhooks/alerts`——burst = amount 满速真突发（conn=20），sustained = duration×overallRate 开环恒速（conn=2，红线 ≤20 不破）；逐请求唯一 sourceRef（`lib/gen-alert.mjs`）+ 每档唯一前缀，既防 INV-6 去重把量吃成 occurrences+1，又让各档读数互不掺和。
- **观察口（零新增，全 REST）**：**消费延迟** = alert.created outbox 事件 createdAt（与告警落库同一 SQLite 事务，M2 钟）→ run create 审计行 createdAt（agent 钟，HttpAuditSink 汇入），两侧容器共用宿主内核钟可直接相减；**未消化积压** = 未拉起告警（autorun 未消费）+ 已拉起未终态 run（分发队列），2s 网格采样成曲线，收敛 = 停灌后归零。**口径如实标注：`event_cursors` 表无公开读口（在 agent 自有 SQLite），cursor 滞后以「逐事件消费延迟 + 积压曲线」两个观测量近似**（票 66 授权口径）。
- **错误面分类**：422 = 验型闸 fail-closed 拒收（坏包率）；5xx/超时/网络错 = 过载面——ingest 拐点看后者，两者分开说。
- **档位依据（L0 修正）**：方案 §六规定持续流以 B3 实测分母重推——B3 净室分发水位 4.6-4.8 run/s，故 sustained 取 2/4/6/8 alerts/s（原方案 §三的 10/30/50/100 是 B3 之前的猜测档，作废），burst 取 100/500 两条一次性灌入。

**读数怎么解释**：

- **ingest 面全程稳如平地**：四档 P99 78→54→69→178ms，除 8/s 档抬到 178ms（前档 2.6×，本矩阵唯一一次 ingest 延迟陡升，但仍是毫秒级、且零错误）外几乎不动——**持续流灌到 8/s 都没让 ingest 写面出汗**。
- **消费延迟被 autorun 的 2s tick 量子化**：四档 P50 全部 ≈1.0s、P95/P99 ≈2.0s，档位间几乎不动——autorun 每 tick 最多消费 100 条（BATCH_LIMIT），8/s×120s=960 条也只要 10 个 tick 追平，逐事件 cursor 滞后始终 ≤1-2 个 tick。**消费不是瓶颈，执行才是**：事件很快变成 queued run，真正的过载体现在积压（未终态 run 堆积）而不是消费延迟。
- **积压分界线在 4/s 与 6/s 之间**：2/4 档积压有界（峰 4/12，随到随消化）；6/8 档积压线性增长（峰 261/571，稳态增长不收敛直到停灌）。值得注意：按 B3 净室分母 4.8 run/s 推算，6/s 档峰应 ≈(6−4.8)×120=144、8/s 档 ≈384；实测 261/571 更高——**持续流同时有 ingest 写入时，链路有效排干只有 ~3.4-3.9/s**（ingest 的验型/observables/审计/outbox 写与分发循环共享 SQLite 单写者，且本轮表规模已随 burst+前档积累到数千行），比 B3 净室值低约两成到三成。停灌后两档都线性排干、全部收敛、零丢失（队列只延不丢，与 B3「延迟受害、吞吐恒定」同形态）。

### 拐点结论（B2）

- **错误率起跳点：未达**。1-500 条突发、2-8 alerts/s 持续全部 201、零 422、零 5xx/超时——本量级（单机演示）**没有 ingest 错误拐点**；fail-closed 验型闸在过载矩阵内零拒收（没有坏包，也没有过载拒收）。
- **延迟陡升点：两处分开说**。①ingest 面：唯一陡升在 8/s 档（P99 69→178ms，2.6×），毫秒级、远离错误面，属轻微劣化不是拐点；②链路面：**陡升/积压分界在 4/s 与 6/s 之间**——≤4/s 积压有界且随停灌即排干（消费延迟恒 ~1-2s），≥6/s 积压线性增长（6/s 峰 261、8/s 峰 571），链路进入「排队型」过载。取整判定：**本机链路稳态上界 ≈4-5 alerts/s**（B3 净室 4.6-4.8 run/s 在带并发 ingest 写时收缩到 ~3.4-3.9 run/s）。
- **瓶颈归属（方案 §六 回答）**：拐点不在 ingest（500 条秒灌 P99 51ms 零错误、8/s 持续 P99 178ms 零错误），在**分发循环水位**——B3 已钉净室 4.6-4.8 run/s，B2 补上「带写入负载时收缩到 ~3.4-3.9 run/s」这刀。系统级瓶颈仍是同一个：SQLite 单写者之上串行执行的 run-dispatcher（周期=执行耗时+100ms tick）。

### under-pressure on/off 对照（票 68，B5 防线）

> 装配：`@fastify/under-pressure` 三 Fastify 服务（ingest/M2/agent）真引入，`UNDER_PRESSURE=on` 才注册（缺省=零注册=上文所有表格的口径不变）；on 时阈值显式配置——插件官方缺省全是 0（=该项不检查，README：「if the value is 0 the check will not be performed」），故取教学演示量级保守值 **maxEventLoopDelay=1000ms（README 示例同量级）/ maxHeapUsedBytes=1 GiB / maxRssBytes=1.5 GiB**，均 `UNDER_PRESSURE_MAX_*` env 可覆盖。503 语义全插件自带（`FST_UNDER_PRESSURE` + `Retry-After: 10`）；`/status` 是插件自带暴露口（healthCheck 把 memoryUsage 四项指标并进应答），容器内 curl 即取 eventLoopDelay——透传生效的直接证据。

## B3 · 分发循环水位爬坡（票 65，五档 + 审批 TTL 加测）

### 方法（B3 轮）

- **布景**：默认九服务 + fake LLM，**EVENT_DRIVEN=on（默认口径，兑现 B1 方法节的欠账）** + `setup-openfga.sh`；起压前四口 + guards `/healthz` 全绿；`docker compose down → rm -rf data → up` 清库重跑。agent 启动行核实：`run dispatcher: on (concurrency=1, approval_ttl=86400s)` + `event-driven autorun: on`。
- **拉起方式**：每档并发批量拉起 N 个 alert_flow（N=1/5/10/20/50），全走公开正门 `POST /internal/runs {kind:"alert_flow", alert_id}` → 202 `{run_id, status:"queued"}` 秒回（票 47 异步化语义，真代码核实）。告警经 ingest webhook 正门逐条推送，「推一条 → 立刻拉一条」串行配对——autorun（2s tick）对同一告警的自动拉起被 `hasActiveRun` 防重闸挡掉（completed 也挡，failed 才放行）；竞速窗口只剩单条 HTTP RTT，事后按 alertId→runId 对账。
- **逐条唯一 host**：同主机 24h 活跃案会触发 merge 分支——host 逐条唯一让每条 run 都走 FakeTriageLlm 确定性 tp → create_case → 调查+富化全链（同 run 链上两段，票 36），run 之间可比。
- **观察口（零新增，全 REST）**：run 状态/时刻的真相 = M2 `GET /api/v1/audit`（agent HttpAuditSink 五要素汇入，`createdAt` 是 agent 记录时刻，审计投递延迟不污染时刻）——run 的 create/update 行带完整状态迁移，**队列深度时间序列离线重构**，压测中只做 1s 一次的终态判定轮询。**口径如实标注：`run_jobs` 表无公开读口，队列深度用 runs 状态分布近似**——start 任务 pending ↔ queued run 一一对应（B3 只拉 start），claimed 窗口短暂计入 running。
- **先小量试跑**：脚本内置 probe（2 条）验证推→拉→跑通全链再上量；本轮 probe×2 + 五档共 90 条 alert_flow 全部 202、全部终态，**防重对账双拉=0、抢锁让路=0、审计对账缺口=0**，launch RTT max 13ms。

### 吞吐 vs 理论对照结论（偏差解释）

- **实测平台 4.6-4.8 run/s，理论 ~10 run/s 的偏差=2.1×，原因清楚且可拆账**：理论假设「每 tick 领 1 单、执行零耗时」；真代码里 tick 是**串行不重叠**的——`dispatchOnce` 领 1 单并 **await 执行完**，再等 100ms 才排下轮（run-dispatcher.ts `startRunDispatcher`）。所以真实周期 = 执行耗时 + 100ms tick，不是 100ms。
- **拆账（审计钟，90 条 alert_flow）**：running→终态的执行耗时 **中位 106ms / P95 121ms**（铸票 + 组图 + 分诊六节点 + 调查富化链：M2/guards/chroma 十余次 HTTP 出站全在 executeStartJob 内 await）；queued→running 的领单等待中位 2464ms——那是队列位置 × 周期的排队项，不是执行项。代入：周期 ≈ 106 + 100 ≈ 206ms → 理论天花板 ≈ **4.85 run/s**，与实测 4.6-4.8 严丝合缝（余量是 tick 对齐抖动）。
- **结论重述**：~10 run/s 是「执行耗时→0」的极限，真实天花板公式是 `1/(执行耗时 + 100ms)`；本机执行耗时 106ms 里 tick 纯开销占 48%。要逼近 10 run/s 有两条真代码里的正路：调大 `RUN_DISPATCH`（每 tick 并发领 N 单，dispatchOnce 内 Promise.all，上限受 SQLite 单写者约束——归 B5 压力锤验证）或压短执行耗时。RUN_DISPATCH 缺省 1 是本票口径不动生产代码。

### 拐点结论

- **吞吐无拐点**：1→50 并发档吞吐稳定在 4.6-4.8 run/s，零错误、零 failed、队列峰值恰等于拉起数——分发循环是**吞吐恒定、延迟受害**的形态：延迟随队列深度线性增长（档 50 的 P99 10.3s ≈ 50 × 206ms），不塌不抖。单机演示量级内，agent 常驻循环先于 HTTP 面成为第一个「排队型」瓶颈（对照 B1：写卡 500/s 零错误）。
- **第一个爆的组件判定（方案 §六）**：分发循环实测 ~4.8 run/s 而非 ~10 run/s，且缺口全部来自「tick 内串行执行」——后续 B2 持续流的 ingest 速率只要 >5 alerts/s 就会在 run_jobs 积压（autorun 拉起同样进这条队），设计持续流场景以 4.8 为分母。

### 加测：深队列中审批 TTL 过期裁决（方案 §三 B3 顺带项）

- **布景**：APPROVAL_TTL 配置面核实（run-dispatcher.ts `approvalTtlSecondsFromEnv`，缺省 86400s，agent 启动时读一次；compose 未透传该 env）——用 **/tmp compose override 文件**注入 `APPROVAL_TTL_SECONDS: "5"` 重启 agent（`docker compose -f docker-compose.yml -f /tmp/b3-ttl-override.yml up -d --no-deps agent`，零仓库改动，测完不带 override 重建还原，`approval_ttl=86400s` 复核）。深队列 = 垫队 4 条 alert_flow → knowledge_flow（案件布景：create-case → 状态机 New→InProgress→Closed 带 verdict）→ 压队 30 条 alert_flow（按 206ms/条 ≈ 6.2s 队列工作 > TTL 5s，保证过期时刻队里仍有活）。
- **结果**：kb_write 审批卡开出后 **TTL+174ms** 被时间裁决（卡 created_at=…465427，审计 expire 行=…470601，单卡无双拉），run 终态 failed(approval_expired)——**裁决发生时 alert_flow 队列深度仍有 7**。首跑（压队 15 条）队列先排干、深度 0，数字作废重跑——「深队列」前提要靠队列工作时长 > TTL 来造，15 条 × 206ms ≈ 3.1s < 5s 不够。
- **结论：扫描不会被饿死**——TTL 扫描在每轮 `dispatchOnce` 的**第①步、领任务之前**（真代码核实），与队列深度无关；174ms 的超出量 ≈ 卡在 tick 执行中途开出、要等下一轮 tick 开头扫到（一个周期 ~206ms 的对齐上界），与吞吐节的周期测算互为印证。fail-closed 的「时间出的裁决」在深队列下依然准时。

## B4 · SSE 扇出（票 67，三档 + 1s 轮询对照）

### 方法（B4 轮）

- **布景/纪律**：同 B2/B3 轮（默认九服务 + fake LLM，**EVENT_DRIVEN=on（默认口径）** + `setup-openfga.sh`；每轮 `docker compose down → rm -rf data → up` 清库起跑；三档串行一轮跑完，同轮不并行别的压测；脚本内置 probe（2 订阅者小参数全链路）先验再上量。表中数字取第二轮；第一轮同机复跑方向一致（斜率与延迟形态互证，见结论）。
- **高事件率 run 的造法（实测选定，全公开面）**：M2 `POST /api/v1/cases` 裸建案 + `POST /api/v1/cases/:id/observables` 灌 50 个 tlp/pap=0 的 ip observable（逐条唯一数据防去重合并）→ `POST /internal/runs {kind:"case_flow"}` → 富化 worker 对案件 observables 逐项 analyzer（每项一对 tool_call/tool_result 帧）——**事件量随灌入数线性可调（`B4_OBSERVABLES`），实测 113 事件/run、~0.4s 跑完**（票面授权口径：以「脚本可稳定复现的高事件率 run」为准；单 run 更高事件率没有公开面可造）。
- **被测面（框架红线）**：`GET /api/v1/events/stream?run_id=`——**自实现 fetch-stream SSE 客户端**（WHATWG 帧解析 + `Last-Event-ID` 重连语义，重连先补发后随 tick 续播，服务端实现即如此；终态 run 补发完即收流）。长连流不适用 autocannon——m13 的 autocannon 框架红线已由 B1/B2/B3 兑现，B4 不引入。
- **三相位**：①**实况扇出**——run 202 秒回后 N 订阅者同时挂流至服务端终态收流，对账 N 份帧 id 序列逐条一致；②**重连补发**——每订阅者带 `Last-Event-ID`（铺在实况所见真实 id 集上的采样点）重连，服务端按 id>cursor 补发，逐订阅者对账「不丢不重」（expect=0 的空补发是合法读数）；③**停靠挂流**——knowledge_flow 停在 kb_write 人审闸（awaiting_approval，流不收），N 订阅者**空闲**挂流 30s（无新事件，每订阅者每 100ms 一次 `eventsAfter` 空查——**「每订阅者 100ms 定时器」的纯代价就在这一相位**），同轮先采 0 订阅者基线 12s，同一条采样线按切点分账。
- **对照组**：同 N 的 1s 轮询客户端（普通 fetch 轮 M2 `GET /api/v1/audit?objectId=<run_id>`——run 状态迁移审计行，B3 同款读口），20s 窗；**顺序纪律：布景 → 6s 无轮询基线 → 立刻 launch → 立刻开轮**（首跑把 6s 基线夹在 launch 与开轮之间，终态可见延迟被虚高成基线窗长——已修）。事件可见延迟 = 审计行 createdAt（agent 钟）→ 轮询响应首见时刻。
- **CPU 观察口**：`docker stats --no-stream` 每 5s 采样 agent（扇出面）与 case-backend（轮询面）；docker 多核口径（100%=全机 10 核），单次采样耗时 ~2s。
- **undici 实测坑（已钉 `lib/b4.mjs` 头注）**：Node 22.22 的 fetch 流式响应缺省 `bodyTimeout=300s`——SSE 空闲挂流（无新事件不写包）必被 undici 单方面掐断（`UND_ERR_BODY_TIMEOUT`，真踩：挂流 301s 报 terminated）。SSE 客户端必须用 `bodyTimeout:0` 的 dispatcher。

### 拐点结论（B4，回答「每订阅者 100ms 定时器的实测代价」）

- **代价 = 每订阅者常驻 ~0.1% 容器 CPU（两轮 0.06-0.15%），延迟面零劣化**。N=200 空载扇出把 agent CPU 从基线 ~1.4% 抬到 18.5%（第一轮 21.9%），是 N=50（9.1%/7.6%）的 ~2.0-2.4×；但 e2e P50/P99 三档钉在 ~50/~100ms 不动——方案 §二#4 预言的「N 个订阅者 = N 个定时器抢 agent 事件循环」在本机 200 订阅者内只兑现了 CPU 线性那一半，「eventLoopDelay 第一个崩」没有出现（eventLoopDelay 无现成指标——under-pressure 归票 68 装，这里以 CPU 斜率 + 延迟恒定为证）。
- **拐点外推（只同机比）**：按 ~0.1% CPU/订阅者，agent 空载扇出吃满一台 M4（docker 口径 100%）≈ 千级订阅者；更早到来的约束是每订阅者一条常驻连接 + 每事件 N 次 socket 写（实况相位 113 事件 × 200 订阅者 ≈ 2.3 万帧写入毫秒级完成，未成瓶颈）。
- **取餐铃 vs 轮询的账**：SSE 交付一个事件 ≈ 半个 100ms tick（~50ms），1s 轮询 ≈ 半个 1s 间隔（~750ms）——**SSE 快 13-16×**；代价形态不同：取餐铃（SSE）按订阅者人头常驻付费（空载也要付，~0.1% CPU/人），轮询按使用付费（有人轮才付）但付在读口上、且随表规模恶化。本机演示量级两者都远离崩点，教学结论是「形态差」不是「胜负差」。

## B5 · 防线在压下（票 69，三实验：guards 压下 / gateway 压下 / SQLite 写锤）

> 三个实验的共同问题只有一个：**过载与故障本身就是一种异常——INV-1「异常一律拒绝执行」在压下时松不松？** 每个实验一个脚本（`scripts/bench/b5-*.mjs`），断言判定器在 `lib/b5.mjs`（离线单测锁定），断言失败 = 脚本非零退出。每实验独立轮次（down → rm -rf data → up 起跑），实验内只做容器级 stop/kill/start，services/** 与 compose 零改动；全部语义断言先只读核对了 services 真码再写（guards-client.ts 的 failMode 折裁、app.ts 的先铸票后裁决、db.ts 的 WAL+busy_timeout=5000），不猜。

### 实验① · guards 压下（`b5-guards-kill.mjs`，docker kill → fail-closed 断言）

**方法**：sustained 2/s×12s 基线腿 → 压下腿开压 4s 后 `docker kill` guards 容器（安检员罢工；compose 无 restart 策略实测 `RestartPolicy=no`，kill 后停在 exited 不自动复活；选型 kill 不用 pause——kill=真实故障形态「进程崩溃」，钉 `guards_unreachable/timeout` 出站分支，pause 的 2s 挂起超时是另一条已单测锁定的路径）→ 灌入再续 4s 后停止，**保持压下态排干**（173s）才 `docker start` → 恢复腿 2/s×12s。观察全走 REST（M2 audit 的 `guards_block` DENIED 帧 + run 状态迁移）。

**fail-closed 断言语义（首跑误判教训后定稿）**：归因看**执行时刻**不看到达时刻——kill 后创建且窗内执行完的 run 必有 DENIED 帧（它的一切扫描只能落在压下窗内）；kill 前创建（扫描可能赶在 kill 前跑完）与跨恢复执行（复绿后才轮到执行）的 run 零帧是合法读数，另账记 `preKillCreated`/`crossRecovered`。

| 腿 | 发/201 | runs | completed/failed | guards_block DENIED 帧 | flag 帧 | run P50(ms) | P99(ms) |
|---|---|---|---|---|---|---|---|
| 基线（guards 在位） | 24/24 | 26 | 26/0 | **0** | 0 | 431 | 858 |
| 压下窗（guards 死亡） | 16/16 | 18 | 18/0 | **36**（12 个窗内执行完的 run 人均 3 帧） | 36 | 42788 | 167299 |
| 恢复（guards 就绪） | 24/24 | 26 | 26/0 | 1（偶发超时，见注记） | 0 | 613 | 2462 |

> 机器：Apple M4 × 10 核 · 内存 16 GB · darwin 25.2.0 · arm64 · node v22.22.2（docker 29.4.1）
> 复现：`docker compose down && rm -rf data && JIAOTU_GATEWAY_URL= JIAOTU_API_KEY= docker compose up -d && bash scripts/setup-openfga.sh` 然后 `node scripts/bench/b5-guards-kill.mjs`
> 口径：DENIED 帧 = 审计 `guards_block`（triage scanField，alert_field/kb 通道，缺省 failMode=block，guards-client.ts unreachable 折裁）；flag 帧 = `tool_output_flagged`（调查/富化链 tool_output 通道，票 50 方案 a 显式 failMode=flag 的降级支路）；run 延迟 = 审计钟 queued→终态。

**读数怎么解释**：

- **fail-closed 断言全绿，零一次「绕过扫描的成功出站」**：kill 后创建、窗内执行完的 12 个 run 全部带 DENIED 帧（36 帧 ÷ 12 run = 恰好人均 3——description + srcip/srcuser 两个 untrusted observable，triage verdict_llm 的三次必扫一次不少）；36 帧 result 全 DENIED、reason 全在 fail-closed 合法集；18 个压下窗 run 全到 completed 终态零挂死；恢复腿 26 run 行为如常（P99 2.4s 回基线带）。
- **故障形态被容器网络重塑**：宿主探针看到的是 `ECONNREFUSED`（毫秒级拒接），但 agent 容器视角 kill = 黑洞连接（SYN 无回包）→ 每段扫描烧满 2s `GUARDS_TIMEOUT_MS` 缺省超时 → reason 全是 `guards_timeout` 而非 `guards_unreachable`。两条出站分支都 fail-closed，但「快拒」与「慢拒」的可用性代价天差地别（下条）。
- **fail-closed 的可用性代价首次量化**：压下窗 run P50 42.8s（基线 0.43s 的 ~100 倍）——每段扫描 2s 超时 × 每 run 3-7 段扫描（triage 3 + 链上 flag 扫描）× 串行分发排队。**原文一个字节没进 prompt（换占位符），防线没松，但整条链路的排干被拖到分钟级**——这就是「拒绝执行」四个字在压下时的真实价格。
- **就绪 ≠ 健康**：`docker start` 后 healthz 秒绿，但 guards 冷启动装载 llm-guard/Presidio 可让头几扫超时被拒（二跑实测恢复窗 1 帧 DENIED）——恢复判定必须用「healthz 绿 + 首次真扫描成功」双闸，恢复窗偶发 DENIED 是 fail-closed 对「慢」的保守裁决（拒而非放行），注记不违规。

### 实验② · gateway 压下（`b5-gateway-down.mjs`，approve→mint 失败路径不留悬置态）

**方法**：knowledge_flow 停靠 kb_write 人审闸（awaiting_approval，布景动作全在 gateway 在位时做完——拉起要铸票）→ `docker compose stop gateway`（保安处关门）→ approve 打向死掉的保安处 → 断言 → 压下期推新告警（autorun 照常拉起）→ 断言 → `docker compose start gateway` → 同一张卡重批（可重试）→ 新告警如常。语义出处 app.ts 只读核对：内部模式 approve = **先铸票后裁决**——mint 抛错早退 502，decideApproval 根本不执行。

| 相位 | gateway | 动作 | 观测 | 断言 |
|---|---|---|---|---|
| A 对照 | 在位 | approve | 200，run 0.4s 到 completed | 布景自证 |
| B 压下·approve | 已停 | approve | **HTTP 502 `{"error":"mint_failed"}`**，卡=pending（approver 空/未执行），run=awaiting_approval，无 approve/execute 审计行 | **通过：不留「已批准无票」** |
| C 压下·拉起 | 已停 | autorun 拉起 alert_flow | run → **failed（failReason=mint_failed）**：queued→running→failed + FAILURE kill 审计（code=mint_failed，message=TimeoutError）+ error 事件 | **通过：明确 failed 分支，不留无票 run** |
| D 恢复·重批 | 复绿 | 同卡重批 | 先吃 1 个可重试 502（死 keep-alive）→ 200，卡 approved+executed，run completed（+3.1s） | 通过：可重试语义兑现，批准链如常 |
| D 恢复·新告警 | 复绿 | autorun 拉起 alert_flow | run → completed | 通过：链路如常 |

> 时间：2026-09-12T20:12Z（本地，只同机比；20:10 首跑同机复跑，形态一致）
> 机器：Apple M4 × 10 核 · 内存 16 GB · darwin 25.2.0 · arm64 · node v22.22.2（docker 29.4.1）
> 复现：同实验①布景（EVENT_DRIVEN 默认 on）然后 `node scripts/bench/b5-gateway-down.mjs`
> 口径：内部模式（JIAOTU_GATEWAY_URL 空）。「安全终态」判定 = 卡仍 pending（可重试）+ run awaiting_approval（可观察）+ 无 approve/execute 审计行（INV-8：没发生的裁决不留痕）——三条逐秒核对，重试期间每次 502 后都复核卡被动过没有。

**读数怎么解释**：

- **「先铸票后裁决」的时序就是防线本身**：gateway 死透时 approve 拿到 502 mint_failed，卡分毫未动（pending/approver 空/未执行）、run 仍挂起、审计零裁决痕迹——系统里**不存在**「已批准无票」的中间态，因为铸票失败时裁决这步根本没发生。拉起链同样干净：无票的 run 不悬置，走 queued→running→failed(mint_failed) 明确终态 + FAILURE 强杀审计，可观察可重拉。
- **恢复的最后一课是「可重试」**：gateway 复绿后的第一笔 mint 撞上压下期留下的死 keep-alive 连接（uvicorn 已换进程）再吃一个 502——卡照旧 pending，重试即成（200 → resume → completed）。fail-closed 语义给的不是「永不失败」，是**每个失败都停在可重试的稳定点上**：502 之后没有半吊子状态，重试就是全部善后。

### 实验③ · SQLite 写锤（`b5-sqlite-hammer.mjs`，REST 公开写口并发爬档）

**方法**：只走公开写口 `POST :3002/api/v1/alerts`（M2 upsert）并发锤 case-backend——**绝不以 rw 模式从宿主打开容器在写的 SQLite 文件**（跨界开柜=翻墙，红线）。autocannon closed-loop connections=C 饱和爬档（1/4/16/64，每档 10s），逐请求唯一 sourceRef（201=新建应全量、200=INV-6 去重应零）；同窗采样 `GET /healthz` RTT 作 responsive 旁证。本轮布景 **EVENT_DRIVEN=off** 起 agent（同 B1 口径：autorun 开着每条 upsert 都会拉起 alert_flow，锤的就不是 SQLite 写面了）。

**读数怎么解释**：

- **busy 5s 兜底在位，但它的目标场景在默认拓扑里不存在**：`busy_timeout=5000` 兜的是「跨进程写者抢锁」——而 M2 的库全仓只有 M2 一个进程在写（ingest/agent 的写全走 REST 汇入同一进程，better-sqlite3 单连接同步写在进程内天然串行）。并发锤到 C=64：零 422、零 5xx、零超时，p99 96ms、max 1.45s——**busy 超时边界从公开面不可达，5s 水位线读数 = 「未越过」**。这是结论不是失效：它说明方案 §二#3 的理论机制（busy 等待转延迟、5s 兜底）在本量级演示里连被触发的资格都没有，SQLite 单写者天花板以「吞吐平台 + 延迟陡升」形态出现，而非错误面。

- **健康口与业务口同一进程、同一命运**：/healthz P50 随写压从 2ms 抬到 59ms——同步写占住事件循环时健康口一起变慢（无 shed 时没有第二道保险，对照票 68：under-pressure 装上后才有 shedding 语义）。

## 收尾 · 四天花板理论 vs 实测（B1-B5 全链收官）

方案 §二给四个组件各写了一行理论值；B1-B5 五层压下来，每个理论值都有了本机实测锚点和一句拐点结论。数字全部只同机比（Apple M4 × 10 核 · 16 GB）。

|---|---|---|---|---|---|

**B5 防线三实验的一句一条**（与上表「+」行互补）：

- **guards 压下（B5①）**：kill 后创建、窗内执行完的 12 run 全带 DENIED 帧（人均恰 3 = 必扫段数），零「绕过扫描的成功出站」、零挂死——INV-1 在组件死亡时成立，价格是排干从秒级变分钟级。
- **gateway 压下（B5②）**：approve 502 mint_failed 时裁决根本不发生（卡 pending/run 挂起/审计零痕迹），无票 run 走明确 failed(mint_failed)——**系统里不存在「已批准无票」和「无票悬置 run」两种中间态**；复绿后同一张卡重试即成（先吃 1 个死 keep-alive 的可重试 502），零人工干预零丢失。
- **SQLite 写锤（B5③）**：C=64 零错误 p99 96ms、平台 ~1.4k/s——写面在演示量级离 5s 忙等边界一个数量级以上，兜底机制在位未触发（同票 68「未触发=服务健康」的读法）。
- **shedding（票 68，B5 防线的另一半）**：UNDER_PRESSURE 默认阈值下 B2/B4 全场景未触发 = 服务健康；机制演示档（阈值压到常态 heap 带内）503 真出现且服务存活、压后恢复——「在位的保险丝」被真实验证过会跳。

**全链一句话收官**：四个天花板压到底，这套架构没有一处「崩」，全部是「排队」和「拒绝」——延迟受害、吞吐恒定、fail-closed 不松动；第一个爆的组件是分发循环（实测 4.8 run/s，理论 10 的缺口全来自 tick 内串行执行），第二个露头的是读口（m2-read 76 req/s），而三条防线（guards 闸、保安处先铸票后裁决、SQLite 忙等兜底）在组件被直接压死时全部保持了拒绝语义。压力也是一种异常——这套系统对异常的回答始终是同一句话：**拒绝执行、留下记录、等恢复**。

## 已知边界注记

- **B5① 归因口径（首跑误判教训钉死）**：fail-closed 看**执行时刻**不看到达时刻——必须带 DENIED 帧的是「kill 后创建且窗内执行完」的 run；kill 前创建（扫描可能赶在 kill 前跑完）与跨恢复执行（复绿后才轮到执行）的 run 零帧是合法读数（`preKillCreated`/`crossRecovered` 另账记）。首跑把「压下窗创建的全部 run」当断言集，复绿后排干的 run 被误判「绕过」——归因口径写进 `lib/b5.mjs` 判定器与单测。
- **B5① reason 是 guards_timeout 不是 guards_unreachable**：宿主探针看到 ECONNREFUSED（毫秒拒接），但容器视角 kill = 黑洞连接（SYN 无回包）→ 出站 fetch 烧满 2s `GUARDS_TIMEOUT_MS` 缺省超时 → 走超时分支。两个分支都 fail-closed，但可用性代价天差地别（快拒 vs 慢拒），排障时按 reason 分头查。
- **B5① 就绪闸双闸**：`docker start` 后 healthz 秒绿 ≠ 扫描就绪——guards 冷启动装载 llm-guard/Presidio 可让头几扫超时被拒（二跑实测恢复窗 1 帧 DENIED(guards_timeout)）。恢复判定 = healthz 绿 + 首次真扫描成功；恢复窗偶发合法 reason 的 DENIED 是 fail-closed 对「慢」的保守裁决（拒而非放行），注记不违规、频发才说明没就绪。
- **B5① fail-closed 的可用性代价**：压下窗 run P50 42.8s（基线 0.43s 的 ~100×）= 每段扫描 2s 超时 × 每 run 3-7 段扫描 × 串行分发排队——防线不松的代价由整条链路的排干时间支付，这是设计语义不是缺陷。
- **B5② 恢复首笔 502（死 keep-alive）**：gateway 复绿后的第一笔 mint 可能撞上压下期留下的死连接（uvicorn 已换进程）再吃一个可重试 502——卡仍 pending，重试即成。恢复腿对每次 502 都复核「卡没被动过」，可重试性是断言的一部分不是脚本宽容。
- **B5② 观察口小坑**：FAILURE kill 审计行也带 `status.to=failed` 且无 failReason——`buildRunTimelines` 的 failReason 会被它覆写成 null；权威 reason 在 failed 迁移行（transitions）上，断言从 transitions 取。
- **B5③ 口径与「不可达」结论**：本轮 EVENT_DRIVEN=off（同 B1 隔离 autorun，不然每条 upsert 拉起一个 run，锤的就不是写面）；M2 单进程 better-sqlite3 同步写、无第二写者进程 → `busy_timeout=5000` 兜底的「跨进程写者」场景在默认拓扑公开面不存在——busy 错误面为零是结论不是失效，写面天花板以吞吐平台（~1.4-1.5k writes/s）+ 延迟陡升形态出现；/healthz 与业务口同进程，写压下 P50 从 2ms 抬到 59ms（无 shed 时健康口没有第二道保险）。
- **B5 的「发」列是 autocannon 计数，真实创建数 = 计数 + connections**：停表时每连接约 1 个在途请求已到达服务端创建告警但不计入 statusCodeStats（三腿一致 +2 = conn=2）——对账以 M2 alerts 表实际行数为准。
- **gateway-mint 卡无前置门槛**：`POST /internal/mint`（services/gateway/app.py 真代码核实）是无状态 HMAC 签名口，六字段 `type=task_ticket + jti/sub/case_id/run_id/scope/allowed_tools` 全是自由字段，不查 run/审批布景；SOC_HMAC_KEY 经 .env 注入。本轮直接测成，无需预置。焚毁查重在 M2 used_tokens/验票闸侧，不在此口——mint 的 jti 唯一化只是对齐生产形态。
- **EVENT_DRIVEN=off 偏离默认布景（仅 B1 轮）**：见方法节；B3 已按默认 on 口径另测（见 B3 节，autorun 双拉由防重对账兜底），B2 持续流仍须 on 口径为主、off 做隔离对照。
- **m2-read 的数字强依赖表规模**（本轮 15301 行）：单跑该卡（干净库 + 300 播种）数字会显著更好；跨轮比较需带上表规模注记。
- **限速档不是拐点，B2 已回答拐点在哪**：B1 的 500/s 内四张写卡零错误零超时；B2（票 66）补测链路矩阵后确认——本量级没有 ingest 错误拐点，链路积压分界在 4/s 与 6/s 之间（见 B2 拐点结论）。
- **B2 的 cursor 滞后是近似口径**：`event_cursors` 表无公开读口（在 agent 自有 SQLite，零新增端点），以「逐事件消费延迟（outbox 钟→审计钟，容器共用宿主内核钟）+ 未消化积压曲线」近似——脚本与报告同记。
- **B2 持续流的有效排干低于 B3 净室值**：B3 净室 4.6-4.8 run/s 只算分发；B2 带 ingest 写时实测 ~3.4-3.9 run/s（SQLite 单写者被 ingest 验型/observables/审计/outbox 写分摊，表规模随档积累）——跨轮比较要带上这条注记，别拿 4.8 直接当持续流分母。
- **autocannon 两个工具坑**（已在 scripts/bench/b1-endpoints.mjs 头注钉住）：body 内 `idReplacement` Content-Length 错账会挂死；requests 数组每连接独立从 0 迭代——全局唯一必须走 setupRequest。**B2 首跑补钉第三个**：`path` 必须写在 requests[] 条目内，顶层 path 会被条目缺省 `/` 覆盖（100 发全 404，服务端零痕迹）——已锁进 `lib/b2.mjs buildAutocannonOpts` 及其单测。
- **B4 的 hold 段基线样本薄**：docker stats 单次采样 ~2s，12s 基线只有 2-3 个样本（基线中位=最近邻秩）——CPU 斜率以两轮复跑互证（0.06-0.15% CPU/订阅者），别把单轮中位当精确值。
- **B4 的 e2e 到达时刻按读块记**：同一 TCP 块里的帧共享到达时刻（100ms tick 批量推送下整批同值），帧级到达差在这个口径下不可见。
- **B4 轮询对照读口 `object_id` 无索引**（queryAudit 全表扫）——本轮每轮清库、audit_entries 表小，200 req/s 才 RTT P99 40ms；跨轮比较必须带表规模注记（同 m2-read 的教训）。
- **B4 高事件率 run 的实况窗 ~0.4s**：「单 run 高事件率」到公开面能力为止（事件量 ≈ 13+2×observables 线性可调）；更长的持续窗口由停靠挂流相位补足（那个相位量的是空载定时器，不是事件扇出）。
- **B4 的每订阅者空查走 `(run_id,id)` 索引区间扫**（idx_run_events_run），代价随该 run 事件数而非 run_events 全表——但 agent 侧该表规模无公开读口，数字只同轮内比。
- **undici 流式响应 bodyTimeout 坑**（已在 `lib/b4.mjs` 头注钉住）：Node 22.22 fetch 缺省 bodyTimeout=300s 会把 SSE 空闲挂流单方面掐断（UND_ERR_BODY_TIMEOUT，真踩 301s terminated）——B4 SSE 客户端必须 `bodyTimeout:0` dispatcher，别拿裸 fetch 挂长流。
- **under-pressure 缺省 = off = 零注册**（票 68）：`UNDER_PRESSURE` 不设时三服务一个插件都不装（容器内 `/status` 404 可证），上文所有表格口径与票 66/67 逐字节同源；on 的阈值缺省是**教学演示保守值**（插件官方缺省 0=不检查，故必须显式给值；1000ms/1GiB/1.5GiB，`UNDER_PRESSURE_MAX_*` 可覆盖）——本量级压测全部「未触发=服务健康」，这是结论不是失效。票面提到的 `exposureInterval` 在官方 9.x 不存在，现版是 `sampleInterval`（缺省 1000ms，保持官方缺省未覆盖）；`/status` 的指标应答与 503 语义全是插件自带（exposeStatusRoute/healthCheck 官方选项），零自造响应。
- **shed 会打掉 /healthz**：插件 onRequest 钩子对所有路由生效（含健康检查口）——机制演示档 shed 窗内 agent 容器 healthcheck 同步失败（docker 层可见 unhealthy）。这是「卸载面诚实」的一部分，但意味着 shed 期间 docker healthcheck 不再是可用性信号，观察要用业务探针。
- **审计镜像是 best-effort，shed 窗内会有审计缺口**：机制演示档 case-backend shed 503 打掉了 agent 审计出站（`audit_ingest_failed` warn 多条）——M2 audit 表缺该窗的部分 run 迁移行，业务状态机不受影响（审计旁路不阻塞，票 35 口径）。跨轮以审计对账的要带这条：**shed 窗内的「审计无行」≠「无迁移」**。
- **机制演示档留观异常（未复现、未归因）**：该腿尾部 16 个 run 未到终态（15 告警停 New、1 run 无终态迁移行），重启 agent（m3 孤儿恢复）后无进度、无 pending 审批卡、无 FAILURE 审计、autorun 游标已到位——公开观察面无法归因；under-pressure 只 shed 入站 HTTP，与进程内分发循环无因果链可建。off 基线（票 66）与 on 默认阈值腿同场景均干净排干，本现象仅出现于「阈值压到进程常态 heap 带内、GC/503 颤振 ~215s」的极端档，不复刻不收敛为疑，复现则另开票。
