## 三问

**位置感**：终极目标不变——SOC 数字员工。票地图更新：

```

→ 票06 铸票(py) → 票07 验票闸(TS) → 第一波…
```

票 06（Python 铸票）和票 07（TS 验票闸）隔着一条语言边界，却要操作**同一张票**。
本票先于两者存在，回答三个问题：

- **这一步是干嘛的？** 在写任何铸票/验票代码之前，先把「票长什么样、验票该判什么」
  做成**固定数据**：9 张真实票面（合法、过期、scope 不足、参数篡改、已焚毁五类）
  + 一张期望验票结果表 + 一把两端共用的测试密钥。Python 和 TS 两边以后的测试都跑
  这同一组数据、对同一张答案卡。
- **什么需求逼我们这么设计？** ADR 0001 拍了「搬票型不搬代码」：Python 侧继续用老
  task_token.py 的票型，TS 侧用 node:crypto 重写验票。同一票型两种语言各写一遍，
  **实现漂移**几乎是必然的——比如 TS 的 JSON.stringify 默认无空格，Python 的
  json.dumps 默认带空格，序列化差一个字节，签名就对不上。图纸必须是语言中立的。
- **解决什么麻烦？** 它把「票型」从两份口头约定变成**一份可执行的合同**：任何一边
  改了票面字段、换了序列化规则、动了密钥，契约自检测试当场红——漂移在票 06/07
  动工之前就会被拦住，而不是联调时两边对着猜。

## 跟着数据走：改参数的攻击者为什么会被抓住

拿最精彩的一张 fixture——`approval-token/params-tampered.json`——走一遍：

1. **正常批准**：值班长批准隔离 `web-01`。铸票时把参数做规范化序列化
   `{"host":"web-01"}`（键排序、无空格），算 SHA-256 得
   `sha256:b8dc6b29…`，写进票的 `params_hash` 字段，整张票用密钥签了 HMAC——
   签名完美合法。
2. **攻击者出手**：拿到票后想隔离别的机器，把调用参数改成 `{"host":"web-02"}`。
   他**不改票**（票动了签名就碎，他没钥匙重签），改的是**调用时的参数**——票面
   看起来毫发无损。
3. **被抓住的瞬间**：验票闸把实际参数按同一套规范化规则重算 hash：
   `sha256(…web-02…) = sha256:7a3f…` ≠ 票里的 `b8dc…`。签名完好、票是真票，
   但**参数对不上票绑定的 hash**——403 `params_mismatch`。这就是 INV-2 说的
   「改参数即失效」：签名锁「票没被改」，params_hash 锁「用法没被换」，两把锁
   各管一段。
4. **契约怎么锁住它**：fixture 里这张票的 `probe`（探针）写明用 web-02 去试，
   `expected` 写明 `{"allow": false, "reason": "params_mismatch"}`。py 和 TS 的
   测试都读同一份文件、跑同一个探针、对同一张答案卡——哪天某一边重构成参数
   hash 算漏了 sort_keys，它的契约测试当场红。

## 新技术点：HMAC-SHA256（四要素）

- **名字**：HMAC（Hash-based Message Authentication Code，哈希消息认证码），
  本项目用 SHA-256 做底层，`hmac.new(...)`（py 标准库）/
  `crypto.createHmac(...)`（node:crypto）。
- **作用**：普通哈希谁都能算（改票再重算 hash 就伪造了）；HMAC 是**带钥匙的哈希**
  ——像盖防伪章：章的图案由「文件内容 + 我手里的印章」共同决定，没章的人既盖不出
  合法章，也改不了已盖的文件。所以它同时提供完整性（票没被改）和来源认证
  （票是持钥匙方签的）。
- **参数**：`HMAC(key, message) → 定长摘要`。key 用 UTF-8 原始字节（本项目测试密钥
  是固定 ASCII 串）；message 是要认证的任意字节串（这里是 `b64h.b64p` 那段 ASCII）；
  输出 32 字节，本项目按老票型惯例转 **hex 字符串**放进票的第三段。
- **用法**（两端各一行核心）：
  ```python
  # py（task_token.py:44 原版写法）
  hmac.new(key_bytes, unsigned.encode(), hashlib.sha256).hexdigest()
  ```
  ```js
  // TS（票 07 将用）
  createHmac("sha256", Buffer.from(key, "utf8")).update(unsigned).digest("hex")
  ```
  注意两个坑：验票比较必须用**恒时比较**（py `hmac.compare_digest`，防时序侧信道）；
  hex 是我们票型的约定，标准 JWT 那段是 base64url——别混。

## 关键顿悟

- **契约测试测的是数据，不是实现**。本票没有写任何铸票/验票代码，只写了一组
  「 input + expected answer 」和一份自检（这组数据自身自洽：签名咬合密钥、字段
  照 PRD、探针与期望互洽）。好处：06/07 还没动工，合同已经可以被执行、被违反、
  被红牌——语言边界两侧的漂移从第一天就无处藏身。
- **签名和参数 hash 是两把不同的锁**。HMAC 签名管整张票「未被篡改」；
  `params_hash` 管这张票「只被用于被批准的那组参数」。攻击者可以完全不碰票而换
  参数——只有第二把锁能拦住（INV-2 的本体）。
- **含时间的测试必须注入时钟**。fixture 的 iat/exp 是固定历史值，`合法` 票的
  exp 早就过去了；契约测试一律用 fixture 里的 `verify_now` 当「现在」。否则这批
  合法 fixture 活不过它自己的 TTL——半年后所有测试莫名其妙全红，你还会以为代码
  坏了。这就是「冻结时钟」：让时间也成为契约的一部分。
