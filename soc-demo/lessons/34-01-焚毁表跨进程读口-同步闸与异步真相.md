# 34-01 · 票 34：焚毁表跨进程读口——同步闸与异步真相

## 三问

**位置感**：阶段 7 体检 G 组「遗留标记回收」清偿波的第一票，安全线头置顶：

```
体检 G2 线头清单：G2-1 焚毁读口 ✅你在这里（安全）→ G2-2 审计汇入 → G2-3 run 异步化
→ G2-4 ToolManifest → ……（G2-1 是唯一标了「安全相关，建议置顶」的线头）
```

- **这一步是干嘛的？** 把验票闸的「焚毁表查询」从**只认进程内的小本本**换成**查
  案件后端的总账本**。票 11 交付审批回路时留了一句实话（遗留标记 11-1）：闸查
  焚毁表的接口是同步的 `has(jti)`，而焚毁总账在另一个服务（case-backend 的
  `used_tokens` 表）里，中间隔着一条 HTTP——当时接不上，生产干脆**不查**，一次性
  全靠「卡的 executed_at 只许执行一次 + 票 300 秒自然过期」两层兜底。攻击者拿着
  泄露的 ApprovalToken 换一个进程、换一个 run 再提交，兜底层是拦不全的。
- **什么需求逼我们这么设计？** 两条不变量正面对撞：INV-2 要求「重放必 403」（那就
  必须跨进程查总账，查询是 HTTP，天然异步）；而闸的挂起机制（LangGraph 的
  `interrupt()`）靠**同步抛异常**传播，闸所在的 `executeApproved` 刻意不是 async
  函数（票 11 契约）。硬把闸改成 async，interrupt 的同步语义就断。解法是把
  「异步」和「裁决」拆开：**异步的事（查总账）在进闸之前做完，闸本体一行不动**——
  查询结果装进一个一次性小本本递给闸，闸还是同步地、按老顺序（验签 → 时效 →
  焚毁 → scope/参数）裁决。
- **解决什么麻烦？** 跨进程重放从「靠 TTL 慢慢过期兜底」变成「当场 403
  token_used」；同时 INV-1 的 fail-closed 补上最后一块：M2 查不到（服务挂了/
  超时/5xx）就**拒绝执行**，绝不「查不到就当没烧过」放行。

## 全链路一览

```
【写侧（票 11 就有，不动）】L2 动作执行成功 ──► HttpTokenBurner.burn
                                                fire-and-forget POST
                                                case-backend POST /internal/used-tokens
                                                ──► used_tokens 表（总账本）

【读侧（本票接通）】实例 B 拿泄露票 resume 执行：
  节点 await ctx.executeApproved(tool, params, …)
      │
      ├─ 同步头：awaitApproval ── 决定已落（卡上有票），不抛 interrupt
      ├─ 装填（异步，票 34 新增）：从票 wire 串解出 jti（未验签，只当查询号牌）
      │     └─► HttpUsedTokenReader.lookup(jti)
      │           GET case-backend /internal/used-tokens/:jti
      │           200=已焚 ▸ true   404=未焚 ▸ false   其他/断网 ▸ 抛（读口哑掉）
      ├─ 进闸（同步，本体零改动）：verifyTicket(…, used = 一次性读口)
      │     验签 ✓ → 时效 ✓ → used.has(jti) ── 总账说已焚 ──► 403 token_used
      └─ 403 路的既定下游：DENIED 审计 → 抛 approval_gate_denied → run 强杀 failed
```

生产装配就一行（`index.ts`）：`buildApp({ …, usedReader: new HttpUsedTokenReader() })`。

## 跟着数据走：一张泄露票的跨进程之旅

布景就是测试本体（`app.test.ts`「焚毁表跨进程读口」第一条）：真案例-backend 子进程
+ 两个**完全陌生**的 agent 实例（各自独立的内存库，互相看不见对方任何进程内状态）。

1. **实例 A 正常走完审批**：值班长批准 `isolate_host` → 铸票 `jti=ap_t34_001` →
   闸放行 → 动作执行 → 烧票（fire-and-forget POST 总账）。测试里轮询
   `GET /internal/used-tokens/ap_t34_001` 直到 200，确认总账记上了。审批响应里的
   `approval_token` 就是「泄露面」——它现在落进了攻击者手里。
2. **实例 A 进程消失**（`appA.close()`）。它的内存焚毁表（如果有的话）、卡上的
   executed 标记，对实例 B **全部不存在**。
3. **实例 B 捡到票**：全新的 run、全新的卡。攻击者把泄露票塞进卡里（测试用
   `decideApproval` 直塞——生产里这对应「审批记录被伪造」；INV-9 说了闸只信票
   本身，所以闸的视角和正常 resume 一模一样）→ resume。
4. **装填**：B 的 `executeApproved` 从票串解出 `jti=ap_t34_001`，发 GET 问总账 →
   200 → `burned=true` 装进一次性读口。
5. **进闸**：验签过（票是真票）、时效过（300 秒内）、`used.has("ap_t34_001")` →
   true → `{allow:false, reason:"token_used"}`。
6. **下游照旧**：审计记 `DENIED / reason=token_used`，抛
   `approval_gate_denied:token_used`，run 强杀成 failed，动作没执行第二次。
   关键断言是：**B 本地一切干净，它还是被拒了——唯一可能拦住它的就是总账**。
   这就是「跨进程读口接通」的可证明形态。
7. **捣乱输入**：把 case-backend 关掉再放一张新票进来？读口 GET 直接连接拒绝 →
   抛错 → 哑读口 → 闸内 `has()` 抛 → 落 fail-closed 桶 `signature_invalid` →
   照样拒绝执行。**「问不到账」和「账上没有」是两回事**，后者放行、前者拒。

## 新技术点四要素：async 函数会吞掉同步抛出的异常

- **名字**：JS 语言语义——async 函数体内抛出的异常（哪怕在任何一个 `await` 之前、
  语法上完全同步的位置）都会被包装成 **rejected Promise**，不会同步传播。
- **作用**：这个语义决定了本票的整个形态。LangGraph 的 `interrupt()` 挂起靠
  **同步 throw** 一个 `GraphInterrupt`，框架在调用栈上捕获它才能把 run 停下来。
  如果把 `executeApproved` 整个改成 `async`，interrupt 的异常会变成一个没人
  await 的 rejected Promise——挂起静默失效，闸拒的异常则变成 unhandled rejection。
  本票回归时真实咬过一口：approval-loop 的「票过期强杀」测试红了，run 误报
  completed，异常飞在进程里没人接。
- **参数/规则**：记住一条就够——**「同步抛出」只在非 async 函数里成立**。async
  函数 `async () => { throw x }` 等价于 `() => Promise.reject(x)`。
- **用法**（本项目用在哪：`graph.ts` 的 `executeApproved`）：

  ```ts
  const executeApproved = (tool, params, opts, action) => {
    awaitApproval(tool, params, opts);   // 同步头：未决时 interrupt 同步抛 ← 挂起契约
    if (!decision.approved) return { executed: false, … };
    return (async () => {                // 异步尾段：到这里才允许有 await
      const used = await resolveUsed(token);   // 查总账（HTTP）
      const verdict = verifyTicket(…, used);   // 闸本体仍是同步函数
      …
    })();
  };
  ```

  配套规则：调用一个「决定已决时返回 Promise」的函数，**节点必须 async + await**
  （不 await 会把 Promise 存进 checkpoint 状态，序列化成 `{}`，异常也没人接）。
  本票把 `APPROVAL_DEMO_FLOW` 和测试布景 `l2Flow` 两处 sync 节点改成了 async——
  与 knowledge/chat worker（票 17/23 起全是 async 节点）同款。

## 关键顿悟

- **异步和裁决要拆开**。闸是「法官」，法官必须同步开庭（interrupt 契约）；查总账
  是「送卷宗」，让书记员在开庭前把卷宗送到（闸前装填）。为了异步把法官改成异步
  开庭，整个同步契约就塌了——**在 seam 的调用侧消化异步，比把 seam 改成异步便宜
  得多**。
- **「查不到」≠「没有」**。读口的返回值表面是 boolean，实际是三态：200（已焚）、
  404（未焚）、**其余都是「病了」必须抛**。把三态压成两态（比如 catch 里 return
  false），fail-closed 就开了一个最隐蔽的洞：M2 挂掉 = 所有已焚票都能重放。
- **装填是叠加不是替换**。M2 的 404 说「总账没记」，不代表「本进程小本本没记」——
  合并语义必须取**或**（任何一路说已焚即拒）。测试里专门锁了一条：本地表已焚 +
  M2 未焚 → 照样 token_used。
- **未验签的数据只能当号牌，不能当证据**。装填查询用的 jti 是从票串里**不验签**
  直接解出来的（验签前总得先知道查哪张票）——这不破坏安全，因为查询结果只是给
  闸的一张小抄：票是伪造的，闸的验签步当场拒，小抄根本没机会被读。
- **测试形态即生产拓扑**：跨进程重放要测的是「两个互不知情的进程共享一个总账」，
  所以布景就是「两个全新 buildApp 实例（票 11 先例）+ 真案例-backend 子进程
  （票 30 先例）」——用假布景（同一张内存表）是测不出跨进程语义的。
