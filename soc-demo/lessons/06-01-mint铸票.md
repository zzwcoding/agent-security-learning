# 06-01 · 票 06：mint 铸票——POST /internal/mint

## 三问

**位置感**：m9 安全控制面主体三连开始：

```
票01 CI ✅ → 票02 票面契约 ✅ → 票03 数据地基 ✅ → 票04 guards ✅ → 票05 MCP体检 ✅
→ 票06 铸票 mint ✅你在这里 → 票07 验票闸(TS) → 票08 凭证代理 → worker 大军 → 审批回路
```

- **这一步是干嘛的？** 给 gateway 造一个「铸币车间」：`POST /internal/mint`，两种票
  都能铸——**任务票**（worker 被拉起时发的最小权限门票，TTL 900s）和
  **ApprovalToken**（L2 高危动作经人批准后铸的一次性令牌，TTL 300s）。票的防伪
  钢印是 HMAC-SHA256 自签。
- **什么需求逼我们这么设计？** PRD 的设计哲学一句话：**LLM 是不可信的决策者**——
  它不能给自己授权。所以分诊 agent 能不能调 `isolate_host`，不是 prompt 里写句
  「请勿越权」就完事的，得看它手里有没有票、票上钢印是不是我们盖的、票的 scope
  够不够、过没过期、是不是一次性。这一整套的**源头**就是铸票端：没有签名票，
  后面验票闸（票 07）验什么？
- **解决什么麻烦？** 票 02 造好了「法律」——fixtures/tickets/ 九张历史票 + 期望
  验票结果，是 py 铸票侧和 TS 验票侧的共同契约。但法律得有人执行：本票让 py 侧
  第一次**按契约格式铸票**（冻结时钟+固定 jti 时逐字节复现 fixture，自证同源），
  同时补上 py 自己的解码/验签路径来**消费契约**——九张票逐张跑、逐张对结果。

## 跟着数据走：捣乱者把主机从 web-01 换成 web-02

拿契约里的真实票 `approval-token/params-tampered` 走一遍验票路径——这张票**本身
没被涂改**（签名完好），捣乱发生在**用票的时候**：

1. **切三段**：`token.split(".")` 得 b64 头、b64 票体、hex 钢印。把 `"b64头.b64票体"`
   用测试密钥重算 HMAC-SHA256 → 和第三段一致。**签名验过了**——所以捣乱者没动票，
   动的是票外面的东西。
2. **验时效**：注入 `verify_now = 1757000060`（契约禁 wall clock，测试时刻是
   历史冻结值）< `exp = 1757000300` → 没过期。
3. **验焚毁**：jti 不在 used_tokens → 不是重放。
4. **参数指纹对一下**（关键闸）：票体里锁着
   `params_hash = "sha256:b8dc6b29…"`，那是当初批准的参数 `{"host":"web-01"}`
   的指纹。现在实际要执行的参数是 `{"host":"web-02"}`——重新算指纹，得到的是
   另一串。**对不上 → 403 `params_mismatch`**，和 fixture 的 expected 一字不差。

反方向走一遍铸票：冻结 `iat=1757000000`、按固定键序拼 payload、用测试密钥钢印
——铸出来的 token 和 `approval-token/valid` 的 token **逐字节相同**。这不是巧合，
是签发确定性的铁证：我们的铸币车间和契约出同源。

## 新技术点：HMAC（带钥匙的哈希）四要素

- **名字**：HMAC（Hash-based Message Authentication Code，基于哈希的消息认证码），
  Python 标准库 `hmac` + `hashlib`，零第三方依赖。
- **作用**：普通 sha256 谁都能算——改票的人也能给自己的假票算个新 hash。HMAC 是
  **掺了密钥的 hash**：好比钢印机只有铸币厂有一台，别人手里再强的复印机也压不出
  一样的章。和上一票 guards 的正则扫描是两个世界：那是「查内容」，这是「验身份」。
- **参数**：
  - `hmac.new(key, msg, digestmod)`：`key` 是**原始字节**（UTF-8 直接 encode，
    无 hex 解码无 KDF——contract.json 的 `hmac_key` 约定）；`msg` 也必须
    `encode()` 成字节；`digestmod=hashlib.sha256`。
  - `.hexdigest()` → 64 字符 hex 串，就是票的第三段（教学变体：JWT 标准第三段
    是 b64，我们继承 task_token.py 用 hex，契约 README 有言在先）。
  - **校验端**用 `hmac.compare_digest(a, b)` 而不是 `==`：恒时比较，不管第几个
    字节不同耗时都一样，防「按响应时间逐字节试探签名」。
- **用法**（mint.py 全部家当）：
  ```python
  def sign(key: bytes, unsigned: str) -> str:
      return hmac.new(key, unsigned.encode(), hashlib.sha256).hexdigest()

  def _seal(key, payload):                       # 盖章的对象是 "b64头.b64票体" 这串字节
      b64p = b64u(json.dumps(payload, ensure_ascii=False).encode())
      return f"{HEADER}.{b64p}.{sign(key, f'{HEADER}.{b64p}')}"

  hmac.compare_digest(sign(key, f"{b64h}.{b64p}"), sig)   # 验票：恒时比钢印
  ```
  本项目用在哪：`services/gateway/mint.py` 的 `sign/_seal/unseal`；TS 侧对位实现
  是 `createHmac("sha256", Buffer.from(key,"utf8"))`（票 07）。

## 关键顿悟

- **签名咬的是字节，不是语义**。payload 的 json 里改一个空格、调换两个键的顺序，
  意思没变，钢印就废了。反过来说：**键序也是签名字节的一部分**——所以 mint 按
  PRD §5.8/§5.9 的字段顺序拼 dict、`json.dumps` 用固定分隔符，才能逐字节复现
  fixture。跨语言两端能对上，靠的就是「序列化的每个字节都写死在契约里」。
- **params_hash 是指纹，不是保险箱**。它不加密——`host=web-01` 谁都能从请求里
  看到；它只负责**绑定**：执行时把参数重新算一遍指纹，跟票里那枚对不上就是被
  调包了。「改参数即失效」（INV-2）的全部机制就这一句话。
- **裁决顺序本身就是安全设计**。verify 的顺序是 签名 → 时效 → 焚毁 → scope/参数：
  签名不过的票**连进 json 解析器的资格都没有**（涂改过的字节永远只是字节）；
  任何一步不过立刻短路返回 403。fail-closed 不是口号，是「先问最致命的问题，
  答不上来就枪毙」。
