# 0045 · 阶段 0.1：仓库骨架

## 三问

- **终极目标**：soc-demo 是能拿去汇报的 SOC 数字员工，8 个组件（PRD §4.1）。本阶段只干一件事：给这块地画好格子，让后面每一铲土都有地方放。
- **为什么现在做**：sdd-flow 的纪律是"产物即状态"——目录结构、术语表、仓库规约必须先于代码存在，否则 AI 在新窗口里无处定位。
- **解决什么麻烦**：防止"代码越写越多、东西越放越乱"的经典开局。

## 本阶段产出一览

```
soc-demo/
├── AGENTS.md        # 仓库规约：指向 sdd-flow，写死四条硬性约定
├── CONTEXT.md       # 术语表：角色/领域/工程三类种子词条
├── README.md        # 门面 + 文档地图
├── package.json + pnpm-workspace.yaml + tsconfig.base.json  # pnpm monorepo 底座
├── services/        # ingest / case-backend / agent / guards / gateway / web（空目录，0.2 填）
├── packages/        # 跨服务共享 TS 类型（将来用）
├── specs/  docs/adr/  lessons/  fixtures/alerts/
└── .github/workflows/  # 0.3 填
```

## 关键决定

- **monorepo 一个仓**：6 个自建服务 + 共享类型放一个仓，跨服务改接口一次 PR 搞定；汇报演示也只发一个链接。
- **TS 走 pnpm workspace，Python 服务不进 workspace**：`guards`/`gateway` 用 uv 自理，两类工具链不互相污染。
- **仓库形态：直接并入父仓（安全评估agent）跟踪，不单独建仓**（用户 2026-09-04 拍板）：学习记录与 demo 同仓演进，省一套仓库管理；将来要单独发 GitHub 再拆也来得及。
- **git 纪律**：按 learn-by-rebuild，commit 等你说"提交"。
