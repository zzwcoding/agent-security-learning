# 01-01 · 票 01：CI 守门（spec gate + lint/typecheck/test 进 Actions）

## 三问

**位置感**：终极目标是复刻一个「SOC 数字员工」（告警进来 → 分诊 → 调查 → 处置，
全程可审计）。实现期共 22 张票，先看地图：

```
票01 CI守门 ✅你在这里 → 票02 票契约 → 票03~07 第一波(m2案件后端/m9守卫六件套)
→ 第二波(m1接入/m3调度) → 第三波(m4~m8工人) → 第四波(m10前端/m11评测)
```

为什么第一步是 CI 而不是业务代码？回答三个大白话问题：

- **这一步是干嘛的？** 在仓库门口装一套自动门禁：任何人往 GitHub 推代码（或提 PR），
  GitHub 的机器人会自动替你跑一遍检查——文档规格校验、代码风格、类型检查、测试——
  全过亮绿灯，任何一个挂了亮红灯。
- **什么需求逼我们这么设计？** sdd-flow 的纪律：**CI 要在第一行业务代码之前存在**。
  接下来 20 张票会让 AI（和我）高速写代码，没有门禁，「测试过了才算完」就是一句空话；
  等代码堆起来再补门禁，没人愿意回头还这笔债。
- **解决什么麻烦？** 门禁的本质是**把「完成」的定义从口头变成机器可判定**：
  不是「我觉得写完了」，而是 `check_specs.py` 退出码 0、四个 job 全绿。红灯就是
  客观的「没写完」。

## 全链路一览

门禁住在**父仓** `.github/workflows/ci.yml`（git 仓库根是父仓，工程在 soc-demo/ 子目录，
所以 workflow 要挂在父仓 + 用 paths 过滤只盯 soc-demo 的变化）。一次推送进来后：

```
git push / 提 PR
   │
   ▼
GitHub Actions 认出 ci.yml（paths 过滤：只有 soc-demo/** 或 ci.yml 本身变了才跑）
   │
   ├─► job① spec-gate   python3 tools/check_specs.py        ← 文档规格闸（本票主角）
   ├─► job② ts           pnpm install → lint → typecheck → test
   ├─► job③ python       ruff check → 两个 Python 服务各跑 pytest
   └─► job④ compose      docker compose config -q          ← 编排文件语法闸
   │
   ▼
四个 job 全绿 = ✅ 允许合并；任意一个非零退出 = ❌ 红灯
```

每个 job 就是一台独立的检查机器，互相不知道对方存在，**都只认一条通用语言：进程退出码**
（0 = 过，非 0 = 挂）。

## 跟着数据走：一次捣乱提交的完整旅程

以验收 2 的真实实验为例——我们往 `specs/modules.md` 里塞了一个依赖环，看它怎么被拦：

1. **捣乱注入**：m2 卡本来写 `- 模块: 无（叶子模块）`（specs/modules.md:98），我们改成
   `` - 模块: `m1` ``。而 m1 本来就依赖 m2——于是 m1 → m2 → m1，像两个人互相等对方先动手。
2. **闸门读卡**：`tools/check_specs.py` 的 `parse_modules()` 把 12 张模块卡解析成
   `{卡名: {目录, 依赖列表}}`，`check_graph()` 做深度优先遍历，给每个节点涂色：
   没访过=0、正在这条路径上=1、查完=2。一旦撞见「正在路径上」的节点，环就现形了。
3. **被拦的瞬间**，输出长这样（真实输出）：
   ```
   FAIL  modules.md: 依赖成环：m1 → m2 → m1

   spec gate: 1 失败 / 6 警告
   ```
   然后 `main()` 返回 1（tools/check_specs.py:357），进程非零退出。
4. **红灯亮起**：如果这是一次真实推送，job① 的这一步退出码非 0 → job 红 → 整个 CI 红。
   GitHub 会在 PR 上打红叉，想合并？门都没有。
5. **还原**：`git checkout -- specs/modules.md`，捣乱撤销，再跑变回 `PASS（6 警告）`。
   （6 条警告全是「规划中模块的目录还不存在」——票还没做到，合法。）

正向路径同理：现在不加环，`check_specs.py` 逐卡校验状态合法、依赖无环无悬空、
验收行绑定了测试标识……全过 → `return 0` → 绿灯。

## 新技术点：GitHub Actions workflow（四要素）

- **名字**：GitHub Actions workflow（工作流），YAML 文件放在仓库 `.github/workflows/` 下
  就会被 GitHub 自动识别，属于 GitHub 平台层，不需要装任何包。
- **作用**：代码托管平台上自带的「定时/触发式跑脚本的机器人」。类比：你在仓库门口装了个
  门禁系统，每次有人刷卡进门（push），系统自动执行一套安检流程。和你本地手动跑
  `pnpm test` 的区别：**机器替你跑、人人推送都跑、想偷懒偷不掉**。
- **参数**（本仓库 ci.yml 用到的关键几个）：
  - `on: push/pull_request + paths`——什么事件触发；`paths` 过滤=只有指定文件变了才跑
    （父仓多项目共存，别为不相关目录白烧机器）。
  - `jobs.<名字>`——一台检查机器；`runs-on: ubuntu-latest`——在哪家的机器上跑。
  - `steps`——机器里依次执行的命令；`uses:` 用现成官方动作（如 `actions/checkout@v4`
    先把代码拉下来），`run:` 跑 shell 命令。
  - `defaults: run: working-directory: soc-demo`——这台机器所有命令默认在子目录里执行
    （因为 workflow 挂在父仓根）。
- **用法**：最小样子就是 ci.yml 的 job①（.github/workflows/ci.yml:13-20）：
  ```yaml
  spec-gate:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: soc-demo } }
    steps:
      - uses: actions/checkout@v4
      - run: python3 tools/check_specs.py
  ```
  本项目四个 job（spec-gate/ts/python/compose）都在这个文件里，想加新门禁就是加 job。

## 关键顿悟

- **退出码是 CI 的通用语言**。Actions 不看你打印了什么，只看进程退出码。所以
  check_specs.py 里所有 `fail()` 先攒进列表、最后统一 `return 1`——攒着是为了一次把
  所有错报完，非零退出是为了让门禁亮红。自己写任何门禁脚本，这条是铁律。
- **PASS 证明不了闸门活着，喂捣蛋输入才算数**。一个永远 PASS 的检查器可能根本没在检查
  （假阴性的门禁比没有门禁更危险——它给你虚假的安全感）。所以验收 2 特意要求「人为造个环
  看它咬不咬」。给闸门做验收，和给业务代码写测试是同一个思维。
- **门要先于货**。CI 是门禁，业务代码是货物。第一批货到之前门必须装好并且**验过是真闸**
  ——否则等 20 张票的货堆满了才发现门是画的，没人愿意停下来返工。

## 亲手验证

```bash
cd /Users/divh/Downloads/安全评估agent/soc-demo

# 1. spec 闸门现在应该是绿的
python3 tools/check_specs.py; echo "exit=$?"
# 应看到：spec gate: PASS（6 警告）  exit=0

# 2. TS 三连（CI 的 ts job 逐字同款命令）
pnpm lint && pnpm typecheck && pnpm test
# 应看到：eslint 无输出；typecheck 4 个包 Done；test 三个服务各 1 passed

# 3. 捣乱实验：给 m2 塞环，看闸门咬人（改前记住第 98 行原文）
#    把 specs/modules.md 第 98 行「- 模块: 无（叶子模块）」改成「- 模块: `m1`」，然后：
python3 tools/check_specs.py; echo "exit=$?"
# 应看到：FAIL  modules.md: 依赖成环：m1 → m2 → m1   exit=1

# 4. 还原（这就是「闸门没被永久弄坏」的证据）
git checkout -- specs/modules.md && python3 tools/check_specs.py
# 应看到：又是 PASS（6 警告）
```

说明一点：本票验证时没有真的往 GitHub 推一个红灯提交去「亲眼看红」——CI job 跑的就是
上面这些命令、一字不差，本地 exit=1 推上去必然红。想亲眼验证的话，开个分支塞环推上去
看 Actions 亮红，也是安全的玩法（别在 main 上留着就行）。
