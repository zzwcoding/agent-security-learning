# 03-01 · 票 03：m2 案件后端——六实体 + 状态机 + 审计 + outbox

## 三问

**位置感**：票地图推进到第一波（业务代码正式开工）：

```
票01 CI守门 ✅ → 票02 票面契约 ✅ → 票03 m2案件后端 ✅你在这里
→ 票04/05 m9基座 → 票06 铸票(py) → 票07 验票闸(TS) → 后续 worker/前端/评测
```

- **这一步是干嘛的？** 造全系统的「档案室」：告警（Alert）、案件（Case）、可观察物
  （Observable）、任务（Task）、时间线（TimelineEntry）、审计（AuditEntry）六类实体
  进 SQLite；告警升级成案件的三种结局；状态乱改一律 409；每个写动作自动留审计；
  写后事件进 outbox 待领。全程确定性代码，没有一个 LLM。
- **什么需求逼我们这么设计？** 后面所有 agent（分诊/调查/富化…）的每个动作都要
  「有地方落、有据可查、有闸可拦」：agent 说「我建了案」——档案室说了算；审计要
  能回答「谁在什么时候把标题从 A 改成 B」——diff 必须自动落；焚毁表要防审批票重放
  ——它必须和业务数据同库同事务（m9 卡备注的决策）。
- **解决什么麻烦？** 把「系统的真相」从各 agent 的嘴里收回到一个地方。agent 是
  不可信的叙述者（PRD 设计哲学），档案室是唯一权威：状态机管「合法演进」，审计管
  「发生过什么」，outbox 管「告诉了谁」。这三样立住了，后面的安全防线才有地基。

## 跟着数据走：一张告警的「成新案」之旅

拿真实测试场景走一遍（src/m2.test.ts「成新案」）：

1. **告警入库**：`createAlert` 写一行 alerts（status=`New`，new_date=现在），两行
   observables（`hostname/web-01`、`ip/10.0.0.5`），一个 audit（create），一条 outbox
   事件 `alert.created`——**这四笔在同一个 SQLite 事务里**，要么全有要么全无。
2. **分诊员点「升级成案」**：`POST /alerts/:id/create-case`。store 先做状态机查表：
   迁移表里 alert 的 `New` 后面只挂着 `InProgress`——放行。
3. **档案室连动**：cases 表多一行（编号自动 +1，`case_000001`，linkedAlerts 记下这张
   告警）；两条 observables 的 `case_id` 回填成新案 id（告警的物证归了案）；timeline
   多一条系统条目「case created from alert …」；audit 多两条（建案、改告警状态）。
4. **捣乱者上场**：他试图让这张**还没开过工**的告警直接关掉
   （New→Closed 是告警状态机里不存在的流转）。`assertTransition("alert","New","Closed")`
   查表没查到 → 抛 `InvalidTransitionError` → Fastify 错误处理器映射 →
   **409 `{"error":"InvalidTransition"}`**，档案室纹丝不动。这就是 INV-10 的本体：
   状态只能按表流转，不许静默改写。

## 新技术点：better-sqlite3（四要素）

- **名字**：better-sqlite3，Node.js 生态最快的 SQLite 驱动，同步 API（不用 async/await）。
- **作用**：给 Node 一个嵌入式数据库——不是「连上数据库服务器」，而是**直接打开一个
  文件**（或 `:memory:` 纯内存库）当数据库用。类比：别人是打电话问档案室，它是把
  档案室整个搬进你工位。同步在这个场景是优点：没有网络往返，一行代码就是一次磁盘写。
- **参数**：`new Database(path)`——path 给 `:memory:` 就是内存库（进程一死库就没了，
  测试专用）；`db.pragma("journal_mode = WAL")` 开写日志（单写者多读不堵）；
  `db.prepare(sql).run/get/all(...)` 三件套是预编译语句，参数用 `?` 占位防注入。
- **用法**（本项目就在 db.ts/store.ts）：
  ```ts
  const db = new Database(":memory:");
  db.transaction(() => {          // 事务：里面的写要么全成功要么全回滚
    db.prepare("INSERT INTO cases …").run(id, title);
    recordAudit(db, ctx, "create", id, "case", { created: { title } });
  })();
  ```
  教学版选它的理由：无服务无端口、测试秒级建库，还天然支持「审计与业务同事务」——
  换 PostgreSQL 这句话就要改成监听 binlog 之类的大工程。本地装它时被 pnpm 10 拦了
  原生构建脚本，在根 package.json 加 `pnpm.onlyBuiltDependencies: ["better-sqlite3"]`
  放行（CI 同样生效）。

## 关键顿悟

- **状态机是查表，不是散落的 if**。迁移表只在 statemachine.ts 一处：
  `{ alert: { New: ["InProgress"], InProgress: ["Imported","Closed"], … } }`。所有
  业务动作先查表再动手——INV-10 的「状态机之外的变更一律 409」因此能被 18 格
  组合测试逐格验证。状态规则一旦抄第二份，两处必然漂移。
- **审计可信的前提是同事务**。「signal 式拦截器」听着玄，实现就是：业务写和审计写
  放进同一个 `db.transaction`。若先写业务再补审计，进程中途崩掉就会出现「案卷存在
  但没人承认建过它」——审计的完整性靠的是数据库原子性，不是代码自觉。
- **outbox 是微服务世界的「先记账再喊话」**。写库成功但广播失败 = 消费者永远不知道
  这事；所以事件先作为一行插进 outbox_events（和业务同事务），消费者凭游标
  `?after=<id>` 来领。这就是 m2 卡说「首版用 SQLite 轮询、将来可换 Kafka」的原因：
  接口（可轮询的事件流）先立住，运输工具以后随便换。
