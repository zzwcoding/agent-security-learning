# 场景 9 · 步 9.1 —— 发起假设与五态门口（proposed→hunting 同事务口径）

> 场景 1《一条 TP 告警的一生》讲的是**被动链**：探头推来报案单，系统像接警台一样
> 沿「进门→分诊→建案」往前走——每一步的输入都是上一步递过来的。场景 9 讲的是**主动环**：
> 没有新告警，数字员工自己写下一张「待验证的怀疑」——[TERMS「侦查怀疑书」](TERMS.md)条
> （又称狩猎立项，hypothesis）——然后一轮一轮「选组合→扇出取证→收敛裁决」（即
> [TERMS「撒出去·收回来」](TERMS.md)条的扇出/收敛），直到证据
> 够定性。这是报案电话之外的另一条命脉，m14 编排循环的入口。
>
> 本步只回答三个问题：**怀疑书怎么立的？**（M2 建档 + 同事务发事件）**五态状态机的门口
> 长什么样？**（proposed→hunting→concluded/refuted/cancelled）**轮 1 是谁、在什么时候拉起的？**
> （autorun 消费 hypothesis.created）。planner 怎么选组合留到 9.2，扇出留到 9.3。
>
> 术语卡：本篇比喻全部沿用 [TERMS.md](TERMS.md)；编排循环的八个新词条在 TERMS「编排循环」节，
> 正文第一次遇到只做回指、不再各说各话；每站开头的 📍 行是
> [9-big-picture.html](9-big-picture.html) 里的同款节点，读文时可以到图上对照。

## 一、操作（位置感）

打开 web 端（http://localhost:5173）的「狩猎」页。跟场景 1 的流水线页比一下：那边看的是
**run 直播**（一个格子接一个格子），这边看的是**假设台账**——列表按五态打 Tag，顶部有
发起表单（假设文本 + 模板下拉），点开一条假设能看到它的**轮次视图**（9.5 细讲）。

先看模板下拉里有什么（这就是轮 1 之前唯一需要人做的选择）：

```bash
curl -s localhost:3003/api/v1/templates | python3 -c "
import json,sys
for t in json.load(sys.stdin)['templates']:
    print(t['template_id'],'| 菜单:',t['menu'],'| max_rounds:',t['max_rounds'])"
```

预期：四张卡——`hunt_webshell` / `hunt_c2_beacon` / `hunt_credential_leak`（票 79 三族）
和 `ir_host_compromise`（票 80 IR 族），每张卡带着自己的**能力菜单**
（[TERMS「派工菜单」](TERMS.md)条：菜单围栏里的工具名数组）和 `max_rounds: 6`。
菜单是什么、为什么每张卡不一样，9.2 专门讲；本步记住一句话就够了：
**怀疑书生下来就挂在一族预案卡上，卡片决定了它后续每一步能点什么菜**。

然后发起一条怀疑书（下面命令会贯穿本步全程，$HYP 就是它）：

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST localhost:3002/api/v1/hypotheses \
  -H 'content-type: application/json' -H 'x-actor-id: soc1@soc.local' \
  -d '{"text":"怀疑 web01 被植入了 webshell：上传目录出现新脚本文件","template_id":"hunt_webshell"}'
```

预期：`HTTP 201`，响应里 `status:"proposed"`、`hypothesis_id:"hyp_…"`。**接下来什么都别按**，
隔两三秒再查一次详情，状态自己变成了 `hunting`——没人点按钮，是谁干的？这就是本步的主线。


### 站 1 · 建档：档案和叫号永远对得上

📍 大图节点:HYP_CREATE(9.1 发起假设与五态门口)

建档本体是一件事务里写三样东西——账面行、审计、叫号屏：

📄 [services/case-backend/src/hypotheses.ts:107-125](soc-demo/services/case-backend/src/hypotheses.ts#L107)

```ts
export function createHypothesis(
  db: DB,
  input: HypothesisInput,
  ctx: Ctx,
): Record<string, unknown> {
  return db.transaction(() => {
    if (!input.text?.trim()) throw new HypothesisInvalidError("text_required");
    const id = `hyp_${randomUUID()}`;
    db.prepare(
      `INSERT INTO hypotheses (id, template_id, text, status, proposed_by, created_at)
       VALUES (?, ?, ?, 'proposed', ?, ?)`,
    ).run(id, input.template_id ?? "", input.text, input.proposed_by ?? ctx.actor.id, nowMs());
    recordAudit(db, ctx, "create", id, { ... });
    emitEvent(db, "hypothesis.created", { hypothesisId: id, templateId: input.template_id ?? "" });
    return mapHypothesis(requireHypothesisRow(db, id)) as Record<string, unknown>;
  })();
}
```

这就是 [TERMS「叫号屏」](TERMS.md)条说的**事务型 outbox**（INV-6 家族）在第七实体上的复刻：
账面行（hypotheses 表，proposed）、审计（INV-8 五要素）、拉起信号（`hypothesis.created`）
**同事务**落库——不存在「账还没立、拉起信号先飞出去」的中间态。文件头注释把口径写成
「行为约定 1 的同事务口径」（[hypotheses.ts:5-6](soc-demo/services/case-backend/src/hypotheses.ts#L5)）：
**提出即落档案室账面、同事务发事件**。对比场景 1 的告警落库（1.2 的 `alert.created` 同事务）：
同一个模式第三次出场，因为「账面」和「叫号」分家是所有对不上账事故的起点。

还有一个值得点名的口径：提出者不止人。`proposed_by` 落的是调用方 actor——人（`soc1@soc.local`）
可以提，紫队 eval 的攻击 fixture 也会自动转出怀疑书（actor=system，S12 的主角）。接口不关心
对面是人还是程序，只关心**这一笔有没有记账**。

### 站 2 · 五态门口：proposed 是候诊室，hunting 才算开查

📍 大图节点:HYP_FSM(9.1 发起假设与五态门口)

假设的合法流转表全仓只有一处：

📄 [services/case-backend/src/statemachine.ts:27-33](soc-demo/services/case-backend/src/statemachine.ts#L27)

```ts
  hypothesis: {
    proposed: ["hunting"],
    hunting: ["concluded", "refuted", "cancelled"],
    concluded: [],
    refuted: [],
    cancelled: [],
  },
```

四个必看的点：

1. **proposed 只有一条出路**：进 `hunting`。谁来推这一步？不是人，是循环——9.2 会看到
   轮 1 的 intake 节点开跑前把 proposed 推成 hunting（「开查了」），这条迁移的 actor 是
   `agent:hunt_flow`。
2. **三个终态都是空数组**：concluded（命中）/ refuted（证伪）/ cancelled（取消）——
   终态不可回退，表外迁移一律 409（INV-10）。TERMS「状态机速记」的 hypothesis 行
   就是这张表的速记版。
3. **取消不是第五条路，是 hunting 的一条出路**：`cancel_reason` 只是 cancelled 上的
   原因标注（user_cancelled/planner_broken/spin/budget + 循环侧 time/budget_rounds，
   六因一态）——9.6 捣乱实验会亲眼看到其中两因。
4. **refuted 是正经终态不是失败**：证伪归档是有价值的产物（TERMS「无人值守破案率」条的
   「诚实的阴性资产」），9.6 收敛分岔讲它的另一半。

**为什么状态机要做成查表而不是 if？** 跟 alert/case/kbentry 用的是同一张 `assertTransition`
查表件（[hypotheses.ts:141](soc-demo/services/case-backend/src/hypotheses.ts#L141) 调用处）——
实体越多，「谁能在什么状态干什么」越不能散落成散装 if。表就是闸：任何代码想把 concluded
改回 hunting，都在这一行被 409 弹回来，不需要每个调用点自觉。

### 站 3 · 看板的接了第二单：hypothesis.created → hunt_flow 轮 1

📍 大图节点:AUTORUN_HUNT(9.1 发起假设与五态门口)

[TERMS「看板的」](TERMS.md)条那条 2 秒 autorun 循环，场景 1 里只挂了两个事件分支
（alert.created / case.closed）；编排循环给它解禁了第三、第四个分支：

📄 [services/agent/src/autorun.ts:222-241](soc-demo/services/agent/src/autorun.ts#L222)

```ts
  if (e.topic === "hypothesis.created") {
    // 票 73（L0 派发中裁决①，autorun.ts 的唯一解禁分支）：hypothesis.created → hunt_flow
    // 轮 1 拉起——spec 行为约定 1「假设提交即置 proposed 并拉起 hunt_flow」的消费半边，
    // 照 alert.created 先例。防重两道闸缺一不可（hasActiveRun + hasRoundRun，见 deps 注释）；
    // 拉起经 deps.launch（index.ts 装配 = HuntLauncher.launchRound：door 正门 + 簿记锚落账），
    const hypId = typeof e.payload.hypothesisId === "string" ? e.payload.hypothesisId : "";
    if (!hypId) return { action: "skipped", skip: { topic: e.topic, refId: "", reason: "malformed_payload" } };
    const seen = batchSeen.get("hunt_flow") ?? new Set<string>();
    if (seen.has(hypId)) return { action: "skipped", skip: { topic: e.topic, refId: hypId, reason: "dup_batch" } };
    if (deps.hasActiveRun("hunt_flow", hypId)) {
      return { action: "skipped", skip: { topic: e.topic, refId: hypId, reason: "run_exists" } };
    }
    if (deps.hasRoundRun(hypId, 1)) {
      return { action: "skipped", skip: { topic: e.topic, refId: hypId, reason: "round_exists" } };
    }
    try {
      await deps.launch({ kind: "hunt_flow", hypothesisId: hypId });
    } catch (err) {
      return { action: "failed", error: String(err) };
    }
```

三道防重闸一个都不能少（[TERMS「防重三闸」](TERMS.md)条的 hunt 版）：

- `dup_batch`：同一批事件里重复投递（内存去重）；
- `run_exists`：agent runs 表里该假设已有**非 failed** 的 hunt_flow run
  （[autorun.ts:127-132](soc-demo/services/agent/src/autorun.ts#L127) 的 `runsLookup`，
  票 90 后读的是 runs.hypothesis_id 专用列）；
- `round_exists`：m14 簿记 `hunt_run_links` 里该假设第 1 轮已有锚
  （`hasRoundRun(hypId, 1)`，真相源是 ledger 的 `findByRound`）。

为什么 runs 表之外还要第二道簿记锚？autorun.ts:107-111 的注释写了分工：runs 行挡
「进行中/已完成」，簿记锚挡「游标丢失重放 + 轮 1 执行失败后的自动重拉」——后者是轮次机
的语义（失败轮允许重试），不归防重管。两把锁各管各的钥匙。

第四个分支（`hypothesis.cancelled`，[autorun.ts:249-276](soc-demo/services/agent/src/autorun.ts#L249)）
本步先不展开——它通向 9.6 捣乱实验①的取消停止链，这里只记住：看板的现在管四件事，
拉起和取消各占一半。

拉起失败（正门非 2xx）= 游标不动、下轮重试（at-least-once，与 alert.created 同款语义）。
「不丢」优先于「不阻塞」，重试安全由上面三道闸兜住。

### 站 4 · 正门：第三种 intake

📍 大图节点:RUN_GATE_HUNT(9.1 发起假设与五态门口)

体检项目由注册表的 `intake` 字段说了算。编排循环的两个 kind 吃第三种 id：

📄 [services/agent/src/app.ts:312-327](soc-demo/services/agent/src/app.ts#L312)


### 站 5 · 轮号簿记：轮 1 的锚从这里落

📍 大图节点:LAUNCH_ROUND(9.1 发起假设与五态门口)

📄 [services/agent/src/orchestration/launcher.ts:23-36](soc-demo/services/agent/src/orchestration/launcher.ts#L23)

```ts

      // 票 90 正名：door wire 发 hypothesis_id（runs.hypothesis_id 专用列在位，
      // case_id 位承载清偿——wire 面不再超载 case_id）。
```

`hunt_run_links` 表（[ledger.ts:41-53](soc-demo/services/agent/src/orchestration/ledger.ts#L41) 的

autorun 拉起这一刻就落了，比图开跑还早——**先有轮号，后有轮**。

## 三、服务与中间件卡

**卡 1 · ▼假设实体：账面 + 状态机 + 同事务 outbox（第七实体，自研）**

- **它是什么**：M2 里第七个实体（告警/案件/审批卡/KB 提案/时间线/审计之后的又一个），
  三件套形态照抄 kb.ts 先例：SQLite 账面（hypotheses + hypothesis_rounds 两张表，
  [db.ts:147](soc-demo/services/case-backend/src/db.ts#L147)、[db.ts:163](soc-demo/services/case-backend/src/db.ts#L163)）、
  查表状态机、同事务 outbox。
- **市面替代**：Wazuh/TheHive 这类平台把「猎手想验证什么」通常记在案外（case 的 task 或
  外部笔记），没有一等实体的状态机；或者反过来用工作流引擎（Temporal/Camunda）把状态机
  交给框架。
- **为何这么选**：假设的状态迁移要跟**审计、outbox、轮次归集**绑在一个事务里，这恰恰是
  「拿别人的工作流引擎」最别扭的地方——外部引擎的状态和自家账面永远隔着一次网络调用。
  一张 SQLite 表 + 查表状态机，409/审计/事件全在本地事务内闭环，与 1.2 的告警状态机、
  3.x 的 KB 提案状态机同一份心智。
- **业务上怎么选**：状态要不要跟钱袋子（审计/下游联动）同生共死？要——自建实体+查表
  状态机；只是流程编排、状态跟账面可以松耦合——才轮到外部工作流引擎。

## 场景题闯关（本步 1 题）

**Q：autorun 拉起轮 1 有三道防重闸（dup_batch/run_exists/round_exists）。runs 表的
run_exists 已经挡住「同假设已有 run」了，为什么还需要查 hunt_run_links 的 round_exists？**
用「游标丢了会怎样」推一遍。

<details><summary>答案（点击展开）</summary>

两条闸的钥匙不同：runs 行挡的是「进行中/已完成」的 run；簿记锚挡的是**游标丢失重放 +
轮 1 执行失败后的自动重拉**。autorun 的消费游标持久在 agent 库（event_cursors），但假设
游标行丢了、outbox 从头重放，runs 表里那条轮 1 run 若已经 failed（重试语义不挡 failed），
run_exists 放行——此时 round_exists 查 hunt_run_links 的轮锚：锚在（拉起时就落账，9.1 站 5）
→ 跳过，不会给同一条假设起第二个轮 1 run。反之只有 runs 闸也不够：run 行可能被人清、
簿记锚还在——**「拉起过」这个事实的真相源是簿记，不是 run 行的存在性**。</details>
