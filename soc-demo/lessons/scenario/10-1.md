[站1] executeStartJob：payload 里没有票 → ticketSpecFor 按注册表现铸父票 → 组图开跑

### 站 1 · 父票：铸于 run 起，面是"决策面的菜单"

📍 大图节点:DISPATCH_LOOP → PARENT_MINT(10.1 两票时序)

202 秒回那一刻**还没有票**——票是分发循环领走 start 任务、真正"开工"那一刻才铸的
（[app.ts:537-568](soc-demo/services/agent/src/app.ts#L537)）：

```ts
  async function executeStartJob(
    runId: string,
    actor?: { type: string; id: string },
    payload?: Record<string, unknown> | null,
  ): Promise<void> {
    const run = requireRun(db, runId);
    let nodes = opts.nodes;
    if (opts.makeNodes) {
      try {
        const preTicket = typeof payload?.ticket === "string" ? payload.ticket : null;
        const task = taskOf(payload?.task);
        const spec = preTicket ? null : ticketSpecFor(run.kind, task);
        const minted = preTicket
          ? { token: preTicket }
          : await mint.mintTaskTicket({ ... });
        nodes = await opts.makeNodes(run, minted.token, { actor });
```

读三个点：①`preTicket` 为空（hunt_flow 的 start 载荷只有 actor，实测
`{"actor":{"type":"system","id":"internal"}}`）→ 走 `ticketSpecFor` 按注册表现铸；②铸完
**立刻组图**（`opts.makeNodes(run, minted.token, …)`）——票先于图，无票不组图；③注释口径
「票 76：dispatch 时已铸的 hunt_task 子票随任务在册 → 直接用（时序归 dispatch）；其余路径
按票面解析器现铸（旧 kind 恒注册表票面，时序零变化）」
（[app.ts:535-536](soc-demo/services/agent/src/app.ts#L535)）——**一个函数里住着两种铸票
时序**，这是 T11/T12 的代码分界。

父票面印的是什么？注册表 hunt_flow 行
（[run-kinds.ts:300](soc-demo/services/agent/src/run-kinds.ts#L300)）：

```ts
    ticket: { sub: "agent:hunt_flow", scope: ["case:read"], allowedTools: huntFlowTicketFace() },
```

`huntFlowTicketFace()`（[hunt-pack.ts:88-90](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L88)）
= 机制默认菜单 ∪ 三族模板菜单 ∪ hypothesis_register——我实测正好 **10 件**：
`kb_lookup, siem_query, related_alerts, playbook_lookup, graph_query, outbound_conn_query,
proc_lineage_query, file_change_query, web_access_query, hypothesis_register`。全是 L0/L1
（INV-3：决策面物理无 L2）。注意 [TERMS「派工菜单」](TERMS.md)条的分层口径：**这 10 件是
"父票面"（planner 只读面 + register），不是 planner 每轮看到的菜单**——每轮菜单是模板注入
的子集（hunt_webshell 族只有 4-5 件），planner 只能照当轮菜单点菜（10.3 的闸），父票面
只是"所有可能菜单的并集"这一个真相源。

### 站 2 · 子票：铸于正门内，面只装一件工具

📍 大图节点:CHILD_MINT(10.1 两票时序)

dispatch 逐任务打正门（[launcher.ts:37-40](soc-demo/services/agent/src/orchestration/launcher.ts#L37)，
`door.post({ kind: "hunt_task", hypothesis_id, task })`），门内看到 hunt_task 带任务上下文，
就地现铸窄票（[app.ts:374-394](soc-demo/services/agent/src/app.ts#L374)）：

```ts
    let childTicket: string | null = null;
    if (
      body.kind === "hunt_task" && opts.makeNodes &&
      body.task !== undefined && typeof body.task?.tool === "string" && body.task.tool
    ) {
      try {
        const spec = ticketSpecFor(body.kind, body.task);
        const minted = await mint.mintTaskTicket({
          jti: `tk_${randomUUID()}`, sub: spec.sub, caseId: run.caseId, runId: run.id,
          scope: [...spec.scope], allowedTools: [...spec.allowedTools],
        });
        childTicket = minted.token;
      } catch (err) {
        failUnTicketedRun(run.id, err);
        return reply.status(502).send({ error: "mint_failed" });
      }
    }
```

解析器把票面收到多窄？（[run-kinds.ts:342-354](soc-demo/services/agent/src/run-kinds.ts#L342)）

```ts
export function ticketSpecFor(kind: string, task?: { tool?: unknown } | null): RunKindTicket {
  const spec = requireRunKind(kind).ticket;
  if (kind !== "hunt_task" || !task) return spec;
  // 显式任务上下文但 tool 缺失/为空 = 载荷畸形——fail-closed 拒解析，绝不静默放宽到菜单级
  if (typeof task.tool !== "string" || !task.tool) {
    throw new Error("hunt_task 任务上下文缺 tool，子票面无法解析（fail-closed）");
  }
  const parentFace = REGISTRY.hunt_flow.ticket.allowedTools;
  if (!parentFace.includes(task.tool)) {
    throw new Error(`hunt_task 子票拒铸：工具 ${task.tool} 不在父票菜单内（INV-11，铸票缝 fail-closed）`);
  }
  return { ...spec, allowedTools: [task.tool] };
}
```

`allowedTools: [task.tool]`——**一行就是窄票的全部秘密**：票面只装这一趟唯一的那件工具。
第 349-352 行是 [TERMS「派工菜单」](TERMS.md)条说的 INV-11 **第二道闸（铸票缝）**：任务
工具不在父票菜单内 → 拒铸抛错 → 门把这条 run 标 failed(mint_failed) + 502——越界任务在
铸票唯一通道上就拿不到票。10.2 会把这道闸拆开打一遍。

### 站 3 · 两代票的落盘差异：父票不落盘，子票在册

📍 大图节点:T_RUNJOBS(10.1 两票时序)

子票跟着 start 任务**落盘**（[app.ts:400-404](soc-demo/services/agent/src/app.ts#L400)
`enqueueRunJob(db, run.id, "start", { actor, …(childTicket ? { ticket: childTicket } : {}),
…(body.task ? { task: body.task } : {}) })`），执行件直接取用——注释那句「不再按 kind 二次
铸」就是它。父票则只活在组图调用栈里，**不入库**。这个差异是"为什么子票要在门内现铸"的
直接后果：dispatch 拉起子 run 时任务才存在，票必须跟着任务走才能在异步队列里不丢。

## 三、服务与中间件卡

**卡 1 · ▼两票制（父票 + narrow-scope 子票，票 76）**

- **它是什么**：扇出型 run 的票分两层——父票铸于 run 起（决策面能力并集，面 ≈ 菜单真相
  源），子票铸于 dispatch 正门内（每任务单工具），`ticketSpecFor` 是两张票共同的解析出口。
- **市面替代**：一张大票跑全程（OAuth offline_access + 宽 scope 的常见反模式）；或运行时
  策略引擎逐请求裁权（OPA/Cedar 形态）。
- **为何这么选**：大票 = 并行变横向越权 + 泄漏面最大；运行时裁权 = 每动作多一跳出网、
  引擎故障即全场停摆。铸造时收窄把权限最小化压到**发牌时**，验票闸本地验、fail-closed，
  异步队列里票随任务走、无"先拉起再补票"的悬置窗口。
- **业务上怎么选**：出工前能开清单的 → 铸窄票；真要运行时才知道的 → 才上策略引擎，且必须
  给引擎配 fail-closed 缺省。宁可票多发几张，不让一张票什么都干。

## 六、捣乱实验（必选）

**捣乱 A · 不带任务直拉 hunt_task——窄票机制不会"送宽票"：**

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST localhost:3003/internal/runs \
  -H 'content-type: application/json' -d '{"kind":"hunt_task","hypothesis_id":"'$HYP'"}'
```

预期：`202`（无任务上下文 → ticketSpecFor 走注册表菜单级兜底，
[run-kinds.ts:344](soc-demo/services/agent/src/run-kinds.ts#L344) `if (kind !== "hunt_task"
|| !task) return spec;`——直拉/恢复路径的旧口径），run 正常建。但这条"白拿宽票"的 run 跑
不起来：它绕开了 launcher 的簿记路径，intake 炸「簿记缺行」（机制桩 fail-closed，9.3 捣乱 B
已实测过同款）。**结论：门不会替你造任务，但也不会给你一张能跑的大票**——宽进窄出，
簿记是拉起合法性的账。

（10.2 的捣乱①是本步捣乱 A 的强化版：任务带了，但工具越界——那才是"伪造超宽子票"的正戏。）

## 场景题闯关（本步 1 题）

**Q：把 executeStartJob 的 `preTicket` 逻辑删掉、改成"所有 kind 都在 executeStartJob 现铸"，
两票制会退化成什么？用 T12 的三条时序断言逐条推。**

<details><summary>答案（点击展开）</summary>

退化成"子票也铸于 run 起"的单票时序版，但注意子 run 是 dispatch **运行中**才决定要不要
拉起的——executeStartJob 根本不知道未来任务。硬要保留扇出只有两条路：①子 run 拉起重走
一遍 executeStartJob 式现铸（时序从"门内"挪到"门后"，票与任务分离，出现"run 行已建、票
还没铸"的悬置窗口——T15 的无悬置断言红）；②回到"一张大票跑全程"（T12 的
`claims.allowed_tools` 单工具断言红、T13 的子票⊆父菜单且单工具断言红）。T12 三条断言
（晚于 planner/铸于门内/每任务恰一枚）钉的正是"权限分配跟着任务走"这个时序本身——
**删掉 preTicket 不是省一次查表，是把"发牌时最小化"退化成"用牌时猜需求"**。</details>
