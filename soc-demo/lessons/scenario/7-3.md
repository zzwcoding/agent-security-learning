### 站 1 · 闸的三岔口：分级只在"两手空空"时出场

[verify-ticket.ts:196-208](soc-demo/services/agent/src/verify-ticket.ts#L196)：

```ts

    // 不由票面 fixture 覆盖——README「reason 枚举」节）
    if (tierOf(toolCall.name) === 0) return { allow: true, reason: "allow" }; // L0 只读免验
    if (tierOf(toolCall.name) === 2) return deny("require_approval"); // L2 必须经人审批铸票（FR-S2.4）
    return deny("no_ticket"); // L1 写工具（含未登记默认级）没带票
  } catch {
    return deny("signature_invalid");
  }
```

（此块上邻还有两行 `if (typeof ctx.approvalToken === "string") …` / `if (typeof
ctx.ticket === "string") …` 的分岔，原文见 [verify-ticket.ts:197-198](soc-demo/services/agent/src/verify-ticket.ts#L197)。）
三岔口的优先级：**先看手里有没有签名票，再看登记表**。手里真有票，登记表的 tier
根本不参与裁决——这是理解本步全部对照实验的钥匙。教具 S1 幕的实测（无票闯闸）：

```
list_approvals tierOf = 1（登记行 tier=L1）
list_approvals（无票） → 403 no_ticket
get_alert（无票，对照：L0 免验待遇） → allow（allow）
```

用上岗黑话念一遍：list_approvals 是"要持票才能上的岗"（L1），空手到岗亭 = 403
no_ticket——**没配枪（没票）就别想上岗**；隔壁 get_alert 是免验岗（L0），空手
直接过。注意 403 no_ticket 的另一层含义：**登记成 L1 和不登记（默认级也是 L1）
在闸这个口上是同一个回答**——登记改变的从来不是"无票吃不吃 403"，是别的东西
（站 4 揭底）。

### 站 2 · 持票路径：票面五连检查

[verify-ticket.ts:211-224](soc-demo/services/agent/src/verify-ticket.ts#L211)：

```ts
// 任务票路径（PRD §5.8）：worker 的任务级最小 scope 票
function verifyTaskTicket(
  key: Buffer,
  toolCall: { name: string; params?: unknown },
  ctx: VerifyCtx,
  nowSec: number,
): VerifyResult {
  const p = asTicketClaims(unseal(key, ctx.ticket as string));
  if (nowSec >= p.exp) return deny("token_expired"); // JWT 语义：当前时刻须严格早于 exp（py 同式）
  if (ctx.used?.has(p.jti)) return deny("token_used"); // 重放防线（INV-2：焚毁表是唯一真相）
  if (!p.allowed_tools.includes(toolCall.name)) return deny("scope_insufficient"); // INV-3：任务票永不含 L2
  if (ctx.caseId !== undefined && p.case_id !== ctx.caseId) return deny("scope_insufficient"); // case 绑定
  if (ctx.runId !== undefined && p.run_id !== ctx.run_id) return deny("scope_insufficient"); // run 绑定
  return { allow: true, reason: "allow", payload: p };
}
```

注意第 220 行那个 `includes(toolCall.name)`——**字符串精确匹配**，这就是大小写
戏法的案发现场。也注意这段里**没有一行读登记表**：持票裁决只认票面字节。S2 幕
请真网关铸票（教具 [7-3-gate-demo.mts:71-78](soc-demo/lessons/scenario/scripts/7-3-gate-demo.mts#L71)）：

```ts
const mintBody = {
  type: "task_ticket",
  jti: `tk_s7_${randomUUID().slice(0, 8)}`,
  sub: "agent:case_flow",
  case_id: CASE_ID,
  run_id: RUN_ID,
  scope: ["case:read", "case:write"],
  allowed_tools: ["get_alert", "siem_query", "list_approvals"],
};
```

实测回包：`payload.exp=…（TTL 900s）、allowed_tools=["get_alert","siem_query",
"list_approvals"]`——新工具的名字第一次出现在一张**真签名**的任务票上。重要口径
（1-3 讲过的铸票口脾气）：**网关铸票不查登记表**，`allowed_tools` 签什么就是什么。
那"票面合法"谁管？票面 ⊆ 登记表由对账测试咬死（tools-manifest.test.ts 的"五个
run kind 票面 allowedTools 全部已登记"）——生产里票面来自 run-kinds 注册表，注册
表来自 worker TOOLS 常量，TOOLS ⊆ manifest 全程有测试盯防。我们的票是教具直接
向铸票口点的菜——这正是这条防线要防的"内部人绕过注册表点菜"形态，教学期拿来
做对照正合适（防线分层：闸不查表，表管的是注册表那一层）。

**② 是本步最反直觉的事实**：登记行摘了，票还好使——闸的持票通道从头到尾没有

①无票通道的分级回退（默认级 L1，与登记 L1 同值，本例恰好无感；若摘的是 L0/L2

"票面 ⊆ manifest"有测试咬死，摘行后任何把 list_approvals 加回票面的改动都过不了
CI。一句话：**登记表的效力前移到铸票与对账，不在闸的持票通道**——已铸的票是
签名事实，摘行不溯及既往。

## 三、服务与中间件卡

**卡 1 · 铸票口与验票口的分工（离线授权的两端）**

- **它是什么**：gateway /internal/mint 只管"签字"（HMAC 盖章，字段照单全收）；
  agent 的 verifyTicket 只管"查票"（验签+五连检查）。两端共享的只有密钥与票型
  契约——铸票口不查登记表、验票口不查注册表，各自深模块。
- **市面对照**：①OAuth2 授权服务器 vs 资源服务器（同构：AS 签 token，RS 验
  token，中间不通信）；②Kerberos 的 KDC 与服务端；③单体应用"发权限时顺手查库"
  （耦合在发端，扩不动）。
- **本项目为什么分工**：验票在每一个工具调用的热路径上，铸票在冷路径上——分开
  之后验票侧零网络依赖（本地验签，FGA 停机都影响不到它，4.2 的闸是另一道）。
  代价是"票面合法性"只能靠**铸票上游的构造纪律 + 测试**保障，本步站 4 的对照
  实验就是这条边界的实况演示。
- **业务上怎么选**：授权面要拆"签发/验证"两端时，先画清楚"哪一层知识在哪端"——
  分级知识在登记表（对账管）、票面事实在票上（验签管）、执行意愿在调用方（注册
  表管）。三张清单分家，才拆得动。

**卡 2 · 三层能力面：登记面 / 票面 / 执行体**

- **它是什么**：一个工具在 run 里"真的能被调到"要连过三层——①登记面（manifest
  在册，分级/族有身份）；②票面（某个 run kind 的 allowedTools 包含它）；③执行体
  （某个 worker 的 execTool/只读路由有它的 case，或 LLM 会提名它）。三层各自有
  独立的守门机制：对账测试/铸票注册表/worker 代码。
- **市面对照**：①IAM 的"权限已授予"vs"应用菜单已实现"vs"前端按钮已渲染"三层
  脱节（经典工单：权限开了功能没有）；②API 网关的路由表/配额表/后端实现。
- **本项目为什么显式分三层**：安全语义挂在第一层（分级决定闸行为），能力语义挂
  在后两层。分开之后，"登记先行"成为可能——先给身份、再谈持票、最后接执行，
  每一步都可独立验收（本场景 7.2/7.3 就是在第一二层逗留）。
- **业务上怎么选**：新能力上线的节奏判据——凡挂安全语义的面（分级/授权），宁可
  三层分开逐步收编，也不要一把梭"代码即注册"（漏一处静默漂移的病灶就在这）。

**捣乱 B · 大小写戏法**（S4 幕）：持真票、把工具名写成大写开头的 `List_Approvals`：

```
  审计 DENIED#1: tool=List_Approvals reason=scope_insufficient result=DENIED details={…}
  run 被强杀，错误：scenario7_gate_denied:scope_insufficient
```

**判据**：403 scope_insufficient（不是 no_ticket——票在手、名字对不上）+ 闸拒
审计落账 + 抛错强杀（INV-1 不吞错）。呼应 7.1 捣乱 B：登记正则拒绝大写名字 →
就算有人手工塞进登记表和票面，闸的精确匹配还是最后一道关口。工具名在整条链上
是**同一个字符串常量**，任何一环的大小写漂移都会被某一层咬住——但哪层咬是运气，
纪律是全链一致。

**捣乱 C · 票面不含它**（S6 幕，三态辨析的收尾）：铸一张 `allowed_tools` 只有
`["get_alert","siem_query"]` 的票，拿去问 list_approvals：

```
手里没票           → 403 no_ticket
票里没这个工具      → 403 scope_insufficient
票里恰好有（S2 那张） → allow
```

**判据**：两种 403 的分界线在"票是否存在"，不在"票是否覆盖"——no_ticket 是
"岗亭要票"，scope_insufficient 是"票不对口"。排查口诀：先看手里有没有签名票，
再看票面 `allowed_tools` 逐字（大小写！）含不含被调工具，最后才轮到查登记表
（分级/默认级）——顺序就是站 1 三岔口的代码顺序。

**本步小结**：list_approvals 过完了闸的洗礼——无票 403、真网关铸票后持票过闸、
真 handler 查出真台账；三场对照（摘行/大小写/票面不含）把"登记的效力范围"划得
清清楚楚：闸认票不认表，登记执法在铸票与对账；INV-3 对号（零审批卡、零 L2 票面）。
