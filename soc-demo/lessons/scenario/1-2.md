# 1-2 · 去重与落库：档案室的查重台账

> 场景 1「一条 TP 告警的一生」第 2 步。上一步前台把单子递到了档案室门口，这一步进
> 档案室内部，看它怎么做到"同一起案件只建一次档"。

**位置感**：

```
✅ 1.1 布景与推单
✅ 1.2 去重与落库（你在这里）
⬜ 1.3 自动拉起与铸票
⬜ 1.4 分诊六节点（上）
⬜ 1.5 分诊六节点（下）
⬜ 1.6 收官透视
```

## 一、这一步做什么

上一步的结尾，前台（ingest）把翻译好的单子 POST 给了档案室（case-backend）。档案室
收到后要回答两个问题：

1. **这是新案还是旧案？** 同一条探头规则反复响是常态（比如每次有人暴力猜密码，探头
   都报同一个警情编号）——每次都建新档案，档案室早就被同一起案子塞满了。所以要查重。
2. **建档之后谁接着干？** 真正的分诊在后面的"数字员工"那里，档案室只负责把"有新案了"
   这个消息**登记在叫号屏上**——这张屏叫 outbox（出站箱），下一步的自动化就是看屏干活的人。

本步讲透档案室的两个内部机制：**upsert 查重**（INV-6 的主体）和**同事务落三张表**
（档案 + 台账 + 叫号屏，INV-8 的实现方式）。

## 二、调用链

先接上一步的尾巴，再进档案室内部：

```
前台 ingest（上一步的站 5）
  │ POST http://case-backend:3002/api/v1/alerts   （同步站柜台）
  ▼
▼ services/case-backend（档案室 :3002，框架 ▲Fastify）
    app.ts:89 路由 → 再验四要素（不信任上一站）→ store.ingestAlert()
      ① 一条 upsert SQL：新面孔建行 / 老面孔 occurrences+1（数据库原子完成，无查询竞态）
      ② 按 dedup 分岔：
         老面孔 → 台账记一条 update diff（occurrences 从几到几）
         新面孔 → 存可观测物 + 台账记 create + 叫号屏写 alert.created
      ③ 以上全部包在一个事务里：要么全成，要么全不算
  │ 回执：dedup ? 200 : 201
  ▼

```

### 站 2 · 一条 SQL 同时干"查"和"写"：upsert

主角函数登场。📄 [services/case-backend/src/store.ts:233-249](soc-demo/services/case-backend/src/store.ts#L233)：

```ts
export function ingestAlert(db: DB, input: AlertInput): IngestAlertResult {
  return db.transaction(() => {
    const seenAt = nowMs();
    const row = db
      .prepare(
        `INSERT INTO alerts (id, type, source, source_ref, title, description, severity, tlp, pap,
                             status, tags, raw, date, new_date, last_seen)
         VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, 'New', ?, ?, ?, ?, ?)
         ON CONFLICT(source, source_ref)
         DO UPDATE SET occurrences = occurrences + 1, last_seen = excluded.last_seen
         RETURNING id, occurrences`,
      )
      .get(
        randomUUID(), input.type, input.source, input.sourceRef, input.title,
        input.description ?? "", input.severity ?? 2, input.tlp ?? 2, input.pap ?? 2,
        j(input.tags ?? []), input.raw ? j(input.raw) : null, input.date ?? seenAt, seenAt, seenAt,
      ) as { id: string; occurrences: number };
```

大白话拆这句 SQL（这叫 **upsert**：update + insert 合一字）：

- `INSERT INTO alerts …`——先按"新案"尝试建行；
- `ON CONFLICT(source, source_ref)`——但如果撞了**唯一约束**（下面站 5 讲这个约束
  哪来的），说明同号旧案已存在，别报错，改成执行 `DO UPDATE`；
- `DO UPDATE SET occurrences = occurrences + 1, last_seen = …`——旧档案上盖"又出现
  一次"章，并把"最后看到时间"刷成现在；
- `RETURNING id, occurrences`——不管走了哪个分支，把这一行的档案号和当前出现次数
  **一次性带回来**。

为什么要这么写，而不是"先 SELECT 查一遍、没有再 INSERT"？因为"查"和"写"是两个
动作，中间有时间缝：两条一模一样的单子同时到，两边都查到"没有"，然后各建一份——
这就是**并发竞态**。upsert 把判断压进数据库引擎内部一条原子指令，SQLite 一次只放行
一个写事务，谁后到谁自动走进 `DO UPDATE` 分支，**结构性防重**，不靠应用层小心。

它的函数头注释也把职责写得明明白白。📄 [services/case-backend/src/store.ts:224-227](soc-demo/services/case-backend/src/store.ts#L224)：

```ts
// m1 告警接入的写入口（票 09）：upsert 语义，重复 (source, sourceRef) 走唯一索引冲突
// → occurrences+1 + 刷新 last_seen，不新建行、不发 alert.created（INV-6：不重复触发流水线），
// 但记一条审计 diff（INV-8：occurrences 变了就是写操作）。与 createAlert 的区别：
// createAlert 是「无脑新建」（手工/测试路径），这里才是带去重的正门。
```

### 站 3 · 按 dedup 分岔：新旧案待遇不同

📄 [services/case-backend/src/store.ts:250-274](soc-demo/services/case-backend/src/store.ts#L250)：

```ts
    const dedup = row.occurrences > 1;
    const ctx: Ctx = { actor: { type: "system", id: "m1:ingest" }, requestId: randomUUID() };
    if (dedup) {
      recordAudit(db, ctx, "update", row.id, "alert", {
        occurrences: { from: row.occurrences - 1, to: row.occurrences },
        lastSeen: "refreshed",
      });
    } else {
      for (const o of input.observables ?? []) {
        db.prepare(
          `INSERT INTO observables (id, alert_id, data_type, data, message, tlp, pap, ioc, tags, source_alert_id)
           VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)`,
        ).run(
          randomUUID(), row.id, o.dataType, o.data, o.message ?? null,
          o.tlp ?? 2, o.pap ?? 2, o.ioc ? 1 : 0, j(o.tags ?? []), row.id,
        );
      }
      recordAudit(db, ctx, "create", row.id, "alert", {
        created: { title: input.title, sourceRef: input.sourceRef },
      });
      emitEvent(db, "alert.created", { alertId: row.id, source: input.source, sourceRef: input.sourceRef });
    }
    return { alert: getAlert(db, row.id) as Record<string, unknown>, dedup };
  })();
}
```

三个看点：

- `dedup` 怎么判？`occurrences > 1`——出现次数超过 1 就说明走进了 `DO UPDATE` 分支。
  妙处：不需要第二个查询，站 2 `RETURNING` 带回来的数字**本身就是判定结果**。
- **老面孔**只做一件事：台账记一笔"改动说明"（occurrences 从几变几）。**不发事件**——
  这是 INV-6 的后半句"不重复触发流水线"：分诊自动化是被 `alert.created` 叫号的，
  旧案不重新叫号，就不会被反复分诊。
- **新面孔**做三件事：存可观测物（1.1 翻译出的 IP/文件名/指纹，挂到这张档案下）、
  台账记 create、叫号屏写一条 `alert.created`。最后把完整档案 + dedup 标记返回给路由。

### 站 4 · 同一个事务：档案、台账、叫号屏一起落

站 2 开头那行 `db.transaction(() => { … })()` 是个包裹：里面的每一条 INSERT 要么
**全部生效**，要么**全部回滚**，不存在中间态。看一下两个幕后小函数。
📄 [services/case-backend/src/store.ts:135-139](soc-demo/services/case-backend/src/store.ts#L135)：

```ts
function emitEvent(db: DB, topic: string, payload: unknown): void {
  db.prepare(
    "INSERT INTO outbox_events (topic, payload, created_at) VALUES (?, ?, ?)",
  ).run(topic, j(payload), nowMs());
}
```

`emitEvent` 不是"发消息"，就是**往 outbox_events 表里插一行**——这就是 outbox 模式
（出站箱模式，下面卡 2 细讲）：先把要广播的消息当**普通数据**存起来，跟档案同事务
落库，谁想消费谁来看表。读它的口子。
📄 [services/case-backend/src/store.ts:899-910](soc-demo/services/case-backend/src/store.ts#L899)：

```ts
export function pollEvents(db: DB, after: number, limit = 100): unknown[] {
  return (
    db
      .prepare("SELECT * FROM outbox_events WHERE id > ? ORDER BY id LIMIT ?")
      .all(after, limit) as Record<string, unknown>[]
  ).map((row) => ({
    id: row.id,
    topic: row.topic,
    payload: pj(row.payload as string, {}),
    createdAt: row.created_at,
  }));
}
```

HTTP 面上它是 [services/case-backend/src/app.ts:318-321](soc-demo/services/case-backend/src/app.ts#L318)
的 `GET /api/v1/events?after=N`——"给我 N 号之后的事件"。`id` 是自增序号，**按序号
翻页**这个设计，1.6 的 SSE 断线续传（INV-7）直接复用它。至于台账 `recordAudit`
（[store.ts:110-133](soc-demo/services/case-backend/src/store.ts#L110)），1.1 已见过它的
产物（那条 FAILURE 记录就是它兄弟），这里只需注意：它也是普通 INSERT，跟档案写
**同一个事务**——档案室头注释（[store.ts:1-3](soc-demo/services/case-backend/src/store.ts#L1)）
写的"所有写操作在同一事务内落审计条目（INV-8『审计同库同事务』）"就是指这个。

为什么"同事务"值钱？反例想一下：先建档案、再写台账，第二步万一失败（比如进程崩了），
就出现"档案存在但台账没记录"的鬼档案；反过来就是"台账有记录档案却没有"的鬼记录。
同事务保证三张表**要么都记了、要么都没记**，事后对账永远对得上。

### 站 5 · 查重的根基：唯一索引

upsert 里的 `ON CONFLICT(source, source_ref)` 之所以能工作，是因为建表时就立了规矩。
📄 [services/case-backend/src/db.ts:32-34](soc-demo/services/case-backend/src/db.ts#L32)：

```sql
-- 票 09（INV-6）：去重唯一约束兜底在 M2 SQLite——重复推送 (source, source_ref) 走
-- upsert occurrences+1，靠索引而非应用层查-插，防并发重复（PRD §6-M1 实现机制）
CREATE UNIQUE INDEX IF NOT EXISTS idx_alerts_dedup ON alerts(source, source_ref);
```

大白话：`alerts` 表全体行里，`(source, source_ref)` 这一对的组合值**全库只许出现
一次**（source=哪家探头、source_ref=它的第几号警情，合起来就是 1.1 说的报案单
身份证号）。谁想插第二对相同的，数据库引擎当场拒绝——普通 INSERT 拒绝、upsert
则转入 `DO UPDATE`。occurrences 列本身也在建表时备好了
（[db.ts:26](soc-demo/services/case-backend/src/db.ts#L26) `occurrences INTEGER NOT NULL DEFAULT 1`）。

顺带看档案室开库时的两条 pragma（[db.ts:156-164](soc-demo/services/case-backend/src/db.ts#L156)）：
`journal_mode = WAL`（写操作先记旁账再合并，读写不互相堵）和 `busy_timeout = 5000`
（撞上别人正在写就等 5 秒而不是立刻报错）——九服务共享一个 SQLite 的底气就这两行，
头注释称为"单写者"口径：写永远排队，读随便。

## 三、服务与中间件卡

**卡 1 · ▲better-sqlite3 —— 档案室的档案柜本体**

- **替我们干了件什么体力活**：SQLite 是个**嵌在进程里的数据库**——不是 MySQL 那种
  需要单独安装、单独启动、走网络连的数据库服务，就是一个库文件（本项目里是
  `data/case-backend/case-backend.sqlite`），谁打开谁读写。better-sqlite3 是 Node.js
  里操作它的驱动包，特点是**同步 API**（`db.prepare(...).get()` 直接返回结果，不是
  Promise）——代码读起来就是一步步的账房动作，适合本项目"单写者排队"的简单模型。
- **本项目怎么配置**：[services/case-backend/src/db.ts:156-164](soc-demo/services/case-backend/src/db.ts#L156)
  的 `openDb()`：开库 → 两条 pragma（WAL + 忙等 5 秒）→ 执行 DDL 建八张表 → 老库补列。
  库文件经 compose 卷挂到宿主机（1.1 站 6 那行 `volumes`），容器重建数据不丢。
- **市面上同类**：node:sqlite（Node 22+ 内置，免安装但较新）、Prisma/Drizzle（ORM，
  带类型和迁移管理但重）、PostgreSQL（真服务器库，并发强但要单独运维）。
- **本项目为什么选 better-sqlite3**：单机教学系统，一个写者、零运维、一个文件就是
  全部数据（备份=拷文件）；同步 API 让"同事务落三张表"这种账房逻辑一目了然。上
  PostgreSQL 是杀鸡用牛刀，上 ORM 多一层概念。
- **业务上怎么选**：单机工具/嵌入式/演示原型 → SQLite 系；多服务并发写、要网络
  访问、要复杂查询 → PostgreSQL/MySQL；大团队多业务共享库 → 加 ORM 管迁移和类型。
  另注意 SQLite 的天花板是"一个写者"——本项目把 agent 侧的 runs 库、guards 侧的
  mapstore 拆成**各自独立的库文件**（"三库"），就是在给这个天花板留余量。

**卡 2 · outbox 模式（自研）—— 叫号屏**

- **替我们干了件什么体力活**：服务之间要"有新案了，快来干活"这类通知。直接调对方？
  那样档案室就得知道"谁会来消费"且调用失败就丢消息。outbox 的做法：把通知**写成
  自己库里的一行数据**（`outbox_events` 表，[db.ts:109-114](soc-demo/services/case-backend/src/db.ts#L109)），
  和业务数据同事务落库；消费方自己按序号来翻表（`pollEvents`，[store.ts:899-910](soc-demo/services/case-backend/src/store.ts#L899)）。
  单和活永远对得上——消息不会因为谁宕机而消失，最多晚点到。
- **自研还是开源**：模式自研（就是一张表 + 两个函数），但这是业界标准套路，名字就叫
  **Transactional Outbox**，微服务消息可靠投递的经典解法。
- **本项目怎么配置**：无配置，两张函数：写侧 `emitEvent`、读侧 `pollEvents`。目前两个
  topic：`alert.created`（步 1.3 的 autorun 消费它自动拉起分诊）和 `case.closed`
  （[store.ts:519](soc-demo/services/case-backend/src/store.ts#L519)，步 3.1 知识沉淀的触发信号）。
- **市面上同类**：Kafka/RabbitMQ/Redis Stream（专业消息中间件，吞吐大、带订阅推模式、
  要单独部署运维）；PostgreSQL LISTEN/NOTIFY（库内推送但不持久）。
- **本项目为什么选自研 outbox**：单机、消费方就一个 agent 进程、消息量每案几条——
  起一个 Kafka 容器运维成本远超收益；而且事件和业务同库同事务，**天然不丢**，这正是
  INV-6/INV-8 要的口径。
- **业务上怎么选**：单机小系统、消费者少、要绝对不丢 → outbox 表；多服务、多消费者、
  高吞吐、要重试/回压/广播 → Kafka/RabbitMQ；已有 PostgreSQL 又只要轻量通知 →
  LISTEN/NOTIFY 或逻辑复制。什么时候迁移：消费方超过两三个、需要回放历史全量事件时。

## 四、防线对号

- **INV-6（重复报案只算一起）**：本步主菜，两半都实证过——① 不新建：唯一索引
  `idx_alerts_dedup` 拦住同号二插，upsert 走 `occurrences+1`（站 2/站 5）；② 不重复
  触发：`alert.created` 只在首次建档时写叫号屏（站 3），旧案推送事件表纹丝不动。外加
  一层并发保险：判断压在数据库原子指令里，两条同号单同时到也只有一条能建档。
- **INV-8（写操作必留台账）**：新案记 `create`、旧案记 `update` diff（occurrences
  从几到几）、连 1.1 的 422 拒收都记——**且全部与业务写同事务**（站 4），台账和档案
  永远对得上。
- **INV-10（状态机外变更 409）的边界预览**：本步的 upsert 不动 `status` 列（始终
  'New'），不踩状态机；什么时候会踩、409 长什么样，场景 2/3 讲三结局和关案时对号。
