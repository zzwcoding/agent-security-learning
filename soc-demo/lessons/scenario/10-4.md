# 场景 10 · 步 10.4 —— 路由建议 vs 路由决定：审计分痕查询

> 编排循环里有两个"嘴"对同一份任务组合说话：planner 说"我**建议**这么干"
> （[TERMS「循环三件套」](TERMS.md)条的拟单的），dispatch 说"我**决定**这么干"。
> 如果两句话混进同一条审计记录，出了分歧就永远说不清"是建议错了还是执行走样了"。
> 本票把这两句话拆成两个 action——`hunt_plan_suggest`（A，建议）与
> `hunt_dispatch_decide`（B，决定）——**两条 action 逐条可查、可对账**。
> 这是 INV-8（写操作必留台账）在路由场景的精化：不只是"留痕"，是"按语义分痕"。
>
> 📍 大图节点：AUDIT_SPLIT → T_AUDIT（[10-big-picture.html](10-big-picture.html)）

### 站 1 · A 半边：建议账长什么样

📍 大图节点:AUDIT_SPLIT(10.4 审计分痕)

建议账在 planner 产出组合、菜单闸放行之后落
（[planner.ts:252-268](soc-demo/services/agent/src/orchestration/planner.ts#L252)）：

```ts
  // 审计分痕 A（路由建议）：planner 输出组合；决定（B）= flow.ts dispatch 的
  // hunt_dispatch_decide。两个 action 可区分可查（INV-8 五要素）。
  recordAudit(audit, runId, {
    action: "hunt_plan_suggest",
    objectId: runId,
    objectType: "run",
    result: "SUCCESS",
    details: {
      round_no: ctx.state.round_no,
      hypothesis_id: ctx.state.hypothesis_id,
      tasks: capped,
      tasks_returned: tasks.length,
      truncated,
      attempts,
      sanitized_fields: sanitized.length,
    },
  });
```

details 里的 `tasks_returned`（LLM 原始给了几件）与 `truncated`（被 T03 截掉没有）专门留着
对账用：**建议账记"LLM 说了什么"，决定账记"代码干了什么"**，中间的每一次收窄都有痕。
契约断言在 [planner.test.ts:190-208](soc-demo/services/agent/src/orchestration/planner.test.ts#L190)
（T03 用例内）：建议条目带 `truncated: true, tasks_returned: 3`，且
`new Set([suggest?.action, decide?.action]).size).toBe(2)`——两个 action 名同帧可查，
建议 ≠ 决定。

### 站 2 · B 半边：决定账与"无决定即无 B"

📍 大图节点:AUDIT_SPLIT(10.4 审计分痕)

决定账在 dispatch 扇出**成功后**落
（[flow.ts:194-200](soc-demo/services/agent/src/orchestration/flow.ts#L194)）：

```ts
        recordAudit(audit, runId, {
          action: "hunt_dispatch_decide",
          objectId: runId,
          objectType: "run",
          details: { round_no: roundNo, hypothesis_id: hypothesisId, children, tasks_fingerprint: ctx.state.tasks_fingerprint },
          result: "SUCCESS",
        });
```

`children` 是实际拉起的子 run id 数组——它跟 `hunt_run_links` 簿记一一对应
（[ticketing.test.ts:63-64](soc-demo/services/agent/src/orchestration/ticketing.test.ts#L63)
"门记录与子票一一对应"的审计侧版本），决定账因此可以作为簿记的**交叉证据**。
反向的精妙在失败路径：planner 被拒的轮次，dispatch 开头就空手而归
（[flow.ts:138-143](soc-demo/services/agent/src/orchestration/flow.ts#L138)
`if (ctx.state.planner_failed === true) { ctx.state.children_ids = []; return; }`）——
**无决定就不落 B 半边**（T04 断言 `hunt_dispatch_decide` 不在场），拒绝轮的账面只有一条
DENIED。账的"缺行"本身也是语义：`SUCCESS` 两条 = 建议被执行；只有 A 没有 B = 建议被闸拦下
（去查同 requestId 下的 `hunt_plan_denied`）。

### 站 3 · 为什么分痕而不是一条记录

📍 大图节点:AUDIT_SPLIT(10.4 审计分痕)

一条记录塞不下两份责任。A 的作者是一个 LLM（它的产出按 schema 验过、截过、也可能被拒），
B 的作者是确定性代码（它的产出是 run/票/簿记的物理事实）。混写会发生两种事故：追责时
"建议就是执行"的糊涂账（planner 提议 isolate_host 被拦，混写后看起来像"系统做过"）；
对账时找不到分歧点（组合在截断/拒铸/防转哪一步变形的，无痕可循）。分痕后对账就是
逐字段 diff：`tasks`（建议、截后）对 `children`（决定）对 `hunt_run_links`（簿记）对
`runs`（物理行）——四层真相源各答各的问题。

## 三、服务与中间件卡

**卡 1 · ▼审计分痕（建议/决定两 action，票 74）**

- **它是什么**：路由链上的每一步各落五要素条目（actor/objectId/objectType/details +
  requestId/result），A（hunt_plan_suggest）与 B（hunt_dispatch_decide）两个 action 名
  可区分，DENIED 家族（plan_denied / dispatch_mint_denied / round_spin_denied）同框架。
- **市面替代**：单条"审计流水"（一动作一条，混写语义）；或应用外旁路（Langfuse 观测面）。
- **为何这么选**：审计是**对账证据**不是日志——查询粒度必须与责任粒度对齐。requestId
  把一个 run 的所有账串成一条线，action 把"谁说的/谁做的/谁拦的"分开；观测旁路（事件/SSE）
  是另一条腿，两边同源不同用（TERMS「留痕」条：执行没发生的证明 = 事件流里少一对工具帧）。
- **业务上怎么选**：决策链上有 LLM 参与 → 必须分痕（建议与执行不是一个责任主体）；
  纯代码路径 → 单条足够。判据是"这一步的输出有没有被另一个自主主体改写的可能"。

## 场景题闯关（本步 1 题）

**Q：审计查到某轮"只有 hunt_plan_suggest、没有 hunt_dispatch_decide、也没有
hunt_plan_denied"，最可能是哪个环节断了？给出你的排查顺序。**

<details><summary>答案（点击展开）</summary>

先看查询维度再下结论：requestId 是不是父 run 的（hunt_<runId> 少一位就假缺行）。然后按
分痕语义推：A 在场说明 planner 走到了"建议落账"这一步（菜单闸/schema 闸都过了）——之后
B 缺席只可能死在 dispatch 与落账之间。排查顺序：①同 requestId 下找
`hunt_dispatch_mint_denied`（铸票缝拒——T15：dispatch 逐任务铸票失败先落 DENIED 再上抛，
run 被 runner 强杀，决定账不落）；②找 `hunt_round_spin_denied`（防转拒组合——组合被拒
也算"无决定"）；③查 runs 表该 run 的 status/fail_reason（mint_failed/其他强杀）与
run_jobs（start 任务是否真的被分发循环领走——202 与派活的没有触发关系，任务卡在队列里
连 dispatch 都没开始）；④hunt_run_links 该轮簿记行（先有轮号后有轮）。**缺行的位置
本身就是断点定位器**——这正是分痕比混写多买的能力。</details>
