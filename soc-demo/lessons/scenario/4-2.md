# 场景 4 · 步 4.2 —— 意图闸三态：OpenFGA 这位裁判怎么判

> 4.1 的捣乱实验 A 里，soc1 想隔离主机被拒了，理由是"该格为「—」"；值班长发同一句话
> 却开出了卡。同一个动作、不同的人，命运由谁决定？答案是 chat 子图第四站 **intent_gate**
> （意图闸）——它对每个意图给出三种裁决之一：`allow`（只读直查）/ `require_approval`
> （转审批开卡）/ `deny`（拒绝并解释）。本步拆开这道闸：可见性收窄和 OpenFGA 裁决两个
> 数据源怎么配合、"soc1 100% deny"为什么是结构保证而非配置巧合、裁判联系不上时为什么
> 宁可全拒。主角卡 `apr_baf3f3a8` 继续在场边候场（它就是 require_approval 态的产物）。

## 一、操作（位置感）

本步的操作全是"换脸说话"——同一批话用四种预置身份各说一遍，看闸怎么分道：

1. **soc1 问只读问题**（allow 态直查）；
2. **soc1 提高危动作**（deny 态，4.1 已见，本步挖内部）；
3. **redteam 问只读问题**（连只读都 deny——红队在矩阵里是整行"—"）；
4. **把裁判停了再问**（fail-closed 压轴实验，做完恢复）。

另外补一个手动口：OpenFGA 的 check 接口可以直接 curl——绕开所有应用代码，直接问
裁判本人"这个人能不能执行那个工具"，验证应用层说的和裁判想的一致：

```bash
cd /Users/divh/Downloads/安全评估agent/soc-demo
STORE=$(python3 -c "import json; print(json.load(open('services/gateway/plugins/fga_ids.json'))['store_id'])")
MODEL=$(python3 -c "import json; print(json.load(open('services/gateway/plugins/fga_ids.json'))['model_id'])")
curl -s -X POST "http://127.0.0.1:18080/stores/$STORE/check" \
  -H 'content-type: application/json' \
  -d "{\"tuple_key\":{\"user\":\"user:duty_lead\",\"relation\":\"can_execute\",\"object\":\"tool:isolate_host\"},\"authorization_model_id\":\"$MODEL\"}"
# 预期：{"allowed":false} —— 值班长对 isolate_host 也只是"可见可提请"，没有直接执行权
```

`fga_ids.json`（store/model id 的对牌）每次跑 `bash scripts/setup-openfga.sh` 都会刷新
——OpenFGA 容器是内存存储，栈一停授权世界就没了，30 秒重建（1.1 讲过的布景纪律）。

## 二、调用链

先看全景。意图闸裁决一个意图的完整决策树：

```
「请把主机 app-01 隔离」（message + role）
  ▼
[intent_classify] 关键词/LLM → tool=isolate_host, confidence=0.9     （4.1 站 3）
  ▼
[intent_gate] decideIntent(role, tool, fga) —— 三道关：
  ① 角色在册吗？  soc1/duty_lead/admin/redteam 之外的 → deny「未知角色」
  ② 工具在册吗？  A.2 四族清单之外的     → deny「未知工具」
  ③ 角色看得见它吗？（visibleTools）     看不见 → deny「该格为—」★ soc1×isolate 死在这
  ▼
  ④ 问真裁判：OpenFGA check(user:<角色>, can_execute, tool:<工具>)
       allow（L0）           → state=allow         只读直查
       deny + 非L0（L1/L2）  → state=require_approval 转审批开卡
       deny + L0             → state=deny           只读也不给
       裁判超时/不可达       → state=deny           fail-closed，deny 覆盖 allow
  ▼
  裁决落审计（intent_gate 行，DENIED 或 SUCCESS）→ 越权时 denied 事件给 web 红标
```

### 站 1 · 两份数据源：可见性清单和真裁判

意图闸的裁决靠两份数据源，gate.ts 头注释先把丑话说明白：

📄 [services/agent/workers/chat/gate.ts:1-15](soc-demo/services/agent/workers/chat/gate.ts#L1)

```ts
// m8 对话 Copilot · 意图闸三态裁决（FR-M8.4；PRD §6-M8「Tracecat 三态对齐」）。
//
//   allow            = 只读意图且 OpenFGA allow → 路由 worker 只读面直查（L0 免票族）
//   require_approval = 动作意图（L1/L2，角色可见可提请）→ 转审批回路（票 11 铸 ApprovalToken）
//   deny             = 不可见 / 未知角色工具 / 裁判不可达 → 拒绝并解释（fail-closed，INV-1）
//
// 裁决的两个数据源都是真件：
//   - 可见性 = A.2 矩阵（visible-tools.ts，与真 openfga 世界同一份 matrix.json）；
//   - 可直查 = 真 OpenFGA check（fga-client.ts，user:<角色> can_execute tool:<工具>）。
// 三条硬语义：
//   1. soc1 发起 L2 意图 100% deny——A.2 里 soc1 对 KB 入库/高危响应两族的格子是「—」，
//      不可见在 FGA 之前就拒了（m8 卡测试计划/eval 遍历口径）。
//   2. 动作意图一律转审批（FR-M8.4 原文）——哪怕 FGA 对 L1 有直接授权（soc1 能 close_alert），
//      对话面也只提请、不直执行：Copilot 没有写手，只有建议与提请。
//   3. 裁判联系不上 ≠ 无罪推定（INV-1）：FGA 超时/不可达/ids 不可读一律 deny 并解释。
```

第一份数据源是**可见性清单**——"这个角色看得见/可提请哪些工具"。它按 A.2 权限矩阵
逐格翻译成一张硬编码表（矩阵原文在 `services/gateway/fga/matrix.json`，工具→族→分级
的单一来源）：

📄 [services/agent/workers/chat/visible-tools.ts:39-44](soc-demo/services/agent/workers/chat/visible-tools.ts#L39)

```ts
const VISIBLE_FAMILIES: Record<string, string[]> = {
  soc1: ["readonly_query", "case_write"],
  duty_lead: ["readonly_query", "case_write", "kb_write", "incident_response"],
  admin: ["readonly_query", "case_write", "kb_write", "incident_response"],
  redteam: [],
};
```

大白话：**soc1 的世界只有查和写案卷**；值班长/管理员多看两族——KB 入库和高危响应
（isolate/block），但"看得见"=可以提请，不是可以干；**红队什么都看不见**（它在矩阵里
是整行"—"，红队是演示攻击的演员，不是系统用户）。

第二份数据源是**真裁判** OpenFGA——一个开源的细粒度授权引擎（Google Zanzibar 论文的
开源实现），专管"谁对什么有什么关系"。本项目问它的只有一句话：`user:<角色>` 对
`tool:<工具>` 有没有 `can_execute` 关系。agent 侧的出站客户端：

📄 [services/agent/src/fga-client.ts:66-78](soc-demo/services/agent/src/fga-client.ts#L66)

```ts
  const res = await fetchImpl(`${apiUrl}/stores/${ids.store_id}/check`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({
      tuple_key: { user: fgaUser, relation: "can_execute", object: toolObj },
      authorization_model_id: ids.model_id,
    }),
    signal: timeoutSignal(timeoutMs),
  });
  if (!res.ok) throw new Error(`fga_http_${res.status}`);
  const obj = (await res.json()) as { allowed?: unknown };
  if (typeof obj.allowed !== "boolean") throw new Error("fga_bad_shape");
  return obj.allowed;
```

一个 HTTP POST，回一个布尔。注意两个 fail-closed 小细节：非 200 抛错、回包里 `allowed`
不是布尔也抛错——**裁判的回答含糊 = 当作没答**（异常由上层收进 deny）。

### 站 2 · 裁判脑子里的世界：三类型两元组

OpenFGA 里存的是一个授权模型加一堆元组。本项目的模型（`services/gateway/fga/openfga_model.json`）
定义了三种对象，其中 `tool` 的 `can_execute` 关系用了 Zanzibar 的经典招数 **tupleToUserset**
（"展开"：问工具的授权者 = 先找它所属的族，再问谁对这个族有 can_execute）：

📄 [services/gateway/fga/openfga_model.json:14-30](soc-demo/services/gateway/fga/openfga_model.json#L14)

```json
    {
      "type": "tool",
      "relations": {
        "member_of": { "this": {} },
        "can_execute": {
          "tupleToUserset": {
            "tupleset": { "relation": "member_of" },
            "computedUserset": { "relation": "can_execute" }
          }
        }
      },
      "metadata": {
        "relations": {
          "member_of": { "directly_related_user_types": [{ "type": "family" }] }
        }
      }
    }
```

模型定下"关系怎么算"，数据就是往里填元组。整个 A.2 矩阵（4 角色 × 4 族 × 17 工具）
在授权世界里只有**两组元组**，重建引擎的 `desired_tuples` 一页写完：

📄 [services/gateway/fga/setup_openfga.py:94-105](soc-demo/services/gateway/fga/setup_openfga.py#L94)

```python
def desired_tuples(matrix: dict) -> list[dict]:
    """角色×族授权 + 族×工具归属，两组元组就是 A.2 的全部内容。"""
    out = []
    for role, spec in matrix["roles"].items():
        for fam in spec["families"]:
            out.append({"user": f"user:{role}", "relation": "can_execute",
                        "object": f"family:{fam}"})
    for fam, spec in matrix["families"].items():
        for tool in spec["tools"]:
            out.append({"user": f"family:{fam}", "relation": "member_of",
                        "object": f"tool:{tool}"})
    return out
```

大白话：第一组写"**谁能用哪族工具**"（soc1 能用 readonly_query 族……），第二组写
"**每族里有哪些工具**"（readonly_query 族里有 siem_query……）。问"user:soc1 能不能
执行 tool:siem_query"时，裁判自己顺藤摸瓜：siem_query 属于 readonly_query 族 →
soc1 对这族有 can_execute → **allowed**。给角色加一个工具 = 加一条"族×工具"元组，
加一个角色 = 加一条"角色×族"元组——矩阵的行列各只有一处真相，不会出现"改了配置
忘了改代码"的漂移。

soc-demo 用 OpenFGA 而不是在代码里写 `if role == "soc1"` 的原因也在这：**授权是数据，
不是代码**。改权限不用发版；裁判独立部署，应用自己说了不算；每次裁决天然可审计。

### 站 3 · 三道收窄 + 一次裁决：decideIntent 全文

现在读闸本体。前半段三道收窄（角色在册、工具在册、可见性），全是**纯内存查表**——
不花网络调用：

📄 [services/agent/workers/chat/gate.ts:30-47](soc-demo/services/agent/workers/chat/gate.ts#L30)

```ts
export async function decideIntent(role: string, tool: string, fga: FgaChecker): Promise<GateDecision> {
  const knownRoles = ["soc1", "duty_lead", "admin", "redteam"];
  if (!knownRoles.includes(role)) {
    return { state: "deny", role, tool, reason: `未知角色「${role}」：不在四种预置身份内，fail-closed 拒绝（INV-1）` };
  }
  const fam = familyOf(tool);
  const tier = tierOf(tool);
  if (!fam || !tier) {
    return { state: "deny", role, tool, reason: `未知工具「${tool}」：不在 A.2 工具族清单内，fail-closed 拒绝` };
  }
  // 可见性 = 第一收窄（FR-M8.2）：清单上看不见的工具，意图直接拒绝并解释
  if (!visibleTools(role).includes(tool)) {
    return {
      state: "deny",
      role, tool,
      reason: `角色 ${role} 对 ${tool}（${fam} 族，${tier}）不可见：A.2 权限矩阵该格为「—」，无权发起该操作`,
    };
  }
```

**soc1 的 isolate_host 意图死在第 41 行**——soc1 的可见清单只有两族，isolate_host
属于 incident_response 族，`visibleTools("soc1")` 里根本没有它。根本轮不到问裁判。
这就是"soc1 100% deny"的实现处：**不是裁判判得严，是soc1 看不见这扇门**。4.1 捣乱 A
那句"该格为「—」"的拒绝理由，出处就是 45 行。

过了三道收窄，才轮到真裁判发言，然后按工具分级分道：

📄 [services/agent/workers/chat/gate.ts:48-73](soc-demo/services/agent/workers/chat/gate.ts#L48)

```ts
  // 真 OpenFGA check（票 12 容器）：问「这个角色能不能直接执行这个工具」
  const verdict = await fga(`user:${role}`, tool);
  if (!verdict.allowed) {
    // 裁判病了/说不行。可见 + L2 = 「需审批」格子，deny 是预期答案 → 转审批回路；
    // 其余（L0 被拒、裁判不可达）一律拒绝并解释，deny 覆盖 allow（INV-1）。
    if (verdict.reason === "fga_denied" && tier !== "L0") {
      return {
        state: "require_approval",
        role, tool,
        reason: `${tool} 属 ${fam} 族（${tier}）：动作意图一律转审批流程（FR-M8.4），已提请值班长裁决`,
      };
    }
    const why = verdict.reason === "fga_denied"
      ? `OpenFGA 裁决 deny：角色 ${role} 无 ${tool} 的直接执行权`
      : `授权裁决不可用（${verdict.reason}）：fail-closed 拒绝（INV-1），deny 覆盖 allow`;
    return { state: "deny", role, tool, reason: why };
  }
  if (tier === "L0") {
    return { state: "allow", role, tool, reason: `${tool} 属只读查询族（L0），OpenFGA allow：路由 worker 只读面直查` };
  }
  // FGA allow 的写族（如 soc1 的 close_alert）在对话面同样只提请不直执行（语义 2）
  return {
    state: "require_approval",
    role, tool,
    reason: `${tool} 属 ${fam} 族（${tier}）：动作意图一律转审批流程（FR-M8.4），已提请值班长裁决`,
  };
```

这段是全步的心脏，四条岔路逐条读：

1. **裁判说 deny 且工具是 L1/L2 → require_approval**（53-59 行）。注意矩阵里 L2 两族
   **没有任何角色**有直接执行权（matrix.json 的 a2_note 原文："直接执行 FGA 一律 deny，
   唯一通道是审批铸一次性 ApprovalToken"）——所以值班长的 isolate_host 走到裁判那里
   得到的也是 deny，但**这个 deny 是预期答案**，闸把它翻译成"需审批"而不是"拒绝"。
   4.1 的主角卡 `apr_baf3f3a8` 就是这样来的。
2. **裁判说 deny 且是 L0、或裁判压根联系不上 → deny 并解释**（60-63 行）。
3. **裁判说 allow 且是 L0 → allow**（65-67 行）：只读直查。
4. **裁判说 allow 但是写工具**（68-73 行）→ 照样 require_approval！soc1 确实有
   close_alert 的直接执行权（第一节亲手查过 `soc1 can_execute close_alert => True`），
   但**对话面上没有写手**——Copilot 只提请，不代持任何写权限。哪怕裁判放行，闸也不放。

第 4 条值得单独停一下：它防的是"权限提升幻觉"——如果对话面允许直执行 L1，那么任何
能跟 Copilot 聊天的人（包括将来接入的自动化）就能借 soc1 的身份关单。**"可见"与
"可直查"是两个正交的位**（visible-tools.ts 注释原话），闸把它们分开用：可见性决定
"能不能提"，FGA+分级决定"提了之后走哪条道"。

### 站 4 · 客户端的 fail-closed 收口

裁判是个网络服务，会超时会宕机。出站客户端把一切异常收口成结构化的 deny：

📄 [services/agent/src/fga-client.ts:94-108](soc-demo/services/agent/src/fga-client.ts#L94)

```ts
  return async (user, tool) => {
    let ids: FgaIds | null;
    try {
      ids = opts.ids !== undefined ? opts.ids : loadFgaIds.load();
    } catch {
      return { allowed: false, reason: "fga_ids_unreadable" };
    }
    if (!ids) return { allowed: false, reason: "fga_ids_unreadable" };
    try {
      const allowed = await queryOpenfga(apiUrl, ids, user, `tool:${tool}`, timeoutMs, opts.fetchImpl);
      return allowed ? { allowed: true } : { allowed: false, reason: "fga_denied" };
    } catch (e) {
      return { allowed: false, reason: outboundTimeoutReason("fga", isOutboundTimeout(e)) };
    }
  };
```

四层兜底：对牌（store/model id）读不到 → `fga_ids_unreadable`；裁判明确说不行 →
`fga_denied`；超时 → `fga_timeout`；连接拒绝 → `fga_unreachable`。**除了"裁判明确
说 allow"，其余一切都不是 allow**——这就是 INV-1"deny 覆盖 allow"在授权链上的形状。
gate.ts 拿到 `fga_denied` 之外的理由时（60-63 行），连"需审批"都不给：裁判病了，
连"该不该走审批"都无法担保，那就全拒。

## 三、服务与中间件卡

### 卡 1（开源）· OpenFGA：外置授权裁判

- **它是什么**：CNCF 项目，Google Zanzibar 论文（"以关系元组统一表达授权"）的开源
  实现。核心抽象：授权模型（关系怎么算）+ 元组（谁对什么有什么关系）+ check 接口
  （问一句 allowed 与否）。本项目的模型小到 32 行 JSON：user / family / tool 三类型、
  一个 tupleToUserset 展开。
- **本项目怎么配置**：官方镜像容器（compose 服务 openfga，宿主映射口 18080），内存
  存储；`bash scripts/setup-openfga.sh` 幂等重建授权世界（store 按名复用、模型逐字节
  比对复用、元组差量同步），产出的 store/model id 刷进 `fga_ids.json` 供 agent 与
  gateway 插件同读——**两端问的是同一个裁判的同一个世界**。
- **市面上同类**：Ory Keto（同思想的另一开源实现）、SpiceDB（Zanzibar 系，Go）、
  OPA（策略引擎，另一路数：策略即代码）/ 自研 RBAC 中间表。
- **本项目为什么选它**：教学价值在"授权是独立服务+数据"这个架构事实——应用进程
  被攻破也改不了授权世界；矩阵即元组，改权限不发版；check 是标准接口，谁都能问
  （chat 意图闸、gateway 的 fga_check 插件、场景 6 的 PII 反查白名单都是它的客户）。
- **业务上怎么选**：关系型授权（文档共享、组织架构继承）→ Zanzibar 系；纯角色表且
  规模小 → 数据库一张 RBAC 表+缓存就够，别为规模没用上的场景引入独立组件；策略里
  混着环境条件（时间、IP）→ OPA 这类策略引擎更合身。

### 卡 2（自研）· gateway 的 fga_check 插件：同一位裁判的第二法庭

- **它是什么**：挂在 ContextForge（官方镜像）`tool_pre_invoke` 钩子上的 Python 插件
  （`services/gateway/plugins/fga_check.py`）——MCP 工具每次被调用前，拿调用者身份问
  同一个 OpenFGA 一句 can_execute，False/不可达/数据不可读一律 403。
- **为什么有两道**：chat 意图闸管"**这个意图能不能提**"（对话面，TS 侧）；fga_check
  插件管"**这个工具调用能不能执行**"（执行面，网关侧）。一个管入口一个管出口，互相
  不信任——就算有人绕开 chat 子图直接对网关发起工具调用，网关门口还站着同一个裁判。
  认不出的脸按 default_user（user:anonymous，零权限元组）处理，天然全 deny。
- **业务上怎么选**：授权检查要**在每一层重复**而不是只做一次——SOC 平台里 LLM、
  工具网关、下游 API 各自验权是常态（纵深防御的授权版）。代价是延迟（多一跳网络
  check），换来的是"任何一层被绕过都不放行"。

## 四、防线对号

| 防线 | 在本步的落点 |
|---|---|
| **INV-1**（fail-closed，deny 覆盖 allow） | 裁判超时/不可达/对牌不可读一律 deny（fga-client.ts:94-108）；未知角色/未知工具/不可见全 deny（gate.ts:30-47）；本步停 openfga 实测：连只读查询都拒 |
| **A.2 矩阵 / FR-M8.2**（可见性即第一收窄） | soc1 看不见 incident_response 族 → isolate_host 意图在查裁判之前就死（100% deny 的结构保证）；redteam 整行"—"连只读都不可见 |
| **FR-M8.4**（动作意图一律转审批） | FGA allow 的 L1 写工具在对话面照样 require_approval（gate.ts:68-73）——Copilot 没有写手 |
| **INV-3 / D7**（票面无 L2） | L2 两族在 FGA 世界**没有任何角色**有直接执行权（matrix.json a2_note）——授权数据本身就长成"必须走审批"的形状 |
| **INV-8**（全链审计） | 每次裁决落 intent_gate 审计行（decision/reason 逐字），DENIED 者带 result=DENIED；denied 事件发 web 红标 |
| **口径同源** | 可见性表、matrix.json、真 openfga 元组三处同源（matrix 单一来源），setup 脚本幂等保证漂移可重建 |

**零工具调用、run 照常 completed**——红队在整个工具面上是瞎子。对照 soc1 问同一句：
related_alerts 直查成功。"权限不是按人好坏，按格子"——红队的格子是整行"—"。

**B · 伪装角色硬闯（编排面没有登录口）**：
公开面 `/api/v1/chat` 有会话验签拦着，但编排面 `/internal/runs` 收 role 字段——试试
编一个：

```bash
curl -s -X POST http://127.0.0.1:3003/internal/runs -H 'content-type: application/json' \
  -d '{"kind":"chat_flow","case_id":"case_000002","message":"请把主机 app-01 隔离","role":"hacker"}'
# 预期：202（run 建了）……然后
sleep 3
sqlite3 "file:soc-demo/data/agent/agent.sqlite?mode=ro" \
  "SELECT substr(payload,1,150) FROM run_events WHERE run_id=( \
     SELECT id FROM runs WHERE kind='chat_flow' ORDER BY created_at DESC LIMIT 1) \
   AND type='denied';"
# 预期（本步实测 run_7c33e17b）："未知角色「hacker」：不在四种预置身份内，fail-closed 拒绝（INV-1）"
```

编排面是内网信任口（2.3 讲过它"薄"），但意图闸把它当不可信输入对待：role 字段只是
个字符串，不在四张脸名单里就全拒——**入口可以薄，裁决必须硬**。

**C · 把裁判停了（fail-closed 压轴）**：

```bash
docker compose stop openfga
# 拿 soc1 的会话再问一遍只读问题（命令同"亲手验证 2"）
curl -s -X POST http://127.0.0.1:3003/api/v1/chat \
  -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
  -d '{"message":"198.51.100.23 还出现在哪些告警","case_id":"case_000002"}'
# 预期（本步实测 run_192a4446）：denied 帧
#   "授权裁决不可用（fga_timeout）：fail-closed 拒绝（INV-1），deny 覆盖 allow"
docker compose start openfga && bash scripts/setup-openfga.sh   # 恢复布景（内存世界要重建）
```

**连只读查询都被拒了**——明明 soc1 有 related_alerts 的直接执行权，明明答案就在库里。
这正是设计要的效果：裁判联系不上时，"平时允许"不能自动降级成"现在也允许"（想想
反过来会怎样：攻击者只需想办法让 openfga 宕机，就能把授权系统变成无授权系统）。
对照组：场景 3.4 的 chroma 检索面病了是 **fail-open**（降级=无知识继续干活）——两个
外部依赖，两种口径，分界线是**这个依赖病了，攻击者能不能借它放行本不该放行的事**。
授权不可用=可能放行危险动作 → fail-closed；知识检索不可用=少个参考 → fail-open。

**D · 纸面推演**：如果可见性表和 FGA 元组漂移了（比如 matrix.json 给 soc1 加了
incident_response 族，但忘了重跑 setup-openfga.sh）——闸第 41 行放行 soc1 的隔离
意图，第 49 行裁判说 fga_denied，非 L0 → **require_approval**。结果：soc1 能提请
主机隔离了，值班长会看到一张"提请人 soc1"的卡。漂移的后果不是直接放行而是**降级成
人审**——这正是把 L2 的最后裁决权留给人的好处：前面所有层都错了，还有一道人闸。
（纪律上这仍是要防的漂移——所以 setup 脚本设计成幂等、可随时重跑。）
