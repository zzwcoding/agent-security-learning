📄 [services/agent/src/tools-manifest.test.ts:41-62](soc-demo/services/agent/src/tools-manifest.test.ts#L41)

```ts
function parsePrdA1(): A1Row[] {
  const prd = readFileSync(new URL("docs/prd.md", ROOT), "utf8");
  const section = prd.split("### A.1")[1];
  if (!section) throw new Error("PRD 缺附录 A.1（文档即契约，节不能丢）");
  const rows: A1Row[] = [];
  for (const line of section.split("\n")) {
    if (!line.startsWith("|")) {
      if (rows.length > 0) break; // 表格结束后遇到正文 → 收工
      continue; // 表头前的引语行
    }
    const cells = line.trim().replace(/^\||\|$/g, "").split("|").map((c) => c.trim());
    if (cells.length < 3) continue;
    const names = [...cells[0].matchAll(/`([^`]+)`/g)].map((m) => m[1]);
    if (names.length === 0) continue; // 表头/分隔行
    const tier = cells[2];
    if (!["L0", "L1", "L2"].includes(tier)) {
      throw new Error(`PRD A.1 出现非法分级「${tier}」（行：${cells[0]}）`);
    }
    for (const name of names) rows.push({ name, tier });
  }
  return rows;
}
```

（细则转伪代码：第一列反引号里的名字抽出来当工具名——一格可以放两个，比如
`` `deisolate_host` / `unblock_ip` ``；第三列是分级；表格结束后遇到正文就收工。）
这就是"文档面"三个字的机制含义：**改 A.1 表不改 manifest，测试当场红；反之亦然**。

**为什么 list_approvals 不进 FGA 矩阵**：矩阵管的是"角色×工具族→chat 对话面可
见/可提请"（4.2 的意图闸念的就是它）。我们的台账读口还没接进对话面（没有任何
worker 的 LLM 会提名它），先登记持证、暂不进可见面——这正是"点名例外"机制的
用途：**例外必须写名字，不许悄悄多**。四方对账的完整图景：

```
fixtures/tools.manifest.json（唯一事实来源）
   ≡ docs/prd.md A.1        （文档面：逐字一致 + 计数快照 24）
   ≡ worker 工具面/票面      （代码面：五个 TOOLS 常量 + 五个 run kind 票面 ⊆ manifest）
```

第三条"⊆"方向说明：对账测试只要求"worker 面里的每个工具都已在册"，**不要求
登记了的工具都被某个 worker 持有**——`isolate_host` 四件 L2（无 worker 持票）和
本步的 `list_approvals` 都是"登记在册、无人持票"的合法状态。

```ts
// 出身：票 48 gen:tool 脚手架生成的空壳（`pnpm gen:tool list_approvals --tier L1

import { fileURLToPath } from "node:url";
import Database from "better-sqlite3";

/** 缺省数据源：agent 服务自持库（compose 挂 ./data/agent:/app/data，票 41 口径）。 */
export const DEFAULT_AGENT_DB = fileURLToPath(
  new URL("../../../data/agent/agent.sqlite", import.meta.url),
);

const STATUSES = new Set(["pending", "approved", "rejected", "expired"]);
```

handler 本体（[list_approvals.ts:39-52](soc-demo/services/agent/src/list_approvals.ts#L39)）：

```ts
/** 审批台账查询：按状态过滤（可选）、按创建时间倒序，limit 夹在 1..100。 */
export async function list_approvals(
  params: Record<string, unknown> = {},
): Promise<ListApprovalsResult> {
  const dbPath =
    typeof params.dbPath === "string" && params.dbPath ? params.dbPath : DEFAULT_AGENT_DB;
  const status = typeof params.status === "string" && params.status ? params.status : undefined;
  if (status !== undefined && !STATUSES.has(status)) {
    throw new Error(`bad_status:${status}（只认 pending/approved/rejected/expired）`);
  }
  const rawLimit = typeof params.limit === "number" && Number.isFinite(params.limit) ? params.limit : 20;
  const limit = Math.min(Math.max(Math.floor(rawLimit), 1), 100);
  if (!existsSync(dbPath)) throw new Error(`db_not_found:${dbPath}`);
  const db = new Database(dbPath, { readonly: true, fileMustExist: true });
```

查询半边的细则转伪代码（原文在
[list_approvals.ts:53-84](soc-demo/services/agent/src/list_approvals.ts#L53)）：
两条 prepared statement 二选一（带/不带 status 过滤），`ORDER BY created_at DESC,
rowid DESC` 倒序；`total` 用 COUNT 单独算——**total 是过滤后的总数，不是截断后的
行数**（台账页脚"pending 共 N 张"要的是 N）；返回值逐字段显式装配，六个台账字段
之外的一个字节不带；`finally` 里 `db.close()`。

三条安全语义给保安队翻译一遍：**物理只读**=发的是"参观证"不是"钥匙"，handler
就算被说服了想写也写不了；**数据最小化**=台账给的是"卡号+状态"，卡上写的 L2
草稿全文不出门（场景 3/5 的审批卡 params 里可是装过整篇知识草稿的）；**fail-closed**
=查不了台账就报错，不拿"空台账"糊弄人——值班长以为没有待批事项，比系统报错
危险得多。

## 三、服务与中间件卡

**卡 1 · 文档即契约（PRD 表格被测试现场解析）**

- **它是什么**：A.1 分级表不是"给人看的文档"，是测试的**输入**——`parsePrdA1()`
  每次 `pnpm test` 都把 markdown 表格解析成断言数据。文档漂移=测试红，和代码漂移
  同罪同罚。
- **市面对照**：①文档与代码各写各的（最常见，必然漂移）；②OpenAPI/JSON Schema
  一类机读契约（彻底但写作成本高，PRD 变成写代码）；③"文档+解析器"折中（本卡：
  文档保持人话，格式约束换机器可读）。
- **本项目为什么这么做**：工具分级是安全语义，"PRD 说的"和"闸认的"必须一个是
  另一个的镜像。markdown 表格加一个 20 行解析器，成本远低于引入一套契约工具链。
- **业务上怎么选**：值得"文档即契约"的是**改动少、语义重、有稳定表格形态**的
  内容（分级表、权限矩阵、端口表）；常改的叙述性文档千万别绑进测试，否则改个
  错别字都是 CI 红灯。

**卡 2 · 点名例外清单（KNOWN_NOT_IN_A1 / extra 点名）**

- **它是什么**：对账规则"两边必须相等"在现实里总留不住——总有合法的"一边多
  一点"。机制回应：多出的部分**必须逐个写名字**进例外清单，清单外再冒一个就红。
  本步 `list_approvals` 加入 gateway 侧点名名单（与 `get_case` 并列），而 A.1 侧
  因为文档同步了，`KNOWN_NOT_IN_A1` 不用动。
- **市面对照**：①快照测试全量快照（改一行更新一整张，噪音大）；②allowlist/denylist
  （安全领域同构：默认拒绝+显式放行）；③baseline 文件（eslint 排除列表同思路）。
- **本项目为什么选点名**：例外清单是**安全债台账**——每个名字都该有一句"为什么
  还没对齐"。匿名的例外（`extra.length <= 1` 这类）等于给漂移开门。
- **业务上怎么选**：凡"理想态是相等，现实允许少量例外"的对账面，用点名清单；
  判据是看例外能不能一句话说清理由——说不清的例外不该存在。

**判据**：计数没变、名字没变、只有分级不一致——"分级逐字一致"断言精准咬住

哪天有人按文档"免验"直查，就真漏了。

**捣乱 C · 病表闯闸**（登记表 JSON 坏了，闸敢不敢放行）——即亲手验证 ③ 的 S2 幕：
