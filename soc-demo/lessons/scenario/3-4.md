## 二、调用链

全景。分诊 kb_check（1.4 的站 4）往下到向量库本体一共**三层 seam**（TriageKb → VectorStore →
REST client），每层都是可替换的 adapter——层数先声明，免得一问剥一层：

```
kb_check 节点（triage/flow.ts:147-178，1.4 已逐行讲过）
  │  拼查询参数 {host, path, user} → 亮票过闸（kb_lookup，L1）
  ▼
[TriageKb 接口] —— 分诊眼里的"知识库"（一个 lookup 方法）
  ├─ MemoryKb（票 13 内存 stub：4 条手写种子，确定性匹配）
  └─ ChromaKb（票 17 真检索面 adapter：拼查询文本→向量查询→映射 KbHit）
       │  查询文本 = [host, path, user].filter(Boolean).join(" ")
       │  病了 → console.warn + 返回 []（fail-open，可用性口径）
       ▼
[VectorStore 接口] —— 检索面本体（upsert / query 两个动作）
  ├─ MemoryVectorStore（内存替身：hashEmbedding + 余弦排序，单测确定性）
  └─ RealChromaClient（chroma 官方容器 REST v2 的 fetch client）
       │  upsert：POST /collections/:id/upsert（自算 256 维向量一起送）
       │  query：POST /collections/:id/query（n_results=k，score=1−distance）
       ▼
chroma 容器（compose 服务，宿主 18000；L2 空间 HNSW 索引）
```

装配处在 index.ts 一眼可见——**一个环境变量决定两个面用谁**：

📄 [services/agent/src/index.ts:59-62](soc-demo/services/agent/src/index.ts#L59)

```ts
const kbStore: VectorStore = KB_CHROMA_URL
  ? new RealChromaClient({ baseUrl: KB_CHROMA_URL })
  : new MemoryVectorStore();
const kbForTriage = KB_CHROMA_URL ? new ChromaKb(kbStore) : new MemoryKb();
```

compose 里设了 `KB_CHROMA_URL=http://chroma:8000`，生产走下路；本机离线开发不设，走上路
（内存替身，重启即空）。注意分诊的 KB（`kbForTriage`）和沉淀的写面（`kbStore`）是**同一个
seam 的两个用法**——写面只有 kb_write 用（INV-5），读面是 kb_check。

📍 大图节点:CK_Q(3.4 检索面)

### 站 3 · VectorStore：接口只有两个动作

📍 大图节点:VS_MATH(3.4 检索面)

📄 [services/agent/workers/knowledge/vector-store.ts:50-54](soc-demo/services/agent/workers/knowledge/vector-store.ts#L50)

```ts
/** 向量库 seam：upsert 幂等（重复 approve/resume 重入安全），query 只查已入库条目。 */
export interface VectorStore {
  upsert(doc: VectorDoc): Promise<void>;
  query(text: string, k: number, where?: { kind?: string }): Promise<VectorHit[]>;
}
```

两个动词正好对应知识的"生"（kb_write 的 upsert）与"用"（kb_check 的 query）。`upsert`
幂等（同 id 覆盖）是 3.3 讲过的重放安全的另一半；`where` 参数支持按 kind 过滤（chroma 的
`where` 元数据过滤），当前 ChromaKb 没用它——留作将来"只检索某类知识"的扩展位。

**MemoryVectorStore**（单测替身）的查询实现值得逐字看——它就是"向量检索"的最小可读版：

📄 [services/agent/workers/knowledge/vector-store.ts:108-119](soc-demo/services/agent/workers/knowledge/vector-store.ts#L108)

```ts
  async query(text: string, k: number, where?: { kind?: string }): Promise<VectorHit[]> {
    const q = this.embedding(text);
    const hits: VectorHit[] = [];
    for (const { vec, doc } of this.docs.values()) {
      if (where?.kind && doc.metadata.kind !== where.kind) continue;
      let dot = 0;
      for (let i = 0; i < DIM; i++) dot += q[i] * vec[i];
      hits.push({ id: doc.id, score: dot, text: doc.text, metadata: doc.metadata });
    }
    // 分数降序，稳定次序（同分按 id）——确定性断言依赖它
    return hits.sort((a, b) => (b.score - a.score) || (a.id < b.id ? -1 : 1)).slice(0, k);
  }
```

向量检索的全部数学就这三行：查询文本变向量 → 跟每条库内向量算**点积**（向量同向=相似，
点积大）→ 降序取前 k。最后那个"同分按 id"的 tie-break 是教学系统的诚实：**排序必须确定**，
单测断言才不抖。真 chroma 用 HNSW 近似索引换性能，语义相同。

### 站 4 · hashEmbedding：把文本变成"词面指纹"

📍 大图节点:VS_MATH(3.4 检索面)

embedding 注入件（缺省 `hashEmbedding`，`KB_EMBEDDING=chroma_default` 可切服务端模型）
的三个零件：

📄 [services/agent/workers/knowledge/vector-store.ts:70-85](soc-demo/services/agent/workers/knowledge/vector-store.ts#L70)

```ts
/** 分词：ascii 词 + CJK 单字（中文无空格，按字切）。检索语义 = 词面匹配。 */
export function tokenize(text: string): string[] {
  return text.toLowerCase().match(/[a-z0-9_]+|[\u4e00-\u9fff]/g) ?? [];
}

/** 稳定哈希 TF 向量：词频按 hash 投到 DIM 维，L2 归一化。同文本必得同向量。 */
export function hashEmbedding(text: string): number[] {
  const vec = new Array<number>(DIM).fill(0);
  for (const tok of tokenize(text)) {
    vec[fnv1a(tok) % DIM] += 1;
  }
  let norm = 0;
  for (const v of vec) norm += v * v;
  norm = Math.sqrt(norm);
  return norm === 0 ? vec : vec.map((v) => v / norm);
}
```

大白话翻译：把文本切成词（英文按词、中文按字），每个词用 FNV-1a 哈希成 256 维空间里的
一个"抽屉号"，词出现一次往抽屉里丢一颗豆子，最后整桶归一化。于是——

- **共享词面 → 向量相近**：查询和文档都含 "centos7"，同一个抽屉都有豆子，点积就大。
  教具 S1 实测：同文本向量逐位一致；S2 里 kb_A（含 centos7/演练）拿到 0.505，不含交集
  词的 kb_B/kb_C 是 0.000。
- **不共享词面 → 完全不相关**："SSH 爆破"跟 "brute force" 在这个模型里**毫无关系**——
  没有"语义理解"，只有词面指纹。这是它跟服务端语义模型（把"爆破"和 "brute force" 映到
  相近向量）的本质差距，换来的是**离线零依赖、跨进程逐位确定**（CI 不用下 80MB 模型，
  断言不抖）。
- **换模型不改代码**：embedding 是构造函数注入件，`KB_EMBEDDING=chroma_default` 一换，
  RealChromaClient 就不发本地向量、改发原文让服务端模型算——检索语义升级，seam 两侧
  零改动。

### 站 6 · 三个诚实的教学点：S3 输出里的"咦"

📍 大图节点:CH_COLL(容器 chroma)

教具 S3 那两行奇怪的输出，拆开是三个真问题：

**① score 为什么是负数？** 因为真容器的集合建在 **L2 距离**空间（3.2 看过的集合配置
`"space": "l2"`），而 score 的算法是 `1 - distance`——L2 距离是欧氏距离（约 0~1.41），
减完自然可能为负。这条口径当年注释写错成 cosine，票 51 已把注释修正为如实版
（[vector-store.ts:39-44](soc-demo/services/agent/workers/knowledge/vector-store.ts#L39)：
只保证"越大越近"的排序单调性，绝对数值不可跨实现互读——内存件是归一化向量的点积、
真 chroma 是 1−distance）。**排序不受影响**（越近 distance 越小、score 越大）；读教具
输出时记一条：score 只用来排名，别当相似度百分比解读。

**② 为什么"量子纠缠态"也命中？** 两个原因叠加：布景集合里**只有 1 条**，top-k 没有
**分数门槛**（不是"score>0.8 才算命中"，是"最 near 的 k 条照单全收"）——库越空，"命中"
越廉价。内存替身同款语义（S2 的 k=2 把 0 分的 kb_B 也返回了）。

**③ "命中"≠"相关"，那 R1 会不会被带偏？** 会面上：任何 env_fact 命中都触发"建议关单"
（R1 只看 kind，不看 score 也不看标题）。当前系统安全吗？安全，但**不是因为检索准**，而是
因为 INV-5——检索面里每一条都是人审过的**真事实**，"命中一条真事实"最坏也只是让分诊
多看一眼内部登记。这就是为什么"入库闸（D8）+人审（INV-5）"是知识系统**真正的承重墙**，
检索相关性只是体验问题。生产化时该补的是 score 阈值+语义模型（和"命中条目与告警主机
一致性校验"），路线已明。

顺带一个实操坑（教具外的手打实验）：直接 curl chroma 用 `query_texts` 让服务端自己
embedding 会报错（本版本要求 `query_embeddings`）——**写入方和查询方必须用同一个
embedding 函数**，向量空间才对得上。我们的 client 两侧都用注入的同一个函数，结构上
锁死了这个坑。

## 三、服务与中间件卡

### 卡 1（领域卡）· 知识检索的两副面孔：SQL LIKE vs 向量 top-k

- **它们是什么**：同一个知识库的两种查询。SQL LIKE（3.2 的 `/kb/search`）：`%关键词%`
  精确子串匹配，命中即中，给人对账用。向量 top-k（本步）：文本变向量比距离，返回最
  近的 k 条，给分诊机器用——查询词和文档**不必完全一致**，共享关键词面即可相近。
- **为什么分诊用向量**：告警是"centos7 Invalid user blimey"，知识是"环境事实：centos7
  授权红队演练"——两者没有一个词完全相等，但共享 "centos7" 词面，向量检索能把它们
  拉到一起；LIKE 做不到。为什么账面用 LIKE：人查账要的是"精确找到那条记录"，模糊相似
  反而是干扰。
- **业务上怎么选**：查询词与文档词面高度重叠（主机名、路径、账号——SOC 知识检索恰好
  是）→ 词面向量+小模型足够；要"意思相近"（同义词、跨语言）→ 语义 embedding 模型
  （代价：在线依赖+结果不确定）。**先问检索是给谁的、错一条的代价多大**，再选模型。

### 卡 2（自研纪律）· adapter 双实现：stub 不是"假货"，是 seam 的另一半

- **它是什么**：`TriageKb`/`VectorStore` 两个接口各配两个实现（内存替身 + 真容器 client），
  构造时注入。替身不是偷懒的 mock：MemoryVectorStore 是**完整实现**（同样的 embedding、
  同样的排序语义、同样的 top-k 行为），只是把存储从容器换成 Map。
- **回报**：① 单测离线确定性（CI 无 docker 也全绿，同分按 id 的 tie-break 就是为断言
  不抖）；② 票 13 用 stub 打通分诊、票 17 换真件，**分诊侧一行不改**；③ 本步教具脚本
  能在同一份代码上"S2 内存/S3 真容器"对照跑，语义差异一目了然。
- **市面同款**：hexagonal architecture（端口-适配器）的标准操作；testcontainers 是"用真件
  做集成测试"的同题另解——本项目两者都用（单测替身 + `chromaSmokeProbe` 能力探测的
  真容器冒烟：容器不可达显式 skip，绝不静默装绿）。
- **业务上怎么选**：接口小（两个动词）才养得起双实现；接口一旦长大（十几个方法），维护
  两份的成本会吃掉收益——**seam 要切在窄处**。
