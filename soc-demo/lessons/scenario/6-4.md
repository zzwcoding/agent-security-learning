### 站 1 · 按钮现身：两个条件的合取

前端纯逻辑层（React 之外可单测，[reveal.ts](soc-demo/services/web/src/reveal.ts)）
管"要不要出按钮"的两个判断：

📄 [services/web/src/reveal.ts:10-25](soc-demo/services/web/src/reveal.ts#L10)

```ts
/** 反查可见角色（A.2 特殊化口径：PII 反查不走工具闸，端点白名单 duty_lead/admin；
 *  与 services/agent/src/app.ts 的 PII_REVEAL_ROLES 同源，改一边必红）。 */
export const PII_REVEAL_ROLES: ReadonlySet<string> = new Set(["duty_lead", "admin"]);

export function canRevealPii(role: string | undefined): boolean {
  return !!role && PII_REVEAL_ROLES.has(role);
}

// <TYPE>：大写字母开头、大写字母/数字/下划线组成、成对尖括号——普通文本里的
// 「a < b」、小写标签都不算（不误报）。
const PLACEHOLDER_RE = /<[A-Z][A-Z0-9_]*>/g;

export function findPlaceholders(text: unknown): string[] {
  if (typeof text !== "string") return [];
  return [...new Set(text.match(PLACEHOLDER_RE) ?? [])];
}
```

两个设计决定值得划线。**其一，名单是镜像不是真身**：注释原话"与 app.ts 的
PII_REVEAL_ROLES 同源，改一边必红"——web 这份只管按钮可见性（6.3 讲过的
"可见性即第一收窄"），服务端名单才是权威闸；web 不能 import agent 的源码
（边界规则），两边一致性靠**测试锚定**（reveal.test.ts 有专门断言）。
**其二，占位符是扫出来的不是猜出来的**：正则 `<[A-Z][A-Z0-9_]*>` 只认大写实体
形态——正文里的"a < b"、HTML 小写标签都不会误触发按钮（注释原话"不误报"）；
`findPlaceholders` 输入非字符串返回空、输出去重保序——**文本里没有占位符就不出
反查按钮**，这是"检测驱动"与"猜"的分界线。

### 站 2 · 点击之后：并发反查与就地渲染

📄 [services/web/src/pages/CasePage.tsx:43-63](soc-demo/services/web/src/pages/CasePage.tsx#L43)

```ts
  // 票 49：反查结果按时间线条目就地展示（key → 人话行）。
  const [reveals, setReveals] = useState<Record<string, string>>({});

  // 票 49（ADR 0004-3）：脱敏占位符反查——把这条时间线里的每个 <TYPE> 占位符
  // 经 agent 受控端点（会话 + 角色白名单 + INV-8 审计）反查回原文，就地展示。
  // 服务端是权威闸，这里按钮可见性只是第一道收窄；结果只渲染给发起人自己。
  const revealRow = async (key: string, body: string): Promise<void> => {
    const placeholders = findPlaceholders(body);
    if (!session || placeholders.length === 0) return;
    try {
      const results = await Promise.all(placeholders.map((p) => revealPii(p, session.token)));
      setReveals((prev) => ({
        ...prev,
        [key]: results.map((r) => `${r.placeholder} → ${r.originals.join("、") || "（查无记录）"}`).join("；"),
      }));
    } catch (e) {
      const text = revealErrorText(e);
      setReveals((prev) => ({ ...prev, [key]: text }));
      message.error(text);
    }
  };
```

三个交互细节都有口径：**每个占位符一发请求**（`Promise.all` 并发——一条 note 里
三个占位符就是三发，M2 审计里三行 SUCCESS，各记各的 match_count）；**结果就地
显示在条目脚下**（`reveals[key]` 只存浏览器这页的 state——"结果只渲染给发起人
自己"，注释原话）；**失败也用人话就地显示**（revealErrorText，站 5）。

api 层的出站形态（薄客户端原则：同源相对路径 + Bearer 会话）：

📄 [services/web/src/api.ts:259-268](soc-demo/services/web/src/api.ts#L259)

```ts
export function revealPii(placeholder: string, token: string): Promise<PiiReveal> {
  return request<Record<string, unknown>>("/api/v1/pii/reveal", {
    method: "POST",
    headers: { "content-type": "application/json", authorization: `Bearer ${token}` },
    body: JSON.stringify({ placeholder }),
  }).then((r) => ({
    placeholder: typeof r.placeholder === "string" ? r.placeholder : placeholder,
    originals: Array.isArray(r.originals) ? r.originals.map(String) : [],
  }));
}
```

注意路径是**同源相对路径**（api.ts 文件头注释："跨源问题由 vite dev 代理解决"）
——浏览器只认识 :5173 自己，转发是谁的活？站 3 揭箱，本步的主角问题就出在这。

📄 [services/web/vite.config.ts:47-58](soc-demo/services/web/vite.config.ts#L47)

```ts
    proxy: {

      "/api/v1/alerts": { target: m2, changeOrigin: true },

      "/api/v1/kb": { target: m2, changeOrigin: true }, // 幕 5 KB 人审的 REST 面（curl 等价脚本用）
      "/api/v1/webhooks": { target: ingest, changeOrigin: true },
```

**数一遍：`/api/v1/pii` 不在表里**。vite dev server 按前缀最长匹配转发，没有匹配
规则的请求落在 vite 自己身上——`POST /api/v1/pii/reveal` 得到 404（空 body）。
本步实测的对照：

```
curl 直打 agent  :3003/api/v1/pii/reveal  → 200 {"placeholder":"<CN_ID>","originals":["110101199003071234"]}
curl 走浏览器线  :5173/api/v1/pii/reveal  → 404 空 body（请求根本没离开 vite）
```

前端拿到这个 404 后的表现，走 request 基座的兜底链：

📄 [services/web/src/api.ts:16-23](soc-demo/services/web/src/api.ts#L16)

```ts
async function request<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(path, { headers: { "content-type": "application/json" }, ...init });
  const body = (await res.json().catch(() => ({}))) as Record<string, unknown>;
  if (!res.ok) {
    throw new ApiError(res.status, typeof body.error === "string" ? body.error : "unknown");
  }
  return body as T;
}
```

404 且 body 解析不出 `error` 键 → `ApiError(404, "unknown")` → `revealErrorText`
按 status 404 给出"**映射表里查不到这个占位符（可能来自 mapstore 建立之前的
脱敏）**"——文案把"代理断线"误报成了"映射缺失"（revealErrorText 的 404 分支是
为 agent 的 `placeholder_unknown` 写的，它分不清这两种 404）。这条完整故障链
（按钮现身 → 点击 → 误导文案）已按纪律记入总纲"发现的问题"转票（修法：proxy
表加一行 `"/api/v1/pii": { target: agent, changeOrigin: true }`，学习阶段不改生产
代码）。

**为什么测试没抓住**：web 的页面测试跑在 jsdom 里，fetch 被 mock 直接拦截
`/api/v1/pii/reveal` 并回 200（pages.test.tsx:516-527）——**测试替身把代理层整段
绕过去了**，"单元全绿、走线断裂"。这是前端项目的经典盲区：mock 让你测得了
组件逻辑，测不了部署拓扑。

### 站 4-5 · 口径三问：原文为什么只在"点开的那一下"出现

交互设计看完，把 6.3 的敏感面口径翻译成 UI 语言。**问一：原文为什么不进时间线？**
时间线条目落 M2 库、web 全员可见、还进 eval 与检索——它是**广播面**；原文是
**点名面**。把 6.1 的脱敏产出粘进案卷可以（本步开头那条教具 note 就是这么造的），
但反查结果的原文如果回写时间线，就等于"值班长查一次，全员永久可见"——受控口
瞬间退化成广播口。所以代码里 `setReveals` 只写前端 state，**没有任何回写调用**；
刷新页面即消失，原文的落盘处自始至终只有 mapstore（6.3 大搜查的 0 命中就是这条
口径的账面证明）。

**问二：为什么点开才反查（而不是页面加载就自动还原）？**三个理由：①**最小暴露**
——原文跨网出现在响应体里的次数，正比于"有人主动要求知道"的次数；自动还原会让
每次刷新页面都产生 N 发原文传输，审计簿全是噪音，真正的"谁在什么时候想知道"反而
被淹没。②**责任显式化**——按钮即请求：点下去的那个人、那个时刻、那几个占位符，
在 M2 审计里一一对应（小字"每次查询留审计"不是装饰）；自动还原会把这个责任链
稀释成"系统自己干的"。③**权限差异**——soc1 看同一页面时按钮根本不出现（检测驱动
+角色镜像名单），页面加载自动还原就得给 soc1 也发原文或发 403 风暴，两头不讨好。
lazy reveal 让权限差异收敛成一个按钮的 display。

**问三：SSE 在哪？**——不在。反查是**请求-响应**的人的动作（6.3 证明它不产生
run），SSE 通道（/api/v1/events/stream）只承载 run 事件流；反查结果不存在事件
形态，也就不存在"原文经 SSE 泄漏给订阅者"的面。全链走线一句话：**广播面
（时间线/SSE）只有占位符，原文只在点对点的 REST 响应里，且那一下有审计。**

## 三、服务与中间件卡

**卡 1 · 检测驱动的敏感入口 UI（自研前端形态）**

- **它是什么**：敏感操作的入口不靠角色硬编码菜单，也不靠全局开关，而是
  "**数据里出现了什么 + 你是谁**"两个条件合取才渲染（本步：正文有 `<TYPE>` +
  角色在镜像名单）。占位符形状本身就是"这里有被脱敏内容"的机器可读标记——
  6.1 选占位符形态的伏笔在这里兑现。
- **市面对照**：①基于路由的角色守卫（整页整页控，粒度粗）；②feature flag
  平台（控的是功能不是数据形态）；③按需加载+权限点的数据行内操作（企业
  中后台常见做法，思想同本卡）。
- **本项目为什么这么做**：反查的需求天然是**行级**的——同一页面，有的条目
  带占位符有的不带；同一角色，看得见的条目脚下才有入口。"检测驱动"让入口
  自动跟随数据形态，新增一种占位符类型（比如未来的 `<PERSON>`）前端零改动。
- **业务上怎么选**：敏感动作入口的设计判据是"**入口的粒度是否等于数据的粒度**"
  ——行级敏感用行级入口（本卡）；页面级敏感用路由守卫；全局敏感用功能开关。
  无论哪种，**前端入口永远只是第一收窄**（按钮可以藏，服务端闸必须硬——本步
  捣乱 A 就是在测这个）。

**卡 2 · dev 代理与薄客户端走线（vite proxy 模式）**

- **它是什么**：浏览器只发同源相对路径，dev server 按前缀表转发给各后端
  （auth/chat→agent，cases/alerts→M2，webhooks→ingest）——后端零 CORS 配置，
  前端零环境感知。compose 里 web 容器 env（AGENT_URL/M2_URL/INGEST_URL）与
  vite.config.ts 读的是同一组开关。
- **市面对照**：①后端直开 CORS（每个服务配 Access-Control 头）；②独立 API
  网关/BFF 层（生产常见，dev 阶段重）；③环境变量注入 baseURL 直连（跨源
  cookie/凭证麻烦）。
- **本项目为什么选代理表**：九服务、三个后端、一个前端——代理表就是**前端的
  服务目录**，一行一个服务，分叉规则一目了然（"每个前缀只属于一个服务"）。
  代价本步也亲见了：**新增后端路由必须同步加表**，漏一行就是一条断走的线，
  且单元测试测不出来（jsdom 没有代理层）。
- **业务上怎么选**：dev/小团队 → vite proxy 表（直观、零基建）；生产/多前端 →
  统一网关或 BFF（一处管鉴权/限流/路由）；无论哪种，**给走线配一条端到端
  冒烟**（curl 打 :5173 全部代理前缀各一发，断言非 404）——本步的问题就是
  这条冒烟缺席漏掉的。

## 四、防线对号

| 防线 | 在本步的位置 |
|---|---|
| 可见性即第一收窄（FR-M8.2 同款） | 按钮只对 duty_lead/admin 渲染（镜像名单）——soc1 的页面上入口不存在 |

| 敏感面口径（INV-4 类推的 UI 半边） | 反查结果只进前端 state：不回写时间线（广播面只有占位符）、不发 SSE、刷新即逝 |

| 每查必审计的 UI 呈现 | 按钮旁小字明示"每次查询留审计"；一发点击 = N 发请求 = N 行审计（占位符一一对应） |
| lazy reveal（最小暴露） | 点开才反查：原文跨网次数=主动求知次数，责任链在审计簿上一一对应 |
| 走线完整性（本步新增教学点） | vite proxy 表漏行 → 按钮 404 误导文案——已记"发现的问题"转票；教训=走线要配端到端冒烟 |

**捣乱 B · 走线排错三连问**（收官排错题，把本步的走线问题亲手走一遍）：

> duty_lead 在案件页点"反查 PII"，条目脚下出现红字"映射表里查不到这个占位符

> 三问：①请求死在哪一段？②文案为什么误导？③最小验证命令是什么？

<details><summary>答案</summary>

①请求死在 **vite dev 代理**：api.revealPii 发的是同源相对路径，vite.config.ts 的
proxy 表没有 `/api/v1/pii` 前缀行，请求落在 vite dev server 自己身上返回 404，
根本没到 agent（更没到 guards/mapstore）。②文案误导的原因：request 基座把"解析
不出 error 键的 404"打包成 `ApiError(404,"unknown")`，revealErrorText 按 status=404
走了"映射缺失"分支——那个分支是为 agent 的 `placeholder_unknown`（真查无此人）
写的，两种 404（代理断线 vs 映射缺失）共用一个文案。③最小验证：`curl -s -o
/dev/null -w '%{http_code}' -X POST http://127.0.0.1:5173/api/v1/pii/reveal -H
"authorization: Bearer $TOK" -d '{"placeholder":"<CN_ID>"}'` → 404，而 3003 同发
200；修复 = proxy 表加 `"/api/v1/pii": { target: agent, changeOrigin: true }`（已记
总纲转票，学习阶段不动生产代码）。方法论：**前端报"资源不存在"时，先分清是
业务 404 还是拓扑 404**——同一串字符，死因隔着一层代理。

</details>

**捣乱 C · 纸面推演：把反查结果回写时间线会怎样**（不动手的思考题）：假设为了
"方便其他同事查看"，把 `reveals[key]` 的原文提交回 M2 时间线（新增一个 note）。

## 场景 6 闯关（三题）

<div>

**题 1 · 豁免的因果**：调查报告里有两条 IP——`10.47.100.23`（自家 db-01 的内网
地址）和 `198.51.100.23`（外联 C2）。过一道 `/pii/anonymize` 后各变成什么？
为什么同一台识别器给出两种待遇？如果哪天有人提议"干脆全部 IP 都脱了最安全"，
你会用哪句话反驳？

<details><summary>答案</summary>

`10.47.100.23` 原样存活（RFC1918 豁免），`198.51.100.23` 换成 `<IP_ADDRESS>`（公网
照脱）。机制：`Rfc1918ExemptIpRecognizer` 继承内建 IpRecognizer 的识别结果，再用
RFC1918 三段正则（10/8、172.16-31、192.168/16）把内网命中**过滤掉**——"先照常认，
再把内网的扔掉"。待遇差异的依据是**"这条数据是谁的身份"**：内网 IP 是资产标识
（同主机归并/资产核对的关键证据，决策记录 #8），脱了它"告警里的 10.47.100.23 和
案卷里的 db-01 是不是同一台机器"就没法答——脱敏破坏业务正确性；公网 IP 在告警里
多半是"外面的地址"（可能是受害人家宽、可能是 C2），带着它出域是给别人递隐私。
反驳那句话："脱敏的目的不是脱得越多越安全，是**该出域的最小集**——把资产标识
也脱掉，安全没有多一分，调查能力先少一半；真正该问的是'这条数据出域后泄露的是
谁的秘密'"。（顺带的边界题：环回 127.0.0.1 不在三段里，照脱——豁免清单是精确
网段，不是"不重要的 IP"。）

</details>
