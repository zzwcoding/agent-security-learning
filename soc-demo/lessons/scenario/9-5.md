## 二、调用链

```
[父 run · outcome 节点（judge 判不充分分支）]
  ▼
[站1] gap：消毒 → LLM 翻译缺口 → 结构化 {gap_description, unknown, suggested_focus}
  │     （坏形重试 1 次，再败机制档缺口降级——翻译失败 ≠ 停摆）
  ▼
[站2] recordRound：轮次归集落 M2（(hypothesis_id, round_no) 唯一，重放幂等替换）
  ▼
[站3] round_relay 事件 → relay 件（dispatcher 层）→ launchRound 拉起 round k+1
  │     幂等锚：ledger.findByRound 有行 = 已拉起，重放跳过
  ▼
[round k+1 的 intake 读出 gap → planner 输入带缺口 → C₂≠C₁（9.2 已见）]
  ▼
[站4] 防转指纹：相邻轮「任务集+gap 摘要」相同 → hunt_round_spin_denied
  │     → cancelled(spin)，不冒充 refuted
```

### 站 1 · gap：把「不够」翻译成「补什么」

📍 大图节点:GAP(9.5 gap 换轮)

outcome 节点里，judge 说不充分就走 gap 翻译（[flow.ts:293-297](soc-demo/services/agent/src/orchestration/flow.ts#L293)）：

```ts
        // 不充分 → gap 翻译缺口（票 75 真节点：gap.ts 消毒 + 结构化缺口 schema 降级）
        let gap: RoundRecord["gap"] = null;
        if (judge && !judge.sufficient) {
          gap = await analyzeGap({ orch, audit, runId }, ctx);
        }
```

`analyzeGap`（[gap.ts:121-193](soc-demo/services/agent/src/orchestration/gap.ts#L121)）与
planner/judge 是同一套纪律的第三份实现：消毒（judge 裁决与既有证据都是上游 LLM 产物，
tool_output 通道，非 allow 占位符）→ LLM 翻译 → `parseGap` 显式验型
（[gap.ts:63-77](soc-demo/services/agent/src/orchestration/gap.ts#L63)：`{gap_description,
unknown, suggested_focus[]}` 三字段全必填）→ 坏形重试 1 次 → 再败**机制档缺口降级**
（[gap.ts:166-180](soc-demo/services/agent/src/orchestration/gap.ts#L166)）：拿 judge 的
gap_description 兜底、unknown 标 `gap_parse_degraded`——**翻译失败 ≠ 停摆**：下一轮
planner 仍拿到一个能消费的 gap 形；若下一轮组合真因此原地踏步，防转指纹闸兜底掐断。
三个决策面连「降级后谁兜底」都是对齐的。

产物去向两头都有主：随轮次归集落 M2（站 2），下一轮 intake 读出来当 planner 输入
（9.2 站 1 的 `ctx.state.gap = lastGap`）。**gap 是轮与轮之间的接力棒，不是日志**。

### 站 2 · 轮次归集：一轮的全部事实，一行不落地进假设账面

📍 大图节点:RECORD_ROUND(9.5 gap 换轮)

归集写口（[flow.ts:300-306](soc-demo/services/agent/src/orchestration/flow.ts#L300)）把
本轮四样东西打成一包送 M2：

```ts
        await orch.port.recordRound(hypothesisId, {
          round_no: roundNo,
          tasks,
          children: joined.map((c) => ({ run_id: c.run_id, status: c.status })),
          judge,
          gap,
        });
```

M2 侧的落账（[hypotheses.ts:204-239](soc-demo/services/case-backend/src/hypotheses.ts#L204)）
有个关键设计：**(hypothesis_id, round_no) 唯一**，重报同轮是 `ON CONFLICT … DO UPDATE`
幂等替换、不产生第二行（INV-6 同族，注释原话「事件重放/重报同轮幂等替换」）：

```ts
    db.prepare(
      `INSERT INTO hypothesis_rounds (id, hypothesis_id, round_no, tasks, children, judge, gap, created_at)
       VALUES (?, ?, ?, ?, ?, ?, ?, ?)
       ON CONFLICT(hypothesis_id, round_no)
       DO UPDATE SET tasks = excluded.tasks, children = excluded.children,
                     judge = excluded.judge, gap = excluded.gap`,
    ).run( ... );
```

为什么幂等这么要紧？relay 与 autorun 都是 at-least-once 语义（0-0 第 2 节），同一条
「round 1 完成」的事实被重放两次时，账面不能长出两个 round 1。写口公开在 REST
（[app.ts:373-387](soc-demo/services/case-backend/src/app.ts#L373) 的
`POST /api/v1/hypotheses/:id/rounds`，重放 200、首报 201），编排循环经
hypothesis-port 的 adapter 调它——跨服务只走公开面（R1），agent 不翻 M2 的库。

children 数组就是 [TERMS「查证轮」](TERMS.md)条说的「父子 run 簿记的假设侧视图」：
agent 侧真相在 hunt_run_links（9.3），假设侧视图在 hypothesis_rounds.children——两处
口径同源（都来自轮次 outcome 一起上报），读哪个都能对上家谱。

### 站 3 · relay：循环性不在图里，在 dispatcher 层

📍 大图节点:RELAY(9.5 gap 换轮)

归集完，不充分的轮在事件流上发一条接力信号（[flow.ts:319-326](soc-demo/services/agent/src/orchestration/flow.ts#L319)）：

```ts
          ctx.emit("audit", {
            action: "round_relay",
            hypothesis_id: hypothesisId,
            next_round: roundNo + 1,
            parent_run_id: runId,
            fingerprint: ctx.state.tasks_fingerprint,
          } as Record<string, unknown>);
```

**为什么循环不画进图里？** flow.ts 文件头（[:3-7](soc-demo/services/agent/src/orchestration/flow.ts#L3)）
写死：「图内永远一轮一条串行链（ADR 0005）」——LangGraph 的图是有限状态机，把「不知道
几轮的循环」塞进图，checkpoint、预算账、取消信号全都要跟着变成变长的；把循环拆到
图外，每轮就是一张普通的串行六节点图，**轮 k 的终点发事件、接力件把它折成轮 k+1 的
拉起**——跟 9.1 里 autorun 拉轮 1 用的是同一把 launcher（[index.ts:217-219](soc-demo/services/agent/src/index.ts#L217)
注释：hypothesis.created → 轮 1 与 relay 的轮间接力共用同一 launcher）。

接力件（[relay.ts:26-55](soc-demo/services/agent/src/orchestration/relay.ts#L26)）的幂等双保险：

```ts
    const key = `${p.hypothesis_id}:${p.next_round}`;
    if (deps.ledger.findByRound(p.hypothesis_id, p.next_round)) {
      deps.log?.({ info: "round_relay_dup", ... });
      return;
    }
    if (inflight.has(key)) return;
```

（[relay.ts:37-43](soc-demo/services/agent/src/orchestration/relay.ts#L37)）①簿记锚：该轮已
拉起 → 重放/迟到事件跳过；②在途集合：拉起尚未落账的窗口内重复投递也只起一次。
跟 9.1 的防重三闸对齐看：autorun 防的是「同事件重放起重轮」，relay 防的是「同接力事件
重复投递」——**每一层过闸口，都自己带幂等**。

### 站 4 · 轮次视图逐字段解读（S9 的招牌读法）

📍 大图节点:ROUND_VIEW(9.5 gap 换轮)

回到开头那段 JSON，每一轮五个字段各管一个问题的答案：

| 字段 | 答什么问题 | 读法要点 |
|---|---|---|
| `round_no` | 第几轮 | 从 1 连续递增；断号=有轮没跑成（去 runs 表查 failed） |
| `tasks` | 这轮查了什么（组合 C_k） | tool 在不在模板菜单里；params 有没有带上一轮 gap 的焦点（C₂ 应有）；rationale 是 planner 的一句话依据 |
| `children` | 扇出几路、各自结局 | run_id 可回查 runs 表与事件流；status=failed 的轮不冤枉：judge 拿到的是 failed 摘要 |
| `judge` | 拍板结果 | sufficient/verdict/confidence/gap_description 四件套；confidence 紧贴地板 0.7 的收敛要多看一眼（9.4 纪律三） |
| `gap` | 为什么有下一轮、下一轮查什么 | null = 本轮收敛（终局）；suggested_focus 就是下一轮 params 里的 focus——**C₂≠C₁ 的证据就在这** |

配合 hunt_run_links 表（家谱）与 runs 表（每个 run 的状态机/预算账），轮次视图把「一个
假设的一生」从立项到终态完整铺开——web 狩猎页的轮次卡片读的就是这份数据
（[TERMS「侦查怀疑书」](TERMS.md)条说的「页面映射轮次视图行」）。

### 站 5 · 防转指纹：「换轮必须换组合」是闸不是建议

📍 大图节点:SPIN_GATE(9.5 gap 换轮)

环最怕的不是查得慢，是**原地打转烧钱**：LLM 每轮都给同一个组合、gap 也没实质变化——
没有闸的话，max_rounds=6 就是 6 轮一模一样的烧 token。防转指纹
（[spinFingerprint，llm-stubs.ts:122-126](soc-demo/services/agent/src/orchestration/llm-stubs.ts#L122)）：

```ts
export function spinFingerprint(tasks: PlannedTask[], gap: GapOutput | null): string {
  return "sha256:" + createHash("sha256")
    .update(`${taskFingerprint(tasks)}#${gap ? paramsHash({ gap }) : ""}`)
    .digest("hex");
}
```

指纹 = hash(排序后的任务集 + **本轮规划时输入的 gap**)。gap hash 在指纹内就是「实质
变化豁免」：组合相同但缺口输入被新证据改写了 → 指纹不同 → 不判空转；组合与缺口双双
原地踏步 → 相邻轮指纹相同 → dispatch 处拒组合（[flow.ts:150-170](soc-demo/services/agent/src/orchestration/flow.ts#L150)，
9.3 站 1 认过门牌）：

```ts
        if (fingerprint !== "" && fingerprint === prevFingerprint) {
          recordAudit(audit, runId, { action: "hunt_round_spin_denied", ..., result: "DENIED" });
          ctx.emit("audit", { action: "hunt_round_spin_denied", round_no: roundNo, fingerprint });
          await orch.port.transition(hypothesisId, "cancelled", { reason: "spin" });
```

**拒组合 → 假设 cancelled(spin) → 空轮归集（outcome 的 spin 分支
[flow.ts:248-259](soc-demo/services/agent/src/orchestration/flow.ts#L248)，拒组合事实可
回放）→ 无接力。** 注意终态是 cancelled 不是 refuted——组合没查出新东西，不等于「证明了
假设不成立」；把查不动冒充成证伪，是环最隐蔽的说谎方式，这里被状态机口径堵死（9.6
捣乱②同款口径：cancelled 不冒充 refuted）。

**一个诚实的实测观察**：fake 栈打不着这把闸——FakeLoopGap 的 suggested_focus 是
`followup:{evidence_so_far.length}`（[llm-stubs.ts:73-83](soc-demo/services/agent/src/orchestration/llm-stubs.ts#L73)），
轮数涨一焦点就变，指纹必然不同。这不是闸失灵：**「相邻轮组合必不同」在 fake 里是机制
保证**（llm-stubs.ts:6-8 注释原话「相邻轮组合必不同，即 fake LLM 两轮 C₂≠C₁ 的机制
保证」），真 LLM 才有机会偷懒、才轮到指纹闸执法。行为断言在 flow.test.ts。

## 三、服务与中间件卡

**卡 1 · ▼循环性在 dispatcher 层（事件接力 vs 图内环，自研编排形态）**

- **它是什么**：轮间循环 = 图外接力件订阅 round_relay 事件 → 复用拉起件开下一个 run；
  图内只有一条六节点串行链。
- **市面替代**：LangGraph 的条件边 + 自环（图内循环）；Temporal 的 child workflow +
  continue-as-new（框架级循环）。
- **为何这么选**：图内环让「每轮一本预算账」「每轮一次取消检查」「每轮独立 checkpoint」
  全变成变长状态，框架能力（中断恢复/时间旅行）对变长循环支持都很别扭；接力形态下
  每轮是普通 run，m3 的全部既有机器（202/分发/预算/审计/SSE）原样生效——**编排循环
  没有为"循环"定制任何新基建**。代价是轮间状态要经 M2 归集中转（gap/证据流水），但
  这笔中转本来就是账面该记的。
- **业务上怎么选**：循环体里有「每轮独立记账/可独立取消/可独立恢复」诉求 → 图外接力；
  纯内存小循环（毫秒级）→ 才图内解决。判断标准：循环的**每一圈要不要被运行时当独立
  实体看待**。

## 五、亲手验证（必选）

**① 读轮次视图，亲手验证 C₂≠C₁：**

```bash
curl -s localhost:3002/api/v1/hypotheses/$HYP | python3 -c "
import json,sys; d=json.load(sys.stdin)
for r in d['rounds']:
    print('round',r['round_no'],'C=',['%s(%s)'%(t['tool'], ','.join(t['params'].keys())) for t in r['tasks']],
          '| judge:', (r['judge'] or {}).get('sufficient'), '| gap:', bool(r['gap']))"
```

预期（hunt_webshell 实测）：

```
round 1 C= ['playbook_lookup(q)', 'graph_query(q)'] | judge: False | gap: True
round 2 C= ['graph_query(q,focus)'] | judge: True | gap: False
```

C₁ 两件、C₂ 一件且参数多了 focus（值就是 round 1 的 suggested_focus `["initial"]`）——
**换组合的证据链：gap 的焦点字段出现在下一轮的 params 里**。

**② 看接力事件的幂等锚：**

```bash
sqlite3 "file:data/agent/agent.sqlite?mode=ro" \
  "SELECT substr(payload,1,200) FROM run_events WHERE run_id='$RUN' AND payload LIKE '%round_relay%';"
sqlite3 "file:data/agent/agent.sqlite?mode=ro" \
  "SELECT role, round_no, substr(run_id,1,13) FROM hunt_run_links WHERE hypothesis_id='$HYP' ORDER BY created_at;"
```

预期：父 run 事件流一条 `round_relay`（next_round:2）；簿记四行 round1/两 task/round2——
relay 落的锚与 autorun 落的锚格式一致（都是 launcher 落的），`findByRound` 查的就是
role='round' AND round_no=2 那行。

**③ 归集幂等（重放同轮不产生第二行）：**

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST localhost:3002/api/v1/hypotheses/$HYP/rounds \
  -H 'content-type: application/json' -H 'x-actor-id: agent:hunt_flow' \
  -d '{"round_no":1,"tasks":[],"children":[],"judge":null,"gap":null}'
sqlite3 "file:data/case-backend/case-backend.sqlite?mode=ro" \
  "SELECT round_no FROM hypothesis_rounds WHERE hypothesis_id='$HYP' ORDER BY round_no;"
```

预期：`HTTP 200`（dedup=true——同轮重放走 UPDATE 分支）；表里还是两行（round 1 被
空数据**替换**）。⚠️ 这是写口幂等的直接验证，会把你教学主角的 round 1 归集覆盖成空——
**用完场后别把这招用在要留档的假设上**，或者干脆拿一条新的假设玩。（幂等替换的威力
与危险同源：事件重放安全的前提是「重放的是同一份事实」。）

## 六、捣乱实验（必选）

**捣乱 A · 手写一条「空轮」归集，看轮次视图怎么暴露它：**

接着 ③ 的现场（round 1 已被覆盖为空 tasks/children/judge=null/gap=null）再读一次
轮次视图——这就是 9.2 站 1 说的「失败轮归集形」：`tasks=[]` 且 `judge=null`。机制里
它有专门用途（planner 连续两轮失败的判定原料，[flow.ts:108-109](soc-demo/services/agent/src/orchestration/flow.ts#L108)：
「失败轮归集形 = 空组合且无 judge」→ 下一轮再失败 → cancelled(planner_broken)）——
**空轮是一个有语义的状态，不是脏数据**。你刚才能手动写出它，恰恰因为写口是公开幂等的；
机制自己写它时，每一笔都带 hunt_round_outcome 审计（details 里有 planner_failed:true
或 spin:true 标注）——**同一种形态，有没有审计痕，是账面与涂改的分界**。

**捣乱 B · 推演 spin 闸的触发条件（grep 验证，不必实测）：**

要让指纹闸触发，得让「相邻轮任务集 + gap」完全一致。用 fake 三件套推一遍：

1. planner 有 gap 时换 pivot 工具（llm-stubs.ts:42-56）→ 任务集必变 → 指纹必变；
2. FakeLoopGap 的 focus 随 evidence_so_far 长度变（llm-stubs.ts:79）→ gap hash 必变。

两条路都堵死了 → fake 永远打不着闸（实测两轮就收敛，也到不了第三轮）。真 LLM 下
这两个「必变」都变成「通常变」，闸才有活干。验证闸本身在位：

```bash
grep -n "hunt_round_spin_denied" services/agent/src/orchestration/flow.ts services/agent/src/orchestration/flow.test.ts | head -4
```

预期：flow.ts:154（记录）与 flow.test.ts（行为断言）各有着落——**闸的机制在 dispatch、
断言在测试、教学在本步**。

## 场景题闯关（本步 1 题）

**Q：防转指纹 = hash(任务集 + gap)。如果把 gap 从指纹里去掉（只 hash 任务集），会误伤
哪种合法轮次？用「两轮查同一工具但焦点不同」举例说明。**

<details><summary>答案（点击展开）</summary>

gap hash 在指纹内表达「实质变化豁免」。去掉它，只认任务集：假设第一轮查
file_change_query 发现可疑文件，gap 翻译出的焦点是「该文件的进程来源」；第二轮 planner
合理决定**再查一次 file_change_query、但参数聚焦到新查明的进程路径**——组合名相同、
实质输入完全不同（新证据改写了缺口）。没有 gap hash，这两轮会被误判成空转、直接
cancelled(spin)——**把「增量追查」错杀成「原地打转」**。有了 gap hash，焦点变了指纹就
变，追查放行；真正该拦的是「组合与缺口双双原地踏步」的纯空转。这也解释了实测里
fake 栈为什么永远打不着闸：FakeLoopGap 的焦点随轮数递增，指纹天然不同。</details>
