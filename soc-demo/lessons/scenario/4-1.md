# 场景 4 · 步 4.1 —— L2 建议从哪来：调查报告的"纸上谈兵"与 chat 的"提请单"

> 场景 3 讲的是知识入库这一种 L2（kb_write）的审批全链。场景 4 换一种更"危险"的 L2——
> **高危响应动作**（隔离主机、封禁 IP），把审批之旅从头再走一遍，走得更深：意图闸三态、
> 信封链盖印、ApprovalToken 的密码学细节、六种拒票理由、焚毁与保质期。
> 第一步先回答一个"源头"问题：**"把主机隔离掉"这个念头是谁产生的？** 答案有两个——
> 调查报告会在案卷上写"建议隔离"，但它只是纸上谈兵，永远不会自己动手；
> chat 对话里人说"请隔离"，系统才真的开一张审批卡。这两个来源之间的落差，
> 场景 2 埋的 case_000002 正好是活教材。
> 术语卡词翻 `TERMS.md`（同一比喻体系：审批卡/一次性密令/焚毁坟场/意图闸/手令票面/闸体…），
> 本文遇到老术语只回指不另起解释。

**位置感**（本场景 7 步路线图）：

```
✅ 4.1 L2 建议从哪来（你在这里）
⬜ 4.2 意图闸三态
⬜ 4.3 interrupt 挂起与审批卡
⬜ 4.4 值班长批准：铸 ApprovalToken
⬜ 4.5 resume 与验票：六拒因
⬜ 4.6 焚毁与一次性
⬜ 4.7 保质期与队列（收官 + 闯关三题）
```

## 一、操作（位置感）

先看"纸上建议"长什么样。打开 case_000002（场景 2 反复用过的爆破案，web 界面选案 or
直接 curl），它的时间线里躺着一份调查报告，末尾"建议动作"一节写着：

```
### 建议动作（只建议不执行；L2 须走人审）
- `isolate_host` {"host":"app-01"} — 调查认定严重度 ≥3，建议隔离主机
  （只建议：worker 无 L2 票，执行须人审铸票）
```

再查审批台账——这份建议对应的审批卡有多少张？答案是**零**：

```bash
curl -s http://127.0.0.1:3003/api/v1/approvals | python3 -c \
  "import json,sys; [print(c['id'][:14],c['status'],c['tool']) for c in json.load(sys.stdin)]"
# 本步实测（动手前）：只有场景 3 留下的两张 kb_write 卡，没有任何 isolate_host 卡
```

这就是场景 2.3 说的"**建议/执行鸿沟**"的实况：机器查完案子确实想隔离 app-01，但这个
念头只落在案卷文本里，审批流程压根没被触发。**建议（recommendation）和执行（execution）
之间隔着一整条人审链**——本场景就是把这条链拆开看。

然后看第二个来源。用值班长的脸登录，在对话框里说出那句话：

```bash

curl -s -X POST http://127.0.0.1:3003/api/v1/auth/login \
  -H 'content-type: application/json' -d '{"username":"duty_lead@soc.local"}'
# 预期：200，返回 token（HMAC 签名的会话票）+ visible_tools（这个角色看得见的工具清单）
```

拿 token 调 chat 正门（下文"亲手验证"有完整命令）。本步实测，SSE 流的最后两帧：

```
event: token
data: {"type":"token","run_id":"run_6ae4b2bf-…","delta":"isolate_host 属审批动作：
       已提交审批卡，等待值班长裁决（批准后经 ApprovalToken 验签执行）。"}

event: approval_required
data: {"type":"approval_required","run_id":"run_6ae4b2bf-…",
       "approval_id":"apr_baf3f3a8-fd09-4fcc-9c80-0c4f67e66a88",
       "node":"execute","tool":"isolate_host","params":{"host":"app-01"}, …}
```

同样是"隔离 app-01"这个念头：调查报告产生的只进案卷（零张卡），人从对话里说的

### 站 1 · 调查报告的建议是怎么"生"出来的

📍 大图节点:INV_SUGGEST（4.1 建议来源）

场景 2.3 讲过报告的输出契约（parseReport 显式验型、findings 引用真实工具输出）。当时
没展开的是 `recommended_actions` 这个字段怎么填。教学环境的"调查 AI"是规则件
（AGENT_LLM=fake，1.5 讲过这个开关），它的填法是纯查表：

📄 [services/agent/workers/investigation/llm.ts:134-141](soc-demo/services/agent/workers/investigation/llm.ts#L134)

```ts
      recommended_actions:
        kase.severity >= 3 && kase.entities.hosts[0]
          ? [{
              tool: "isolate_host",
              params: { host: kase.entities.hosts[0] },
              justification: "调查认定严重度 ≥3，建议隔离主机（只建议：worker 无 L2 票，执行须人审铸票）",
            }]
          : [],
```

大白话：**案子够严重（≥3）而且知道是哪台主机**，报告就建议"隔离这台主机"。case_000002
严重度 3、主机 app-01，两条都中——所以它的报告里有这条建议。把这一步的三件套补齐：
**为什么用纯查表**——建议的参数（动哪台主机）必须来自确定性事实（案件严重度+实体清单），
不能让模型自由发挥（做反了会怎样：LLM 信口建议"隔离 db-99"，审批卡上冻住的就是一个
编造参数，值班长批的是幻影）；**为什么只建议**——见下面站 2 的结构证据。注意 justification
里那句自我声明："只建议：worker 无 L2 票"——这不是给用户看的客套话，是代码结构的如实描述。
调查 worker 的类里**根本没有**审批回路：

📄 [services/agent/workers/investigation/flow.ts:25-26](soc-demo/services/agent/workers/investigation/flow.ts#L25)

```ts
//   - worker 没有 awaitApproval/executeApproved——调查报告的 recommended_actions
//     只是建议，「只提建议不动手」落在结构上：isolate_host 永远到不了执行层。
```

对比 chat worker（来源 B）：它的类里**有** `ctx.executeApproved`（本步站 4 会读到）。
"能不能动手"不写在提示词里、不靠 AI 自觉，靠**这个 worker 有没有装配那根管子**——
这是本项目反复出现的纪律：安全语义落在代码结构上，不落在品格上。

### 站 2 · 建议落进案卷：一行字而已

📍 大图节点:TL_WRITE（4.1 建议来源）

建议生成后去哪？跟着 write_timeline 节点走一遍。报告先被渲染成人读的 markdown：

📄 [services/agent/workers/investigation/schema.ts:118-123](soc-demo/services/agent/workers/investigation/schema.ts#L118)


小节标题自己就写着"只建议不执行"。然后整个 markdown 连同结构化 JSON 一起，作为一条
时间线写入案卷（这一步调的是 `add_timeline_entry`——L1 写工具，过的是任务票闸）：

📄 [services/agent/workers/investigation/flow.ts:493-512](soc-demo/services/agent/workers/investigation/flow.ts#L493)


看清楚这个终点：`addTimelineEntry`——**档案室的笔**（TERMS"档案室"条：case-backend :3002
管告警/案件/审计/KB 账面），不是审批开卡器。调查子图五站走完，"建议隔离"的最终归宿是
案卷上的一行字。把这条来路的时序接缝一次钉死：**产物躺在哪**——M2 库 `timeline_entries`
表里的一行（body 带建议 markdown）；**谁来接手**——**没有谁**：审批链不读时间线、没有
循环扫建议、没有事件广播，它和审批流程的触发关系是**零**；对照来源 B 同一时刻的样子——
chat 的 `approval_required` 帧落进 run_events 表后，SSE 每 100ms 读增量推给 web 审批页弹卡。
同一种"隔离主机"的念头，一边躺进没人翻的表，一边落进实时直播——这就是两条来路的全部
时序差别。谁负责把案卷上的建议变成执行？**看的人**。人工读报告 → 人觉得有理 → 人去触发
审批——本系统里这条链没有自动化，是刻意的（"AI 可以建议，动手必须人拍板"）。3.5 的
关单建议也一样：outcome 节点只落建议字段，真正关单的是 SOC1 手点的 close_flow。

### 站 4 · execute 分岔：只读直查 vs 提请审批

📍 大图节点:EXEC_SPLIT（4.2 意图闸三态）

意图和参数都有了，execute 节点按意图闸（TERMS"意图闸"条：chat worker 的 intent_gate，

📄 [services/agent/workers/chat/flow.ts:312-325](soc-demo/services/agent/workers/chat/flow.ts#L312)

### 站 5 · 实测对账：一张卡的一生起点

📍 大图节点:OPEN_CARD（4.3 挂起与审批卡）

本步实测的 run `run_6ae4b2bf` 事件序列（agent 库 run_events 表，id 737-750）：

| id | 事件 | 说明 |
|---|---|---|
| 737 | audit update queued→running | 开跑 |
| 738/739 | node_enter/exit input_guard | 注入扫描通过 |
| 740-743 | load_context + tool_call/tool_result get_alert | 拉案件上下文，L0 只读过任务票闸（tier:"L0"） |
| 744/745 | intent_classify | 关键词命中 isolate_host 0.9 |
| 746/747 | intent_gate | 三态裁决 = require_approval |
| 748 | node_enter execute | 进执行节点 |
| 749 | token 帧 | "已提交审批卡，等待值班长裁决" |
| 750 | **approval_required** | 开卡 + interrupt 挂起（卡 `apr_baf3f3a8`） |

审批卡落在 agent 库的 approvals 表里（pending），run 行状态翻成 `awaiting_approval`；
M2 审计簿同步多一行开卡留痕（INV-8）：

```
sqlite> SELECT action, actor, object_type, result FROM audit_entries
        WHERE object_id LIKE 'apr_baf3f3a8%';
create|{"type":"system","id":"m3:supervisor"}|approval|SUCCESS
```

把"开卡"这个动作的时序接缝一次钉死（后面每一步都踩在这条链上）：**①产物此刻躺在哪**——
agent 库 `approvals` 表一行 pending 卡（TERMS"审批卡"条：L2 高危动作的"待批条"，
卡是唯一真相）、`run_events` 表一帧 approval_required、M2 审计一行 create；**②等多久、
谁接手**——**没有人在等**：run 冻在 awaiting_approval，值班长不批就一直挂着（唯一会
再来碰它的是 4.7 的 TTL 扫描）；**③两边的触发关系**——审批页弹卡靠 SSE 听事件总线
（不轮询 run），值班长的批准也不"叫醒"这个 run，只是往 `run_jobs` 表塞一行 resume
诉求，由分发循环领走（4.4/4.5 接力）。挂起的世界里没有回调，只有表。

对照来源 A：case_000002 的调查报告建议在案卷里躺了好几天，M2 审计簿里它对应的
审批卡行数是 **0**。同一个"隔离 app-01"的念头，从对话来是 pending 卡，从报告来只是
文字——这就是"L2 建议从哪来"的完整答案。

## 三、服务与中间件卡

### 卡 1（自研）· 意图分类器：fake 关键词规则与真 LLM 同一枚 seam

- **它是什么**：chat 子图的 `ChatLlm` 接口（classify/answer 两个方法）。AGENT_LLM=fake
  时是本步读到的关键词规则件，=real 时换成 RealChatLlm（minimax-m2 经 gateway 凭证
  代理，1.5 讲过的出站链路）——路由换件不换接口，五站子图代码一行不动。
- **本项目怎么配置**：`AGENT_LLM` 环境变量一个开关（run-kinds.ts 组图时选件）。
- **市面上同类**：专用 NLU 平台（Rasa、Dialogflow——意图+实体训练那套）；LLM 时代的
  function calling / tool use（模型直接吐结构化 tool call）。
- **本项目为什么选"分类器只产意图"**：不管 fake 还是真模型，分类器的输出被压成最小的
  `{"tool","confidence"}`，**参数走 deriveParams 确定性通道**——模型想编参数都没有口子。
  这比 function calling 直接吐全参保守得多：聊天面是攻击者能自由输入的面（场景 5.2
  主场），能少给模型一个自由度就少给一个。
- **业务上怎么选**：意图少且固定（就十几个工具）→ 关键词规则/小分类模型就够，还确定
  可测；意图开放、说法千奇百怪 → 真 LLM 分类，但输出面照本系统这样收窄到"提名+置信度"。

### 卡 2（领域）· mockAction：响应动作的"演习弹"

- **它是什么**：chat 执行体里那个 `mockAction` 工厂（flow.ts:115-123）——isolate_host
  返回 `{mock_edr:"isolated", host}`，block_ip 返回 `{mock_fw:"blocked"}`。审批链上的
  验票、焚毁、审计全是真的，唯独对外的"枪响"是假的。PRD §11 定的口径：响应动作一律
  mock，不对接真实 EDR/防火墙。
- **为什么要 mock**：教学环境不能真把你的电脑断网。但注意 mock 的位置——在**验票闸
  之后**（`ctx.executeApproved` 的最后一个参数，闸放行了才轮到它）。所以"演习弹"不影响
  "枪栓流程"的教学价值：从意图到执行的全部安全机制照常运转。
- **市面上同类**：SOAR 平台的 responder/connecter 生态（TheHive 的 Cortex responder、
  Splunk SOAR 的 playbook action）——真件要对接 EDR（CrowdStrike/EDR 的 host isolate
  API）、防火墙、邮件网关，每个动作一个集成器。
- **业务上怎么选**：接真实响应动作前先问三件事——动作**可逆吗**（隔离能解除，删文件
  不行）、**误触发代价多大**（生产库隔离=业务停摆）、**审计能不能还原现场**。代价高的
  动作就该像本系统一样：L2、人审、一次性票、mock 先行演练。

**B · 含糊其辞（低置信不猜）**：
