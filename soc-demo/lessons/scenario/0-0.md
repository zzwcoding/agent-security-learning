## 1. 编制表：9 个容器各演什么角色

一句话总纲：**自研件演"人"，官方件演"柜"**。人事关系（TERMS「人与窗口」节）：报案单由演示员（`scripts/replay.ts`，TERMS「演示员」条）推进前台，档案全归档案室，数字员工自己一滴权限没有、出站全靠保安处发手令。

| 容器（技术栈 · 宿主端口） | 它演什么角色（TERMS 比喻 + 代码名） | 一句话职责 |
|---|---|---|
| ingest（Fastify·TS · :3001） | 前台/收案窗口（TERMS「前台/收案窗口」条） | 收 Wazuh 格式告警：验型 422、severity 映射、不可信标记都在门口做，脏数据不进屋 |

## 2. 常驻循环表：3 个不睡觉的人

系统里没有"消息中间件在推"，只有 3 个轮询循环在盯表（术语：TERMS「排队与拉起」节）。**周期与表名全部 grep 自源码**，附行号：

| 谁（比喻 + 代码名） | 盯哪张表/哪条流 | 周期（实测） | 接到活后干什么 |
|---|---|---|---|
| 看板的（autorun 循环，TERMS「看板的」条） | 档案室的叫号屏：M2 库 `outbox_events` 表（经 REST `GET /api/v1/events?after` 读，autorun.ts:50-58）；自己读到第几号记在 agent 库 `event_cursors` 表（autorun.ts:25,69-84） | **2s**（autorun.ts:234 缺省 `?? 2000`；生产装配 index.ts:159 不传 intervalMs，吃缺省） | 逐事件裁决（autorun.ts:160-203）：`alert.created` → 拉起 alert_flow，`case.closed` → 拉起 knowledge_flow；拉起 = 打自家正门 `POST /internal/runs`（index.ts:154）。防重两道闸：查 agent `runs` 表（autorun.ts:110-115）+ 查 M2 kb 提案账面（autorun.ts:120-133）。**拉起失败游标不动、下轮重看**（autorun.ts:213-217，at-least-once） |
| 派活的（run-dispatcher 循环，TERMS「派活的」条） | agent 库 `run_jobs` 表（事务内 `pending→claimed` 防双吃，run-dispatcher.ts:85-98）；每轮还顺带扫审批卡保质期（`approvals` 表里过期 pending 卡，run-dispatcher.ts:205-216） | **100ms**（app.ts:48 `DISPATCH_INTERVAL_MS = 100`，生产装配经 buildApp 传入 app.ts:607） | 每轮两件事（run-dispatcher.ts:197-234）：①过期的审批卡判 expired、run 判 failed(approval_expired)——时间出的裁决也是裁决；②领 start/resume 任务执行（app.ts:599-603）：start = 铸手令→组图→开跑，resume = 从审批挂起处续跑。任务抛错完结不重试（毒丸不崩循环，run-dispatcher.ts:100-103） |
| 取餐铃（SSE 推送，TERMS「取餐铃（SSE）」条） | agent 库 `run_events` 表（按 `run_id AND id > 游标` 查增量，app.ts:570 → events.ts:64-67） | **100ms/每个订阅者**（app.ts:49 `SSE_PUSH_INTERVAL_MS = 100`，setInterval 在 app.ts:584；不是全局一个循环，是每条 SSE 连接各挂一个） | 把事件增量按 SSE 帧推给浏览器；断线重连按 `Last-Event-ID` 先补发再续播（app.ts:556-559）；run 到终态、写完最后一批即收流（app.ts:575-581） |

### 时序接缝：谁等谁、最多等多久（七原则第 2 条）

- **告警链的接缝**：告警落档案室时，`alert.created` 事件同事务写上叫号屏（store.ts:217/270 → store.ts:135-137）；看板的**最多 2 秒后**的下一个 tick 看到它；派活的**最多 100ms 后**的下一个 tick 领走 run。两段轮询之间没有暗号，只靠表。
- **run 拉起的接缝**：`POST /internal/runs` 落 `run_jobs` 表即回 202 秒回（app.ts:314-315）。**202 是给调用方的回执，派活的不知道有 202**——它只认 run_jobs 表（TERMS「派活的」条的常见误读）。反例：同步时代的旧形态真的是"202 前把活干完"（run-dispatcher.ts:3-5 文件头原文记着），结果 HTTP 客户端要替员工背整个执行期，连接一断执行就悬空——这正是票 47 翻转时序的原因。
- **为什么节奏不一样**：autorun 干的是"看见新告警拉起流水线"，2 秒粒度对演示足够、还给防重查询留了余量；分发与 SSE 干的是"执行与直播"，100ms 在演示里就是"实时"（app.ts:46-47 注释原话口径）。若 autorun 失败也推游标，事件就真丢了——所以它定死"失败不动游标、跳过才推"（TERMS「游标/水位线」条）。

### 3.2 一张票：铸造 → 亮票验票 → 焚毁入坟场（以 L2 一次性密令为例）

票是多层概念，先按七原则第 7 条打招呼：**票一共四层——①凭证层（为什么要有票：员工零权限）②签名层（HMAC，密钥只有保安处有）③时效层（TTL）④权限层（票面写清能动哪个工具）**。0-0 只画生命线（第①层的事）；②③④层的完整拆解在 TERMS「手令/任务票」条的分层栏，场景 4（4.4 铸造 / 4.5 验票六拒因 / 4.6 焚毁）逐步讲全。

```
[审批卡] approvals 表 pending 一张（TERMS「审批卡」条：L2 高危动作的待批条）
   │  值班长点批准 POST /api/v1/approvals/:id/approve     app.ts:429
   ▼  保安处铸造（TTL 300s）                              app.ts:445 → gateway/app.py:24、mint.py:70
╔─ 身份 1：一次性密令 ApprovalToken（HMAC 三段票）───────╗
║  一动作一铸；批准≠执行（批完先秒回）                    ║  mint.py:25（300s）；秒回 app.ts:456
╚═══════════════════════════════════════════════════════╝
   │  resume 诉求落 run_jobs → 派活的领走（≤100ms）        run-dispatcher.ts:61-74
   ▼  闸前亮票验票（唯一动作入口，TERMS「闸体/闸」条）      gated-call.ts:74 verifyTicket
      （跨进程重放还先查坟场）                             graph.ts:261 usedReader.lookup
╔─ 身份 2：验过票的授权 → 真的去执行那个 L2 动作 ─────────╗
╚═══════════════════════════════════════════════════════╝
   │  用后即焚                                            graph.ts:324 → token-ports.ts:143
   ▼  POST :3002/internal/used-tokens                     case-backend/src/app.ts:323 → store.ts:920
╔─ 身份 3：坟场 used_tokens 表里的一行案底 ──────────────╗
║  重放必 403 token_used（读口 app.ts:331/:973）         ║  TERMS「焚毁/坟场」条（INV-2）
╚═══════════════════════════════════════════════════════╝
```

别把两种票混成一种（TERMS 各一条）：L1 **手令/任务票**（Ticket，TTL 900s，mint.py:24）是干活的工牌，铸于拉起（app.ts:253-255 注释口径；票 47 后铸票随任务进分发循环 app.ts:310-312），**900s 过期即失效、不进坟场**；L2 **一次性密令**（ApprovalToken，TTL 300s）才有人审、才有焚毁仪式。反例：若任务票也进坟场，坟场会被海量工牌灌满，真正该盯的重放信号反而被淹——两张票两套账是有意设计。

定死一条分工口径：**大图是事后索引，不是入门教材**。它把调用链压成节点和连线，密度高、零叙述——没读过 0-0 和正文的人直接看图，只会看到一堆名字；读过的人用图 10 秒定位。所以不要试图把大图加密到能当教材（密度灾难），也不要求 0-0 详尽到能替图（两者各有各的活：0-0 管"懂"，大图管"找"）。
