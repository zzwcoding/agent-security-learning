# 场景 3 · 步 3.1 —— 关案触发：case.closed 怎么自动拉起知识沉淀（ASP 门控、LLM 草稿）

> 场景 1 里告警自己走进来被分诊建案，场景 2 里案子被查透、指标被体检。现在案子到了生命周期的
> 终点：**关案**。但关案不是"结束"，是"沉淀"的开始——一个 SOC 干了三年最值钱的不是某个案子
> 结了，而是"**下次再遇到这种案子，新人能不能直接抄作业**"。这一步回答三个问题：
> ① 案子一关，系统怎么"自己知道"该去提炼知识了？（事件桥：不用消息队列的订阅）
> ② 为什么提炼**只信人给的 verdict**，AI 自己说的不算？（ASP 门控）
> ③ LLM 草稿怎么产出、怎么把关？——草稿产出后**停在一张审批卡上**，批准/驳回留到 3.3。

---

## 一、操作（位置感）

先说清楚一个容易搞混的区别：系统里有**两种"关"**——

| 动作 | 关的是什么 | 入口 | 触发什么 |
|---|---|---|---|
| 一键确认关单（票 39） | **告警**（alert） | web 告警页按钮 → `close_flow` run | `close_alert` 工具落库，**不发事件** |
| 关案（本步主角） | **案件**（case） | 只有 REST：`POST /api/v1/cases/:id/close` | 状态转 Closed + **发 `case.closed` 事件** |

web 告警页那个"确认关单"按钮走的是 close_flow（场景 4 会作为审批之旅的一站细讲），它
**只关告警**；而知识沉淀的扳机挂在**案件**关案上——只有 M2 的关案口会往事件小票夹里塞
`case.closed`。所以本步我们用 curl 直接操作案件。

本步布景（承接场景 2）：栈全绿，4 个案件**全部停在 New 状态、verdict 全空**，知识账面
（kb/proposals）和检索面（chroma）都是空的。主角是 **case_000004**——centos7 的 SSH 爆破案
（场景 1 主角告警建的案）。

剧本：SOC1 复核后认定，centos7 上那波 SSH 失败登录其实是**授权红队演练**（登记号
DX-2026-09），所以案件该以 `benign_true_positive`（良性真实事件：事是真的，但人是自己人）
关案。关案之后三件事会**自动**发生：

1. agent 日志 2 秒内出现 `autorun_launched`——事件桥把沉淀子图拉起来了；
2. M2 知识账面多出一条 `proposed` 草稿（`env_fact` 环境事实）；
3. run 停在 `awaiting_approval`——草稿卡在一张审批卡上等值班长裁决，**检索面纹丝不动**。

## 二、调用链

先看全景。从值班长按下关案到草稿停在审批卡上，全程八站：

```
值班长 soc1
  │  PATCH /api/v1/cases/case_000004  {"status":"InProgress"}   ← 状态机：New 只能去 InProgress
  │  POST  /api/v1/cases/case_000004/close {"verdict":..., "verdictNote":...}
  ▼
[站1] M2 关案口 —— 两道闸（verdict 必填 → 状态机仲裁）→ 改账 + 审计
  │     同一个事务里 emitEvent("case.closed") 落 outbox events 表（本步实测 id=16）
  ▼
[站2] agent 事件桥（autorun 常驻循环）—— 每 2 秒问 M2："15 号之后有新事件吗？"
  │     GET /api/v1/events?after=15  →  拿到 id=16 的 case.closed
  ▼
[站3] 单事件裁决 —— 三道防重：dup_batch / run_exists / kb_exists，全跳过则不拉
  ▼
[站4] 拉起 = 打自己家的正门 —— app.inject POST /internal/runs（与手动触发同轨道）
  │     intake="case" → 必须带 case_id；注册表票面铸任务票（出生即绑 case_000004）
  ▼
[站5] knowledge_distill —— get_case 过闸读案 → ASP 门控（无 verdict 即跳过）
  │     → 不可信段 wrapUntrusted 包装 → 拼 prompt → LLM 提炼 → parseDraft 把关
  │     → kb_propose 过闸，M2 建 proposed 草稿
  ▼
[站6] kb_write —— L2 唯一正门：开审批卡 interrupt，run 挂起 awaiting_approval
  │     （值班长在卡上能看到草稿全文——这就是 D8 人审入库闸；3.3 细讲）
  ▼
[站7] 账面 vs 检索面 —— M2 kb_entries 有 proposed 草稿；
        chroma kb_entries 记录数 = 0（proposed 物理不进检索面，INV-5）
```

### 站 1 · 关案口：两道闸 + 一张事件小票

关案口在 M2（case-backend）。先看它头顶那句注释——"ASP「无判定不许关案」"：

📄 [services/case-backend/src/store.ts:496-522](soc-demo/services/case-backend/src/store.ts#L496)

```ts
// 三结局之三：关案。verdict 必填（ASP「无判定不许关案」，FR-M2.2）。
export function closeCase(
  db: DB,
  caseId: string,
  body: { verdict?: string | null; verdictNote?: string },
  ctx: Ctx,
): Record<string, unknown> {
  return db.transaction(() => {
    const kase = requireCase(db, caseId);
    if (!body.verdict || !(VERDICTS as readonly string[]).includes(body.verdict)) {
      throw new VerdictRequiredError();
    }
    assertTransition("case", kase.status as string, "Closed");
    db.prepare(
      "UPDATE cases SET status = 'Closed', verdict = ?, verdict_note = ?, end_date = ? WHERE id = ?",
    ).run(body.verdict, body.verdictNote ?? null, nowMs(), caseId);
    recordAudit(db, ctx, "update", caseId, "case", {
      status: { from: kase.status, to: "Closed" },
      verdict: { from: kase.verdict, to: body.verdict },
    });
    // 票 17（PRD 图 case_closed → knowledge_distill）：关案事件的 outbox 出口——
    // 沉淀子图的触发信号。当前触发形态与 alert_flow 同款由调用方 POST /internal/runs
    // （票 13 先例），事件先进 outbox 供下游/演示观察。
    emitEvent(db, "case.closed", { caseId, verdict: body.verdict });
    return getCase(db, caseId) as Record<string, unknown>;
  })();
}
```

这三十行里藏着三个安全设计，逐个说：

**第一道闸：verdict 必填，且必须是四个枚举值之一。** 没给 verdict、给了"自由发挥"的值
（比如 `"我感觉没问题"`），都会被 `VerdictRequiredError` 挡下。注意检查顺序——**先查
verdict、再查状态机**：一个既没 verdict 又停在 New 的案子来关案，报的是 `verdict_required`
而不是状态错误（本步捣乱实验 A/B 会实测这个顺序）。

**第二道闸：状态机仲裁。** `assertTransition` 查的是这张流转表——它是全系统状态机的
唯一事实来源：

📄 [services/case-backend/src/statemachine.ts:10-21](soc-demo/services/case-backend/src/statemachine.ts#L10)

```ts
  case: {
    New: ["InProgress"],
    InProgress: ["Closed"],
    Closed: [],
  },
  // 票 17（INV-5）：知识条目 proposed → approved/rejected，人审是唯一迁移口；
  // 终态不可再迁移——表外变更一律 409（INV-10）
  kbentry: {
    proposed: ["approved", "rejected"],
    approved: [],
    rejected: [],
  },
```

两个重点：**案件 `Closed: []`——关了就打死了，没有重开**（对比告警 `Closed: ["InProgress"]`
可以重开：案子是结论，结论不发悔改卡；告警只是线索，看走眼了可以捡回来）。另外下半张表
`kbentry` 就是本步主角知识条目的状态机，先混个脸熟：proposed 是草稿，人审后二选一进终态。

**第三件事：事件小票和账本同生共死。** `emitEvent("case.closed", …)` 写在 `db.transaction`
**里面**——关案改账和塞事件小票是同一个 SQLite 事务，要么都成要么都不成。不存在"案子关了
但小票忘塞了"的中间态。这张小票长什么样？本步实测：

```json
{ "id": 16, "topic": "case.closed",
  "payload": { "caseId": "case_000004", "verdict": "benign_true_positive" } }
```

顺带把两道闸的报错码记一下（`VerdictRequiredError` 的 httpStatus **刻意定成 409** 而不是
400——设计者把"违反业务规则"一律归为冲突，`store.ts:23-30`）：

| 捣乱方式 | 报错码 | HTTP |
|---|---|---|
| 不带 verdict | `verdict_required` | 409 |
| 带了 verdict 但状态是 New | `InvalidTransition` | 409 |

### 站 2 · 事件桥：不用消息队列的"穷人版订阅"

小票塞进了 M2 的 `events` 表，可谁来看这张小票？——agent 进程里有个常驻循环，名叫
autorun。它的自我介绍写在文件头：

📄 [services/agent/src/autorun.ts:1-9](soc-demo/services/agent/src/autorun.ts#L1)

```ts
// m3 内部模块 autorun（票 40·G2-9 清偿）：事件驱动自动拉起——M2 outbox 的消费循环。
//
// 线头（checkup G2-9）：alert.created 进了 outbox 没人消费（票 09 起只有生产端）、
// case.closed 同样悬空（票 17 补的 emit）。PRD 消息旅程 step4/step11 与 m3 卡接口契约
// 写的「内部触发：M2 alert.created 事件 → POST /internal/runs」在本票接通：agent 进程内

//   alert.created → alert_flow（分诊，TP 后同 run 链调查富化，票 36）
//   case.closed   → knowledge_flow（提炼，kb_propose → 人审闸，票 17）
// close_flow 不挂自动：SOC1 手动确认是票 39 的语义（AI 出主意，人按按钮）。
```

看到没——场景 1 里"告警进来分诊自动跑"和本步"案子关了沉淀自动跑"，**是同一个循环干的**。
它在干嘛？三个零件：一只眼睛（读事件）、一个书签（游标）、两条腿（拉起）。

**眼睛**——读事件就是个带分页的 GET：

📄 [services/agent/src/autorun.ts:50-58](soc-demo/services/agent/src/autorun.ts#L50)

```ts
  async eventsAfter(after: number, limit = BATCH_LIMIT): Promise<OutboxEvent[]> {
    const res = await fetch(
      `${this.baseUrl}/api/v1/events?after=${encodeURIComponent(after)}&limit=${encodeURIComponent(limit)}`,
      { signal: AbortSignal.timeout(5000) },
    );
    if (!res.ok) throw new Error(`outbox events read failed: HTTP ${res.status}`);
    const json = (await res.json()) as { events?: OutboxEvent[] };
    return json.events ?? [];
  }
```

**书签**——消费到哪条了，记在 agent 自己的 SQLite 里（`event_cursors` 表，一行叫
`m2_outbox` 的水位线）。本步实测，主循环跑完后：

```
sqlite> SELECT * FROM event_cursors;
m2_outbox|16        ← 16 号小票已消费，重启不会重放
```

**循环本体**——立即跑第一轮，之后每 2 秒一轮，串行不重叠：

📄 [services/agent/src/autorun.ts:233-253](soc-demo/services/agent/src/autorun.ts#L233)

```ts
export function startAutorun(deps: AutorunDeps, opts: { intervalMs?: number } = {}): { stop(): void } {
  const intervalMs = opts.intervalMs ?? 2000;
  let stopped = false;
  let timer: ReturnType<typeof setTimeout> | null = null;
  const tick = async (): Promise<void> => {
    if (stopped) return;
    try {
      await pollAutorunOnce(deps);
    } catch (err) {
      deps.log?.({ warn: "autorun_poll_failed", error: String(err) });
    }
    if (!stopped) timer = setTimeout(() => void tick(), intervalMs);
  };
  void tick();
  return {
    stop(): void {
      stopped = true;
      if (timer) clearTimeout(timer);
    },
  };
}
```

**两条腿**——"拉起"怎么拉？这里有个本步最优雅的设计：autorun 不自己铸票不自己组图，
它**把事件折成一次对自家正门的 POST**。生产装配在 index.ts：

📄 [services/agent/src/index.ts:148-158](soc-demo/services/agent/src/index.ts#L148)

```ts
    const launch: Parameters<typeof startAutorun>[0]["launch"] = async (req) => {
      // 拉起 payload 的实体字段按注册表 intake 定（票 44）：alert = alert_id，case = case_id
      // ——原来「kind === alert_flow 特判」的手抄口径收敛进注册表一格。
      const payload = runKindOf(req.kind)?.intake === "alert"
        ? { kind: req.kind, alert_id: req.alertId }
        : { kind: req.kind, case_id: req.caseId };
      const res = await app.inject({ method: "POST", url: "/internal/runs", payload });
      if (res.statusCode >= 300) {
        throw new Error(`internal/runs HTTP ${res.statusCode} ${res.body}`);
      }
    };
```

`app.inject` 是 Fastify 的"自己给自己发请求"——不走网络，直接进程内调自家路由。好处：
**自动触发和你在终端敲 curl 走的是同一条轨道**（正门校验→铸票→组图→执行→审计），不给
自动化开任何旁路。场景 1 的 1.3 讲过"正门只有一个"——事件桥也得排队走正门。

最后补一句开关：这个循环受环境变量 `EVENT_DRIVEN` 控制，缺省 on，设 off 就关（手动
POST 和 evals 不受影响，[autorun.ts:257-259](soc-demo/services/agent/src/autorun.ts#L257)）。

### 站 3 · 单事件裁决：三道防重

拿到 16 号小票，先裁决要不要动。`case.closed` 分支的完整逻辑：

📄 [services/agent/src/autorun.ts:182-201](soc-demo/services/agent/src/autorun.ts#L182)

```ts
  if (e.topic === "case.closed") {
    const caseId = typeof e.payload.caseId === "string" ? e.payload.caseId : "";
    if (!caseId) return { action: "skipped", skip: { topic: e.topic, refId: "", reason: "malformed_payload" } };
    const seen = batchSeen.get("knowledge_flow") ?? new Set<string>();
    if (seen.has(caseId)) return { action: "skipped", skip: { topic: e.topic, refId: caseId, reason: "dup_batch" } };
    if (deps.hasActiveRun("knowledge_flow", caseId)) {
      return { action: "skipped", skip: { topic: e.topic, refId: caseId, reason: "run_exists" } };
    }
    try {
      if (await deps.hasKbEntryForCase(caseId)) {
        return { action: "skipped", skip: { topic: e.topic, refId: caseId, reason: "kb_exists" } };
      }
      await deps.launch({ kind: "knowledge_flow", caseId });
    } catch (err) {
      return { action: "failed", error: String(err) };
    }
    seen.add(caseId);
    batchSeen.set("knowledge_flow", seen);
    return { action: "launched", kind: "knowledge_flow", refId: caseId };
  }
```

三道防重，从轻到重：

1. **dup_batch**（批次内查重）：同一批事件里同一案子出现两次，只拉第一次。什么时候会
   发生？游标丢失重放的时候——同一张小票被读两遍。
2. **run_exists**（agent 侧查 runs 表）：这个案子已有非 failed 的 knowledge_flow run 就不再拉
   （[autorun.ts:110-115](soc-demo/services/agent/src/autorun.ts#L110)，failed 不挡=允许重试）。
3. **kb_exists**（M2 侧查知识账面）：这个案子已有 proposed/approved 提案也不再拉
   （[autorun.ts:120-133](soc-demo/services/agent/src/autorun.ts#L120)，全量拉回来按
   source_case_id 过滤——端点没有按案子过滤的参数，演示规模全量拉最省事）。

还有一个隐蔽但关键的口径，写在裁决函数头上：

> 跳过（含坏事件、防重命中）都推进游标——它们是「想清楚了不动作」；只有失败不动游标
> （下轮重试）。

（[autorun.ts:158-159](soc-demo/services/agent/src/autorun.ts#L158)）翻译成大白话：**"不做"
和"做不了"是两回事**——前者盖章通过往下走，后者原地把书签按住，下轮再来。配合三道防重，
就算书签丢了整批重放，也不会拉起重复的沉淀 run（at-least-once 投递 + 幂等消费 = 效果上的
exactly-once）。

### 站 5 · knowledge_distill：提炼四步（读案 → 门控 → 提炼 → 提案）

整个节点就是四步，都在 [flow.ts:89-177](soc-demo/services/agent/workers/knowledge/flow.ts#L89)。
第一步，读案——和所有工具调用一样，亮票过闸：

第二步，**ASP 门控**——本步的题眼。ASP = Agent System Prompt 的规范要求："AI 的结论不能
当作事实沉淀，只有人给的判定才可以"。代码里的长相：

📄 [services/agent/workers/knowledge/flow.ts:97-108](soc-demo/services/agent/workers/knowledge/flow.ts#L97)

```ts
            action: "knowledge_skip",
```

细品这条防线的**纵深**：关案口已经要求 verdict 必填了（站 1），为什么这里还要再查一遍？
因为**拉起口不查关案状态**——任何人都能 `POST /internal/runs {"kind":"knowledge_flow",

## 三、服务与中间件卡

### 卡 1（自研）· outbox + 游标轮询：穷人版消息订阅

- **它是什么**：M2 的 `events` 表当"发件箱"（业务事务内塞小票），agent 用 2 秒一轮的
  GET + 自己库里的游标水位线当"收件"。
- **市面替代**：Kafka / RabbitMQ / Redis Stream——专职消息中间件，推模式、多消费者、
  消息路由、重试死信一应俱全。
- **为何选它**：① **不丢事件**是小票和账本同事务写死的（站 1），MQ 方案里"业务落库"和
  "发消息"是两个系统，照样要做本地消息表——不如直接用表；② demo 规模一个消费者两个
  topic，MQ 的收益全用不上，成本（多一个组件、多一份运维）倒是全要付；③ 游标在
  SQLite 里，重启不丢、可观测（一句 SELECT 看水位）。
- **业务上怎么选**：消费者 >2 个、需要广播、事件量上每秒千条——上 MQ；单一消费者、
  事件是业务事务的附属品、想省一个组件——outbox+轮询就是正解。真 SOC 里事件总线
  （Kafka）是标配，但那是"量"的问题不是"对错"的问题。

### 卡 2（开源）· chroma：知识检索面的本体（首秀）

- **它是什么**：开源向量数据库（官方容器镜像），存文本的"语义坐标"（embedding 向量），
  支持按相似度检索。本系统用它当知识库的**检索面**——分诊时查"这个主机/路径有没有
  既往知识"。
- **本项目怎么用**：compose 起官方镜像（宿主口 **18000**，8000 高频被占）；agent 侧
  `RealChromaClient` 只说它的 REST API v2，**不引官方 npm client**（把 server 版本锁进
  lockfile，出站形态用契约测试锁死）；embedding 注入可选——默认 `hashEmbedding`
  （本地确定性哈希向量，离线零依赖），`KB_EMBEDDING=chroma_default` 切服务端模型
  （需出网下载 80MB，[vector-store.ts:12-16](soc-demo/services/agent/workers/knowledge/vector-store.ts#L12)）。
- **市面替代**：pgvector（Postgres 插件，账面检索面一体）、qdrant、weaviate、FAISS（库
  不是服务）。
- **为何选它**：官方容器 + HTTP 就能说话，demo 依赖最小；账面（SQLite）和检索面（chroma）
  **刻意分家**——账面给人审流程看，检索面给分诊机器查，两套读写权限、两种生命周期，
  INV-5 正是靠这个分家才做到结构性成立。
- **业务上怎么选**：已经在用 PG 且检索规模小——pgvector 少一个组件；独立知识库、要
  多路召回/元数据过滤——chroma/qdrant 这类专职向量库。
- 本步它只露了半张脸（count=0），3.4 检索面才是它的主场。

## 四、防线对号

| 防线 | 在本步的落点 |
|---|---|
| **ASP 门控**（FR-M7.1 + FR-M2.2） | 双保险：关案口 verdict 必填 409（第一道）+ worker 内 `!detail.verdict` 防御再拦 skip（捣乱 C 实证）。AI 的结论不配沉淀，只有人给的 verdict 配 |
| **INV-3**（任务票物理无 L2） | 知识票 `allowed_tools = [get_case, kb_propose]`——写检索面的 kb_write 连票面都进不去 |
| **INV-5**（人审是入库唯一通道） | 检索面唯一写入路径在 kb_write 已验签执行体里；proposed 时 chroma count=0（本步实测） |
| **INV-10**（状态机表外变更 409） | kbentry 状态机 `proposed → approved/rejected`，终态不可再迁移（3.3 会打 409） |
| **D8 / FR-M7.5**（人审入库闸=投毒第一防线） | 审批卡 params 带**草稿全文** + params_hash 指纹——值班长批的是眼见为实的那一版 |
| **INV-6**（防重） | autorun 三道防重：dup_batch / run_exists / kb_exists，游标丢失重放也不重复沉淀 |
| **INV-8**（五要素审计） | 关案两条 update（含 verdict 变更）+ kb_entry create + knowledge_skip，全部进同一张 audit_entries |
| **FR-S3.1**（数据不是指令） | 案件描述/timeline 进 prompt 前 wrapUntrusted 包装；verdict/verdict_note 走可信区 |

**一个诚实备注**（教学点，非 bug）：本步 M2 审计里 kb_entry create 的 actor 显示
`system`——因为 `HttpKnowledgeM2` 的 REST 调用没转发 `x-actor-id` 头，M2 按"无头=系统"
口径记（与 2.3 发现的"内网信任口薄"同款现象）。真实的执行体身份锚在三处：票面 sub
`agent:knowledge`、body 里的 `proposed_by`、以及 3.3 批准时 ApprovalToken 上的值班长身份
（INV-9 锚人）。内网口不验头、身份走 body 字段，是本系统反复出现的信任分层设计。

## 六、捣乱实验（必选）

**A · 不给 verdict 就想关案**（结果已在亲手验证 2）：`409 verdict_required`。注意你的案
子此刻还是 New 状态（同样非法），但报的是 verdict 错——**先查 verdict 后查状态机**，
第一道闸先响。

**B · 给了 verdict 但跳过 InProgress 直接关**：`409 InvalidTransition`。状态机不吃"跳级"——
案子的生命线必须是 New → InProgress → Closed 一站一站走。（对照：告警可以 Closed →
InProgress 重开，案子不行——结论不发悔改卡。）

**C · 对没关案的案子直拉沉淀子图**（拉起口不查关案状态，试试 worker 的防御再拦）：

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:3003/internal/runs \
  -H 'content-type: application/json' -d '{"kind":"knowledge_flow","case_id":"case_000002"}' -H 'x-actor-id: soc1'
# 预期：{"run_id":"run_93d5e558-…","status":"queued"} / HTTP 202   ← 正门照收，不查关案

sleep 3
sqlite3 "file:soc-demo/data/agent/agent.sqlite?mode=ro" \
  "SELECT id,status,steps,tokens_used FROM runs WHERE case_id='case_000002' AND kind='knowledge_flow';"
# 预期：run_93d5e558-…|completed|2|0   ← 正常跑完（不是失败！），steps=2 两节点都走完，tokens=0（LLM 没调）
```

再看它的脚 Audit 和账面：

```bash
sqlite3 "file:soc-demo/data/agent/agent.sqlite?mode=ro" \
  "SELECT type,json_extract(payload,'$.tool') FROM run_events WHERE run_id='run_93d5e558-d5ce-4eec-aa2a-3a0dfacad4ae' ORDER BY id;"
# 预期：只有 get_case 一站过闸，没有 kb_propose

sqlite3 "file:soc-demo/data/case-backend/case-backend.sqlite?mode=ro" \
  "SELECT action, json_extract(actor,'$.id'), details FROM audit_entries WHERE action='knowledge_skip' ORDER BY created_at DESC LIMIT 1;"

curl -s http://127.0.0.1:3002/api/v1/kb/proposals | python3 -c "import json,sys; print(len(json.load(sys.stdin)['proposals']))"

```

读法：run **completed 而不是 failed**——skip 是"想清楚了不动作"，是合法结局（对比捣乱 D
的 failed）。整个攻击被三层消化：拉起口 202 照收（宽进）→ worker 门控 skip（防御再拦）→
审计留痕 `no_verdict`（事后可查）。**零污染、零编造、有据可查。**
