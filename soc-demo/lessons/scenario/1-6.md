## 一、这一步做什么

一条告警从报案到落判，系统里留下了**三层记录**：档案室的库表（alerts/cases/audit）、
agent 的 run 行与事件（runs/run_events）、以及 web 页面上人看到的一切。前两层是
机器的账，第三层是人的窗。本步把三层**对上账**：事件流里的每一条都能在前五篇找到
出处；web 页上看到的每个数字都能追到库表的一行。

用一条**建案型 run** 做标本：`run_0e4cddbb-…`（fim-510 告警，db-01 主机，TP 建案，
41 条事件）——它比主角多了"建案成功 + 链上调查"两段，是全场景最完整的一生。

## 二、调用链

### 站 0 · 一条 run 的一生，41 条事件的分段地图

```
run_0e4cddbb-…（fim-510 → db-01，TP 建案）事件分段：
├── #1      audit   queued→running            ← 1.5 站 0：run 接管，审计镜像成事件
├── #2-13   前三节点                          ← 1.4：load_alert(亮票+抢锁)→
│                                             kb_lookup→search_cases_by_host
├── #14-16  self_audit_checkpoint             ← 1.5 站 0：建案前书面声明
├── #17-18  verdict_llm                       ← 1.5 站 2-4：判定（无 tool_call——
│                                             LLM 不是工具，不走票闸，走凭证代理）
├── #19-22  outcome：create_case              ← 1.5 站 5：亮票建案（db-01 无活跃案）
├── #23-40  investigate_case → enrich_case    ← 本站 1：同 run 链上调查+富化
│             （load_case → plan → tool_loop: siem_query/related_alerts/… → write_report）
└── #41     audit   running→completed         ← 落幕
```

对着 [1.4 亲手验证 ①](1-4.md) 的命令把 run_id 换成本条，这 41 行就是你亲手能
dump 出来的。**每一行都能指认出处**——这就是"学透"的样子：不是背下 41 行，
而是任何一行都知道它为什么存在。

### 站 1 · TP 之后：同 run 链上自动接调查

分诊判 TP 并落案后，**同一个 run 内**直接接上调查+富化链——这是 1.3 讲过的
注册表设计，📄 [services/agent/src/run-kinds.ts:156-171](soc-demo/services/agent/src/run-kinds.ts#L156)：

```ts
    // 分诊六节点 + 链上调查+富化（链上节点名见 case_flow 的 pipelineNodes）。只有 TP 的
    // create_case 分支会把 case_id 写进交接态——FP/merge 分支链空转跳过。
    makeGraph: (deps) => (run, ticket) => [
      ...makeTriageFlow({
        runId: run.id,
        requestId: `launch_${run.id}`,
        ticket,
        m2: new HttpTriageM2(),
        kb: deps.kb,
        llm: deps.llmMode === "fake"
          ? new FakeTriageLlm()
          : new RealTriageLlm(new GatewayLlmClient({ requestId: `launch_${run.id}`, actor: "agent:triage" })),
        audit: deps.audit,
      }),
      ...makeCaseChain(deps, run.id, ticket),
    ],
```

一张票（1.3 站 4 讲过：scope 是三族工具的**并集**）、一张图：分诊六节点在前，
调查+富化节点挂尾。分岔的机关藏在交接态里：只有 `create_case` 分支往
`ctx.state.case_id` 写了值（1.5 站 5），链上的 `investigate_case` 靠它知道"查哪个
案子"——主角告警是并案分支没写 case_id，所以它的链上两节点**空转**（1.4 亲手验证 ①
里你见过：investigate_case/enrich_case 进出但没有一次 tool_call）。建案型 run 就
不同了，#23 起真干活：

```
#23  node_enter investigate_case
#24  tool_call  load_case(get_alert)        —— 把案卷再领一遍（照样亮票）
#26  audit      plan: ["siem_query 按 db-01 pivot 查询（强制时间窗）","related_alerts 聚合…"]
#27  tool_call  tool_loop(siem_query)       —— 查 SIEM 语料（时间窗契约，1.4 的闸照咬）
#29  audit      tool_output_flagged         —— 工具的输出也要安检！防线管到出口
#30  tool_call  tool_loop(related_alerts)   —— 聚合同主机告警
…   …（报告写作 write_report → add_timeline_entry 落案件时间线）

```

调查子图干了什么、三条缰绳怎么防 AI 打转、报告怎么只提建议不动手——**场景 2 全篇
拆它**，这里只带你看清接口：分诊的落判是调查的入口，一个 run 一张票一串节点，
不换轨、不重开。

### 站 2 · SSE 事件流：run 的"直播 + 点播"

事件落在 `run_events` 表（1.4 的 dump 就是它），web 上看到的直播是 HTTP 长连接
推出来的。📄 [services/agent/src/app.ts:550-560](soc-demo/services/agent/src/app.ts#L550)：

```ts
  app.get("/api/v1/events/stream", (req, reply) => {
    const q = req.query as { run_id?: string; after?: string };
    if (!q.run_id) return reply.status(400).send({ error: "run_id_required" });
    const run = getRun(db, q.run_id);
    if (!run) return reply.status(404).send({ error: "not_found" });

    const h = req.headers["last-event-id"];
    const raw = (Array.isArray(h) ? h[0] : h) ?? q.after ?? "0";
    const last = Number(raw);
    let cursor = Number.isFinite(last) ? last : 0;
```

这就是 **SSE**（Server-Sent Events，下面卡 1）：连接挂住，后台每 100ms
（[app.ts:49](soc-demo/services/agent/src/app.ts#L49)）把 `cursor` 之后的新事件推
给浏览器，每条带自增 `id:`。关键的野蛮生长点在第四行——**断线重连时浏览器自动带
`Last-Event-ID` 头**（SSE 标准），服务端从那条之后**补发**。所以这条流是
"直播 + 点播"二合一：直播期间实时看，掉线的窟窿按 id 补齐——INV-7 的原话：
"每个事件恰好到达一次，不丢不重"。我在布景里实测过：拿
`Last-Event-ID: 38` 重连 41 事件的 run，服务器精确补出 `#39/#40/#41` 三条（你
亲手验证 ③ 自己做一遍）。

## 三、服务与中间件卡

**卡 1 · ▲SSE（Server-Sent Events）—— 单向直播的便宜方案**

- **替我们干了件什么体力活**：让浏览器页面上 run 的节点一个个"亮起来"。本质就是
  一个**不关门的 HTTP 响应**：服务端慢慢写、浏览器慢慢读，每条消息带个自增 id。
- **自研还是开源**：HTML5 标准（不是库，是浏览器原生能力），服务端就是普通 HTTP
  响应头 `text/event-stream` + 持续写行（[app.ts:561-566](soc-demo/services/agent/src/app.ts#L561)）。
- **本项目怎么配置**：Fastify `reply.hijack()` 接管原始响应（绕过框架的序列化），
  100ms 一次从 `run_events` 表增量读、增量推——没有独立的消息服务，账在库里、
  直播是库的视图。
- **市面上同类**：WebSocket（双向，重）、长轮询（兼容性好、浪费多）、普通轮询
  （最笨但最稳）。
- **本项目为什么选 SSE**：run 事件的推送是**纯单向**的（用户只看不发），SSE 用
  HTTP 就够；自带断线重连 + `Last-Event-ID` 语义，正好接住 INV-7 的"恰好一次"。
  WebSocket 的双向能力在这里是浪费。
- **业务上怎么选**：单向通知/进度/行情 → SSE；聊天/协同编辑等双向 → WebSocket；
  要穿过老代理/企业防火墙 → 轮询兜底。**通用原则**：推送通道再花哨，消息真相
  也要落库可回放（本项目的 run_events 就是）——通道会断，账不会。

**卡 2 · ▲Vite + React 19 + antd 5 —— web 的三件套**

- **替我们干了件什么体力活**：Vite 是前端开发的"热灶台"（改代码浏览器秒刷新），
  也是打包器（build 出静态文件）；React 管页面组件与状态；antd（蚂蚁的 Ant
  Design）是现成的中后台零件库——表格、表单、抽屉、标签，SOC 这种"看数据、
  点按钮"的界面正好是它的主场。
- **本项目怎么配置**：`services/web/` 一个 Vite 工程；antd 用 React 19 需要
  兼容 patch（package.json 里一条 patch 依赖，PRD 技术栈表 C7 点名 antd 5）。
  页面组件七个（站 3 的表），API 调用集中在 [services/web/src/api.ts](soc-demo/services/web/src/api.ts)。
- **市面上同类**：Vue3+Element Plus / Naive UI、Next.js+shadcn、Svelte；antd 的
  对手是 MUI、Element。
- **本项目为什么选 React+antd**：SOC 中后台 = 大量表格/表单/详情抽屉，antd 开箱
  即用且中文文档全；React 生态的测试链（本仓 pages.test.tsx）成熟。Vite 因为快、
  零配置够用。
- **业务上怎么选**：中后台/数据密集 → React/Vue + 组件库（antd/Element）；
  面向 C 端的品牌页 → 定制设计系统更划算；团队强 Vue 就 Vue+Element，**别为了
  组件库换框架**——组件库是给效率的，不是给信仰的。

## 四、防线对号

- **INV-7（事件恰好一次）**：站 2 全篇——id 自增落库、Last-Event-ID 补发、不丢
  不重。它让"直播"建立在"账本"上：SSE 断一百次，run_events 里的账分毫不差。
- **INV-8（审计是真相源）**：站 0 的地图里 `audit` 类型事件与状态迁移、工具调用
  一一成对——事件流是台账的广播（1.5 站 0 的原话），web 审计页读的就是真相源
  本尊（audit_entries）。
- **防线的出口延伸**：站 1 事件 #29 `tool_output_flagged`——不只输入要安检
  （1.5 站 1），**工具的输出**进上下文前也要过扫描仪。防线是全链路连续的，
  不是只守大门。

## 场景 1 闯关（三道场景题，先自己答，再对照文章验证）

**第 1 题**：同一条告警被探头连推三遍（1.2 干过），流水线为什么只会跑一次？
请说出**三道防线**各自的名字（库的、编排的、分诊台的）和它们分别防的是哪种
重复。
<details><summary>对照</summary>
库的：alerts 表 (source, source_ref) 唯一索引 + upsert occurrences+1（1-2 站 2/5）；
编排的：autorun `hasActiveRun` 查 runs 表非 failed 的同类 run 就跳过（1-3 站 2）；
分诊台的：verdict 拾取锁 `WHERE verdict IS NULL` 条件更新，抢不到就让路（1-4 站 2）。
三道分别拦"库里重复建档""同一告警重复拉起""并发两个 run 重复分诊"。</details>

**第 2 题**：攻击者伪造了一张任务票，内容写着"允许 merge_alert"，直接调 agent
的图执行并案——他会卡在哪一步？（提示：票据的防伪章是什么、密钥在谁手里、
闸拒了之后发生什么。）
<details><summary>对照</summary>
卡在 makeGatedCall 的 verifyTicket（1-4 站 3）：HMAC-SHA256 防伪章需要 SOC_HMAC_KEY，
密钥只活在 gateway（1-3 站 5），agent 都没有——伪造者更造不出正确签名；闸拒 =
审计 DENIED + 抛错 → run 强杀 failed（INV-1 fail-closed，不带病执行）。</details>

**第 3 题**：主角告警是 TP，但它没有新建案子，而是"并"进了别人的案子（状态
Imported）。是谁决定建案还是并案的？AI 在这个决定里扮演什么角色、被怎么核查？
<details><summary>对照</summary>
merge_check 节点先查"同主机 24h 活跃案"（1-4 站 5，机器查的事实）；outcome 节点
按 `state.merge` 分岔：有活跃案 → merge_alert，无 → create_case（1-5 站 5）。AI
只给判定和**建议动作**，且必须在 self_audit 里复述核查结果——与机器实际结果
矛盾就强制降 uncertain 交人工（1-5 站 4）。**决定权在确定性代码，AI 的发言
可对质**。</details>

答完把答案（或卡住的点）告诉主窗口——答错/卡壳的记进总纲学习日志，就是真缺口。
