# 场景 2 · 步 2.5 —— timeline 装配与 web 呈现（两种报告条目、字段透视）

> 场景 2 收官步。调查报告、富化报告写进了案件时间线——但「写进去」只是档案室的事，
> 值班长在 web 上看到的**一条时间线**是怎么装配出来的？本步拆两件事：**装配**（web
> 把两路数据源合成一条时间线的纯函数，以及它「不猜时间」的纪律）和**呈现**（两种
> 报告条目各自的标签、颜色、字段透视）。最后照例：亲手验证、捣乱实验、场景 2 闯关题。

## 一、操作（位置感）

打开 web（http://localhost:5173）→ 案件页 → 点开 case_000003。你看到的时间线从上到下：

- **系统**（灰点）：建案条目、关联告警记录；
- **调查报告**（蓝标 · agent:investigation）：markdown 排版的报告正文；
- **富化报告**（紫标 · agent:enrichment）：对账式报告，标题行右侧还挂着一串小标签
  `info / info / refused / malicious / info`——这就是「字段透视」：web 没有重新理解
  报告，它只是把 `structured` 里的评级序列变成了彩色小标签；
- 若案件有审批卡（场景 4 的主角），还会看到**金色**的审批行。

用肉眼核对一件事：富化报告正文「逐项结果」的五行的顺序，和标签序列
`info, info, refused, malicious, info` **一一对应**——第三行是 tlp=4 那条被拒发的
hash（refused），第四行是 tlp=2 放行查出 malicious 的同值 hash。前端没有撒谎的
自由，因为它只透传。

### 站 1 · M2 侧：一张表、一个排序、一次 JSON 还原

📄 [services/case-backend/src/store.ts:779-787](soc-demo/services/case-backend/src/store.ts#L779)

```ts
export function listTimeline(db: DB, caseId: string): unknown[] {
  return db
    .prepare("SELECT * FROM timeline_entries WHERE case_id = ? ORDER BY created_at, rowid")
    .all(caseId)
    .map((r) => {
      const row = r as Record<string, unknown>;
      return { ...row, structured: pj(row.structured as string, null) };
    });
}
```

三点：**只有一张表**——系统条目、调查报告、富化报告、（将来的）审批/执行记录全在
`timeline_entries`（场景 2 各步写的 kind 都见过实物了）；**排序双保险**
`ORDER BY created_at, rowid`——同一毫秒内按插入序，绝不出现「并列时抖动」；**structured
是 JSON 字符串存储、读出时还原**——机读真相整存整取，不经任何改写。

路由薄得像纸（[app.ts:186-187](soc-demo/services/case-backend/src/app.ts#L186)）：
`GET /api/v1/cases/:id/timeline` 直通 `listTimeline`——读口不做业务加工，加工是
消费者（web）自己的事。

### 站 2 · web 装配层：两路合流 + 不猜时间

web 的时间线来源有**两路**——这是本步最容易被忽略的设计。先读装配函数的头注释：

📄 [services/web/src/timeline.ts:1-10](soc-demo/services/web/src/timeline.ts#L1)

```ts
// 案件时间线装配（FR-M10.4 的纯函数层，React 之外可单测）。
//
// 「时间线」从哪来？两路公开数据，页面把它们合成一条：
// ① M2 timeline_entries（GET /api/v1/cases/:id 的 timeline 字段）——worker 们写的
//    系统条目/调查报告/富化报告（kind 是写入口透传的，读什么渲染什么）；
// ② agent 审批卡 REST（GET /api/v1/approvals）里 case_id 对得上的卡——审批与执行
//    条目不另立数据源：审批卡（INV-8 有全链审计）本来就是这些动作的事实来源。
// 原则：不猜时间。每行的 ts 都来自数据本身的 created_at/decided_at；执行的
// 「已执行」标记并进审批行文案（wire 只有 executed 布尔，没有执行时间戳，编一个
// 就是造假）。
```

📄 [services/web/src/timeline.ts:92-98](soc-demo/services/web/src/timeline.ts#L92)

```ts
/** 详情里的 timeline 条目 + 该案件的审批卡 → 按时间升序的一条时间线。 */
export function assembleTimeline(d: CaseDetail, approvals: ApprovalCard[]): TimelineRow[] {
  const fromTimeline = (d.timeline ?? []).map(entryRow);
  const fromApprovals = approvals
    .filter((c) => c.caseId === d.id)
    .flatMap(approvalRows);
  return [...fromTimeline, ...fromApprovals].sort((a, b) => a.ts - b.ts);
}
```

两个值得抄走的工程判断：

1. **审批不另立「时间线数据源」**。审批卡本来就有完整的状态与审计（INV-8），web
   把它**投影**进时间线视图——数据只有一个事实源，视图可以多副面孔。反过来做
   （审批时往 timeline_entries 里再写一条冗余记录）就要面对两边不同步的永恒噩梦。
2. **不猜时间**。每行的时间戳必须来自数据本身；wire 上没有的时间（比如执行时刻）
   宁可并进文案（「已执行（一次性 token 用后即焚）」）也不编一个数。「编一个就是
   造假」——这句注释值得贴在所有 dashboard 工程的墙上。

装配是**纯函数**（React 之外可单测）——`services/web` 的 `timeline.test.ts` 四个
用例测的就是它（两路合流、排序、审批行文案），本步亲手验证 ③ 会带你跑。

### 站 3 · 两种报告条目的「字段透视」

先看 kind → 标签/颜色的翻译表：

📄 [services/web/src/timeline.ts:26-36](soc-demo/services/web/src/timeline.ts#L26)

```ts
const KIND_META: Record<string, { label: string; color: string }> = {
  system: { label: "系统", color: "default" },
  investigation_report: { label: "调查报告", color: "blue" },
  enrichment_report: { label: "富化报告", color: "purple" },
  approval: { label: "审批", color: "gold" },

  // 没见过的 kind 不瞎翻译：原样当标签（worker 写什么透传什么）
  return KIND_META[kind] ?? { label: kind, color: "default" };
}
```

「没见过的 kind 不瞎翻译」——还记得 2.3 捣乱 B 吗？M2 写口不校验 kind，所以 `bogus_kind`
真的存进去了；web 的应对不是崩，也不是猜，而是**原样透传**当标签显示。全链路的
宽容性设计在最后一环闭环：闸管写、存储老实存、视图老实显示、人来做判断。

富化条目独有的**字段透视**——从 structured 里抽出评级序列：

📄 [services/web/src/timeline.ts:38-49](soc-demo/services/web/src/timeline.ts#L38)

```ts
/** 富化 structured（enrichment/report.ts ReportInput）→ 四档标签序列。
 *  没外发的行给 refused——「为什么只有 N 项有评级」的对账。 */
function levelsOf(structured: unknown): string[] | undefined {
  const results = (structured as { results?: { ok?: boolean; level?: string }[] } | null)
    ?.results;
  if (!Array.isArray(results)) return undefined;
  return results.map((r) => (r.ok ? (r.level ?? "info") : "refused"));
}

function entryRow(e: TimelineEntry): TimelineRow {
  const meta = metaOf(e.kind);
  const levels = e.kind === "enrichment_report" ? levelsOf(e.structured) : undefined;
```

用 case_000003 的真数据走一遍（亲手验证 ① 会复算）：富化报告 structured 的
`results` 依次是 `ok+info / ok+info / 拒发 / ok+malicious / ok+info`，levelsOf 输出
`["info","info","refused","malicious","info"]`——**逐行对应报告正文的五行**。注意
「拒发行给 refused 标签」：被 TLP 闸门拦下的 IOC 在 web 上不消失、不假装，它顶着
`refused` 标签告诉值班长「这条因为太敏感没查」（2.4 的对账精神一路透传到 UI）。

两种报告条目在 web 上的差别就这一处：**调查报告没有 levels**（它的 findings 是
自由证据，不该被压成四档色签），富化报告有（它的本质就是逐项评级）。呈现形态
尊重数据本性，不搞统一卡片美学。

## 三、服务与中间件卡

**卡 1 · ▼视图装配纯函数层（web 自研模式）**

- **它是什么**：把「数据合成」从 React 组件里抽出来，做成不碰框架的纯函数
  （assembleTimeline/entryRow/levelsOf），组件只负责渲染。web 仓库里这个模式到处
  都是（pipeline.ts、audit.ts、reveal.ts……每个都配同名 .test.ts）。
- **市面替代**：① 数据加工写在 useEffect/useMemo 里（组件即逻辑，测不了）；
  ② 后端出一个「time-line 聚合口」替前端拼好（服务端多一个特制端点，前端变薄）。
- **为何这么选**：纯函数层能被 vitest 直接测（不挂组件树），测试跑得飞快
  （本步实测 1.75s/4 例）；「web 不能 import agent 源码」的边界规则下，跨源合成
  只能发生在 web 侧，纯函数层是它唯一可测的形态。代价：两路数据的**取数**仍要
  组件协调（CasePage 拉详情+审批卡再喂给装配），取数逻辑薄但存在。
- **业务上怎么选**：视图层只要有「合成/换算/对账」逻辑，就抽纯函数层；纯渲染
  （标签映射、颜色）留组件。判断标准：这段逻辑**需不需要挂载 React 才能验证**？
  需要，就是写坏了。

**卡 2 · ▲ antd Timeline / Tag（呈现件选型）**

- **它是什么**：Ant Design 的时间线组件（色点+自由内容槽）与标签组件（色系内置），
  案件时间线、评级透视都靠它们。
- **市面替代**：shadcn/ui+Tailwind（自由度高、要自己拼）；自研组件（完全可控，
  维护贵）；纯表格（信息密度高，叙事性差）。
- **为何这么选**：SOC 案件时间线的核心诉求是「**扫一眼读出险情**」——antd 的色系
  语义（gold=待办、red=高危）与 Tag/TimeLine 的组合刚好把这个诉求变成零成本；
  且 antd5 的中文生态与运维后台气质匹配（1.6 已定 antd5，此处是同一选型的自然
  延伸）。
- **业务上怎么选**：给值班 7×24 盯屏的人做界面，**色彩语义的一致性**比视觉独特性
  值钱得多——用什么组件库其次，全站「红=险、金=等人」不破例才是硬要求。

## 四、防线对号

| 防线 | 在本步的位置 |
|---|---|
| 单一事实源 | 审批不写冗余时间线行——web 投影审批卡进视图（timeline.ts 头注②） |
| 不猜时间（证据纪律） | ts 只取数据的 created_at/decided_at；没有的时间并进文案，不编 |
| 全链宽容 | 写口不校验 kind（2.3 捣乱 B）→ 存储老实存 → web 原样透传标签——不崩不猜 |
| XSS 卫生 | body 用 `<pre>` 文本渲染，绝不 innerHTML LLM 产物 |
| 字段透视不造假 | levelsOf 只读 structured.results 的 ok/level；拒发行如实给 refused |
| INV-8（呈现侧） | 审批行的「已执行/待执行」直接来自一次性 token 状态——执行半边可见 |

## 六、捣乱实验（必选）

**捣乱 A · 给时间线塞一条「不认识的 kind」，看全链路谁接谁传**（2.3 捣乱 B 的续集）：

```bash
curl -s -X POST localhost:3002/api/v1/cases/case_000002/timeline \
  -H 'content-type: application/json' \
  -d '{"kind":"mystery_kind","author":"duty_officer_test","body":"捣乱：web 你认识我吗？"}' >/dev/null
curl -s localhost:3002/api/v1/cases/case_000002/timeline | python3 -c "
import json,sys
items=json.load(sys.stdin)
items=items if isinstance(items,list) else items.get('entries',[])
m=[e for e in items if e['kind']=='mystery_kind'][-1]
print('M2 存了:', m['kind'], '|', m['body'])"
```

预期链路：M2 **201 收下**（写口不校验）→ 装配层 `metaOf` 翻译表查无 → **原样透传**
（`mystery_kind` 当标签、灰色点）→ web 案件页显示一个你没见过的灰标签行，页面
不炸不猜。**写口松、存储实、视图诚、判断归人**——一条非法 kind 走完全链，每层
的行为都符合自己的职责。（这条捣乱行留在 case_000002 当教具，body 自带「捣乱」
字样。）

**捣乱 B · 排序捣乱——把「现在」写进 created_at 会怎样**：

用 REST 写时间线时 body 里**没有** created_at 字段可传（wire 就没这字段，回看 2.3
的 POST 路由：只收 kind/author/body/structured），所以「前端伪造时间」在写口就进
不来；再对照 web 侧——`entryRow` 的 ts 取 `e.created_at`，装配层不接受任何外部
传入的时间参数。想造一条「显示在未来」的时间线行，唯一办法是改数据库——**三道门
（wire 无此字段、装配不收参、组件只透传）把「不猜时间」从注释变成了物理事实**。
可以自己核对一遍：`grep -n "created_at" services/case-backend/src/app.ts | grep -i timeline`
看 POST 路由的字段清单。
