> 前面七 + 三步都在"栈已经跑着"的前提下讲行为；这一步回答最底层的问题：**这一整栋
> 楼是怎么从一张图纸长出来的**。`docker-compose.yml` 是总装图纸——九个服务、六个

> 封条核对、图例走读这些**不碰数据**的手段，唯一动真格的重建只重建 agent 一个容器
> （收场景 7 埋的接口：让 25 行登记表上线），数据在 bind mount 里纹丝不动。

## 一、操作（位置感）

本步不写代码，动的是一个容器（agent）和一堆只读命令。全流程：

```bash
cd /Users/divh/Downloads/安全评估agent/soc-demo

# ① 图纸校验：渲染一遍配置，语法/引用错当场报（不碰任何容器）
docker compose config -q && echo "config OK"
docker compose config --services | sort     # → 九个服务名（站 1）

# ② 可选扩展间：开了 profile 才进图纸
docker compose --profile observability config --services | wc -l   # → 11
docker compose --profile real-wazuh config --services | wc -l      # → 10

# ③ 收口场景 7 的接口：重建 agent 容器（只此一个），让 25 行登记表上线
docker compose build agent
docker compose up -d agent                  # 只重建 agent，其余八个容器不眨眼
```

本步实测的收口证据，先亮出来：

```
soc-demo-agent-1 Up 15 seconds (healthy)     ← 唯一被重建的容器（15 秒转 healthy）
soc-demo-case-backend-1 Up 10 hours (healthy) ← 其余八家 uptime 原样
```

容器内登记表从 **24 行（旧烤制）→ 25 行**，`list_approvals` 在**运行面读口**可见
（容器内用与在线服务完全同款的 `tierOf()` 探：`list_approvals = 1`（L1）、
`registeredTools() = 25`）。八项布景计数重建前后逐项相等——零数据损失（第五节
逐项复点）。

## 二、调用链

全景：一条 `docker compose up -d` 的装配线，以及本步实际走的"纸面装配"：

```
docker compose up -d（真装配，本步只对 agent 执行）
  ① 读 docker-compose.yml + .env          → 渲染出最终配置（docker compose config 的内容）
  ② 按依赖拓扑排序                          → depends_on { condition: service_healthy }
  ③ 缺镜像的按 build: 现场造 / 有 image: 的按 digest 拉
  ④ 逐个起容器、跑 healthcheck              → 127.0.0.1 探活（不走 localhost，见图纸头注）
  ⑤ bind mount 挂数据卷                     → data/ 四仓库接上宿主盘

本步的纸面装配（对九服务零打扰）：
  config -q / config --services / config 渲染   ← 把 ①-⑤ 的结果"打印"出来核对
  build agent && up -d agent                    ← 只走一遍真装配，收场景 7 的接口
```

### 站 1 · 图纸与名册：先 `config` 再 `up`

📍 大图节点:COMPOSE(8.4 compose 图纸)（名册的机器断言在同子图 TOPOTEST）

图纸头三行是全文件的"施工须知"。📄 [soc-demo/docker-compose.yml:1-3](soc-demo/docker-compose.yml#L1)：

```yml
# SOC 数字员工 · 单机编排（PRD §4.1 组件清单 C1-C7；eval/MCP CLI 不进 compose）
# 端口规划：ingest 3001 / case-backend 3002 / agent 3003 / web 5173 / guards 8001 / gateway 8002 / chroma 8000 / contextforge 4444 / openfga 18080(宿主) / langfuse 13000(宿主，可选)
# 健康检查一律用 127.0.0.1 不用 localhost：alpine 镜像里 localhost 优先解析 ::1，服务只绑 IPv4 会被误判挂掉
```

第三行是踩过坑才写上去的：alpine 容器里 `localhost` 会先解析成 IPv6 的 `::1`，
而服务只监听 IPv4——healthcheck 会把活生生的好人误判成死人。所以所有探活写
`127.0.0.1`。先说清 `config` 与 `up` 的时序关系：`config` 只做**纸面装配**——
读图纸加 .env 渲染出"如果真起，会是什么样"，不碰任何容器、不拉任何镜像；`up`
才是真装配。所以本步对九服务的全部核对都走纸面，唯一动真格的只有站 5 对 agent
的一次 `build && up`。名册本身不用背，让机器念（本步实测逐字）：

```
$ docker compose config --services | sort
agent case-backend chroma contextforge gateway guards ingest openfga web
```

九个服务，一个不多一个不少——这个名册**有机器断言守着**（不是口头约定）。📄 [soc-demo/services/agent/src/compose-topology.test.ts:126-131](soc-demo/services/agent/src/compose-topology.test.ts#L126)：

```ts
    // 票面基线：默认一键起的九服务一个不能少（演示会话实测口径）
    expect(svcs).toEqual([
      "agent", "case-backend", "chroma", "contextforge", "gateway",
      "guards", "ingest", "openfga", "web",
    ]);
  });
```

谁往 compose 里私加/私删默认服务，agent 测试套件当场翻红——图纸也是被 CI 看住的。

### 站 2 · 六枚封条：digest 钉，为什么每个官方镜像都长这样

📍 大图节点:SEALS + TOPOTEST(8.4 compose 图纸)（一站两节点：封条本体 SEALS、执法者 TOPOTEST）

数一数 compose 里所有 `image:` 行，六个官方镜像**全部**以 `@sha256:…` 结尾：

| 服务 | 镜像 | digest（前 8 位） | 钉的出处 |
|---|---|---|---|
| chroma | chromadb/chroma@sha256:1e0b73a1… | 1e0b73a1 | 票 17/26 |
| openfga | openfga/openfga@sha256:78d1fa60… | 78d1fa60 | 票 43 |
| contextforge | ghcr.io/ibm/mcp-context-forge@sha256:98dfab27… | 98dfab27 | 票 26 |
| langfuse（profile） | langfuse/langfuse@sha256:85c278dc… | 85c278dc | 票 37 |
| langfuse-db（profile） | postgres@sha256:18cfe3ef… | 18cfe3ef | 票 37 |
| wazuh-manager（profile） | wazuh/wazuh-manager@sha256:80cada6a… | 80cada6a | 票 38 |

比喻：tag（如 `chromadb/chroma:1.0.0`）是**门牌**——同一个人的门牌可以被房东改挂
给别人；digest 是**封条**——内容物有一个字节不同，封条号就对不上。供应链安全的
底线：生产环境引用第三方镜像，认封条不认门牌。chroma 那格的注释把"为什么"写得
很透。📄 [soc-demo/docker-compose.yml:126-131](soc-demo/docker-compose.yml#L126)：

```yml
    # 票 17（ADR 0002 框架红线：真 chromadb 落 compose）：官方镜像按 digest 钉（票 26
    # 先例——latest 漂移不可接受；本 digest 实测 = chroma 1.0.0，arm64 本地已验，
    # REST /api/v2/*）。服务端默认 embedding 首次写入会运行时下载 onnx 模型，与离线
    # 纪律冲突 → agent 侧默认显式带 hashEmbedding 出站（vector-store.ts 文件头），
    # KB_EMBEDDING=chroma_default 可切服务端模型，容器才需要出网。
    image: chromadb/chroma@sha256:1e0b73a187a28757c572acba508c46f48c9e8b0acaf5c20e6d95cdedce1acdf6
```

封条不是自己封的就有用——得有人查。查封条的执法者之一是拓扑测试。📄 [soc-demo/services/agent/src/compose-topology.test.ts:38-46](soc-demo/services/agent/src/compose-topology.test.ts#L38)：

```ts
  test("官方镜像按 digest 钉（票 26/17 先例：latest 漂移不可接受），且不重建（ADR 0001：自写件不动镜像内部）", () => {
    for (const name of ["langfuse", "langfuse-db"]) {
      const image = serviceBlock(name).match(/image:\s*(\S+)/);
      expect(image, `${name} 缺 image`).not.toBeNull();
      expect(image?.[1] ?? "", `${name} 未按 sha256 digest 钉`).toMatch(/@sha256:[0-9a-f]{64}$/);
      expect(serviceBlock(name), `${name} 不许 build（官方镜像直接用）`).not.toMatch(/\n\s+build:/);
    }
    expect(serviceBlock("langfuse").match(/image:\s*(\S+)/)?.[1] ?? "").toContain("langfuse/langfuse");
  });
```

看清楚执法范围：这个测试钉的是 **langfuse 对 + wazuh-manager（三对 profile 镜像）**；
默认栈的 chroma/openfga/contextforge 三枚封条目前靠 compose 注释 + 评审纪律守——
捣乱实验 B 会演示这个盲区的存在（已记总纲"发现的问题"）。另一个执法者是 CI 的
`compose-config` job（8.5 见），但它只校验语法，不校验封条。

### 站 3 · 图例：.env 口径——三个值、两个空、一条注释

📍 大图节点:ENVEX(8.4 compose 图纸)

`.env.example` 是图纸的图例：每个变量谁在吃、空值是什么语义，注释都写死了。📄 [soc-demo/.env.example:1-3](soc-demo/.env.example#L1)：

```bash
# 复制为 .env 使用（.env 已 gitignore 不入库）。未列出的变量一律吃 compose 内建默认。
# 口径（票 41-② / 票 06）：教学假值可跑通全链路；真部署删假值，由部署环境注入真值，
# 绝不放真密钥进仓库。
```

三个"有值"的变量（本机 `.env` 实测）：`SOC_HMAC_KEY`（**gateway 铸票 / agent 验票
共享同一枚**——铸票/验票的分工回指 TERMS「保安处」条与「手令/任务票」四层；
场景 4 整条审批链的信任根就是这行教学假值）；`AGENT_LLM=fake`
（离线确定性口径，8.1 的快道连它都不读——演习室自带伪件）；`LLM_MODEL=minimax-m2`。两个"留空"的变量语义更讲究。📄 [soc-demo/.env.example:14-16](soc-demo/.env.example#L14)：

```bash
# 仅 AGENT_LLM=real 时需要：上游地址与真 key。key 只挂 gateway 进程，绝不进 agent。
SOC_LLM_UPSTREAM=https://api.minimaxi.com
SECRETS_LLM_API_KEY=
```

空 ≠ 没配好，空是**一种执勤状态**：`SECRETS_LLM_API_KEY` 空 → 网关对 LLM 出站
一律回 `503 deny_no_secret`（5.5 实测过的 fail-closed 执勤位）；8.1 里 judge 的
`not_evaluable` 也是被这个空值触发的。一个空行同时管住了"LLM 不会偷偷出网"和
"评估裁判显式缺席"两件事。图纸侧的对应写法是**缺省值语法**——agent 的模式开关：

📄 [soc-demo/docker-compose.yml:43](soc-demo/docker-compose.yml#L43)

```yml
      AGENT_LLM: ${AGENT_LLM:-real}
```

`${AGENT_LLM:-real}` 读作：.env 里写了就用写的，没写默认 `real`（生产装配默认走
真 LLM 经凭证代理——票 27 的框架红线：**默认值是安全侧**，想离线必须显式说 fake）。
而 `.env.example` 的演示口径给的是 `AGENT_LLM=fake`——同一行图纸，生产读出 real、
课堂读出 fake，这就是"图例"的作用。

还有一条红线藏在 git 里：`.env` 本尊**永不入库**（本步实测 `git check-ignore .env`
命中）。`.env.example` 入库当图例，真值/假值都只活在本机与部署环境。

### 站 4 · 两间可选扩展房：profiles（observability / real-wazuh）

📍 大图节点:COMPOSE(8.4 compose 图纸)（"不许暗依赖"的专条断言在 TOPOTEST）

默认九服务是"一键可起"的水位线（PRD 验收口径）；可选能力**不进默认图纸**，挂
`profiles:` 标签，点名才装配。本步实测：

```
$ docker compose --profile observability config --services | wc -l    → 11
  （九服务 + langfuse + langfuse-db：LLM 调用 trace 观测旁路，票 37）
$ docker compose --profile real-wazuh config --services | wc -l       → 10
  （九服务 + wazuh-manager：真规则引擎 backdrop，logtest 喂数用，票 38）
$ docker compose config -q                                            → 过
```

设计纪律有三条，都写在注释与测试里：①**水位线**——langfuse 坚持用 v2 单镜像 +
postgres（v3 要拖 clickhouse/minio 全家桶，违反"一键可起"）；②**不许暗依赖**——
agent 的 depends_on 里若写了 langfuse，`up -d` 会隐式激活 profile 把默认栈拖肥
（compose-topology.test.ts:54-57 专门断言不许这么写）；③**旁路开关**——就算容器
起了，agent 侧 `LANGFUSE_PUBLIC_KEY` 双空 = 镜像旁路零开销（.env.example L18-22
那两条注释键就是开关）。想看真探头干活同理：`docker compose --profile real-wazuh
up -d wazuh-manager` 起官方 4.14.7 规则引擎，喂数脚本 `scripts/wazuh-logtest-feed.ts`
把同一批 fixture 喂进真规则引擎重判（1.1 卡 2 讲过它的扮演分工）。

### 站 5 · 重建收口：只动一个容器，场景 7 的接口今天兑现

📍 大图节点:REBUILD + T_MST(8.4 compose 图纸 / 容器 agent)

场景 7 留的部署边界：真登记表 25 行，但运行中的 agent 容器还是旧镜像里烤制的
24 行。收口动作两步——**造新镜像、换容器**：

```bash
docker compose build agent   # 造 soc-demo-agent 新镜像（COPY 当前的 fixtures/ 进去）
docker compose up -d agent   # 只重建 agent 容器，其余八家 uptime 原样
```

时序接缝在这两步之间：`build` 完成的那一刻，新镜像**躺在本地镜像库里**，任何
运行中的容器都还不知道它存在；`up -d agent` 才用新镜像**换掉旧容器**（停旧、
起新、healthcheck 探活每 5 秒一发、约 15 秒转 healthy）。两步之间隔着一次"人工
检查新货"的机会——这就是文末"想得更深一步"那道题的物理基础。上线之后，25 行
登记表要等到**下一次验票闸做分级判定**（tierOf 被调）才被真正读到——本步用同款
读口探针主动读了一次（见下文 ③），不用等业务流量来验。
造镜像时把什么烤了进去？agent 的 Dockerfile 末三行 COPY 是关键。📄 [soc-demo/services/agent/Dockerfile:11-14](soc-demo/services/agent/Dockerfile#L11)：

```dockerfile
COPY tsconfig.base.json ./
COPY services/agent/ services/agent/
# 票 18：chat 只读面 siem_query 的 fixture 语料（FixtureSiem 读 fixtures/alerts/）
COPY fixtures/ fixtures/
```

宿主 `fixtures/tools.manifest.json` 现在是 25 行，新镜像自然烤进 25 行。重建后
三重验证（本步实测逐字）：

```
① 容器 healthy：soc-demo-agent-1 Up 15 seconds (healthy)
② 文件面：容器内 /app/fixtures/tools.manifest.json → 25 个工具，
   list_approvals = ('list_approvals', 'L1', 'readonly_query')
③ 运行面：容器内用在线服务同款读口探——
   $ docker compose exec agent ./node_modules/.bin/tsx -e \
     "import('/app/services/agent/src/tools-manifest.ts').then(m => …)"
   registeredTools: 25   list_approvals tierOf = 1（L1）   get_alert tierOf = 0（L0）
```

③是最硬的一层：`tierOf()` 正是在线验票闸做分级判定调的同一个函数（7.3 的"登记面/
票面/执行体"三层里，这一步把**登记面**从 24 行对齐到 25 行；票面与执行体本就与
登记行无关——所以行为零变化，这也是 7.3 摘行对照教过的"闸认票不认表"的另一面）。

### 站 6 · 数据仓与布景：bind mount 是布景的命根子

📍 大图节点:T_DATA(容器 agent)（挂载三件套的图纸原文见下方引用块，落在 COMPOSE 图纸里）

agent 的挂载三件套（一块数据盘 + 两块只读共享件）。📄 [soc-demo/docker-compose.yml:76-85](soc-demo/docker-compose.yml#L76)：

```yml
    volumes:
      # 票 41（B5·对账一-4 清偿）：runs/run_events/checkpoints/审批卡落宿主盘，
      # 审批 interrupt 处杀进程重启可恢复（m3 卡测试计划）。落点 /app/data 不是
      # 票 10 注释里的 /data：index.ts 的 ../../../data/ 从 services/agent/src/
      # 往上三级，容器内 WORKDIR=/app/services/agent → 解析到 /app/data，同
      # case-backend 口径（挂 /data 等于没挂，库照旧落容器层重启照丢）。
      # 真容器证据：bash scripts/agent-smoke-41.sh
      - "./data/agent:/app/data"
      - "./services/gateway/plugins:/fga:ro" # store/model id 与 contextforge 插件同源一份
      - "./services/gateway/fga:/fga-matrix:ro" # matrix.json = 可见工具清单的单一来源
```

全栈四块 bind mount 数据盘：`data/agent`（runs/事件/审批卡/checkpoint）、
`data/case-backend`（告警/案卷/审计/KB 账面/焚毁坟场）、`data/guards`（PII 映射表）、
`data/chroma`（知识检索面）。**bind mount 的内容在宿主盘**——容器删了、重建了、
升级了，数据一根毫毛不少；反过来 `docker compose down -v` 会拆匿名卷（本仓数据
在 bind mount 其实不受 -v 影响，但**教学纪律是这条命令根本不许出现**：拆布景
的风险动作一律不进肌肉记忆）。注释里那个"挂 /data 等于没挂"的勘误是真实事故：
容器内路径解析靠 `WORKDIR` 与相对路径的配合，挂错一层，数据就悄悄落到容器层，
重启全丢。

重建为什么伤不到它？**代码/产物进容器靠构建（镜像层），数据在宿主盘（bind
mount）**——8.2 的 Eval 页两份 run_at 讲过同一物理定律的产物版。所以"重建 agent"
这个动作天生与"清布景"无关：本步八项计数复点全部相等（第五节）。

## 三、服务与中间件卡

**卡 1 · ▲Docker Compose —— 单机编排的装配图纸**

- **替我们干了件什么体力活**：把"起九个容器、配端口、挂盘、注环境变量、按依赖
  等健康"从九十九条命令压成一条 `up -d`。它管装配，不管运行中治理（那是 k8s 的
  事）——单机教学/demo 的甜点位。
- **本项目怎么配置**：一个 299 行的 yml（含注释）。三个惯用法值得偷走：①
  `depends_on: {condition: service_healthy}` 让依赖序由健康说话（agent 等
  case-backend/guards/gateway 三家 healthy 才起，chroma/openfga 无 healthcheck 就
  退一档 `service_started`）；②healthcheck 一律 `127.0.0.1`（站 1 的 ::1 坑）；
  ③缺省值语法 `${VAR:-默认}` 把"生产默认安全侧、课堂显式开假"编码进图纸。
- **市面上同类**：docker compose v2（本仓用法，`docker compose` 子命令）、
  k8s+helm（集群正解，重）、podman-compose、nixos 容器声明（另类洁癖）。
- **本项目为什么选它**：教学要"一键可起、一键可拆、可复现"——compose 的声明式
  图纸 + digest 封条 + bind mount 数据外置正好三条全占，且学员不用先学 k8s。
- **业务上怎么选**：单机 demo/小团队内部工具 → compose；多机、要弹性/滚动发布/
  自愈 → k8s；中间态（几台机器、不想上 k8s）→ compose + 逆代理或 nomad。
  铁律同源：**图纸入库、数据外置、镜像封条**——这三条到了 k8s 一条都不变。

**卡 2 · digest 钉 —— 供应链封条（tag 与 digest 的差别）**

- **它是什么**：`镜像@sha256:…` 直接按内容哈希取货。tag 是可变指针（`1.0.0`、
  `latest` 都能被重新指向别的构建），digest 是内容地址——**封条号对不上就是货不对**。
- **本项目怎么配置**：六个官方镜像全钉（站 2 表格）；自研三件（ingest/case-backend/
  agent 一族）没有 `image:` 行、走 `build:` 现场造——自研件的可复现靠"源码入库 +
  锁文件（pnpm-lock）"，第三方件才需要 digest 封条。
- **一个真实的坑（contextforge 备案）**：镜像仓库有"多架构 index digest"和"单架构
  子 manifest digest"两种封条号，Docker Hub 的 index 本机能拉、某些 ghcr 场景的
  index 反而拉不动，最后钉的是 arm64 子 manifest——compose 注释里整段备案（票 26）。
  升级跟踪以 index digest 前进为准。教训：**封条也有门派，钉之前先在本机真拉一遍**。
- **市面上同类**：cosign 签名（内容之外再验"谁封的"）、SBOM（货物的零件清单）、
  私有镜像代理/缓存（出口统一）。digest 钉是这一族里成本最低、收益立竿见影的一档。
- **业务上怎么选**：教学/演示 → digest 钉 + 注释备案足够；生产 → 钉 + 签名验证 +
  私有代理三件套；任何时候 `latest` 出现在生产图纸里都该当场打回。

## 四、防线对号

- **INV-1（fail-closed）藏在图纸里**：`SOC_HMAC_KEY` 缺失 → 拒铸票/拒登录（compose
  gateway 注释原文"缺它铸票 fail-closed（票 06 口径，INV-1）"）；`SECRETS_LLM_API_KEY`
  空 → `deny_no_secret` 执勤（5.5）。图纸的默认值方向都倒向安全侧（`AGENT_LLM:-real`
  ——想不安全必须显式说 fake）。
- **水位线（决策记录）**："一键可起"是验收口径：默认九服务拓扑由
  compose-topology.test.ts 的九服务名册断言看死（站 1），可选能力走 profiles 且
  禁止暗依赖（该测试 54-57 行的专条）。
- **数据存续 = 布景存续**：四块 bind mount（站 6）+ 禁 `down -v` 纪律 + 票 41 的
  "挂错目录 = 数据落容器层重启丢"勘误。本步重建的零损失复点是这条防线的年度演习。
- **部署边界（8.2 定理的容器版）**：代码/产物进容器靠构建（Dockerfile COPY），
  数据靠 bind mount——7.3 的 24/25 行登记表、8.2 的两份成绩单、本步的重建收口，
  三次同一律。
- **契约**：`docker compose config` 的渲染结果被两个消费方吃——CI 的
  compose-config job（语法闸）与 compose-topology.test.ts（语义闸）。图纸既有
  人读的注释，也有机器读的断言。

```bash

# A. 摘封条对照（有执法者的镜像）：把 langfuse 的 digest 换成 :latest → 拓扑测试当场翻红

#   判据（诚实的坏消息）：compose 语法闸不校验封条；拓扑测试又只钉了 profile 三对
```
