## 一、操作（位置感）

盲区报告的数据流在 [purple.ts:346-357](soc-demo/evals/src/rigs/purple.ts#L346)
（discovered 为 false 时装配）：

```ts
const blindSpot: PurpleBlindSpot | null = discovered ? null : {
  family: entry.family,
  missingChain: entry.ground_truth.blind_spot?.missing_chain ?? "（映射表未标注缺失链——判定失真必红，见 groundTruthOk）",
  toolDimension: entry.ground_truth.blind_spot?.tool_dimension ?? "（映射表未标注工具维度——判定失真必红，见 groundTruthOk）",
  loopGap: (() => { … runA.gapRecords 末条 … })(),
  unsatisfiedSignatures: signatures.filter((s) => !s.ok).map((s) => s.reason),
};
```

四个字段的来源分成两派——**循环侧真产物**与**映射表标注**，故意各留一半：
`loopGap` 是 gap_analyzer 节点自己产出的结构化缺口（[TERMS「循环三件套」](TERMS.md)条
的找缺口的，真节点输出不是 rig 编的）；`missingChain/toolDimension` 是 12.1 映射表
miss 例必须配的标注（装载闸管的）；`unsatisfiedSignatures` 是 12.3 三重验的失败
reason 原文（hit 例被投毒时它才有货）。注意两个 `??` 兜底文案——**判定失真必红，
见 groundTruthOk**：盲区字段不许静默空着，兜底文案本身就是一条红指向。

📍 大图节点:BLIND(12.4 盲区三件套)

01_inject_srcuser_uncertain（SSH 无效用户试探，未得逞）在 purple-team.json 里的
盲区报告原文：

```json
"blindSpot": {
  "family": "credential_leak",
  "missingChain": "语料无 /etc/shadow FIM 篡改、无凭据外带外联——凭据试探类攻击的得逞痕迹缺席（本例攻击本就未得逞）。",
  "toolDimension": "auth 探测维缺失：5710/5712 失败登录聚源查询（siem_query 实体检索不在族菜单）——凭据试探/爆破维需要 auth 日志维工具。",
  "loopGap": {
    "gap_description": "取证面证据不足（既往 0 轮、本轮 2 份子报告），按剧本换维度补查",
    "unknown": "取证面证据不足（既往 0 轮、本轮 2 份子报告），按剧本换维度补查",
    "suggested_focus": ["initial"]

  "unsatisfiedSignatures": []

```

对照 12.2 的逐例轨迹读：循环两轮跑了 playbook_lookup/file_change_query（轮 1）、
outbound_conn_query/graph_query（轮 2），取证面全零命中——judge 收敛为 miss、
怀疑书 refuted。**循环侧的结论是"这怀疑没证据支持"（loopGap 记录了它一路找证据
的缺口）；映射表侧的结论是"这类攻击的得逞痕迹在语料里设计性缺席，且族菜单缺
auth 日志维工具"**。两派合起来才是完整盲区：前者说"我找不到"，后者说"为什么
找不到、补什么能找到"。`unsatisfiedSignatures` 是空的——01 本来就是 miss 例
无签名，这个字段为 hit 例判定失真时准备（12.3 捣乱①里 02 例的失败 reason 就落
在这里）。

六个维度读出一个共同形状：**全部是"非 SIEM 工具维度"**。狩猎族的菜单（

检查（[purple.ts:477-483](soc-demo/evals/src/rigs/purple.ts#L477)）把这变成门槛：
6 个未发现例全部要有 loopGap 非空 + 缺失链 + 工具维度，缺一件点名。

### 站 3 · 0/4 是丢人的数字吗？——阴性资产的正确用法

📍 大图节点:BLIND→T_ARTIFACTS(盲区进报告进工装)

不是——它是这张成绩单里**最值钱的一行**。三步用法：①**对账面**：发现率 5/11
配上盲区六维，"低"就有了结构化的解释（不是循环笨，是取景框缺六个数据源）；
②**建设面**：四个维度就是内容层的下一批工单模板（给凭证族补 auth 日志维工具 →
先走 S7 登记流程 → 再扩预案卡菜单 → 重跑紫队看发现率变化——一张闭环的建设
路线图）；③**诚实面**：`weakest_family=credential_leak` 进报告、进 web Eval 页
（12.5 实测），系统公开承认自己最弱的一族——**能自曝其短的自证才是自证**，只报
喜的评估是广告。对照 12.3 的因果还要补一句：这 4 例里有的（01/05/11）攻击本就
未得逞或设计性零痕迹，"发现不了"恰是防线正确——盲区报告把这两种"没发现"
（防线挡住了 vs 取景框没盖上）分得清清楚楚，`missing_chain` 逐例写了是哪种。

## 三、服务与中间件卡

**卡 · ▼盲区聚类（紫队报告的阴性半边）**

- **它是什么**：按假设族归堆未发现例，每族产出 misses/发现数/未发现例名单/
  缺失工具维度去重集；`weakest_family` 取 misses 最多的族（平手按族名字典序）。
- **市面替代**：报告里放一句"发现率 45%，未发现 6 例"（无聚类无维度）。
- **为何这么选**：无结构的阴性数字不可行动——"6 例没发现"读不出任何工单；
  聚类+维度把阴性数字变成**带优先级的建设清单**（最弱族+缺哪些数据源一目了然），
  这也是"发现不了的也要有产出"这句教学句的落点。
- **业务上怎么选**：凡负向指标（未发现/未拦截/未覆盖），交付时必须带**归因结构**
  （按什么聚类、缺什么、下一步补什么）——不带归因的失败数字只是焦虑发生器。

## 六、捣乱实验②（本票指定）：预算注水——把硬顶改成"无限轮次"烧烧看

**改法**：把 [purple.ts:46](soc-demo/evals/src/rigs/purple.ts#L46) 的机制硬顶
20 改成 999999（模拟"嫌预算小，开到无限"）：

```bash
sed -i '' 's/  max_rounds_hard_cap: 20,/  max_rounds_hard_cap: 999_999, \/\/ 捣乱②：预算注水/' evals/src/rigs/purple.ts
cd evals && pnpm exec vitest run src/rigs/purple.test.ts
```

实测（**6 passed——测试一个都红不了**，这本身就是结果）：

```
Test Files  1 passed (1)
      Tests  6 passed (6)
```

再看数字（注水前后 digest 快照比对，真实输出）：

```
注水后 totals: {'fixtures': 11, 'discovered': 5, 'discovery_rate': 0.455} | budget: 999999
digests vs 注水前: ALL EQUAL
02 budgetDetail: rounds=4（硬顶 999999/模板 6）、llmTokens=264（run 档 500000）、终态=concluded | withinBudget: true
```

**答案的三层讲究**：①**烧不出第 6 个发现**——发现率 5/11 纹丝不动、11 例 digest
逐字节不变：循环行为由波表+语料+确定性三件套决定，与预算上限无关；"无限烧 token
必发现"在这个判定语义下是**数学上不成立**的（discovered 认证据不认工时，12.3 站 1）。
②**绑定档根本没动**——实际生效的上限是 `Math.min(硬顶, 模板档)`（12.3 站 3 的双
取小），硬顶注到 999999 后 min(999999, 6) 仍是 6；模板档是内容层数据
（hunt-templates max_rounds），注水机制常量连它的一根毛都碰不到。③**注水必然
留痕**——报告的 `budget.max_rounds_hard_cap=999999` 和每例 budgetDetail 的
"硬顶 999999"字样如实记账：口径是资产，被改必留审计痕迹，"数字一样但口径变了"
在工件里一眼可见（对照 12.3 捣乱①：那是对账红，这是如实留痕——两种失真两种
处理，都是机器可见）。

## 场景题闯关（本步 1 题）

**Q4：如果把 credential_leak 的盲区四个维度全补齐（auth 聚源/KB 审计聚合/L2 执行
审计/凭证外带审计四个新工具），credential_leak 族的下一次紫队成绩单会是 4/4 吗？
提示：01/05/11 三例的攻击本就没得逞。**

<details><summary>答案（点击展开）</summary>

不会，也不该。01/05/11 三例的攻击**未得逞或设计性零痕迹**（01 试探未得逞、05 毒
提案被人审驳回、11 是 INV-4 金丝雀）——补齐工具维度后，循环能做的是**更快、更
有据地证伪**（查 auth 日志确认无爆破成功、查外带审计确认无泄露），而不是把
miss 翻成 hit；它们的 `expected` 仍是 miss，映射表标准答案不用改。真正可能翻绿
的是一个假设性场景：**同样类型的攻击如果哪天真得逞了**（语料里出现 /etc/shadow
FIM 或凭据外带外联），补了 auth 探测维的循环才有工具去发现它——这正是票 81 实现记录
说的"供后续内容层扩工具维度时对账"的口径。所以扩维度的正确预期不是"发现率
冲到 11/11"，而是：①发现率里"因缺工具而漏"的成分归零；②证伪例的证据链从
"SIEM 全零命中"变成"跨账本审计确认"（更硬的阴性证据）；③真正得逞的新攻击
现场能被抓到。**紫队成绩单的两半——发现率与盲区——各自诚实，才合得出真实的
系统能力**。</details>
