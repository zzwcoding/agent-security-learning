### 站 2 · 27 格全拒实测：100% 是遍历出来的数字

📍 大图节点:OFFMENU27(11.4 菜单外工具全量遍历)

```bash
cat > /tmp/ir-menu-demo.mts <<'EOF'
import { loadHuntTemplates } from "/Users/divh/Downloads/安全评估agent/soc-demo/services/agent/workers/investigation/hunt-pack.js";
import { registeredTools, tierOf } from "/Users/divh/Downloads/安全评估agent/soc-demo/services/agent/src/tools-manifest.js";
import { planRound } from "/Users/divh/Downloads/安全评估agent/soc-demo/services/agent/src/orchestration/planner.js";
import { MemoryAuditSink } from "/Users/divh/Downloads/安全评估agent/soc-demo/services/agent/src/audit.js";
const ir = loadHuntTemplates().find((f) => f.template_id === "ir_host_compromise")!;
const menu = [...ir.menu];
const offMenu = registeredTools().filter((t) => !menu.includes(t));
console.log("ir 菜单:", menu.join(", "));
console.log("全仓在册:", registeredTools().length, "件 | 菜单外:", offMenu.length, "件");
let denied = 0;
for (const tool of offMenu) {
  // 每格：脚本化 planner 硬点菜单外那一件 → 真 planRound 裁决
  const audit = new MemoryAuditSink();
  const ctx = { state: { hypothesis_text: "x", evidence_so_far: [], gap: null, menu,
    max_rounds: ir.max_rounds, max_tasks: ir.max_tasks, round_no: 1, hypothesis_id: "hyp-ir-demo" },
    emit: () => {}, charge: () => {}, checkLlm: () => {} } as never;
  const llm = { planner: async () => ({ tasks: [{ tool, params: {}, rationale: "越菜单" }], tokens: 24 }) };
  await planRound({ orch: { llm, scan: async (t: string) => ({ blocked: false, action: "allow", text: t }) }, audit, runId: "run-ir-demo" }, ctx);
  const d = audit.entries.find((e) => e.action === "hunt_plan_denied");
  if ((ctx.state as never as Record<string, unknown>).planner_failed === true
      && d?.result === "DENIED" && (d?.details as Record<string, unknown>)?.reason === "offmenu_tool") denied++;
}
console.log(`遍历结果: ${denied}/${offMenu.length} 全部 hunt_plan_denied · offmenu_tool · 零重试`);
EOF
cd services/agent && pnpm exec tsx /tmp/ir-menu-demo.mts
```

实测：

```
ir 菜单（host 维度收窄）: playbook_lookup, graph_query, file_change_query, outbound_conn_query, proc_lineage_query
全仓在册工具: 32 件 | 菜单外: 27 件
菜单内工具 tier: playbook_lookup=L0 graph_query=L0 file_change_query=L0 outbound_conn_query=L0 proc_lineage_query=L0
菜单外重点: web_access_query 在外? true | isolate_host 在外? true | isolate_host tier=L2
遍历结果: 27/27 全部 hunt_plan_denied · offmenu_tool · 零重试
```

逐格打分的三要素：`planner_failed=true`（整轮终止、**零重试**——菜单外无重试价值，
spec 行为 4）、`tasks=[]`（越界组合零子 run）、审计 `hunt_plan_denied/DENIED/offmenu_tool`
（五要素留痕）。27 格里 L2 家族（isolate_host/block_ip/deisolate_host/unblock_ip/kb_write）
全数在场——**收窄不只是业务效率，L2 与 planner 之间隔着整个菜单维度**。

## 三、服务与中间件卡

**卡 1 · ▼零登记增量对账（ir-template.test.ts 票 79 范式扩展）**

- **它是什么**：三组断言咬死"第二业务不扩票面"——①ir 菜单 ⊆ manifest 在册表
  （[:99-104](soc-demo/services/agent/workers/investigation/ir-template.test.ts#L99)）；
  ②**含 ir 与不含 ir 的票面并集逐工具相等**，且真注册表票面
  （`requireRunKind("hunt_flow").ticket.allowedTools`）与"不含 ir"重算式相等
  （[:106-118](soc-demo/services/agent/workers/investigation/ir-template.test.ts#L106)）；
  ③register/isolate_host 不入 ir 菜单、菜单内零 L2
  （[:120-124](soc-demo/services/agent/workers/investigation/ir-template.test.ts#L120)）。
- **市面替代**：代码评审口头确认"新业务没加工具"。
- **为何这么选**：菜单是数据后，"悄悄扩权"最舒服的通道就是改数据文件——对账测试把
  "零登记增量"变成 CI 断言，塞特权（11.1 捣乱①）当场红。
- **业务上怎么选**：每新增一张预案卡，同款对账补一行点名（菜单/上限/建议面）；票面
  并集真要扩（新能力维度）→ 那是 S7 的活：先登记 manifest，再谈业务。

## 场景题闯关（本步 2 题 + 收官对照）

**Q1：ir 菜单里 5 件全是 L0 只读工具。如果业务方说"应急取证要看全景，把 L1 的
add_timeline_entry 加进卡里"——数据上可行、登记上可行吗？链路上哪几处会跟着变、
哪几处绝不会变？**

<details><summary>答案（点击展开）</summary>

数据上可行（menu 是卡上的数组）、登记上可行（add_timeline_entry 在册 L1，票 79 范式
对账只会问"在不在 manifest"）。跟着变的：卡上 menu 行、模板清单 API 返回、e2e 布景
的族签名（[familyOfMenu:127-130](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L127)
按菜单集合签名回族——菜单变了签名就变，waves 数据得同步配）。**绝不会变的**：机制层
五个文件一行不动（菜单闸/铸票缝/验票闸照数据执法）、票面并集不变（该工具已在 S2
调查族的父票面里）。这正是"动态性是有边界配置的"的另一面：**配置内的变化是自由的，
配置外的变化才需要动机制**——而"哪些算配置内"由 PRD §13.4b 的业务口径与对账测试
共同圈定。加 L1 写工具同时要想清业务代价：planner 的组合空间从"纯只读取证"变成
"可写账面"，S12 的紫队 eval 会把它计入攻击面。</details>

**Q2：S7 说"登记先于代码"，S11 说"加业务只要数据"——两句话合起来，对"第三块业务"
（PRD §13.4 候选表里的"告警风暴归因"，模板级预期增量）意味着什么？动手清单是什么？**

<details><summary>答案（点击展开）</summary>

意味着第三块业务的**全部动工清单是内容层四件**：①一张新预案卡
（fixtures/hunt-templates/<new>.json：句式族+菜单子集+上限+waves）；②契约测试
（ir-template.test.ts 范式：模板在册/菜单⊆manifest/零登记增量/轨迹钉死）；③必要的
语料补条（剧本库/告警语料，照票 80③ 先例）；④CI 侧零动作——零增量闸对它的 diff
自动生效（一条命令，绿即过）。若候选业务需要**新工具**（如"钓鱼邮件调查"的工具级
预期增量）→ 先回 S7 的流程（gen:tool→manifest 登记→三方对账），登记完回到本场景的
清单。**"能力从登记来（S7），业务从数据来（S11）"——两个清单都不含机制层**，这就是
"一套循环五块业务"主张的可复制配方。</details>

**收官对照表（S7 ↔ S11 姊妹篇）：**

| | S7《新增一个工具》 | S11《第二个业务零增量》 |
|---|---|---|
| 加什么 | 一件工具（能力面） | 一门业务（内容层） |
| 纪律句 | 登记先于代码 | 加业务只要数据 |
| 真相源 | manifest ≡ TOOLS ≡ PRD A.1 三方对账（[7-2](7-2.md)） | 预案卡（[TERMS「预案卡」](TERMS.md)条），机制只投影四字段 |
| 闸 | tools-manifest 对账测试 + tierOf 分级闸 | 零增量闸（T20）+ 菜单对账测试 |
| 红的代价 | 该票返工（编码问题） | 架构回炉回 L0（分层铁律问题） |
| 共同底座 | **约定先于实现**——自由度先被约定圈定，再交给数据/代码 | 同左 |

**本场景收束**：四步连起来读——第二个业务的落地增量是一个 JSON 文件（11.1）、这条
主张有 CI 闸背书（11.2）、行为差异全从数据长出来（11.3）、选路空间被菜单收窄到
host 维度且 27 格全拒、L2 止步于建议文本（11.4）。**"一套循环五块业务"不是愿景，
是一条跑在 CI 里的绿。**下一场景 [S12（紫队闭环）](../scenario/00-导览总纲.md)：
把攻击 fixture 自动转成假设源，同一循环无人值守跑出自主发现率。
