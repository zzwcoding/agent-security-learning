> **docker restart 之后反查同一个占位符**（映射在盘上不在内存的铁证），和**内存
> 模式对照组**（进程一退就忘——PRD 原口径长什么样）。

## 一、操作（位置感）

先看铁皮柜在哪。mapstore 是 guards **自持**的一只 SQLite（不占 M2/agent 的库），
落点由 compose 的一行卷挂载钉死：

📄 [docker-compose.yml:85-91](soc-demo/docker-compose.yml#L85)

```yaml
  guards:
    build: ./services/guards
    ports: ["8001:8001"]
    # 票 49（ADR 0004-3）：PII mapstore（占位符→原文）落宿主盘——脱敏映射重启不丢，
    # /pii/reveal 反查口才有粮。库文件缺省 data/pii-mapstore.sqlite（CWD=/app），
    # 挂 ./data/guards:/app/data 同 case-backend/agent 卷口径（挂别处=重建丢映射）。
    volumes: ["./data/guards:/app/data"]
```

链路大白话：容器里的 guards 进程 CWD 是 `/app`，它写 `data/pii-mapstore.sqlite`
即 `/app/data/…`；compose 把宿主的 `./data/guards` 挂在 `/app/data` 上——**文件
真正落在宿主机仓库目录里**（`soc-demo/data/guards/`，`.gitignore` 的 `data/` 兜住
不进 git）。注释里那句"挂别处=重建丢映射"是血泪口径：容器层文件随容器销毁而亡，
不挂宿主盘，6.1 记的账就是内存账。

操作上摸一眼柜子里的文件形态（WAL 三件套）：

```bash
ls -la soc-demo/data/guards/
# 预期（实测）：pii-mapstore.sqlite（主库）+ -shm + -wal（WAL 预写日志两件套）
```

`-wal`/`-shm` 是 SQLite WAL（Write-Ahead Logging）模式的标配：写先进日志、
后台再合并回主库——跟 1.2 讲过的 M2 库、agent 库同款形态，全仓三只业务库加这只
封存对照表，四只 SQLite 一个打法。

### 站 1 · 表结构：一行一个"占位符×原文"对

📄 [services/guards/pii_store.py:21-29](soc-demo/services/guards/pii_store.py#L21)

```py
DDL = """
CREATE TABLE IF NOT EXISTS pii_map (
  placeholder TEXT NOT NULL,
  original TEXT NOT NULL,
  entity_type TEXT NOT NULL,
  first_seen INTEGER NOT NULL,
  PRIMARY KEY (placeholder, original)
);
"""
```

四列一门亲：占位符、原文、实体类型、**首见时间**（毫秒时间戳）。主键是
`(placeholder, original)` 二元组——同一个占位符可以挂多条原文（`<PHONE_NUMBER>`
对应多个不同手机号），同一条"占位符×原文"对只存一行。这就是文件头注释说的
形态记票（[pii_store.py:13-15](soc-demo/services/guards/pii_store.py#L13)）：
wire 占位符保持 `<TYPE>` **不编号**（FR-S4.1 契约与票 24 契约测试不动），同一
占位符的多个原文以列表全收。对比常见的"带编号占位符"方案（`<PHONE_1>`、
`<PHONE_2>`）：编号方案反查是点对点，但 wire 文本形状会随命中的顺序漂移——
同一段文本今天脱出 `<PHONE_1>` 明天脱出 `<PHONE_2>`，下游契约测试全得跟着抖。
不编号的代价是"反查一回一串"，由 `first_seen` 首见序兜住稳定性（站 4）。

### 站 2 · 库文件落哪、连接怎么管

路径三级火箭：env 覆盖（测试接缝）→ CWD 相对路径 → compose 卷挂载把相对路径
钉到宿主盘。同一条 docstring 照顾了三种身份的读者：容器里的服务（CWD=/app）、
本机开发的进程（CWD=services/guards/）、测试（tmp_path）。**懒建**也是这里的一
个隐含语义——没人脱敏就先不开库（验收测试
[test_pii_mapstore.py:85-90](soc-demo/services/guards/test_pii_mapstore.py#L85)
专门锚了这一点：`assert not path.exists()` 在先）。

连接管理，单例 + 两个工程细节：

📄 [services/guards/pii_store.py:39-52](soc-demo/services/guards/pii_store.py#L39)

```py
class PiiMapStore:
    """sqlite 薄壳：record（脱敏时写）+ reveal（反查时读）。单连接复用——
    FastAPI 的 def 端点跑在线程池里，sqlite3 默认 check_same_thread=True 会炸，
    这里显式放行（写全是毫秒级小事务 + WAL，串行化由 sqlite 自己的锁兜底）。"""

    def __init__(self, path: str):
        if path != ":memory:":
            parent = os.path.dirname(path)
            if parent:
                os.makedirs(parent, exist_ok=True)
        self._conn = sqlite3.connect(path, check_same_thread=False)
        self._conn.execute("PRAGMA journal_mode = WAL")
        self._conn.executescript(DDL)
        self._conn.commit()
```

`check_same_thread=False` 的注释值得读两遍：FastAPI 的 `def` 端点（非 async）跑
在线程池里，同一只库连接会被不同线程先后使用——sqlite3 默认"谁建谁用"直接炸，
显式放行后靠 WAL + sqlite 自己的写锁兜串行化（写全是毫秒级小事务，抢不到就等）。
`PRAGMA journal_mode = WAL` 就是第一节你看到 `-wal`/`-shm` 文件的出处。

### 站 3 · record：幂等落账

📄 [services/guards/pii_store.py:54-63](soc-demo/services/guards/pii_store.py#L54)

```py
    def record(self, pairs: list[dict]) -> None:
        """写入 占位符→原文 对（重复对幂等）。pairs 元素：
        {placeholder: "<TYPE>", original: 原文切片, entity_type: TYPE}。"""
        now = int(time.time() * 1000)
        self._conn.executemany(
            "INSERT OR IGNORE INTO pii_map (placeholder, original, entity_type, first_seen)"
            " VALUES (?, ?, ?, ?)",
            [(p["placeholder"], p["original"], p["entity_type"], now) for p in pairs],
        )
        self._conn.commit()
```

`INSERT OR IGNORE` 吃掉主键冲突：同一段文本脱一百遍，账上永远只有一行——
**first_seen 也不刷新**（IGNORE 掉的那次连 `now` 都不落）。这保证"首见序"真是
首见序：第一个把某个手机号送进脱敏口的文本决定了它在反查列表里的位置。本步实测
把 6.1 的主探针原样重打两遍，行数纹丝不动（见"亲手验证 ③"）。

### 站 4 · reveal 与重启实验

📄 [services/guards/pii_store.py:65-72](soc-demo/services/guards/pii_store.py#L65)

```py
    def reveal(self, placeholder: str) -> list[str]:
        """按占位符反查全部原文（首见序）。查无此人 = 空表，由调用方落 404。"""
        rows = self._conn.execute(
            "SELECT original FROM pii_map WHERE placeholder = ?"
            " ORDER BY first_seen, original",
            (placeholder,),
        ).fetchall()
        return [r[0] for r in rows]
```

一条 SQL：按占位符精确匹配，`ORDER BY first_seen, original` 双键排序——首见时间
相同（同一次脱敏命中多个同型实体）时按原文典序，**输出顺序完全确定**。查无此人
返回空表，404 的落法在 app.py（6.1 站 1：一视同仁，不透露库存）。

重启实验在"亲手验证 ①"亲手做。这里先给个"进程内的重启等价物"——验收测试
怎么锁"落盘重启不丢"：

📄 [services/guards/test_pii_mapstore.py:49-53](soc-demo/services/guards/test_pii_mapstore.py#L49)

```py
def test_reopen_store_survives_restart():
    """验收 1：落盘重启不丢。reset_store() 关掉现连再按同一路径重开 = 换进程的等价物。"""
    anonymize(TEXT)
    pii_store.reset_store()
    assert reveal("<PHONE_NUMBER>").json()["originals"] == [PHONE]
```

`reset_store()`（[pii_store.py:90-96](soc-demo/services/guards/pii_store.py#L90)）
关掉旧连接、清掉单例指针——下一次 `get_store()` 按同一路径重开新库。测试里它
扮演"重启"：**同一文件路径重开，映射还在 = 落盘生效**。测试是进程内的等价复现，
本步的实验则是真刀真枪 `docker restart`——两层证据一个结论。

## 三、服务与中间件卡

**卡 1 · SQLite 当嵌入式账本（自持 sqlite 薄壳）**

- **它是什么**：不引数据库服务，把"一张表+两条 SQL"的需求交给进程内的 SQLite
  文件。全仓四例：M2 案卷库、agent 运行库（含 runs 队列）、chroma 背后的存储、
  本步的 pii-mapstore——同一件工具，四种账本。
- **本项目怎么配置**：`sqlite3.connect` + WAL + 单例连接（站 2）；路径走 env
  接缝；数据落宿主靠 compose bind mount（卡 2）。
- **市面替代**：①Redis（内存库+快照，重启语义靠配置，还多养一个服务）；②
  Vault Transit / 专门的映射服务（企业级 token 保管库，重）；③纯内存字典
  （PRD 原口径，重启即丢——正是 ADR 0004-3 改判掉的形态）。
- **本项目为什么选 SQLite**：账本的需求是"**写得进、查得出、重启不丢、零运维**"，
  SQLite 四项全占且零依赖；"映射在盘上"是反查口的生命线，内存字典给不了承诺。
  代价（并发写弱、跨进程共享要小心）在这个量级（一张表、毫秒级小事务）不存在。
- **业务上怎么选**：单服务小账本（映射、队列、缓存索引）→ SQLite；多服务共享
  一份状态 → 别用文件，上真数据库；密钥级敏感数据的保管 → Vault 类专件（带
  审计、租期、轮换），SQLite 账本配文件系统权限兜底够 demo 与小团队用。

**卡 2 · bind mount 与数据生命周期（compose volumes 口径）**

- **它是什么**：compose 把宿主机目录原样挂进容器（`./data/guards:/app/data`），
  容器层的读写就是宿主层的读写——容器销毁重建，数据原地不动。
- **本项目怎么配置**：guards 与 case-backend（`./data/case-backend`）、agent
  （`./data/agent`）同款口径——**三只业务库三只宿主目录**，谁的数据谁一个柜子。
- **市面替代**：①named volume（Docker 管理的卷，不占仓库目录，但"数据在哪"
  对人不可见）；②对象存储/网络盘（多机共享时用）；③不挂载（数据随容器亡——
  明确拒绝）。
- **本项目为什么选 bind mount**：教学与调试要**看得见摸得着**——本步的机检、
  只读核查、甚至"偷库"捣乱推演，都因为库文件就躺在仓库目录里才可亲手做；
  1.2 的 SQLite 铁律（宿主只读 `mode=ro`）也建立在同一事实上。
- **业务上怎么选**：单机部署/开发环境 → bind mount（直观）；生产集群 → named
  volume 或云盘（可迁移、可快照）；无论哪种，**数据的生命周期要跟容器分开管**——
  "容器可弃、数据长存"是有状态服务的第一课。

## 六、捣乱实验（必选）

**捣乱 A · 内存对照组：FR-S4.2 原口径会怎么死**（亲手证明"映射在盘上不在内存"
的另一半——如果它只在内存，重启即忘）：

```bash
docker exec soc-demo-guards-1 python -c "
import os
os.environ['PII_MAPSTORE_PATH'] = ':memory:'
from pii_store import get_store, reset_store
get_store().record([{'placeholder':'<CN_ID>','original':'110101199003070000','entity_type':'CN_ID'}])
print('进程1 reveal:', get_store().reveal('<CN_ID>'))
reset_store()"
docker exec soc-demo-guards-1 python -c "
import os
os.environ['PII_MAPSTORE_PATH'] = ':memory:'
from pii_store import get_store, reset_store
print('进程2 reveal:', get_store().reveal('<CN_ID>'))
reset_store()"
```

预期（实测逐字）：进程 1 查得到 `['110101199003070000']`，进程 2 查到 `[]`——
`:memory:` 库随进程亡。这就是 PRD FR-S4.2 原文"映射表仅服务端内存保留、会话/run
结束即弃"的活样子：**脱敏完一个会话，反查口就永久失忆**。ADR 0004 裁决 3 改判
成落盘，改的不是实现是语义——"做了映射就配一个受控反查口"，映射的生命周期从
会话级拉到永续，反查才有粮。判据：进程 2 查空 = 复现成功；落盘模式（验证 ①）
同实验查得回 = 对照成立。

**捣乱 B · 伪造占位符形状扫雷**（反查口的输入面：什么形状给什么待遇）：

```bash
for p in '<FOO>' '<cn_id>' ' ' ' <CN_ID> '; do
  printf '%-12s => ' "$p"
  curl -s -X POST http://127.0.0.1:8001/pii/reveal -H 'content-type: application/json' \
    -d "{\"placeholder\":\"$p\"}" -w ' [%{http_code}]'
  echo
done
```

预期（实测逐字）：

- `<FOO>` → 404 `placeholder_unknown`——形状像，库里没有；
- `<cn_id>` → 404——**大小写敏感**，占位符必须是大写实体名（精确匹配，不猜）；
- `' '`（纯空格）→ 400 `placeholder_required`——strip 后为空，参数不合格式；
- `' <CN_ID> '` → 200 命中——首尾空格被 strip 容错（app.py 站 1 的
  `placeholder.strip()`）。

判据：四种输入四种待遇各归各位（404/404/400/200），且两个 404 的响应体**逐字
相同**——查无此人统一口径，绝不暗示"库里还有别的"。这层是 guards 的裸口待遇；
6.3 要在 agent 侧看到同一张扫雷图怎么被"角色闸"再包一层——**裸口只认账，
闸口才认人**。

**捣乱 C · 纸面推演：重启偷映射行不行**（不动手的思考题）：攻击者想让反查口
失忆或想偷走对照表，各需要什么？让映射丢：光 `docker restart` 没用（本步主实验），
得**删宿主文件** `soc-demo/data/guards/pii-mapstore.*`——攻击面从"容器"上移到
"宿主机文件权限"；在容器里删也没用吗？有用，但那已经是拿到容器内任意执行权之后
的事，且删了宿主文件它自己也得走 bind mount（同一只文件）。偷映射：同一条路——
宿主读 `mode=ro` 就能全文捞出原文。结论：**mapstore 的安全边界不在容器，在宿主
机的文件权限与机房门禁**；应用层管的是"谁能走反查口"（6.3），存储层管的是
"谁够得着柜子"——两层别指望互相替班。
