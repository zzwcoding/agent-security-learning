# 1-4 · 分诊六节点（上）：执行器、领单、问知识库、查同主机

> 场景 1 第 4 步。1.3 结尾 run 拿到了任务票；这一步进入**分诊台**内部：图纸怎么变成
> 真在跑的流水线（LangGraph 执行器），以及前三个节点——领卷宗（load_alert）、问知识库
> （kb_check）、查同主机正在办的案子（merge_check）。

**位置感**：

```
✅ 1.1 布景与推单
✅ 1.2 去重与落库
✅ 1.3 自动拉起与铸票
✅ 1.4 分诊六节点（上）（你在这里：执行器 + 前三节点）
⬜ 1.5 分诊六节点（下）（自我声明 + LLM 判定 + 落判）
⬜ 1.6 收官透视
```

## 一、这一步做什么

分诊（triage）是数字员工的核心手艺：把一条告警判成 **FP**（误报，狼没来）/**BTP**
（良性真报，狼来了但是自家的看门狗）/**TP**（真报，狼来了）/**Uncertain**（拿不准，
交人）。判定的工序是固定六步（PRD §6-M4 定死）：

```
load_alert → kb_check → merge_check → self_audit_checkpoint → verdict_llm → outcome
  领卷宗      问知识库     查同主机        建案前自我声明            LLM 判定      落判
```

本步讲两件事：**流水线本身怎么转**（LangGraph 执行器：谁在推节点走、每走一步留下
什么痕迹），以及**前三步**——它们全是"动手前先摸清情况"的确定性工序。后三步
（自我声明、AI 判定、落判）是下一步 1.5 的主菜。

真实数据先行：主角告警（vt-87105 报毒，web-01 主机）的分诊已经跑完了，它在
事件流里留下了一条完整的脚印，本步边讲边对脚印。

## 二、调用链

```
1.3 的 dispatcher executeStartJob（票已到手）
  │ 铸好的任务票 + run 交接态 {kind, alert_id}
  ▼
▼ services/agent/src/graph.ts（执行器，框架 ▲LangGraph.js）
  站 0  runFlow()            run: queued→running；审计镜像成事件
  站 1  compileFlowGraph()   FlowNode[] 声明成 StateGraph：每节点套一层
  │                          「node_enter → 限步 → 干活 → node_exit → 盖检查点」
  ▼
▼ workers/triage/flow.ts（分诊六节点，前三个）
  站 2  load_alert           亮票领卷宗（get_alert）+ 抢分诊锁（claimVerdict）
  站 3  每个动作的闸 makeGatedCall   验票 → 闸拒=DENIED+强杀 / 放行=广播+执行
  站 4  kb_check             亮票查知识库（kb_lookup，chroma 向量检索）+ 命中再安检

```

### 站 0 · 开跑：run 接管与"审计即广播"

📄 [services/agent/src/graph.ts:393-403](soc-demo/services/agent/src/graph.ts#L393)
（`runFlow` 开头）：

```ts
async function runFlow(db: DB, runId: string, deps: DriveDeps, plan: FlowPlan): Promise<RunRow> {
  const { ctx, budget, nodes } = deps;
  const actor = ctx.actor ?? { type: "system", id: "m3:supervisor" };
  // 审计 → SSE 的镜像：审计是真相源，事件流是它的广播（PRD §6-M3 事件类型含 audit）
  const mirrorAudit = (entry: Record<string, unknown>) => emitEvent(db, runId, "audit", entry);
  const transitionAndMirror = (to: RunRow["status"]) => {
    const from = (getRun(db, runId) as RunRow).status;
    transitionRun(db, runId, to, ctx);
    mirrorAudit({ action: "update", result: "SUCCESS", status: { from, to } });
  };
  transitionAndMirror("running");
```

run 状态 `queued→running`（走 1.3 讲过的 `transitionRun` 状态机正门，INV-10），
且每次迁移都**镜像一条事件**。你待会在亲手验证里看到的事件流第一行
`audit|{"status":{"from":"queued","to":"running"}}` 就是它。设计口吻是"**审计是
真相源，事件流是它的广播**"——台账（audit_entries）和叫号屏（run_events）记同一
件事，看哪个都行，但只有台账是法定的。

### 站 1 · 图纸变机器：FlowNode[] → StateGraph

六节点在 [flow.ts:122-330](soc-demo/services/agent/workers/triage/flow.ts#L122)
里就是一个普通数组 `FlowNode[]`（每项 `{name, run}`）。把它变成真流水线的是
LangGraph.js 的 StateGraph——先看**每个节点被套的那层壳**
📄 [services/agent/src/graph.ts:351-365](soc-demo/services/agent/src/graph.ts#L351)：

```ts
  type FlowUpdate = { run: Record<string, unknown> };
  const entries: [string, (state: typeof RunFlowState.State) => Promise<FlowUpdate>][] =
    deps.nodes.map((node) => [
      node.name,
      async (state) => {
        cursor.node = node.name;
        emitEvent(db, runId, "node_enter", { node: node.name });
        deps.budget.step(); // 资源兜底之一：max_steps（默认 20）
        const working = { ...state.run };
        await node.run({ ...nctx, state: working });
        emitEvent(db, runId, "node_exit", { node: node.name });
        progress.completed += 1;
        saveProgress(db, runId, progress.completed, deps.budget.tokens);
        return { run: working };
      },
    ]);
```

每个节点的壳干五件事：**进节点广播** `node_enter` → **计一步**（预算闸：最多 20 步，
超了强杀，防流程打转烧钱）→ 把流水线状态浅拷贝一份给节点**原地改** → **出节点广播**
`node_exit` → 进度和 token 记账回写 run 行。再接线：
📄 [services/agent/src/graph.ts:367-377](soc-demo/services/agent/src/graph.ts#L367)：

```ts
  const sg = new StateGraph(RunFlowState).addSequence(entries);
  sg.addEdge(START, deps.nodes[0].name);
  for (let i = 0; i < deps.nodes.length - 1; i++) {
    sg.addEdge(deps.nodes[i].name, deps.nodes[i + 1].name);
  }
  sg.addEdge(deps.nodes[deps.nodes.length - 1].name, END);

  // checkpointer = 信封 hash 链（BaseCheckpointSaver）；nodeLabel 让每个节点跑完后的
  // 框架检查点盖上「刚跑完的节点名」，框架簿记检查点（输入态）落成 __input__。
  const checkpointer = new EnvelopeCheckpointSaver(db, () => cursor.node);
  return sg.compile({ checkpointer });
```

`addSequence` 按数组顺序一条边一条边串起来，末节点接 `END`——六节点子图在声明里
直接可读。两件值得记住的事：

- **每个节点跑完盖一个"检查点"**（checkpoint＝存档点）：`durability: "sync"`
  （[graph.ts:416](soc-demo/services/agent/src/graph.ts#L416)）保证存档落库后才走
  下一步。存档不是普通备份——它是**信封 hash 链**（EnvelopeCheckpointSaver，文件
  [checkpointer.ts](soc-demo/services/agent/src/checkpointer.ts)）：每份存档盖上
  前一份存档的指纹，一环扣一环。谁中途改了历史状态，链条对不上当场穿帮——这是
  审批 resume（场景 4）"重启后接着跑还算数"的信任根基。
- **为 LangGraph 值不值？** 这就是阶段 7 体检后补票 23 的故事：原来这里是手写
  执行循环，[graph.ts:1-5](soc-demo/services/agent/src/graph.ts#L1) 头注释写明
  "手写执行循环换成 @langchain/langgraph 的 StateGraph 声明编排……L2 挂起/恢复走
  框架原生 interrupt()/Command(resume)"。框架真正还的债在**挂起/恢复**（场景 4
  的审批中断），本步先记住：节点、边、存档点都是框架的标准件。

### 站 2 · load_alert：领卷宗，顺便抢锁

📄 [services/agent/workers/triage/flow.ts:123-144](soc-demo/services/agent/workers/triage/flow.ts#L123)：

```ts
      name: "load_alert",
      run: async (ctx) => {
        cursor.node = "load_alert";
        const alertId = ctx.state.alert_id as string;
        const alert = await gated(ctx, "get_alert", { alert_id: alertId }, () => deps.m2.getAlert(alertId));
        if (!alert) throw new Error(`alert_not_found:${alertId}`);
        ctx.state.alert = alert;
        // FR-M4.5 拾取即锁（M2 条件更新 WHERE verdict IS NULL）。抢锁失败 = 另一个
        // run 已拾取同一条告警：本 run 让路（completed + skipped），绝不重复分诊。
        const claim = await deps.m2.claimVerdict(alertId);
        if (!claim.ok) {
          ctx.state.triage = { skipped: true, reason: claim.reason };
          record({
            action: "triage_skip",
            objectId: alertId,
            objectType: "alert",
            details: { reason: claim.reason, run_id: deps.runId },
            result: "SUCCESS",
          });
        }
      },
```

领卷宗（`get_alert`）本身是一次工具调用——**第一个动作就先亮票**（`gated(...)`，
下一站拆它）。抢锁这一下更值得看：出站实现是往 M2 发
`PATCH /api/v1/alerts/:id {verdict:"in-progress"}`（[m2.ts:77-82](soc-demo/services/agent/workers/triage/m2.ts#L77)），
而 M2 那头的落点是这条 SQL（📄 [services/case-backend/src/store.ts:583-587](soc-demo/services/case-backend/src/store.ts#L583)）：

```ts
      if (body.verdict === "in-progress") {
        const res = db.prepare(
          "UPDATE alerts SET verdict = 'in-progress' WHERE id = ? AND verdict IS NULL",
        ).run(alertId);
        if (res.changes === 0) throw new VerdictLockedError(alertId); // 别人已拾取/已终值
```

大白话：这条 UPDATE 带一个**附加条件** `AND verdict IS NULL`——只有"还没人认领"
的告警才改得动；改动行数为 0 = 锁在别人手里，当场报 409。这就是 1.3 说的
"并发同告警只分诊 1 次"的最后兜底：autorun 防重（站 2 上一课）管"我不重复拉"，
这把锁管"别人拉了我也白拉"。抢锁失败的 run 不算失败——它把 `triage.skipped`
置位，后面五个节点全部让路（每个节点开头第一行 `if (skipped(ctx)) return;`），
run 体面地 `completed` 收场，台账记一条 `triage_skip`。

### 站 3 · 每个动作的闸：makeGatedCall

站 2 的 `gated(ctx, "get_alert", params, action)` 是分诊 worker 的**唯一动作入口**，
闸体在 📄 [services/agent/src/gated-call.ts:73-95](soc-demo/services/agent/src/gated-call.ts#L73)：

```ts
    const hash = paramsHash(params);
    const verdict = verifyTicket(
      { name: tool, params },
      deps.creds(tool, params),
      Math.floor(Date.now() / 1000),
      { hmacKey: deps.hmacKey },
    );
    if (!verdict.allow) {
      const site = deps.deny({ tool, reason: verdict.reason, paramsHash: hash });
      site.record({
        action: "deny",
        objectId: site.objectId,
        objectType: site.objectType,
        details: { tool, reason: verdict.reason, params_hash: hash, ...site.extraDetails },
        result: "DENIED",
      });
      throw new Error(`${deps.prefix}_gate_denied:${verdict.reason}`);
    }
    deps.onAllow?.(verdict);
    deps.emitToolCall?.(ctx, { tool, paramsHash: hash });
    const result = await action();
    deps.emitToolResult?.(ctx, { tool });
    return result;
```

四步舞：**①算参数指纹**（paramsHash：参数规范化后取 SHA-256，[mint.py:37-40](soc-demo/services/gateway/mint.py#L37)
同源口径——"你到底要用什么参数"这件事被钉死成指纹，事后换参数=对不上指纹）；
**②验票**（verifyTicket 拿任务票重算防伪章、查过期、查这个工具在不在票面的
allowed_tools 里——六个拒绝理由的细节留给场景 4）；**③闸拒**（台账记 DENIED +
**抛错**——错误一路抛回站 1 的壳，run 被 1.3 见过的强杀逻辑打成 failed。fail-closed：
闸说不，就没有任何"绕过去试试"）；**④放行**（广播 tool_call → 干活 → 广播
tool_result）。票 43 之前这套舞步在六个 worker 里复印了六遍还漂移出三处微差
（[gated-call.ts:3-8](soc-demo/services/agent/src/gated-call.ts#L3) 头注释自查原文），
现在收成一份——**安全语义只许有一份拷贝**。

### 站 4 · kb_check：问自家台账（KB 优先核验）

📄 [services/agent/workers/triage/flow.ts:148-177](soc-demo/services/agent/workers/triage/flow.ts#L148)：

```ts
      run: async (ctx) => {
        if (skipped(ctx)) return;
        cursor.node = "kb_check";
        const alert = ctx.state.alert as AlertDto;
        const params = { host: hostOf(alert), path: pathOf(alert) ?? "", user: userOf(alert) ?? "" };
        const hits = await gated(ctx, "kb_lookup", params, () =>
          deps.kb.lookup({
            host: params.host || undefined,
            path: params.path || undefined,
            user: params.user || undefined,
          }),
        );
        // m7 卡备注：检索注入内容同样过不可信包装（guards kb 通道：命中 strip 清洗，
        // block 剔除该条）——知识库内容对 LLM 仍是数据不是指令。
        const cleaned: KbHit[] = [];
        for (const hit of hits) {
          const d = await scan(`${hit.title}\n${hit.body}`, "kb", deps.scanOpts);
          if (d.blocked) {
            record({
              action: "guards_block",
              objectId: deps.runId,
              objectType: "kb_hit",
              details: { title: hit.title, action: d.action, reason: d.reason ?? null },
              result: "DENIED",
            });
            continue;
          }
          cleaned.push(d.action === "strip" && d.text ? { ...hit, body: d.text } : hit);
        }
        ctx.state.kb = cleaned;
      },
```

两个看点。**其一，查什么**：拿主机名/文件路径/用户名三个可观测物去查知识库——
"这台机器是不是自家资产？这个路径是不是登记过的计划内变更？"这是 FR-M4.2 的
**KB 优先核验**：先查内部事实，再看外部威胁情报，顺序不能反（否则一台被误报的
自家服务器可能被当成攻击目标）。生产检索面是 chroma 向量库：
📄 [services/agent/workers/knowledge/kb.ts:23-35](soc-demo/services/agent/workers/knowledge/kb.ts#L23)：

```ts
  async lookup(params: KbLookupParams): Promise<KbHit[]> {
    const q = [params.host, params.path, params.user].filter(Boolean).join(" ");
    if (!q) return [];
    let hits;
    try {
      hits = await this.store.query(q, this.k);
    } catch (e) {
      // fail-open（可用性）：检索面病了 → 等价无 KB（PRD 异常与边界），留下可见痕迹
      console.warn(`[kb] 检索面不可达，降级为 0 命中：${e instanceof Error ? e.message : String(e)}`);
      return [];
    }
    return hits.map((h) => ({ kind: h.metadata.kind, title: h.metadata.title, body: h.text }));
  }
```

注意这里的口径反转：**检索面病了不拦流程**，记行日志降级为 0 命中继续分诊
（fail-open）。跟闸的 fail-closed 正好相反——因为知识库是**提速件**不是**安全闸**
（[kb.ts:8-9](soc-demo/services/agent/workers/knowledge/kb.ts#L8) 注释原话）：
查不到 KB 无非慢一点、笨一点，拦住告警才是事故。

**其二，KB 里的东西也不是自己人**：命中的每条知识都要过 guards 注入扫描
（`scan(..., "kb")`）——知识库是人审后入库的（INV-5，检索面里物理不存在未审条目），
但"审核过的内容"仍可能在教会话时被塞了私货，所以对 LLM 而言它仍是"别人递的话"，
照规矩安检。（投毒 KB 攻防是场景 5.3 的主菜。）

问的是：**这台机器 24 小时内有没有还没结案的案子？** 出站落到 M2 的

库内是这条 SQL（📄 [services/case-backend/src/store.ts:734-746](soc-demo/services/case-backend/src/store.ts#L734)）：

```ts
export function findActiveCases(db: DB, host: string, withinHours: number): unknown[] {
  const since = nowMs() - withinHours * 3_600_000;
  return (
    db
      .prepare(
        `SELECT c.* FROM cases c
         JOIN observables o ON o.case_id = c.id AND o.data_type = 'hostname' AND o.data = ?
         WHERE c.status IN ('New', 'InProgress') AND c.start_date >= ?
         GROUP BY c.id ORDER BY c.number DESC`,
      )
      .all(host, since) as Record<string, unknown>[]
  ).map((r) => mapCase(r));
}
```

查的是案件名下**hostname 类型的可观测物**（1.1 站 4 埋的伏笔在这里兑现：当初
从告警里抽出的 hostname observable，现在成了归并的钥匙）。查到的结果存进
`ctx.state.merge`，它的两个关键字段（查了几件活跃案、有没有同主机案）会在 1.5 的
self_audit 和 outcome 里当裁判用。**你现在就能看到它的效果**：布景 12 条告警全来自
少数几台主机，TP 的归并成了 4 个案子（db-01/app-01/web-01/centos7 各一）——主角
告警到分诊台时 web-01 已有活跃案，于是它走的是**并入**而不是新建（1.5 的 outcome
站细讲这个分岔）。

## 三、服务与中间件卡

**卡 1 · ▲LangGraph.js —— 流水线的轨道与道岔**

- **替我们干了件什么体力活**：把"一串节点按序跑、跑到某节点可能要**停下来等人**、
  等到了**从原地接着跑**"这件脏活包了。我们只声明节点和边（站 1 的十几行），挂起
  （`interrupt()`）、唤醒（`Command(resume)`）、存档节奏（checkpointer）都是框架
  原生件。最大的债在场景 4：审批挂起时 run 停在节点中间，值班长批准后**从信封链
  末态续跑**——这个"暂停/续跑"如果手写，就是一套自研状态机 + 持久化 + 恢复语义。
- **自研还是开源**：开源（@langchain/langgraph，LangChain 官方编排库）。本项目
  票 23 从手写循环**回补**成它——那是一次真实的"框架红线"教训（阶段 7 体检发现
  承诺的框架被手写替代，记 ADR 0002 强制回补）。
- **本项目怎么配置**：[graph.ts:185-190](soc-demo/services/agent/src/graph.ts#L185)
  声明图状态（单通道 `run`，后写覆盖）；`compile({ checkpointer })` 挂上自研的
  信封存档器；`thread_id` 即 run_id——框架的"会话"概念直接对齐 run 实体。
- **市面上同类**：Temporal/Camunda（工作流引擎，重、面向业务流程）、自研执行循环
  （本仓的前世）、XState（状态机，前端味）、简单 for 循环（无挂起恢复能力）。
- **本项目为什么选它**：AI 工作流的"人在环上"（human-in-the-loop）是一等公民
  ——`interrupt()` 就是为"跑到一半等人拍板"设计的；且它是 TypeScript 库，跟
  agent 服务同语言，不引入第二个运行时。
- **业务上怎么选**：AI 步骤+人工审批混合、要断点续跑 → LangGraph；纯业务审批流
  （表单/审批人/超时升级）→ Camunda 类 BPM；不需要挂起的固定管道 → 普通函数
  串行就够了，**别为用框架而用框架**。

**卡 2 · ▲chroma —— 知识库的检索面**

- **替我们干了件什么体力活**：向量检索。传统检索靠关键词对上就对上（LIKE '%web-01%'），
  向量检索把文本变成一串数字（向量），**意思近的数字距离近**——"web-01 上的计划内
  变更"和"web01 的变更登记"字面不同、意思相同，关键词查不到，向量查得到。chroma
  就是专门存这些向量、按距离找最近 K 条的开源数据库。
- **本项目怎么配置**：官方镜像一个容器（:8000，digest 钉版）；agent 侧
  [index.ts:62](soc-demo/services/agent/src/index.ts#L62) 一行决定用不用它：
  `KB_CHROMA_URL` 设了（compose 里设为 `http://chroma:8000`）→ 生产 ChromaKb；
  没设 → MemoryKb 离线种子（4 条手写条目，[triage/kb.ts:26-51](soc-demo/services/agent/workers/triage/kb.ts#L26)），
  离线开发不依赖任何容器。检索 top-k=5（决策记录 #6，[kb.ts:18](soc-demo/services/agent/workers/knowledge/kb.ts#L18)）。
- **市面上同类**：pgvector（PostgreSQL 插件，库顺手带上）、FAISS（库不是服务，
  进程内）、Milvus/Qdrant（独立向量库，规模更大）、Elasticsearch（混合检索）。
- **本项目为什么选 chroma**：教学规模（几十条知识）、一行 compose 起容器、
  HTTP 接口简单到本章看得懂、自带持久化目录挂载（`data/chroma`）。
- **业务上怎么选**：原型/小规模 → chroma 或 pgvector（已有 PG 就 pgvector）；
  千万级向量/多租户 → Milvus/Qdrant；要全文+向量混合 → Elasticsearch；
  **别忽略的通用规律**：向量库解决"怎么找"，解决不了"存的东西对不对"——
  入库闸门（本项目 INV-5 人审通道）永远在库外面。

## 四、防线对号

- **INV-3（票面无 L2）+ 唯一动作入口**：load_alert/kb_check/merge_check 三个节点
  的每一次出站都是 `gated(...)` 亮票——查案、查 KB、查活跃案全是**只读**工具，
  但照样过闸；闸体全仓只有 makeGatedCall 一份（站 3），安全语义不兴复印件。
- **INV-1（fail-closed）**：闸拒 = DENIED 台账 + 抛错强杀（站 3）；对照面是 KB
  检索的 fail-open 降级（站 4）——**哪里必须死板、哪里允许变通，是按"这东西是
  安全闸还是提速件"定的，不是随手选的**。
- **INV-6 的最后兜底**：verdict 拾取锁（站 2，条件 UPDATE）——三个防重层次的
  第三层，"并发同告警只分诊 1 次"压在一条 SQL 上。
- **INV-5（人审唯一入库通道）**：kb_check 的检索面物理只见 approved 条目——
  不是查询时过滤，而是**入库时就只放进过审的**（[kb.ts:4-6](soc-demo/services/agent/workers/triage/kb.ts#L4)
  注释："检索面里只有 kb_write（人审批准后）放进去的条目，proposed/rejected
  物理不可见"）。
- **信封 hash 链（防篡改）**：每节点一存档、存档带前链指纹（站 1）——run 的
  一生（含每个节点改了什么状态）事后不可抵赖、不可涂改，这是场景 4 审批 resume
  的信任底座。
