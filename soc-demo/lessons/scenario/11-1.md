### 站 2 · 装载与投影：机制只认识四个字段

📍 大图节点:HUNT_PACK(11.1 内容层装载包)

卡怎么进入运行系统？装载逻辑住在**内容层**的
[hunt-pack.ts](soc-demo/services/agent/workers/investigation/hunt-pack.ts)（m5 领地，
文件头注释自证"零机制代码"，[:1-13](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L1)）：

```ts
export function loadHuntTemplates(dir: string = HUNT_TEMPLATES_DIR): HuntTemplateFixture[] {
  return readdirSync(dir)
    .filter((f) => f.endsWith(".json"))
    .map((f) => JSON.parse(readFileSync(join(dir, f), "utf8")) as HuntTemplateFixture)
    .sort((a, b) => a.template_id.localeCompare(b.template_id));
}
```

（[hunt-pack.ts:51-56](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L51)）
装载就是把目录下 `*.json` 逐个读进来——**第四张卡落盘即入册，没有任何注册代码要动**。
登记缝是 [HuntTemplateSource](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L64)
（[:64-84](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L64)，票 79① 的
注册缝实现）：`of(templateId)` 命中卡 → 投影给机制；未登记 id → 落机制默认档。

投影函数是分层铁律的手术刀（[:59-61](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L59)）：

```ts
export function toLoopTemplate(f: HuntTemplateFixture): LoopTemplate {
  return { templateId: f.template_id, maxRounds: f.max_rounds, maxTasks: f.max_tasks, menu: [...f.menu] };
}
```

**机制四字段以外的内容字段（句式族/槽位/waves/遏制建议）一个都不进机制**——机制层
的格式契约只有 [template.ts:9-15](soc-demo/services/agent/src/orchestration/template.ts#L9)
的 `DEFAULT_TEMPLATE` 同款形状（那是 R10 边界规则钦定的"格式类型定义单文件例外"），
[TERMS「预案卡」](TERMS.md)条口径："机制层写一次（循环只认格式契约+上限四字段），
业务内容全是数据"。

机制侧消费这张卡的入口有两处（机制文件**只认接口不认业务**）：

- 父票面单一来源：[run-kinds.ts:300](soc-demo/services/agent/src/run-kinds.ts#L300)
  `allowedTools: huntFlowTicketFace()`——票面 = 机制默认菜单 ∪ 全部卡的菜单 ∪ register
  （[hunt-pack.ts:88-90](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L88)），
  第四张卡入册时票面并集**没有变大**（ir 的 5 件全在既有并集内——11.4 的"零登记增量"
  对账咬的就是这个）；
- planner 每轮可见菜单：模板圈定的子集注入
  （[TERMS「派工菜单」](TERMS.md)条），装配在
  [index.ts:181](soc-demo/services/agent/src/index.ts#L181)
  `new HuntTemplateSource(new DefaultTemplateSource())` 与

  一行，票 93② 之后就绪。

## 三、服务与中间件卡

**卡 1 · ▼预案卡（JSON 数据文件，fixtures/hunt-templates/）**

- **它是什么**：一个业务的全部内容声明——身份、句式族、菜单子集、上限、既定查询计划、
  遏制建议文本；被内容层装载包读入、按机制四字段投影进循环。
- **市面替代**：SOAR 平台的 playbook 编辑器（表单+数据库）；或把业务规则硬编码进
  编排引擎。
- **为何这么选**：数据文件进 git = 每个业务的"配方"有版本、有 diff、有评审；新业务
  PR 到来时，评审者看的就是这一个文件——业务边界在 review 里一目了然（菜单收窄了
  什么、上限给了多少）。编辑器适合运营期，教学与验收期数据文件最诚实。
- **业务上怎么选**：业务结构同构（都是"怀疑→查证→收敛"）→ 模板数据化；出现真正的
  结构差异（如 §13.4 候选表里的"扇出宽度现场决定"）→ 那才是机制演进票，回 L0。

## 场景题闯关（本步 1 题）

**Q：把 ir 卡的 `max_rounds` 从 6 改成 60，机制的哪段代码会变？预算双闸为什么拦不住
"烧穿"？提示：回看 [TERMS「预案卡」](TERMS.md)条与
[TERMS「查证轮」](TERMS.md)条的预算双闸分层。**

<details><summary>答案（点击展开）</summary>

机制代码一行不变——`max_rounds` 是机制四字段之一，模板数据改 6→60，投影函数原样把
60 送进机制，循环照单全收（"登记面缺席 ≠ 拒跑"的同一枚硬币：数据在契约内，机制不
质疑）。预算双闸是**机制侧的天花板**（run 级闸先抛、轮级闸后抛，20 轮硬顶开跑前即拒，
[TERMS「查证轮」](TERMS.md)条）：60 超过机制硬顶的部分开跑前就会被拒——所以"烧穿"
拦得住，但**业务为什么想要 60 轮**才是对账要点：卡的上限是业务对"这门生意最多花多少"
的表态，把表态调到机制顶格 = 让每次取证都按最坏预算排期，业务评审该问的是"6 轮
为什么不够"，而不是让数字野蛮生长。这正是 11.2 要讲的：**机制管天花板，数据管表态**。</details>
