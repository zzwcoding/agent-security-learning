## 一、操作（位置感）

九服务 healthy（`docker compose ps`），`AGENT_LLM=fake` 教学档。真栈发一条 C2 心跳
怀疑书（S9 的同一扇门 [POST :3002/api/v1/hypotheses](soc-demo/services/case-backend/src/app.ts#L343)，
template_id=hunt_c2_beacon，文本=c2 卡句式族渲染的标准实例）：

```bash
RESP=$(curl -s -m 5 -w "\n%{http_code}" -X POST localhost:3002/api/v1/hypotheses \
  -H 'content-type: application/json' -H 'x-actor-id: soc1@soc.local' \
  -d '{"text":"怀疑主机 web01 存在 C2 心跳：外联目的 203.0.113.66 出现周期性信标，且 sh 由 cron 拉起维持持久化。","template_id":"hunt_c2_beacon"}')
echo "$RESP" | tail -1        # 预期 201
HYP=$(echo "$RESP" | head -1 | python3 -c "import json,sys; print(json.load(sys.stdin)['id'])")
echo "HYP=$HYP"
sleep 14                       # 教学栈三轮接力（round_relay 事件拉起，S9 9.4 口径）
curl -s -m 5 "localhost:3002/api/v1/hypotheses/$HYP" | python3 -c "
import json,sys
h = json.load(sys.stdin)
print('终态:', h['status'], '| template_id:', h.get('template_id'))
for r in h.get('rounds', []):
    tools = ','.join(t['tool'] for t in r.get('tasks', []))
    j = r.get('judge') or {}
    print(f\"轮{r['round_no']}: {tools}  judge.sufficient={j.get('sufficient')} verdict={j.get('verdict')}\")"
```

实测（主角：`HYP=hyp_265f157e-e59d-4903-8dfa-4849c693a1e5`，2026-09-13 本机栈）：

```
终态: concluded | template_id: hunt_c2_beacon
轮1: playbook_lookup  judge.sufficient=False verdict=None
轮2: outbound_conn_query  judge.sufficient=False verdict=None
轮3: outbound_conn_query,proc_lineage_query  judge.sufficient=True verdict=hit
```

**轮 1 的组合里出现了 `playbook_lookup`**——这就是本步的可观察变化：planner 的消费面
扩到知识源了。它在 [TERMS「查证轮」](TERMS.md)条的第一轮先去查剧本库（"三个月前有人
猎过同款吗"），13.2 专门走查它查到了什么。

## 二、调用链与真实落点

### 站 1 · 菜单从哪来：预案卡是唯一真源（机制不持第二份清单）

📍 大图节点:TPL_CARD(13.1 预案卡=菜单真源)

[TERMS「派工菜单」](TERMS.md)条的铁律：拟单只能照菜单点，菜单真源是模板注入的子集，
**机制不持第二份工具清单**。c2 卡的 menu 字段
（[hunt_c2_beacon.json:8](soc-demo/fixtures/hunt-templates/hunt_c2_beacon.json#L8)）：

```json
"menu": ["playbook_lookup", "graph_query", "outbound_conn_query", "proc_lineage_query"]
```

四件工具两半分家：`playbook_lookup`/`graph_query` 是**知识面**（本场景主角），
`outbound_conn_query`/`proc_lineage_query` 是**取证面**（S9 已教）。intake 节点把卡上
菜单原样注入交接态（[flow.ts:119](soc-demo/services/agent/src/orchestration/flow.ts#L119)
`ctx.state.menu = [...template.menu]`），planner 的可见世界就此圈定——**菜单收窄即选路
空间收窄**，知识工具进菜单 = 选路空间多了知识维度，机制层零 if/else。

装载链与 S11 同款：[index.ts:181](soc-demo/services/agent/src/index.ts#L181)
`HuntTemplateSource(new DefaultTemplateSource())` 登记缝——三族+应急卡优先、未登记 id
落机制默认档（[template.ts:9-14](soc-demo/services/agent/src/orchestration/template.ts#L9)
的默认菜单只有 kb_lookup/siem_query/related_alerts 三件**旧世界**工具，根本没有知识面）。
对照着看就明白"消费面扩容"扩的是什么：**默认档的菜单里没有剧本库和图谱**——是
[TERMS「预案卡」](TERMS.md)条这张卡把知识工具带进菜单的。

**分家口径（TERMS 词条照应）**：[TERMS「预案卡」](TERMS.md)条管**循环怎么排**（菜单子集/
上限/waves 推进序），weknora 剧本库管**查询怎么抄**（既定查询的内容母本）。别把
pb-c2-001 当成第五张卡——它不是卡，是卡上 waves 引用的查询参考册（13.2 走查）。

### 站 2 · 两件知识工具的登记面：L0 只读 + 写工具的票面归属

📍 大图节点:MENU_GATE(13.1 菜单闸·INV-11 第一道闸)

三工具在 manifest 的登记面
（[tools.manifest.json:21-23](soc-demo/fixtures/tools.manifest.json#L21)）：
`playbook_lookup`/`graph_query` = **L0 只读**（family=readonly_query），
`hypothesis_register` = **L1 写**（family=case_write，票面描述原话"仅供 outcome 收敛归档
步，不入 planner 组合菜单"）。分级语义由 committed 测试咬死
（[weknora.test.ts:217-234](soc-demo/services/agent/workers/investigation/weknora.test.ts#L217)）：
L0 免验票直接放行（查询无副作用），L1 无票 403 no_ticket。

**为什么 register 不进组合菜单**（票 79 L0 裁定②口径）：菜单是 planner 的**选路空间**，
而"要不要把假设-证据关系写进图谱"不是选路问题——它是收敛归档步的固定动作
（[TERMS「撒出去·收回来」](TERMS.md)条 miss 半边），写口必须唯一。所以父票面
（[hunt-pack.ts:88-90](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L88)
huntFlowTicketFace = 机制默认菜单 ∪ 三族菜单 ∪ register）里有它，但任何
[TERMS「预案卡」](TERMS.md)条的 menu 数组里都没有它——planner **选不到**，13.4 会看到
毒剧本想走这条缝时两面各是什么下场。

### 站 3 · plan 起手式：剧本/图谱开局写在 prompt 契约里

📍 大图节点:PLANNER(13.1 拟单的消费面)

hunt 版 plan prompt 的起手式
（[hunt-prompt.ts:59-60](soc-demo/services/agent/workers/investigation/hunt-prompt.ts#L59)）：

> "狩猎起手式：先调剧本/图谱类工具锚定取证面与既定查询，再按假设句式族落取证维度"

这是**狩猎与告警调查的第一差异**写进 prompt 契约的位置：告警调查（S2）从现场证据
直接开始；狩猎（S9 起）先问知识平面"这类怀疑的标准打法是什么"，再落取证维度。
选路依据=**现场证据+历史研判**的历史研判半边，就在这句起手式里。菜单渲染
（[renderHuntMenu:14](soc-demo/services/agent/workers/investigation/hunt-prompt.ts#L14)）
把每件工具的参数契约+描述一并给 planner——playbook_lookup 的描述原文就带着
"能力菜单的剧本半边"。教学档的 fake 拟单的不消费 prompt 文本（fake 纪律"只吃输入
结构"，11.3 站 2 同款口径），真 LLM 档（票 81）才直接读它——**prompt 契约由测试钉死
防漂移**，这也是诚实形态的一部分：fake 档教的是机制与数据，不冒充 LLM 读过 prompt。

亲眼看一眼渲染出来的菜单面（契约级 tsx，照抄可复现）：

## 三、为什么这么设计（三层拆）

| 层 | 设计 | 不这样会怎样 |
|---|---|---|
| 机制层 | 只认格式契约（templateId/maxRounds/maxTasks/menu 四字段，[template.ts:9](soc-demo/services/agent/src/orchestration/template.ts#L9)），菜单真源=卡 | 机制层硬编码"狩猎要用剧本库"→ 第三类知识工具又要改 m14——零增量铁律破产 |
| 内容层 | 知识工具进卡（menu 字段）+ waves 引用剧本库 | 菜单写成全局常量→ 每族假设看到同样的选路空间，菜单收窄失去意义 |
| 票据层 | L0/L1 分级 + register 出组合菜单 | 写工具进了 planner 菜单 → LLM 拆单时可以"顺手写图"——写口不再唯一，INV-5 的前提塌掉 |
