### 站 1-2 · 两道静态闸：格式闸与执行闸的分家

spec gate 管格式（表在不在、例外有没有理由），边界闸管执行（禁令真的拦得住吗）。
边界闸的规则注册表，[tools/check_boundary.py:37-47](soc-demo/tools/check_boundary.py#L37)：

```python
KEYS = [
    ("R1", "各 workspace 包互相 import"),
    ("R2", "引用 services 内部实现"),
    ("R3", "中立层 import services"),
    ("R4", "反引仓库级"),
    ("R5", "packages/mcp-audit"),
    ("R6", "services/web"),
    ("R7", "互不 import"),
    ("R8", "依赖方向单向"),
    ("R9", "healthz"),
]
```

最讲究的设计在头注释里（[check_boundary.py:7-9](soc-demo/tools/check_boundary.py#L7)
原文）：

```python
- 表里每行禁令都必须有闸消费（缺行 → 表与闸失配 FAIL）；
- 闸里每个检查器都必须能在表里找到自己的行（删规则不删闸 → FAIL）；
- 豁免按「例外」列解析（无理由的例外 check_specs.py 已经拦了，这里只管执行）。
```

翻译：**规则表与检查器互为对方的对账对象**——写了规矩没人查，红；有检查器没写
规矩，也红。这套"表与闸互查"的思想，跟 7.2 的工具对账网（manifest ≡ A.1 ≡
worker 面 ≡ 矩阵）是同一个物种：**单一事实来源 + 所有消费方互相点名**。顺便一提，
gen-tool.mjs 自己就是 R3 的模范（中立层零依赖、不 import 工程内部任何模块）——
7.1 站 1 讲过它的头注释，这里对上了号。

## 三、服务与中间件卡

**卡 1 · 边界闸（规则表驱动的 import 检查器）**

- **它是什么**：零依赖 python 脚本，把 specs/modules.md 的"边界规则"表逐条对代码
  库真跑 import 检查（TS 三种 import 形态 + py 侧互引/反向 import），外加表与闸
  的互查（缺行红、删闸红）与自测（--self-test 18/18：违规样本必红、豁免样本必绿）。
- **市面对照**：①eslint no-restricted-imports（规则散在 lint 配置里，没有"表"这
  个单一事实来源）；②dependency-cruiser（能力强，规则也是配置文件——思想最近）；
  ③ArchUnit（Java 世界的同思想件）。
- **本项目为什么自写**：规则表长在 specs/modules.md 的**架构文档**里，人和机器读
  同一张表——文档即契约的又一处落地（7.2 卡 1 的续篇）。自写 ~470 行换"架构规则
  有人在机器上盯防"，划算。
- **业务上怎么选**：模块边界值得机器盯防的判据是"越界的代价是否静默"——import
  越界编译照样过、测试照样绿，不查就烂；这类规则优先上闸。凡 CI 能红的问题，
  别靠 code review 的人眼。

**卡 2 · 基线即账本（测试数与删除行的库存管理）**

- **它是什么**：把"全量测试通过数 + skipped 数"当库存数字记账（486+3 → 492+3），
  把对既有测试文件的每一行删除当出库单据审计（git diff 逐行亮账 + 理由）。
- **市面对照**：①coverage 阈值（保覆盖率数字，但删测试换测试看不出来）；②变更
  冻结期（一刀切）；③PR 模板里的"我删了什么"自述栏（本卡机器化的版本）。
- **本项目为什么这么管**：安全系统的测试就是防线本体——删一条闸的测试等于拆一段
  围墙。数字对账（+6）+ 行级亮账（5 行全是签到窗）双保险，比单一 coverage 数字
  分辨率高得多。
- **业务上怎么选**：防线类代码（闸/对账/审计）适用最严口径：数量只增不减、删除
  必须带单据；普通业务代码可放宽到"覆盖率不降"。区分对待，纪律才守得住。

## 场景 7 闯关（三题）

<div>

**题 1 · 三种身体状态**：登记表 fixtures/tools.manifest.json 有三种"身体状态"——
健康、病了（JSON 坏）、摘了一行。把 `list_approvals`、`get_alert`、一个从没登记
过的 `no_such_tool` 分别在这三种状态下无票调用，闸各给什么裁决？其中哪种状态
会让"登记在册的老员工"也进不了门？

<details><summary>答案</summary>

**健康表**：`get_alert`（L0）→ allow（免验待遇）；`list_approvals`（L1）→ 403
no_ticket；`no_such_tool`（未登记 → policy.unregistered_tier=L1）→ 403 no_ticket。
**病表**：三个全一样——403 **signature_invalid**。机制：manifest 读不到/JSON 坏 →
`tierOf()` 抛 → 落进闸体 try 的兜底（INV-1：粮草病了绝不放行，fail-closed 桶的
名字叫 signature_invalid）——这就是"连正牌 L0 老员工 get_alert 也进不了门"的
状态。**摘行副本**：`get_alert` 照旧 allow（它还在表里）；`list_approvals` 与
`no_such_tool` 同为 403 no_ticket——摘行后它就是未登记工具，默认级 L1 与它登记
的 L1 同值，闸的回答逐字节相同。（7.2 探针三幕全实测；判据口诀：**表说什么闸信
什么，表病了闸关门，表缺行按最严默认级待人**。）

</details>

**题 2 · 闸认票不认表**：值班长手里有一张真网关铸的任务票，allowed_tools 里写着
`list_approvals`。①此刻有人把登记表里这一行摘掉，这张票还能过闸吗？②那摘行
到底破坏了什么？请说出至少三处杀伤点，并指出哪一处才是"下一张票装不下它"的
真正执法者。③如果把该行的 tier 从 L1 改成 L0，这张"含它的票"的裁决会变吗？无票
调用呢？

<details><summary>答案</summary>

①**能**。闸的持票路径（verifyTaskTicket）只做五连检查：验签→时效→焚毁→
allowed_tools 精确匹配→case/run 绑定——全程没有一行读登记表，票是签名事实，
摘行不溯及既往（7.3 S5 幕实测：持票 allow、handler 照常执行）。②杀伤在三处闸外：
a) 对账测试当场翻红（A.1 有它、manifest 没它——计数快照 + 点名清单两道）；
b) 无票通道的分级回退（本例 L1→默认 L1 同值无感；摘 L0/L2 行则闸行为立刻变化）；
c) **下一张合法票再也装不下它**——生产票面来自 run-kinds 注册表（worker TOOLS
常量），"票面 ⊆ manifest"由 tools-manifest.test.ts 咬死，CI 不绿就合不进去。
真正的执法者是 **c 的对账网 + 铸票上游**，不是闸。③tier 改 L0：持票裁决**不变**
（有票走票面，不看分级）；**无票调用立刻翻脸**——从 403 no_ticket 变成 allow
（L0 免验）——分级只在闸的三岔口"两手空空"分支出场（7.3 站 1）。这也反过来
解释了为什么改任何 tier，"全表扫描：无票调用时 L0 allow / L1 no_ticket / L2
require_approval"那条测试就翻脸。

</details>

**题 3 · 新工具的三层能力面**：同事说"我跑 `pnpm gen:tool` 生成了个新工具，登记
表里也有它了，为什么真容器 run 里永远看不到它被调用？"请按"登记面/票面/执行体"
三层解释缺了哪几层，每层补齐各要动哪些地方，以及为什么本场景刻意只走到第二层
就停（提示：想想 fake LLM 的计划、共享布景、和"登记 ≠ 持票 ≠ 执行体认识它"）。

<details><summary>答案</summary>

三层里我们走完了前两层：**①登记面**（manifest 行 + A.1 + 点名快照——7.2 齐活，
分级/族有身份、闸的分级读口认它）；**②票面**（7.3 教具已证明"票面装得下它就
过闸"——但生产里 run kind 的票面来自 run-kinds 注册表，注册表来自 worker TOOLS
常量，list_approvals 不在任何常量里，所以**没有任何合法生产票会包含它**——补齐
= 把它加进某个 worker 的 TOOLS 常量并同步对账断言）；**③执行体**（缺）——worker
的 execTool/只读路由 switch 里没有它的 case，fake LLM 的计划词典里没有它的关键词，
所以就算票面装了、闸也放了，run 里也没有任何代码路径会**发起**这个调用（execTool
的 default 分支会抛 unreachable_tool）。补齐=在目标 worker 加执行体 case +（若走
LLM 提名）prompt 契约/fake LLM 计划 + 相应测试——这就是票 48 注释"全仓摸 6+ 处"
的剩余几处。**为什么停在第二层**：接进 worker 工具面=改 worker 编排与 fake LLM
行为，会改变现有 run 的事件流/步数/token 账（共享布景污染 + 超出本场景"新增工具
最小闭环"的授权边界）；而闸的语义验证（过闸/拒绝/三态）在第二层已经可以全部
实测。生产化排期时三层要一次收编并对账齐动——半层上生产比不上生产的危害大
（票面装了、执行体没有 = 一个永远 unreachable 的授权，白挂攻击面）。

</details>
