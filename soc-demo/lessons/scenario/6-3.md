## 一、操作（位置感）

反查链路全图：`web（6.4）→ agent :3003 POST /api/v1/pii/reveal → guards :8001
/pii/reveal → mapstore`。中间这道 agent 端点是**唯一合法入口**——它先验会话
（你是谁），再对角色白名单（你配不配），才向 guards 转发。为什么要这道中间闸，
不在 guards 上直接做权限？因为 guards 是**内网裸口**（6.2 的扫雷就是证据：它只
认账不认人），而"认人"需要的会话验签、角色模型都长在 agent 侧——把闸放在
"人的会话"所在的那一层，才验得了真身份。

操作上把四张预置脸都拉出来打一遍同一发反查（`<CN_ID>` 是 6.1 主探针埋的假身份
证占位符）：

```bash
cd /tmp
for u in duty_lead soc1 admin redteam; do
  TOK=$(curl -s -X POST http://127.0.0.1:3003/api/v1/auth/login \
    -H 'content-type: application/json' -d "{\"username\":\"$u@soc.local\"}" \
    | python3 -c "import json,sys; print(json.load(sys.stdin)['token'])")
  printf '%-10s => ' "$u"
  curl -s -w ' [%{http_code}]' -X POST http://127.0.0.1:3003/api/v1/pii/reveal \
    -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
    -d '{"placeholder":"<CN_ID>"}'
  echo
done
```

预期（实测逐字）——一张表看清"谁有钥匙"：

```
duty_lead  => {"placeholder":"<CN_ID>","originals":["110101199003071234"]} [200]
soc1       => {"error":"pii_reveal_forbidden"} [403]
admin      => {"placeholder":"<CN_ID>","originals":["110101199003071234"]} [200]
redteam    => {"error":"pii_reveal_forbidden"} [403]
```

注意 soc1 的待遇：**查告警、写案卷样样行的分析师，反查 PII 就是 403**——反查不是
"谁的职级高"的问题，是"谁的职责需要"的问题（分析师办案用占位符就够了，要把
"证人 A"还原成真人，得值班长或管理员点头）。另注意 403 响应体里**只有错误码，
没有任何暗示"这个占位符存不存在"**——被拒的人连柜子里有没有这份档都不该知道。

### 站 1-3 · 反查口本体：闸的三层与审计闭包

📍 大图节点:REVEAL_A(6.3 受控反查)（闸体两层 = 图上 ROLE_GATE 会话+白名单、
AUDIT_GATE 三态审计，同站相邻）

先看端点头上的设计注释——它是 6.3 全部的"为什么"：

📄 [services/agent/src/app.ts:566-571](soc-demo/services/agent/src/app.ts#L566)

```ts
  // ---- 票 49（ADR 0004-3）：PII 受控反查口。全链：web（duty_lead/admin）→
  // 本端点（会话验签 + 角色白名单 + INV-8 审计）→ guards /pii/reveal（mapstore）。
  // 反查是人的动作不是工具调用：不走 FGA 工具闸（A.2 四族装不下「PII 反查」，
  // 端点级白名单是裁决落法，票面记票交 L0 追认）——可见性即第一收窄（FR-M8.2
  // 同款口径），web 只给这两个角色出按钮，这里的闸兜底。每查必审计（含被拒的查），
  // 审计 details 只记命中条数、绝不记原文（敏感面金丝雀，INV-4 类推口径）。
```

"反查是人的动作不是工具调用"这句是钥匙：4.2 的 OpenFGA 裁判管的是 **worker 的
工具调用**（`tool:<名字>` 的 can_execute），而反查发生在"人要看一眼"的场景——
没有 run、没有票、没有 worker，A.2 的工具矩阵里塞不进这个动作（ADR 0004 追认
原文："不进 FGA 工具矩阵——反查是人的平台动作而非 worker 工具调用"）。硬塞的
代价是给工具矩阵开"平台动作"的特例口，得不偿失；所以裁决落法是**端点级白名单**
——代码里一张两个名字的集合：

📄 [services/agent/src/app.ts:572-582](soc-demo/services/agent/src/app.ts#L572)

```ts
  const PII_REVEAL_ROLES: ReadonlySet<string> = new Set(["duty_lead", "admin"]);
  app.post("/api/v1/pii/reveal", async (req, reply) => {
    const key = sessionKey();
    if (!key) return reply.status(503).send({ error: "hmac_key_missing" });
    const h = req.headers.authorization;
    const token = typeof h === "string" && h.startsWith("Bearer ") ? h.slice(7) : null;
    const claims = token ? verifySession(token, key, Math.floor(Date.now() / 1000)) : null;
    if (!claims) throw new UnauthorizedError();
    const body = (req.body ?? {}) as { placeholder?: unknown };
    const placeholder = typeof body.placeholder === "string" ? body.placeholder.trim() : "";
    if (!placeholder) return reply.status(400).send({ error: "placeholder_required" });
```

三道关按顺序过：**HMAC 密钥不在**（服务装配坏）→ 503 拒一切；**会话验不过**
（没带/带坏 token）→ 401；**占位符参数空** → 400。会话本身就是 4.2 登录口发的
那枚签名票（`duty_lead@soc.local` 全称登录，角色长在 claims 里）——所以白名单
读的是**验签后的角色**，不是请求体里自称的字符串：伪造 role 在这条链上无效
（对照 4.2 捣乱 B 的编排面 `role:"hacker"`——那是另一个入口的另一种防法）。

接着是审计闭包与角色闸——先定义"怎么记"，再判"放不放"：

📄 [services/agent/src/app.ts:584-604](soc-demo/services/agent/src/app.ts#L584)

```ts
    const ctx = httpCtx(req.headers as Record<string, unknown>);
    const auditReveal = (
      result: "SUCCESS" | "FAILURE" | "DENIED",
      details: Record<string, unknown>,
    ): void => {
      audit.record({
        action: "pii_reveal",
        actor: { type: "user", id: claims.sub },
        objectId: placeholder,
        objectType: "pii_placeholder",
        details,
        requestId: ctx.requestId,
        result,
        createdAt: Date.now(),
      });
    };

    if (!PII_REVEAL_ROLES.has(claims.role)) {
      auditReveal("DENIED", { reason: "role_forbidden", role: claims.role });
      return reply.status(403).send({ error: "pii_reveal_forbidden" });
    }
```

`auditReveal` 是个三参闭包：五要素（谁/查了什么占位符/结果/请求号/何时）在闭包里
定型，调用方只补 result 和 details。**"每查必审计"的实现就在这个闭包的位置**——
它定义在角色闸**之前**，往下读你会看到 SUCCESS/DENIED/FAILURE 三条岔路全都调它，
没有任何一条路径能绕开记账。为什么反查要留痕（INV-8）？因为反查是"敏感值离开
柜子的那一下"——谁在什么时候想知道谁的身份，这件事本身就是要害情报：被拒的查
记 `DENIED`，details 带 `role_forbidden` 和**被拒者的角色**——"soc1 在什么时候
试图反查什么占位符"留了全账，踩线行为（反复试探占位符）在台账上一眼可见。

审计的时序落点也要交代（跨组件跳接三件套）：`audit.record` 在返回响应**之前**
被调用（代码顺序保证"先记账后回包"的意图），但它出站走的是 case-backend 的
REST 口（`POST :3002/internal/audit`），fire-and-forget——**不阻塞回包、失败也
不拖垮反查**，出站失败只打一条 `audit_ingest_failed` 的 warn 日志（可 grep 可接
告警）。所以"查完立刻去 M2 审计流页翻"偶尔要等一两百毫秒才刷出来——账一定在，
只是不搭响应的顺风车。

### 站 4 · 出站件：guards 病了不编原文

📍 大图节点:OUT_REVEAL(6.3 受控反查)

过了闸，向 guards 转发。出站纪律与 llm/fga/guards 扫描同源（票 43 的共享出站件
口径）：

📄 [services/agent/src/guards-client.ts:97-113](soc-demo/services/agent/src/guards-client.ts#L97)

```ts
/** 按占位符向 guards 反查原文。上游语义：404 = 映射表查无此人（unknown），
 *  其它非 200 = guards 病了；响应形状不对也按病了算（guards_bad_shape）。 */
export async function revealPii(
  placeholder: string,
  opts: PiiRevealOptions = {},
): Promise<PiiRevealOutcome> {
  const baseUrl = opts.baseUrl ?? process.env.GUARDS_URL ?? "http://guards:8001";
  const timeoutMs = opts.timeoutMs ?? Number(process.env.GUARDS_TIMEOUT_MS ?? DEFAULT_TIMEOUT_MS);
  try {
    const res = await fetch(`${baseUrl}/pii/reveal`, {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ placeholder }),
      signal: timeoutSignal(timeoutMs),
    });
    if (res.status === 404) return { ok: false, reason: "placeholder_unknown" };
    if (!res.ok) return { ok: false, reason: `guards_http_${res.status}` };
```

404 单独归类（`placeholder_unknown`，映射表里真没有），其余非 200 全是"guards
病了"。注释里"响应形状不对也按病了算"的把关在后半段：

📄 [services/agent/src/guards-client.ts:114-129](soc-demo/services/agent/src/guards-client.ts#L114)

```ts
    const data = (await res.json()) as { placeholder?: unknown; originals?: unknown };
    if (
      !Array.isArray(data.originals) ||
      !data.originals.every((x) => typeof x === "string")
    ) {
      return { ok: false, reason: "guards_bad_shape" };
    }
    return {
      ok: true,
      placeholder: typeof data.placeholder === "string" ? data.placeholder : placeholder,
      originals: data.originals,
    };
  } catch (e) {
    return { ok: false, reason: outboundTimeoutReason("guards", isOutboundTimeout(e)) };
  }
}
```

**回包里 `originals` 不是全字符串数组 = 当作没收到**（`guards_bad_shape`）。这行
把关在反查链上格外要紧：这个端点负责把原文递给有权限的人——上游回了个畸形包
（比如代理层注入、版本错位），宁可 502 也不能把不明不白的字节当原文递出去。
catch 收口沿用 outbound.ts 的唯一口径（TimeoutError/AbortError → `guards_timeout`
，其余 → `guards_unreachable`）。整个出站件**任何失败都返回 `{ok:false, reason}`
，绝不抛异常炸端点，也绝不编造原文**（文件头注释
[guards-client.ts:84-86](soc-demo/services/agent/src/guards-client.ts#L84) 原话：
任何失败都收口成 `{ok:false, reason}`，绝不抛异常炸端点，也绝不编造原文）。

### 站 5 · 分岔组装与三态审计

📍 大图节点:AUDIT_GATE(6.3 受控反查)（审计落点 = 图上 T_AUDIT，档案室 M2 库；
guards 侧对端 = 图上 REVEAL_G）

📄 [services/agent/src/app.ts:605-616](soc-demo/services/agent/src/app.ts#L605)

```ts
    const outcome = await (opts.revealPii ?? httpRevealPii)(placeholder);
    if (!outcome.ok) {
      auditReveal("FAILURE", { reason: outcome.reason });
      if (outcome.reason === "placeholder_unknown") {
        return reply.status(404).send({ error: "placeholder_unknown" });
      }
      return reply.status(502).send({ error: "guards_unavailable" });
    }
    // 成功审计只记「谁查了占位符 X、命中几条」——查回的原文一个字节不进 details
    auditReveal("SUCCESS", { match_count: outcome.originals.length });
    return { placeholder, originals: outcome.originals };

```

三个终态对齐三色审计：查无此人 → 404 + `FAILURE(reason=placeholder_unknown)`；
guards 病 → 502 + `FAILURE(reason=guards_timeout|guards_unreachable|…)`；查到 →
200 + `SUCCESS(match_count=N)`。**原文只出现在最后一种的响应体里**——审计行里
连"命中了什么"都没有，只有"命中几条"。`opts.revealPii ?? httpRevealPii` 是 seam
（测试注入假件，[pii-reveal.test.ts](soc-demo/services/agent/src/pii-reveal.test.ts)
用它锁契约），生产装配走 HTTP 出站件。

## 三、服务与中间件卡

**卡 1 · 端点级角色白名单（自研裁决形态）**

- **它是什么**：不走通用授权引擎，在端点代码里放一张硬名单（`Set(["duty_lead",
  "admin"])`），会话验签后的角色不在名单里就 403。
- **本项目怎么配置**：app.ts:572 一行集合；web 侧 reveal.ts 有一份**镜像名单**
  （管按钮可见性），两边一致性靠测试锚定（改一边必红）——"权威闸在 agent，
  web 只是第一收窄"（FR-M8.2 同款口径，6.4 展开）。
- **市面替代**：①给 FGA 矩阵加"平台动作"类型（通用但要把人的动作塞进工具
  模型）；②API 网关层 RBAC 中间件（集中管，但与业务会话模型耦合）；③注解式
  权限框架（Spring Security @PreAuthorize 一类，形态同本卡但机制重）。
- **本项目为什么选端点白名单**：全系统**只有这一个**"人的平台动作"——为它扩
  授权模型、加配置格式，复杂度花在一处需求上不划算。白名单 + 会话验签 + 必审计
  三件套 20 行讲完，且正反测试都有锚（pii-reveal.test.ts 的角色闸组）。
- **业务上怎么选**：平台动作只有零星几个 → 端点白名单（本项目）；"谁能不能干
  什么"开始成矩阵（几十角色×几十动作）→ 通用授权引擎（FGA/OPA）；**判据是
  授权规则的规模与变化频率**——规则少而稳用代码，规则多而善变用数据。

**卡 2 · 敏感面金丝雀口径（INV-4 的类推）**

- **它是什么**：给"最敏感的那类数据"立一条**可机器断言的卫生规矩**——本步是
  "原文只活在 mapstore 和有权限的响应体两处"；5.5 的同门是"SECRETS 值只活在
  网关与出站瞬间"。口径的共同点：**不是靠人小心，是靠 grep 全可观测面来证明**。
- **本项目怎么配置**：审计 details 只记 `match_count`（app.ts:614）；出站件
  fail-closed 不编原文（guards-client.ts:86 注释）；测试面金丝雀断言
  （pii-reveal.test.ts:145-162：成功/被拒/失败三路走完，审计序列化后
  `toContain("<PHONE_NUMBER>")` 且 `not.toContain(ORIGINAL)`——**占位符可以进
  审计（它就是要审的对象），原文一个字节都不许**）。
- **市面替代**：①字段级加密/格式保留加密（FPE，库里也存密文，破库也拿不到
  明文）；②DLP 出站扫描（事后兜底网）；③数据脱敏代理（查询引擎层统一改写）。
- **本项目为什么选"不落+可 grep"**：demo 的威胁模型是"内部可观测面（库表、
  日志、审计、SSE）任何有读权限的人都能翻"——最省钱的对策是让敏感值**根本不
  出现在这些面上**，然后用全量 grep（5.5 的搜索法、本步的 dump 搜索）把口径
  变成可复验的断言。
- **业务上怎么选**：怕拖库 → 字段级加密上真家伙；怕内部人员顺手复制 → 精确
  授权+必审计（本步）+ 影子流程治理；两者不互斥，生产 SOC 通常叠加。**共同
  铁律：敏感值的每一条合法出口都要有一个"门"，门上挂账**——没有门的出口
  （日志、错误消息、缓存）就是泄露的默认路径。

## 六、捣乱实验（必选）

**捣乱 A · 把 guards 停了，看反查的 fail-closed**（钥匙在手的值班长，柜子搬走
了怎么办）：

```bash
docker stop soc-demo-guards-1 && sleep 2
TOK=$(curl -s -X POST http://127.0.0.1:3003/api/v1/auth/login \
  -H 'content-type: application/json' -d '{"username":"duty_lead@soc.local"}' \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['token'])")
curl -s -w ' [%{http_code}]' -X POST http://127.0.0.1:3003/api/v1/pii/reveal \
  -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
  -d '{"placeholder":"<CN_ID>"}'
docker start soc-demo-guards-1 && sleep 9   # 恢复布景，等 healthy
docker compose -f soc-demo/docker-compose.yml ps guards --format "{{.Name}} {{.Status}}"
curl -s -w ' [%{http_code}]' -X POST http://127.0.0.1:3003/api/v1/pii/reveal \
  -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
  -d '{"placeholder":"<CN_ID>"}'
```

预期（实测逐字）：停机时 `{"error":"guards_unavailable"} [502]`——**不是空列表、
不是"查无此人"、更不是编一条原文凑数**；恢复 healthy 后同一发 `200` 逐字还原。
再对账审计：停机那一发留了 `FAILURE | {"reason":"guards_timeout"}`（Docker 停容器
的端口转发黑洞连接吃满 2s 超时——与 5.2 捣乱 A 同款现象），恢复后是 `SUCCESS`。
判据：502 响应体里查不到任何原文形状的字符串 + FAILURE 审计在账 = fail-closed
成立。

**捣乱 B · 伪造占位符在闸口内的一发**（<FOO> 这种库里没有的占位符，配上合法
钥匙打正式入口）：

```bash
TOK=$(curl -s -X POST http://127.0.0.1:3003/api/v1/auth/login \
  -H 'content-type: application/json' -d '{"username":"duty_lead@soc.local"}' \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['token'])")
curl -s -w ' [%{http_code}]' -X POST http://127.0.0.1:3003/api/v1/pii/reveal \
  -H "authorization: Bearer $TOK" -H 'content-type: application/json' \
  -d '{"placeholder":"<FOO>"}'
# 预期（实测）：{"error":"placeholder_unknown"} [404]
sqlite3 "file:soc-demo/data/case-backend/case-backend.sqlite?mode=ro" \
  "SELECT result, substr(details,1,50) FROM audit_entries WHERE action='pii_reveal' \
   ORDER BY created_at DESC LIMIT 1;"
# 预期（实测）：FAILURE | {"reason":"placeholder_unknown"}
```

判据：**查无此人也是 FAILURE 审计**——"谁在什么时候试图反查一个不存在的占位符"
本身就是值得留账的侦查行为；对比 6.2 捣乱 B 的 guards 裸口（同样的 404 但无
审计），闸口的语义是"**每一发都有账**，命中与否是第二件事"。

**捣乱 C · 纸面推演：LLM 能不能替人反查**（本场景最要紧的边界题）：假设调查
LLM 在分析占位符文本时"想"知道 `<CN_ID>` 后面是谁——它有什么通道？翻工具面：
`tools.manifest` 里没有 reveal 类工具（反查根本不是工具）；翻编排面：
`/internal/runs` 只能拉起 worker 子图，子图工具集里同样没有；翻输出面：它能把
占位符写进报告，但还原原文的动作只存在于 `POST /api/v1/pii/reveal`——**需要
duty_lead 的登录会话**。结论：LLM 全链路摸不到原文，反查通道上人是唯一持钥者。
这正是"反查是人的动作不是工具调用"裁决的安全红利：**把 A.2 工具矩阵里根本
不存在的权限，变成 LLM 结构上无法申请的权限**。
