## 一、操作（位置感）

判定的全部逻辑在 [purple.ts:335-344](soc-demo/evals/src/rigs/purple.ts#L335)
（discovery_rate_ground_truth 的逐例判定段）：

```ts
const signatures = evalSignatures(entry, runA);
const lastRound = [...runA.rounds_full].sort((a, b) => b.round_no - a.round_no)[0];
const judgeVerdict = lastRound?.judge?.verdict ?? null;
const judgeHit = runA.status === "concluded" && judgeVerdict === "hit";
// 发现 = judge hit ∧ ground truth 签名三重验全过（不靠 LLM 自评——签名逐格机器复核）
const discovered = judgeHit && signatures.length > 0 && signatures.every((s) => s.ok);
```

一行公式三个必要条件：①循环收敛到 concluded 且末轮 judge 说 hit（**半判据**）；
②存在签名（hit 例必配，12.1 装载闸管的）；③**每一条**签名三重验全过（`every`——
一条不过整体不算发现）。注意 judge 在这里的位置：它是"必要条件"不是"充分裁判"
——judge 说 hit 而签名缺位 = 不发现；反过来 judge 眼花了说 miss（12.2 表里没有
这种例，但语义上）签名全过也不冒充发现，因为 `judgeHit` 还在公式里。**两半都不
是橡皮图章，合起来才算数。**

## 二、调用链与真实落点

### 站 1 · 三重验逐腿拆：每条签名的三次独立点名

📍 大图节点:GT_GATE(12.3 发现判定·签名三重验)

[evalSignatures](soc-demo/evals/src/rigs/purple.ts#L161)
（[purple.ts:161-181](soc-demo/evals/src/rigs/purple.ts#L161)）对每条签名
（tool/param/value/traces）验三条腿：

| 腿 | 代码 | 验什么 | 为什么独立必要 |
|---|---|---|---|
| ①轨迹执行 | `rounds_full.find(...)` → `executedRound`（[:163-166](soc-demo/evals/src/rigs/purple.ts#L163)） | 签名查询真的被 planner 组合并 dispatch 过（轮号在场） | 防"结论对了但没干过活"——判定锚在**行为**不在口供 |
| ②取证面命中 | 子 run 报告 `total=N` 正则提取 → `reportedTotal>0`（[:167-169](soc-demo/evals/src/rigs/purple.ts#L167)） | 该查询的取证面真有产出 | 防"查了但两手空空也算发现"——审计真相源 INV-8（hunt_task_report 逐条对） |
| ③语料在场 | [corpusHasTrace](soc-demo/evals/src/rigs/purple.ts#L147) 读 `fixtures/alerts/<trace>.json` 原文含签名值（[:147-151](soc-demo/evals/src/rigs/purple.ts#L147)） | 攻击植入痕迹确实在语料里 | **与循环执行解耦的独立复核**——不信任布景自身，直接问原始数据 |

三条腿任何一条断，`ok=false` 并给出**具体到腿的 reason**（[:170-178](soc-demo/evals/src/rigs/purple.ts#L170)
四级递进：未执行/报告缺席/取证面零命中/语料缺痕迹）。12.2 表 02 例的三条签名在
产物里的原文（purple-team.json）：

```
proc_lineage_query cron          → ok=true | 三重验通过（轮 2 total=2，语料痕迹在场）
file_change_query /var/www/…/sh.php → ok=true | 三重验通过（轮 3 total=1，语料痕迹在场）
outbound_conn_query 203.0.113.66 → ok=true | 三重验通过（轮 4 total=3，语料痕迹在场）
```

三个"轮 N"恰好是 11.3 真栈四轮轨迹的第 2/3/4 轮——布景轨迹与真栈轨迹同构，
判卷面逐轮对得上。

### 站 2 · 对账闸：标准答案错了，红给你看

📍 大图节点:GT_GATE(对账半边·groundTruthOk)

三重验算出 `discovered` 之后，还有一道**对账自证**（[purple.ts:370](soc-demo/evals/src/rigs/purple.ts#L370)）：

```ts
groundTruthOk: discovered === (expected === "hit"),
```

逐例问一句："判出来的发现状态，和标准答案说的一致吗？"——11 例全对账一致时
`purple_ground_truth_discovery` 检查绿（[purple.ts:463-469](soc-demo/evals/src/rigs/purple.ts#L463)），

### 站 3 · 预算口径：发现的另一道防注水闸

📍 大图节点:BUDGET_GATE(12.3 预算口径·防烧 token 注水)

[TERMS「无人值守破案率」](TERMS.md)条把预算口径写死了，代码在两处：
常量档 [PURPLE_BUDGET](soc-demo/evals/src/rigs/purple.ts#L44)
（[purple.ts:44-51](soc-demo/evals/src/rigs/purple.ts#L44)：硬顶 20/模板档 6/run
token 档 500k——后者同 [budget.ts:123-127](soc-demo/services/agent/src/budget.ts#L123)

[purple.ts:342-344](soc-demo/evals/src/rigs/purple.ts#L342)：

```ts
const cap = Math.min(PURPLE_BUDGET.max_rounds_hard_cap, tpl.max_rounds);
const withinBudget = runA.status !== "cancelled" && runA.rounds.length <= cap && runA.llmTokens <= PURPLE_BUDGET.run_token_cap;
```

三个要点：①**双取小**——机制硬顶和模板内容档谁紧听谁的（本布景实际绑定的是

（purple-team.json 的 `budget.note` 逐字可查）。防的质疑很具体：**"发现率低？

发现率纹丝不动、digest 逐字节不变。发现不奖励"跑得多"，只认证据（站 1 的三重验）；
预算口径存在的意义是把"我们允许它跑多少"先钉死，让数字在这个约束下诚实。

## 三、服务与中间件卡

**卡 · ▼八项场景专项检查（purple.test.ts 钉死的门槛面）**

- **它是什么**：[purple.test.ts:26-35](soc-demo/evals/src/rigs/purple.test.ts#L26)
  钉死 extraChecks 清单——映射完备/模板注册/ground truth 对账/hit 签名三重验/
  miss 盲区报告/预算内/双跑复现/两份数字自洽。每项进门槛与通用断言同权，**judge
  评分不在清单里**。
- **市面替代**：只断言最终数字 `expect(totals.discovered).toBe(5)`。
- **为何这么选**：只钉数字，口径漂了数字也可能碰巧对（比如双跑关了、签名放宽了、
  映射改了——5 这个数都可能是对的）；八项检查把**数字的来路**逐段钉死，任何一段
  失真都以自己的名字红（12.2/12.3 的两次翻红都是检查点名的，不是数字对不上才发现）。
- **业务上怎么选**：指标进 CI 的形态 = 数字断言 + 口径分段断言；"防注水"不是
  口号，是清单里每一个 `purple_*` 检查的名字。

## 场景题闯关（本步 1 题）

**Q3（注水质疑·票面指定应答题）：有人质疑："自主发现率的判定链里有 judge——
judge 也是 LLM，让 LLM 参与判定不就是自评比 LLM 好看吗？另外，把预算开大点多烧
点 token，5/11 总能刷成 11/11 吧？"——两层质疑，分别用本步的哪个机制挡回去？**

<details><summary>答案（点击展开）</summary>

**第一层（LLM 自评注水）**：discovered 公式（站 1）里 judge 结论只是**半判据**，
且是必要非充分——另一半是签名三重验，三条腿全是机器复核：腿①查轨迹里这个查询
真被组合执行过（行为）、腿②查审计真相源里取证面 total>0（INV-8 留痕，不是 LLM
口供）、腿③读原始语料文件确认攻击痕迹在场（与循环完全解耦的独立复核）。judge
想虚报 hit？签名缺位照样不发现。judge 被下游衰减压成 miss？签名全过也不虚报——
但注意方向：这套设计防的是"往好看漂"（虚报发现），miss 方向由对账闸
（groundTruthOk）兜住"标准答案说 hit 而判了 false"的失真。**判卷面没有一票由
LLM 独裁**——这就是"judge 评分零进门槛"（决策 10）在紫队的落地形态。

**第二层（烧 token 刷分）**：三层挡——①**预算写死且进报告**：轮数双取小
（机制硬顶 20 ∧ 模板档 6）、token ≤ hunt_flow run 档 500k、cancelled 不冒充发现
（站 3），口径本身是报告的必填段，藏着掖着不了；②**发现不奖励轮数**：discovered
的三个条件没有一条与"跑了多少轮"正相关——多烧的 token 只会买来更多 gap 轮或
被预算掐成 cancelled，不会买来第 6 个签名通过（12.4 亲测：硬顶改 999999 注水，
发现率 5/11 纹丝不动、digest 逐字节不变）；③**复现证据钉死口径**：双跑 digest
相等意味着任何"跑法变化"都会先在 digest 上现形再谈数字——想靠改跑法刷分，先过
"轨迹为什么变了"这一关。合起来：**自主发现率测的是"预算内的真实能力"，预算内
三个字不是限定语，是防注水的三道闸本身**。</details>
