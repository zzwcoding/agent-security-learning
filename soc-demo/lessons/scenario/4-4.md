# 场景 4 · 步 4.4 —— 值班长批准：铸一枚 ApprovalToken（HMAC 三段解剖）

> 卡 pending 着，run 挂起着，现在值班长按"批准"。这个动作的产出不是"执行"——是
> **一枚签名的授权书**：ApprovalToken。本步把它的铸造过程从头走到尾：agent 为什么自己
> 不签、要出远门找 gateway 铸？"先铸票后裁决"的顺序为什么不能反？票面的九个 claims
> 各防什么？主角卡 `apr_baf3f3a8`（isolate_host）在本步被正式批准，铸出的 token
> `ap_4a9d6e0d…` 我们逐字段解剖——4.5 拿它验票，4.6 看它焚毁。
> 术语卡词翻 `TERMS.md`（同一比喻体系：审批卡/一次性密令/手令票面/闸体…），老术语
> 只回指不另起解释。

## 一、操作（位置感）

本步主角操作一行命令（approver 必填，署名不留白）：

```bash
curl -s -X POST http://127.0.0.1:3003/api/v1/approvals/apr_baf3f3a8-fd09-4fcc-9c80-0c4f67e66a88/approve \
  -H 'content-type: application/json' -d '{"approver":"duty_lead"}' | python3 -m json.tool
# 预期：200，body 四件——approval_id / approval_token（三段式长串）/ run_id /
#       run_status: "awaiting_approval"   ← 秒回契约：批准此刻，执行还没发生
```

注意 `run_status` 还是挂起态：批准的 200 回来时，续跑任务才刚进队列（票 47 时序契约）。
真正的执行发生在几百毫秒后的分发循环里（4.5 的戏）。值班长此刻拿到手的，是一张
**签了名的授权书**，不是执行回执。

本步实测，批准返回的 token 解开长这样（base64url 的 payload 段）：

```
header : {"alg": "HS256", "typ": "JWT"}
payload: jti         : ap_4a9d6e0d-63a9-4b7c-9460-273b6ca6c7f8
         approval_id : apr_baf3f3a8-fd09-4fcc-9c80-0c4f67e66a88
         approved_by : duty_lead
         tool        : isolate_host
         params_hash : sha256:7f36978b6bab48e9251dc1c15340efe29f4a71efaa14698cdd8837c1630b94bd
         case_id     : case_000002
         iat         : 1789025609
         exp         : 1789025909        ← exp-iat = 300 秒
         used        : false
sig    : a51bc33ff257b76a7c138cb3bb613ca3…（hex 摘要，非标准 JWT 的 b64 段）
```

先打分层预告的招呼（原则：多层概念第一次出现要声明总层数）。TERMS"手令"条给 L1
任务票分过**四层**——ApprovalToken 同样四层，本步一次讲全，后文逐步标"这是第几层"：
**①凭证层**=这枚一次性密令本身（为什么要有：数字员工零权限，L2 执行授权全靠它领）；
**②签名层**=HMAC 三段里的 sig（没密钥造不出假票，密钥只在 gateway）；**③时效层**=
iat/exp 这对 300 秒保质期；**④权限层**=票面 claims 里的 tool/params_hash/case_id
（能动哪个工具、对哪份参数、绑哪个案）。

## 二、调用链

先看全景。一次批准，横跨三个服务、两个密钥域：

```
值班长 duty_lead
  │  POST /api/v1/approvals/apr_baf3f3a8…/approve  {"approver":"duty_lead"}
  ▼
[站1] agent 审批端点（app.ts:429）三道前置：
        缺 approver → 400 approver_required      （署名不留白，实测）
        卡不存在    → 404
        卡非 pending → 409 InvalidTransition     （廉价预检，真仲裁在站3）
  ▼
[站2] 先铸票后裁决：agent 出远门铸票
  │    POST gateway /internal/mint {type:"approval_token", jti:ap_随机, …}
  │    gateway 读 env SOC_HMAC_KEY → mint.mint_approval_token()
  │    网关病了/缺钥 → 502 mint_failed，卡仍 pending 可重试（捣乱 B 实测）
  ▼
[站3] 决定落卡（decideApproval 审批状态机仲裁）：
        pending→approved，卡上落 token + token_jti + approver + decided_at
        M2 审计 approve（actor=user:duty_lead，真人）
        后到者 409（并发双批只放行先到者，3.3 已证）
  │    → enqueueRunJob(resume) → 200 秒回 {approval_token, run_status:"awaiting_approval"}
  ▼
[站4] 分发循环捡起 resume 任务 → 信封链复核 → Command(resume) 唤醒 execute
        （4.5：节点重跑 → awaitApproval 查到 approved+token → 验票闸）
```

### 站 3 · 票面的九个 claims：每个字段都是一道防线

📍 大图节点:GW_MINT（gateway 容器）

铸造本体在 mint.py——py 件是票型的权威定义（ADR 0001 搬票型不搬代码）：

📄 [services/gateway/mint.py:70-89](soc-demo/services/gateway/mint.py#L70)

```python
def mint_approval_token(key, *, jti, approval_id, approved_by, tool, params,
                        case_id, iat=None, ttl=APPROVAL_TTL):
    """铸 ApprovalToken（PRD §5.9）：L2 动作经人批准后的一次性令牌（FR-S2.4）。

    params_hash 绑定具体参数——改参数即失效（FR-S2.2/INV-2）；used 恒以 False 铸出
    （一次性语义，焚毁登记在 M2 used_tokens 表，验票闸查表防重放）。
    """
    iat = int(time.time()) if iat is None else iat
    payload = {  # 字段集与顺序照 PRD §5.9，一字不增不减
        "jti": jti,
        "approval_id": approval_id,
        "approved_by": approved_by,
        "tool": tool,
        "params_hash": params_hash(params),
        "case_id": case_id,
        "iat": iat,
        "exp": iat + ttl,
        "used": False,
    }
    return _seal(key, payload), payload
```

九个 claims 逐个对号（对照本步开头解剖的 `ap_4a9d6e0d` 实物）：

| claim | 防什么 | 谁在验 |
|---|---|---|
| `jti`（ap_4a9d6e0d…） | 票的唯一身份证——焚毁登记、防重放都按它对账 | 闸查 used_tokens（4.5/4.6） |
| `approval_id` | 回指审批卡——票不是凭空的，是从某张卡长出来的 | 追溯/对账 |
| `approved_by`（duty_lead） | 谁批的写死进票面——票自己带着批准人的名字 | 审计复核（INV-9） |
| `tool`（isolate_host） | 票只对铸造时那个工具有效——拿隔离票去封 IP？没门 | 闸（scope_insufficient） |
| `params_hash` | **批什么执行什么**：参数指纹，改参数即失效 | 闸（params_mismatch） |
| `case_id` | 票绑案件——A 案的票不能用在 B 案 | 闸（scope_insufficient） |
| `iat`/`exp` | 保质期 300 秒（mint.py:25 `APPROVAL_TTL = 300`，任务票是 900s——**越危险越短命**） | 闸（token_expired） |
| `used: false` | 一次性语义的声明位——真相位在 M2 used_tokens 表，票面声明不算数 | （声明位，读口验真） |

按开头分层预告归类：`jti`/`approval_id`/`approved_by`/`used` 属**①凭证与身份**（used
同时是④的一次性声明位）；`tool`/`params_hash`/`case_id` 属**④权限层**（票面）；`iat`/
`exp` 属**③时效层**；**②签名层**不在 payload 里——它是 `_seal` 盖上去的第三段。
单独说说 params_hash 为什么**绑参数**而不是只绑工具名：工具名一样、参数换成另一台主机，
"批 app-01 隔离、执行 db-01 隔离"就成立了——指纹把参数逐字节锁进票面，**换参数即失效**，
闸那头重算哈希一对就穿帮（4.5 站 4 实测）。至于 TTL 300s 为什么比 L1 任务票的 900s 短
（TERMS"手令"条）：**越危险越短命**——不可逆动作的授权窗每多一秒，重放/误用的暴露面
就多一秒；可撤销的 L1 写操作才配得上三倍寿命。

签名怎么打上去的：

📄 [services/gateway/mint.py:92-95](soc-demo/services/gateway/mint.py#L92)

```python
def _seal(key: bytes, payload: dict) -> str:
    """b64url(payload) + 对 "b64h.b64p" 签 hex——签名咬的是原始字节，不是解析结果。"""
    b64p = b64u(json.dumps(payload, ensure_ascii=False).encode())
    return f"{HEADER}.{b64p}.{sign(key, f'{HEADER}.{b64p}')}"
```

两个细节让它"像 JWT 又不是 JWT"：① 签名是 **hex 摘要**（64 个十六进制字符），不是
标准 JWT 的 base64 段（教学变体，本步实测 sig `a51bc33f…` 全是十六进制位）；②
**签名咬的是原始字节**——TS 侧验票（4.5）对 `b64h.b64p` 原串重算 HMAC 比对，不解析后
重新序列化再比（那样键序空格都会打架：py 的 json.dumps 默认带空格，本步解出的 header
`{"alg": "HS256", "typ": "JWT"}` 冒号后有空格，就是 py 序列化的指纹）。被改过字节的票
永远进不了 JSON 解析器——验签在解析之前（fail-closed 第一关）。

actor=user:duty_lead）和 approval_decided 事件广播（4.5 实测事件 945）。

然后端点立刻返回（站 1 引过的 app.ts:457-464）：`run_status` 取自**当下**的 run 行——
此刻续跑还在队里，所以秒回的是 `"awaiting_approval"`。本步实测，200 返回后约两三秒，
run 才走到 completed。**批准和执行在时间上也是解耦的**（票 47 异步化），不只是概念上。
这条全场景最要紧的接缝，钉成三句话：**①产物此刻躺在哪**——200 回给值班长时，`approvals`
表多一行 approved（token 正本在卡上）、`run_jobs` 表多一行 resume 诉求、M2 审计多一行
approve(user:duty_lead)；**②等多久、谁接手**——分发循环（派活的，TERMS"派活的"条）
下一个 tick（默认 500ms 一轮）把 resume 领走；**③两边的触发关系**——**没有**。200 是
给调用方的回执，分发循环不认识 HTTP，它只认 run_jobs 表（TERMS"派活的"条的常见误读：
"以为 202 和派活循环有触发关系——没有"）。所以值班长拿到的 200 里 run_status 还是
awaiting_approval：**批准的产出是"授权书 + 一条待办"，不是"已执行"**——批完先秒回，
执行在 resume 之后（TERMS"一次性密令"条：批准≠执行）。

## 三、服务与中间件卡

### 卡 1（自研）· gateway 铸票服务：密钥单点的小型 STS

- **它是什么**：gateway 里 60 行的 FastAPI 路由 + mint.py 一个纯函数模块。全系统只有
  它摸得到签名密钥（SOC_HMAC_KEY）；所有票（L1 任务票 TTL 900s / L2 ApprovalToken
  TTL 300s）都从这一个口子签出。
- **为什么集中铸票**：① agent 不持钥——单服务被攻破不等于全网授权被伪造；② 票型
  一处定义——TS 侧只有验票闸没有第二套签发逻辑，杜绝"两套实现漂移出两格式的票"；
  ③ TTL/字段集/序列化的口径改一处生效。这就是迷你版 STS（Security Token Service）。
- **市面上同类**：云厂商 STS（AWS STS 的临时凭证，15 分钟到几小时）；Keycloak/
  OAuth2 授权服务器（签 JWT access token）；Vault 的 dynamic secrets。
- **本项目为什么手写**：教学环境九服务已经不小，再进一个 Keycloak 就喧宾夺主；
  手写 60 行反而把"签发/验证/焚毁"三个角色拆得清清楚楚。头注释也写明了演进路线
  （app.py:5-6："教学版 HMAC 自签 + SECRETS_* 凭证真值仓，蓝图注释 STS/Keycloak 演进"）。
- **业务上怎么选**：已有 IdP → 用它的 token 端点，别再养一个签发件；需要短时效、
  范围收窄的"动作级"授权（不是"用户级"）→ 自研薄 STS 常常比硬套 OAuth2 更清晰；
  无论选哪条，**签发与验证分属两个进程**这一条别让步。

### 卡 2（协议）· HMAC-SHA256：一把对称钥的签名怎么做出"防伪"

- **它是什么**：带密钥的哈希——`HMAC(key, message)`。同一把钥：签发方用它签，验证方
  用它重算比对。对比 RSA/ECDSA 的公私钥体系：HMAC 两端共享同一把钥，谁验票谁就能签票
  ——所以"验票的人必须比签发的人多"在 HMAC 世界里不成立，密钥的可信域就是票的可信域。
- **本项目怎么配置**：SOC_HMAC_KEY 一把钥全家通用（会话票、任务票、ApprovalToken、
  参数指纹的 canonicalJson……不，指纹不用钥）。`.env.example:7` 的教学值
  `local-demo-hmac-key-not-for-prod` 一眼假——真部署换掉它是上线清单第一行。
- **为什么够用**：单系统内网、签发验发两端都是自己服务、票面有 exp/jti/焚毁表兜底
  ——HMAC 的"共享钥"缺点（验者可签）在这个威胁模型里不是主要矛盾；换来的是零依赖、
  微秒级验签、契约测试可逐字节复现（fixtures/tickets/ 里的票是冻结 iat 后真签出来的）。
- **市面上同类**：EdDSA/RS256（非对称——验票方只持公钥，验者多签者少时必选）；
  PASETO（把"算法混淆"类 JWT 攻击从协议层堵死的设计）。
- **业务上怎么选**：签发方唯一且可信域封闭 → HMAC 够；第三方要能验你的票（你签它验）
  → 必须非对称（RS256/EdDSA），否则你把签名权也交了出去；对算法协商敏感的场景
  （header 里 alg 字段被塞 none 的老攻击）→ PASETO 或钉死算法白名单。

## 四、防线对号

| 防线 | 在本步的落点 |
|---|---|
| **INV-2**（一次性 + 参数绑定） | `params_hash` 烧进票面（params 取自卡不取自请求）；`used:false` 铸出、焚毁见 4.6；TTL 300s（mint.py:25） |
| **INV-9**（审批唯一依据是签名票） | token 三段 HMAC 签名，验签不信文本；`approved_by` 写死进票面随票走 |
| **INV-10**（状态机 409） | 廉价预检挡非 pending（省票），真仲裁在 decideApproval 事务（后到者 409，票作废 300s 自焚） |
| **INV-1**（fail-closed） | gateway 缺钥拒签 500；agent 铸票失败 502 `mint_failed`、卡保持 pending 可重试——"已批准无票"的悬置态结构上造不出来 |
| **D8 / FR-M7.5**（批什么执行什么） | 票面 tool+params_hash 双绑定；闸侧重算指纹对票（4.5 实测） |
| **INV-8**（审计记真人） | M2 审计 approve 行 actor=user:duty_lead（署名进台账）；卡上 approver/decided_at 同步落 |
| **密钥最小暴露** | SOC_HMAC_KEY 只在 gateway env（compose 不给默认值）；agent 出站铸票不持钥 |


把顺序反过来想想：先落 approved 再铸票，铸票失败就卡在"人说可以但没有授权书"——
卡不是 pending（重批 409）也不是 executed（没 token），死锁。**"先铸票后裁决"六个字
买的就是这条可重试路径**。边角：B4 那次我们第一次重试仍拿 502——gateway 容器起了
但 healthcheck 未过，服务还没就绪；稍等再试即可。故障实验自己也会故障，这是布景的
诚实。

**C · 并发双批的下场（纸面推演，3.3 实测过 409）**：两人同时批同一张卡，各自铸出
一枚票——裁决事务只放行先到者，后到者 409，他手里那枚 token 成了**已签名但无主**
的废纸。它不能执行（卡已 approved 且带 token_jti，闸认卡上的正本），300 秒 TTL 自焚
兜底。4.7 的保质期扫描会把这个下场演给你看（另一张卡因断链永远无法执行，token 同样
自焚——那枚 `ap_d00d9edd…` 现在应该已经过期了）。

**D · 纸面推演**：如果 agent 自己藏一把钥在 env 里本地签票——铸票不再有网络依赖，
故障实验 B 直接消失……代价是九个服务人人都持钥：任一容器被攻破 = 攻击者可自签任意
ApprovalToken（隔离任意主机）。集中铸票多了一跳网络，买的是"密钥只活在一个 env 里"。
公钥体系（RS256/EdDSA）能进一步把"验"和"签"分开——但那是生产化的下一阶段，教学版
先用拓扑（单点签发）弥补密码学（对称钥）的短板。
