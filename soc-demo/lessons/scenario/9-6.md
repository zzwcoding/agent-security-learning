# 场景 9 · 步 9.6 —— 收敛分岔与两个捣乱实验：hit 建案 / miss 归档 / 取消 / 预算烧光

> 环的收官站。judge 说 sufficient（9.4），轮次环走到岔路口——[TERMS「撒出去·收回来」](TERMS.md)条
> 的收敛分岔（行为约定 9）：**verdict=hit → 建案（concluded）**，查实了，回到场景 1 的世界
> （案子进 M2，S2 的调查链接着接手）；**verdict=miss → 证伪归档（refuted）**——没查实
> 不是白跑，归档案承载结论、假设关系登记入图，是「诚实的阴性资产」。另一条非收敛出路
> 也在这步讲完：**cancelled**——人取消与预算烧光，各自怎么安全停下，为什么 cancelled
> 永不冒充 refuted。
>
> 两个捣乱实验是本场景的正戏：① hunting 态取消——在途的活是安全停还是带病跑；
> ② 预算烧光——状态落 cancelled 不冒充 refuted。两个都亲手实测过，其中捣乱①的竞态
> 变体还真的撞出一个生产缺陷（已转票，见文末）。
>

### 站 2 · 五态收官与 S1 呼应：被动链 vs 主动环

📍 大图节点:HYP_FSM(9.6 收敛分岔)

到这里，[TERMS「状态机速记」](TERMS.md)hypothesis 行的五态全部走过了：

```
proposed --轮1 intake--> hunting --judge sufficient--> concluded（hit 建案）
                        |--judge sufficient--> refuted（miss 归档+register）
                        |--取消/预算/spin/planner_broken--> cancelled（原因标注）
```

**S1《一条 TP 告警的一生》的结构呼应**（本场景的开场问题，现在可以完整回答了）：

| | S1 被动链 | S9 主动环 |
|---|---|---|
| 起点 | 探头推来的报案单（别人告诉你出事了） | 数字员工自己写的怀疑书（我怀疑有事，去证明或证伪） |
| 形态 | 一条直线：进门→分诊→建案，走到终点即结束 | 一个环：选组合→扇出→收敛→不充分就换组合再来，直到终态 |
| 「下一步查什么」 | 上一步的结局决定（TP 才建案） | **本步查到的证据决定**（gap 驱动换组合——动态路由） |
| 终点 | 建案（进 S2 调查） | 建案（回到 S1 的世界）/ 证伪归档 / 取消 |
| 治理重点 | 验型、去重、verdict 锁 | 菜单围栏、防转、预算双闸、取消停止链 |

两环相扣：主动环的 hit 产出物就是被动链的输入物（案）。S1 结尾说「TP 建案之后是下半场」
（S2），S9 结尾说「hit 建案之后，案子同样进 S2 的调查链」——**同一个案卷，两条来路**。

## 三、捣乱实验①（必选）：hunting 态取消——子任务安全停还是带病跑

**实验设计**：假设在 hunting 态（轮次在途），值班长 POST cancel。要观察四件事：
账面几时变 cancelled；在途的轮次 run 与子 run 怎么停；下一轮还起不起；审计链全不全。

**步骤 1 · 挂上取消（等 status 一变 hunting 立刻 POST）：**

```bash
RESP=$(curl -s -X POST localhost:3002/api/v1/hypotheses -H 'content-type: application/json' \
  -H "x-actor-id: duty_lead@soc.local" -d '{"text":"捣乱A：取消实验","template_id":"hunt_webshell"}')
HYP=$(echo "$RESP" | python3 -c "import json,sys; print(json.load(sys.stdin)['hypothesis_id'])")
for i in $(seq 1 100); do
  ST=$(curl -s localhost:3002/api/v1/hypotheses/$HYP | python3 -c "import json,sys; print(json.load(sys.stdin)['status'])")
  if [ "$ST" = "hunting" ]; then
    curl -s -o /tmp/c.json -w "cancel: HTTP %{http_code}\n" -X POST localhost:3002/api/v1/hypotheses/$HYP/cancel \
      -H 'content-type: application/json' -H "x-actor-id: duty_lead@soc.local" \
      -d '{"by":"duty_lead@soc.local","reason":"user_cancelled"}'; break
  fi
  sleep 0.15
done
```

预期：`cancel: HTTP 200`，响应体 status=**cancelled**、cancel_reason=user_cancelled——
**账面秒落终态**（取消端点与 `hypothesis.cancelled` 事件同事务，[hypotheses.ts:175-187](soc-demo/services/case-backend/src/hypotheses.ts#L175)）。

**步骤 2 · 看 run 家谱怎么收场（等 5 秒）：**

```bash
sleep 5
sqlite3 "file:data/agent/agent.sqlite?mode=ro" \
  "SELECT r.kind, l.role, l.round_no, r.status, r.steps, r.fail_reason
   FROM runs r JOIN hunt_run_links l ON r.id=l.run_id WHERE l.hypothesis_id='$HYP' ORDER BY r.created_at;"
```

**实测结果**（我跑出来的形状）：

```
hunt_flow | round|1 | completed | 6 |          ← 轮 1 自然跑完（在途轮不被腰斩）
hunt_task | task|1  | failed    | 2 | node_error:execute   ← 子 run 死于签名契约（fake 参数）
hunt_task | task|1  | failed    | 2 | node_error:execute
hunt_flow | round|2 | failed    | 0 | node_error:intake    ← 轮 2 被拉起但 intake 拒开
```

事件流里轮 2 的最后一帧：`{"code":"node_error","node":"intake",
"message":"hypothesis_inactive:cancelled"}`（[flow.ts:100-103](soc-demo/services/agent/src/orchestration/flow.ts#L100)
的那个分支）。

**结论分四条**：

1. **在途轮安全停的口径是「不腰斩、不加新」**：取消信号经 `hypothesis.cancelled` 事件 →
   autorun 消费 → `requestCancel` 进取消板（[cancel.ts:114-157](soc-demo/services/agent/src/orchestration/cancel.ts#L114)，
   信号板首写 wins）→ 各 run 的**节点包装层**在每个节点进场前查板
   （[throwIfCancelled，cancel.ts:78-83](soc-demo/services/agent/src/orchestration/cancel.ts#L78)；
   父链 [flow.ts:54-69](soc-demo/services/agent/src/orchestration/flow.ts#L54)、子链
   [task-flow.ts:24-30](soc-demo/services/agent/src/orchestration/task-flow.ts#L24)、真执行体
   [hunt-executor.ts:142](soc-demo/services/agent/workers/investigation/hunt-executor.ts#L142)）。
   命中即抛 `BudgetExceededError(parent_cancelled)` 走 runner 既有强杀路径——**下一个节点
   边界即断，不再产生任何取证工作量**；已经跑完的节点不回滚。本实验里轮 1 跑得比取消
   信号快（信号要经 autorun 的 2s tick 中转），所以它是 completed 而不是 failed——
   **「安全停」的度量是停止后零新增工作，不是把在途工作炸掉**。
2. **未起的轮不起**：relay 照常拉起轮 2（幂等锚照落），但轮 2 intake 读 M2 账面发现
   已 cancelled → 炸响 → failed(hypothesis_inactive:cancelled)。**账面是终局裁决者**——
   就算 agent 进程内信号板还没来得及设，跨服务的状态机也不会让环继续转。
3. **审计链全程五条**（`GET /api/v1/audit?objectId=$HYP`）：create（user）→ transition
   proposed→hunting（agent:hunt_flow）→ **cancel（user，hunting→cancelled，reason）** →
   hunt_round_outcome（轮 1 归集）→ **hunt_cancel（agent:hunt_flow，source=user）**——
   人取消的账与机制停止的账**分两条各记各的**（INV-8）。
4. **竞态变体（进阶观察）**：我另做了一轮「轮 2 已过 intake 时才取消」的竞态——轮 2 继续跑
   到 judge(hit) → converge 建了案 → 状态迁移被 M2 409 弹回（cancelled→concluded 非法）
   → run failed(node_error:outcome)。**409 说明状态机守住了「cancelled 不可能被事后
   concluded」**；但 converge 的顺序是先建案后迁移（judge.ts:350→371），409 时案已经落——
   留下一个挂在已取消假设上的孤儿案、且无 hunt_case_created 审计。**这是实测撞出的
   生产缺陷，已转 [票 93](../.scratch/tickets/issues/93-hunt-converge-orphan-case.md)，
   本文章只如实记录不顺手修**。

## 四、捣乱实验②（必选）：预算烧光——状态落 cancelled 不冒充 refuted

**实验设计**：默认预算档烧不穿（fake 每调用 24 token，run 级 500k），所以用预算档位表
**既定的 env 覆写口子**（[budget.ts:120-121](soc-demo/services/agent/src/budget.ts#L120)：
`<KIND>_MAX_TOKENS_PER_RUN` 等键可 env 调档）把 run 级 token 档临时压到 50。教具做法：
临时 compose override 注入 env（零代码改动、用后即删还原），`docker compose up -d agent`。

```bash
cat > docker-compose.override.yml <<'EOF'
services:
  agent:
    environment:
      HUNT_FLOW_MAX_TOKENS_PER_RUN: "50"
EOF
docker compose up -d agent && sleep 10
```

**步骤 1 · 发起一条假设，等终态：**

```bash
RESP=$(curl -s -X POST localhost:3002/api/v1/hypotheses -H 'content-type: application/json' \
  -H "x-actor-id: soc1@soc.local" -d '{"text":"捣乱B：预算烧光实验","template_id":"hunt_webshell"}')
HYP=$(echo "$RESP" | python3 -c "import json,sys; print(json.load(sys.stdin)['hypothesis_id'])")
sleep 12
curl -s localhost:3002/api/v1/hypotheses/$HYP | python3 -c "
import json,sys; d=json.load(sys.stdin)
print('status:',d['status'],'| cancel_reason:',d['cancel_reason'],'| rounds:',len(d['rounds']))"
```

**实测结果**：

```
status: cancelled | cancel_reason: budget | rounds: 0
```

**步骤 2 · 对账三条线（run / 审计 / 事件）：**

```bash
sqlite3 "file:data/agent/agent.sqlite?mode=ro" \
  "SELECT r.status, r.steps, r.tokens_used, r.fail_reason FROM runs r
   JOIN hunt_run_links l ON r.id=l.run_id WHERE l.hypothesis_id='$HYP' AND l.role='round';"
curl -s "localhost:3002/api/v1/audit?objectId=$HYP" | python3 -c "
import json,sys
for a in json.load(sys.stdin): print(a['action'],'|',a['result'],'|',str(a.get('details'))[:80])"
sqlite3 "file:data/agent/agent.sqlite?mode=ro" \
  "SELECT substr(payload,1,140) FROM run_events WHERE run_id= \
   (SELECT run_id FROM hunt_run_links WHERE hypothesis_id='$HYP' AND role='round') AND type='error';"
```

**实测输出**：

```
failed | 5 | 72 | budget_exceeded:token_budget
create | SUCCESS | …
transition | SUCCESS | {'status': {'from': 'proposed', 'to': 'hunting'}}
transition | SUCCESS | {'status': {'from': 'hunting', 'to': 'cancelled'}, 'reason': 'budget'}
hunt_cancel | SUCCESS | {'reason': 'budget', 'source': 'budget'}
{"code":"budget_exceeded","kind":"token_budget","limit":50,"used":72,"node":"outcome"}
```

**机制链逐环对上**：

1. 轮 1 一路烧账：planner 24 + judge 24 = 48（<50 还活着）→ outcome 里 gap 翻译再 charge
   24 → **72 > 50**，`RunBudget.charge` 抛 `BudgetExceededError("token_budget")`
   （[budget.ts:87-92](soc-demo/services/agent/src/budget.ts#L87)）；
2. runner 强杀路径收口：failed + fail_reason=`budget_exceeded:token_budget` + kill 审计
   FAILURE + error 事件（[graph.ts:450-457](soc-demo/services/agent/src/graph.ts#L450)——
   「资源兜底触发要 Web 可见」）；
3. 取消机制消费 error 事件：只认轮次 run 的预算强杀
   （[cancel.ts:159-167](soc-demo/services/agent/src/orchestration/cancel.ts#L159) 的
   `link.role !== "round"` 过滤——子 run 的预算归子 run，不牵连全假设），档位映射
   token_budget → budget（[cancelReasonOfBudgetKind，:68-72](soc-demo/services/agent/src/orchestration/cancel.ts#L68)）；
4. `requestCancel` 把账面推到 cancelled(reason=budget)（远端 409 免重 PATCH 的口径见
   cancel.ts:123-129 注释）→ hunt_cancel 审计（source=budget）。

**预期断言（票面验收行）**：status=**cancelled**（不是 refuted、不是 hunting 挂死）、
cancel_reason=**budget**、rounds=0（轮没跑完就没有归集）、kill 审计 FAILURE 可回放。
**为什么不能冒充 refuted**——refuted 是「查了、证据说明假设不成立」的**裁决**；预算烧光
是「没查完」的**停止**。前者是证据结论、后者是资源事实，混用就是让台账说谎（9.5 的
spin 同款口径）。TERMS「状态机速记」hypothesis 行那句「取消六因只是 cancelled 的原因
标注」在这里长出了实体。

## 六、场景题闯关（S9 收官三题）

**题 1 · 五态轨迹**：一条假设从 proposed 到 concluded，状态机一共被推了几次、各由谁推、
各在哪一行代码？（答案要点：三次迁移——proposed→hunting 由轮 1 intake 的 startHunting
（flow.ts:99，actor=agent:hunt_flow）；hunting→concluded 由 converge 的 transition
（judge.ts:371）；都在 statemachine.ts:27-33 的查表里过闸。proposed 由 POST /api/v1/hypotheses
建出来（不算「推」）。变体：若中途 refuted，轮 2 intake 会炸 hypothesis_inactive（flow.ts:100-103）。）
