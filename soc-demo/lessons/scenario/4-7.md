# 场景 4 · 步 4.7 —— 保质期与队列：时间出的裁决也是裁决（收官）

> 主角卡批准了、票烧了、审计定案了——但系统里还漂着几样"没人理"的东西：没人批的
> pending 卡、铸了没花的 token、队列里排队的任务。它们不能永远悬着。本步讲**时间**
> 这位看不见的值班员：审批卡的保质期（APPROVAL_TTL，默认一天，超时作废、run 落终局）、
> token 的 300 秒寿命（过期即死）、以及 run_jobs 队列的"秒回-消费"异步形态——票 47
> 把"HTTP 请求替 supervisor 背执行期"翻转成"落队即回，后台细嚼慢咽"。文末是**场景 4
> 闯关三题**。
> 术语卡词翻 `TERMS.md`（同一比喻体系：审批卡/一次性密令/派活的…），老术语只回指
> 不另起解释。

## 一、操作（位置感）

本步两幕：

**第一幕（队列观察）**：拉一个非 chat 的 run，看"秒回"怎么发生——POST 返回时 run 才
queued，一秒内后台分发循环把它做完。顺手看 run_jobs 表的三态（pending→claimed→done）。

**第二幕（TTL 实弹）**：让一张 pending 卡**过期**。真实保质期是一天（86400 秒，等你
点不动）——教法是停栈把卡的 created_at 回拨一天再起栈，分发循环下一轮扫描就会办它：
卡 pending→expired、run 落 failed(approval_expired)、审计逐条留痕。（涉及停 agent 改
库——SQLite 铁律照旧：动库必先停容器；造的教具卡照例留档。）

本步实测素材：新造的卡 `apr_0d4cc044`（isolate_host，run `run_0525627d`），队列观察
对象 run `run_152a0010`（case_flow 直拉 case_000003）。

## 二、调用链

先看全景。分发循环的每一轮（默认 500ms 一轮）都在做两件事，顺序固定：

```
startRunDispatcher（agent 进程后台）
  │ 每 500ms 一轮 dispatchOnce
  ▼
[第①件] 审批卡保质期扫描（时间出的裁决优先于人可能出的裁决）
    listExpiredPendingApprovals(db, ttl)   ← pending 且 created_at 早于 ttl 截点的卡
    expireApprovalCard(卡)：一个事务四件事
        ① 状态机仲裁：只有 pending 能 expired（非 pending 409 回滚）
        ② UPDATE 卡 → expired
        ③ 审计 expire + 广播 approval_decided(decision:"expired", by:"system:approval_ttl")
        ④ run 终局：awaiting_approval → running → failed(approval_expired)（两步合法迁移）
  ▼
[第②件] 领任务执行（并发上限内，默认 1）
    claimRunJobs：事务内 pending→claimed（防双吃）
    execute(job)：start=铸票组图开跑 / resume=重组图续跑（4.3-4.5 的全部戏）
    completeRunJob：成功失败都算消费完毕（毒丸不重试、循环不崩）
  ▼
（下一轮……）
```

### 站 1 · 一轮两件事：时间优先于队列

📍 大图节点:TTL_SCAN（4.7 保质期与队列）

📄 [services/agent/src/run-dispatcher.ts:205-216](soc-demo/services/agent/src/run-dispatcher.ts#L205)

```ts
  // ① 审批卡保质期：超时 pending 卡自动作废 → run failed(approval_expired) + 审计
  const ttl = deps.approvalTtlSeconds ?? approvalTtlSecondsFromEnv();
  for (const card of listExpiredPendingApprovals(deps.db, ttl)) {
    try {
      expireApprovalCard(deps.db, card.id, ctx, ttl);
      res.expired.push(card.id);
      deps.log?.({ info: "approval_expired", approval_id: card.id, run_id: card.runId });
    } catch (err) {
      // 竞态兜底（卡刚被裁决等）：状态机会抛 409——下轮再看，不崩循环
      deps.log?.({ warn: "approval_expire_failed", approval_id: card.id, error: String(err) });
    }
  }
```

扫描在领任务**之前**——"过期"比"干活"急。先把这条接缝钉死，它回答一个容易懵的
问题"**TTL 到点了是谁发现的**"：没有独立的定时器，也没有 cron——**过期裁决由派活的
循环顺带扫出**（TERMS"派活的"条：run-dispatcher 循环 + run_jobs 表）：分发循环每轮
dispatchOnce（默认 500ms 一轮）在领任务之前先问一遍 `listExpiredPendingApprovals`
（pending 且 created_at 早于"now − 86400s"截点的卡），有就当场办它。循环不只得领
任务，还是时间裁决的执行者——所以过期不会在到点那一毫秒发生，而是在到点后的下一个
tick 发生（教学实验里回拨 created_at 后"起栈 8 秒内就办了"就是这个节奏）。为什么
过期比干活急？一张过期卡若先被批准，值班长批的
是一张系统已经判死的卡（审批状态机拦得住，但廉价预检只查 pending 不查截止时间）；
先扫掉，后面的裁决天然干净。catch 里那句注释是并发世界的礼貌：卡在你扫描和作废之间
恰好被批准了——状态机 409，下轮再看，**循环绝不为一个竞态崩掉**。

📄 [services/agent/src/approvals.ts:249-255](soc-demo/services/agent/src/approvals.ts#L249)

```ts
    // run 终局：awaiting_approval 不能直接 failed（状态机无此迁移）——照消费循环的
    // 认领语义先转回 running 再强杀，两步都是合法迁移，审计各留一条（INV-8）。
    const run = getRun(db, card.runId);
    if (run && (run.status === "awaiting_approval" || run.status === "running")) {
      if (run.status === "awaiting_approval") transitionRun(db, card.runId, "running", ctx);
      transitionRun(db, card.runId, "failed", ctx, "approval_expired");
    }
```

两段合起来是"过期"的全貌，四个要点：

1. **expired 是审批状态机的合法终态**（pending→expired 过状态机仲裁）——不是悄悄
   删行。审批台账上永远查得到"曾有一张卡，2026-09-10 造，次日过期"（INV-10：状态机
   之外的变更一律 409，过期的裁决也走正门）。
2. **过期审计记 actor=m3:dispatcher**——4.6 的 execute 记的是 m3:supervisor，这里记
   dispatcher：**裁决者是谁要留痕**，哪怕裁决者是时间本身。
3. **run 必须有终局**："过期"是时间出的裁决，run 不能永远挂在 awaiting_approval 上
   等一个永远不会来的批准（approvals.ts:215-219 注释原话）。
4. **两步迁移的迂回**：状态机没有 awaiting_approval→failed 这条边（看 CONTEXT.md
   状态机表），所以先转回 running 再强杀——**宁可绕两步合法迁移，不开一条直通的
   后门边**。本步实测的审计序完美复现了注释：`awaiting_approval→running（dispatcher）
   → running→failed, failReason=approval_expired（dispatcher）`，两条各留一笔。

本步实测（回拨 created_at 后起栈，扫描下一轮即办）：

```
审计：expire | m3:dispatcher | {"status":{"from":"pending","to":"expired"},
      "tool":"isolate_host","run_id":"run_0525627d-…","ttl_seconds":86400}
事件：approval_decided {"decision":"expired","by":"system:approval_ttl"}
run：run_0525627d → failed(approval_expired)
卡：apr_0d4cc044 → expired
```

### 站 3 · 队列秒回：POST 只负责落队

📍 大图节点:ENQ_202（4.7 保质期与队列）

另一件大事——票 47 的异步化形态。非 chat 的 run 拉起，请求只干一件事：

📄 [services/agent/src/app.ts:310-315](soc-demo/services/agent/src/app.ts#L310)

```ts
    // 票 47（ADR 0004-1）：非 chat kind 落 queued 即秒回——执行移交后台分发循环
    // （run-dispatcher）。铸票/组图/执行全跟着任务走进循环（铸票失败的 502 面随之
    // 变成 run failed(reason=mint_failed)，失败可观察且「不留无票 run」口径不变）。
    // actor 随任务落盘：异步后请求头早没了，close_flow 的确认审计还得记到人头上（票 39）。
    enqueueRunJob(db, run.id, "start", { actor });
    return reply.status(202).send({ run_id: run.id, status: run.status });
```

本步实测的完整时间线（case_flow 直拉 case_000003）：

```
POST /internal/runs → 202 {"run_id":"run_152a0010-…","status":"queued"}   ← 秒回
1 秒后查 run_jobs：38|run_152a0010-…|start|done                            ← 已被消费完
再查 runs：completed|2                                                     ← 两节点跑完
```

把"秒回"的接缝按老规矩钉一遍：**①产物此刻躺在哪**——`run_jobs` 表一行 start 任务
（pending）；**②等多久、谁接手**——分发循环（派活的）下一个 tick（≤500ms）领走；
**③两边的触发关系**——**没有**，202 是给调用方的回执，循环只认 run_jobs 表（TERMS
"派活的"条的常见误读原文在此照用）。整个场景 4 的审批链用的正是同一条队列：4.4 的
resume 诉求也是这样落表、被领走、才轮到 4.5 的验票执行。

细节两枚：① `enqueueRunJob` 的 payload 里塞了 actor——**异步后 HTTP 请求头早没了**，
close_flow 那类"记到人头上"的审计只能靠任务落盘时把人头带上（票 39 的先见）；② chat
是唯一例外（app.ts:304-308 注释：SSE 流本身就是产品，对话体验不能改成"先 202 再另开
流听"）——4.1 你看到的 chat 同步流是刻意的保留节目。

### 站 4 · 队列本体：一张 SQLite 表当 MQ

📍 大图节点:CLAIM（4.7 保质期与队列）

📄 [services/agent/src/run-dispatcher.ts:85-98](soc-demo/services/agent/src/run-dispatcher.ts#L85)

```ts
export function claimRunJobs(db: DB, limit: number): RunJobRow[] {
  return db.transaction(() => {
    const rows = (
      db.prepare("SELECT * FROM run_jobs WHERE state = 'pending' ORDER BY id LIMIT ?").all(limit) as Record<string, unknown>[]
    ).map((r) => mapJob(r) as RunJobRow);
    const at = nowMs();
    for (const j of rows) {
      db.prepare("UPDATE run_jobs SET state = 'claimed', claimed_at = ? WHERE id = ?").run(at, j.id);
      j.state = "claimed";
      j.claimedAt = at;
    }
    return rows;
  })();
}
```

领任务是一个事务：查 pending、改成 claimed、返回——**防双吃**（就算将来并发上限调大
或多进程部署，同一任务也只会被认领一次）。任务的一生三态：pending（排队）→claimed
（在办）→done（完结，成败都算——**毒丸不重试**，重试是 autorun 的事，run-dispatcher.ts:100
注释）。resume 诉求还有一层去重：

📄 [services/agent/src/run-dispatcher.ts:67-74](soc-demo/services/agent/src/run-dispatcher.ts#L67)

```ts
  if (action === "resume") {
    const existing = mapJob(
      db
        .prepare("SELECT * FROM run_jobs WHERE run_id = ? AND action = 'resume' AND state != 'done' ORDER BY id LIMIT 1")
        .get(runId) as Record<string, unknown>,
    );
    if (existing) return existing;
  }
```

同 run 未完结的 resume 任务复用一条——4.4 捣乱 B 里"gateway 没就绪连按两次批准"的
场景，若第二次也成功落卡，队列里不会叠出两个 resume（陈旧双批不叠加执行）。

### 站 5 · 两把时间尺：卡的 24 小时与票的 300 秒

📍 大图节点:TTL_SCAN（4.7 保质期与队列）

场景 4 里时间一共设了两道闸，量级差 288 倍，各有各的管区。分层口径先对齐：这两把尺
都是 4.4 分层预告里**③时效层**的展开——票的 300s 已经在验票闸兑现（4.5 S2 实测
token_expired），卡的 24h 在本步兑现；同一层，两个对象，两套节奏：

| | 审批卡保质期 | ApprovalToken 保质期 |
|---|---|---|
| 时长 | `APPROVAL_TTL_SECONDS`，默认 86400（run-dispatcher.ts:113-117） | `APPROVAL_TTL = 300`（mint.py:25） |
| 管谁 | **pending 的卡**（没被裁决的提请） | **已批准的票**（批准之后、执行之前） |
| 谁来执行裁决 | 分发循环 TTL 扫描（主动） | 验票闸验 exp（被动，4.5 S2 实测） |
| 过期后果 | 卡 expired + run failed(approval_expired) | 403 token_expired，票作废（卡还是 approved——但永远执行不了了） |
| 节奏隐喻 | 人的节奏：一天之内想清楚批不批 | 机器的节奏：批完五分钟内必须干完 |

布景里现成的两枚教具正好各占一边：4.7 实验卡 `apr_0d4cc044`（pending 过期——卡的
24 小时尺）；4.3 断链教具的票 `ap_d00d9edd`（批准后永远没能执行，300 秒一到即死——
票的 300 秒尺，4.5 脚本 S2 实测过同款拒因）。**批准不是永久授权：批的动作有下限保质
期（票 300s），批的资格有上限保质期（卡 24h）**。再补一句"为什么票比手令短"：
L2 一次性密令的 300s 比 L1 任务票的 900s（TERMS"手令"条）短三倍——**越危险越短命**，
不可逆动作的授权窗每多一秒，重放/误用的暴露面就多一秒（4.4 站 3 mint.py:25 的口径）。

### 站 6 · 进程死了怎么办：重启恢复

📍 大图节点:RECOVER（4.7 保质期与队列）

分发循环开工前先收一次盘面（recoverDispatcherState，run-dispatcher.ts:132-165）：
claimed 没人认领的任务回 pending（"claimed 是进程内的手，进程没了手就松开"）；孤儿
running 判 failed(orphaned_by_restart) 而不是重置重跑——**重跑会让图从头重放节点，
M2 时间线/审计重复留痕**；孤儿已终局的 start 任务作废。本场景 4.3/4.5 的实验重启过
agent 两次，都没触发孤儿判定（没有 run 恰好死在 running）——纸面推演留着：谁想实测，
起一个 case_flow 后立刻 stop agent 再 start，audit 里就会多一行 kill(orphaned_by_restart)。

## 三、服务与中间件卡

### 卡 1（自研）· SQLite 表当队列：不要 MQ 的勇气

- **它是什么**：run_jobs 一张表 + enqueueRunJob/claimRunJobs/completeRunJob 三个函数，
  外加 500ms 的轮询循环。ADR 0004-1 的裁决：**不引入消息中间件产品**——队列的诉求
  （start/resume 两类待办）总量小、可靠性要求（不丢、不双吃）靠 SQLite 事务天然满足、
  运维面零新增。
- **为什么成立**：单 agent 进程消费（RUN_DISPATCH 并发默认 1）、任务量是人审批节奏
  的（一天几十个）、且真相库本来就是 SQLite——把队列放同一个库里，"任务与状态一致"
  是免费的（enqueue 与决定落卡同进程同事务域）。MQ 的真正收益（跨机分发、削峰、
  百万级吞吐）在这里一个都用不上。
- **市面上同类**：RabbitMQ/Redis Stream/Kafka（按吞吐与拓扑复杂度递增）；Postgres
  SKIP LOCKED 队列（同思想的"用数据库当队列"正装版）；Temporal（队列+工作流引擎
  合体）。
- **业务上怎么选**：任务量小于人的审批节奏 → 数据库表+轮询，把复杂度预算省给别处；
  多消费者/跨机/需要重试拓扑 → 上 MQ，但把"任务与状态同库"的一致性重新自己挣；
  长事务多人工节点 → 直接上工作流引擎。**判断依据是消费侧的拓扑，不是"队列"这个词
  听起来多专业**。

### 卡 2（领域）· 两个 TTL 的分工：审批系统的"双钟"

- **它是什么**：卡钟（24h，人的节奏——一天之内不想清楚就别批了）和票钟（300s，机器
  的节奏——批完立刻就该干完）。两钟之间还有个隐含约束：**resume 通常在批准后毫秒级
  发生**（分发循环 100-500ms 接单），所以 300s 的票窗在正常运行里绰绰有余；真正吃满
  300s 的场景只有异常（队列堵死、进程反复崩溃）——而那正是你希望票作废的场景。
- **市面上同类**：OAuth 授权码 10 分钟 + access token 15 分钟-2 小时的双层设计
  （授权码=卡的节奏，access token=票的节奏，连"短的管执行、长的管资格"都同构）；
  银行的预约转账（预约单 24h 有效 + 单次验证码 5 分钟）。
- **业务上怎么选**：两个 TTL 的比值要跟着人工介入的节奏走——值班长批示高峰是
  小时级，卡钟 24h 合理；若审批要跨周会签，卡钟得拉到周级且票钟不变（批准瞬间的
  执行窗依旧短）。**给"批准"设保质期常被忘掉，但它恰恰是防"橡皮图章化"的关键：
  一张三个月前的卡今天被批准，今天的人根本不记得当时为什么提请**。

|---|---|

## 六、捣乱实验（必选）

**A · 过期卡还想批复活（本步主实验）**：3.3 的 409 后到者实验换了个更狠的版本——
对 expired 卡按批准：

```bash
curl -s -w " | HTTP %{http_code}\n" -X POST \
  http://127.0.0.1:3003/api/v1/approvals/apr_0d4cc044-1c9f-4c29-b664-60a7980c3286/approve \
  -H 'content-type: application/json' -d '{"approver":"duty_lead"}'
# 预期：{"error":"InvalidTransition"} | HTTP 409   ← 廉价预检直接挡：expired ≠ pending
```

想救活它？唯一正路是**重新提请**（chat 再说一遍，开新卡走新审批）——过期不可撤销，
跟 3.2 的"终态再裁 409"同一哲学：终局就是终局。

**B · 重复的 resume 诉求（队列层的幂等）**：纸面推演——4.4 捣乱 B 里 gateway 未就绪
连按批准只成功一次；假如两次都成功呢？decideApproval 状态机让第二次 409（决定只落
一次），但两次都会走到 enqueueRunJob——run-dispatcher.ts:66-73 的去重在这里收口：
同 run 未完结的 resume 复用一条，队列不叠任务，续跑至多执行一次。**去重不住在 HTTP
层（幂等键），住在队列层**——因为这里知道"同一个 run 不需要醒来两次"。

**C · 毒丸任务（纸面推演）**：假如某个 run 的图一跑就炸（比如注个坏的 kind）——
execute 抛错 → catch 记 failed → **finally 里 completeRunJob 照样执行**（run-dispatcher.ts:228-230）。
任务完结、循环健康、错误只在日志面。对照 3.5 的 autorun（事件消费失败不推游标=会
重试）：**队列的失败哲学是"毒丸不重试"（重试交给上游），事件桥的失败哲学是"不推
游标=必然重试"**——两座桥对失败的态度相反，因为容错的位置不同：队列后面是人可观察
的 run 终态，事件桥后面是不能再丢的游标。

**D · 纸面推演：假如没有 TTL 扫描**？pending 卡永远 pending、挂起 run 永远
awaiting_approval。三个月后一位新值班长清理积压，看到一张三个月前的"隔离 app-01"
提请，顺手批准——信封链完好（4.3 证过它不受时间影响）、图照常复活、token 铸出、
五秒内 app-01 被隔离。**没有人做错了什么**：卡是真的、批准是真签的、执行是合规的——
除了这个提请早就过时了。TTL 扫描防的就是这个：**审批的"资格"和"意愿"都会过期，
系统必须替人记住这件事**（approvals.ts:215-219 注释："「过期」是时间出的裁决"）。

**题 1 · 批准按钮之后的三秒**：值班长按下批准，approve 端点 200 返回

<details><summary>答案</summary>

顺序（4.4 站 2-4 → 4.5 六站）：① decideApproval 决定落卡（approved + token/token_jti
落卡，审批审计记 duty_lead）→ ② enqueueRunJob(resume) → ③ 端点 200 秒回（此刻执行
尚未发生——**批准 ≠ 执行**）→ ④ 分发循环 claimRunJobs 领任务 → ⑤ executeResumeJob
重铸 L1 任务票、重组 worker 图 → ⑥ resumeRun：状态门（awaiting_approval）+ 信封链
整链复核 → ⑦ Command(resume) 唤醒，execute 节点**从头重跑** → ⑧ awaitApproval 查卡
拿到 approved+token → ⑨ resolveUsed 装填：问 M2 used_tokens 读口 → ⑩ 验票闸五连

→ ⑬ tool_result 事件 → run completed。

卡已 approved（票随 300s TTL 自焚）。fail-closed 的代价恰恰是它的价值：裁判不在场，
枪不响。

**题 2 · 三张"过期"的牌**：同样放一个月不做任何事，下列三者各自的结局？
（a）pending 的审批卡；（b）approved 卡上铸出但没执行的 ApprovalToken；（c）焚毁登记
后的 used_tokens 行。顺带说明：为什么（b）的死亡对系统是**好事**？

<details><summary>答案</summary>

（a）**被 TTL 扫描作废**：pending→expired（审批状态机终态），run 两步合法迁移落
failed(approval_expired)，expire 审计 actor=m3:dispatcher、ttl_seconds 落 details
（4.7 主实验）。没有终局才是 bug——"过期是时间出的裁决"。（b）**token_expired 死亡**：
票的 exp 是 300 秒后（4.4 站 3），一个月后任何人拿它过闸都是 403；卡本身还是 approved
（TTL 只扫 pending），但这张卡永远执行不了了——除非重新提请开新卡。它死得其所：
**票的短命封顶了"批准后执行窗"的长度**，也就封顶了 4.6 捣乱 C 那种崩溃窗口的重放
风险——批准的效力必须随时间衰减，否则一张被遗忘的票就是一枚埋着的雷。（c）**永生**：
used_tokens 是焚毁账本，没有 TTL、没有清理——重放防线要求"烧过"这件事被**永远**
记住（UNIQUE 约束永久拦截同 jti 二次登记，4.6 捣乱 A 实测 409）。三张牌：资格会过期、
执行窗会过期、**案底永不过期**。

</details>
