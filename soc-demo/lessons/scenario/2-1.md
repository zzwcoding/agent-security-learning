# 场景 2 · 步 2.1 —— case_flow 拉起与调查子图入口（investigate_case、related_alerts）

> 场景 1 里我们看着一条告警走完「分诊六节点」，TP 的结局是建案。建案之后， PRD §4.2 的
> 故事还有下半场：**调查**（把案子查透）和**富化**（把可疑指标送去体检）。本步只回答两个问题：
> **这条调查链是怎么被拉起来的？** 拉起来之后，**第一站进了哪里、第一颗子弹（related_alerts 工具）
> 是怎么从 LLM 的一句话变成一条真实查询的？** 工具循环的缰绳（防打转、上下文治理）留到 2.2，
> 调查报告留到 2.3，富化留到 2.4。

---

## 一、操作（位置感）

先在系统里找到「调查」这个动作的入口。

**入口有两个，共用同一条链**：

1. **链上**（场景 1 已经见过）：分诊 TP 建案后，**同一个 run 内**接着跑调查+富化——
   建案型 run_0e4cddbb 的 41 条事件里，后半段就是它（1.6 只指了个路，没进门）。
2. **直拉**（本步主角）：对**已经存在的案件**，直接 `POST /internal/runs` 声明
   `{"kind":"case_flow","case_id":"..."}`——相当于保安队长对一桩旧案说：**专案组，重新进场查一遍**。

用浏览器开 web 端（http://localhost:5173），进「流水线」页：case_flow 这种 kind 在视图里
是两个方格子——`investigate_case → enrich_case`。记住这两个格子名，一会儿调用链里
你会发现**格子是外壳，里面还藏着一整个子图**。

本步布景（承接场景 1）：栈全绿，4 个案件（case_000001=db-01 rootkit、case_000003=web-01
合案）、15 条告警。主角是 **case_000001**——场景 1 链上调查已经给它写过一份调查报告，
本步直拉再让它长一份，顺便验证「重复拉起会怎样」。

## 二、调用链

先看全景。从你在终端敲下 curl 到报告落进案件时间线，全程八站：

```
你（或自动化脚本）
  │  POST /internal/runs  {"kind":"case_flow","case_id":"case_000001"}
  ▼
[站1] agent 正门 :3003 —— 注册表校验（intake="case" → 必须带 case_id）
  │  createRun：runs 表插一行 queued + 审计 create          ← 202 秒回
  ▼
[站2] 分发循环捡起任务 —— 按注册表票面找 gateway 铸任务票（票面绑定 case_000001）
  ▼
[站3] executeRun 拼交接态 —— {kind:"case_flow", case_id:"case_000001"} 塞进图的状态
  ▼
[站4] investigate_case 交接节点（外壳）—— 从交接态摸出 case_id，
  │     开一块干净子白板，把调查子图整个跑一遍
  ▼
[站5] load_case（子图内）—— 读案件详情 + primary 告警日期锚点
  ▼
[站6] plan（子图内）—— LLM 列调查任务清单
  ▼
[站7] tool_loop（子图内）—— LLM 裁决 → 签名契约 → 亮票过闸 → 执行
  │     第一颗子弹：related_alerts（翻 M2 报案登记台账做同主机聚合）
  ▼
[站8] report_llm → write_timeline（子图内）—— 报告落案件时间线（2.3 细讲）
```

### 站 1 · 正门：同一个门，吃不同的 id

正门 `POST /internal/runs` 在 1.3 已经逐行走过（注册表校验 → createRun → 入队 → 202）。
case_flow 走的是**同一个门**，差别只在进门时的体检项目——1.3 那条告警流吃 `alert_id`，
这条案件流吃 `case_id`，谁吃什么由注册表里的 `intake` 字段说了算：

📄 [services/agent/src/app.ts:264-272](soc-demo/services/agent/src/app.ts#L264)

```ts
    const desc = runKindOf(body.kind);
    if (!desc) {
      return reply.status(400).send({ error: "unknown_kind", details: [body.kind] });
    }
    if (desc.intake === "case") {
      if (!body.case_id) return reply.status(400).send({ error: "case_id_required" });
    } else if (!body.alert_id) {
      return reply.status(400).send({ error: "kind_and_alert_id_required" });
    }
```

注意它只查了 **case_id 非空**，没查案件真的存在——这个「宽进」埋着本步捣乱实验 A 的伏笔。
后面的 createRun、入队、202 秒回与 1.3 完全同一路（[app.ts:289-315](soc-demo/services/agent/src/app.ts#L289)），
不再重复。

那 case_flow 在注册表里长什么样？——一个 kind 的全部静态知识（吃什么 id、票面、图工厂）
都在这一条描述符里：

📄 [services/agent/src/run-kinds.ts:220-232](soc-demo/services/agent/src/run-kinds.ts#L220)

```ts
  case_flow: {
    intake: "case",
    pipelineNodes: CASE_FLOW_NODES,
    ticket: {
      // 票 36：case_flow 的链上两 worker（调查 m5 + 富化 m6）同 run 共票——allowed_tools =
      // 两个 L1 工具族的并集（INV-3 依旧：并集里没有任何 L2），scope 只含案件读写。
      sub: "agent:case_flow",
      scope: ["case:read", "case:write"],
      allowedTools: [...new Set([...INVESTIGATION_TOOLS, ...ENRICHMENT_TOOLS])],
    },

  },
```

票面三行值得逐字读：`scope` 只有案件的读写（`case:read`/`case:write`）；
`allowed_tools` 是**调查六件 ∪ 富化工具**去重后的并集——因为一张任务票在拉起时就要铸好，
而这张票要伺候链上两个 worker（2.4 你会见到富化的工具面）。并集里**没有任何 L2**：
`isolate_host`（隔离主机）这种高危动作连票面都进不去（INV-3）。LLM 就算在报告里
提议「隔离 db-01」，也只是一行**建议文字**——它手里根本没有执行那张票。

### 站 2 · 铸票：这张票从出生就绑定案件

分发循环捡起 start 任务后铸票。这里有个 1.3 没有的细节——**case_flow 的票铸出来时就
绑定了案件**，分诊票做不到（分诊开跑时案件还不存在）：

📄 [services/agent/src/app.ts:379-388](soc-demo/services/agent/src/app.ts#L379)

```ts
        const spec = requireRunKind(run.kind).ticket;
        const minted = await mint.mintTaskTicket({
          jti: `tk_${randomUUID()}`,
          sub: spec.sub,
          // 分诊时还没有 case（闸侧跳过绑定校验）；其余 kind 绑定案件（FR-S2.2）——
          // 票 36 起 case_flow 同 knowledge_flow 口径：case_id 随拉起即在
          caseId: run.kind === "alert_flow" ? null : run.caseId,
          runId: run.id,
          scope: [...spec.scope],
          allowedTools: [...spec.allowedTools],
        });
```

`caseId: run.kind === "alert_flow" ? null : run.caseId` 这一行就是两个世界的分界线：
分诊票不绑案（案还没建），case_flow 票**出生即绑 case_000001**。绑定的好处是：
这张票拿去动别的案件的写口时，闸会认出「票和案对不上」而拒收——手令上写的是
查 1 号档案柜，就不能拿去开 3 号柜。

### 站 3 · 交接态：case_id 怎么进到图里

票铸好、图组好，开跑前还要把 run 行里的案件 id 交给图。交接态（state）就是图的
**案卷首页**，第一页上写着「本次 run 查的是哪个案子」：

📄 [services/agent/src/graph.ts:484-486](soc-demo/services/agent/src/graph.ts#L484)

```ts
    initialState: opts.initialState ?? (run.caseId
      ? { kind: run.kind, case_id: run.caseId }
      : { kind: run.kind, alert_id: run.alertId }),
```

run 行里有 caseId（case_flow 拉起时就在）→ 首页写 `{kind:"case_flow", case_id:"case_000001"}`；
没有 caseId（alert_flow）→ 写 alert_id。就这一条三元，决定了后面每一站去哪找实体。

### 站 4 · investigate_case：交接节点是外壳，不是子图本体

现在到本步最有意思的设计。调查子图（load_case→plan→tool_loop→report_llm→write_timeline
五个内部节点）**并不直接铺在 runner 的大图里**，而是被一个叫 `investigate_case` 的
**交接节点**整个包起来。先看外壳名单：

📄 [services/agent/workers/case-flow.ts:31-34](soc-demo/services/agent/workers/case-flow.ts#L31)

```ts
/** web 流水线视图的 case_flow 预置骨架（FR-M10.2）。名单与
 *  fixtures/sse-events.json flow_nodes.case_flow 两端契约锁
 *  （agent 侧闸 = src/case-flow.test.ts，web 侧闸 = pipeline.test.ts）。 */
export const CASE_FLOW_NODES = ["investigate_case", "enrich_case"] as const;
```

web 流水线页上那两个格子就是这行名单——**外壳只露两个节点**。为什么不把子图五个节点
直接铺进大图？文件头注释讲了两条硬理由（[case-flow.ts:22-26](soc-demo/services/agent/workers/case-flow.ts#L22)）：
调查和富化子图**各有一个叫 `load_case` 的节点**，LangGraph 一张 StateGraph 里同名节点
没法共存；而且 alert_flow 组图时案件还不存在，没法预组子图。所以用一个交接节点把子图
「整团」捧在手里。

交接节点本体：

📄 [services/agent/workers/case-flow.ts:43-63](soc-demo/services/agent/workers/case-flow.ts#L43)

```ts
/** 交接态里的案件 id：case_flow 直拉 = run.caseId；alert_flow 链上 = TP 建案
 *  （outcome 的 create_case 分支）写入。没有 = 本 run 没建案（FP/BTP/Uncertain、
 *  并入旧案的 merge 分支）→ 链整体空转跳过。 */
function caseIdOf(ctx: NodeCtx): string | null {
  const v = ctx.state.case_id;
  return typeof v === "string" && v !== "" ? v : null;
}

export function makeCaseFlow(deps: CaseFlowDeps): FlowNode[] {
  return [
    {
      name: "investigate_case",
      run: async (ctx) => {
        const caseId = caseIdOf(ctx);
        if (!caseId) return;
        // 子状态隔离：worker 子图按 {case_id, ticket} 交接（m5 卡）在干净状态上跑，
        // 产物以命名空间键并回主状态——不与分诊前段的 case/outcome 等键互踩。
        const sub: NodeCtx = { ...ctx, state: { case_id: caseId } };
        for (const n of makeInvestigationFlow({ ...deps.invest, caseId })) await n.run(sub);
        ctx.state.investigation = { outcome: sub.state.outcome };
      },
    },
```

三个动作，比喻着看很顺：

- `caseIdOf`：**翻案卷首页**找案件号。直拉的 case_flow，案号是站 3 写上去的；
  链上的 alert_flow，案号是分诊 outcome 节点建案那一刻才写上去的——**两种入口
  在这里汇成同一种读法**，这就是「两入口共用一条链」的全部实现。
- `if (!caseId) return;`：**没案子就散会**。场景 1 的主角 run_e7db506a 是 merge 分支
  （并进旧案、没建新案），它跑链上这两格时就是在这里安静空转——事件流里只有
  node_enter/node_exit，一行工具帧都没有（1.6 你数过）。
- `state: { case_id: caseId }`：**给专案组开一块干净白板**。子图在只有 case_id 的
  新状态上跑，不把分诊前段的一堆中间变量带进来；跑完只把成果 `investigation.outcome`
  抄回大状态。前台的白板和专案组的白板互不涂改。

**内部节点去哪了？** runner 只给外壳两节点发 node_enter/node_exit 帧（所以 run 行
steps=2），但子图内部绝不是黑箱——每个工具帧和审计帧都带着**内部节点名**。看本步
实测事件流（站 7 之后统一看）就一目了然。

### 站 5 · load_case：把案子读成一张「调查简报」

进入子图第一站。注意它的注释——读案件不走 LLM 工具面，是 adapter 直读（省票面额度，
也因为这一步不需要智能）：

📄 [services/agent/workers/investigation/flow.ts:282-298](soc-demo/services/agent/workers/investigation/flow.ts#L282)

```ts
    {
      name: "load_case",
      run: async (ctx) => {
        cursor.node = "load_case";
        // run 主体的装配读（case_id 来自 run 交接态，不经 LLM）——与票 13 的
        // claimVerdict/patchOutcome 同类：M2 直连 adapter 读，不占 LLM 工具面。
        const detail = await deps.m2.getCaseDetail(deps.caseId);
        if (!detail) throw new Error(`case_not_found:${deps.caseId}`);
        // primary alert 日期 = 查询窗锚点（get_alert 在 A.1 里属分诊/调查共用 L0，过闸）
        const primaryId = detail.linkedAlerts[0];
        let primaryAlertDate = detail.startDate;
        if (primaryId) {
          const alert = await gated(ctx, "get_alert", { alert_id: primaryId }, () => deps.m2.getAlert(primaryId));
          if (alert && typeof alert.date === "number") primaryAlertDate = alert.date;
        }
        ctx.state.case = caseViewOf(detail, primaryAlertDate);
      },
    },
```

四件事：

1. `getCaseDetail` 读案件详情——**档案室直读**，不亮票（adapter 读口，同分诊的
   claimVerdict 一族）。案件不存在就抛 `case_not_found`——这行 throw 就是捣乱实验 A
   的爆点，伏笔见后文。
2. 取 `linkedAlerts[0]` 当 **primary 告警**，并**亮票**（`gated`，L0 工具 `get_alert`）
   读它的日期——这个日期是后面所有查询的**时间窗锚点**。
3. 锚点默认值是 `detail.startDate`（建案时间）。注意一个细节： startDate 是**建案的
   墙钟时间**（我们的案例里是 2026 年！），而告警的 date 是**事发时间**（语料里是
   2023 年）。只要 linkedAlerts[0] 读得到，锚点就会用告警日期覆盖建案日期——查 2023
   年的事，就该用 2023 年的窗口。
4. `caseViewOf` 把案件详情折成一张**调查简报**（CaseView）：

📄 [services/agent/workers/investigation/flow.ts:130-149](soc-demo/services/agent/workers/investigation/flow.ts#L130)

```ts
  const caseViewOf = (detail: {
    id: string; title: string; severity: number; status: string;
    observables?: { dataType: string; data: string }[];
  }, primaryAlertDate: number): CaseView => {
    const obs = detail.observables ?? [];
    const byType = (t: string): string[] => obs.filter((o) => o.dataType === t).map((o) => o.data);
    return {
      caseId: detail.id,
      title: detail.title,
      severity: detail.severity,
      status: detail.status,
      entities: {
        ips: byType("ip"),
        users: byType("other"), // seed 映射口径：srcuser → dataType "other"
        hosts: byType("hostname"),
        files: byType("filename"),
      },
      primaryAlertDate,
    };
  };
```

简报上只有五样：案子是谁、多严重、什么状态、手里有哪些实体（IP/用户/主机/文件）、
锚点日期。case_000001 的简报读出来就是：主机 db-01，severity 2，没有 IP 没有用户，
锚点 = 告警 60d38721 的日期。**后面 LLM 做的所有决定，都以这张简报为出发点。**

### 站 6 · plan：先列任务清单，再动手

调查不是上来就乱查，先让 LLM 出一份任务清单：

prompt 由简报拼装（[prompt.ts:231-239](soc-demo/services/agent/workers/investigation/prompt.ts#L231)），
最后一句特意嘱咐「所有查询强制带 time_window，窗口从 primary alert 日期出发」。
生产里这行代码我们布景是 fake LLM，它的「思考」是确定性规则——**按实体优先级
（ip→user→host）排 pivot 查询，有主机就排同主机聚合，有主机或用户就排 KB 核验**：

📄 [services/agent/workers/investigation/llm.ts:46-54](soc-demo/services/agent/workers/investigation/llm.ts#L46)

```ts
  async plan(call: PlanCall): Promise<{ tasks: string[]; tokens: number }> {
    const e = call.input.case.entities;
    const pivot = e.ips[0] ?? e.users[0] ?? e.hosts[0];
    const tasks: string[] = [];
    if (pivot) tasks.push(`siem_query 按 ${pivot} pivot 查询（强制时间窗）`);
    if (e.hosts[0]) tasks.push(`related_alerts 聚合同主机 ${e.hosts[0]} 的历史告警`);
    if (e.hosts[0] || e.users[0]) tasks.push("kb_verify 内部事实核验（资产/用户清单）");
    return { tasks, tokens: this.tokensPerCall };
  }
```

任务清单会作为一条 `audit` 事件广播出去——你等会儿在事件流里会亲眼看到这三行任务。
fake 的任务清单永远一样（同一个案子），real LLM 的清单会随案件不同而变化，但**消费
清单的方式完全一样**——这就是 fake/real 共用契约的意义。

### 站 7 · related_alerts：一颗子弹从「想法」到「查询」的全路径

tool_loop 是 2.2 的主角，这里只借它的一圈，看**一次工具调用**要过几道关。伪代码
（真实实现见 [flow.ts:313-414](soc-demo/services/agent/workers/investigation/flow.ts#L313)，2.2 拆解）：

```
伪代码 —— tool_loop 的一圈：
  d = LLM 裁决（下一步调什么工具、带什么参数）         ← llm.decide
  若 d == finish：出循环
  ① 防打转：同工具+同参数 已查过？→ 拒绝，记审计        （2.2）
  ② 签名契约：validateToolCall(tool, params)           ← 本站讲
  ③ 亮票过闸：makeGatedCall → verifyTicket             ← 本站讲
  ④ 执行：execTool 分派到 adapter
  ⑤ 观察治理：guards 扫描 + 摘要/落盘                  ← 本站讲扫描，细则 2.2
  观察记录进 observations，喂回下一圈 LLM
```

**第一关：LLM 怎么决定调 related_alerts？** fake 的裁决规则——siem_query 查完才轮到它
（[llm.ts:68-71](soc-demo/services/agent/workers/investigation/llm.ts#L68)）：

```ts
    if (!done.has("related_alerts") && e.hosts[0]) {
      // FR-M5.2 同主机历史告警聚合
      return { kind: "tool", tool: "related_alerts", params: { scope: "host", value: e.hosts[0], time_window: win }, tokens: this.tokensPerCall };
    }
```

参数三件套：`scope:"host"`、`value:"db-01"`、`time_window`（锚点 ±24h，由
[llm.ts:32-37](soc-demo/services/agent/workers/investigation/llm.ts#L32) 的 `windowAround` 算出）。

**第二关：签名契约。** 参数形态不对就打回，不执行也不烧后端——错误作为「观察」喂回
LLM 让它换路子（PRD 的说法：工具报错计入证据缺口并继续）。related_alerts 的契约段：

📄 [services/agent/workers/investigation/prompt.ts:114-119](soc-demo/services/agent/workers/investigation/prompt.ts#L114)

```ts
    case "related_alerts": {
      const scope = params.scope;
      if (scope !== "entity" && scope !== "rule" && scope !== "host") return { ok: false, error: "bad_scope" };
      if (!nonEmpty(params.value)) return { ok: false, error: "value_required" };

```

`checkTimeWindow`（[prompt.ts:82-90](soc-demo/services/agent/workers/investigation/prompt.ts#L82)）
是「查询强制时间窗」契约的执行体：必须有、from/to 都得是能解析的时刻、还得 from ≤ to，
缺一样报 `time_window_required` / `bad_time_window.*`，**绝不替 LLM 补默认值**——不给
「查全库」这个选项，是上下文治理的第一道闸（完整的缰绳故事 2.2 讲）。

**第三关：亮票过闸。** 工具调用只有一个入口 `gated`，它就是 1.4 见过的 makeGatedCall
的又一处装配（[flow.ts:112-126](soc-demo/services/agent/workers/investigation/flow.ts#L112)）：
广播 `tool_call` 帧 → verifyTicket 验 HMAC 任务票（sub/scope/allowed_tools/案件绑定/
TTL 全查）→ 放行执行 → 广播 `tool_result` 帧。**闸拒 = 审计 DENIED + 抛错强杀整个 run**，
绝不带病运行（INV-1）。

**第四关：执行。** execTool 的分派（[flow.ts:164-170](soc-demo/services/agent/workers/investigation/flow.ts#L164)）
把 related_alerts 路由到 adapter 函数：

```ts
      case "related_alerts":

          scope: params.scope as "entity" | "rule" | "host",
```

**第五关：related_alerts 本体——翻报案登记台账的确定性过滤。** 注意它查的**不是 SIEM**
（监控录像库是另一个工具 siem_query，2.2 讲），而是 **M2 案件后端的告警库**——
「系统里登记过的所有报案」：

📄 [services/agent/workers/investigation/m2.ts:116-146](soc-demo/services/agent/workers/investigation/m2.ts#L116)

```ts
function matchesScope(alert: AlertDto, scope: RelatedScope, value: string): boolean {
  const obs = alert.observables ?? [];
  if (scope === "host") return obs.some((o) => o.dataType === "hostname" && o.data === value);
  if (scope === "rule") return alert.tags.includes(value);
  // entity：ip observable 或 srcuser（seed 映射口径 srcuser → dataType "other"）
  return obs.some(
    (o) => (o.dataType === "ip" || o.dataType === "other") && o.data === value,
  );
}

/** related_alerts 工具的执行体（flow 里经 gated 调用）。数据源 = M2 告警库：
 *  系统内见过的历史告警聚合，与 siem_query（fixture SIEM 语料）互补。 */
export async function relatedAlerts(m2: InvestigationM2, params: RelatedAlertsParams): Promise<RelatedAlertsResult> {
  const all = await m2.listAlerts();
  const from = Date.parse(params.time_window.from);
  const to = Date.parse(params.time_window.to);
  const matched = all.filter((a) => {
    const t = typeof a.date === "number" ? a.date : Date.parse(String(a.date));
    return t >= from && t <= to && matchesScope(a, params.scope, params.value);
  });
  return {
    total: matched.length,
    alerts: matched.slice(0, params.max_results ?? 10).map((a) => ({
      id: a.id,
      title: a.title,
      severity: a.severity,
      status: a.status,
      date: a.date,
    })),
  };
}
```

三个必看的点：

1. **确定性**：没有一行 LLM。拉全量告警列表 → 按时间窗过滤 → 按范围匹配（host 比对
   hostname observable；rule 比对 tags；entity 比对 ip/srcuser）→ 排序无关地返回。
   同样的问题永远同样的答案，所以它是**可复算**的——亲手验证第 3 步我们就复算一遍。
2. **total 与返回列表可以不一样**：`total` 是真命中数，`alerts` 数组被
   `max_results ?? 10` 截断。这是一个「诚实接口」：告诉 LLM 台账上总共有 11 条，
   但只递给它前 10 张卡片——既不撒谎也不撑爆上下文。
3. **数据源口径**：related_alerts 只看得到**进了系统的**告警（M2 库）；SIEM 语料里
   有、但没推过 webhook 的日志它看不见。反过来 siem_query 查的 fixture 语料里也有
   系统外的「野日志」。两个工具互补，正好对应现实中「告警台账」和「原始日志检索」
   两个数据面。

跑完一圈，观察（含 flag 标记）记进 `observations`，LLM 下一圈看着观察继续裁——
直到 `finish` 或步数用尽。收尾的 report_llm/write_timeline（站 8）是 2.3 的主角，
这里只看一眼实测结果：报告落进了案件时间线，findings 逐字引用工具输出。

## 三、服务与中间件卡

**卡 1 · ▼交接节点 + 子状态隔离（编排形态，自研）**

- **它是什么**：把一个 worker 子图整团包进一个外壳 FlowNode：外壳负责「从交接态摸
  实体 id + 开干净子状态 + 收成果」，内部节点借外壳的 ctx 顺序执行。
- **市面替代**：LangGraph 原生做法是把子图做成 subgraph 节点直接挂进大图（框架支持
  嵌套 StateGraph）；或者干脆平铺所有节点、用命名前缀避免撞名。
- **为何这么选**：① 调查/富化两个子图各有 `load_case`，同名节点进不了同一张
  StateGraph，平铺就得改节点名——改名字丢的是「代码与 PRD 术语一一对应」；
  ② alert_flow 组图时案件还不存在，子图只能**运行时**才构造（case_id 从交接态来），
  交接节点的惰性构造正好满足；③ web 流水线视图只需要两级骨架（分诊六格 / 案件两格），
  内部细节用 tool_call/audit 帧呈现即可。代价也要诚实：外壳内不走 LangGraph 的
  checkpoint，**子图中间态不可断点续跑**——但调查子图全程无人工挂起点（interrupt 只
  在审批面用），这个代价为零。
- **业务上怎么选**：子图是「无人工停留的纯执行段」→ 交接节点整团包；子图里有
  「等人拍板」的停顿 → 必须用框架原生 interrupt/subgraph，别自己包。判断标准只有
  一条：**中间态要不要被恢复系统看见**。

**卡 2 · ▼related_alerts 的数据面：拉回来自己过滤 vs 查询下推**

- **它是什么**：`listAlerts()` 全量拉告警 → agent 进程内 `filter()` 做时间窗+范围匹配。
  O(n) 内存过滤，n=系统告警总数（本布景 15 条）。
- **市面替代**：把过滤条件下推到存储层——SQL `WHERE date BETWEEN ? AND ?` +
  observable 表 JOIN；或接真 SIEM（Elastic/Splunk）的服务端聚合查询。
- **为何这么选**：demo 阶段告警库是 SQLite 单表、量级是「百」而不是「亿」，全量拉回
  进程内过滤是最简单、最可测（纯函数，单测不用起库）、最可复算（确定性）的实现。
  把查询下推优化到存储层属于「等数据量逼你再做」的典型——提前做只会让 adapter
  变厚、测试变难。
- **业务上怎么选**：看三个量——数据量（全量拉得动吗）、匹配逻辑复杂度（进程内写
  函数比拼 SQL 灵活）、数据源归属（自家库才敢随便拉；别人的系统要走它的查询接口
  免得拖垮人家）。三条里任何一条爆表，就该下推。真 SOC 里 related_alerts 对接的
  通常是 SIEM/EDR 的服务端聚合接口，本项目的 siem_query 才是它的原型。
