# 场景 9 · 步 9.2 —— planner 选组合：能力菜单 fail-closed 与审计分痕

> 9.1 里假设被拉起了轮 1 的 hunt_flow run。本步进到轮次链的第一段：**intake**（装配交接态）
> 和 **planner**（[TERMS「循环三件套」](TERMS.md)条里的「拟单的」——每轮决定「下一轮查什么」
> 的 LLM 决策面）。核心教学点一句话：**"下一步查什么取决于上一轮查到什么"，在这条链上是
> 数据流，不是口号**——gap 从上一轮归集里读出来、喂进 planner 的输入，planner 的输出
> （任务组合 C_k）决定扇出几路子 run。

> 但 planner 自己也是 LLM、也不可信。所以它的输出要过**三道闸**才能算数：输出契约
> （schema 显式验型）、能力菜单（fail-closed，菜单外整轮终止）、任务上限（截断）。
> 本步把这三道闸跟「建议/决定审计分痕」一起讲透。
>

### 站 1 · intake：一轮的案卷首页

📍 大图节点:INTAKE(9.2 planner 选组合)

intake 干的全是「把这一轮要用的东西从各处读齐、摊在交接态上」。逐段读
[flow.ts:74-124](soc-demo/services/agent/src/orchestration/flow.ts#L74)：

**轮号从簿记推导，不靠传参。** [flow.ts:83-85](soc-demo/services/agent/src/orchestration/flow.ts#L83)：

```ts
        const link = orch.ledger.get(runId);
        const priorRounds = orch.ledger.rounds(hypothesisId).filter((l) => l.runId !== "" && l.runId !== runId);
        const roundNo = link?.roundNo ?? priorRounds.length + 1;
```

relay 拉起时就落了轮号（9.1 站 5 的锚），intake 优先读它；竞态窗口（intake 先于补账）按
既往轮数推导——注释里写明「两条路殊途同归，轮号漂移会在轮次归集处暴露」。**轮号是簿记
事实，不是消息里带的声明**——这个口径跟 1.3「票面真相源在注册表」一脉相承：能查出来的
就不信传进来的。

**模板查找两档。** [flow.ts:89-90](soc-demo/services/agent/src/orchestration/flow.ts#L89)：
`orch.templates.of(detail.template_id)`——生产装配是 `HuntTemplateSource`（三族/IR 模板优先，
[模板登记面 hunt-pack.ts:64-84](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L64)），
未登记 id 落机制默认档（[template.ts:9-21](soc-demo/services/agent/src/orchestration/template.ts#L9)）：

```ts
export const DEFAULT_TEMPLATE: LoopTemplate = {
  templateId: "default",
  maxRounds: 20,
  maxTasks: 2,

```

9.1 捣乱 C 那条不带 template_id 的假设，intake 读到的就是这张卡——`max_rounds: 20`、
菜单三件。**机制层不持第二份业务菜单**：默认档只有「上限四字段 + 查证只读面」，业务
语义（句式族、既定查询计划）全在 fixtures 的四张卡上（TERMS「预案卡」条：加第二个业务
零机制增量）。

**max_rounds 硬顶在开跑前拒。** [flow.ts:94](soc-demo/services/agent/src/orchestration/flow.ts#L94)
调 `assertRoundsBudget(roundNo, template.maxRounds)`（[budget.ts:209-213](soc-demo/services/agent/src/budget.ts#L209)）：
第 maxRounds+1 轮在**这个轮 run 的第一个节点**就被 `BudgetExceededError("rounds")` 拒掉，
走 runner 既有强杀路径——不给这一轮留任何副作用（比「跑一半发现超轮」便宜得多）。这是
[TERMS「查证轮」](TERMS.md)条说的「预算双闸」的轮数半边；token/墙钟半边在节点包装层
（[flow.ts:52-69](soc-demo/services/agent/src/orchestration/flow.ts#L52)，每轮一本独立账，
9.6 捣乱②的主角）。

**首轮前置 hunting。** [flow.ts:95-103](soc-demo/services/agent/src/orchestration/flow.ts#L95)：

```ts
        if (roundNo === 1) {
          // 行为约定 1：hunt_flow 首轮开始前置 hunting（proposed→hunting，INV-10 迁移；
          // 远端 409 原样上抛 = fail-closed，不带病开跑）
          if (detail.status !== "proposed") throw new Error(`hypothesis_not_proposed:${detail.status}`);
          await orch.port.startHunting(hypothesisId);
        } else if (detail.status !== "hunting") {
          // 轮间被取消/终局：不再起轮（行为约定 12 停止语义的骨架形态）
          throw new Error(`hypothesis_inactive:${detail.status}`);
        }
```

两个分支一正一反：轮 1 要求账面还是 proposed（被人抢跑成终态的假设轮 1 拒开）；轮 2+ 要求
账面还在 hunting（**取消/终局了的假设不再起轮**——9.6 捣乱①实测的 `hypothesis_inactive:cancelled`
就是这个分支抛的）。注意「远端 409 原样上抛」：状态机是 M2 的，agent 侧推不动（比如竞态里
被人抢先）就炸响停跑，绝不带病开跑。

**交接态摊开**（[flow.ts:105-123](soc-demo/services/agent/src/orchestration/flow.ts#L105)）：
`gap`（上一轮的缺口，首轮 null）、`evidence_so_far`（每轮一行「roundN:工具A+工具B」的
证据流水）、`prev_fingerprint`（上一轮的防转指纹原料，9.5 细讲）、`menu`（模板菜单的
拷贝）。一轮要用的一切都在这一行行赋值里——**planner 不自己去找数据，它只消费交接态**，
这是轮次链六节点可以逐个单测的前提。

### 站 2 · planner：拟单的三道闸

📍 大图节点:PLANNER(9.2 planner 选组合)

planner 节点本体只有一行委托（[flow.ts:128-133](soc-demo/services/agent/src/orchestration/flow.ts#L128)），
全部机制收在 `planRound`（[planner.ts:162](soc-demo/services/agent/src/orchestration/planner.ts#L162)）。
按执行顺序读：

**第一道：防注入消毒（进 prompt 之前）。**
[sanitizePlannerInput（planner.ts:113-149）](soc-demo/services/agent/src/orchestration/planner.ts#L113)
把输入里的每一段不可信文本（假设文本走 user_input 通道、证据/gap 走 tool_output 通道——
上游 LLM 产物也算不可信）逐个送安检员扫描：

```ts
  const hypothesis_text = await scanOne(input.hypothesis_text, "user_input", "hypothesis_text");
  const evidence_so_far: string[] = [];
  for (let i = 0; i < input.evidence_so_far.length; i++) {
    evidence_so_far.push(await scanOne(input.evidence_so_far[i], "tool_output", `evidence_so_far:${i}`));
  }
```

判定映射（[planner.ts:118-127](soc-demo/services/agent/src/orchestration/planner.ts#L118)）：
allow 留原文；strip 用安检员的清洗文本；**block/flag/fail_closed 一律占位符 `[blocked:字段名]`**
——注意 flag（只是打标、没拦）在这里也算命中，替换成占位符。这是 planner 与调查循环
observe() 的**刻意差异**（planner.ts:5-10 文件头注释）：调查的 prompt 是证据面（打标留痕、
原文照进上下文），planner 的 prompt 是**决策面**（原文零进 prompt，事件/审计只记字段与
判定不记原文，INV-4 邻域卫生）。消毒发生时会广播一条 `hunt_prompt_sanitized` 审计事件
（[planner.ts:174-182](soc-demo/services/agent/src/orchestration/planner.ts#L174)）。

**第二道：输出契约 + 菜单闸（出 prompt 之后）。** LLM 回包先过 `parsePlan`
（[planner.ts:83-100](soc-demo/services/agent/src/orchestration/planner.ts#L83)）：
`{tasks:[{tool,params,rationale}]}`、tasks ≥ 1、逐字段验形——坏形**重试 1 次**
（[planner.ts:205-231](soc-demo/services/agent/src/orchestration/planner.ts#L205)，real adapter
抛的 bad_shape 与假件回的坏形同态收进同一个重试循环），再败写 `hunt_plan_denied` 审计、
本轮终止——**fail-closed 不编造**：宁可这轮空转，不让 planner 编一个看起来像样的组合。

schema 过了还不够，还有菜单闸（[planner.ts:235-239](soc-demo/services/agent/src/orchestration/planner.ts#L235)）：

```ts
  const offMenu = tasks.filter((t) => !raw.menu.includes(t.tool));
  if (offMenu.length > 0) {
    deny("offmenu_tool", { attempts, tools: offMenu.map((t) => t.tool.slice(0, 64)) });
    return;
  }
```

菜单外工具**不 retry、整轮终止**（行为约定 4）——比 schema 失败更严，因为「能选菜单外
工具」说明这组输出整体不可信。这就是 [TERMS「派工菜单」](TERMS.md)条的第一道闸：拟单只能
照菜单点。为什么这么狠？planner 的菜单真源是模板注入的子集，而它的**票面**（9.3 的窄票）
也只能从同一个真源出——如果菜单闸松一道，LLM 点了票面外的菜，铸票缝（第二道闸）虽然还能
拦住，但那已经是「靠下游兜底」而不是「上游不犯错」了。两道闸独立成立、绕过一道还有一道
（TERMS「派工菜单」条原文），这是纵深，不是冗余。

**第三道：上限截断 + 指纹。** 超过 max_tasks 的组合**截断不拒整轮**
（[planner.ts:241-244](soc-demo/services/agent/src/orchestration/planner.ts#L241)，T03——
「想多查」和「不可信」是两回事，前者裁到上限就行）；然后算防转指纹
（[planner.ts:250](soc-demo/services/agent/src/orchestration/planner.ts#L250)，`spinFingerprint`，
9.5 拆）。最后落**审计分痕 A**：

```ts
  recordAudit(audit, runId, {
    action: "hunt_plan_suggest",
    objectId: runId,
    objectType: "run",
    result: "SUCCESS",
    details: { round_no: ..., tasks: capped, tasks_returned: tasks.length, truncated, attempts, sanitized_fields: ... },
  });
```

（[planner.ts:254-268](soc-demo/services/agent/src/orchestration/planner.ts#L254)）
`hunt_plan_suggest` = 路由**建议**；等 dispatch 真的按它扇出时，还有一笔 `hunt_dispatch_decide`
= 路由**决定**（9.3）。两个 action 可区分可查——「LLM 提议了什么」和「机制实际执行了什么」
是两笔账，出了分歧一眼能定位。这是 [TERMS「循环三件套」](TERMS.md)条说的「审计分痕」。

## 三、服务与中间件卡

**卡 1 · ▼LLM 决策面的「消毒 → 验型 → 菜单闸 → 截断」流水线（自研，三个决策面复用）**

- **它是什么**：planner/judge/gap 三个 LLM 决策面共用同一套输出纪律：不可信段消毒占位 →
  schema 显式验型（坏形重试 1 次）→ 领域闸（菜单/一致性/置信地板）→ 上限截断 → 建议
  审计。三面的实现三份、纪律一份。
- **市面替代**：structured output / function calling（OpenAI JSON mode 等）可以在**模型侧**
  约束输出形状；LangGraph 侧也有人把校验写进节点 retry 逻辑。
- **为何这么选**：模型侧约束解决的是「形」，解决不了「权」——组合合不合法是**菜单**的
  事、证据够不够是**判据**的事，这些闸必须握在机制手里而不是信任模型的自律。schema
  验型 + 独立领域闸双层，让「换模型/换 provider」只动 adapter 一层（llm-real.ts），
  闸零改动。
- **业务上怎么选**：决策面的输出要**触发副作用**（扇出子 run/建案）→ 三道闸一个都不能省
  （fail-closed）；纯展示性的 LLM 输出（摘要/标题）→ schema 可以放宽。判断标准：错了
  谁买单——买单的是下游执行，就得闸死。

## 场景题闯关（本步 1 题）

**Q：同样是 planner 输出越界——「选了菜单外工具」整轮终止不重试，「超出 max_tasks」却
只截断不拒整轮。两种宽严不一的口径，各在防什么？**

<details><summary>答案（点击展开）</summary>

菜单外（offmenu_tool）说明这组输出**整体不可信**——planner 连「哪些工具存在」都没搞对，
它的 params/rationale 一概不能要，重试等于给不可信输出第二次机会（T04 fail-closed）。
超 max_tasks（T03）说明输出**可信但贪多**——「想多查几个面」是合理性错误，裁到上限
照常执行，审计里带 truncated 留痕。一句话：**信任问题掐死、数量问题裁剪**。同款分辨
在 9.4 还会出现一次：judge 坏形降级是「不收敛」而不是「收敛为 miss」——出错的输出永远
不许被解释成安全的那个方向。</details>
