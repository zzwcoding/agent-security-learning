## 一、为什么"加业务不改机制"值得专门一课

传统做法里，加一个业务=加一堆 if/else。想象编排循环是第一版写的：里面到处是
`if (业务 == "webshell")` 这样的分支——每来一个新业务，机制文件就要开膛一次。开膛的
代价不在行数，在风险：机制层是全业务共用的地基，每改一次，**所有存量业务一起陪着重测**；
改的人还得把五个业务的规则全装进脑子里。业务越多，机制越脆——这是"越加越烂"的死亡
螺旋，也是本仓 PRD §13.1 拍板时点名要埋葬的形态。

本仓的答案是分层拍板（PRD §13.1 交付物分层表）：**交付物是循环机制，不是狩猎业务**。

| 层 | 内容 | 形态 | 变更频率 |
|---|---|---|---|
| 机制层（m14） | planner/judge/gap 三 LLM 节点、轮次链、扇出/收敛、两票票务、预算双闸 | 代码，写一次 | 几乎不动 |
| 内容层（业务） | 假设模板 = 句式族 + 菜单子集 + 轮次上限 | 数据（[TERMS「预案卡」](TERMS.md)条），fixtures/ 下一个 JSON 文件 | 每新业务一个 |
| 验证层 | 第二个业务落地"零 m14 增量" | 断言（零增量闸）：diff 与机制层交集为空 | 每次 diff 都查 |

这条分层不是靠自觉守的——它有一条**否定式断言**咬着：票 80（应急取证模板落地）的
git diff 与机制层领地交集必须为空，CI 里 `tools/check_zero_increment.py` 逐次检查，
不过 = 架构返工而非业务票返工（回 L0 裁决）。本场景 11.2 就把这条闸亲手跑红、跑绿。

而"机制不改，新业务哪来的行为差异"——答案全在 [TERMS「预案卡」](TERMS.md)条的数据里：
菜单子集收窄 = planner 的选路空间收窄（11.4 实测 27 个工具 100% 选不得）；
既定查询计划（waves）= fake LLM 的确定性拆条轨迹（11.3 真栈四轮收敛）；
遏制建议 = 只出文本的文本（INV-3/9：L2 动作止于人工审批，11.4 收口）。
