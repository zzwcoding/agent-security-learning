### 站 3 · 进闸前装填：把跨进程的焚毁真相搬进来

闸本体是同步函数，而焚毁真相在另一个进程的 SQLite 里（M2 的 used_tokens 表）。票 34
的解法：**进闸之前先把真相问回来，装进一个一次性的读口对象**：

📄 [services/agent/src/graph.ts:253-274](soc-demo/services/agent/src/graph.ts#L253)

```ts
  const resolveUsed = async (token: string): Promise<BurnRegistry | undefined> => {
    if (!deps.used && !deps.usedReader) return undefined; // 两路都没接 = 不查（既有测试便利口径）
    if (!deps.usedReader) return deps.used;
    let burned: boolean | null = null;
    let failure: unknown = null;
    const wireJti = jtiFromWire(token);
    if (wireJti !== null) {
      try {
        burned = await deps.usedReader.lookup(wireJti);
      } catch (e) {
        failure = e; // INV-1：读口病了闸必须病
      }
    }
    const local = deps.used;
    return {
      has: (jti: string) => {
        if (failure !== null) throw failure;
        if (burned === true && jti === wireJti) return true;
        return local ? local.has(jti) : false;
      },
    };
  };
```

三个看点：① `jtiFromWire` 只解 wire 串的 payload 拿 jti、**不验签**——伪造票在闸的
验签步就会死，装填结果根本轮不到被读（graph.ts:235-237 注释原话），查询浪费不起也
信任不起；② 读口病了不吞——`failure` 被捕获存着，等闸里 `has()` 一碰就炸（闸必须病）；
③ 装填是**叠加不是替换**：M2 说已焚 → 拒；M2 没烧 → 再问本地表（如进程内
MemoryBurnRegistry），**任一路说已焚都必须拒**（graph.ts:249-252 注释："合并取或"）。

M2 侧的读口（HttpUsedTokenReader）状态码即语义：

📄 [services/agent/src/token-ports.ts:116-124](soc-demo/services/agent/src/token-ports.ts#L116)

```ts
  async lookup(jti: string): Promise<boolean> {
    const res = await fetch(
      `${this.baseUrl}/internal/used-tokens/${encodeURIComponent(jti)}`,
      { signal: AbortSignal.timeout(2000) },
    );
    if (res.status === 200) return true;
    if (res.status === 404) return false;
    throw new Error(`used_tokens lookup failed: HTTP ${res.status}`);
  }
```

200=已焚、404=未焚、**其他一切状态码和网络错都抛**——"查不到真相"和"真相是没有"
是两回事（token-ports.ts:103-104 注释原话），前者必须让闸病掉。

### 站 4 · 验票闸本体：五连裁决的全部机制就五行

📄 [services/agent/src/verify-ticket.ts:227-241](soc-demo/services/agent/src/verify-ticket.ts#L227)

```ts
function verifyApproval(
  key: Buffer,
  toolCall: { name: string; params?: unknown },
  ctx: VerifyCtx,
  nowSec: number,
): VerifyResult {
  const p = asApprovalClaims(unseal(key, ctx.approvalToken as string));
  if (nowSec >= p.exp) return deny("token_expired");
  if (ctx.used?.has(p.jti)) return deny("token_used"); // 一次性（INV-2：重放必 403）
  if (p.tool !== toolCall.name) return deny("scope_insufficient"); // 票只对铸造时的那个工具有效
  // 参数指纹比对：改参数即失效（FR-S2.2/INV-2 的全部机制就这一句话）
  if (paramsHash(toolCall.params) !== p.params_hash) return deny("params_mismatch");
  if (ctx.caseId !== undefined && p.case_id !== ctx.caseId) return deny("scope_insufficient");
  return { allow: true, reason: "allow", payload: p };
}
```

裁决顺序（头注释："签名 → 时效 → 焚毁 → scope/参数，fail-closed 短路"）一行一个
拒因，全部由 4.4 铸进票面的 claims 说话：`unseal` 验签（签名不过抛异常，外层 try
收进 signature_invalid）→ `exp` 验时效 → `used.has(jti)` 验焚毁 → `tool` 验工具 →
`paramsHash` 重算参数指纹 → `case_id` 验案件绑定。**注释里那句"全部机制就这一句话"
值得背下来**：批什么执行什么的全部保证，就是"执行前重算参数哈希、跟票面指纹对一下"。

### 站 5 · 教具七幕：每一种拒因的实弹

脚本做的事就是把站 4 的闸体当成靶场：本地按 py 票型**自签**一批票（密钥与栈同源，
序列化连 py json.dumps 的空格都一致），逐个喂给 verifyTicket。两幕值得细说：

- **S3 与 S7 的区别**：S3 的焚毁表是进程内的假件（`{has: () => true}`）——证明的是
  "闸认焚毁表"；S7 问的是**真 M2 的 REST 读口**——证明的是"跨进程也认"。而且 S7 的票
  是本地自签的同 jti 票：**焚毁真相按 jti 对账，不认签名**——哪怕你签得出天衣无缝的
  票，jti 在坟场里就是死票（4.6 讲这是怎么发生的）。
- **S6 的两个拒因来自分级登记表**：手里什么票都没有时，闸查 `tierOf(tool)`（读
  fixtures/tools.manifest.json）——L0 免验放行、L2 直接 `require_approval`（想执行
  必须走人审）、其余 `no_ticket`。未登记工具按"默认 L1"对待：**没登记就没票可用**
  （fail-closed 更严口径，verify-ticket.ts:82-86 注释）。

## 三、服务与中间件卡

### 卡 1（自研）· 票型双端对冲：py 铸、TS 验、fixtures 裁决

- **它是什么**：同一张票的两种实现——py 侧 `mint.verify()`（gateway/mint.py:114）与
  TS 侧 `verifyTicket`（verify-ticket.ts），由 `fixtures/tickets/` 契约样品锁死：
  冻结 iat 后两端对同一批样品跑同一组断言，逐字节对冲漂移（ADR 0001 后果节的纪律）。
- **为什么要两份**：签发在 gateway（py/FastAPI）、验证在 agent（TS/LangGraph）——
  语言跟着各服务的生态走。票型契约（字段集+顺序+序列化+签名形态）是两个世界的
  唯一接口，fixtures 是它的可执行规格。本步教具脚本的本地铸造器也是照着这份契约
  手工对齐的（连 py json.dumps 的分隔符空格都复刻）——对齐成本就是契约的复杂度
  计量。
- **市面上同类**：Pact 一类消费者驱动契约测试；OpenAPI/JSON Schema + 多语言代码生成
  （生成物的一致性由生成器保证，代价是生成器本身成为单点）。
- **业务上怎么选**：跨语言的关键安全件 → 双实现+样品对冲，谁也不许"顺手改"；能同
  语言 → 共享一个库，消灭第二实现；样品要覆盖**全部拒因**（本项目 contract.json 的
  reasons 枚举）——只测 happy path 的契约测试是装饰品。

### 卡 2（领域）· 一次性手令：SOC 业务里的重放防线

- **它是什么**：INV-2 的业务形态。值班长的 ApprovalToken 是"一次性密令"——口谕
  （对话文本）无效（INV-9），密令（签名票）只领一次任务，办完即焚（used_tokens），
  再拿出来对不上账（token_used 403）。本步 S7 证明焚毁账本是**跨进程**的：卡在 agent
  库、坟场在 M2 库，谁也别想只改自己那边。
- **为什么 L2 要一次性而 L0 查询可重复**：查询错一千次也只是白跑；隔离错一次业务
  停摆。可重复的授权靠"权限"（任务票 900s 内反复用），不可逆的动作只配"次数=1"的
  授权——**授权的有效次数应该跟动作的可逆性成反比**。
- **市面上同类**：JWT 的 jti + 黑名单（本项目焚毁表的通用形态）；OAuth refresh token
  rotation（用一次换一次，旧票即刻作废——同思想）；银行 U 盾/动码令牌（一次一密）。
- **业务上怎么选**：动作不可逆或高代价 → 强制一次性+短 TTL+焚毁账本；账本本身要
  **跨进程可信**（独立服务、审计同库同事务——M2 的 used_tokens 和 audit_entries
  就是同库同事务，票 03 口径）；给"事后追责"留对账链（4.6 的审计四连）。
