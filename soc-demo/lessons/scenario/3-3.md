# 场景 3 · 步 3.3 —— 人审闸：一张审批卡的批准与驳回（kb_write L2 正门）

> 3.1 把草稿冻在了审批卡上，3.2 认清了账面和检索面是两个世界。本步按下"批准"——
> 然后你会发现这两个字背后是**一整条授权链**：gateway 铸一枚一次性 ApprovalToken →
> 决定落卡 → 冻住的 run 被异步拉起 → 验票闸验签 → token 用后即焚 → 执行体才动手
> （M2 账面翻 approved + chroma 进检索面）。驳回半边则简单得多，但有个漂亮的对称：
> **驳回 = 检索面永不写入，run 照常走完**。3.2 留下的幽灵条目正好当对照组——同一句
> "批准"，走没走对门，chroma 知道答案。token 的密码学细节（HMAC 三段、六种拒因、
> 跨进程重放 403）是场景 4 的主场，本步只点到为止。
>
> 术语卡：比喻照旧沿用 [TERMS.md](TERMS.md)（审批卡/一次性密令/焚毁/派活的/KB 人审闸……），
> 首遇只回指；每站开头的 📍 行对应 [3-big-picture.html](3-big-picture.html) 同名节点。

## 一、操作（位置感）

本步主角：3.1 冻结的审批卡 `apr_0f984f53…`（tool=kb_write，params 带主角草稿全文）。
操作全在 agent 的审批 REST（web 审批页的按钮背后就是这两个端点）：

- 批准：`POST /api/v1/approvals/:id/approve`，body 必须带 `approver`（**没有缺省值**——
  3.2 的 M2 kb approve 缺省 duty_lead 是"留痕镜像"的宽容，这里是审批正门，人必须署名）；
- 驳回：`POST /api/v1/approvals/:id/reject`，带 `approver` 和可选 `reason`。

本步实测两件事：

1. **正片批准**主角卡 → run 复活走完、M2 翻 approved（reviewed_by=duty_lead）、
   **chroma count 0→1**、token 进 used_tokens 坟场；
2. **驳回演示**：直拉第二次沉淀给 case_000004 造一张新卡（复现 3.1 的拉起），然后驳回
   → 新提案 rejected 且原因留痕、**chroma 纹丝不动**、run 照常 completed。

做完这两件事，账面里三条 kb 条目正好构成一组完整教材：approved（正门入库）、
approved 幽灵（绕门入库、检索面查无）、rejected（驳回、检索面查无）。

## 二、调用链

先看全景。批准的完整授权链（六站）与驳回的捷径：

```
值班长 duty_lead
  │  POST /api/v1/approvals/apr_0f984f53…/approve {"approver":"duty_lead"}
  ▼
[站1] 审批端点 —— 廉价预检（非 pending 即 409）→ 先铸票后裁决
  │     gateway /internal/mint 铸 ApprovalToken（HMAC 三段，烧进 params_hash）
  ▼
[站2] 决定落卡 + resume 入队 —— decideApproval 审批状态机仲裁（后到者 409）
  │     200 秒回 {approval_token, run_id, run_status:"awaiting_approval"}
  │     ※ 批准与执行解耦：此刻动作还没执行，token 只是一张"授权书"
  ▼
[站3] 分发循环捡起 resume 任务 —— 重组 worker 图：重铸 L1 任务票（票面无 L2 不变）
  ▼
[站4] kb_write 节点从头重跑 —— awaitApproval 轮查卡：已 approved 且带 token
  ▼
[站5] 验票闸（makeGatedCall 审批变体）—— 验签/查焚毁真相/params_hash 对指纹
  │     全过 → 执行体：① M2 approve 账面 ② chroma upsert 检索面（INV-5 正门）
  │     → 焚毁登记 used_tokens → 执行标记 → tool_result 事件
  ▼
[站6] node_exit → run completed（steps=2 走满）

驳回路径（对比）：[站1] 直接跳过铸票 → [站2] 决定落卡(rejected) + resume 入队
  → [站3][站4] 同样重组图重跑节点 → awaitApproval 查到 rejected → 不进闸不执行
  → M2 rejectProposal 账面留痕（reject_reason）→ node_exit → run completed
  ※ 检索面自始至终零写入
```

### 站 1 · 审批端点：先铸票，后裁决

📍 大图节点:APR_EP(3.3 人审闸)

批准端点的核心段（[app.ts:429-465](soc-demo/services/agent/src/app.ts#L429)，节选）：

📄 [services/agent/src/app.ts:434-456](soc-demo/services/agent/src/app.ts#L434)

```ts
    // 廉价预检：卡已被裁决就别去麻烦 gateway（真仲裁仍在 decideApproval 事务里，
    // 这里只为省掉「后到者白铸一枚随即作废」的票）
    if (card.status !== "pending") {
      throw new InvalidApprovalTransitionError(card.status, "approved");
    }
    // 先铸票后裁决：铸票失败 → 卡仍 pending 可重试，不留「已批准无票」的悬置态。
    // 并发双批会各铸一枚，但裁决事务只放行先到者，后到的票随 409 一起作废（300s 自焚）。
    // resume 的任务票重组（票 17）挪进了分发循环的执行步——决定已落卡，图必须能被
    // 异步重组（任务票铸失败在循环里审计 FAILURE，run 仍挂起可观察）。
    let minted: Awaited<ReturnType<MintClient["mintApprovalToken"]>>;
    try {
      minted = await mint.mintApprovalToken({
        jti: `ap_${randomUUID()}`,
        approvalId: id,
        approvedBy: body.approver,
        tool: card.tool,
        params: card.params,
        caseId: card.caseId,
      });
    } catch {
      return reply.status(502).send({ error: "mint_failed" });
    }
    await decideAndResume(id, { approve: true, approver: body.approver, token: minted.token, tokenJti: String(minted.payload.jti ?? "") }, req.headers);
```

三个设计决策值得逐字读：

**① 先铸票后裁决。** 顺序反了会怎样？如果先落"approved"再铸票，铸票失败就留下
"人说可以但没有授权书"的悬置态——卡不是 pending（不能重新走流程）也不是 executed
（没有 token），死锁。先铸票则失败时卡还是 pending，值班长重按一次就行。

**② 并发双批不作弊。** 两个人同时点批准，会铸出两枚 token——但决定落卡走审批状态机
事务（[approvals.ts:156](soc-demo/services/agent/src/approvals.ts#L156) `decideApproval`），
只有先到者成功，后到者 409，他手里那枚 token 成了废纸（300 秒 TTL 自焚，场景 4.7 细讲）。
本步实测重复批准：

```
POST /api/v1/approvals/apr_0f984f53…/approve（第二遍）
→ {"error":"InvalidTransition"} HTTP 409
```

**③ token 里烧的是整张卡的指纹。** `mintApprovalToken` 的入参带 `tool + params + caseId`——
gateway 把 params 的哈希（3.1 见过的 `params_hash`）烧进 token。之后闸验票时会拿**实际执行
参数**重新算哈希对指纹：卡上展示的是 A 草稿、执行时想换成 B 草稿？验签当场拒绝。这就是
"**批什么执行什么**"的结构保证（场景 4.4/4.5 展开_token 构造与六种拒因）。

### 站 2 · 决定落卡与 resume 入队：批准和执行是解耦的

📍 大图节点:DECIDE(3.3 人审闸)

**先把"批准"到"执行"之间这条时序接缝说透**：值班长拿到 200 回执的那一刻，动作当然还没
执行——此刻的产物躺在两张表里：决定躺在 agent 的 `approvals` 表（TERMS「审批卡」条：
approved + 烧进卡里的 token，卡是唯一真相），续跑任务躺在 `run_jobs` 表（一行 resume）。
**等多久、谁接手**：TERMS[「派活的（派活清单）」](TERMS.md)那条分发循环**每 100ms tick
一次**把 resume 领走（本步实测批准到 run completed 隔两三秒，大头是 resume 重组图和执行体
的两次出站调用）。**触发关系**：照旧没有——approve 端点不知道分发循环的存在，它只往表里
塞任务；循环只认表。所以"批准"这个动作的全部产出就是**两张表各多一行**，执行是另一拨人
（循环）按表办事。

📄 [services/agent/src/app.ts:483-491](soc-demo/services/agent/src/app.ts#L483)

### 站 3 · resume 重组图：为什么续跑前要重铸一张 L1 任务票

📍 大图节点:RESUME(3.3 人审闸)

分发循环捡到 resume 任务后（[app.ts:419-427](soc-demo/services/agent/src/app.ts#L419)
`executeResumeJob`），会先重组 worker 图：

📄 [services/agent/src/app.ts:333-351](soc-demo/services/agent/src/app.ts#L333)

```ts
  /** 票 17：makeNodes 图的 resume 组图。拉起时 worker 图是按 run 组的（票 13 工厂），
   *  resume 若不带它，runOpts 的静态 nodes 会把图换成薄径——LangGraph 找不到挂起的
   *  worker 节点直接跑完，L2 动作静默丢失。故 resume 前按原 run.kind 重新铸任务票
   *  （票面规格不变，INV-3 依旧无 L2）并重组 worker 图；静态 nodes（薄径/演示图）不受影响。
   *  票 47 起由分发循环的执行步调用（决定已落卡后异步重组），不再在审批端点里同步做。 */
  async function rebuildResumeNodes(runId: string): Promise<FlowNode[] | undefined> {
    if (opts.nodes || !opts.makeNodes) return opts.nodes;
    const run = requireRun(db, runId);
    const spec = requireRunKind(run.kind).ticket;
    const minted = await mint.mintTaskTicket({
      jti: `tk_${randomUUID()}`,
      sub: spec.sub,
      caseId: run.caseId,
      runId: run.id,
      scope: [...spec.scope],
      allowedTools: [...spec.allowedTools],
    });
    return opts.makeNodes(run, minted.token);
  }
```

这段注释是本站全部重点：**worker 图是按 run 组的**（组图时捕获了那张 L1 任务票），进程
重启或异步续跑时图已经不在了，必须照注册表票面**重新铸一张任务票**、重新组图。注意票面
规格原样照抄——`allowed_tools` 还是 `get_case/kb_propose`，**依然没有 kb_write**（INV-3）。
一张 L1 任务票+一枚 L2 ApprovalToken，各管各的，续跑也不混。

### 站 4 · awaitApproval：节点重跑，卡是唯一真相

📍 大图节点:AWAIT(3.3 人审闸)

图接回去后，kb_write 节点**从头重跑**（LangGraph interrupt 的语义：resume 后节点重新执行）。
重跑会再次走到 `executeApproved` → `awaitApproval`——这次轮查卡，查到的是已决状态：

📄 [services/agent/src/graph.ts:211-233](soc-demo/services/agent/src/graph.ts#L211)

```ts
  const awaitApproval = (tool: string, params: unknown, opts?: ApproveOpts): ApprovalDecision => {
    const o: ApproveOpts = opts ?? {};
    for (;;) {
      const existing = findDecidableCard(db, runId, tool, paramsHash(params));
      if (existing?.status === "rejected") return { approved: false, approvalId: existing.id };
      if (existing?.status === "approved" && existing.token) {
        return { approved: true, approvalId: existing.id, token: existing.token };
      }
      // pending = 决定还没落（重启后批准前的重入），幂等再中断，不重复开卡。
      // LangGraph 原生 interrupt：未决即抛 GraphInterrupt 挂起本 superstep。resume 后
      // 节点从头重跑，interrupt() 可能回吞旧 resume 值直接返回——决定以 DB 为准，
      // 回到循环顶重查卡；卡仍未决就再次中断，直到没有新 resume 值真正挂起。
      const card = existing ?? openApprovalCard(db, {
        runId,
        node: cursor.node,
        tool,
        params,
        caseId: o.caseId ?? null,
        reason: o.reason ?? null,
      }, deps.ctx);
      interrupt(card.id);
    }
  };
```

这是个**无限循环套 interrupt** 的结构，读法："**卡是唯一真相，DB 说了算**"。每圈先查卡：
rejected → 直接带着驳回决定返回；approved 带 token → 带着授权书返回；没决 → 开卡（或复用
已开的）+ `interrupt()` 挂起。注释里那个"回吞旧 resume 值"的边角是 LangGraph 的实现细节：
resume 值可能被 interrupt() 原样返回给你，但代码不信任它，回循环顶重查 DB——**框架的返回值
会骗人，数据库不会**。

本步实测，批准路径的续跑事件（run_0d96d113 事件 624-629）：

| seq | 事件 | 说明 |
|---|---|---|
| 624 | `approval_decided`（kb_write） | 值班长的决定落卡 |
| 625 | audit | 决定审计（actor=duty_lead，真人） |
| 626 | `node_enter kb_write` | **resume 重进节点（从头重跑）** |
| 627 | `tool_call kb_write`（带 approval_id） | 这次是 L2 动作过闸 |
| 628 | `tool_result kb_write`（带 result） | 执行体返回 `{kb_id,…,status:"approved"}` |
| 629 | `node_exit kb_write` | 走完，run completed |

### 站 6 · 执行体：翻账面 + 进检索面（INV-5 正门）

📍 大图节点:EXEC_KB(3.3 人审闸)

3.2 站 4 钉过的那条缝，答案在这里揭晓：**"账面 approved"到"进 chroma"之间，动手写检索面的
是闸放行后的这个执行体**——不是 M2（它没有那行代码），不是 approve 端点（它只管落卡+入队），
而是 resume 把 worker 图拉起来、节点重跑、`awaitApproval` 查到已决卡、验票闸六查全过之后
才出场的这个匿名函数。时机上是**异步的**：值班长批准后隔两三秒才发生。闸放行后才轮到
3.1 站 6 埋的那个执行体（[flow.ts:204-235](soc-demo/services/agent/workers/knowledge/flow.ts#L204)）：

📄 [services/agent/workers/knowledge/flow.ts:204-224](soc-demo/services/agent/workers/knowledge/flow.ts#L204)


两步走，先账面后检索面。一个耐人寻味的细节：第一步遇到 409（`InvalidTransition`）**不抛**，
按"resume 重入幂等"放行——想想 3.1 说的"执行后、标记落库前崩溃"的窗口：如果执行体跑完
M2 approve 后 run 意外崩了，重试 resume 会再进一遍执行体，账面已是 approved（409），
**chroma upsert 本身幂等**（同 id 覆盖），所以重放安全。对比 3.2 的幽灵条目：M2 的 approve
REST 端点自己也能翻账面，但它**没有第二步**——第二步住在这条已验签的路径里。

本步实测，chroma 里那条正门入库的条目（POST /collections/:id/get）：

```json
{ "ids": ["kb_11d09bb0-…"],
  "metadatas": [{ "kind": "env_fact", "title": "环境事实：centos7 …",
                  "source_case_id": "case_000004", "tags": ["centos7","env_fact"] }],
  "documents": ["环境事实：centos7 …\n## 事实\n- 主机：centos7；…" ] }
```

id=提案 id（两边对得上账）、document=title+body 拼接（kb_write 写入时的 `text` 字段，
检索时命中返回的就是它）、metadata 四件套（kind/title/出处/tags——3.4 分诊检索时
`ChromaKb` 会把这些映射成 KbHit）。

## 三、服务与中间件卡

### 卡 1（自研）· 两种票：L1 任务票 vs L2 ApprovalToken

- **它是什么**：系统里所有"票"分两种。**L1 任务票**（`tk_…`）：worker 拉起时铸，活一个
  run 的生命周期，工具面 = 该 worker 的 L1 工具集，闸在每次工具调用时验。**L2
  ApprovalToken**（`ap_…`）：人批准时一枚一铸，活 300 秒，只授权**一个动作**（tool +
  params_hash 指纹），闸在执行前验，**用后即焚**（TERMS「一次性密令（ApprovalToken）」条：
  一动作一铸、用后即焚、批准≠执行）。
- **为什么要两种**：L1 回答"这个 agent 正常上班能干什么"（读案、写时间线这类低危日常）；
  L2 回答"这一次破例做什么危险的事"（写知识库、隔离主机）。前者量大、面宽、可重验；
  后者量小、面窄、一次性。把两者混成一张票，要么日常被审批淹死，要么高危动作失去
  人审——票的粒度就是权限的粒度。
- **业务上怎么选**：凡是"AI 可以反复做"的写操作→任务票工具面；凡是"AI 只能建议、人来
  拍板"的操作→审批卡+一次性 token。判定标准就一条：**这个动作做错了，能撤销吗？
  撤销代价多大？**（时间线写错可删，主机隔离了业务停摆。）

### 卡 2（开源）· LangGraph interrupt/Command：框架原生的"暂停-恢复"

- **它是什么**：LangGraph.js 的原生挂起机制——节点内抛 `interrupt(cardId)`，整图在当前
  superstep 冻结（状态已进 checkpointer）；恢复时用 resume 值重启该节点，节点**从头重跑**。
- **本项目怎么用**：`awaitApproval` 把 interrupt 包成"轮查卡的循环"——不信框架回吞的
  resume 值，每圈以 DB 里的卡为准（[graph.ts:219-222](soc-demo/services/agent/src/graph.ts#L219)
  注释原话）。挂起态由 openApprovalCard 在开卡事务里原子写进 run 行（awaiting_approval），
  重启后靠 checkpointer 的信封链续跑（1.4 讲过的信封 hash 在挂起恢复时同样防篡改）。
- **市面替代**：自研状态机（把"挂起"做成一种 run 状态、把节点做成状态迁移函数）——本
  系统 run 行确实有 awaiting_approval 状态，但图内部的中断点/恢复点交给框架，省掉手写
  "跑到哪个节点"的簿记。Temporal/Celery 这类工作流引擎是更重的同思想件。
- **业务上怎么选**：挂起恢复点少、流程图稳定→LangGraph 这类轻框架；长事务、跨天、
  需要人工介入点极多→重量级工作流引擎（Temporal）；只是"等一个外部回调"→一张状态
  位+轮询可能就够了。

**C · 纸面推演（场景 4 主场，先挂账）**：这枚 token 如果——过期 300 秒后才用（`ticket_expired`）、
执行参数被换（`params_mismatch`）、焚毁后重放（`already_used`）、签名被改（`signature_invalid`）、
M2 焚毁读口病了（fail-closed 也拒）——闸各用什么理由拒、审计怎么记，4.5《resume 与验票》
逐个实测。本步你只需记住结构：**验签在闸、焚毁在执行后、真相在跨进程读口**。

**D · 纸面推演**：如果 resume 时**不**重组 worker 图（`rebuildResumeNodes` 缺位），静态
薄径图里没有 kb_write 节点——LangGraph 找不到挂起节点直接跑完，run 看似 completed、
L2 动作**静默丢失**（token 铸了没花、知识没入库、没有报错）。这是票 17 用真金白银换来的
教训（app.ts:333 注释原文），也是"静默丢失"类缺陷的典型样本：**不炸响的故障比炸响的更贵**。
