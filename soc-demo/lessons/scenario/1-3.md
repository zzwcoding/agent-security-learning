# 1-3 · 自动拉起与铸票：数字员工上班，先领手令

> 场景 1 第 3 步。上一步档案室建好了档、在叫号屏（outbox）写了 `alert.created`；
> 这一步看**数字员工**（agent 服务）怎么看到叫号、自动开工——以及它开工前必须先
> 干的一件事：**去保安处领一张写清"能动什么"的手令**（任务票）。

**位置感**：

```
✅ 1.1 布景与推单
✅ 1.2 去重与落库
✅ 1.3 自动拉起与铸票（你在这里）
⬜ 1.4 分诊六节点（上）
⬜ 1.5 分诊六节点（下）
⬜ 1.6 收官透视
```

## 一、这一步做什么

前两步的主角都是"库"——这一步起，**干活的进程**登场了。agent 服务（数字员工，
:3003）里挂着两个后台循环，像值班室里两个不睡觉的员工：

- **看板的（autorun）**：每 2 秒瞄一眼档案室的叫号屏（outbox 表），看到
  `alert.created` 就自动拉起分诊；
- **派活的（dispatcher）**：每 0.1 秒看一眼自家任务队列（run_jobs 表），领了任务
  就去**铸票、组队、开工**。

为什么开工前要先领手令（任务票）？这就是这套系统的安全卖点：数字员工**自己手里
一滴权限都没有**——查档案、写案件每一步都要亮票，票是保安处（gateway）签的、
上面写死了能碰哪几个抽屉（scope）、能用哪几件工具（allowed_tools）、几点失效
（TTL 900 秒）。没有票，图的第一步都迈不出去。

## 二、调用链

```
（后台）档案室叫号屏 outbox_events：新行 alert.created   ← 1.2 的站 4
  │ 每 2 秒
  ▼
▼ services/agent（数字员工 :3003，框架 ▲Fastify）
  站 1  autorun.pollAutorunOnce()   读一批事件，逐条裁决
  站 2  autorun.decide()            拉起/跳过/失败的裁决台（防重三道）
  站 3  app POST /internal/runs     自家正门：注册表校验 → 建 run（queued）→ 入队
  │                                  202 {run_id} 秒回
  站 4  dispatcher 消费循环          领任务 → executeStartJob：向 gateway 铸任务票
  │ POST http://gateway:8002/internal/mint   （同步，2 秒超时）
  ▼
▼ services/gateway（保安处 :8002，框架 ▲FastAPI）
  站 5  mint_token() → mint_task_ticket()   拿 HMAC 密钥签出三段式票据
  │ 回 {token, payload}
  ▼
agent 拿着票组图开工（1.4/1.5 的分诊六节点，本步到"票到手"为止）
```

### 站 1 · 看板的看板：消费一轮

📄 [services/agent/src/autorun.ts:206-229](soc-demo/services/agent/src/autorun.ts#L206)：

```ts
export async function pollAutorunOnce(deps: AutorunDeps): Promise<AutorunPollResult> {
  let cursor = deps.cursor.get(AUTORUN_CURSOR);
  const batch = await deps.events.eventsAfter(cursor, BATCH_LIMIT);
  const res: AutorunPollResult = { scanned: batch.length, launched: [], skipped: [], cursor };
  const batchSeen = new Map<string, Set<string>>();
  for (const e of batch) {
    const d = await decide(e, deps, batchSeen);
    if (d.action === "failed") {
      res.failed = { topic: e.topic, refId: String(e.payload.alertId ?? e.payload.caseId ?? ""), error: d.error };
      deps.log?.({ warn: "autorun_launch_failed", topic: e.topic, after: cursor, error: d.error });
      break; // 游标不动，下轮从失败事件重试（at-least-once）
    }
    cursor = e.id;
    deps.cursor.set(AUTORUN_CURSOR, cursor);
    if (d.action === "launched") {
      res.launched.push(`${d.kind}:${d.refId}`);
      deps.log?.({ info: "autorun_launched", kind: d.kind, refId: d.refId, event: e.id });
    } else {
      res.skipped.push(d.skip);
    }
  }
  res.cursor = cursor;
  return res;
}
```

核心是一根**游标**（水位线）：存在 agent 自己的库里
（[autorun.ts:69-84](soc-demo/services/agent/src/autorun.ts#L69) 的
`dbCursorStore`，表 `event_cursors`），记着"看到几号事件了"。每轮从 `cursor 之后`
读一批（最多 100 条），**逐条裁决、逐条推游标**。出错怎么办？文件头的口径
（[autorun.ts:20-21](soc-demo/services/agent/src/autorun.ts#L20)）："拉起失败 =
at-least-once：本批中止、游标不动、下轮重试——**不丢**优先于**不阻塞**"。那重试
会不会把同一条告警拉起两次？这正是站 2 防重三道存在的理由。

```python
def mint_task_ticket(key, *, jti, sub, case_id, run_id, scope, allowed_tools,
                     iat=None, ttl=TASK_TTL):
    """签任务票（PRD §5.8）：worker 拉起时的任务级最小 scope 票（M9-S6）。

    iat 不传取当前时间；测试冻结 iat 即可逐字节复现契约 fixture。
    返回 (token, payload)，payload 给调用方看 exp 等 claims。

    iat = int(time.time()) if iat is None else iat
    payload = {  # 字段集与顺序照 PRD §5.8，一字不增不减
        "jti": jti,
        "sub": sub,
        "case_id": case_id,
        "run_id": run_id,
        "scope": list(scope),
        "allowed_tools": list(allowed_tools),
        "iat": iat,
        "exp": iat + ttl,
    }

```

票长什么样？文件头（[mint.py:6-8](soc-demo/services/gateway/mint.py#L6)）给了
**票型公式**：

```
token = <b64url(header)>.<b64url(payload)>.<hex(hmac_sha256(key, "b64h.b64p"))>
```

三段用点号连起来，像一张对折两次的密令：第一段写"用什么算法签的"，第二段写
**手令内容**（谁能动哪个抽屉、能用哪几件工具、几点失效——`exp = iat + 900` 秒，
[mint.py:24](soc-demo/services/gateway/mint.py#L24) `TASK_TTL = 900`），第三段是
**防伪章**：只有持同一把密钥（`SOC_HMAC_KEY`，只活在 gateway 的环境变量里）才能
造得出来；agent 那边验票时重算一遍对得上，才认这张票。伪造票 = 在不知道密钥的
情况下造出正确的防伪章，密码学上不可行。

## 三、服务与中间件卡

**卡 1 · HMAC 签名票（自研票型，密码学原语 ▲标准 HMAC-SHA256）**

- **替我们干了件什么体力活**：让"你有没有资格干这件事"这件事，**不靠查户口、
  靠验章**。agent 不用维护权限数据库，gateway 签完票就撒手；谁拿到票，验签的
  一方自己就能独立判断真伪和有效期——分布式的信任，靠一小段数学。
- **自研还是开源**：HMAC-SHA256 本身是几十年的国际标准原语（Python 标准库
  `hmac`、Node 标准库 `crypto` 都内置）；**票型是自研的教学变体**——签名段用 hex
  摘要而非标准 JWT 的 b64 段（[mint.py:6-8](soc-demo/services/gateway/mint.py#L6)
  写明"教学变体，非 JWT 标准 b64 段"），为的是跨语言 fixture 能逐字节复现。
- **本项目怎么配置**：密钥 `SOC_HMAC_KEY` 只挂在 gateway 的 env
  （[app.py:31-33](soc-demo/services/gateway/app.py#L31)），`.env` 里是教学假值，
  真部署由环境注入；agent 侧验票用同一把（[app.ts:76-77](soc-demo/services/agent/src/app.ts#L76)
  `hmacKey`，缺省读同一 env）。
- **市面上同类**：标准 JWT（PyJWT/jose 库，生态通用）、非对称签名 RS256/Ed25519
  （签发方持私钥、验证方只持公钥）、PASETO（"JWT 的修正版"）。
- **本项目为什么选 HMAC 对称票**：单机九容器、签发方和验签方就两家且同持一把
  教学密钥——对称最简单、最快、讲解最透；hex 变体让"改一个字节签名就变"肉眼
  可见。代价是**对称 = 谁能验谁就能签**，这在生产是要掂量的。
- **业务上怎么选**：内部微服务互信、双方同域 → HMAC 对称票够用；票要发给**外部**
  或验证方多而签发方少 → 非对称（RS256/Ed25519，私钥只在签发方）；正经产品直接用
  成熟 JWT 库 + 短 TTL + jti 防重放，别手搓变体（本项目手搓是**教学需要**，不是
  生产建议）。

**卡 2 · run-kinds 注册表（自研模式）—— 流水线的"一张花名册"**

- **替我们干了件什么体力活**：系统里有五种流水线（分诊/沉淀/对话/调查链/关单），
  每种"吃什么单子、票面给什么、图怎么组"曾经散在 9+ 个文件里
  （[run-kinds.ts:3-8](soc-demo/services/agent/src/run-kinds.ts#L3) 头注释原文：
  "一个 run kind 的知识散在 9+ 处……加一个 kind 要全仓摸一遍，漏一处就静默漂移"）。
  票 44 把它们收进**一张表**（[run-kinds.ts:140](soc-demo/services/agent/src/run-kinds.ts#L140)
  `REGISTRY`）：kind → {吃 alert 还是 case、票面、图工厂}，其他代码各取所需。
- **本项目怎么配置**：纯代码内注册表 + 一条完整性测试（五个 kind 三件套齐全、
  INV-3 无 L2、与 web 端预置节点样品契约对齐）——改表不改测试，CI 红。
- **市面上同类**：配置文件驱动的流程引擎（Camunda/Temporal 这类工作流平台）、
  注解/装饰器扫描（NestJS 模式）、schema 校验集中定义（Zod/Pydantic 单源）。
- **本项目为什么选代码内注册表**：五种流程、变化慢、要**类型检查和测试锁**——
  代码内的表最直白；上工作流平台是杀鸡用牛刀，注解扫描则把"有哪些流程"藏进
  魔法里，教学和审查都难。
- **业务上怎么选**：流程种类固定且少（<10）→ 注册表；流程由业务人员动态编排、
  要版本化/回滚/人工介入节点 → 工作流引擎（Temporal/Camunda）；只怕字段漂移 →
  schema 单源 + 测试。

## 四、防线对号

- **INV-3（worker 票面永不含 L2）**：本步的铸票源头——注册表里 alert_flow 的
  `allowed_tools` 是分诊∪调查∪富化三个 **L1** 工具族的并集
  （[run-kinds.ts:53-54](soc-demo/services/agent/src/run-kinds.ts#L53) 注释原文：
  "INV-3：票面永不含 L2"）。高危动作（隔离主机、写 KB）不在这张票上，它们要走
  场景 4 的人工审批。
- **INV-1（fail-closed）**：三处都在本步——不在册 kind 一律 400（站 3）；gateway
  没有密钥拒签 500（站 5）；铸票失败 run 明着 failed(mint_failed)，绝不留一张
  "无票奔跑"的 run（站 4）。
- **INV-6 的第三道保险**：1.2 的唯一索引管"库里不重复"、1.3 站 2 的 `run_exists`
  管"同一告警不重复拉起"、再加上票 13 的 verdict 锁（1.5 上场）兜并发——同一
  告警被重复分诊的三条路全部堵死。
- **INV-8/INV-10**：run 出生（createRun）与每次状态迁移（`transitionRun`，
  [runs.ts:84-115](soc-demo/services/agent/src/runs.ts#L84)——断言合法迁移才落库，
  非法 409）都带审计；铸票失败走 `queued→running→failed` 是**合法两步迁移**，
  状态机不破例。

## 六、捣乱实验

```bash
# A. 造一个不在册的流水线种类 → 注册表当场拒收（无任何残留）
curl -s -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:3003/internal/runs \
  -H 'content-type: application/json' -d '{"kind":"nuke_everything","alert_id":"4e11d030-2339-48f3-98c7-f1a0a8bb100e"}'
#   应看到 {"error":"unknown_kind","details":["nuke_everything"]} + HTTP 400

# B. 在册的 kind 但缺单子号 → 400，不造空 run
curl -s -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:3003/internal/runs \
  -H 'content-type: application/json' -d '{"kind":"alert_flow"}'
#   应看到 {"error":"kind_and_alert_id_required"} + HTTP 400

# C. 保安处下班了还能开工吗？——铸票断路的活教材
docker compose stop gateway
curl -s -X POST http://127.0.0.1:3003/internal/runs \
  -H 'content-type: application/json' \
  -d '{"kind":"alert_flow","alert_id":"4e11d030-2339-48f3-98c7-f1a0a8bb100e"}'
#   仍会拿到 202 {run_id}（正门只管收单入队）——但几秒后：
sqlite3 "file:data/agent/agent.sqlite?mode=ro" \
  "SELECT status, fail_reason FROM runs ORDER BY created_at DESC LIMIT 1;"
#   应看到 failed|mint_failed ——「不留无票 run」：票没领到，run 明着失败，不静默、不裸奔
docker compose start gateway
#   把保安处叫回来。这条失败 run 留着无妨（autorun 防重对它不生效——手工造的，
#   但 failed 本来就允许重拉），1.6 透视时它还是个现成的"失败长什么样"教具
```
