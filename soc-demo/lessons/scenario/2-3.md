# 场景 2 · 步 2.3 —— 调查报告（findings 引用真实工具输出、只提建议不动手）

> 巡逻完了要交报告。调查报告是 LLM 在这条链上**话语权最大**的产物：案情结论、严重度、
> 影响资产全由它写。话语权大，把关就必须硬。本步讲两根定海神针——
> **① findings 必须引用真实工具输出**（说谎的报告自动降级成「自由文本+污点标记」）；
> **② 只提建议不动手**（报告里可以喊「隔离主机」，但从结构上就到不了执行层，零 L2）。

---

## 一、操作（位置感）

先看一份**已经落库的真报告**——用 2.2 里 A/B 实验拉过的 case_000002（app-01 案，
severity 3，正是会触发「建议隔离」的档位）：

```bash
curl -s localhost:3002/api/v1/cases/case_000002/timeline | python3 -c "
import json,sys
items=json.load(sys.stdin)
items=items if isinstance(items,list) else items.get('entries',[])
rep=[e for e in items if e['kind']=='investigation_report']
print(rep[-1]['body'])"
```

读三个位置：**Findings** 段的每条 evidence 都是工具输出的逐字摘录（比如 SIEM 日志原文、
关联告警的 alert id）；**建议动作** 段写着 `` `isolate_host` {"host":"app-01"}``——
sev≥3 的案子 fake LLM 必提隔离；然后去审批卡 REST 确认**什么都没发生**：

```bash
curl -s localhost:3003/api/v1/approvals
```

预期：`{"approvals":[]}`。建议文字躺在报告里，审批卡一张没开，主机一根网线没拔。
「建议」与「执行」之间隔着整条人审链（场景 4 的主角），本步先看清链条的起点为什么
根本推不动终点。

再确认 web 端（http://localhost:5173 案件详情页）：报告渲染成排版好的 markdown 时间线
条目——人读的是 `body`，机读的 `structured`（同一行记录里的另一个字段）才是程序
消费的真相。**双形态**是本步第二张卡的主题。

### 站 2 · prompt 装配：只喂观察史

export function buildReportPrompt(input: ReportCall["input"]): string {

### 站 3 · attempt()：schema 验型 + 证据复核，一次过两关

📄 [services/agent/workers/investigation/flow.ts:429-440](soc-demo/services/agent/workers/investigation/flow.ts#L429)

```ts
        const attempt = async (): Promise<{ text: string; evidenceOk: boolean; error: string | null }> => {
          const call: ReportCall = { prompt: buildReportPrompt(input), input };
          const startedAt = Date.now();
          const reply = await deps.llm.report(call);
          ctx.charge(reply.tokens);
          ctx.checkLlm(startedAt, Date.now());
          const parsed = parseReport(reply.text);
          if (!parsed.ok) return { text: reply.text, evidenceOk: false, error: parsed.error };
          // findings 引用真实工具输出的确定性半边：source_tool 必须真被调用过
          const evidenceOk = parsed.report.findings.every((f) => loop.executed.includes(f.source_tool));
          return { text: reply.text, evidenceOk, error: evidenceOk ? null : "finding_source_tool_not_executed" };
        };
```

两道关，一道比一道有趣：

- **parseReport 显式验型**（[schema.ts:45-92](soc-demo/services/agent/workers/investigation/schema.ts#L45)）：
  逐字段手写把关——summary 非空字符串、severity 是 1-4 整数、confidence 0-1、
  findings 每条三字段齐全、incomplete 只许 boolean……文件头注释点破为什么不用
  JSON Schema 库：「undefined 参与比较会静默漏过，必须逐字段把关——fail-closed 的
  schema 版」。类型不对 → `bad_summary` / `bad_severity_assessment` 这类精确错误码。
- **证据复核（本步的灵魂）**：`loop.executed` 是站 5（2.2）里每次工具**成功执行**后
  记下的名单；`findings.every(f => loop.executed.includes(f.source_tool))` 逐条核对
  ——你报告里引用的每个 source_tool，必须真在这份名单上。LLM 说「web_search 查到」
  而 web_search 根本不在工具面（更没执行过）？`finding_source_tool_not_executed`，
  这一次 attempt 判死。

注释里「确定性半边」五个字值得停留：这一行只能证明**工具被执行过**，证明不了
evidence 文字**逐字**来自那个工具的输出（LLM 可以执行了 siem_query 却编造引文）。
逐字比对属于 eval 层的另一半（fixtures 契约群+评测断言，场景 8.1 的领地）。
**闸管得住「引用没跑过的工具」，管不住「跑了工具还编原文」——两层各管一半，
合起来才是完整的证据链。**

### 站 4 · 重试一次，然后降级

📄 [services/agent/workers/investigation/flow.ts:442-481](soc-demo/services/agent/workers/investigation/flow.ts#L442)

```ts
        let result = await attempt();
        if (result.error !== null) {
          // PRD 异常与边界：schema 校验失败重试 1 次，仍失败降级自由文本 + 标记
          record({
            action: "llm_retry",
            objectId: deps.runId,
            objectType: "investigation_report",
            details: { error: result.error },
            result: "FAILURE",
          });
          result = await attempt();
        }

        if (result.error === null) {
          const parsed = parseReport(result.text);
          // attempt 通过 = parse 必 ok；这里再解一次拿强类型的 report
          if (!parsed.ok) throw new Error(`unreachable: ${parsed.error}`);
          const incomplete = loop.incomplete || parsed.report.incomplete === true;
          const structured = { ...parsed.report, incomplete };
          ctx.state.report = {
            body: renderReportMarkdown(parsed.report, { caseId: kase.caseId, title: kase.title }),
            structured,
            degraded: false,
            incomplete,
          } satisfies ReportState;
        } else {
          record({
            action: "report_degraded",
            objectId: deps.runId,
            objectType: "investigation_report",
            details: { error: result.error },
            result: "FAILURE",
          });
          ctx.state.report = {
            body: `<!-- report_degraded: 调查报告 schema/引用校验未过，以下为自由文本 -->\n${result.text}`,
            structured: null,
            degraded: true,
            incomplete: loop.incomplete,
          } satisfies ReportState;
        }
```

降级不是丢弃：报告原文**照样进时间线**，但带三重污点——正文开头 `<!-- report_degraded: … -->`
注释、`structured: null`（机读真相缺席，下游程序看得见）、审计 FAILURE
`report_degraded`。比喻：实习生交了份不合规报告，主管**不撕掉**，而是钉一张
「未经核验」的粉色便签一起归档——案卷完整，但谁看了都知道这份不能直接信。
两条路线都把 `incomplete` 合并进账（循环截断 OR 报告自认，取或——任何一边说
不完整就是不完整）。

### 站 5 · 渲染：一个真相，两张脸

📄 [services/agent/workers/investigation/schema.ts:98-113](soc-demo/services/agent/workers/investigation/schema.ts#L100)

```ts
/** TheHive task log 风格的渲染体（TimelineEntry.body）。structured 才是机读真相，
 *  body 是人读的渲染——两者同写一条 timeline（FR-M5.4 双形态）。 */
export function renderReportMarkdown(
  report: InvestigationReport,
  meta: { caseId: string; title: string },
): string {
  const lines: string[] = [
    `## 调查报告 · ${meta.title}`,
    "",
    `- 案件: ${meta.caseId}`,
    `- 结论: ${report.summary}`,
    `- 严重度评估: ${report.severity_assessment}（confidence ${report.confidence}）`,
```

以及结尾的诚实徽章（[schema.ts:127-129](soc-demo/services/agent/workers/investigation/schema.ts#L127)）：

```ts
  if (report.incomplete) {
    lines.push("", "⚠️ **调查不完整**：max_steps 用尽被截断，以上为部分调查结果。");
  }
```

**structured 是真相，body 是渲染**——渲染永远是确定性代码干的（LLM 只写 structured
的原料），所以你在 web 上看到的每个标题、每个列表项都能机械地映射回 JSON 字段。
Findings 空时渲染「（无——证据缺口如实留白，不编造）」，建议为空渲染「（无）」，
0 命中的诚实贯穿到展示层。

## 三、服务与中间件卡

**卡 1 · ▼结构化输出的把关（手写显式验型 + 证据交叉核对）**

- **它是什么**：LLM 回包 → 显式逐字段验型（parseReport）→ 与运行时事实交叉核对
  （source_tool ∈ executed）。两关都过才算结构化报告。
- **市面替代**：① JSON Schema / Zod / Pydantic 声明式校验；② 模型厂商的
  structured outputs（强制 JSON 模式）；③ 只验 JSON 可解析，字段全信。
- **为何这么选**：声明式 schema 只能验「形」，验不了「实」——source_tool 是不是
  真执行过，schema 写不出来，必须跟 `loop.executed` 交叉核对。形这一半手写而不用
  库，是因为错误码要精确到字段（`bad_time_window.order` 这种喂回 LLM 能自纠的
  错误），且显式验型把「undefined 陷阱」摆在明面上（schema.ts 头注原话）。
  厂商 JSON 模式只保形不保实，且把可靠性押在单一厂商特性上。
- **业务上怎么选**：所有「LLM 输出会变成机读真相」的地方，形+实两道都要有。
  只有形的（内部草稿）可以用库省事；形实都不验的（直接信 LLM 文本）只允许出现在
  不落库、不触发动作的场景。

**卡 2 · ▼报告双形态：body 人读 + structured 机读（TheHive task log 先例）**

- **它是什么**：一条 timeline 条目同时存渲染后的 markdown（body）和原始 JSON
  （structured）。人看 body，程序（web 图表、eval 断言、下游 worker）吃 structured。
- **市面替代**：① 只存 markdown，程序用正则反解析（脆）；② 只存 JSON，人看工具里
  临时渲染（案卷不可读）；③ 双存但两处各自演化（漂移——本项目用「渲染是确定性
  函数」锁死：body 永远可以从 structured 算出来）。
- **为何这么选**：SOC 案卷的用户一半是人（值班长、复盘），一半是程序（web 页面、
  评测、下一个 worker）。TheHive（开源 SOC 案件管理平台）的 task log 就是这个形态
  的成熟先例，照抄不丢人。
- **业务上怎么选**：任何「LLM 产物要进案卷/报表」的场景都该双形态。判断标准：
  这份内容**半年后**被谁消费？被人 → body 不能少；被程序 → structured 不能少；
  都有 → 双形态 + 确定性渲染。

## 六、捣乱实验（必选）
