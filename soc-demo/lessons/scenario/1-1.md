# 1-1 · 布景与推单：把告警从前台正门推进来

> 本篇是场景 1「一条 TP 告警的一生」的第 1 步。场景目标：跟着一条会升级成案件（TP）的告警，
> 从进门走到结案，把系统的主干链路走一遍。

**位置感**（本场景 6 步路线图）：

```
✅ 1.1 布景与推单（你在这里）
⬜ 1.2 去重与落库
⬜ 1.3 自动拉起与铸票
⬜ 1.4 分诊六节点（上）
⬜ 1.5 分诊六节点（下）
⬜ 1.6 收官透视
```

## 一、这一步做什么

在真实的安全公司里，告警是楼里成百上千个"烟感探头"（装在每台服务器上的安全软件）
自动打回来的**报案电话**。我们这套系统叫 soc-demo，它的第一个动作就是接报案——但教学
环境里没有真探头，所以我们派了个**演示员**替探头干活：把 12 份写好的报案单
（`fixtures/alerts/` 里的 JSON 文件）一份一份从前台正门递进去。

本步就三件事：

1. 把系统跑起来（九个容器，一条命令）；
2. 让演示员推一遍单（`pnpm replay`），12 份全部被前台接收；
3. 故意递几份填错的单，看前台怎么拒收、怎么记台账。

本步的主角是这份报案单 `fixtures/alerts/vt-87105-malware.json`：服务器上有个文件
`/tmp/invoice_apr.zip`，VirusTotal（一家查毒机构）说 70 个杀毒引擎里 5 个报毒。
这个告警后面会升级成案件，全场景都跟着它走。

### 站 0 · `pnpm replay` 这条命令到底是什么

pnpm 只是个"替你跑脚本"的传令兵，它去 [package.json:13](soc-demo/package.json#L13)
查到这张字条：

```json
"replay": "tsx scripts/replay.ts",
```

意思是：用 tsx（一个能直接运行 TypeScript 文件的小工具）执行 `scripts/replay.ts`。
而前台窗口的**门牌号**（端口）是编排文件定的，[docker-compose.yml:5-10](soc-demo/docker-compose.yml#L5)：

```yaml
ingest:
  build: { context: ., dockerfile: services/ingest/Dockerfile }
  ports: ["3001:3001"]
  # 缺它 m2client 回退 127.0.0.1:3002——容器里指 ingest 自己，webhook 必 500
  environment:
    CASE_BACKEND_URL: http://case-backend:3002
```

两个要点：`ports: ["3001:3001"]` 把容器的 3001 开到你笔记本的 3001，所以你 curl
本机 3001 就是敲前台的门；`CASE_BACKEND_URL` 是前台转交档案室用的地址——
`case-backend` 是**容器名**，在容器网络里它就是门牌号（等价于"档案室在 3 号楼"），
不用记 IP。上面那行注释还提醒了：这个环境变量要是没配，前台会把单子转交给自己，
转死循环。

### 站 1 · 演示员读单递单

📄 [scripts/replay.ts:58-67](soc-demo/scripts/replay.ts#L58) · 批量递单的主循环：

```ts
export async function replay(opts: ReplayOptions): Promise<ReplayRecord[]> {
  const files = readdirSync(opts.dir).filter((f) => f.endsWith(".json")).sort();
  const gapMs = Math.max(0, Math.round(1000 / Math.max(opts.rate, 1)));
  const out: ReplayRecord[] = [];
  for (const f of files) {
    if (out.length > 0 && gapMs > 0) await new Promise((r) => setTimeout(r, gapMs));
    out.push(await replayOne(opts.url, f, readFileSync(join(opts.dir, f), "utf8")));
  }
  return out;
}
```

大白话：把 `fixtures/alerts/` 下所有 `.json` 按文件名排好队，每隔 `gapMs` 毫秒递一份
（默认每秒 5 份，`--rate` 可调），**每份都等前台回话了才递下一份**——站柜台等叫号，
不是扔下就走。递单这个动作本身在 [scripts/replay.ts:39-43](soc-demo/scripts/replay.ts#L39)：

```ts
const res = await fetch(`${url}/api/v1/webhooks/alerts`, {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: payload,
});
```

就是最普通的 HTTP POST。注意它递的是**文件原文**（`readFileSync` 出来的字符串），不解析
不加工——演示员只负责跑腿，单子长什么样由 fixture 文件说了算。

### 站 2 · 前台收案：先验资格

📄 [services/ingest/src/app.ts:48-55](soc-demo/services/ingest/src/app.ts#L48) · 正门路由开头：

```ts
app.post("/api/v1/webhooks/alerts", async (req, reply) => {
  const body: unknown = req.body;
  const alerts: unknown[] = Array.isArray(body) ? body : [body]; // FR-M1.1 单条/批量
  const details: string[] = [];
  alerts.forEach((w, i) => {
    const v = validateWazuhAlert(w);
    if (!v.ok) details.push(...v.details.map((d) => `[${i}] ${d}`));
  });
```

第一行就处理了个现实问题：来的可能是一张单，也可能是一摞单（JSON 数组）——`[body]`
把单张也包成摞，后面代码只用一种写法。然后**每一张**都过一遍资格审查，不过审的把原因
记进 `details`（带 `[0]` 这种序号，说明是摞里第几张坏了）。

📄 [services/ingest/src/wazuh.ts:21-33](soc-demo/services/ingest/src/wazuh.ts#L21) ·
资格审查本身（收案只卡两条硬标准）：

```ts
export function validateWazuhAlert(w: unknown): Validation {
  if (typeof w !== "object" || w === null || Array.isArray(w)) {
    return { ok: false, details: ["body_not_object"] };
  }
  const o = w as Obj;
  const details: string[] = [];
  const rule = asObj(o.rule);
  if (rule.id === undefined || rule.id === null || rule.id === "") details.push("rule.id_missing");
  if (typeof o.timestamp !== "string" || Number.isNaN(Date.parse(o.timestamp))) {
    details.push("timestamp_missing_or_invalid");
  }
  return details.length > 0 ? { ok: false, details } : { ok: true };
}
```

大白话：① 整体得是个对象（不是数字不是字符串）；② `rule.id`（警情编号）必须有；
③ `timestamp`（报警时间）必须是能看懂的时间写法。**就这三条，别的一概不查**——单子上
出现谁也没见过的字段？照收，原样塞进 `raw` 留底（`wazuh.ts:137`）。

为什么要这么松？PRD 给前台定的职责是"收案窗口"：管单子**能不能收**，不管单子内容
**干不干净**。查得太死，探头厂商明年加个新字段，我们前台就把正经告警拒了；完全不查，
连"这是张报案单"都不成立。所以只卡"身份成立"的最低限度。

### 站 3 · 拒收分支：先记台账，再退单

📄 [services/ingest/src/app.ts:56-66](soc-demo/services/ingest/src/app.ts#L56) ·
有任何一张不过审时走这里：

```ts
if (details.length > 0 || alerts.length === 0) {
  // 票 35（票 09-3）：校验失败 422 同时向 M2 审计 FAILURE（actor=ingest），
  // objectId 取批里第一条声明的告警 id（溯源锚）；await 但 adapter 自吞错——
  // 审计挂了 422 照发，只是本地多一行 warn 日志。
  await m2.auditFailure({
    objectId: alerts.length > 0 ? declaredAlertId(alerts[0]) : "unknown",
    details: { reasons: details.length > 0 ? details : ["empty_body"] },
    requestId: requestIdOf(req.headers as Record<string, unknown>),
  });
  return reply.status(422).send({ error: "invalid_alert", details });
}
```

大白话：拒收之前先干一件事——**往档案室的台账里记一笔 FAILURE**（谁拒的：`m1:ingest`；
拒的是哪单：警情编号，实在取不到就写 `unknown`；为什么拒：和退回给演示员的
`details` **同一份理由**，不是两套说法）。然后才回 `422`。这样前台就算天天拒单，
台账上也有完整记录可查——你待会儿在第六节亲手查过这条。

还有一类坏单更极端：**纸都撕破了**（JSON 写了一半）。这种连路由函数都进不去，框架
直接报错——前台的"错误盖写器"接住它（细则较多，给伪代码；真实实现在
[services/ingest/src/app.ts:18-34](soc-demo/services/ingest/src/app.ts#L18)）：

```
伪代码 · 出错盖写器(请求出错的场合):
    若 错误是“JSON 残缺”或框架给的 400:          # Fastify 对畸形 JSON 默认回 400
        若 请求走的是告警正门: 往台账记一笔 FAILURE（原因=错误消息）  # 同样留痕
        回 422 { error: "invalid_alert", details: [错误消息] }
    否则:
        回 500 internal_error                    # 真程序 bug，另案处理
```

效果：无论"字填错"还是"纸撕破"，演示员看到的都是统一的 **422 invalid_alert**——
前台不让你猜"到底是我格式不行还是它程序坏了"，答案只有一种：**你的单子不合格**。

### 站 4 · 方言翻译：mapWazuhAlert

过审的单子进入翻译间。探头系统说"探头方言"（Wazuh 格式），我们档案室记"档案方言"
（TheHive 格式），翻译由
📄 [services/ingest/src/wazuh.ts:107-140](soc-demo/services/ingest/src/wazuh.ts#L107)
的 `mapWazuhAlert` 一手包办。翻译时顺手做三件好事，一件一件看：

**好事 a · 换算严重度**（探头用 0-15 分，我们用 1-4 级）。
📄 [services/ingest/src/wazuh.ts:10-15](soc-demo/services/ingest/src/wazuh.ts#L10)：

```ts
export function severityFromLevel(level: number): number {
  if (level >= 15) return 4;
  if (level >= 10) return 3;
  if (level >= 5) return 2;
  return 1;
}
```

主角告警 `rule.level = 12` 落进 `>= 10` 档 → `severity: 3`（高）。纯查表，没有任何
智能成分——**确定性**是收案窗口的纪律，翻译环节混进"随机发挥"，后面所有环节都没法复现。

**好事 b · 盖不可信封条**。📄 [services/ingest/src/wazuh.ts:36-38](soc-demo/services/ingest/src/wazuh.ts#L36)：

```ts
export function untrustedSection(field: string, content: string): string {
  return `[untrusted:true field:${field}]\n${content}\n[/untrusted]`;
}
```

正文里的 `full_log`（探头抓回来的原始日志，比如那条 HTTP 请求记录）是**攻击者路径上的
东西**——里面每个字符都可能是坏人写的。翻译时把它用一对封条包起来：
`[untrusted:true field:full_log] …… [/untrusted]`，意思写明"这段是外人说的话"。
下游（比如给 AI 看的提示词）看到封条就知道：**这是资料，不是命令**，不许照着办。

**好事 c · 抽出可观测物**（observable＝案子里值得记录的"实物"：IP、文件名、指纹）。
📄 [services/ingest/src/wazuh.ts:60-67](soc-demo/services/ingest/src/wazuh.ts#L60)：

```ts
push("hostname", agent.name, "agent.name", false);
push("ip", data.srcip, "data.srcip", true);
push("other", data.srcuser, "data.srcuser", true);
push("url", data.url, "data.url", true);
push("filename", sys.path, "syscheck.path", false);
for (const [k, v] of Object.entries(sys)) {
  if (HASH_FIELD.test(k)) push("hash", v, `syscheck.${k}`, false);
}
```

大白话：从报案单里翻出五类实物——哪台机器（hostname）、哪个 IP（ip）、哪个用户
（srcuser）、哪个网址（url）、哪个文件（filename/文件指纹 hash）。最后一个参数就是
**封条开关**：`agent.name`（我们装的探头名）和 `syscheck.*`（我们自己的文件完整性
检查）是**自己人**写的，不封；`data.*` 一族全在攻击路径上，**一律封**。你第五节会
亲手对照这个差别。源码里没有注释，判断标准就是这一条线：**攻击者能不能亲手写这个字段**。

**翻译的组装与收尾**。📄 [services/ingest/src/wazuh.ts:117-139](soc-demo/services/ingest/src/wazuh.ts#L117)：


### 站 5 · 出站转交档案室

📄 [services/ingest/src/m2client.ts:57-70](soc-demo/services/ingest/src/m2client.ts#L57) ·
前台递单给档案室的唯一通道：

```ts
async ingestAlert(input: AlertInput): Promise<IngestResult> {
  const res = await fetch(`${this.baseUrl}/api/v1/alerts`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(input),
  });
  const body = (await res.json().catch(() => null)) as
    | { alert?: { id?: string }; dedup?: boolean }
    | null;
  if ((res.status === 200 || res.status === 201) && body?.alert?.id) {
    return { alertId: body.alert.id, dedup: body.dedup === true };
  }
  throw new Error(`m2 ingest failed: HTTP ${res.status} ${JSON.stringify(body)}`);
}
```

三个看点：① `baseUrl` 来自站 0 那个 `CASE_BACKEND_URL` 环境变量
（[services/ingest/src/app.ts:11](soc-demo/services/ingest/src/app.ts#L11)，没配就回退
`127.0.0.1:3002`）；② 200/201 之外一律**抛错**——档案室要是回了 500，前台绝不会
假装收下了，错误往上冒，演示员终端上看得见；③ 这段代码写在 `HttpM2Client` 类里，
而前台路由只认 `M2Client` **接口**（[m2client.ts:47-50](soc-demo/services/ingest/src/m2client.ts#L47)）——
测试时换一个内存假档案室（`MemoryM2Client`），前台代码一行不改。这就是"接缝（seam）"：
换零件不拆机器。

### 站 6 · 档案室收档：查重，给回执

📄 [services/case-backend/src/app.ts:89-101](soc-demo/services/case-backend/src/app.ts#L89) ·


的出处。`ingestAlert()` 里面**怎么**做到"同一个身份证号只建一次档、计数加一、还顺手
发事件"——是下一步 1.2 的主菜，这里先记住接口：进单子，出 `alert + dedup`。

## 三、服务与中间件卡

**卡 1 · ▲Fastify —— 前台窗口的"柜台台面"**

- **替我们干了件什么体力活**：ingest 是个网站后台，总得有个框架负责"听端口、收
  HTTP 请求、解析 JSON、把请求分给对应的处理函数"这些杂活。Fastify 就是这个台面，
  我们只写"收到单子之后干什么"的业务部分（站 2 到站 4 的全部代码）。
- **自研还是开源**：开源（Node.js 的 Web 框架，v5）。九个服务里有三个
  （ingest / case-backend / agent）都架在它上面。
- **本项目怎么配置**：每个服务一个文件（如 [services/ingest/src/app.ts:10-14](soc-demo/services/ingest/src/app.ts#L10)
  的 `buildApp()`）里 `Fastify()` 建实例 → 注册路由 → 注册一个**错误盖写器**（站 3
  讲过）：框架对畸形 JSON 默认回 400，我们盖成 422——本仓库口径是"单子不合格"统一
  叫 422，前台不区别对待"字填错了"和"纸撕破了"。
- **市面上同类**：Express（最老牌、资料最多、但接口老）、NestJS（大而全、带一整套
  规范、学习成本高）、Koa（轻量、生态小）。
- **本项目为什么选 Fastify**：我们每个服务都是"几个接口的小后台"，要的是轻、快、
  对 TypeScript 友好、内置 JSON 处理——Fastify 恰好都占；NestJS 那套企业规范对
  九个微服务是杀鸡用牛刀。
- **业务上怎么选**：小团队、接口不多、追求性能 → Fastify；大团队、要统一架构和
  装饰器规范 → NestJS；接手老项目或团队只会 Express → 别为了新而新。

**卡 2 · ▲Wazuh —— 报案电话的真身（本项目里被"扮演"）**

- **替我们干了件什么体力活**：真实世界里的告警源头。它是开源的主机安全检测系统
  （OSSEC 的后裔）：在每台服务器上装探针，探针按几千条规则盯着日志，发现可疑就
  生成一条**固定格式的 JSON 报案单**发出来。我们收到的每份单子里的 `rule.id`、
  `rule.level`、`full_log` 都是它的格式（站 2/站 4 翻译的就是它）。
- **本项目怎么配置/为什么被扮演**：教学环境追求**确定性**——今天推 12 份单，明天
  还是这 12 份，学的东西才可复现。所以默认链路里 Wazuh 不出现，由
  `scripts/replay.ts`（演示员）直接递同样格式的单子。演示员有三条铁律
  （写在 [CONTEXT.md](soc-demo/CONTEXT.md) 的「回放」词条）：① 单子只从正门递，
  **绝不直接塞档案室**；② 推模式，跑一次推一遍，不搞自动轮询；③ 它不是服务，
  不进 docker-compose。想看真探头干活也有开关：
  `docker compose --profile real-wazuh up -d wazuh-manager` 会起官方 4.14.7 镜像，
  把同一批单子的正文喂进**真规则引擎**重新判，判出来的回包还是走正门进来——默认
  九个服务一个不动。
- **市面上同类**：Splunk（商业、贵、分析强）、Elastic Security（开源系、和 ES 栈
  绑定）、QRadar（IBM 商业）、Suricata（管网络流量这半边）。
- **业务上怎么选**：已经全面用 Wazuh 的公司 → 告警源就是它，零改造接我们的正门；
  用别家探头的 → 写个翻译层，把别家格式转成 Wazuh 方言再递正门（翻译规则集中在
  `wazuh.ts` 一个文件里，换源只动它）；只想学原理 → 像本项目一样用回放扮演。

## 四、防线对号

本步踩中三样安全设计：

- **INV-8（写操作必留台账）**：422 拒收也记审计（站 3 的拒收分支）。我亲手验过：
  递一份警情编号是 999 的坏单，档案室的审计簿里就多一条 `action=ingest /
  actor=m1:ingest / result=FAILURE / reasons=[timestamp_missing_or_invalid]`，且
  reasons 与退回给演示员的拒收理由**同源**（同一份摘要，不是两套说法）。有人想从
  正门乱塞东西，台账上一定留痕。
- **INV-6（重复报案只算一起）的预告**：我把 12 份单推了两遍，第二遍全部回
  `200 dedup:true`，且档案号和第一遍**完全相同**（如 web-31101 始终是
  `868076a7-04c9…`）。库里那份主角告警的 `occurrences` 字段已经是 2——查重的库内
  机制是下一步（1.2）的主菜，本步先见到它的外部样子（站 6 的三态回执）。
- **不可信封条（untrusted 标记）**：报案单里攻击者能够亲手写的字段，入库即封条
  （站 4 好事 b/c）。对照实测：主角告警的可观测物里，`hostname=web-01`（我们自己
  的探头名，攻击者写不了）**无**封条；而 SQLi 告警里的 `ip=198.51.100.7` 和
  `url=/products.php?id=1 UNION SELECT…`（攻击路径上的东西）**都盖了** `untrusted`
  封条。这层封条后面防的是"提示词注入"攻击（场景 5 上场）。

  数据——停栈后删掉 `data/` 下四个子目录再重起即可（见 1.2 的布景说明）。

## 六、捣乱实验

学完收案规则，递几张坏单试试前台拒不拒（这些都是往正门塞一次性请求，不改任何
文件，无需还原）：

```bash
# ① 报案单没有警情编号 → 应被拒收
curl -s -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:3001/api/v1/webhooks/alerts \
  -H 'content-type: application/json' -d '{"timestamp":"2026-09-10T10:00:00Z"}'
#   应看到 {"error":"invalid_alert","details":["[0] rule.id_missing"]} + HTTP 422

# ② 报警时间瞎写 → 应被拒收
curl -s -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:3001/api/v1/webhooks/alerts \
  -H 'content-type: application/json' \
  -d '{"rule":{"id":"999"},"timestamp":"yesterday-ish"}'
#   应看到 details:["[0] timestamp_missing_or_invalid"] + HTTP 422

# ③ 纸都撕破了（半截 JSON）→ 还是拒收，错误措辞统一也是 422
curl -s -w '\nHTTP %{http_code}\n' -X POST http://127.0.0.1:3001/api/v1/webhooks/alerts \
  -H 'content-type: application/json' -d '{"rule":{"id":12'
#   应看到 "Body is not valid JSON…" + HTTP 422

# ④ 拒收留台账了吗？——拿编号 999 去审计簿里查
curl -s 'http://127.0.0.1:3002/api/v1/audit?objectId=999' | python3 -m json.tool
#   应看到一条 result=FAILURE 的 ingest 审计，reasons 和 ② 的拒收理由一致
```

想得更深一步：前台为什么**只卡**警情编号和报警时间这两样，别的全放行？
（提示：想想"探头厂商明年加个新字段"和"每条字段都要审"这两个世界，哪个能
活下去。）——这正是站 2 讲的职责边界：收案窗口管"单子能不能收"，不管"单子
内容干不干净"；内容的水位治理是后面防线的事。
