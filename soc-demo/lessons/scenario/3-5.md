有意思的一点：`close_alert` 是 **L1 工具**（关单可撤销——告警能重开，FR-M2.1），所以它
配得上进任务票，不需要 ApprovalToken。但执行前有两道保险，全在子图的第一节点里：

📄 [services/agent/workers/triage/close.ts:80-90](soc-demo/services/agent/workers/triage/close.ts#L80)

```ts
        // 预检三连（具名错误 → failReason/error 事件 → web 人话）：
        // ① 分诊结论定了没有（verdict null/in-progress = 没分诊完，不猜）；
        // ② AI 建议是不是关单（确认按钮执行的是"建议"，不是自由关单权）；
        // ③ 是不是已经关了（重复确认/并发先到者——M2 状态机也会拦，这里给更早的人话）。
        if (!alert.verdict || !M2_FINAL_VERDICTS.has(alert.verdict)) {
          throw new Error(`close_verdict_missing:${alertId}`);
        }
        const advice = alert.verdictAi as { recommended_action?: unknown } | null;
        if (!advice || advice.recommended_action !== "close") {
          throw new Error(`close_advice_missing:${alertId}`);
        }
```

预检②尤其值得念三遍：**确认按钮执行的是"建议"，不是自由关单权**。没有 AI 建议、或建议
不是 close 的告警，谁按按钮都关不了（走人工流程去）。执行节点把整个关单动作包在闸内
（"无票不落地"：票面缺 close_alert 时连状态前置都不许发生），落地后一条 `close_confirm`
审计把**确认人**（x-actor-id 派生的 soc1）记进五要素——INV-8 的"记到人头上"在这里兑现。

本步实测收官对账：

```text

close_flow run_66e2b653：completed，steps=2（get_alert / close_alert）
审计：create(soc1) → close_confirm(soc1)   ← 人头在 agent 侧审计（M2 REST 写口照旧 system，
                                              与 3.1 备注同款信任分层）
```

**环，闭上了**：3.1 的一次关案沉淀 → 3.3 的一次人审入库 → 本步的一条同类告警秒级建议
关单。知识库不是文档库，是**会自己回来上班的决策依据**。

## 三、服务与中间件卡

### 卡 1（自研形态）· 建议-确认-执行三段式：AI 参与度的水位计

- **它是什么**：本系统对"AI 能替人做多少事"给出的答案是一个**三段水位计**——
  **建议**（AI 自由出，verdict_ai/recommendation，零授权）、**确认**（人对 AI 的建议盖
  章，close_flow 一键/审批卡批准）、**执行**（盖章后才发生，最小票/一次性 token）。
  同一个架构里有三种参与度并存：分诊 verdict 是"AI 判、落档可追溯"；关单是"AI 建议、
  人确认、最小票执行"；隔离主机是"AI 建议、审批卡+一次性 token 执行"（场景 4）。
- **市面对照**：SOC 工具链的通用演进（SOAR playbook 全自动 → 人机回路 human-in-the-loop
  → 纯人工），TheHive 的 case task 模式、Cortex responder 的 approve 门槛都是同一思想。
- **业务上怎么选**：按**动作的可逆性与爆炸半径**定水位——可逆且低危（写时间线、落
  verdict）给 AI 直做；可逆但涉及结论（关单）加确认；不可逆或高危（隔离、封 IP、写
  知识库）加审批+一次性授权。水位是按动作逐个定的，不是按系统一刀切。

### 卡 2（领域卡）· SOC 知识反馈闭环：从"文档库"到"会上班的知识"

- **它是什么**：本场景跑通的五步环：关案（有结论）→ 提炼（结构化草稿）→ 人审（质量闸）
  → 入库（可检索）→ 命中（下次同类告警提速）。对标 TheHive 生态的实践（M507 决策点的
  KB 优先、HolmesGPT 的知识沉淀提案），本系统的差异化在**防线上**：入库必经人审
  （D8/INV-5）、命中内容过注入安检（guards kb 通道）、检索面写入路径唯一（结构保证
  而非约定）。
- **为什么值得做**：SOC 的痛点不是"没知识"是"知识不在决策路径上"——wiki 里躺着的
  演练登记不会自己跑到分诊台前。反馈闭环把"沉淀"变成流程的副产品（关案自动提炼），
  把"使用"变成分诊的第一步（KB 优先）。
- **业务上怎么起步**：先关死"无结论不关案"（ASP 关案闸），知识自然随关案生长；三类
  条目起步够用（fp_pattern/runbook/env_fact）；质量靠人审不靠 LLM 自觉。

## 四、防线对号

| 防线 | 在本步的落点 |
|---|---|
| **建议 ≠ 执行** | R1 只产出 `recommended_action: "close"`；关单要 close_flow + 预检三连 + 人按按钮（捣乱 B 实测拦下越权关单） |
| **预检三连** | verdict 未定不猜（①）/ 无建议不给关（②）/ 已关不重复（③）——具名错误直达 web 人话 |
| **INV-3** | close_flow 最小票 `[get_alert, close_alert]`，close_alert 是 L1（可撤销）；scope 只有 alert:update |
| **INV-8** | `close_confirm` 审计记 soc1 人头（谁按的按钮）+ SSE 时间线镜像 |
| **KB 优先的顺序** | R1 先于 R2：先内部事实后外部威胁——顺序本身就是防线（自家资产不被当靶子） |
| **溯源链** | 告警 rationale ← KB title ← 人审记录（3.3）← 案件 verdict_note ← 演练登记 DX-2026-09——AI 的每句话可回溯到人 |

用 8 位短 id 关"不存在的告警"，得到的是同一个节点的 `alert_not_found` 强杀——预检连
对象存在性都在闸前查。）

**B · 纸面推演：把告警换成 web-01 的同类报文再推**？R1 会命中吗？——不会：kb_check 的
查询词面是 "web-01"（+路径/用户），跟那条 centos7 环境事实**零共享词面**，3.4 的 S1
已经证明这种查询相似度趋近 0；然后 R2 接管（web 告警的 url 特征命中攻击证据）→ tp →
并案或建案。**知识命中是有边界的：主机不对口，知识不出手**——这个边界恰好挡住了
"一条 env_fact 惠及全宇宙"的误关单灾难（也再次说明 3.4 站 6 的 P3 为什么要补"主体一致性
校验"）。

**C · 纸面推演：假如 3.3 那天值班长驳回了呢？** 账面 rejected、检索面零写入——本步
推新告警时 kb_check 查无命中，R1 不触发，R2 攻击证据接管 → tp → 又建一个案。同一个
世界，两种世界观都自洽：**批准的知识会回来上班，驳回的知识从没存在过**（分诊的世界里
它连"被拒绝"都不曾发生——检索面查无，不是"查到了但标了拒绝"）。

## 场景 3 闯关（三题）

<div>

**题 1 · 重放的游标**：某天 agent 容器重启，autorun 的游标意外回退，case_000004 的
`case.closed` 事件（16 号小票）被**重新消费了两次**（同一轮里 dup、下一轮又来一次）。
知识沉淀会被拉起几次？分别被哪道防重拦住？如果这两次是有人手动 `POST /internal/runs`
直拉的呢？

<details><summary>答案</summary>

**自动路径：0 次拉起。** 三道防重接力：① 同一批里的重复 → `dup_batch`（batchSeen 查重）；
② 下一轮的重复 → `run_exists`（agent runs 表里已有非 failed 的 knowledge_flow run）；
③ 就算 run 记录丢了 → `kb_exists`（M2 账面里 case_000004 已有 proposed/approved 提案）。
三次消费全部"跳过但推游标"——想清楚了不动作。**手动路径：两次都会真跑**——
`/internal/runs` 正门不做防重（防重住在 autorun 层），两次直拉会产出**两条重复提案、
两张审批卡**。这就是 3.1 捣乱 E / 3.2 捣乱 D 反复敲的黑板：自动化的纪律在事件桥，
人工的责任在按下回车前。

</details>

**题 2 · 幽灵的病根**：3.2 的幽灵条目（直连 M2 REST approve，账面 approved）永远进不了
chroma。请按顺序说出**正门批准**从"按按钮"到"chroma count+1"之间的全部检查点，并指出
幽灵跳过了其中哪些。

<details><summary>答案</summary>

正门链条（3.3 六站）：① 审批端点廉价预检（卡必须 pending）→ ② gateway 铸 ApprovalToken
（HMAC 三段，烧入 tool+**params_hash**+caseId+approvedBy+TTL）→ ③ 决定落卡（审批状态机
仲裁，后到者 409）→ ④ resume 入队、重组 worker 图（重铸 L1 任务票）→ ⑤ 节点重跑，
awaitApproval 查到已决卡 → ⑥ **验票闸**：签名验签 / TTL / params_hash 对指纹 / 跨进程
焚毁真相查询 → ⑦ 执行体（M2 approve 账面 + **chroma upsert**）→ ⑧ 焚毁登记 + 执行标记。
幽灵从 ③ 直接跳到了"M2 账面翻状态"——②④⑤⑥⑦⑧全没有。而 chroma 的 upsert 只住在
⑦ 那个已验签执行体里（INV-5 的结构保证），所以账面翻得再欢，检索面纹丝不动。
一句话：**它拿到了"批准的结果"，没走"批准的路"**。

</details>

**题 3 · uncertain 的案子**：SOC1 复核一个案子后仍拿不准，决定关案并给
`verdict=uncertain`（四个合法枚举之一，关案口放行、事件照发、沉淀 run 照拉）。沉淀子图
会产出什么？每一步（LLM、schema 把关、账面）各是什么结局？为什么系统要这样设计？

<details><summary>答案</summary>

**产出：一条 skip 审计，仅此而已。** knowledge_distill 读到 verdict=uncertain 后，
FakeKnowledgeLlm 的 ASP 门控规则返回 `{skip:true, reason:"verdict=uncertain：无可沉淀的
确证结论"}`（[llm.ts:33-35](soc-demo/services/agent/workers/triage/llm.ts#L33)）；parseDraft
把 skip 视为合法输出（schema 三分支之二）；flow 落一条 `knowledge_skip`（SUCCESS）审计、
run 正常 completed、kb_propose 不发生、账面零新增、检索面零写入。设计意图正是 ASP 门控的
灵魂：**知识条目的每句话都会成为未来分诊的依据（R1 命中即建议关单），没有确证结论的
"知识"等于往决策路径里塞猜测**——宁可不错提，不可编造。对照：alert 层的 uncertain 会置
InProgress 挂人工（outcome 三结局之三），case 层的 uncertain 允许关案（案件状态机只认
流程不认信心）——但"拿不准"的东西在哪个层面都**进不了知识库**。

</details>
