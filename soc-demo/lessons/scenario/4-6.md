# 场景 4 · 步 4.6 —— 焚毁与一次性：这枚票的后事

> 4.5 的闸口放行了，mock_edr 报了 isolated——但"一次性"三个字还没兑现。票执行完不是
> 尾声而是第二幕：**焚毁登记**（M2 used_tokens 表）、**执行盖章**（审批卡 executed_at）、
> **审计定案**（create→approve→execute 三连）。本步看这枚票的后事怎么办，以及为什么
> "一次性"要在**三个地方**同时设防——票面的声明、跨进程的账本、卡上的执行章，各管一
> 摊，缺一不可。
> 术语卡词翻 `TERMS.md`（同一比喻体系：焚毁坟场/一次性密令/审批卡…），老术语只回指
> 不另起解释。

## 二、调用链

先看全景。闸放行之后的收尾四拍，顺序是铁律：

```
验票闸 allow（4.5 站 4）
  ▼
[拍1] 执行：action(params) —— mock_edrisolated, host:app-01
  ▼
[拍2] 焚毁登记：deps.burn.burn(jti, "approval")
        → HttpTokenBurner POST M2 /internal/used-tokens（fire-and-forget）
        → M2 侧 registerUsedToken：INSERT used_tokens + recordAudit 同一个事务
        → 重复登记 UNIQUE 冲突 → JtiExistsError 409（幂等护栏，本步实测）
  ▼
[拍3] 执行盖章：markApprovalExecuted —— UPDATE approvals SET executed_at
        → 审计 execute 行（actor=m3:supervisor，记操作不记内容）
  ▼
[拍4] 事件收口：emitEvent tool_result（带 approval_id 与 result）
  ▼
node_exit → run completed —— 票的一生终结于三个库的四行记录
```

### 站 1 · 收尾四拍与顺序铁律

📍 大图节点:EXEC_ACT（4.6 焚毁与一次性）

3.3 站 5 引过闸体的核心段，本步把镜头对准它后面的四行——顺序本身就是设计：

📄 [services/agent/src/graph.ts:322-333](soc-demo/services/agent/src/graph.ts#L322)

```ts
      const result = await gatedApproval(nctx, tool, params as Record<string, unknown>, async () =>
        (await action(params)) as Record<string, unknown>);
      deps.burn?.burn(jti, "approval"); // INV-2：用后即焚（生产 = M2 used_tokens）
      markApprovalExecuted(db, decision.approvalId, jti, deps.ctx);

```

**先过闸（4.5），后执行，再焚毁，最后标记**——顺序倒了会发生什么，逐个想：

- 先焚毁后执行？执行一失败，票已经烧了——值班长得重批一轮，"误伤授权"。
- 先标记后焚毁？标记说"已执行"、账本说"没烧过"——两个真相互相打脸，对账永远对不平。
- 焚毁和标记之间没有先后？有：焚毁在前（跨进程的真相先落账），标记在后（进程内的
  卡随后的盖章）——中间崩溃的窗口下面站 3 细说，兜底安排是有意的。

四拍里的跨进程边界也交代清楚：拍 1 执行是进程内的函数调用（枪响就在 agent 进程里）；
拍 2 焚毁是**跨容器出站**——agent → `POST :3002/internal/used-tokens`（M2 落账），
而且是发完即走、不等回包；拍 3 盖章又回到进程内（agent 自己的库）。所以"焚毁完成"
的真相到达 M2 有一个网络延迟窗口，兜底链站 3 讲。

### 站 2 · 执行章：记操作不记内容

📍 大图节点:MARK（4.6 焚毁与一次性）

📄 [services/agent/src/approvals.ts:198-208](soc-demo/services/agent/src/approvals.ts#L198)

```ts
/** 执行标记：闸放行 + 动作跑完后打。执行过的卡不再授权第二次执行（一次性）。 */
export function markApprovalExecuted(db: DB, id: string, jti: string, ctx: RunCtx): void {
  const card = requireApproval(db, id);
  db.prepare("UPDATE approvals SET executed_at = ? WHERE id = ?").run(nowMs(), id);
  ctx.audit.record({
    action: "execute",
    actor: ctx.actor ?? { type: "agent", id: "m3:supervisor" },
    objectId: id,
    objectType: "approval",
    // 记操作不记内容（FR-S5.2）：工具名 + 参数指纹 + 票 jti，不落参数原文与执行输出
    details: { tool: card.tool, params_hash: card.paramsHash, jti },
```

两个看点：① **executed_at 是一次性的第二道防线**——票面 `used:false` 只是声明，
焚毁账本是跨进程真相，而卡上的执行章是"这张卡已经消费过"的进程内权威。三处合起来，
"同一个 (run, tool_call) 只执行一次"才有三重保险。② 审计 details 的取舍写着
**FR-S5.2：记操作不记内容**——工具名、参数指纹、票 jti 够定位一次执行了；参数原文
和执行输出不进审批审计（那是工具自己的 tool_result 事件的职责，事件 950 里你见过
`mock_edr:isolated`）——审计要能定案，但不当数据的第二次存储。

### 站 3 · 焚毁写口：fire-and-forget 的取舍

📍 大图节点:BURN（4.6 焚毁与一次性）

📄 [services/agent/src/token-ports.ts:143-151](soc-demo/services/agent/src/token-ports.ts#L143)

```ts
  burn(jti: string, source = "approval"): void {
    void fetch(`${this.baseUrl}/internal/used-tokens`, {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ jti, source }),
    }).catch((e: unknown) => {
      console.error(JSON.stringify({ warn: "used_tokens_register_failed", jti, error: String(e) }));
    });
  }
```

写口是**发完即走**（fire-and-forget）：POST 发出去、失败只打日志、绝不阻塞执行器。
为什么敢这么松？对比 4.5 的读口（同步、2 秒超时、失败闸必须病）——**写与读的安全
等级刻意不对称**：读口失败=闸在不知情时可能放行重放 → fail-closed；写口失败=重放
防线暂时缺一环 → 但有兜底（token-ports.ts:7-9 头注释原话："同进程即时重放的缺口
另有卡的 executed_at 单次执行标记兜底"，外加重放窗被 TTL 300 秒封顶）。兜底链完整
列一遍：执行章（进程内）→ TTL 自焚（时间）→ 焚毁账本（跨进程，写补上之后立即恢复
权威）。3.3 站 6 讲过"执行后、标记落库前崩溃"的窗口，这里把兜底链补全了。

### 站 4 · M2 侧落账：焚毁与审计同一个事务

📍 大图节点:USED_WR（case-backend 容器）

📄 [services/case-backend/src/store.ts:917-929](soc-demo/services/case-backend/src/store.ts#L917)

```ts
  return db.transaction(() => {
    const burnedAt = nowMs();
    try {
      db.prepare("INSERT INTO used_tokens (jti, source, burned_at) VALUES (?, ?, ?)").run(
        body.jti, body.source ?? null, burnedAt,

    } catch (e) {

      throw e;

```

两个看点：① **焚毁与它的审计在同一个事务里**（票 03 口径"审计同库同事务"）——
"烧过"和"记得烧过"是同一笔写，不存在"账本有了、台账没记"的中间态（INV-8 的

第二条 INSERT 撞唯一约束 → JtiExistsError（httpStatus 409，store.ts:47-49）。本步实测：

```bash

  -H 'content-type: application/json' \
  -d '{"jti":"ap_4a9d6e0d-63a9-4b7c-9460-273b6ca6c7f8","source":"approval"}'
# 预期：{"error":"jti_exists"} | HTTP 409   ← 重放防线在账本层的兜底：就算闸全瞎了，
#                                            同一枚票想在坟场里躺两次也躺不进去
```

焚毁落账还顺手给 M2 审计簿添了一行 `execute`（object_type=used_token，details 记
source）——本步开头查到的 jti 审计行就是它。

### 站 5 · 一次性的结构面：执行过的卡连"查卡"都不配

📍 大图节点:FIND_CARD（4.6 焚毁与一次性）

一次性不只靠账本，还写在**找卡的查询条件**里：

📄 [services/agent/src/approvals.ts:107-124](soc-demo/services/agent/src/approvals.ts#L107)

```ts
/** 找该 (run, tool_call) 最新一张「还能生效」的卡。已执行过的卡排除——同一 run 里
 *  再次提请同样的 tool_call 要开新卡走新审批（一次性语义的结构面）。 */
export function findDecidableCard(
  db: DB,
  runId: string,
  tool: string,
  hash: string,
): ApprovalRow | null {
  return mapApproval(
    db
      .prepare(
        `SELECT * FROM approvals
          WHERE run_id = ? AND tool = ? AND params_hash = ? AND executed_at IS NULL
          ORDER BY created_at DESC, rowid DESC LIMIT 1`,
      )
      .get(runId, tool, hash) as Record<string, unknown>,
  );
}
```

`executed_at IS NULL` 这半句是灵魂：执行过的卡在 awaitApproval 眼里**不存在**——同一
run 里再次提请同样的动作（哪怕参数一模一样），只能开新卡、走新一轮人审。"批准一次，
永久生效"这个诱人的优化，在查询条件这一层就被焊死了。

三处对账的实战价值在断链教具上现形：`ap_d00d9edd`（4.3 那张永远无法执行的卡的票）
不在坟场里——**账本说没烧过 = 执行确实没发生**。反过来主角票三处齐全：账本有行
（used_tokens）、卡上有章（executed_at）、审计有案（execute 三连）。**一次性不是
一个开关，是一份能互相对账的证据链**。

## 三、服务与中间件卡

### 卡 1（领域）· 焚毁三件套：一个"一次性"三个真相互相咬合

- **它是什么**：票面声明（`used:false`）、焚毁账本（M2 used_tokens）、执行章
  （approvals.executed_at）。三个位各有人查：票面声明给"肉眼审票"的人看；账本给
  验票闸的跨进程读口查（4.5）；执行章给审批回路和找卡查询用（本站 5）。
- **为什么要三个**：它们有不同的失效模式——票面声明会被伪造（所以"不算数，账本
  说话"）；账本写入是异步的、有崩溃窗口（所以要执行章+TTL 兜底）；执行章在 agent
  库里、跨进程查不到（所以跨进程场景必须问账本）。**没有单点真相，只有互相咬合的
  证据链**——这跟分布式系统"没有单一事实来源时用对账"是同一门手艺，只是这里对账
  的是安全语义。
- **市面上同类**：JWT 的 revocation list（黑名单模式 = used_tokens 的近亲）；OAuth
  的 token introspection 端点（读口的标准化形态）；数据库的幂等键（UNIQUE + 409）。
- **业务上怎么选**：授权消费后必须不可再用 → 账本+约束是底线；要求"执行必须可追溯
  到人" → 审计与账本同事务；允许"偶尔重复执行也无害"的动作 → 可以只靠 TTL，别为
  它养一套焚毁设施——机制的重量跟动作的代价成正比。

### 卡 2（自研）· 写读不对称：同一个真相的两个口，两种脾气

- **它是什么**：焚毁真相的写口（HttpTokenBurner，fire-and-forget，失败只打日志）和
  读口（HttpUsedTokenReader，同步必答，失败闸必须病）。同一个 M2 端点家族，两种
  容错策略。
- **为什么不对称**：读失败在**安全路径**上（闸拿不到真相就做裁决）→ 必须显式失败，
  宁可拒好票；写失败在**事后登记**路径上（动作已经做完了，登记晚一点/重试一下都行）
  → 阻塞执行器毫无收益，还有崩溃窗口恶化的风险。判据一句话：**这个失败发生在裁决
  之前还是之后**。
- **本项目怎么配置**：写口在 graph.ts 的执行流里 `deps.burn?.burn(jti, "approval")`
  一行；读口在进闸前的 `resolveUsed` 装填——同一个 token-ports.ts 里两件挨着放，
  不对称设计一眼可读。
- **市面上同类**：事务性发件箱（transactional outbox，写口可靠化的标准解——
  token-ports.ts:134-135 注释也点名了这个演进路线："换本地镜像表 + outbox 补偿的
  adapter，调用方零改动"）；CQRS 的读写分离（读写诉求不同则容错策略不同）。
- **业务上怎么选**：登记缺失的后果能用其他兜底盖住（TTL/执行章）→ fire-and-forget
  够用；登记缺失不可接受（监管口径的"操作即留痕"）→ 上 outbox，别裸奔。读口永远
  fail-closed——这一侧没有讨价还价。


对照主角票（count=1）：**在不在坟场 = 执行有没有发生**。这张票同时已经过了 300 秒
TTL（4.3 铸出后从未被使用）——"铸了没花的票"的两个终局（被账本遗忘 + 被时间作废）
它一个都没躲过，4.7 就讲时间这一半。

**C · 崩溃窗口推演（焚毁与盖章之间）**：假设拍 2（焚毁）成功、拍 3（盖章）前进程
崩溃——账本说烧过、卡上没章。resume 重入会怎样？awaitApproval 用 findDecidableCard
查卡：这张卡 executed_at 为 NULL（章没打上），查到的是 approved+token 的旧卡——节点
再次拿同一枚票进闸，读口说已焚（token_used 403）强杀。**不会重放**，但 run 会 failed，
动作其实已经做过了——状态略尴尬但没有安全后果。这正是 3.3 站 6"执行体对 M2 409 幂等
放行"要解的同类问题在 isolate_host 侧的样子（kb_write 有 chroma upsert 幂等可重入，
mock_edr 没有幂等重入的必要——所以强杀就是正确答案）。窗口被 TTL 300 秒封顶，4.7
见。

**D · 纸面推演**：如果焚毁在执行**前**（先烧票再干活）——闸放行后立刻烧，然后执行
崩溃：票没了、活没干成、审批卡上也没有失败记录。值班长重批一轮（授权误伤），审计里
还得解释"烧过的票没干过活"。现在的顺序（执行→焚毁→盖章）把最贵的错误留给最少见的
场景，把可恢复的状态留给常见路径——**顺序设计就是状态机设计**。
