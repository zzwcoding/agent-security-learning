# 场景 2 · 步 2.4 —— 富化：TLP/PAP 确定性闸门、analyzer fixture 表、artifacts 去重回写

> 链上第二格 `enrich_case`。如果说调查 worker 是「带着 LLM 的侦探」，富化 worker 就是
> 一台**流水线检测仪**：把案件里的可疑指标（IOC）逐个送去外部情报库验「毒」，查完
> 把新发现回写案卷。整台机器**没有一个 LLM 决策点**——查什么、按什么顺序、什么不外发
> 全在代码里。本步三个主角：**TLP/PAP 闸门**（数据密级高于仪器的，一个字节都不许出
> 门）、**analyzer fixture 表**（情报库在 demo 里就是个目录）、**artifacts 去重回写**
> （查出来的新线索并回案卷，不重复登记）。本步的布景证据极其漂亮：同一个 hash 在
> 报告里出现两次，一次放行一次拒发——密级闸门的活教材。
>
> 术语卡：比喻照旧沿用 [TERMS.md](TERMS.md)（手令/闸体/案卷……），首遇只回指；
> 每站开头的 📍 行对应 [2-big-picture.html](2-big-picture.html) 同名节点。

---

## 一、操作（位置感）

先对齐两个名词。**TLP**（Traffic Light Protocol，红绿灯协议）：情报的**敏感度**，
0-4 = CLEAR/GREEN/AMBER/AMBER+STRICT/RED，TLP:RED=只许案卷内知悉；**PAP**（Permissible
Actions Protocol，行动许可协议）：这份情报**允许被拿去做什么**（比如能不能交给外部
伙伴），0-3。两者都挂在 observable 上（场景 1 里建案时随告警带来的）。

**analyzer**：外部信誉查询仪。Cortex（开源 SOC 自动化平台的 analyzer 组件）契约子集
的两个：`vt_lookup`（VirusTotal 风格的 hash/domain/fqdn 查询）和 `ip_reputation`
（IP 信誉）。demo 里它们是 **fixture 情报表**——`fixtures/ti/` 目录下按 observable
的值命名的 JSON 文件，命中读文件、未命中「no-record」，零网络。

操作上看一遍现状就够了（不必新拉）：

1. 看 TI 情报表里有哪些「案底」：`ls fixtures/ti/` → 两个文件，恶意文件 hash 和
   一个 IP。
2. 打开 web（http://localhost:5173）案件页 case_000003：时间线里 2.1 直拉留下的
   富化报告——**同一个 hash 两行**：tlp=4 的标 `[refused]`（拒发），tlp=2 的标
   `[malicious]`（查了，VT 评级 5/70）。这就是本步的全部剧情，下面逐站拆。

## 二、调用链

```
enrich_case（外壳交接节点，2.1 站 4）
  ▼
[站1] load_case —— 读案件全部 observables（含每条的 tlp/pap）
  ▼
[站2] enrich —— 逐条 observable 过五步流水线：
      ① 类型映射：hash/domain/fqdn/ip 才查，其余内部实体跳过（对账栏交代）
      ② 签名契约 validateToolCall（tlp/pap 是不是界内整数）
      ③ 亮票过闸 gated（vt_lookup/ip_reputation 是票面工具）
      ④ TLP/PAP 确定性闸门：tlp>2 或 pap>2 → DENIED 审计 + 拒发（不外发不抛不杀）
      ⑤ analyzer 查询（fixture 表）→ guards 扫描输出 → artifacts 回写（L1 add_observable）
  ▼
[站3] write_report —— 对账式报告进时间线（body + structured 双形态）
```

### 站 3 · 分析包装层：签名、亮票、密级闸，全在 backend 之前

📍 大图节点:ENR_ANALYZE(2.4 富化)

📄 [services/agent/workers/enrichment/flow.ts:108-129](soc-demo/services/agent/workers/enrichment/flow.ts#L108)

```ts
  /** analyzer 工具的执行包装层：签名契约 → 验票闸（gated）→ TLP/PAP 确定性闸门 →
   *  才轮到 backend。闸拒在包装层就地解决：DENIED 审计 + refused 结论，不外发、
   *  不抛不杀（拒绝是数据敏感度语义，不是授权链缺口——授权链缺口才强杀）。 */
  async function analyze(ctx: NodeCtx, call: AnalyzerCall, analyzer: AnalyzerName): Promise<AnalyzerOutcome> {
    const sig = validateToolCall(analyzer, { ...call });
    if (!sig.ok) return { kind: "refused", errorMessage: `signature:${sig.error}` };
    const payload = await gated(ctx, analyzer, { ...call }, async (): Promise<AnalyzerOutcome> => {
      const gate = tlpPapGate(call, ANALYZERS[analyzer]); // 确定性中间件：同入同出，不靠 prompt
      if (!gate.ok) {
        record({
          action: "tlp_pap_denied",
          objectId: deps.caseId,
          objectType: "analyzer_call",
          details: { analyzer, ...call, error: gate.errorMessage },
          result: "DENIED",
        });
        return { kind: "refused", errorMessage: gate.errorMessage };
      }
      return { kind: "result", payload: await deps.analyzers.lookup(analyzer, call) };
    });
    return payload;
  }
```

四个层次各司其职，谁也不抢谁的活：

1. **签名契约**（tools.ts）：tlp/pap 是不是**界内整数**（TLP 0-4、PAP 0-3，
   [tools.ts:61-64](soc-demo/services/agent/workers/enrichment/tools.ts#L61)）、dataType
   是否该 analyzer 收的类型。注意分层注释的提醒（[tools.ts:8-12](soc-demo/services/agent/workers/enrichment/tools.ts#L8)）：
   `tlp=4` 的调用**签名是合法的**——拒它是闸门的活。签名管「格式对不对」，闸门管
   「语义放不放」。
2. **亮票过闸**（gated）：vt_lookup/ip_reputation 都在 case_flow 票面（2.1 站 2 的
   工具并集里），验票同样查 run 绑定与 allowed_tools。
3. **TLP/PAP 闸门**（下一站细看）——注意它**在 gated 的回调里**、backend 之前：
   闸拒的调用一个字节都到不了 fixture 表/真 analyzer。
4. **拒发 ≠ 强杀**：注释说得极准——「拒绝是数据敏感度语义，不是授权链缺口」。
   TLP 超限返回 `refused`（带逐字拒因），run 照常跑完出报告；对比 2.2 站 5：
   闸拒（`_gate_denied`）才枪毙整条 run。**意外绕得过，越权必须停；而「数据太敏感
   不该出门」既不是意外也不是越权，是业务结论，记下来继续干活。**

**为什么密级闸必须卡在「富化门口」（gated 回调内、backend 之前）？做反了会怎样**——
外发查询的语义是「查 = 已经出了门」：假如把闸放在 analyzer **之后**（先查回来，再决定
要不要用结果），fixture 表固然无事，但换真件（Cortex/VT）那天，查询本身就已经把自家
IOC（在查什么、什么时候查、谁在查）告诉了外部服务商——泄密在查询发出那一毫秒就既遂，
事后把结果扔掉毫无意义。闸放在门口，才能保证「超限的调用一个字节都没出门」是物理事实
而不是处理决定。

### 站 4 · 闸门本体：一个纯函数

📍 大图节点:TLP_GATE(2.4 富化)

📄 [services/agent/workers/enrichment/analyzers.ts:68-78](soc-demo/services/agent/workers/enrichment/analyzers.ts#L68)

```ts
/** TLP/PAP 闸门本体（m6 卡 Seam ②，FR-M6.2）。先 tlp 后 pap（先撞先报）；边界不冤枉：
 *  等于 max 放行，只有「大于」才拒。errorMessage 是契约——审计与富化报告逐字引用。 */
export function tlpPapGate(call: AnalyzerCall, analyzer: AnalyzerDescriptor): GateVerdict {
  if (call.tlp > analyzer.max_tlp) {
    return { ok: false, errorMessage: `tlp_exceeded: observable tlp=${call.tlp} > max_tlp=${analyzer.max_tlp}` };
  }
  if (call.pap > analyzer.max_pap) {
    return { ok: false, errorMessage: `pap_exceeded: observable pap=${call.pap} > max_pap=${analyzer.max_pap}` };
  }
  return { ok: true };
}
```

三行逻辑，三个讲究：**先 tlp 后 pap**（一条调用两个都超时，报先撞到的）；**边界
不冤枉**（`>` 才拒，`=` 放行——analyzer 挂牌 max_tlp=2 就是「2 及以下我都配处理」）；
**拒因是契约**（`tlp_exceeded: observable tlp=4 > max_tlp=2` 这串字会逐字出现在
审计和报告里，测试按它断言）。analyzer 的门槛在描述符里（[analyzers.ts:41-44](soc-demo/services/agent/workers/enrichment/analyzers.ts#L41)），
两个 analyzer 都是 max_tlp=2/max_pap=2——**「TLP:RED 不外发」就压在这三行纯函数上，
不在任何 prompt 里**。纯函数 = 同入同出 = 可单测、可复算、可审计。

**布景里的活证据**：case_000003 的 hash observable 有两行（同值不同源：一行来自
告警的 TLP:AMBER 源 tlp=2，一行来自 TLP:RED 源 tlp=4）。2.1 直拉后的富化报告：

```
- [refused] `vt_lookup` hash `c05640e2…`（tlp=4/pap=2） → 未外发：tlp_exceeded: observable tlp=4 > max_tlp=2
- [malicious] `vt_lookup` hash `c05640e2…`（tlp=2/pap=2） → VT:reputation=5/70
```

**同一个值，密级低的行查了、密级高的行被拒**——闸门吃的是「这一行 observable 的
tlp」，不是「这个 IOC 查没查过」。M2 审计里留下对应的 DENIED 台账：

```
action=tlp_pap_denied | result=DENIED | {"analyzer":"vt_lookup","data":"c05640e2…",
  "dataType":"hash","tlp":4,"pap":2,"error":"tlp_exceeded: observable tlp=4 > max_tlp=2"}
```

### 站 5 · analyzer 后端：情报库就是一个目录

📍 大图节点:TI_FIX(2.4 富化)

📄 [services/agent/workers/enrichment/analyzers.ts:93-117](soc-demo/services/agent/workers/enrichment/analyzers.ts#L93)

```ts
/** fixture 表 mock analyzer（m6 卡 Adapter，FR-M6.1「结果由内置情报 fixture 表驱动」）。
 *  表文件按 observable 的 data 值命名：fixtures/ti/<sha1|ip|domain>.json——情报库就是
 *  一个目录，命中读文件、未命中 no-record，没有任何网络。 */
export class FixtureAnalyzerTable implements AnalyzerBackend {
  private readonly dir: string;

  constructor(dir: string) {
    this.dir = dir;
  }

  async lookup(_analyzer: AnalyzerName, call: AnalyzerCall): Promise<AnalyzerResult> {
    let raw: { taxonomies?: AnalyzerTaxonomy[]; full?: unknown; artifacts?: { dataType: string; data: string }[] };
    try {
      raw = JSON.parse(await readFile(join(this.dir, `${call.data}.json`), "utf8"));
    } catch {
      return { ...NO_RECORD, summary: { taxonomies: NO_RECORD.summary.taxonomies.map((t) => ({ ...t })) } };
    }
    return {
      success: true,
      summary: { taxonomies: (raw.taxonomies ?? []).map((t) => ({ ...t })) },
      full: raw.full,
      artifacts: (raw.artifacts ?? []).map((a) => ({ ...a })),
    };
  }
}
```

  主角。
- **IP 198.51.100.23**：评级 suspicious，但 `full` 里埋着一句话——

- 未命中返回 **no-record**（[analyzers.ts:86-91](soc-demo/services/agent/workers/enrichment/analyzers.ts#L86)）：

### 站 6 · artifacts 回写：查出来的新线索并回案卷

📍 大图节点:ENR_WRITE(2.4 富化)

analyzer 的产出里除了评级还有**新 observable**（比如从 VT 报告里抠出的关联文件名）。
回写走 L1 工具 `add_observable`，同样亮票（[flow.ts:204-211](soc-demo/services/agent/workers/enrichment/flow.ts#L204)）：

```ts
          // FR-M6.3：analyzer 提取的 artifacts 经 L1 add_observable 回写案件
          for (const a of payload.artifacts ?? []) {
            const params = { case_id: deps.caseId, dataType: a.dataType, data: a.data, tags: [`from:${analyzer}`] };
```

每条回写自动带溯源标签 `from:vt_lookup`——半年后翻案卷，这条线索是谁查出来的
一清二楚。去重的真相源在 M2 侧：

📄 [services/case-backend/src/store.ts:670-692](soc-demo/services/case-backend/src/store.ts#L670)

```ts
export function addCaseObservable(
  db: DB,
  caseId: string,
  input: ObservableInput,
  ctx: Ctx,
): AddCaseObservableResult {
  return db.transaction(() => {
    requireCase(db, caseId);
    const existing = db
      .prepare("SELECT * FROM observables WHERE case_id = ? AND data_type = ? AND data = ?")
      .get(caseId, input.dataType, input.data) as Record<string, unknown> | undefined;
    if (existing) {
      const oldTags = pj<string[]>(existing.tags as string, []);
      const merged = [...oldTags, ...(input.tags ?? []).filter((t) => !oldTags.includes(t))];
      const newMessage = existing.message ?? input.message ?? null;
      db.prepare("UPDATE observables SET tags = ?, message = COALESCE(message, ?) WHERE id = ?").run(
        j(merged), input.message ?? null, existing.id as string,
      );
      recordAudit(db, ctx, "update", existing.id as string, "observable", {
        tags: { from: oldTags, to: merged },
        message: { from: existing.message ?? null, to: newMessage },
        dedup: true,
      });
```

按 `(case_id, data_type, data)` 找已有行：有 → **不建新行，只并 tags**（同样的标签
不重复），audit 记 update + `dedup:true`，HTTP 200；没有 → 新建，201。这正是 1.2
告警 upsert 的富化版：**同一个「报档案只登记一次，重复出现只加批注」的哲学**。

**布景活证据（两连拍）**：2.1 直拉 case_000003，hash 命中 malicious，回写 artifact
`invoice_apr.zip`——案件里原本只有 `/tmp/invoice_apr.zip`（带路径前缀），按整串比对
不算重复 → 报告写 `dedup: 否，新建`；本步准备时再拉一次同案 → 这次报告写
**`dedup: 是，并 tags 未建新行`**。同一份报告的对账栏还有个细节彩蛋：内部实体跳过
从 11 变 12——第一次回写的新行自己成了下一个「内部实体」，流水线吃自己的产出，
账目分毫不乱。

### 站 7 · write_report：对账式报告

📍 大图节点:ENR_REPORT(2.4 富化)

📄 [services/agent/workers/enrichment/flow.ts:257-271](soc-demo/services/agent/workers/enrichment/flow.ts#L257)

```ts
/** summary 一句话对账：几项查了、评级分布、几项 no-record、几项被拒、几项内部跳过。
 *  评级名与 no-record 字样进 summary（机读面 eval 直接 grep 这两个字段）。 */
function buildSummary(en: EnrichmentState): string {
  const byLevel = { malicious: 0, suspicious: 0, safe: 0, info: 0 };
  let noRecord = 0;
  for (const i of en.items) {
    if (i.ok && i.level) byLevel[i.level] += 1;
    if (i.taxonomies?.some((t) => t.predicate === "no-record")) noRecord += 1;
  }
  const noRecordPart = noRecord > 0 ? `（其中 no-record ${noRecord} 项）` : "";
  return (
    `查了 ${en.items.length} 个 observable：malicious ${byLevel.malicious}、suspicious ${byLevel.suspicious}、` +
    `safe ${byLevel.safe}、info ${byLevel.info}${noRecordPart}；TLP/PAP 拒绝 ${en.refused_count} 项；内部实体跳过 ${en.skipped_internal} 项。`
  );
}
```

富化报告是**对账单**不是作文：查了几项、各档几条、拒了几项、跳过几项——四栏数字
加起来必须等于案件 observable 总数（case_000003 的报告：查了 5 + 拒绝 1 已含在
5 内 + 跳过 11 = 17 行 observable，分毫不差）。渲染标记 `[malicious]/[refused]`
是**可 grep 的契约**（[report.ts:54-87](soc-demo/services/agent/workers/enrichment/report.ts#L53)）：
web 案件页和评测断言都靠这些锚点读报告。评级取最严重档（`worstLevel`，
[report.ts:29-35](soc-demo/services/agent/workers/enrichment/report.ts#L33)）。

## 三、服务与中间件卡

**卡 1 · ▼ Cortex analyzer + TLP/PAP（协议选型，自研子集）**

- **它是什么**：analyzer = 外部信誉查询仪的标准封装（调用四元组、taxonomies 评级、
  artifacts 提取）；TLP/PAP = 情报界的**敏感度与许可**红绿灯。二者都来自 Cortex/
  TheHive 生态的成熟契约，本项目裁剪实现。
- **市面替代**：① 全套 Cortex（Python 服务器 + 几十种 analyzer，重）；② 直接调
  VirusTotal/AbuseIPDB API（各家一个形状，没有统一抽象）；③ 商业威胁情报平台
  （TIP，如 MISP/ThreatConnect）。
- **为何这么选**：要的是 Cortex 的**契约**（四元组+taxonomies+TLP/PAP 语义——它
  把「数据能不能出门」做成了行业标准）而不是它的运行时。自己实现 100 行的子集，
  换真 analyzer（microsandbox 跑 Cortex 容器，票 16 的 seam）时接口不变。
- **业务上怎么选**：看情报源的**数量与异构性**——两三家源，自己抽象（本项目）；
  十家以上异构源，上 MISP/Cortex 让别人维护适配。而 TLP/PAP 无论规模都该要：
  「这条 IOC 允许被谁知道、允许拿去干什么」是情报协作的法律级语义，没有替代品。

**卡 2 · ▼ fixture 目录当情报库（offline-first 的测试与演示面）**

- **它是什么**：`fixtures/ti/<值>.json` 按值命名的目录，命中读文件、未命中
  no-record，零网络零服务。
- **市面替代**：① 起 MISP/Cortex 容器（真但重）；② mock 库（memono/wiremock）
  返回录制的 API 响应；③ 测试里函数内联假数据。
- **为何这么选**：目录即数据库，**谁能往里放什么一目了然**（场景 5 会往里放「投毒
  analyzer」的案底，审查它就是审查一个文件）；「按值命中」把 VT 的真实语义（查一个
  hash → 一个 JSON 报告）保真到可回放；未命中 no-record 与真 API 行为对齐。与
  1.4 的 chroma、2.2 的 fixture SIEM 同一打法：**每个外部依赖都有「目录/文件」级
  的离线替身**。
- **业务上怎么选**：凡是「查一个键 → 返回一份结构化报告」的外部依赖，离线替身都
  优先做成**数据文件**而不是代码 mock——数据文件可以被审计、被版本管理、被当成
  教材；代码 mock 藏在测试里，业务方看不见。

## 四、防线对号

| 防线 | 在本步的位置 |
|---|---|
| TLP/PAP 确定性闸门（FR-M6.2，OPSEC） | tlpPapGate 纯函数；超限→DENIED 审计+报告逐字拒因+一个字节不外发；布景实测 tlp=4 行被拒 |
| 内部实体不外发 | ANALYZER_OF 白名单外一律 skipped_internal（hostname/filename/url 不进外部信誉库） |
| 签名/闸门分层 | tools.ts 管格式（枚举界），tlpPapGate 管语义（max_tlp/max_pap），gated 管授权——三层互不抢活 |
| 拒发 ≠ 强杀 | 闸拒（授权链缺口）才枪毙 run；TLP 拒发是业务结论，refused 后照常出报告 |
| tool_output 通道卫生 | analyzer 是可污染第三方件（布景 TI 表里真埋了投毒 note），guards flag 打标放行 |
| INV-3 / INV-8 | ENRICHMENT_TOOLS 无 L2；回写/报告全亮票；tlp_pap_denied 与 observable update（dedup）全进 M2 审计 |
| 溯源与对账 | artifacts 带 `from:<analyzer>` 标签；报告四栏对账+可 grep 标记；dedup 并 tags 不建重复行 |
