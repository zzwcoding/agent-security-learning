### 站 3 · 为什么"至少一个过滤维度"是契约不是建议

📍 大图节点:MENU_GATE(呼应 13.1 的上下文治理)

`lookup_requires_filter`（[weknora.ts:89](soc-demo/services/agent/workers/investigation/weknora.ts#L89)）
与 kb_verify 同款：**防"全库捞"**。没有过滤维度的 lookup 会把整本剧本库塞进 LLM 上下文
——上下文治理的起点（P3 的 top-k 无门槛教训，[5.3](5-3.md) 站内提过）。stub 的 lookup
是 includes 匹配（真 weknora 是语义检索——**票 83 对接后回填**：/search 的打分语义与
top-k 口径，stub 不冒充），但"无过滤维度拒绝"这条契约在两个形态里逐字节同语义——
契约测试
（[weknora.test.ts:65-70](soc-demo/services/agent/workers/investigation/weknora.test.ts#L65)）
钉的是调用方依赖的形状，不是实现细节。

## 三、为什么这么设计

- **为什么剧本库是"参考册"不是"卡"**：一张[TERMS「预案卡」](TERMS.md)条管一族怀疑的
  **循环编排**（几轮/每轮几任务/菜单多窄），剧本库管**查询内容**（查什么字段/什么口径）。
  混一张卡的下场：改查询口径要动循环上限的评审面——两个变更频率完全不同的东西绑死。
  数据形态也分开：`fixtures/hunt-templates/` vs `fixtures/weknora/playbooks.json`。
- **为什么 stub 期剧本库只读零写口**：4 张册子是 git 布景——没有任何工具能写它
  （weknora 三工具里唯一的写是 hypothesis_register，且只写关系图）。剧本库的"摄取面"
  属于 weknora 真仓的 /ingest——**票 83 对接后回填**（attack 面全量过防线，挂起条件见
  [13-5](13-5.md)）。换句话说：**stub 期毒剧本连可投递的门都找不到**，能投递的关系图
  写口在 13.4 拦。
- **"三个月前有人猎过同款"的诚实说法**：stub 期的剧本库是 4 张静态册子（无时间轴、
  无命中统计）；真仓的第二幕（SOC 实体图谱）才有"旧案-实体"的时序关系。本场景教的
  是**消费机制**（怎么查、查到后进哪条链、被哪道闸管），不是冒充数据丰富度。

## 场景题闯关（本步 1 题）

**Q：planner 点了 `playbook_lookup` 不带任何参数（想"把剧本库全看一遍再决定"）。这个
调用会走到 MemoryPlaybookLibrary.lookup 吗？观察里会写什么？这个拒绝保护的是什么？**

<details><summary>答案（点击展开）</summary>

走不到。execute 节点先过签名契约
（[validateWeknoraToolCall:84-90](soc-demo/services/agent/workers/investigation/weknora.ts#L84)）：
tag 与 query 双空 → `{ok:false, error:"lookup_requires_filter"}`，**违约调用不执行、不碰
store**，错误文本作为观察返回给 LLM（weknora.ts:82-83 注释原话口径——与
validateToolCall/validateHuntToolCall 同款语义）。子 run 的 execute 会因契约违约 fail-closed
（hunt_tool_signature:lookup_requires_filter 上抛=子 run failed 可观察），judge 半边按
"failed 子报告不是证据"处理（hunt-pack.ts:175 isFailedReport）——绝不折成 hit/miss。
保护的对象是**上下文治理**：全库捞会把 4 册全文塞进 prompt（P3 教训：库越小毒条目越
容易被捞，同样"库越小全捞越便宜"）——所以"至少一维过滤"是契约级闸，不是 prompt 里
的礼貌请求。</details>
