# 场景 4 · 步 4.3 —— interrupt 挂起与审批卡：run 怎么"停在第 748 行"

> 4.1 的主角卡 `apr_baf3f3a8` 已经在台账上躺了两步。本步回答一个调度问题：run 明明是
> agent 进程里的一段函数调用，怎么会**停在 execute 节点半中间**，一停几个小时，还能在
> 4.5 被"从外面"唤醒继续跑？答案有两半：**LangGraph 的 interrupt**（把"等人"变成一种
> 图状态）和**信封链检查点**（把"停在哪、带着什么"变成盘上的事实）。顺带把审批卡的
> 开卡事务拆给你看——"挂起"这个动作在数据库里是一次原子操作完成的四件事。
> 术语卡词翻 `TERMS.md`（同一比喻体系：审批卡/一次性密令/意图闸…），老术语只回指
> 不另起解释。

## 一、操作（位置感）

本步不动任何按钮——主角卡还 pending 着（4.4 才轮到值班长按）。要看的是"挂起"在四个
地方的落盘痕迹：

1. **runs 表**：`run_6ae4b2bf` 的 status = `awaiting_approval`（五种 run 状态之一，
   CONTEXT.md 状态机：running→awaiting_approval→running 是合法往返）；
2. **approvals 表**：`apr_baf3f3a8` 的 status = `pending`；
3. **checkpoints 表**：这个 run 的信封链——6 环，最后一环 node 是 `intent_gate`
   （execute 节点**没有**信封：它没跑完，图冻在半路）；
4. **checkpoint_writes 表**：一行 `idx=-3, channel=__interrupt__` 的特殊写入——
   resume 唤醒时要读的"闹钟"，value 里就是卡 id。

外加一个**对外的活口**：SSE 事件流。挂起不是静默的——`approval_required` 事件已经
落盘，值班长的审批页（web 界面）就是靠它弹卡的；你断线重连，流会按游标补发（INV-7）。

```
curl -s "http://127.0.0.1:3003/api/v1/events/stream?run_id=run_6ae4b2bf-…&after=749"
# 预期：先补发 id:750 approval_required 帧，然后流保持打开等你（实时段）
```

## 二、调用链

先看全景。从"执行到一半"到"盘上四个角落各留一字"，一共四步：

```

  │
  ▼ 同步段（刻意不是 async 函数——interrupt 必须同步抛）

    查卡 findDecidableCard(run, tool, params_hash) → 没有
    openApprovalCard(db, {runId, node, tool, params, …})   ★一个事务四件事:
        ① run 状态门: running→awaiting_approval（非 running 抛 409 整卡回滚）
        ② INSERT approvals 一行（pending + params_hash 指纹）
        ③ emitEvent(approval_required)  ← 落盘事件总线，SSE/web 审批页的信号

  ▼

    run 已在 awaiting_approval（①做的），"挂起"不是失败，也不算完成
  │
  ▼ 盘上静物（此刻进程里没有任何东西在为这个 run 转）
```

### 站 1 · awaitApproval：卡是唯一真相（3.3 已见，本站补深半截）

📍 大图节点:AWAIT（4.3 挂起与审批卡）

3.3 引过这个无限循环的全文（审批卡=TERMS"审批卡"条：agent `approvals` 表的"待批条"，
run 挂在 awaiting_approval，卡是唯一真相）。本步只深挖一个此前一笔带过的细节——**为什么"未决"要
反复 interrupt**，看注释原文：

📄 [services/agent/src/graph.ts:219-233](soc-demo/services/agent/src/graph.ts#L219)

```ts
      // pending = 决定还没落（重启后批准前的重入），幂等再中断，不重复开卡。
      // LangGraph 原生 interrupt：未决即抛 GraphInterrupt 挂起本 superstep。resume 后
      // 节点从头重跑，interrupt() 可能回吞旧 resume 值直接返回——决定以 DB 为准，
      // 回到循环顶重查卡；卡仍未决就再次中断，直到没有新 resume 值真正挂起。
      const card = existing ?? openApprovalCard(db, {
        runId,
        node: cursor.node,
        tool,
        params,
        caseId: o.caseId ?? null,
        reason: o.reason ?? null,
      }, deps.ctx);
      interrupt(card.id);
    }
  };
```

大白话：LangGraph 的 interrupt 有个实现细节——唤醒时它会把"resume 值"原样还给
interrupt() 调用点，代码看起来像"继续跑了"，但**决定可能根本还没落**。所以循环不信
框架给的任何东西，每圈都回数据库查卡：rejected 就带驳回走、approved+token 就带授权
走、pending（包括刚开的新卡）就**再 interrupt 一次**——直到框架没有新的 resume 值
可回吞，图才真正冻住。"框架的返回值会骗人，数据库不会"，这是挂在嘴边的纪律。

### 站 2 · openApprovalCard：挂起是一次原子操作

📍 大图节点:OPEN_CARD（4.3 挂起与审批卡）

开卡不是"写一行数据"这么简单——它同时是 run 的状态迁移、事件广播和审计留痕。这些
事全在一个 SQLite 事务里：

📄 [services/agent/src/approvals.ts:74-92](soc-demo/services/agent/src/approvals.ts#L74)

```ts
  return db.transaction(() => {
    // run 状态门：只有 running 能挂起（INV-10）
    transitionRun(db, input.runId, "awaiting_approval", ctx);
    db.prepare(
      `INSERT INTO approvals (id, run_id, node, tool, params, params_hash, case_id, reason, status, created_at)
       VALUES (?, ?, ?, ?, ?, ?, ?, ?, 'pending', ?)`,
    ).run(
      id, input.runId, input.node, input.tool,
      JSON.stringify(input.params) ?? "null", hash,
      input.caseId ?? null, input.reason ?? null, now,
    );
    emitEvent(db, input.runId, "approval_required", {
      approval_id: id,
      node: input.node,
      tool: input.tool,
      params: input.params,
      params_hash: hash,
      reason: input.reason ?? null,
    });
```

函数头注释（approvals.ts:57-58）就是概括："开卡即挂起（一个事务里做三件事）：插卡 →
广播 approval_required → run 转 awaiting_approval。run 不在 running 时状态机抛 409，
整卡回滚——「挂起」这个动作本身就是原子的。"

三个看点：

1. **状态门在最前**。run 不在 running（比如已被 TTL 扫描器判了 failed）→ `transitionRun`
   抛 409 → 整个事务回滚 → 卡不存在、事件没发过。不会出现"卡开着、run 却终局了"的
   僵尸组合（INV-10 的造型：状态机之外的变更宁可炸也不静默改写）。
2. **卡上带着指纹**。`params_hash` 在开卡时就烙上（4.1 实测 SSE 帧里的
   `sha256:7f36978b…`）——后续"批什么执行什么"的全链条都靠这一枚指纹对齐。
3. **事件在事务内落盘**。`approval_required` 走的是 events 表（落盘总线），不是内存
   回调——值班长页面哪怕此刻断线，重连后按游标补发照样收到（INV-7）。SSE 帧里你
   看到的每个字段（approval_id/params/params_hash/reason）都出自这里。

再把"开卡之后到值班长点批准之前"这段接缝钉死：**①产物此刻躺在哪**——`approvals`
一行 pending 卡 + `run_events` 一帧 approval_required；**②它怎么到人眼前**——SSE 通道
每 100ms 读事件总线增量推给 web，值班长审批页据此弹卡；web 不轮询 run 也不轮询
approvals 表，只听事件总线（INV-7 补发兜断线）；**③值班长的批准怎么回来**——**没有
任何回调**：批准动作只往两张表各写一行（approvals 落决定 + run_jobs 落 resume 诉求，
4.4 拆），谁也不去"叫醒"这个挂起的 run——叫醒是分发循环的活（4.5）。挂起的 run 若
永远没人批，唯一会再来碰它的是 4.7 的 TTL 扫描。

### 站 3 · interrupt 与图冻结：为什么 executeApproved 刻意不是 async

📍 大图节点:SUSPEND（4.3 挂起与审批卡）

interrupt 抛出（GraphInterrupt）必须发生在**同步代码段**——这是 LangGraph 的机制要求，
而 worker 节点全是 async 的。所以 `executeApproved` 被刻意设计成"同步段 + 异步尾段"两截：

📄 [services/agent/src/graph.ts:276-283](soc-demo/services/agent/src/graph.ts#L276)

```ts
  const executeApproved: NodeCtx["executeApproved"] = (tool, params, opts, action) => {
    // 同步段：awaitApproval 里的 interrupt() 必须同步抛出——本函数刻意不是 async 函数，
    // async 节点（票 17 起 worker 全体）与 sync 节点（approval_demo）都先原样走完这段
    // （票 11 契约）。
    const decision = awaitApproval(tool, params, opts);
    if (!decision.approved || !decision.token) {
      return { executed: false, outcome: "rejected", approvalId: decision.approvalId };
    }
```

`awaitApproval`（查卡/开卡/interrupt）全在同步段；interrupt 一抛，节点函数根本走不到
返回值那行——图冻结。剩下的（验票闸、执行、焚毁）都在"决定已决"的异步尾段（graph.ts:294
起的 IIFE），那是 4.5 的戏份。

图冻结后，`runFlow` 拿到的 invoke 返回值长着 `__interrupt__` 通道，收尾代码认得它：

📄 [services/agent/src/graph.ts:380-384](soc-demo/services/agent/src/graph.ts#L380)

```ts
/** 挂起判定：LangGraph 在 invoke 返回值里带 __interrupt__ 通道 = run 停在 interrupt 处
 *  （此时审批卡已开、run 已被 openApprovalCard 原子地转入 awaiting_approval）。 */
function isSuspended(result: unknown): boolean {
  return result !== null && typeof result === "object" && "__interrupt__" in result;
}
```

📄 [services/agent/src/graph.ts:462-471](soc-demo/services/agent/src/graph.ts#L462)

```ts
  if (isSuspended(result)) {
    saveProgress(db, runId, progress.completed, budget.tokens); // 挂起前的计费照记（token 兜底跨 resume 连续）
    // resume 重入后再次挂起（卡仍未决，幂等再中断）时 run 已被 transitionAndMirror
    // 转回 running——挂起态必须落回 awaiting_approval，状态机与 Web 观察面才一致
    // （首次挂起由 openApprovalCard 在开卡事务里完成这一步）。
    if ((getRun(db, runId) as RunRow).status === "running") {
      transitionAndMirror("awaiting_approval");
    }
    return getRun(db, runId) as RunRow;
  }
```

**挂起不是失败也不是完成**——run 状态停在 awaiting_approval，计费（tokens/steps）照记
（4.1 实测 run 的 tokens 数在挂起时就已非零）。467 行那个"落回 awaiting_approval"是
resume 重入的边角：第二次挂起时 run 已被 resume 流程转回 running，这里把它拨回去，
状态机与观察面才一致。

### 站 4 · 信封链盖印：检查点怎么防篡改

📍 大图节点:ENVELOPE（4.3 挂起与审批卡）

图每跑完一个 superstep，框架调 checkpointer 落盘一次。本项目的 checkpointer 不是框架
自带的 SqliteSaver，而是自研的 `EnvelopeCheckpointSaver`——每次 put 都给状态**盖一枚
带链的信封**：

📄 [services/agent/src/checkpointer.ts:189-197](soc-demo/services/agent/src/checkpointer.ts#L189)

```ts
    const [, bytes] = await this.serde.dumpsTyped(saved);
    const stateJson = Buffer.from(bytes).toString("utf8");
    const envelope = sealEnvelope(this.latestEnvelope(runId), {
      runId,
      node: this.nodeLabel() || "__input__",
      stateJson,
    });
    putCheckpoint(this.db, envelope, stateJson);
    return { configurable: { thread_id: runId, checkpoint_ns: "", checkpoint_id: checkpoint.id } };
```

盖印的数学在 envelope.ts 的纯函数里：

📄 [services/agent/src/envelope.ts:46-61](soc-demo/services/agent/src/envelope.ts#L46)

```ts
export function sealEnvelope(
  prev: Envelope | null,
  input: { runId: string; node: string; stateJson: string },
): Envelope {
  const seq = (prev?.seq ?? 0) + 1;
  const stateRef = "sha256:" + sha256Hex(input.stateJson);
  const prevHash = prev?.hash ?? GENESIS_PREV_HASH;
  const hash = paramsHash({
    run_id: input.runId,
    seq,
    node: input.node,
    state_ref: stateRef,
    prev_hash: prevHash,
  });
  return { runId: input.runId, seq, node: input.node, stateRef, prevHash, hash };
}
```

区块链那招，两句说清：**每环的 stateRef 锁住状态快照的原始字节**（改一个字节都对不上）；
**每环的 hash 盖住"自己全部字段 + 上一环的 hash"**（改链上任何一环，从那环往后全部
对不上）。头注释（envelope.ts:10-12）还补了一句较真的取舍：hash 盖的是 JSON 原串
不是规范化形态——**连键序重排都算篡改**（字节变了就是变了）。

读回来时逐环复核：

📄 [services/agent/src/envelope.ts:63-74](soc-demo/services/agent/src/envelope.ts#L63)

```ts
/** 整链复核：seq 连续、prev_hash 逐环相扣、state_ref 对得上状态字节、hash 重算一致。
 *  任何一条不满足 = 落盘状态被动过 → TamperedCheckpointError（resume 必拒）。 */
export function verifyChain(rows: EnvelopeRow[]): void {
  let prev: Envelope | null = null;
  for (const row of rows) {
    if (row.seq !== (prev?.seq ?? 0) + 1) {
      throw new TamperedCheckpointError(`chain gap at seq ${row.seq}`);
    }
    const expectedStateRef = "sha256:" + sha256Hex(row.state);
    if (row.stateRef !== expectedStateRef) {
      throw new TamperedCheckpointError(`state bytes tampered at seq ${row.seq}`);
    }
```

为什么审批 run 特别需要这个？想一遍威胁模型：挂起的 run = 一张"暂停的授权支票"——
批准后 resume，图会从检查点恢复**当时的 state**（意图、参数、案件上下文）继续执行。
如果有人能改盘上的状态字节（比如把 params 里的 host 从 app-01 改成别的，或者把审批
决定提前塞进状态），恢复执行的就是**被调包的现场**。信封链让这种调包在恢复第一刻
就被戳穿——"宁可不恢复，不可恢复出被篡改的状态"（checkpointer.ts:6-7 注释）。

### 站 5 · 盘上实况与"闹钟"

📍 大图节点:T_CKPT（4.3 存储）

```
        WHERE thread_id='run_6ae4b2bf-…' AND idx=-3;

```

`idx=-3` 是 `__interrupt__` 的保留位（checkpointer.ts:126-131 的 WRITES_IDX_MAP），
value 里就是卡 id。resume 时框架读这行"闹钟"，把 execute 节点重新拉起来——然后就是
站 1 说的"从头重跑 + 卡是唯一真相"。闹钟、卡、信封链三处指向同一个 id `apr_baf3f3a8`：
**挂起态的全部真相都在盘上，进程可以死，run 不会丢**。

## 三、服务与中间件卡

### 卡 1（自研）· EnvelopeCheckpointSaver：把自研件装进框架接缝

- **它是什么**：继承 LangGraph 的 `BaseCheckpointSaver`，把三个框架钩子接在自己的
  语义上——`put`=盖信封追加、`getTuple`=整链复核后才交出状态、`putWrites`=interrupt/
  resume 任务写入（特殊通道占负位，checkpointer.ts:126-131）。纯数学（sealEnvelope/
  verifyChain）留在 envelope.ts 纯函数层，类只做"装进框架"这件事。
- **为什么不直接用框架的 SqliteSaver**：框架自带件只管"存得下、读得回"，不管"读回的
  是不是原来那份"。审批场景挂起的是授权支票，防篡改是一等需求——所以宁可自己实现
  接口也不裸用。两个世界的差距就是 verifyChain 那 20 行。
- **市面上同类**：LangGraph 官方 saver 家族（内存/SQLite/Postgres）；Temporal（把
  事件历史做成长事务账本，重得多）；自己在业务层做快照+版本号。
- **业务上怎么选**：挂起恢复的 state 里没有权限语义 → 官方 saver 足够；state 决定
  "恢复后做什么危险的事"（审批、支付、部署）→ 必须有完整性校验，hash 链是教科书解；
  跨天跨人长事务 → 上重量级工作流引擎，别手搓。

### 卡 2（开源）· LangGraph superstep 与 durability="sync"（持久化半边）

- **它是什么**：LangGraph 按 superstep 推进图——一批节点跑完算一步，每步结束调
  checkpointer 存检查点。`durability: "sync"`（graph.ts:416）指定**检查点落库完成后才
  进下一步**；本项目的 thread_id 就是 run_id（信封链的 run 维度锚）。
- **本项目怎么用**：3.3 卡 2 讲过 interrupt/Command 的挂起-恢复语义（控制流半边），
  本卡是它的持久化对偶：**没有每步落盘，interrupt 冻结的就是内存里的图**——进程一死
  什么都丢，"等值班长批准"变成"等进程投胎"。每 superstep 一个信封，冻结的才是一份
  可以隔夜、可以跨进程、可以验真伪的盘上事实。实测主角 run 跑了 5 个节点，盘上 6 环
  （多的一环是框架输入态簿记，node 列记 `__input__`）。
- **市面上同类**：Celery 的任务状态（只有任务级，没有图级检查点）；Airflow（DAG 级
  重跑，颗粒太粗）；Step Functions（云上同思想件）。
- **业务上怎么选**：流程里有"等人"环节 → 必须框架级检查点（不是 try/catch 能救的）；
  等人环节超过小时级/跨班次 → 还要考虑挂起态的可审计（谁能改它？本项目的答案：
  信封链）；纯内存短流程 → 不必付每步落盘的代价。

|---|---|
| **INV-10**（状态机 409） | 开卡事务的状态门：非 running 一律 409 整卡回滚（approvals.ts:75-76）——挂起这个动作本身受状态机仲裁 |
| **INV-7**（SSE 不丢不重） | approval_required 在事务内落 events 表；断线重连按 Last-Event-ID/after 游标补发（实测 after=749 恰好补出 id:750 一帧） |

| **INV-1 / FR-M3.3**（fail-closed 持久化版） | resume 前整链复核，篡改任意字节 → TamperedCheckpointError 拒绝恢复+审计；"宁可不恢复，不可恢复出被篡改的状态" |
| **INV-2 的地基**（params_hash） | 卡在开卡瞬间烙下参数指纹（approval_required 事件带 params_hash 原文）——4.4/4.5 验票对的就是这枚 |

读法：**"批准成功"和"恢复执行"是两件事**。值班长的 200 只说明决定落了卡、token 铸了
（本步实测铸出的 token `ap_d00d9edd…`，300 秒 TTL 自焚，4.7 讲它的下场）；真正去复活

绝不带着被调包的现场继续执行**。

**C · 纸面推演**：如果开卡的四件事不放在一个事务里，有两种碎法，各有各的惨法——
①先插卡后转状态，转状态 409：卡开着、run 终局，值班长面对一张永远批不动的死卡（批了
resume 也进不了 running）；②先转状态后插卡，插卡失败：run 挂在 awaiting_approval，
台账上却没有卡——**审批面无卡可批、执行面无人可醒**，只能靠人肉查库救。一个事务的
原子性把这两种惨案一起埋了（approvals.ts:57-58 注释"整卡回滚"）。

**D · 纸面推演**：如果检查点不存在（想象 LangGraph 没配 checkpointer）——interrupt
冻结的只是内存里的图，值班长还没点批准，agent 容器因部署重启了一下：run 的状态行还是
awaiting_approval（那是 openApprovalCard 写的），但图没了、state 没了，run 永远挂着
等一个不可能的 resume。这就是"挂起必须落盘"的全部理由：**挂起的时间尺度是人的时间
尺度**（分钟到小时），进程的时间尺度扛不住它。
