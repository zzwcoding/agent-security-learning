# 场景 3 · 步 3.2 —— KB 账面：一条草稿的两个世界（kb/proposals REST 面）

> 3.1 的结尾，草稿卡在审批卡上：M2 账面里躺着一条 `proposed`，chroma 检索面里空空如也。
> 本步不往前赶，把"账面"认透——它是 3.3 人审闸的工作台：值班长批的到底是**什么**？
> 在**哪里**记账？记完**谁能看见**？本步还会用一发捣乱实验造出一条"幽灵条目"
> （账面已批准、检索面永远查无），把"**批准了 ≠ 进了检索面**"这个两界分家的设计砸实。
> 这也是给 3.3 备好的对照组：正式人审走对门，草稿才会真正"活"进检索面。
>
> 术语卡：比喻照旧沿用 [TERMS.md](TERMS.md)（KB 账面 vs 检索面/KB 人审闸/叫号屏……），
> 首遇只回指；每站开头的 📍 行对应 [3-big-picture.html](3-big-picture.html) 同名节点。

## 一、操作（位置感）

先说位置感：**知识账面没有 web 页**。web 六页（告警/流水线/案件/审批/审计/评测）里没有它——
kb/proposals 是挂在工作台 M2 上的纯 REST 面，本步全程 curl。这本身是个设计表态：知识沉淀
的"记录"面是给人和程序对账用的，不是又一张炫技大屏。

本步布景（承接 3.1）：账面里应该有一条 `proposed` 主角草稿
（`kb_11d09bb0…`，env_fact，centos7 演练环境事实）。下面所有命令围绕它展开。

**五个端点门牌**（都在 M2 :3002，前缀 `/api/v1/kb`）：

| 方法 | 路径 | 干什么 | 谁调 |
|---|---|---|---|
| POST | `/kb/proposals` | 建档（proposed） | agent 沉淀子图（kb_propose 过闸后） |
| GET | `/kb/proposals[?status=]` | 查账面（可按状态过滤） | 人对账 / autorun 防重查 |
| POST | `/kb/proposals/:id/approve` | 裁决→approved | 正规军走 agent 审批卡；内网也可直调（见捣乱 C） |
| POST | `/kb/proposals/:id/reject` | 裁决→rejected | 同上 |
| GET | `/kb/search?q=&kind=&k=` | **只吐 approved** 的查询面 | 人/Web 查账；分诊机器**不走这里**（走 chroma） |

## 二、调用链

先看全景。一条知识条目从出生到可被检索的一生：

```
POST /kb/proposals（agent kb_propose 或手动）
  │  三道小闸：kind 枚举 / title·body 非空 / 出处案件必须存在（404）
  ▼
[kb_entries 表] status='proposed' —— 账面有户，检索面无踪（INV-5 账面半边）
  │                                  GET /kb/search 查它 → 空
  ▼
人审裁决（proposed → approved / rejected，唯一迁移口，终态再裁 409）
  │  approve：账面翻状态 + reviewed_by 留痕
  │     ↓ 但注意！这只是账面世界的事——
  │     ↓ 检索面（chroma）的写入只发生在 agent kb_write 的已验签执行体里（3.3 正片）
  ▼
两个世界分家：
  账面世界：GET /kb/search 只吐 approved → 人能看到
  检索世界：chroma 向量库 → 分诊机器查的，只有走对门（审批卡→ApprovalToken→kb_write）才进得去
```

### 站 2 · 建档：三道小闸把"垃圾进不了账"写死

📍 大图节点:KB_CREATE(3.2 KB 账面 REST)

建档函数 3.1 已经逐字看过（[kb.ts:85-114](soc-demo/services/case-backend/src/kb.ts#L85)），

| 闸 | 条件 | 报错 | HTTP |
|---|---|---|---|
| 枚举闸 | kind ∉ {fp_pattern, runbook, env_fact} | `kb_invalid` | 400 |

没人答得上"这条知识从哪个案子、哪个人工结论来的"——没法复核、没人敢用；而且 autorun 的
kb_exists 防重（TERMS「防重三闸」条）按 source_case_id 查重，无出处的条目连"这案提过了"
都答不上，防重网直接漏。注意 `POST` 路由层还有一道前置非空检查（`kind_title_body_required`，
[app.ts:267-271](soc-demo/services/case-backend/src/app.ts#L267)）——路由层管"字段给没给"，
领域层管"值合不合法"，两层闸各管各的。

📍 大图节点:KB_DECIDE(3.2 KB 账面 REST)

approve/reject 两个端点几乎对称，看 approve：

📄 [services/case-backend/src/app.ts:291-298](soc-demo/services/case-backend/src/app.ts#L291)

```ts
  app.post("/api/v1/kb/proposals/:id/approve", (req) => {
    const { id } = req.params as { id: string };
    const body = (req.body ?? {}) as { reviewer?: string };
    // reviewer 缺省值班长（CONTEXT 角色：值班长是 L2 审批者）；真实人审身份锚在
    // agent 侧审批卡 + ApprovalToken.approved_by（INV-9），这里是留痕镜像
    const reviewer = body.reviewer ?? (req.headers["x-actor-id"] as string) ?? "duty_lead";

```

reviewer 的三级缺省链：**body 显式给 → x-actor-id 头 → 兜底 "duty_lead"**。注意注释里的
诚实声明：这里的 reviewer 只是**留痕镜像**，真正的人审身份锚在 agent 侧的审批卡和
ApprovalToken 上（INV-9）——3.3 你会看到正规军路径里这条链怎么咬合。

裁决本体 `decideKbProposal`（[kb.ts:134-157](soc-demo/services/case-backend/src/kb.ts#L134)）
核心就三行：查行 → `assertTransition("kbentry", 现状, to)` → 更新。状态机的裁决权：
**只有 proposed 能被裁**，终态（approved/rejected）再裁一律 409 `InvalidTransition`（INV-10，
本步捣乱 C 实测）。审计同事务落一条 `approve`/`reject`，带 reviewer 与 reason。

**把"批准之后谁去写 chroma"这条缝现在就钉死**：approve 端点 200 返回的那一刻，"approved"
只存在于 M2 的 SQLite 一个状态位里——**M2 没有任何一行代码会去写 chroma**，此刻也没有
任何人被通知去做写入。真正把条目送进检索面的执行体住在 agent 侧 kb_write 的已验签路径里
（TERMS「KB 账面 vs 检索面」条："approved 只是账面，进检索面必须走正门执行体"），要等
3.3 那条审批卡→ApprovalToken→闸验签的长路走完、worker 图被 resume 拉起，才轮到它动手。
"账面 approved"和"进检索面"之间隔着的不是时间，是**一整条授权链**——这也是本步捣乱 C
"幽灵条目"能存在的原因。

### 站 5 · 查询面：只吐 approved 的"对外窗口"

📍 大图节点:KB_SEARCH(3.2 KB 账面 REST)

📄 [services/case-backend/src/kb.ts:159-183](soc-demo/services/case-backend/src/kb.ts#L159)

```ts
/** 记录查询面（PRD §6-M7 GET /api/v1/kb/search）：仅 approved，q 对 title/body 做
 *  LIKE，kind 精确过滤，k 缺省 5（决策记录 #6 top-k 口径）。这是给人/Web 看的
 *  账面查询；分诊/调查的向量检索走 agent 侧 chroma 检索面（ChromaKb）。 */
export function searchApprovedKb(
  db: DB,
  filter: { q?: string; kind?: string; k?: number } = {},
): Record<string, unknown>[] {
  const k = Math.min(Math.max(filter.k ?? 5, 1), 50);
  let sql = "SELECT * FROM kb_entries WHERE status = 'approved'";
  const params: unknown[] = [];
  if (filter.kind) {
    sql += " AND kind = ?";
    params.push(filter.kind);
  }
  if (filter.q) {
    sql += " AND (title LIKE ? OR body LIKE ?)";
    const like = `%${filter.q}%`;
    params.push(like, like);
  }
  sql += " ORDER BY created_at, rowid LIMIT ?";
  params.push(k);
  return (db.prepare(sql).all(...params) as Record<string, unknown>[]).map((r) =>
    mapKb(r) as Record<string, unknown>,
  );
}
```

四个口径：**① `WHERE status='approved'` 写死**——proposed/rejected 从 SQL 层就不可见
（INV-5 的账面半边：不是前端帮忙过滤，是数据出口就没长那扇窗）；**② k 夹在 1-50、缺省 5**
（与检索面 top-k=5 同口径，决策记录 #6）；**③ 关键词是 LIKE 模糊匹配**（词面包含，人看
足够）；**④ created_at 升序**——越老的知识越靠前（对照：GET /kb/proposals 列表是 DESC
新者在前，[kb.ts:120-128](soc-demo/services/case-backend/src/kb.ts#L120)——对账看最新，
检索查最老最稳的，两个方向各有道理）。

### 站 6 · 两个世界：账面查询面 ≠ 向量检索面

📍 大图节点:CH_COLL(容器 chroma)

`/kb/search` 的注释里藏了本步最重的一句话：**"这是给人/Web 看的账面查询；分诊/调查的
向量检索走 agent 侧 chroma 检索面"**（TERMS「KB 账面 vs 检索面」条的本步正片）。也就是说
系统里有**两扇看见知识条目的窗**：

| | 账面查询面 `/kb/search` | 向量检索面 chroma |
|---|---|---|
| 数据在哪 | M2 的 SQLite `kb_entries` 表 | agent 侧 chroma 容器 `kb_entries` 集合 |
| 谁在看 | 人 / Web（curl 一发就到） | 分诊 kb_check（场景 3.4 主角） |
| 怎么查 | SQL：status='approved' + LIKE | 向量相似度 top-k |
| 谁能写 | `createKbProposal` / `decideKbProposal`（内网 REST） | **只有 kb_write 已验签执行体**（INV-5） |

两扇窗**数据不同源、权限不同宽**：账面世界里，一条 direct-REST 批准的条目照样"approved
可见"；但检索世界里它**不存在**。为什么要把结构切得这么拧？**假如账面批准直达检索面会
怎样**：往知识库投毒就退化成一次内网 REST 调用——直连 approve 翻个状态位，毒条目立刻
出现在分诊的 prompt 里，人审闸从头到尾没被经过。把 chroma 的写入路径收窄到"全仓唯一一条、
且住在已验签执行体里"（INV-5），绕过人审的"批准"物理上只能造出**账面幽灵**——毒进不了
分诊的嘴。光看代码不容易有体感——本步捣乱 C 造了一条"幽灵条目"
实测砸实。看懂了这一层，你才能真正看懂 3.3：**为什么批准必须走审批卡+ApprovalToken
那条长路，而不是"批准"一下就完事**——因为"批准"只是账面世界的动词，检索世界的门票
在 agent 的 L2 正门手里。

## 三、服务与中间件卡

### 卡 1（架构形态）· System of Record vs System of Access：账面与检索面为什么分家

- **它是什么**：经典架构形态——**记录系统**（账面，SQLite：状态机、审计、人审流程的
  事实源）与**访问系统**（检索面，chroma：为"查得快查得准"优化的只读投影）。写路径
  长而窄（人审闸），读路径短而宽。
- **市面同款**：OLTP 库 + Elasticsearch 投影（电商商品库 vs 搜索索引）、Git 仓库 + CDN、
  消息表 + 读模型（CQRS 的民间版）。共同点：**投影可以重建，事实源只有一个**。
- **本项目怎么用**：chroma 里丢了/病了，账面 approved 条目可以重新 upsert 重建（写入
  代码就一条路，重放即可）；反过来账面是审核痕迹的最终解释权（谁批的、何时批的）。
- **业务上怎么选**：只要出现"同一份数据既要严格事务、又要模糊快查"，就值得分家；
  数据量小到 LIKE 都够用时（我们的 demo 就是），分家的意义不在性能在**权限**——
  检索面的写入路径窄，才有 INV-5 的结构保证。

### 卡 2（领域卡）· SOC 知识库三类条目：不是文档库，是可检索的决策依据

- **三类是什么**：`fp_pattern`（误报模式：这种告警是噪声，下次直接按误报处理）、
  `runbook`（处置经验：真攻击，照单子处置）、`env_fact`（环境事实：授权演练/变更/
  资产登记，下次别升级）。出处是 PRD §5.10，对标 TheHive/HolmesGPT 这类 SOC 助手
  的知识沉淀实践（M507 决策点）。
- **关键认识**：知识条目是**写给下次分诊用的**——3.4 你会看到它被切成 host/path/user
  拼成查询打进向量库，3.5 你会看到 env_fact 命中后分诊直接给 btp 建议关单。所以
  title/body 里写什么（触发特征/判定依据/复核要点）都是**为了机器和人下次都能对上号**，
  这也是 FakeKnowledgeLlm 那张 verdict→kind 词典里 body 模板长那样的原因。
- **业务上怎么起步**：别追求"大而全的 wiki"，先让三类条目跟着关案流程自动长出来
  （本场景正在做的事），人审把住质量关，检索面自然越用越准。

## 四、防线对号

| 防线 | 在本步的落点 |
|---|---|
| **INV-5 账面半边** | `/kb/search` SQL 写死 `status='approved'`；proposed/rejected 从数据出口就不可见（捣乱实验前实测查无） |
| **INV-5 检索面半边** | chroma 唯一写入路径 = kb_write 已验签执行体；直连批准翻账面 **翻不动检索面**（幽灵条目 count=0 实证） |
| **INV-10** | kbentry 终态再裁 409（approved 后再 reject → `InvalidTransition`） |
| **ASP 出处闸** | source_case_id 必须指向真实案件（404）——知识必须有出处 |
| **跨服务契约** | agent `KB_ENTRY_KINDS` 与 M2 `KB_KINDS` 一字不差（[prompt.ts:19](soc-demo/services/agent/workers/knowledge/prompt.ts#L19) ↔ [kb.ts:18](soc-demo/services/case-backend/src/kb.ts#L18)）；两端测试各咬对方 |
| **INV-8** | create/approve/reject 三动作审计同事务；reviewer 记人头 |
| **INV-9** | REST 的 reviewer 只是留痕镜像；真实人审身份锚在审批卡 + ApprovalToken（3.3 正片） |

**C · 重头戏：直连批准，造一条"幽灵条目"**（绕过审批卡直接翻账面，看它进不进检索面）：

```bash
# C1. 手动建档（title 自带"捣乱"字样方便日后辨认）
curl -s -X POST http://127.0.0.1:3002/api/v1/kb/proposals -H 'content-type: application/json' \
  -d '{"kind":"fp_pattern","title":"【捣乱教具】直连批准的幽灵条目","body":"不经审批卡、直连 M2 REST 批准——账面翻 approved，检索面永远查无（3.2 对照组）","tags":["捣乱"],"source_case_id":"case_000004","proposed_by":"soc1:manual"}'
# 预期：201，拿到 id（本步实测 kb_1f5f4196-…）

# C2. 直连 approve（内网信任口不拦你）
curl -s -X POST http://127.0.0.1:3002/api/v1/kb/proposals/kb_1f5f4196-1d44-4563-b1e3-68ec7f9b16d5/approve \
  -H 'content-type: application/json' -d '{"reviewer":"soc1"}'
# 预期：status="approved"，reviewed_by="soc1"，decided_at 落值

# C3. 幽灵现形：两个世界各看一眼
curl -s "http://127.0.0.1:3002/api/v1/kb/search?q=%E6%8D%A3%E4%B9%B1"   # q=捣乱
# 预期：hits 里有它！  ← 账面查询面：approved 就可见

CID=$(curl -s http://127.0.0.1:18000/api/v2/tenants/default_tenant/databases/default_database/collections \
  | python3 -c "import json,sys; print([c['id'] for c in json.load(sys.stdin) if c['name']=='kb_entries'][0])")
curl -s "http://127.0.0.1:18000/api/v2/tenants/default_tenant/databases/default_database/collections/$CID/count"
# 预期：0   ← 向量检索面：它根本不存在！

# C4. 终态再裁，状态机拍 409
curl -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:3002/api/v1/kb/proposals/kb_1f5f4196-1d44-4563-b1e3-68ec7f9b16d5/reject \
  -H 'content-type: application/json' -d '{"reviewer":"soc1","reason":"改主意"}'
# 预期：{"error":"InvalidTransition"} / HTTP 409   ← approved 是终态（INV-10）
```

读法：M2 的 approve 端点是**内网信任口**，直调它账面真会翻——但它翻的只是 SQLite 的
一个状态位。**检索世界的门票在 agent 的 kb_write（L2 ApprovalToken 正门）手里**，那条路
要：审批卡 → 值班长批准 → gateway 铸一次性 token → 闸验签焚毁 → 执行体 upsert chroma。
跳过这条长路的"批准"，产物就是一个**账面已批、检索面查无、永远无法反哺分诊**的幽灵。
它还会占住一个隐性资源：autorun 的 kb_exists 防重按
`source_case_id + proposed/approved` 查重（[autorun.ts:128-131](soc-demo/services/agent/src/autorun.ts#L128)），
幽灵挂着 case_000004 的 approved——若该案的 case.closed 事件将来重放，防重会因它跳过。

**这条幽灵条目是 3.3 的对照组**：下一步走正门批准主角草稿（kb_11d09bb0），你会看到
chroma count 从 0 变 1——同一句"批准"，走没走对门，检索面知道答案。

**D · 纸面推演（不真打）**：账面没有 `(source_case_id, kind)` 唯一约束——同案同 kind 可以
建 N 条提案（3.1 捣乱 E 的另一个面）。防线在流程不在 schema：正规路径里每案只提一次案
（autorun 防重），重复提案只能从手动正门来——纪律分层的老话题了。
