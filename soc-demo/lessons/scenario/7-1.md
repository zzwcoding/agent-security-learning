# 场景 7 · 步 7.1 —— 脚手架：一条命令"生"出一个新工具

> 场景 7 开场。前六个场景我们一直在"读"这套系统，这一整个场景反过来——**往系统里
> 加一个新工具**，把"新增"这件事的全套对账走一遍。本步先干最容易的一件：跑
> `pnpm gen:tool`，让脚手架生成器把新工具的空壳、测试骨架、登记行一次产齐。
> 我们选的工具叫 **`list_approvals`（审批台账查询）**：值班长想知道"现在手头有哪
> 些待批的高危动作卡"——场景 4 攒下的审批台账（agent 库 approvals 表，现有 7 张卡）
> 正好是它的真实数据源；只读、L1 档、零 L2，不给系统添任何新审批面。

**位置感**（本场景 4 步路线图）：

```
⬜ 7.1 脚手架：gen:tool 生成空壳工具（你在这里）
⬜ 7.2 登记：manifest 行、三方一致性（manifest ≡ TOOLS ≡ A.1）
⬜ 7.3 闸的生效与拒绝：登记后过闸、不登记 403 no_ticket、INV-3 无 L2
⬜ 7.4 边界闸与体检：check_boundary、四对账、"测试零删除"纪律
```

> 授权边界说明：学习阶段的红线是"不改生产代码"，但场景 7 的教学本质就是新增一个
> 工具——所以本场景获用户明示授权，允许动：gen:tool 生成物、manifest 加行、
> A.1 文档同步、新工具的测试文件。与本场景无关的生产代码照旧一律不碰。

## 一、操作（位置感）

先说选型，再说操作。**为什么是 `list_approvals`**：①SOC 业务上真有用——审批台账
是场景 4 的主角面，值班长的日常第一问就是"有什么等我批"；②数据源现成——agent 库
的 approvals 表（7 张卡：approved 4 / expired 1 / rejected 2）挂在宿主盘，只读可查；
③安全面干净——纯只读，INV-3 对号时"零 L2"天然成立，不会像加一个高危工具那样
牵出新的审批面。分级取 **L1**，与 `get_case` 的"更严口径"同款：读也要过任务票，
不做免验（7.2 登记时细讲）。

生成器的用法（先空手跑一次，看它自己吐说明书）：

```bash
cd /Users/divh/Downloads/安全评估agent/soc-demo
pnpm gen:tool
# 预期：exit 1，stderr 打印用法一行——
# gen-tool: 用法：node tools/gen-tool.mjs <name> [--tier L1] [--out <dir>] [--manifest <path>]
```

真跑。为了不给共享布景下毒，第一遍把 `--manifest` 指向**真登记表的临时拷贝**
（生成器要求表必须已存在，`--out` 给个临时目录收生成物）：

```bash
mkdir -p /tmp/gen71 && cp fixtures/tools.manifest.json /tmp/gen71/tools.manifest.json
node tools/gen-tool.mjs list_approvals \
  --tier L1 --family readonly_query --owner m3 \
  --desc "审批台账查询（只读：审批卡 id/工具/状态/案号；更严口径按 L1 过任务票，不做免验——get_case 同款）" \
  --out /tmp/gen71 --manifest /tmp/gen71/tools.manifest.json
# 预期（实测）：
# gen-tool: 已登记 list_approvals（tier=L1 family=readonly_query owner=m3）
#   工具空壳   /tmp/gen71/list_approvals.ts
#   测试骨架   /tmp/gen71/list_approvals.test.ts
#   登记行追加 /tmp/gen71/tools.manifest.json
```

一条命令，**三件产出**：空壳工具（`.ts`）、测试骨架（`.test.ts`）、登记行（manifest
里多一行）。这就是本步的全部操作——剩下的篇幅都在拆"这三件产出是怎么来的、
为什么这么设计"。

```
你（终端）
  │ pnpm gen:tool …
  ▼
▼ package.json scripts 字条：node tools/gen-tool.mjs（零依赖 node 脚本，中立层）
  │

```

### 站 1 · 命令从哪来：scripts 字条与入参校验

pnpm 替你跑的字条在 [package.json:15](soc-demo/package.json#L15)：

```json

```

生成器本体是 [tools/gen-tool.mjs](soc-demo/tools/gen-tool.mjs)，文件头注释开宗明义
（第 4-6 行原话）："「新增一个工具」在过去=全仓摸 6+ 处：worker 工具面常量、票面
allowedTools、manifest 登记、handler、测试……漏一处就静默漂移。本生成器把最小闭环

### 站 2 · 登记行：先于代码的"出生证明"

[gen-tool.mjs:64-75](soc-demo/tools/gen-tool.mjs#L64)：

```js
// ① 登记行：重名拒绝——登记面是安全面，覆盖=静默改分级，绝对不行
let raw;
try {
  raw = readFileSync(manifestPath, "utf8");
} catch {
  die(1, `登记表不存在：${manifestPath}（--manifest 要指着一份已存在的 tools.manifest.json）`);
}
const manifest = JSON.parse(raw);
if (manifest.tools.some((t) => t.name === name)) {
  die(2, `${name} 已登记于 ${manifestPath}（重名拒绝，不静默覆盖；要改分级直接编辑登记行）`);
}
manifest.tools.push({ name, tier, family, owner_card: ownerCard, description: desc });
```

注意动作顺序：**push 登记行在前，生成代码在后**——新工具是"先上户口、后长肉身"。
用保安队的话说：登记表（tools.manifest.json）是**保安队的装备清单**，一个还没在
清单上的名字，连"这个人存在"都不成立，谈何上岗。三个拒绝各有退出码：表不存在
exit 1（`--manifest` 必须指着一份**已存在**的表，生成器不替你凭空造表）；重名
exit 2——注释原话"登记面是安全面，覆盖=静默改分级，绝对不行"，要改分级只能
显式编辑登记行，没有"顺手覆盖"这条路。

登记行落到哪张表？真表的门面在 [fixtures/tools.manifest.json:2-6](soc-demo/fixtures/tools.manifest.json#L2)：

### 站 4 · 落盘：写三个文件，重排一张表

[gen-tool.mjs:99-102](soc-demo/tools/gen-tool.mjs#L99)：

```js
mkdirSync(outDir, { recursive: true });
writeFileSync(path.join(outDir, `${name}.ts`), shell);
writeFileSync(path.join(outDir, `${name}.test.ts`), skeleton);
writeFileSync(manifestPath, JSON.stringify(manifest, null, 2) + "\n");
```

最后一行值得停一下：manifest 是**整表重写**（`JSON.stringify(manifest, null, 2)`），
不是文本级追加一行。后果我们实测过：对着真表跑一次生成器，`git diff --stat` 是
**175 处插入 / 24 处删除**——23 行老登记行全被从"一行一条"重排成七行一条的缩进
格式，diff 噪音巨大（JSON 语义一个字节没变，但对账的人看着头疼）。所以本场景的
真表登记（7.2）**手工按既有单行风格加一行**，生成器只管代码与骨架——尊重文件的
既有风格，是登记的礼仪，也是给 `git blame` 和未来 diff 留清净。

## 三、服务与中间件卡

**卡 1 · 脚手架即治理（代码生成器作为安全面的一半）**

- **它是什么**：gen:tool 不是普通的"代码模板生成器"——它一半管代码（空壳+骨架），
  一半管**登记**（manifest 加行），且登记先于代码、重名绝对拒绝。把"新增工具要
  在登记表签到"这件最容易漏的事，焊死在生成流程的第一步。
- **市面对照**：① Yeoman/plop 一类纯代码模板器（不管登记，安全面靠人记）；②
  云厂商的 API 网关控制台（登记=控制台点一下，代码另走一套）；③ Kubernetes 的
  CRD + controller（声明式登记，观念最近，但重了）。
- **本项目为什么这么做**：这个仓的安全语义（L0/L1/L2 分级、审批面）全部长在
  登记行上——登记错=分级错=闸的行为错。所以"生成"和"登记"必须是同一动作，
  且登记面宁可笨一点（重名拒绝、不覆盖）也不聪明地"帮人合并"。
- **业务上怎么选**：凡"漏一步就静默漂移"的多点登记场景（安全组规则、路由表、
  特性开关目录），都值得把登记焊进脚手架；判据是看登记面出事故时的爆炸半径——
  爆炸半径大的，优先焊。

**卡 2 · 临时清单接缝（TOOLS_MANIFEST_FILE env 覆盖）**

- **它是什么**：登记表的读口（tools-manifest.ts）留了 env 覆盖口——测试/演示可以
  把闸的粮草换成一份临时清单，验完复位。gen:tool 的端到端演示测试
  （services/agent/src/gen-tool.test.ts）就是拿这份临时清单跑"生成→登记→过闸→
  删行→闸拒"全链的，真表一个字节不碰。
- **市面对照**：① config 模块热更新（运行时换配置，风险高）；② 依赖注入传配置
  对象（最正统，但要改构造函数签名）；③ 环境变量覆盖 + 模块级缓存 + 显式复位
  （本仓选的，改动最小）。
- **本项目为什么选 env 覆盖**：闸的代码一行不用改，测试就能"换一张表"——
  visible-tools.ts 读 FGA_MATRIX_FILE 是同款先例。代价是必须管好缓存复位
  （resetToolsManifestCache），否则测试之间串味。
- **业务上怎么选**：给"不敢在真数据上做实验"的安全面配一条**换粮草的缝**，是
  测试基建的一部分；缝必须配**必复位**纪律（gen-tool.test.ts 每个用例的 finally
  都在复位）。

## 四、防线对号

| 防线/不变量 | 在本步的位置 |
|---|---|
| fail-closed 默认级（INV-1 的登记面版） | 生成器 tier 缺省 L1（宁严勿松）；未登记工具 policy 默认 L1——"没登记就只剩持票才可动" |
| 登记面是安全面（票 48/ADR 0004-2） | 重名拒绝 exit 2、不静默覆盖；表不存在拒绝生成——登记行的每一次变动都必须是显式的 |
| 边界规则 R3（中立层不 import services） | gen-tool.mjs 零依赖、不 import 工程内部任何模块——生成器自己不越界 |
| 生成物不入库纪律 | generated-tools/ 在 .gitignore；入库的只有生成器本体与（7.2 起）手工收编的生成物 |
| 先登记后持票 | 登记行 push 在代码生成之前——户口先于肉身，7.3 会看到没有户口的调用在闸上是什么下场 |

## 六、捣乱实验（必选）

**捣乱 A · 重名再生成**（验证"登记面绝不静默覆盖"）：

```bash
M=/tmp/gen71/tools.manifest.json
md5 -q $M > /tmp/gen71/m1.txt
node tools/gen-tool.mjs list_approvals --out /tmp/gen71 --manifest $M; echo "exit=$?"
md5 -q $M > /tmp/gen71/m2.txt && diff /tmp/gen71/m1.txt /tmp/gen71/m2.txt && echo "manifest 字节未动"
# 预期（实测）：stderr「list_approvals 已登记于 …（重名拒绝，不静默覆盖…）」
#              exit=2，manifest 的 md5 前后一致
```

**判据**：退出码 2 + 登记表字节级不变。想改分级？只有一条路——显式编辑登记行
（留痕、可 diff、可审）。对照反面教材：很多脚手架"已存在就合并/覆盖"，在安全面
上等于给静默改分级开绿灯。

**捣乱 B · 大小写戏法**（工具名是精确匹配的字符串，不是"长得差不多就行"）：

```bash
node tools/gen-tool.mjs List_Approvals --out /tmp/gen71 --manifest /tmp/gen71/tools.manifest.json; echo "exit=$?"
ls /tmp/gen71/ | grep -i list
# 预期（实测）：exit=1，报「工具名 List_Approvals 不合口径（须匹配 /^[a-z][a-z0-9_]*$/…）」，
#              目录里只有此前生成的 list_approvals.*，没有任何 List_Approvals 文件
```

**判据**：拒在门口（exit 1），一个文件都不落。为什么这么严？7.3 会看到：验票闸对
工具名做的是**字符串精确匹配**——`List_Approvals` 和 `list_approvals` 在闸眼里是
两个工具，前者是"未登记工具"（默认 L1、无票 403）。大小写在登记面上不是审美，
是身份。

**捣乱 C · 参数越界三连**（生成器的入参全是枚举/正则闸）：

```bash
node tools/gen-tool.mjs demo_x --tier L9        --out /tmp/gen71 --manifest /tmp/gen71/tools.manifest.json; echo "exit=$?"
node tools/gen-tool.mjs demo_x --family case_read --out /tmp/gen71 --manifest /tmp/gen71/tools.manifest.json; echo "exit=$?"
node tools/gen-tool.mjs demo_x --owner m3x      --out /tmp/gen71 --manifest /tmp/gen71/tools.manifest.json; echo "exit=$?"
# 预期（实测）：三条全部 exit=1，各自报「--tier 只许 L0|L1|L2」「--family 须是 A.2 四族之一」「--owner 须是模块卡号」
```

**判据**：三连全拒。登记行的每个字段都会被下游对账咬（tier 对照闸的行为、family
对照 FGA 矩阵、owner 对照模块卡）——生成器在入口就把越界值挡住，不让脏字段流进
对账网。

**捣乱 D · 对着真登记表跑一次，看对账闸翻脸**（本步最重要的一幕，跑完立刻还原）：

```bash
node tools/gen-tool.mjs list_approvals --tier L1 --family readonly_query --owner m3 --desc "审批台账查询" \
  --out /tmp/gen71-real --manifest fixtures/tools.manifest.json
git diff --stat fixtures/tools.manifest.json
# 预期（实测）：登记成功；diff --stat 显示 175 insertions(+), 24 deletions(-)——整表被重排
cd services/agent && pnpm exec vitest run src/tools-manifest.test.ts
# 预期（实测）：10 个用例里 1 个红——
#   × manifest 只比 A.1 多已点名的偏差工具（多一个没记票的 → 红）
cd ../.. && git checkout -- fixtures/tools.manifest.json
cd services/agent && pnpm exec vitest run src/tools-manifest.test.ts
# 预期（实测）：10 passed——还原即绿
```

**判据**：登记行一落真表、A.1 还没跟上，对账测试**立刻红**——红在"manifest 比
A.1 多了一个没记票的工具"。这正是登记表 `_readme` 说的"三方法律"在执法：**登记
不是写一行就完，是给全仓的对账网打招呼**；谁单方面漂移谁红。7.2 的正片就是把
这场红"走绿"的全过程。（顺带记下 diff --stat 的教训：生成器整表重排会把 23 行
无关历史卷进 diff，所以 7.2 的真表登记行改用手工单行追加。）
