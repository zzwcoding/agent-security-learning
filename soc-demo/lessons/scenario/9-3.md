## 一、操作（位置感）

布景同 9.2。本步的主菜在两张表和一个端点里：

1. agent 库 `hunt_run_links`——看父子关系（谁是谁的子 run）；
2. agent 库 `runs`——看子 run 的独立人生（自己的状态机/自己的预算账）；
3. `POST /internal/runs`——手动直拉一条 hunt_task（捣乱实验用），看铸票缝怎么拒。

先摆好位置感：轮 1 父 run（hunt_flow）跑到 dispatch 节点时，它在**自己的图里**只是过了
一个节点；但这个节点向 m3 run 机器**又投了两单**（两条 hunt_task run），两条子 run 各自
走完整的「queued→running→failed/completed」人生。**父 run 在 await_children 挂着等，
子 run 在并行跑**——一张图里看不出并行，两行 run 行才看得出。

### 站 1 · dispatch：先过防转闸，再扇出

📍 大图节点:DISPATCH(9.3 扇出两子 run)

dispatch 节点开头先对指纹（[flow.ts:150-170](soc-demo/services/agent/src/orchestration/flow.ts#L150)）：
本轮 `tasks_fingerprint` 与上一轮相同（任务集 + gap 摘要双双原地踏步）→ 记
`hunt_round_spin_denied`（DENIED）审计 → 假设直接迁 cancelled(spin) → 本轮终止。
「换轮必须换组合」是**闸不是建议**——这是 9.5 的正戏，这里先认个门牌。

过了闸才扇出（[flow.ts:171-189](soc-demo/services/agent/src/orchestration/flow.ts#L171)）：

```ts
        const children: string[] = [];
        for (const task of tasks) {
          // 铸票在 m3 正门内走（票 76：launchTask 随任务过门，窄票面由门内解析现铸
          // ——子票铸于 dispatch；门失败（含铸票失败）= 任务不执行、无悬置）。
          try {
            children.push(await launcher.launchTask({ hypothesisId, roundNo, parentRunId: runId, task }));
          } catch (err) {
            // T15（INV-1/8）：铸票失败先落五要素 DENIED（该任务 + 原因可回放），再原样
            // 上抛交 runner 强杀路径收口（run 不带病续跑、无半拉子 run）——fail-closed。
            recordAudit(audit, runId, {
              action: "hunt_dispatch_mint_denied", ..., result: "DENIED",
            });
            throw err;
          }
        }
```

两个 fail-closed 细节：①任务逐个拉起，任何一个失败（含铸票失败）先落 DENIED 审计
（哪路任务、什么原因，可回放）再原样上抛——**run 不带病续跑、无半拉子 run**；②dispatch
自己不碰铸票客户端一个字节（R11 红线：票只归 m3 装配铸），它只把任务递给门。

扇出成功后落**审计分痕 B**（[flow.ts:194-200](soc-demo/services/agent/src/orchestration/flow.ts#L194)）：
`hunt_dispatch_decide`，details 带实际 children 数组与 tasks_fingerprint——跟 9.2 的
`hunt_plan_suggest`（A：建议）对照着读，建议与决定从此可查可对账。最后广播
`hunt_children_declared` 事件（SSE 直播可见「本轮扇出了谁」）。

### 站 2 · 两票制：子票铸于正门内，票面只装一件工具

📍 大图节点:CHILD_MINT(9.3 扇出两子 run)

launchTask 打的还是那扇正门（[launcher.ts:37-51](soc-demo/services/agent/src/orchestration/launcher.ts#L37)）：
`door.post({ kind: "hunt_task", hypothesis_id, task })`——**任务上下文随拉起过门**。门内
看到 hunt_task 带任务，就在本门里现铸一张窄票（[app.ts:375-397](soc-demo/services/agent/src/app.ts#L375)）：

```ts
    let childTicket: string | null = null;
    if (
      body.kind === "hunt_task" && opts.makeNodes &&
      body.task !== undefined && typeof body.task?.tool === "string" && body.task.tool
    ) {
      try {
        const spec = ticketSpecFor(body.kind, body.task);
        const minted = await mint.mintTaskTicket({
          jti: `tk_${randomUUID()}`,
          sub: spec.sub,
          caseId: run.caseId,
          runId: run.id,
          scope: [...spec.scope],
          allowedTools: [...spec.allowedTools],
        });
        childTicket = minted.token;
      } catch (err) {
        failUnTicketedRun(run.id, err);
        return reply.status(502).send({ error: "mint_failed" });
      }
    }
```

票面规格全部出自 `ticketSpecFor`（[run-kinds.ts:342-354](soc-demo/services/agent/src/run-kinds.ts#L342)）——
INV-11 的第二道闸就在这里面：

```ts
  const parentFace = REGISTRY.hunt_flow.ticket.allowedTools;
  if (!parentFace.includes(task.tool)) {
    throw new Error(`hunt_task 子票拒铸：工具 ${task.tool} 不在父票菜单内（INV-11，铸票缝 fail-closed）`);
  }
  return { ...spec, allowedTools: [task.tool] };
```

三个必须读出来的点：

1. **窄票面**：`allowedTools: [task.tool]`——子 run 的票上只印着它这一趟唯一的那件工具。
   父 run 的票（planner 只读面）再宽也不继承；「扇出 N 路」不是「发一张大票」，是 N 张
   各管一件事的小票。TERMS「单趟差」条的这句「只带一张只许干这一件事的窄手令」落点在这。
2. **缝闸 fail-closed**：任务工具不在父票菜单内 → 拒铸抛错 → 门把这条 run 标 failed
   （mint_failed）+ 502 回给 dispatch——**越界任务在铸票唯一通道上就拿不到票**。planner
   的菜单闸（9.2）是第一道，这里是第二道：第一道防「选错」，第二道防「签错」，各自独立
   成立（TERMS「派工菜单」条原文口径）。
3. **任务上下文缺 tool 也拒**：[run-kinds.ts:346-348](soc-demo/services/agent/src/run-kinds.ts#L346)
   显式任务但 tool 缺失/为空 = 载荷畸形，fail-closed 拒解析，绝不静默放宽到菜单级票。

铸出来的子票跟着 start 任务落盘（票 76 两票制），执行件直接用——**不存在「先拉起再补票」
的悬置窗口**，注释里那句「铸票失败 = 该子 run 落 failed(mint_failed)，不 enqueue、无悬置」
就是它。

### 站 3 · 子 run 的独立人生：四节点小图 + 真执行体

📍 大图节点:TASK_FLOW(9.3 扇出两子 run)

每条 hunt_task 是一张四节点小图（[task-flow.ts:31-109](soc-demo/services/agent/src/orchestration/task-flow.ts#L31)）：

- **intake**（[:33-45](soc-demo/services/agent/src/orchestration/task-flow.ts#L33)）：任务不在
  拉起参数里现拿，而是**从簿记恢复**——`ledger.get(runId)` 拿回自己那条 task 行。dispatch
  拉起前任务是"不可知"的（planner 刚产出的），所以交接靠簿记不靠消息；簿记缺行直接炸响
  （「拉起路径绕开了 launcher」的 AssertionError 语义）。
- **plan**（[:47-53](soc-demo/services/agent/src/orchestration/task-flow.ts#L47)）：唯一任务即
  唯一计划步——子 run 不再规划，它只执行（规划是 planner 的事，这是编排的分层）。
- **execute**（[:57-69](soc-demo/services/agent/src/orchestration/task-flow.ts#L57)）：机制图
  这里是个桩；生产装配把桩**换件**成真执行体（[run-kinds.ts:314-330](soc-demo/services/agent/src/run-kinds.ts#L314)
  的 `wireHuntTaskExecutor`，[hunt-executor.ts:108-155](soc-demo/services/agent/workers/investigation/hunt-executor.ts#L108)）。
  真执行体每圈走「签名契约 → 验票闸 → 执行 → 观察」四步：
  签名契约 `executeHuntPackTool`（[:58-74](soc-demo/services/agent/workers/investigation/hunt-executor.ts#L58)）
  先验参数形（查询缺 time_window、playbook_lookup 没带过滤维度等违约**不执行不烧后端**），
  再过 [TERMS「闸体/闸」](TERMS.md)的 makeGatedCall（[hunt-executor.ts:121-134](soc-demo/services/agent/workers/investigation/hunt-executor.ts#L121)，
  creds 就是那张 narrow-scope 子票），最后 `summarizeHuntObservation`
  （[:78-89](soc-demo/services/agent/workers/investigation/hunt-executor.ts#L78)）把结果折成
  `tool total=N hits=M` 的确定性格式——这个摘要就是 judge 的引用痕原料（9.4）。
- **report**（[:72-85](soc-demo/services/agent/src/orchestration/task-flow.ts#L72)）：发
  `hunt_task_finished` 审计事件（带 result_summary/params_hash）+ 落 `hunt_task_report`
  五要素审计。**这个事件是父 run await_children 的唯一正常唤醒源**（9.4 的主角）。

注意四节点外面还包着一层取消检查（[task-flow.ts:24-30](soc-demo/services/agent/src/orchestration/task-flow.ts#L24)）：
每个节点进场前 `throwIfCancelled`——父链取消后子 run 在**下一个节点边界**安全停（9.6 捣乱①
的机制半边，这里先认门牌）。

### 站 4 · 两行 run 行：并行不并权的账面证据

📍 大图节点:T_RUNS_HUNT(9.3 扇出两子 run)

簿记紧跟拉起落账（[launcher.ts:41-48](soc-demo/services/agent/src/orchestration/launcher.ts#L41)）：
`hunt_run_links` 落 role=task 行，带 parent_run_id + round_no + task 全文。跟父 run 的
role=round 行（9.1 站 5）合起来，一张假设的 run 家谱全在这张表里。查起来就是 9.1 用过的
姿势加一个 parent 条件（`childrenOf`，[ledger.ts:104-110](soc-demo/services/agent/src/orchestration/ledger.ts#L104)）。

子 run 的预算账是**独立一本**：hunt_task 不在 budget 档位表里（[budget.ts:122-129](soc-demo/services/agent/src/budget.ts#L122)
只列了 hunt_flow），吃默认档（20 步/50k token/60s）——父 run 的 500k/200 步再紧张也不
挤占子 run 的额度，反过来子 run 烧穿自己那本也烧不到父账。**并行不并权，账也是分开的**。

## 三、服务与中间件卡

**卡 1 · ▼两票制（父票 + narrow-scope 子票，自研票务装配形态）**

- **它是什么**：扇出型 run 的票分两层——父 run 票面 = 决策面能力并集（planner 只读面 +
  register），子 run 票 = 该任务唯一工具，铸于正门内 dispatch 拉起时（票 76）。
- **市面替代**：一把大票跑全程（一张 token 带全部 scope，代理间复用）；或 OPA/Cedar 式
  的「运行时按请求裁权」（每个动作现查策略引擎）。
- **为何这么选**：大票跑全程 = 任何一路被带偏都能干任何一路的事（并行变横向越权）；
  运行时裁权 = 每个动作多一跳出网、且策略引擎病了整个循环陪葬。子票是**铸造时**就收窄到
  「这一趟唯一的工具」，验票闸本地验、fail-closed——权限的最小化发生在发牌时而不是
  用牌时。
- **业务上怎么选**：一次出工只干一件事 → 发窄票（发牌时最小化）；真需要多工具协同的
  单个动作 → 才考虑运行时裁权，但要给策略引擎配 fail-closed 缺省。宁可票多几张，
  不让一张票什么都干。

## 六、捣乱实验（必选）

**捣乱 A · 手拉一条越界任务，看铸票缝拒签：**

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST localhost:3003/internal/runs \
  -H 'content-type: application/json' \
  -d '{"kind":"hunt_task","hypothesis_id":"'$HYP'","task":{"tool":"isolate_host","params":{"host":"db-01"}}}'
sleep 2
sqlite3 "file:data/agent/agent.sqlite?mode=ro" \
  "SELECT kind, status, fail_reason FROM runs WHERE kind='hunt_task' ORDER BY created_at DESC LIMIT 1;"
```

实测：正门回 `{"error":"mint_failed"}` + `HTTP 502`；runs 表最新 hunt_task 行
`failed | mint_failed`。链条是：ticketSpecFor 发现 isolate_host 不在父票菜单
（INV-3 的 L2 高危件，本就进不去任何票面）→ 拒铸抛错 → 门把 run 标 failed（**不留无票
奔跑**）→ 502 回给调用方。**对比 9.2 捣乱 A 的菜单闸**：那次是 planner 选了越界工具被拦
在决策面，这次是直接把越界任务塞进铸票缝——两道闸各拦各的，这就是「绕过一道还有一道」
的亲手实证。

**捣乱 B · 不带任务直拉 hunt_task——窄票面兜底档：**

```bash
curl -s -w "\nHTTP %{http_code}\n" -X POST localhost:3003/internal/runs \
  -H 'content-type: application/json' -d '{"kind":"hunt_task","hypothesis_id":"'$HYP'"}'
```

实测：`202`（不带 task 上下文时，ticketSpecFor 返回**注册表菜单级兜底票面**
（[run-kinds.ts:336-337](soc-demo/services/agent/src/run-kinds.ts#L336) 注释口径——直拉/恢复
路径的旧口径），run 正常建）。这条子 run 跑起来 intake 会炸「簿记缺行」（它绕开了 launcher
的簿记路径）——**机制桩的 fail-closed 炸响**（task-flow.ts:38 的 throw），run failed。两个
结论：①宽进窄出——门不会替你造任务，但也不会给你一张大票；②簿记缺行=拉起路径非法，
炸响而不是猜。

## 场景题闯关（本步 1 题）

**Q：假设 dispatch 发一张「大票」（票面 = 全菜单并集）给两条子 run 共用，省了 N−1 次铸票。
用捣乱 A 的场景推一遍：这样省出来的东西，会在哪一步变成什么风险？**

<details><summary>答案（点击展开）</summary>

大票 = 每条子 run 都持有多路工具的授权。第一层：某条子 run 的 LLM 被上游数据带偏
（比如子报告里混进的话术），它想调**另一路**的工具——大票过闸全绿，越权在物理上畅通；
窄票下这是 verifyTicket 的 allowed_tools 拒绝（闸拒=DENIED+强杀）。第二层：票一旦泄漏
（900s TTL 内），大票泄漏的是整个菜单，窄票只泄漏一件事。第三层：审计归因——大票时代
「谁用了哪件工具」只能靠事后对账，窄票面让票面本身就是答案。**并行取证不并权**，省的
一次铸票买不来这三层。</details>

---

**本步收束**：dispatch 把 C₁ 折成 N 条独立 run（并行）；每条子 run 一张单工具窄票（不并
权）；越界任务死在铸票缝（INV-11 第二道闸实测）；子 run 的账（状态/预算/审计）全部独立。
**下一站 9.4**：父 run 怎么知道子 run 都跑完了——事件唤醒禁轮询的铁律，以及 judge 这个
「拍板的」怎么按 schema 裁决、怎么防合谋。
