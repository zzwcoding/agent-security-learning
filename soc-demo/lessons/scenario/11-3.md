### 站 2 · fake LLM 是"波表解释器"：族识别→查 waves→渲染参数

📍 大图节点:FAKE_LLM(11.3 内容层确定性三件套)

生产装配 [index.ts:196](soc-demo/services/agent/src/index.ts#L196) `makeHuntLoopLlm(LLM_MODE)`
在 fake 档接到内容层
[makeHuntFakeLoopLlm](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L140)
（[hunt-pack.ts:243-245](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L243)）。
它拆单只做三步（[hunt-pack.ts:146-168](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L146)）：

```ts
async planner(input) {
  const family = familyOfMenu(input.menu, families);       // ① 按菜单集合签名回族
  currentFamily = family;
  if (!family || family.waves.length === 0) { /* 机制默认档：单任务退化 */ }
  const waveIdx = input.gap
    ? Math.min(input.evidence_so_far.length, family.waves.length - 1)  // ② gap 换波
    : 0;
  const tasks = family.waves[waveIdx]!.map((w) => ({       // ③ 照波表出任务
    tool: w.tool,
    params: renderWaveParams(w.params, family),
    rationale: w.rationale,
  }));
  return { tasks, tokens: TOKENS_PER_CALL };
}
```

三步全是**通用解释逻辑**：族识别按菜单集合签名（[familyOfMenu:127-130](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L127)，
"只吃输入结构，不编造业务"的 fake 纪律）、轮次推进按 `gap 有无 + 已有证据数`、参数
按 [renderWaveParams:105-123](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L105)
做槽位直替（`{persistence}`→cron、`{time_window}`→卡上时间窗对象）。**ir 的四轮轨迹
没有一行专属代码**——票 80 实现记录原话："fake 轨迹纯靠模板 fixture 表达"。这就是
11.2 零增量闸在行为侧的对应物：机制不改、fake 也不改，改的只有数据。

judge 半边同理（[hunt-pack.ts:170-195](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L170)）：
证据充分性用确定性代理判据（有既往轮 + 本轮 ≥2 份子报告），verdict 取"hit 当且仅当
取证面报告 total>0"（[FORENSIC_TOOLS:95-100](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L95)
——剧本/图谱是导航面不参与裁决）；hit 半边附带卡上的遏制建议文本渲染
（[renderContainmentSuggestions:224-232](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L224)）。

## 三、服务与中间件卡

**卡 1 · ▼假设端到端布景（evals rig 形态，票 79④/80 扩展）**

- **它是什么**：`hunt_pack_e2e`（[hunting.ts:489](soc-demo/evals/src/rigs/hunting.ts#L489)）
  对四族各起一条独立布景：真 buildApp+真注册表+真验票闸+真执行体+真模板登记缝，假设面/
  LLM/register 用内容包假件，逐族断言轮次轨迹与收敛结论（ir 的断言在
  [hunting.ts:538-558](soc-demo/evals/src/rigs/hunting.ts#L538)，四轮工具序列逐轮钉死）。
- **市面替代**：等真 LLM 布景全链跑（慢、贵、不确定）；或只测模板字段存在性（假绿）。
- **为何这么选**：教学档 fake 是**生产同款解释器**（同一 `makeHuntFakeLoopLlm`，index.ts
  一行接的锁），它跑出的轨迹就是"数据→行为"的直接证明；轨迹逐轮钉死在 eval 里，
  任何人改 waves/改菜单，轨迹测试当场红——数据变更也有回归网。
- **业务上怎么选**：机制回归用机制默认档（S10 的 93 格矩阵）；内容轨迹用族布景逐族
  钉——两层布景各测各的，混用会把"数据错了"误诊成"机制坏了"。

## 场景题闯关（本步 1 题）

**Q：ir 卡 waves 轮 4 把 `graph_query` 的 params 从 `{entity:"{host}"}` 手滑写成
`{entity:"{hostnam}"}`（槽位拼错）——渲染函数会怎么处理？最终报告里图谱查的是什么？
这算数据 bug 还是机制 bug？**

<details><summary>答案（点击展开）</summary>

回看 [renderWaveParams:116-117](soc-demo/services/agent/workers/investigation/hunt-pack.ts#L116)：
槽位解析正则认出 `{hostnam}` 这个名字后查 `example_slots`，查无此键 → **原样保留字符串**
`"{hostnam}"` 作为参数值（槽位不炸、不猜、不兜底）。于是轮 4 图谱查询按字面量
`entity="{hostnam}"` 去查——查回 total=0（空结果），但取证面判据只看
outbound_conn_query 的 total（=3），**hit 判定不受影响**，假设照常 concluded。定性：
数据 bug（卡上的槽位拼写），不是机制 bug——机制照契约"查无槽位原样传递"运转正确。
防线在哪？逐族轨迹 eval 的 params 断言（`toMatchObject({ entity: "centos7" })` 级别）
会当场红——数据也有回归网，这正是站 3 卡里"数据变更也有回归网"的实义。</details>
