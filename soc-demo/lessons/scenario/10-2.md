## 一、操作（位置感）

这个演示跑在 **evals 的狩猎 rig**（[evals/src/rigs/hunting.ts](soc-demo/evals/src/rigs/hunting.ts)）
上。布景纪律要先说清楚（诚实标注）：它是**契约级复现**——真 `buildApp` + 真注册表组图 +
真验票闸 + 真签票假件（密钥与闸同门），假设面/LLM 换确定性假件，**不是 docker 栈**。
唯被测对象 = 「铸票面 → 验票闸」的票面语义，这正是本步的主题；真栈侧的对应动作（捣乱①）
会在第六节用 curl 打真门。

rig 的名字叫 `inv11_matrix`（[hunting.ts:137-262](soc-demo/evals/src/rigs/hunting.ts#L137)），
它一口气咬四件事（文件头注释即规格）：

1. **T13** 子票 scope ⊆ 父菜单，遍历 100%；
2. **T14** 每类任务 × 票面 scope 外工具 = 100% 403（工具全集取
   [fixtures/tools.manifest.json](soc-demo/fixtures/tools.manifest.json) 在册表，实测 32 件）；
3. TTL 过期票重放必拒（`token_expired`，INV-2 口径复用既有闸语义）；
4. 子票面永不含 L2（INV-3 沿父子 run 延伸）。

## 二、调用链

```
[真 buildApp + 真注册表组图] launchRound 轮 1 → fake LLM 两轮跑满（子任务覆盖全菜单）
  ▼
[铸票事实收集] 每枚子票的 wire 串存进 tokens 表（真签票假件记账）
  ▼
[遍历矩阵] for 每枚子票 × for 全仓 32 件工具 → verifyTicket 逐格裁决
  │        ├─ 票面内那 1 格 → allow（放行正控，同时证 run/case 绑定）
  │        ├─ 票面外 31 格 → 403 scope_insufficient（T14）
  │        └─ 再补一格：now = exp+1 的重放 → 403 token_expired
  ▼
[矩阵判定] 六条 extraChecks 逐格点名（防恒空假绿）
```

### 站 1 · 遍历的每一格都是真闸裁决

📍 大图节点:INV11_MATRIX(10.2 INV-11 遍历矩阵)

裁决函数不是模拟——它调的就是生产验票闸本体
（[hunting.ts:113-120](soc-demo/evals/src/rigs/hunting.ts#L113)）：

```ts
function verdict(ticket: string, runId: string, caseId: string, tool: string, nowSec?: number): {
  allow: boolean; code?: number; reason: string;
} {
  const v = verifyTicket({ name: tool, params: {} }, { ticket, runId, caseId }, nowSec ?? Math.floor(Date.now() / 1000), {
    hmacKey: KEY,
  });
  return v.allow ? { allow: true, reason: "allow" } : { allow: false, code: v.code, reason: v.reason };
}
```

闸本体（[verify-ticket.ts:211-224](soc-demo/services/agent/src/verify-ticket.ts#L211)）的裁决
顺序：验签 → `token_expired` → `token_used` → **`allowed_tools.includes(toolCall.name)` 否则
`scope_insufficient`**（[:220](soc-demo/services/agent/src/verify-ticket.ts#L220)）→ case/run
绑定不符也是 `scope_insufficient`（[:221-222](soc-demo/services/agent/src/verify-ticket.ts#L221)）。
矩阵的 93 格吃的就是 220 行这一条。而亮票→验票→执行→记账的四步舞，生产里由
[TERMS「闸体/闸」](TERMS.md)条的 `makeGatedCall` 拼装
（[gated-call.ts:66-97](soc-demo/services/agent/src/gated-call.ts#L66)），子 run 的真执行体
拿窄票作凭据进闸（[hunt-executor.ts:121-124](soc-demo/services/agent/workers/investigation/hunt-executor.ts#L121)，
`creds: () => ({ ticket: wiring.ticket, runId: wiring.runId })`）。

## 三、服务与中间件卡

**卡 1 · ▼INV-11 遍历矩阵（eval rig 形态，票 76）**

- **它是什么**：两票制的机器验证布景——真两票链路跑满，对每枚真铸子票做全工具遍历裁决，
  断言以 extraChecks 逐格点名进门槛。
- **市面替代**：抽样渗透测试（人工挑几个工具试）；或只在代码评审里"检查"票面。
- **为何这么选**：权限回归是典型"改一行松一道"的事——manifest 加工具、模板改菜单、闸改
  裁决序，都可能静默放宽。全遍历矩阵把"100%"变成可断言的数字，回归时红在具体哪一格。
- **业务上怎么选**：权限面小（<百格）→ 全遍历；面大了 → 分层抽样 + 对高危工具（L2/写类）
  保留全遍历。原则只有一个：**正控必须在场**（放行格与拒绝格都要有），否则"全 403"可能是
  闸坏死的假绿。

## 六、捣乱实验（必选）

**捣乱 ① · 伪造 scope 超宽子票——验票闸拒吗？（票面指定实验）**

分三层打，答案比直觉有意思。

**第 1 层（真栈）：把越界任务塞进铸票唯一通道——票根本出生不了：**

```bash
HYP=$HYP   # 10.1 的假设 id
curl -s -w "\nHTTP %{http_code}\n" -X POST localhost:3003/internal/runs \
  -H 'content-type: application/json' \
  -d '{"kind":"hunt_task","hypothesis_id":"'$HYP'","task":{"tool":"isolate_host","params":{"host":"db-01"},"rationale":"伪造超宽子票"}}'
sleep 2
sqlite3 "file:data/agent/agent.sqlite?mode=ro" \
  "SELECT substr(id,1,19), status, fail_reason FROM runs WHERE kind='hunt_task' ORDER BY created_at DESC LIMIT 1;"
curl -s "localhost:3002/api/v1/audit?objectId=$(sqlite3 'file:data/agent/agent.sqlite?mode=ro' "SELECT id FROM runs WHERE kind='hunt_task' ORDER BY created_at DESC LIMIT 1;")" \
  | python3 -c "import json,sys; [print(a['action'],'|',a['actor']['id'],'|',a['result'],'|',str(a['details'])[:80]) for a in json.load(sys.stdin) if a['action']=='kill']"
```

实测：门回 `{"error":"mint_failed"}` + `HTTP 502`；runs 最新 hunt_task 行
`failed | mint_failed`；kill 审计的 message 原文就是缝闸的抛错——
`hunt_task 子票拒铸：工具 isolate_host 不在父票菜单内（INV-11，铸票缝 fail-closed）`。
**伪造的第一要求是"有一张票"，这一层连票都没让它存在**（10.1 站 2 的 502 面在此对上号）。

**第 2 层（契约级）：假设窄票已在手，验票闸拒票面外的调用吗？——93 格的现场单格：**

```bash
cat > /tmp/verify-gate-demo.mts <<'EOF'
import { sealTicket, KEY } from "/Users/divh/Downloads/安全评估agent/soc-demo/services/agent/workers/triage/testkit.js";
import { verifyTicket } from "/Users/divh/Downloads/安全评估agent/soc-demo/services/agent/src/verify-ticket.js";
const iat = Math.floor(Date.now() / 1000) - 10;
const narrow = sealTicket({ jti: "tk_demo_narrow", sub: "agent:hunt_task", case_id: "", run_id: "run_demo_child",
  scope: ["case:read"], allowed_tools: ["siem_query"], iat, exp: iat + 900 });
const call = (t: string, tool: string) =>
  verifyTicket({ name: tool, params: {} }, { ticket: t, runId: "run_demo_child", caseId: "" }, iat + 5, { hmacKey: KEY });
console.log("窄票 siem_query  ->", JSON.stringify(call(narrow, "siem_query").reason));
console.log("窄票 isolate_host->", JSON.stringify(call(narrow, "isolate_host")));
EOF
cd services/agent && pnpm exec tsx /tmp/verify-gate-demo.mts
```

实测：`窄票 siem_query -> "allow"`；`窄票 isolate_host -> {"allow":false,"code":403,"reason":"scope_insufficient"}`。
这就是 93 格里的一格，逐格都是它。

**第 3 层（边界诚实话）：那"超宽票"本身，验票闸认得出来吗？——认不出，也不归它认。**

验票闸的裁决面里**没有"父菜单"这个知识**（[verify-ticket.ts:211-224](soc-demo/services/agent/src/verify-ticket.ts#L211)
只有签名/时效/焚毁/票面包含/run·case 绑定）——它裁的是"**持这张票能不能干这件事**"，
裁不了"**这张票面本身该不该这么宽**"。"宽"的执法者全在上游：planner 菜单闸（选不得，
10.3）→ 铸票缝（签不出，本步第 1 层）→ 注册表对账测试（票面 ⊆ manifest 被咬死）→
密钥边界（agent 进程不持 HMAC 密钥，INV-4——没有密钥，谁也自铸不出宽票）。七件事各归
各的闸，**绕过一道还有一道**：这正是「派工菜单」条"两道独立成立"口径的完整版。

## 场景题闯关（本步 1 题）

**Q：矩阵里 3 格"放行正控"为什么必须存在？把它删掉（只断言 93 格全 403），哪种真实的
闸故障会变成全绿？**

<details><summary>答案（点击展开）</summary>

闸坏死（fail-**open** 的镜像病：什么都拒）。verifyTicket 若因密钥读错/manifest 读不到而把
**所有**调用（含票面内的合法调用）都裁 403，93 格照样全 403——"拒绝一切"的坏闸和
"拒绝越界"的好闸在这条断言上不可区分。3 格正控（票面内工具必须 allow，且 run/case 绑定
同时被证明）把方向钉死：**该拒的拒了、该放的也放了**，才是这台闸在执勤。这也是 rig 把
`inv11_in_scope_allow` 列为六检查之一的原因——只有拒绝没有放行的权限测试，测不出
"松"，只测得出"死"。</details>
