# 50 · 压力也是一种异常：防线在压下——B5 收官实验

> 本篇是压测链（票 64-69）的收官教学文。前三问的答案（承压上限、瓶颈先出现在哪）在
> [压力测试报告](../docs/research/2026-09-12-压力测试报告.md)，本篇只讲第三问——**防线
> （fail-closed）在过载下松不松**：把安检员直接杀掉、把保安处整个关掉、拿并发写锤砸档案
> 室，系统应该作何反应。三个实验全部只走公开 HTTP 面，`docker kill` 一下你就知道。
>
> 术语卡：本篇比喻全部沿用 [TERMS.md](scenario/TERMS.md) 存量条目——安检员（guards）、
> 保安处（gateway）、档案室（case-backend/SQLite）、派活的（run-dispatcher）、手令/闸/
> 审批卡/一次性密令、留痕（audit）；首次遇到只回指不重解释。数字引自报告 B5 节与收尾章
> （Apple M4 × 10 核 · 16 GB，只同机比）。

## 一、这节做什么

**一句话**：前几节学的是"系统顺的时候怎么走"，这一节亲手把系统逼到逆风——**压力和故障
本身也是一种异常**，而这套系统对一切异常的回答应该是同一句话：**拒绝执行、留下记录、
等恢复**（INV-1）。

三个实验，每个对应一处"直接把一个组件按停"：

| 实验 | 捣乱动作 | 预期（fail-closed 的压下版） |
|---|---|---|
| ① 杀安检员 | `docker kill` guards 容器，压着 2 条/s 的持续告警流 | 压下窗内每个分诊 run 的不可信段都被拦下（审计 `guards_block`/DENIED 帧），**零一次"绕过扫描的成功出站"**；run 不挂死；恢复后行为如常 |
| ② 关保安处 | `docker compose stop` gateway，审批卡正等人批 | approve 吃 **502 mint_failed**：卡仍 pending（可重试）、run 仍挂起、审计零裁决痕迹——**不存在"已批准无票"的中间态**；无票的 run 走明确 failed(mint_failed)，不悬置 |
| ③ 砸档案室 | 并发写锤（1/4/16/64 连接）只打 REST 公开写口 | 全档零错误、写面平台 ~1.4-1.5k writes/s；**5s 忙等边界在默认拓扑的公开面上不可达**——这是结论不是失效 |

工具面：`scripts/bench/b5-*.mjs` 三个脚本 + `lib/b5.mjs` 断言判定器（离线单测锁定）。
断言失败 = 脚本非零退出——**"应看到什么"不是文档，是机器会咬人的断言**。

## 二、亲手验证（必选）

布景三实验各自独立轮次（down → 清 data → up 起跑，实验内只做容器级 stop/kill/start）。
fake LLM 零出网，数字可复现。

```bash
cd /Users/divh/Downloads/安全评估agent/soc-demo

# ① 杀安检员（全程约 5 分钟：压下态排干要 ~3 分钟，别急着 Ctrl-C）
docker compose down && rm -rf data && JIAOTU_GATEWAY_URL= JIAOTU_API_KEY= docker compose up -d
bash scripts/setup-openfga.sh
cd scripts/bench && node b5-guards-kill.mjs
# 应看到（三腿表 + 断言行）：
#   | 基线（guards 在位） | 24/24 | 26 | 26/0 | 0  | … | run P50 ≈ 431ms |
#   | 压下窗（guards 死亡）| 16/16 | 18 | 18/0 | 36 | … | run P50 ≈ 42.8s |
#   | 恢复（guards 就绪） | 24/24 | 26 | 26/0 | 0~1 | … | run P99 ≈ 2.4s |
#   **fail-closed 断言：全绿**
#   DENIED 帧 reason 集 = [guards_timeout]；"kill 后创建且窗内执行完 12"人均恰 3 帧

# ② 关保安处（约 2 分钟）
docker compose down && rm -rf data && JIAOTU_GATEWAY_URL= JIAOTU_API_KEY= docker compose up -d

# 应看到（五相位表）：

#   | C 压下·拉起   | run → failed（failReason=mint_failed）                              | 通过 |
#   | D 恢复·重批   | 先吃 1 个可重试 502 → 200，卡 approved+executed，run completed       | 通过 |

# ③ 砸档案室（约 1.5 分钟；注意本轮 EVENT_DRIVEN=off——不然每条写入都会拉起流水线）
docker compose down && rm -rf data && JIAOTU_GATEWAY_URL= JIAOTU_API_KEY= EVENT_DRIVEN=off docker compose up -d
bash scripts/setup-openfga.sh && cd scripts/bench && node b5-sqlite-hammer.mjs
# 应看到（四档表）：四行 5xx/超时/网络错 全 0；req/s 1250→1498→1441→1387（平台）；p99 4→14→29→96ms
#   5s 忙等水位线读数：全档 p99 未越过 5000ms——busy 超时边界在默认拓扑的公开面上不可达

# 收官对照表在报告收尾章：
cat ../../docs/research/2026-09-12-压力测试报告.md | grep -A6 "四天花板理论 vs 实测"
```

预期输出的三个"反直觉"，先打预防针：

1. **杀掉安检员，run 反而一个不少全 completed**——fail-closed 拦的是"不可信内容进
   prompt"（换占位符），不是"把 run 杀掉"。防线松没松看 **DENIED 帧**（安检员的拒检
   记录），不看 run 死没死。
2. **压下窗 run P50 42.8 秒**（基线 0.43 秒的 ~100 倍）——容器视角里被 kill 的容器是
   "黑洞"（连接发出去石沉大海），每段扫描烧满 2 秒超时，一个 run 要扫 3-7 段，再加上
   派活的串行排队。**防线不松的代价，由排干时间支付**。
3. **实验③零错误**——档案室只有档案室自己一个写手（前台和数字员工的写全走 REST 汇入
   同一进程），SQLite 的 5 秒忙等兜底防的是"第二个进程翻墙抢锁"，默认拓扑里那个人
   根本不存在。

## 三、捣乱实验（必选）

上面三个就是本节的捣乱实验本体，这里只补三个"捣乱时顺手发现"的边角，都是真跑出来的：

- **捣乱 A 的时序坑：归因看执行时刻，不看到达时刻**。首跑把"压下窗创建的全部 run"当
  断言集 → 复绿后才排干执行的 run 零 DENIED 帧，被误判"绕过扫描"（机器当场红了，正是
  断言该干的事）。正确口径：**kill 后创建且窗内执行完**的 run 必须带 DENIED 帧；kill
  前创建的（扫描可能赶在杀掉之前跑完）和跨恢复执行的，零帧是合法读数。口径已钉进
  `lib/b5.mjs` 判定器与单测。
- **捣乱 B 的复活坑：healthz 绿 ≠ 扫描就绪**。`docker start` 后 healthz 秒绿，但安检员
  冷启动装载 llm-guard/Presidio 模型，头几扫可能超时被拒（实测恢复窗 1 帧 DENIED）。
  恢复判定要用**双闸**：healthz 绿 + 首次真扫描成功。恢复窗偶发 DENIED 不是防线失守——
  是 fail-closed 对"慢"的保守裁决（拒而非放行）。
- **捣乱 C 的复活坑：死 keep-alive**。保安处复绿后的第一笔铸票可能撞上停机期留下的死
  连接，再吃一个 502——卡照旧 pending，重试即成（200 → resume → completed）。恢复腿
  的脚本对每次 502 都复核"卡没被动过"：**可重试不是脚本宽容，是断言的一部分**。

## 四、为什么这样设计（fail-closed 语义）

- **"拒绝执行"是一个动作，不是一个状态**。安检员罢工时，triage 的扫描函数返回
  `blocked=true`——不可信段换成占位符、审计落一条 DENIED（`reason=guards_timeout`），
  run 继续往下走。对比另一种设计"扫描挂了就放行/就跳过"：那不是降级，是把 INV-1 整条
  拆了。宁可贵（排干分钟级），不可骗（原文进 prompt）。
- **"先铸票后裁决"的时序就是防线本身**（实验②的全部秘密）。批准端点先找保安处铸
  一次性密令、铸失败立刻 502 早退——裁决这步在票不存在时**根本不发生**，所以
  "已批准无票"不是被代码防住的，是**在结构上不存在的状态**。和 KB 那节同一条定理：
  安全不变量最好的实现不是"记得检查"，是"别的路根本不存在"。
- **每个失败都停在可重试的稳定点上**。502 之后卡 pending（等保安处回来再批）、run
  awaiting_approval（挂起可观察）、无票 run 直接 failed(mint_failed) + FAILURE 强杀
  审计（可观察可重拉）——没有一种失败会产生"半吊子状态"。fail-closed 给的不是
  "永不失败"，是"失败之后系统仍处于一个诚实的、可继续的状态"。
- **留痕让"拒绝"可审计**。36 条 DENIED 帧就是 36 次"安检员不在岗但拒检照记"——事后
  你能精确回答"压下那三分钟里每一条告警的不可信段被拦了几次、什么原因"。不记留痕的
  拒绝等于没拒绝（你无法区分"拦下了"和"没发生"）。
- **兜底机制要在位，更要知道它防谁**（实验③的教学点）。SQLite `busy_timeout=5000`
  防的是跨进程写者抢锁；默认拓扑里写手只有一个，所以 5 秒水位线在公开面上**不可达**。
  "未触发=服务健康"和票 68 的 shedding 一个读法：保险丝没烧断是好事，但你得亲手验证过
  它真的会跳（票 68 机制演示档 503 真出现 + 服务存活 + 压后恢复）。

## 五、场景题

<div>

**第 1 题**：把实验①的 `docker kill` 换成 `docker pause`（挂起进程、容器仍 running），
DENIED 帧的 `reason` 会从 `guards_timeout` 变成什么？压下窗 run 的延迟会怎么变？
为什么本实验选 kill 不选 pause？
<details><summary>对照</summary>

reason 仍是 `guards_timeout`——pause 下连接被挂起、出站 fetch 同样烧满 2 秒超时
（`guards-client.ts` 的超时分支）；变化的是宿主探针：kill 时宿主侧是 ECONNREFUSED
（毫秒拒接），pause 时宿主侧连接也挂起。选 kill 是因为它是**真实故障形态"进程崩溃"**，
且 compose 无 restart 策略（`RestartPolicy=no` 实测），容器停在 exited、恢复动作显式
可控；pause 更像"人为吊住"，排障语义（不通 vs 慢）不同——`outbound.ts` 的口径注释
说得清楚：超时是"慢"，不可达是"不通"，两条排查路径。</details>

**第 2 题**：实验②里，如果按铃approve 的同时另一个值班长也在批同一张卡（gateway 活着
时），后到者会怎样？结合"先铸票后裁决"，说说为什么后到者白铸的那枚票不构成安全问题？
<details><summary>对照</summary>

后到者吃 409（审批状态机先到先得，`decideApproval` 事务仲裁）；他在裁决**前**也各自
铸了一枚一次性密令，但裁决没轮到他 → 票从未落卡、没人执行，且密令 300 秒自焚。
不安全的从来不是"多铸一枚票"，是"裁决与执行之间票可被复用"——一次性语义（用后即焚 +
执行过的卡不再授权第二次）把这两条都钉死了。实验②证明的是更极端的情形：连铸票都失败
时，裁决与执行同样一个都不会发生。</details>

**第 3 题**：三个实验里系统都"拒绝"了，但拒绝的**对象**各不相同。请分别说出：①②③
各自拒绝的是什么？各用哪条观察口证明"拒绝确实发生了"？
<details><summary>对照</summary>

①拒绝的是**不可信内容进 prompt**——观察口是审计 `guards_block`/DENIED 帧（36 帧、
reason 合法集、人均恰等于必扫段数 3），外加 run 照常 completed（拒内容不拒流程）；
②拒绝的是**无票的授权与执行**——approve 502 且卡/run/审计三处零变化（"已批准无票"
在结构上不存在），无票 run 明确 failed(mint_failed) + FAILURE 审计；③"拒绝"的对象
其实没出现——写面根本没到忙等边界，这题的答案是**诚实**：实测给出的是吞吐平台
（~1.4-1.5k/s）与延迟陡升（p99 96ms@C=64），5s 水位线读数是"未越过"，未触发 ≠ 失效。
三题合起来：fail-closed 的观察口永远是**留痕**（审计帧、状态机终态、分类后的错误面），
不是"感觉系统还活着"。</details>

</div>

## 六、下一步

- **收尾对照表**：报告收尾章把四个理论天花板 vs 实测值摆成一张表（分发循环 ~10 run/s
  理论 vs 4.6-4.8 实测、缺口全在 tick 内串行执行；autorun 2s tick 消费恒 1-2 tick
  追平、消费不是瓶颈；SQLite 5s 忙等在位但公开面不可达、平台 ~1.4-1.5k/s；SSE 200
  订阅者延迟零劣化、每订阅者 ~0.1% CPU）——**四个天花板压到底没有一处"崩"，全是
  "排队"和"拒绝"**。
- **可复跑**：`scripts/bench/b5-*.mjs` 三个脚本每步独立轮次可一键复现（复现命令见
  报告"复现（一键）"节的 B5 三行）；`npm test` 里 b5 判定器的离线单测把"什么算绕过、
  什么算合法跨窗"钉死，改断言语义先改测试。
- **留观与扩展**：guards 冷启动就绪窗（healthz 绿 ≠ 扫描就绪）目前靠双闸探测兜住，
  若要产品化可考虑 guards 自带 readiness 口（需开票，本票零新增端点）；`RUN_DISPATCH`
  调大并发领单是逼近理论 10 run/s 的正路（B3 拆过账），但上限仍受 SQLite 单写者约束
  ——留作下一轮压测的开场问题。
- **布景零损失**：三实验做完记得按脚本头注把栈 down → 清 data → up + setup-openfga
  + replay 12 条告警基线，教学线布景复原。
