# 阶段 3:语法门卫(llm_helper 的第一块砖)

## 一、三问(阶段动机)

**这一阶段是干嘛的**:给 write_file 加第二个门卫——写的是 `.py` 代码的话,
先查语法,语法不对就不让落盘。

**为什么需要**:以后写代码的主要是 AI,而 AI 经常生成语法就通不过的代码。
没有这道闸,坏代码会先写进 workspace,等你(或 AI 自己)运行它时才发现——
多绕一圈,还污染了工作区。把检查提前到"落笔之前",坏代码根本进不了门。

**解决了什么问题**:把"运行时才发现语法错"提前成"写入时就拦下",
而且报错带行号,AI 拿到能直接改。

## 二、全链路一览

```
python cli.py write counter.py "..."
  → cli.py
  → write_file()
  → 门卫 1 _resolve        路径在不在 workspace?(阶段 2 已有)
  → 门卫 2 verify_code_syntax   后缀是 .py 吗?是 → 查语法
  → 磁盘                   两道门卫都过了,才落笔
  → 结果 JSON 里多一个字段:verification = passed / failed / skipped
```

## 三、跟着数据走 3 步

拿捣乱的 `def broken(:` 走一遍:

1. **进来时**:它是 write 的 content 参数,目标文件 `broken.py`。
2. **过门卫 2**:后缀是 `.py`,送 `compile(code, "<string>", "exec")`。
   Python 编译器只"读题"不"做题"——发现括号没合上,抛 SyntaxError,
   还附带"第 1 行"这个信息。
3. **被拦下**:write_file 收到 `(False, "第 1 行: invalid syntax")`,
   返回 `{"success": false, "error": "语法错误: 第 1 行: invalid syntax", "verification": "failed"}`。
   实跑验证:workspace 里自始至终没有 broken.py。

对照组:合法代码 → `"verification": "passed"`;普通文本(.txt)→ `"skipped"`,不挡路。

## 四、新技术点:compile()

- **名字**:`compile`,Python 内置函数(不用 import)
- **作用**:把源码字符串编译成代码对象,但**不执行**。我们借它当免费的语法专家——
  语法有错它抛 SyntaxError,语法没错就安静通过。不需要 AI、不需要网络、不花一分钱。
- **参数**:`compile(source, filename, mode)`
  - `source`:要检查的代码字符串
  - `filename`:只是报错信息里显示的名字,传 `"<string>"` 表示"这不是个真文件"
  - `mode`:`"exec"` 表示这是一整段代码(另有 `"eval"` 用于单个表达式,我们用不上)
- **用法**(本项目 `llm_helper.py:17`):

```python
try:
    compile(code, "<string>", "exec")   # 语法错就抛 SyntaxError
except SyntaxError as e:
    return False, f"第 {e.lineno} 行: {e.msg}"   # e.lineno 是出错行号
```

## 五、关键顿悟

- **能查证的就不用 AI**:语法对不对是"有标准答案"的事,编译器自己就是权威,
  又快又免费。AI 要留给"没有标准答案"的判断(比如"这段代码意图危险吗")——那是阶段 6 的事。
- **门卫有顺序**:先查"在哪写"(边界),再查"写什么"(语法)。顺序反了,
  等于替越界路径里的文件白做检查。
- **结果里写明"查没查"**:`verification: passed / failed / skipped` 三个值,
  让调用方(将来的 AI)知道这份文件到底过没过检,而不是含糊的成功。
