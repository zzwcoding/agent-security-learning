# 阶段 9:file_edit + 覆盖审批(法官开始管"写")

## 一、三问(阶段动机)

**你在整盘棋的哪一步**(终极目标:给 AI 助手用的工具,每个进门先安检):

```
✅ 阶段 2-3   写文件工具:边界 + 语法
✅ 阶段 4-6   跑命令工具:筛子 + 法官
✅ 阶段 7-8   跑代码工具 + 长输出瘦身
👉 阶段 9     法官管到"写":覆盖审批 + 搜索-替换编辑——本阶段(回到安全主线)
⬜ 阶段 10-12 demo 串烧;换回 agent 身上做攻击前后对比
```

**这一阶段是干嘛的**:两件事——① write_file 覆盖**已存在**的文件时,要送 LLM 法官审批;
② 新增 edit_file:搜索-替换式精确编辑。

**为什么需要**:之前法官只管"执行"(跑命令、跑代码)。但"写"同样能闯祸——
覆盖一个已有文件,旧内容一去不回,破坏力不输 `rm`。闸不该只管动作类型,该管**后果**。

**解决了什么问题**:不可逆的写操作有了法官过目;同时 AI 改文件有了"手术刀"(edit),
不用每次整页重盖(write)——改一行和重写整个文件,风险完全不是一个量级。

## 二、全链路一览

```
write_file(覆盖场景)
  → 边界闸 → 文件已存在? → 是 → 法官审批 file_overwrite → 批了才覆盖
edit_file(新工具)
  → 边界闸 → 文件存在? → old_text 一字不差地在文件里?
  → 替换 → 改完是 .py? → 再过语法闸 → 落盘,报告替换了几处
```

## 三、跟着数据走 4 个案子(全部实跑)

1. **精确编辑**:`edit hello.txt "你好" "您好"` → 替换 1 处成功。✅
2. **意图对不上现实**:`edit hello.txt "不存在的内容" "x"` → 拒:"没找到要替换的原文"。
   AI 想象中的文件内容和磁盘上的不一致时,宁可失败也不瞎改。✅
3. **覆盖审批(无 key)**:`write hello.txt ...` 覆盖已有文件 → fail-closed 拒。✅
4. **覆盖审批(有 key)**:法官**也拒了**!理由很到位:"覆盖有数据丢失风险,
   没看到旧内容、没有备份机制,无法判断是否安全"。✅(而且揭示了重要一课,见顿悟 2)

## 四、关键顿悟

(本阶段无新 API——都是已学零件的组合;新东西是**设计决策**:按"后果可不可逆"
决定要不要审批,而不是按"哪个工具"。)

- **闸管的是后果,不是动作类型**:覆盖已有文件和 `rm` 一样是"闯祸级"操作,
  所以写文件也要有法官。判断要不要审批,问的是"这步错了能不能挽回"。
- **法官只能审你给的案情**:覆盖被连拒,因为我们只发了"路径+新内容长度",
  法官看不到旧文件内容、看不到 diff——它只能往最坏想。**审批质量取决于你递的材料**;
  想让合理覆盖能过,就得把旧内容摘要或 diff 一起递给法官(参考项目同样没做,通病)。
- **edit 让意图显式化**:write 是"我说整页是什么样",edit 是"把 A 换成 B"——
  后者自带定位锚点,AI 对文件内容的想象和现实不符时当场失败,而不是静默写坏。
- **语法闸复用到 edit**:改完的代码也要过闸——改之前合法不代表改完还合法
  (实跑:把 `return len` 改成 `return len(` 被当场拦下,括号没合上)。
