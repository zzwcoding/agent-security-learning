# 阶段 2:workspace 边界(file_tools + CLI 骨架)

## 一、三问(阶段动机)

**这一阶段是干嘛的**:做出第一个"带门卫"的工具——往 workspace 目录里写文件,
并给它配一个命令行入口(cli.py)。

**为什么需要这么个设计**:你以后会让 AI 替你操作文件。AI 可能被忽悠(提示注入),
写出 `../../../../etc/xxx` 这种路径。所以真正落笔之前,必须先有个门卫确认:
"这个路径真的在我管的院子里吗?"

**解决了什么问题**:starter-agent 里的老门卫有漏洞——它只看路径字符串的**开头**
(`startswith`)。好比门卫只核对"你报的地址是不是以'幸福小区'开头",
那"幸福小区北街8号"也能混进去,可那根本不是这个小区。新门卫改成逐层核对门牌号。

## 二、全链路一览

```
你在终端敲:python cli.py write hello.txt "你好"
  → cli.py          负责读懂你敲的命令,把参数递给工具
  → write_file()    工具本体,管写文件
  → _resolve()      门卫:先算真实地址,再查在不在院子里;不在就拒
  → 磁盘            只有过了门卫,才真正落笔
  → 屏幕打印 JSON   把"成了/没成、为什么"告诉你
```

## 三、跟着数据走 3 步

拿故意捣乱的 `../escape.txt` 走一遍:

1. **进来时**:它就是个普通字符串,意思是"往上一级目录写 escape.txt"——想翻墙。
2. **过门卫时**:`resolve()` 把 `..` 这种绕路写法换算成真实地址。一换算就露馅:
   落点是项目根目录,根本不是 workspace。
3. **被拦下**:门卫发现地址不在院子里,直接拒。返回一张纸条:
   `{"success": false, "error": "路径越界: ../escape.txt(只允许写 workspace/ 内)"}`
   磁盘从头到尾没被碰一下(实跑验证过,escape.txt 哪儿都没出现)。

## 四、新技术点:Path.relative_to

- **名字**:`Path.relative_to`,Python 标准库 pathlib 里的方法
- **作用**:回答一个问题——"这个文件路径在某个目录**里面**吗?"
  在,就正常返回;不在,就报错(ValueError)。我们的门卫就是它。
- **参数**:只有一个——"参照目录"。
- **用法**(本项目 `file_tools.py:14`):

```python
p = (WORKSPACE_DIR / path).resolve()    # 先把用户给的路径换算成真实地址
p.relative_to(WORKSPACE_DIR.resolve())  # 再问:它在 workspace 里吗?不在就抛错
```

**为什么不用 startswith?** startswith 是"比文字开头":`/workspace-evil/x.txt`
的开头确实是 `/workspace`,会被误判成"在院子里"。relative_to 比的是路径
**一级一级的组成**,假前缀骗不了它。

## 五、关键顿悟

- **先换算真实地址,再做判断**。不 `resolve()` 就检查用户给的原始字符串,
  `..`、符号链接这些"绕路写法"全是空子。
- **门卫不掀桌子,只递纸条**。拒绝时返回 `{"success": false, "error": "..."}`
  而不是让程序崩溃——因为将来读这个结果的是 AI,它得看懂"为什么不行",
  才能跟你解释、或者自己换个方案。
- **CLI 只是第一个用户**。工具代码自己不依赖 cli.py,以后 MCP server 会原样
  复用同一份工具——"同一套工具,换壳不换芯"是刻意的设计。
