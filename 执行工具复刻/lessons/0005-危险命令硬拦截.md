# 阶段 5:危险命令硬拦截(黑名单筛子)

## 一、三问(阶段动机)

**你在整盘棋的哪一步**(终极目标:给 AI 助手用的工具,每个进门先安检):

```
✅ 阶段 2-3   写文件工具:能写,且有边界+语法两道闸
✅ 阶段 4     跑命令工具:能跑,暂无闸
👉 阶段 5     装第一道安检:危险命令黑名单,命中直接拒——本阶段
⬜ 阶段 6     装第二道安检:可疑命令送另一个 AI 审批(救回误伤)
⬜ 阶段 7-9   跑代码工具、长输出截断、文件编辑
⬜ 阶段 10-12 换回 agent 身上:同一个攻击,裸奔版闯祸、带闸版被拦
```

**这一阶段是干嘛的**:给跑命令工具装第一道工序——一张危险命令黑名单
(`rm -rf`、`mkfs` 这类),命令里出现就当场拒掉,不执行。

**为什么需要**:阶段 4 的工具是裸奔的,`rm -rf` 说跑就跑。黑名单是**最便宜**的防线:
不联网、不花钱、瞬间出结果,先把"明抢的"挡住。

**解决了什么问题**:已知危险的命令有了确定性拦截。但实跑暴露了它的两个死穴
(见下面第四节)——这正是下一阶段存在的理由。

## 二、全链路一览

```
python cli.py shell "..."
  → cli.py
  → virtual_terminal()
  → 黑名单筛子          命令里含危险子串吗?
       ├─ 命中 → 直接拒,{"success": false, "error": "命中危险命令模式..."},子进程压根不起
       └─ 未命中 → subprocess.run 照常执行(阶段 4 的老路)
```

## 三、跟着数据走 4 步(全是实跑记录)

1. **正常命令** `ls` → 不含黑名单子串 → 照常执行,列出 workspace 内容。✅
2. **明抢的** `rm -rf /tmp/xxx` → 命中 `"rm -rf"` → 拦截,未执行。✅ 该拦的拦住了。
3. **误伤** `echo 注意:rm -rf 这个参数很危险` → 只是**谈论**危险命令,
   但字符串里含 `"rm -rf"` → 照样被拦。❌ 好人被当成坏人。
4. **绕过** `rm -r /tmp/xxx`(故意不带 f)→ 不含 `"rm -rf"` 这个子串 → 放行了!
   ❌ 坏人换个写法就混过去了。(这条实跑只是因为目录不存在才没删成。)

## 四、新概念:黑名单(denylist)

- **名字**:黑名单 / denylist(安全领域通用术语,对应词:白名单 allowlist)
- **作用**:列一张"已知坏人名单",在名单上的就拦。类比:小区门口的通缉照片墙。
- **参数**:我们的实现就是一张字符串列表 + 子串匹配
  (`execution_tools.py:11-12`),命中即拒。
- **用法/局限**:优点是零成本零延迟;局限就是上面第 3、4 步——
  它**看不懂上下文**(分不清"执行 rm -rf"和"谈论 rm -rf"),
  也**认不出变体**(名单上没写的写法照过)。

## 五、关键顿悟

- **黑名单只能防"已知的、老实写法的"坏**:它防的是"明抢",防不了"乔装"。
  所以参考项目把它定位为**筛子**,不是法官。
- **误伤和下漏是同一个根因**:子串匹配只认字不认意。想减少误伤就得"看懂这句话想干嘛"
  ——这活儿规则干不了,得 LLM 干。这就是阶段 6。
- **两道闸防的是两种坏**:黑名单防"已知坏、量大、要快";LLM 审批防"灰色地带、
  需要判断"。少了任何一道,要么误伤满天飞,要么慢且贵。
