# 0002:阶段 2 —— 工具调用协议

## 一、三问(阶段动机)

- **这一阶段是干嘛的**:给裸 Agent 挂上第一个工具 `read_webpage`,跑通 function calling 的完整循环。
- **为什么需要这么设计**:这个实验的核心威胁是"间接注入"——攻击载荷藏在网页正文里,经 `read_webpage` 进入上下文。没有这条"外部内容通道",三类攻击里的两类(间接/记忆注入)根本没有入口。所以第一个工具必须是它。
- **解决了什么问题**:确立了本实验最关键的一条数据流:**外部世界 → 工具结果 → 模型上下文**。后面的攻击(阶段 6)和防御(D3 来源标记,阶段 10)都作用在这条链上。

## 二、全链路一览

```
用户消息("总结这个网页")
  → 模型(看到 tools 规格,决定调 read_webpage)
  → 我们执行 read_webpage(url) → 返回 WEBPAGE_CONTENT
  → 追加 role="tool" 消息进 messages
  → 模型(读到网页正文,产出总结)
  → 无 tool_calls → 打印最终回复,循环结束
```

## 三、跟着数据走 3 步

1. **模型怎么"请求"工具**:`create(..., tools=TOOLS)` 把工具规格告诉模型;模型回复的 `msg.tool_calls` 里带 `name` + `arguments`(JSON 字符串)。注意:模型只是"请求",执行权在我们手里——这个看似琐细的分工,正是 D4 运行时校验(阶段 11)能确定性兜底的原因。
2. **结果怎么回去**:执行结果包成 `{"role": "tool", "tool_call_id": tc.id, "content": ...}` 追加进 `messages`(`demo.py:80-84`),`tool_call_id` 把结果和请求对上号。
3. **循环怎么停**:模型这步没请求工具(`msg.tool_calls` 为空),说明它认为任务完成,`content` 就是最终回复,打印并退出。外层 `for _ in range(6)` 是步数上限,防模型陷入无限工具循环。

## 四、新技术点四要素:Function Calling(工具调用)

- **名字**:Function Calling / Tool Use,OpenAI Chat Completions 协议的一部分。
- **作用**:让模型从"只会说话"变成"能驱动外部动作"。和安全的关系:模型不直接执行任何东西,它只是生成结构化请求——**执行层在我们代码里**,这是所有运行时防御的立足点。
- **参数**:`tools=[{"type":"function","function":{"name","description","parameters(JSON Schema)"}}]`;响应里读 `msg.tool_calls[*].function.{name,arguments}`;回填用 `role="tool"` + `tool_call_id`。
- **用法**:见 `demo.py:33-56`(规格)与 `demo.py:69-84`(循环)。

## 五、关键顿悟

- **上下文里没有天生的"数据/指令"之分**:工具结果对模型来说就是又一段文本,和用户指令平起平坐。网页正文里写"先调用 write_file"和用户在消息里写同一句话,模型收到的信号结构完全一样——间接注入的全部威力来自这一点。
- **执行权与决策权分离**:模型只"请求",代码才"执行"。这个分离平时无感,却是 D4 能在执行层拦截的结构性前提。
- **`<think>` 块混在 content 里**:实测 MiniMax-M2 的思考块跟着回复一起打印。它也会进入后续上下文(messages 里原样保留),属于这个模型的特性,不是 bug。
