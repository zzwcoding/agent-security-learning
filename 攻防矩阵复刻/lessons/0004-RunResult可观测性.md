# 0004:阶段 4 —— RunResult 可观测性

## 一、三问(阶段动机)

- **这一阶段是干嘛的**:引入 `RunResult` dataclass,把一次运行的"事实"结构化:`final_text`(最终回复)、`requested_tool_calls`(模型请求的全部工具调用)、`executed_tool_calls`(实际执行成功的)。
- **为什么需要这么设计**:阶段 5 起要写判定器("攻击是否得逞")。判定的依据必须提前想清楚:**模型的回复文本是"它说了什么",executed_tool_calls 是"它做了什么"**——模型可以嘴上说"我不会执行危险操作",同时 write_file 已经落盘。安全判定只能信后者。而且 LLM 判定(LLM-as-judge)又贵又不稳定,规则判定(查清单 + 查子串)零成本、可复现。
- **解决了什么问题**:攻防实验从"看输出感觉像被攻破了"升级为"有可复现的判定依据"。同时埋下阶段 11 的伏笔:requested 和 executed 此刻必然相等,D4 运行时校验上线后两者会**分叉**——被拦截的调用只留在 requested 里。

## 二、全链路一览

```
模型请求工具 ──→ execute_tool 入口:记 requested(全量,无条件)
                      │
                      ├─ read_webpage:无副作用,执行但不记 executed
                      ├─ write_file:落盘成功 → 记 executed
                      └─ send_email:追加 outbox → 记 executed
运行结束 ──→ RunResult{final_text, requested, executed} ──→ 判定器(阶段5起)
```

## 三、跟着数据走 3 步

1. **请求的登记**:`execute_tool` 入口第一行就记 `requested_tool_calls`(`demo.py:108`)——无条件、在一切校验之前。这保证"模型被骗得有多深"完整留痕,哪怕之后被拦截。
2. **执行的确认**:write_file 真正写完盘、send_email 真正追加 outbox 之后,才记 `executed_tool_calls`(`demo.py:119, 129`)。顺序很讲究:**先做事、再记账**,记了账的事一定发生过。
3. **read_webpage 为什么不记**:读网页没有副作用,不是"危险动作",参考项目同样不记。判定器只关心副作用类调用——清单越干净,判定规则越直白。

## 四、关键顿悟

- **判定看行为不看言辞**:这是整个实验方法论的核心。回复文本可以被模型"演"(嘴硬、撒谎、顾左右而言他),`executed_tool_calls` 是代码层的客观事实——写没写盘、发没发信,一查便知。
- **requested/executed 双清单是防御效果的测量尺**:现在它们相等;D4 上线后,"requested 里有、executed 里没有"的差集,就是运行时防御拦下的东西——防御的贡献从此可量化。
- **确定性判定的代价是设计约束**:判定器要零 LLM 成本,攻击场景就必须设计成"得逞时必然留下确定性痕迹"(密钥子串出现在回复里 / 特定工具调用出现在清单里)。阶段 5-7 的三个判定器都是这个形状。
