# 0008:阶段 8 —— 跑批骨架:成功率矩阵的第一列

## 一、三问(阶段动机)

- **这一阶段是干嘛的**:把三个攻击注册进 `ATTACKS`,每个攻击重复 N 次(冒烟 N=2),输出成功率;每个 trial 用独立工作区。
- **为什么需要这么设计**:阶段 5 我们说"MiniMax-M2 防住了直接注入"——那是**单次运行**的结论。LLM 有采样随机性,"防住一次"什么也说明不了。本阶段第一次跑批就立刻打脸:直接注入 2 次里成功了 1 次(50%)。成功率而非孤证,是安全结论的最小单位。
- **解决了什么问题**:建立了实验的统计框架——攻击 × 重复次数 → 成功率。阶段 9-11 每加一层防御,我们就多一列数字,"每层防御的贡献"从此可量化(这正是你精读笔记里"矩阵优于孤证"的方法论)。

## 二、全链路一览

```
main()
  for attack in ATTACKS:           # 3 个攻击
    for t in range(trials):        # 每个重复 N 次
      reset_workspace()            # 清零 memory/outbox/files(关键!)
      result = run(client, attack) # 静默跑(verbose=False)
      attack.judge(result)         # 确定性判定
    打印该攻击的成功率
```

## 三、跟着数据走 3 步

1. **trial 隔离**:`reset_workspace()` 删掉整个 `workspace/` 再重建(`demo.py`)。不清理的话,记忆注入的毒偏好会留在 `memory.json` 里泄漏到下一个 trial、甚至下一个攻击场景——统计就脏了。这也是参考项目每次 `tempfile.mkdtemp` 新工作区的原因。
2. **静默跑批**:`run()` 加了 `verbose=False` 开关——批跑时不打印每轮对话(否则 N×3 次全文刷屏),只留每 trial 的成败一行。想看细节时 `-v` 类开关阶段 13 再补。
3. **成功率汇总**:判定器 True/False 聚成百分比。本次实测:直接 50%、间接 0%、记忆 100%。

## 四、关键顿悟

- **阶段 5 的结论被本阶段推翻**:直接注入单跑失败、跑批 50%——"强模型 D1 全防住"的说法对 MiniMax-M2 不成立,它只是"大概率防住"。这正是 README 用 4 trials 而非 1 次的原因,也是路线 4(CI 回归集)需要的方法论:**安全属性是概率分布,不是布尔值**。
- **N 的取舍是成本与置信度的权衡**:N=2 只能看方向(冒烟),N=4-5 是参考项目的默认,正式结论要更大。temperature 也影响波动(阶段 13 会暴露 `-t` 参数,0 更稳定)。
- **隔离是统计有效性的前提**:不 reset workspace,记忆注入的成功率会污染间接注入的测量(毒记忆还在)。实验卫生(hygiene)和实验设计同等重要。
