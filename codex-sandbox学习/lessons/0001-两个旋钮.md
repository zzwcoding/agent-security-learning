# 阶段 1：两个旋钮 —— sandbox ≠ approval

> 信源：[backgrind.com/blog/codex-cli-sandbox-modes](https://backgrind.com/blog/codex-cli-sandbox-modes/)（验证版本 `@openai/codex` 0.146.0）

## 一、三问（阶段动机）

**这一阶段是干嘛的？** 建立整个课程唯一最重要的心智模型：Codex 的权限不是"一个开关"，而是**两个独立的旋钮**。

**因为什么需求需要这么设计？** 终端 agent 会替你执行 shell 命令。要管住它，其实要回答两个不同的问题：

1. 命令跑起来之后，它**物理上能做什么**？（能不能写盘、能不能联网）
2. 当 agent 想做**超出当前能力**的事时，**流程上怎么办**？（问你，还是直接拒绝）

**解决了什么问题？** 如果把这两件事混成一个"权限开关"，就会出现全网最常见的错误理解：以为 approval 提示就是安全边界。但 approval 提示是可以被模型绕着走的（换种方式请求、拆成多步），而问题 1 是**内核强制**的——模型无法跟内核讨价还价。分开设计，才能让"真正的安全边界"（旋钮 1）和"人机交互体验"（旋钮 2）各自调优。

## 二、全链路一览

一次命令从模型嘴里说出来，到真正被执行，走的是这条路：

```
模型提议命令: "rm -rf ./build"
      │
      ▼
┌─────────────────────────────┐
│ 旋钮1 Sandbox Mode          │  ← 内核强制:命令【能做】什么
│ read-only / workspace-write │    违反就是 syscall 级 EPERM
│ / danger-full-access        │    模型无法争辩
└─────────────────────────────┘
      │ 命令被沙箱挡住时
      ▼
┌─────────────────────────────┐
│ 旋钮2 Approval Policy       │  ← 流程决策:被挡后【怎么办】
│ untrusted / on-request      │    问你 → 你放行就越沙箱执行
│ / never                     │    不问 → 失败回喂给模型
└─────────────────────────────┘
      │
      ▼
  执行 或 拒绝(失败信息返回给模型,模型自行适应)
```

一句话记住：**沙箱负责"停住命令"，审批策略负责"停住之后是问你还是告诉模型不行"。**

## 三、跟着数据走：一个越权写盘的完整旅程

以"agent 想往可写目录之外写文件"为例（对应源码 `codex-rs/core/src/safety.rs` 的判定逻辑）：

1. **模型产出工具调用**：一条 shell 命令，比如 `echo hacked > ~/.zshrc`。此时它只是文本，什么都没发生。
2. **进入 safety 判定**：Codex 拿当前生效的 (sandbox_mode, approval_policy) 组合来裁决。比如 `read-only` + `on-request`。
3. **沙箱判定"不能"**：`~/.zshrc` 不在任何可写根内，read-only 下所有写路径在 syscall 层就会失败。
4. **审批判定"怎么办"**：`on-request` → 给你弹一个提示。你点"同意"，这条命令就**在沙箱外**执行，写入成功；你点"拒绝"，命令不执行。
5. **结果回喂模型**：无论执行结果还是"被用户拒绝"，都作为工具调用的返回文本回到上下文，模型据此调整下一步（比如改为只给建议不动手）。

对照组：同样的命令在 `read-only` + `never` 下，第 4 步不弹窗，直接返回硬拒绝文案 *"writing is blocked by read-only sandbox; rejected by user approval settings"*——模型读到这句话自己绕道。**无人值守场景（CI）靠的就是这个：失败变成非零退出码，而不是一个永远等不到按键的提示框。**

## 四、新技术点四要素

### 1. Sandbox Mode（沙箱模式）

- **名字**：`SandboxMode`，Rust 枚举，定义在 `codex-rs/protocol/src/config_types.rs`；CLI 旗标 `--sandbox` / `-s`，配置项 `sandbox_mode`
- **作用**：规定命令在内核层的能力边界。**macOS 用 Apple Seatbelt 策略、Linux 用 bubblewrap 容器实现**（实现细节是阶段 3 的内容），不是提示词、不是正则过滤
- **参数**：三个取值 `read-only` / `workspace-write` / `danger-full-access`（阶段 2 逐个拆）
- **用法**：`codex --sandbox read-only`，或 `~/.codex/config.toml` 里 `sandbox_mode = "read-only"`

### 2. Approval Policy（审批策略）

- **名字**：`AskForApproval`，定义在 `codex-rs/protocol/src/protocol.rs`；CLI 旗标 `-a` / `--ask-for-approval`，配置项 `approval_policy`
- **作用**：规定"沙箱挡住时"的后续流程。它**不产生任何安全边界**，只决定人机交互的密度
- **参数**：CLI 上三个取值 `untrusted` / `on-request`（默认）/ `never`；配置文件里还有一种结构体形态 `granular`（阶段 4 细讲）
- **用法**：`codex -a never`（注意：仅交互式 `codex` 有这个旗标，`codex exec` 没有——阶段 5 讲）

## 五、关键顿悟

- **"会不会弹窗"和"安不安全"是两回事。** 弹窗密度由旋钮 2 控制，安全边界由旋钮 1 控制。觉得烦该调的是旋钮 2，不是放开旋钮 1。
- **approval 可以被模型绕过，sandbox 不能。** 提示词层面的"请小心"不是安全机制；`(deny default)` 的内核策略才是——写操作违反策略时返回 `EPERM`，与模型意图无关。
- **全网一半的教程把两者混为一谈**（包括把 approval 提示当成"沙箱生效"的证据）。学完本阶段你已经比它们强了。
