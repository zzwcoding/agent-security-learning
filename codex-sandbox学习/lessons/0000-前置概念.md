# 阶段 0：前置概念 —— 沙箱是什么，和 Codex 什么关系

> 开课前的背景问答。回答六个问题：沙箱是什么 / 这篇文档讲什么 / 为什么叫"Codex 沙箱" / 两者什么关系 / 为什么用 Codex 要读它 / 对 agent 开发有什么学习价值。

## 1. 沙箱（sandbox）是什么？

**一种由操作系统内核强制执行的能力限制机制**：让一个进程在"被削权的笼子"里运行——笼子外的资源（文件、网络、其他进程）它物理上够不到，越界访问直接在内核层失败（返回 `EPERM` 之类错误）。

关键点在"**谁执行限制**"：

| 限制方式 | 执行者 | 能被被限制者绕过吗 |
|---|---|---|
| 提示词里写"请不要删除文件" | 模型自觉 | 能（幻觉、注入、误解都会破防） |
| 代码里正则拦截"危险命令" | 应用层字符串匹配 | 能（命令写法无穷多，匹配不完） |
| **沙箱** | **操作系统内核** | **不能——它根本不知道笼子的存在，越界只是"失败"** |

沙箱不是新概念：Chrome 每个渲染进程都跑在沙箱里（这就是 Codex macOS 策略直接借鉴 Chromium `common.sb` 的原因），iOS 每个 App 也一样。它的用途永远是同一件事：**跑不完全可信的代码**。

## 2. 这篇文档讲什么？

讲 **Codex CLI 的权限系统**：它给 agent 执行的每条 shell 命令套上哪三种笼子（`read-only` / `workspace-write` / `danger-full-access`）、笼子挡不住时走什么审批流程、三大操作系统上分别用什么内核机制实现、以及日常/CI 场景怎么配。核心论点一句话：**沙箱（能做什么）和审批（想要更多时怎么办）是两个独立旋钮，别混。**

## 3 & 4. 为什么叫"Codex 沙箱"？两者什么关系？

**Codex CLI 是 OpenAI 出的终端编码 agent**——你在终端里用自然语言让它改代码，它自己读写文件、跑命令。

这里有个本质矛盾：agent 的价值恰恰来自"它能真动手"（执行 `npm install`、改源码、跑测试），但"能真动手"就意味着它也可能 `rm -rf`、把你的 SSH 密钥发到某个服务器、或者往 `.git/hooks` 里塞后门。而且威胁不只来自"模型犯傻"——**prompt injection** 让不可信内容（网页、issue、README）也能间接指挥它动手。

所以 Codex 在"模型"和"你的机器"之间砌了一层内核级的墙，这就是 Codex 沙箱。它不是独立产品，是 **Codex CLI 内部的一个子系统**：模型每次提议执行命令，Codex 不直接执行，而是把命令包进沙箱策略里再交给内核。关系一句话：

```
Codex = 会动手的 agent
沙箱 = 管住"动手"这件事的内核笼子
模型负责聪明，沙箱负责让聪明不越界
```

## 5. 为什么用 Codex 还要专门读这个文档？

因为这功能的**默认行为反直觉**，不读就会踩坑：

- **默认值不是常量**：同一个 repo 克隆到两个目录，一个可能是 `workspace-write`、另一个是 `read-only`——取决于你几周前在某个目录里回答过的一次信任提示。脚本里不显式传 `--sandbox`，行为就是抽奖。
- **旗标变动剧烈**：`--full-auto` 已被删除（教程还在推荐它的都过时了）；`on-failure` 只剩个别名， silently 变成了别的意思。
- **平台行为不一致**：Windows 上 `workspace-write` 会被**静默降级**为 `read-only`——不读文档你会以为 agent 出 bug 了。
- **配错的代价不对称**：配松了是安全事故（凭据外泄），配紧了是 agent 啥也干不了。文档教你按场景选到"刚好"的组合。

## 6. 对 agent 开发的学习价值（为什么这门课属于"安全评估"项目）

这篇文档表面是"工具使用说明"，实际是一个**生产级 agent 权限系统的设计案例**。可迁移的设计原则：

1. **纵深防御，不信模型自觉**：安全边界放在内核，不放在提示词。评估任何 agent 产品时第一问就是："它的限制是谁执行的？"——答案是"模型自己"的基本等于没有。
2. **能力与交互分离**：sandbox（能力）和 approval（交互）两个旋钮独立调。自己设计 agent 时，别把"要不要问用户"和"安不安全"耦合在一个开关里。
3. **默认关闭、失败闭合（fail-closed）**：网络默认关、Windows 没沙箱宁可降级也不假装安全、CI 无头模式默认 `never` 不弹窗。安全系统的默认值必须是"出错时倒向安全一侧"。
4. **攻击面思维的具体化**：保护 `.git` / `.agents` / `.codex` 不是洁癖——可写的 `.git/hooks` = 任意代码执行路径。做安全评估时就要这样追"一个可写文件能升级成什么"。
5. **只读模式的隐藏价值**：内核级 read-only 让"多个 agent 并行审同一个仓库"成为安全操作——这是多 agent 架构（如文中 Fusion council）的地基。
6. **可观测性配套**：`CODEX_SANDBOX_NETWORK_DISABLED` 环境变量让测试套件感知沙箱、`codex sandbox -- cmd` 让你实测策略。安全机制必须可被验证，否则只是声明。

一句话：**学它不是学一个 CLI 的旗标，是学"如何给一个能动手执行命令的 agent 套缰绳"的工业界参考答案。** 你做 agent 安全评估时，这些就是评估清单上的条目。
