## 2. 来龙去脉:决策演变七步

以下是本对话的完整推理链,每步标注:输入材料 → 结论 → 对路线的影响。

### 2.1 本体论讨论(两份本地字幕材料)

- **输入**:`[中配] 为什么Agentic系统需要本体论——Frank Coyle,UC Berkeley.en.srt`(Downloads 目录)+ `本体论 Ontology 的新瓶与旧酒.zh.srt`(架构达尔文播客,嘉宾:萧然/张毅)。
- **结论**:①Coyle 微观机制——LLM 是概率决策者,用本体 validator 卡在 agent 工具循环里裁决("Pydantic at the door, ontology at the ledger");②播客宏观形态——工业级 agent = 答案可追溯 + 过程可审计,Palantir 三创新(单企业范围/Action 一等公民/数字孪生),DDD 战术层与本体的建模同源但战略层不可混用。
- **对 soc-demo**:确认了"确定性闸门约束不可信 LLM"的设计哲学(M9);派生了 v2 设想(五张子图:检测/对手借 ATT&CK/资产/响应/经验,case_brief 注入,provenance/污点/写闸三件套 day-one)。

### 2.2 sharptoolbox(人月聊IT)方法论调研

- **输入**:[github.com/sharptoolbox](https://github.com/sharptoolbox),核心仓库 [ontology-driven-dev](https://github.com/sharptoolbox/ontology-driven-dev)(⭐195)。
- **结论**:七模型本体 YAML(M1对象/M2行为/M3规则/M5主体/M6流程/M7报表/MU UI)+ 机器可校验一致性门禁 + 运行时 Ontology Registry(行为注册成 function calling 工具,system prompt 注入语义,写操作只走行为工具)。"模型是唯一语义源"解决跨语言契约漂移。
- **对路线**:票面契约单一来源、行为级权限声明化、M12 规则库的模板参考。

### 2.3 学习顺序决策:v1 → v2(本体)→ v3(演化评测)

- **结论**:先做现 PRD 的 v1,再上本体 v2。理由:①v2 的价值必须靠 v1 基线证明(工具调用数下降);②schema 质量只能从痛点来(没有本体方法论,自顶向下是专家系统死路);③v1 教的 M9 安全工程更稀缺;④v2 落在既有 seam 上,是增量不是重写。风险对冲:5 件零成本种子(见 5.2)。
- **注**:转向 AgentSentry 后,此决策部分失效(见 5.4 去向表)。

### 2.4 OpenART 论文(环境演化红队评测)

- **输入**:[PaperWeekly 解读](https://mp.weixin.qq.com/s/gsUdlMjtloVhtvao5Y2O5A)、[arXiv 2608.00677](https://arxiv.org/abs/2608.00677)、[AI45Lab/OpenART](https://github.com/AI45Lab/OpenART)(⭐125)。
- **结论**:①任务不变、环境持续演化的红队评测:75 配置 pooled ASR 85%,五轮演化 42.9%→94.7%;②延迟传播:被污染状态中位在 23% 进度被读取、64% 处爆雷;③控制基座模型后 harness 身份仍解释 7.6% ASR 方差——**安全长在 harness 上**。对 soc-demo:静态 fixture 有系统性盲区;派生 v3 设计(部署-潜伏-引爆-归因闭环 + 攻击原语目录 + 审查门可达性 CI 不变量)。

### 2.5 dsh-redteam 对比 → 四象限与"评估 agent"设计

- **输入**:[dsh-redteam-model 介绍](https://mp.weixin.qq.com/s/-CVqW5ym6aIWzlf15F9wgA)、[SeaOf0/dsh-redteam-model](https://github.com/SeaOf0/dsh-redteam-model)(第三方,9 红队模式+15 插件,宿主为 [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness))。
- **结论**:AI for Security(目标=传统软件)× Security for AI(目标=agent)的四象限;dsh-redteam 在第一象限,soc-demo 在第四象限。设计了"针对 agent 安全的 agent"三姿态(审计/监测/红队)与统一安全本体(L1 元模型:Asset/Surface/Weakness/Technique/Control/Finding/Trace + L2 双域词汇 ATT&CK/CAPEC/CWE + ATLAS/OWASP/ASB + 桥接边)。传统红队框架 vs agent 红队框架的承重墙差异:执行模型(请求-响应→回合制状态机)、目标模型(资产清单→能力图谱)、判定器(签名→语义+统计)、新增自保护层(目标输出=指令级输入)。

## 4. 核心推理依据(挑战请从这里入手)

### 4.1 M9 ≈ 单系统 AgentSentry

`soc-demo/specs/modules.md` M9 卡:verifyTicket 中间件(一切工具调用先过闸)、审批卡 REST + ApprovalToken(TTL 900s 一次性)、gateway `/internal/mint` 与 `/proxy/llm/*`(凭证代理,agent 不持真 key)、guards `/scan/injection` + `/pii/anonymize`、openfga FGA、M2 审计 + used_tokens 焚毁表、fixtures/tickets 跨语言票面契约。对照 AgentSentry 四域(资产/事件/权限/防护):权限+防护两域基本等价;事件域有单系统版(M2 AuditEntry);**资产域空白**(worker 是代码内子模块,不是被治理对象)——即"泛化"的方向明确:同样的闸,服务对象从"自己的 worker"变成"全企业任意 agent"。

### 4.2 12 个应用场景 × 零件覆盖(分析结论)

间接注入/工具投毒/DLP 外泄/高危操作确认/越权/委托链放大/记忆投毒潜伏/凭据泄漏/IM 渠道滥用/资源滥用/事后取证/离职撤权。结论:9/12 的零件在 v1 路线图已排产(guards=M9、审批=铸票、越权=openfga+票、供应链=M12、预算=M3 budget);需新造的是身份治理层(场景 9/11/12)与接入面。**所有场景的拦截都落在三个收口(模型调用/工具调用/出网)+ 一本身份账,没有一个是靠"教 agent 别上当"**——这是"接入即防护"的产品机理。

### 4.3 本体论的角色演进(三段)

①soc-demo v2:知识供给(检索子图喂 LLM);②评估 agent:分类学(统一安全本体 L1/L2);③安防网关(新):**治理底座**——白皮书七原则用本体语言重读,每条都是可机检的图结构(Agent 一等公民=节点类型;长期/运行时身份=类型分离+派生边;委托链=边链+审计;Policy×Context=对类型化事实的查询)。三个不变量建议第一天编码:委托链无环、权限沿链单调递减、外部渠道到 L2 能力必过审批门(可达性查询)。L1 元模型最终三图归一:防守图(soc-demo)/攻击图(评测线)/治理图(网关)。

### 4.4 生态空白的证据

GitHub 实查(2026-09-08):运行时防护有 llm-guard/NeMo-Guardrails/vigil-llm/Meta LlamaFirewall(论文 [arXiv 2505.03574](https://arxiv.org/abs/2505.03574),官方仓库未核实到);网关有 litellm/envoy ai-gateway;策略引擎有 openfga/spicedb/cedar/opa(通用,不知 agent 为何物);供应链有 cisco mcp-scanner。搜"agent authorization"仅 ⭐1 萌芽项目。**结论:有零件、没产品、身份层全空白。**

### 4.5 风险与反方观点(评估时请独立验证)

- 商业竞品密集(字节 AgentSentry、Invariant、ProtectAI、腾讯等),开源可自部署+身份治理层是留白,但窗口期未知;
- "所有 agent 都接入"在企业现实里是推广问题,不是技术问题——MVP 必须有 30 秒可感知的拦截演示;
- litellm(⭐58k)已有 guardrails 挂钩,基于它扩展 vs 自写薄代理,是真实的路线分叉(见开放问题 8);
- 双语言栈(TS+Py)对开源贡献者是门槛。

### 9.2 白皮书七原则 × 治理不变量
